# /benchmark — сначала мировой опыт, потом код

Владелец запретил изобретать кастом без разбора эталонов: точечные фиксы дали «визуальный мусор и тупики». Этот скилл — обязательная первая ступень продуктовой задачи.

## Аргумент

Продуктовая задача/симптом, например: «редактирование отправленного КП», «напоминания об оплате», «онбординг продавца».

## Шаг 1. Выбрать эталоны под домен

| Домен задачи | Эталоны |
|---|---|
| Сделки, пайплайн, CRM | Odoo CRM/Sales, Bitrix24, Salesforce |
| КП/CPQ, прайсинг, скидки | Salesforce CPQ, Odoo Sales (quotation), PandaDoc, Qwilr |
| Документы, подписание, шаринг | PandaDoc, DocuSign, Qwilr |
| Счета, оплаты, просрочка | Stripe Invoicing, Odoo Accounting, QuickBooks |
| Заказ → поставка → приёмка | Odoo (SO → Delivery → Invoice), SAP (приёмка получателем) |
| Каталог/PIM, маркетплейс | Odoo Inventory, Alibaba/B2B-маркетплейсы |
| Уведомления, инбокс задач | Odoo Activities, Linear/Jira inbox |

Минимум 2–3 эталона. Уже написанные разборы искать в `Docs/dev/specs/spec-*.md` И в `Docs/old/specs/spec-*.md` — закрытая спека остаётся действующим ресерчем, бенчмарк в ней не протухает вместе с планом волн. Не переделывать сделанное.

## Шаг 2. Собрать, как решает каждый эталон

WebSearch/WebFetch по документации и скриншотам эталонов. Для каждого зафиксировать:

- **Название паттерна** (например: Odoo smart-buttons, PandaDoc public link + accept, Stripe computed overdue).
- Путь пользователя по шагам (кто нажимает, что видит, что происходит).
- Какие состояния/статусы существуют и кто их меняет.
- Чего эталон НЕ делает (отсутствие фичи — тоже решение).

## Шаг 3. Gap-анализ против нашего продукта

Посмотреть текущее поведение в коде/UI (при необходимости — `/ux-review` текущего флоу). Таблица:

| Аспект | Эталон (паттерн) | У нас сейчас | Gap | Решение |
|---|---|---|---|---|

## Шаг 4. Вердикт

- **Применяем именованный паттерн X** — и какие волны кода это даёт.
- Кастом допустим ТОЛЬКО если эталона нет — это проговаривается владельцу явно, отдельной строкой.
- Никаких новых блокировок/гейтов/SLA без явного запроса владельца (PRODUCT RULE 2).

Результат — короткий разбор владельцу (паттерн + gap-таблица + предложение волны). Код — только после утверждения картины. Если разбор существенный — сохранить в `Docs/dev/specs/spec-<тема>-<дата>.md`.
