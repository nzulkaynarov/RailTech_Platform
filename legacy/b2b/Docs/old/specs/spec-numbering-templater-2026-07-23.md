## ЧАСТЬ A — Нумерация документов 2.0

### A.0 Что сейчас (симптом)
`crm/services/numbering.py`: формат ЖЁСТКО зашит `{prefix}-{label}-{year}-{NNNNN}` (5 цифр, календарный год, разделитель «-»). Настраивается ТОЛЬКО строка-префикс (`CompanySettings.doc_number_prefix`). Нельзя менять: паддинг, разделитель, наличие/формат даты (год/месяц), период сброса, стартовый номер, суффикс, per-type-префикс. Ядро (race-safe `DocumentSequence` + `select_for_update`, no-gap) — ХОРОШЕЕ, менять не надо; проблема — в НЕгибком формате.

### A.1 Benchmark (Odoo ir.sequence)
Конфигурируемая схема: **Префикс** + **Суффикс** (с токенами даты `%(year)s`/`%(month)s`/`%(day)s`), **Паддинг** (ширина, напр. 00001), **Шаг** (инкремент), **Следующий номер** (старт), **Период сброса** через date_range (никогда/год/месяц), **standard vs no-gap** (no-gap — бутылочное горло под нагрузкой, только если требует регулятор).

### A.2 Целевая картина
**Модель `DocumentNumberingScheme`** (per company; опц. per-doc-type override) с полями:
- `pattern` (маска с токенами): `{prefix}`, `{type}` (код типа: КП/CT/INV/ACT), `{YYYY}`/`{YY}`, `{MM}`, `{seq}` — напр. `{prefix}-{type}-{YYYY}-{seq}` (текущий дефолт) или `{type}/{YYYY}/{seq}` или `{prefix}{seq}`.
- `padding` (ширина seq, дефолт 5), `separator` (для дефолтной сборки), `reset_period` (`never`/`yearly`/`monthly`, дефолт yearly), `start_value` (дефолт 0).
- (опц.) per-type-переопределение `type_code`/паттерна — если компания хочет разный формат для КП vs инвойса.
- Ядро остаётся: `DocumentSequence` scoped по (company, doc_type, **period-key** — год ИЛИ год-месяц в зависимости от reset_period), no-gap.
- **GLOBAL-UNIQUE safety сохраняется**: как сейчас — свой счётчик только у компании с непустым брендирующим элементом (prefix); prefix-less → платформенный счётчик.

**Backend**: `numbering.py` собирает номер из `pattern` схемы (парсер токенов), а не из хардкода. `next_document_number(doc_type, company)` читает схему компании (или дефолтную) + период-ключ по reset_period.

**Frontend**: секция «Нумерация документов» (Settings) → редактор схемы: выбор паттерна (пресеты + кастом), паддинг, период сброса, стартовый номер, **live-превью 3 типов** (уже есть база превью S5) — «ACME-КП-2026-00001» / «КП/2026/00001» и т.д. Меняется вживую.

### A.3 Ограничения (не ломать)
Изменение маски НЕ должно ретроспективно ломать уже выпущенные номера (они снапшот в `number`-поле). Смена reset_period/паттерна применяется к БУДУЩИМ номерам. Уникальность `number` в БД сохраняется. Миграция: `DocumentNumberingScheme` + бэкфилл дефолтной схемой = текущий формат (нулевой визуальный дифф для существующих компаний).

## ЧАСТЬ B — Шаблонизатор «правильный подход»

### B.0 Что сейчас (симптомы владельца)
1. **Дублирование реквизитов**: тело образца = `<p>Настоящим {{company.name}} (ИНН {{company.inn}}) гарантирует…</p>`, а брендовая обёртка `_document_base.html` УЖЕ печатает шапку (лого + название + ИНН + адрес) и футер (`footer_text`). → название/ИНН компании печатаются ДВАЖДЫ (в шапке-колонтитуле и в теле письма).
2. **Топорный редактор**: `DocumentTemplatesSettings` — голая HTML-`<textarea>` + чипы-плейсхолдеры. Предпросмотр показывает ТОЛЬКО тело (`rendered_html`), БЕЗ брендовой обёртки → пользователь не видит реальный документ и потому вставляет реквизиты руками (отсюда дубль).

### B.1 Benchmark (PandaDoc/DocuSign)
- **Letterhead (шапка/футер) = статичный брендинг**, настраивается ОДИН раз (тема/бренд), печатается автоматически на всех страницах. **Тело = только уникальный контент документа.**
- **Переменные/роли для динамики** (контрагент, суммы) — НЕ перепечатывают реквизиты своей компании (они в letterhead).
- **Темы** — единый стиль (цвета/шрифты) поверх тела, не хардкод в каждом шаблоне.
- Ключевой принцип: **не дублировать реквизиты в теле — они живут в letterhead/переменных.**

### B.2 Целевая картина
1. **Разделение letterhead ↔ тело (корень дубля):**
   - Letterhead (шапка с лого/названием/ИНН + футер с реквизитами/подписантом) — УЖЕ есть через `CompanyDocumentProfile` + `_document_base.html`. Оставляем как единый источник бренда.
   - **Тело шаблона = ТОЛЬКО уникальный текст письма** (без повторения названия/ИНН своей компании). Плейсхолдеры остаются для ДИНАМИКИ (контрагент, сделка, суммы, дата) и подписанта — но НЕ для своих реквизитов.
   - **Почистить 5 образцов**: убрать из тела `{{company.name}} (ИНН {{company.inn}})` там, где это дубль шапки; оставить осмысленный текст письма. (Data-migration обновит sample-тела.)
2. **Предпросмотр = ПОЛНЫЙ брендовый документ** (шапка + тело + футер), а не голое тело. Пользователь видит реальный вывод (как в PandaDoc) → перестаёт дублировать реквизиты руками. Реюз `document_brand_context` + `_document_base.html` в preview-эндпоинте (сейчас preview рендерит только тело).
3. **Правильный редактор** (вместо голой textarea) — варианты (вопрос владельцу):
   - **(рек.) Rich-text toolbar** над существующим HTML+санитайзером: жирный/курсив/списки/заголовки/таблица/ссылка — на self-contained lib (напр. TipTap/ProseMirror или лёгкий contentEditable-тулбар), выдаёт чистый HTML → тот же allowlist-санитайзер. Плейсхолдеры вставляются как раньше (чипы). Без тяжёлых зависимостей вне self-contained.
   - Альтернатива: блочный редактор (заголовок/абзац/таблица-блоки) — мощнее, но дольше.
   - Минимум: оставить HTML, но добавить панель форматирования + подсказку «шапка и реквизиты добавляются автоматически — не дублируйте их здесь» + полный предпросмотр (закрывает главную боль дубля даже без WYSIWYG).
4. **Каталог плейсхолдеров**: разделить на «Динамика» (контрагент/сделка/суммы/дата — вставлять в тело) и «Реквизиты компании» (пометить «уже в шапке — обычно не нужны в теле»).

### B.3 Ограничения (не ломать)
SSTI-safe санитайзер/белый список (ревью A4/F2-3) — ЛЮБОЙ новый редактор выдаёт HTML, проходящий тот же `sanitize_template_html`. Снапшот `body_html_snapshot`/`rendered_html` + `brand_snapshot` (иммутабельность ISSUED) — не трогаем. Существующие выпущенные документы не меняются.

## Волны исполнения (мультиагенты; guardrails PRODUCT+IRON RULES; DoD глазами)

| Волна | Задача |
|---|---|
| **N1 — нумерация backend** | Модель `DocumentNumberingScheme` + миграция + бэкфилл дефолтом (текущий формат); парсер маски в `numbering.py`; period-key по reset_period; сохранить global-unique+no-gap; тесты (маска/паддинг/reset/гонка/бэкфилл-совместимость) |
| **N2 — нумерация frontend** | Редактор схемы в «Нумерация» (пресеты+кастом маска, паддинг, reset, старт) + live-превью 3 типов |
| **T1 — letterhead/тело + предпросмотр** | Preview-эндпоинт рендерит ПОЛНЫЙ брендовый документ (шапка+тело+футер); почистить 5 sample-тел (data-migration, убрать дубль реквизитов); каталог плейсхолдеров «Динамика / Реквизиты(в шапке)» |
| **T2 — правильный редактор** | Rich-text toolbar (по решению владельца) поверх HTML+санитайзер, вставка плейсхолдеров, тот же allowlist; либо минимум (панель форматирования+подсказка) |
| **T3 — адверсариальное ревью** | Санитайзер нового редактора (SSTI/XSS), предпросмотр не течёт cost, миграция sample-тел |

_Порядок: A (N1→N2) и B (T1→T2→T3) независимы — можно параллельными треками. T1 (предпросмотр+чистка дубля) — самый быстрый и закрывает ГЛАВНУЮ боль владельца._

## Решения владельца (утверждено 2026-07-23)

**Спека УТВЕРЖДЕНА, рекомендации приняты:**
1. **Редактор → rich-text toolbar** (жирный/курсив/списки/заголовки/таблица/ссылка) поверх HTML+allowlist-санитайзера; вставка плейсхолдеров чипами.
2. **Нумерация → одна company-схема** с токенами на все типы (тип подставляется по коду; per-type-переопределение отложено).
3. **Период сброса → выбор never/yearly/monthly** (дефолт yearly). Убираем хардкод.
4. **Чистка образцов → ДА**: тело = только текст письма, реквизиты своей компании — из шапки (letterhead).
