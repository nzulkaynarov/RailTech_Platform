## 0. Что входит в раздел сегодня

## 1. Бенчмарк (PRODUCT RULE 1)

| Задача | Эталон | Как решено там | Как у нас |
|---|---|---|---|
| Реестр товаров продавца | **Akeneo PIM**, **Shopify Products** | ОДИН реестр, статус — фильтр/таб, серверный поиск и пагинация, bulk-actions | ДВА разных реестра (очередь и «каталог»), в одном нет поиска, в другом нет пагинации |
| Карточка | **Akeneo**, **Amazon Seller Central** | Полноэкранная страница, секции слева, индикатор полноты ВНУТРИ карточки | Sheet-шторка на 20 полей без индикатора полноты |
| Готовность к публикации | **Akeneo completeness** | Процент + список недостающего прямо в карточке, публикация открывается сама | Полнота есть, но только в СПИСКЕ; в форме её нет |
| Массовое наполнение | **Shopify CSV import**, **Akeneo import profiles**, **Coupa/Ariba CIF** | Пользователь САМ сопоставляет колонки своего прайса; профиль сохраняется; повторная загрузка обновляет | Жёсткие алиасы заголовков, маппинга нет, профилей нет |
| ИИ в наполнении | **Shopify Magic**, **Amazon «Generate listing»**, **Akeneo AI suggestions** | Панель предложений по каждому полю: принять / отклонить / править | Молчаливый патч драфта: описание и характеристики применяются, не показываясь |
| Классификация ТН ВЭД | **Avalara / Zonos** | Retrieval + выбор из справочника, пакетное подтверждение | Реализовано хорошо (T3/T4) — лучший кусок раздела |
| Дедупликация | **Akeneo / Salesforce dedupe** | Система предлагает, человек решает | Реализовано (N4) |
| Категории/таксономия | **Google Merchant Center**, **Odoo** | Категория — либо своя (продавец создаёт), либо навязанная площадкой + автоподбор | Навязана площадкой, создать нельзя, автоподбора нет (только текстовая подсказка) |
| Витрина покупателя | Любой маркетплейс | Серверная пагинация, фасеты | Первые 20 позиций без пагинации |

Вывод бенчмарка: **механики у нас есть почти все, а рабочего места — нет.** Раздел собран как
набор отдельных экранов вокруг одной сущности, а эталоны собирают его как один реестр + одну
карточку.

## 2. Тупики (сценарий упирается в стену)

### D1 — 🔴 Каталог обрывается на 20 позициях, и об этом никто не говорит
`ProductManagement.tsx:63` зовёт `useProducts(apiParams)` **без `fetchAll`** →
`catalogApi.getProducts` возвращает `response.data.results` первой страницы
(`catalogApi.ts:186-188`), а DRF режет на `PAGE_SIZE=20` (`core/settings/api.py:63`).
Дальше `applyListParams` пагинирует эти 20 строк клиентски, и `Pager` при `total <= pageSize`
**не рендерится вовсе** (`DataTable/index.tsx:117`).

Итог: и покупатель, и продавец видят ровно 20 товаров площадки. KPI «Всего позиций» показывает
20 (`ProductManagement.tsx:99`). Ни пагинации, ни намёка. Для сравнения — операторская
`AdminCatalogPage` грузит всё (`fetchAll: true`, `admin-catalog/index.tsx:26`): у платформы
инструмент полноценный, у продавца — обрезанный.

### D2 — 🔴 Импорт физически не умеет два из четырёх обязательных полей
Шаблон импорта (`sourcing/views_imports.py:341-354`) — 12 колонок: наименование, бренд, MPN,
ГОСТ, артикул поставщика, описание, ед.изм., цена, валюта, наличие, срок, мин. заказ.
Парсер (`sourcing/catalog_import.py:40-56`) знает ровно эти алиасы.

**Ни «Категория», ни «Код ТН ВЭД» в импорте не существуют.** А порог публикации
(`catalog/completeness.py:67-76`) требует для GENERAL_GOODS: имя + ед.изм. + категория + ТН ВЭД;
для ж/д — ещё идентичность и группу оборудования.

Сценарий владельца «залил прайс на 3 000 позиций» даёт **3 000 неопубликуемых черновиков**, каждый
надо открыть руками и дозаполнить два поля. Ошибок при этом не показывается — импорт рапортует
«Создано: 3000». Это главный тупик наполнения каталога.

Домен при импорте вообще угадывается по ключевым словам (`sourcing/tasks.py:25-48`), т.е. правится
только вручную позже.

### D3 — 🔴 Очередь без поиска, фильтров и пагинации
`NomenclatureQueuePage` не имеет ни `Toolbar`, ни `Pager`. Запрос —
`page_size: 200` (`catalogApi.ts:222`). Кандидатов больше 200 → остальные **не видны никак**.
Найти конкретную позицию в очереди из 200 строк нечем. Сортировка одна — по спросу, сменить нельзя.

### D4 — 🔴 ИИ пишет характеристики вслепую
`useProductForm.ts:129-137`: ответ ИИ мержится в `draft.specifications`. В форме
(`ProductFormSheet.tsx`) **поля характеристик НЕТ** — ни одного. Пользователь видит тост
«применено», сохраняет и обнаруживает 8 придуманных строк в публичной карточке
(`ProductDetail.tsx:176-190`). Убрать или поправить их нельзя нигде в интерфейсе.

По сути: единственный путь записи `specifications` — ИИ, а единственный путь чтения — витрина.
Ручного ввода характеристик в продукте не существует.

### D5 — 🟠 Оплаченный ИИ-выбор кода ТН ВЭД выбрасывается
`catalog/ai_enrich.py:202-212` возвращает `hs_code` (выбранный ИЗ справочника и
детерминированно сверенный, `_accepted_hs_code`) и `hs_candidates`. Тип на клиенте
(`catalogApi.ts:430-434`) этих полей **не содержит**, `runEnrich` их не применяет.

Продавец платит за enrich, получает код — и не видит его; чтобы получить тот же код, жмёт вторую
платную кнопку «Подобрать коды с ИИ». Две оплаты за одну работу.

### D6 — 🟠 Категорию ИИ подсказывает текстом, применить нечем
`suggested_category_hint` печатается строкой (`ProductFormSheet.tsx:100-104`), а выбрать надо
руками в плоском `Select` **всех** категорий без поиска и без фильтра по домену
(`ProductFormSheet.tsx:133-145`). Сейчас в базе 21 категория — терпимо; при сотне это тупик.
(Открытый пункт из хендоффа 04-08 — не закрыт.)

### D7 — 🔴 Нужной категории/группы нет → публикация невозможна, и сделать нечего
`CategoriesPage` и `EquipmentGroupsPage` — чистое чтение: ни создать, ни переименовать, ни
предложить. При этом подпись страницы обещает «**Управление** деревом категорий номенклатуры»
(`ru.json → pages.categories.description`). Продавец, у которого товар не ложится ни в одну
категорию, не может ни опубликовать карточку, ни попросить категорию — обращения к платформе
из этого места нет.

### D8 — 🟡 Мёртвые affordance'ы
`EquipmentGroupsPage.tsx:25` — карточка с `cursor-pointer hover:shadow-md` и шевроном `>`,
**без `onClick`**. Выглядит кликабельной, не делает ничего. Категории (`CategoriesPage`) —
бейджи детей, тоже некликабельные: перейти «в товары этой категории» нельзя.

### D9 — 🟠 Кнопки показываются тем, кому бэкенд откажет
`ProductManagement.tsx:50`: `canManageCatalog = activeStatus === 'SELLER'` — право выведено из
роли, а не из `catalog.manage`. Бэкенд после N3 действительно проверяет пермишен
(`core/permissions.py:93-121`, `catalog/publishing.py:22-42`). Ни одна страница раздела не
использует `useHasCompanyPermission` (проверено grep'ом: `catalog.manage` встречается во фронте
только в `navigation.tsx`). «Наблюдатель» в контексте продавца видит «Добавить товар»,
«Опубликовать», «Объединить» → получает 403 тостом. ADR-0005 требует **скрывать**, а не ловить
отказ.

### D10 — 🟠 Архив — чёрная дыра
Слитый дубль уходит в `ARCHIVED` (`catalog/merging.py:83`) и исчезает из обеих вкладок очереди
(они знают только DRAFT и PUBLISHED, `NomenclatureQueuePage.tsx:54`) и из «Каталога» продавца.
Посмотреть архив, отменить слияние или восстановить карточку нельзя. Слияние необратимо и
непроверяемо — при том, что диалог обещает «спрос и ссылки переедут».

### D11 — 🟠 Валюта оффера игнорируется при выводе
`ProductManagement.tsx:252` и `ProductDetail.tsx:258` печатают `formatMoney(product.base_price,
'UZS')` — **валюта захардкожена**. Оффер имеет собственную `currency`
(`SupplierOffer.currency`), и форма позволяет выбрать USD. Оффер в USD будет напечатан как сумы.
В блоке «Предложения поставщиков» валюта берётся правильно (`ProductDetail.tsx:319`) — то есть
на одной странице два разных поведения.

### D12 — 🟠 «Каталог» продавца — это не его каталог
Страница показывает все PUBLISHED площадки + свои черновики (`catalog/views/products.py:100-110`),
без колонки владельца и без фильтра «мои». Подзаголовок для продавца — «Товары одобренных
производителей-партнёров» (`ru.json → productManagement.subtitle.seller`) — формулировка из
модели, которой больше нет. Продавец не понимает, что здесь его, а что чужое; цена у чужих строк
пустая (её срезает `_CostGateMixin`), и это выглядит как «цена не заполнена», а не «не ваше».

### D13 — 🟡 Мобильный экран каталога
`ProductManagement` рендерит сырую `<Table>` на 8 колонок (`:199-295`). Конвенция проекта —
`ResponsiveDataTable` с карточным фолбэком (её уже применили в очереди, N4). На телефоне
таблица уезжает горизонтально.

### D14 — 🟡 Три «Номенклатуры» и два «Каталога» в одном меню
Раздел = «Номенклатура», первый пункт в нём = «Номенклатура», а страница «Каталог» для продавца
озаглавлена «Номенклатура» (`productManagement.title.seller`). При этом пункт «Каталог» есть и
в разделе, и верхнего уровня (для покупательской стороны) — у компании, которая и покупает, и
продаёт, в меню **два одинаковых пункта «Каталог»**.

### D15 — 🟡 Из карточки нельзя ничего сделать
`ProductDetail` для владельца не имеет ни «Редактировать», ни «Опубликовать», ни «Снять с
публикации». Кнопка «Открыть» на вкладке «Опубликовано» ведёт именно туда — то есть в тупик:
чтобы поправить, надо вернуться в список и нажать «Дополнить».

### D16 — 🟡 Нет снятия с публикации и удаления
У оператора удаление есть (`admin-catalog/index.tsx:123-132`), у продавца — нет ни удаления, ни
архивации, ни возврата в черновик. Ошибочно опубликованная карточка остаётся в каталоге навсегда.

### D17 — 🟡 Медиа только после сохранения
`ProductFormSheet.tsx:359-363`: «фото и документы можно добавить после создания». Двухшаговость,
которой нет ни у Shopify, ни у Akeneo (там медиа — часть черновика).

### Захардкожено (нарушает Rule 2 / вводит в заблуждение)

1. **Валюта вывода `'UZS'`** — `ProductManagement.tsx:252`, `ProductDetail.tsx:258`. Реальный
   баг для оффера в USD.
2. **`stock_status` и `base_price` товара = ПЕРВЫЙ оффер** (`serializers.py:335-351`) — у товара
   с несколькими продавцами покупатель видит наличие произвольного из них.
3. **Fallback «Под заказ»** для товара без оффера — `ProductManagement.tsx:325-331`: покупателю
   обещают доступность там, где предложения нет вовсе.
4. **Цепочка тернарников по кодам наличия** в трёх местах (`ProductManagement.tsx:259, 325`,
   `ProductDetail.tsx:89`): `IN_STOCK/ON_ORDER/EXPECTED`, всё остальное → «Неактивен».
   Справочный `OUT_OF_STOCK` печатается как «Неактивен».
5. **`base_price: "0"`** как значение-заглушка при отсутствии оффера (`serializers.py:347-351`)
   вместо `null`.
6. **Права через роль**: `canManageCatalog / showPrices = activeStatus === 'SELLER'`
   (`ProductManagement.tsx:49-50`, `ProductDetail.tsx:34-35`).
7. **Режим отображения по роли**: `viewMode = activeStatus === 'BUYER' ? 'grid' : 'list'`
   (`ProductManagement.tsx:44`) — выбор пользователя не запоминается.
8. **Порог полноты по домену** — в коде (`completeness.py:67-76`). Это осознанно и правильно
   (Rule 1: не в БД, но и не «магическое число»), фиксирую как принятое решение, а не долг.

## 5. Целевая логика (redesign)

### 5.1. Информационная архитектура: 6 пунктов → 3

```
Товары                     (side: sell)
├── Мои товары             ← ЕДИНЫЙ реестр: табы Кандидаты / Черновики / Опубликованные / Архив
├── Загрузка прайса        ← импорт + история загрузок
└── Справочники            ← табы: ТН ВЭД · Категории · Группы оборудования (read-only + «предложить»)

Каталог площадки           (side: buy) — витрина, серверная пагинация, фасеты
```

Никаких «Номенклатур» в трёх смыслах. Раздел называется по объекту («Товары»), витрина
покупателя — единственный «Каталог».

### 5.2. Один реестр вместо двух

Табы = статус (`DRAFT` дополнительно делится на «Кандидаты из заявок» — те, у кого есть
`source_deal`/`demand_count` — и «Черновики»). Обязательно:
- серверный поиск (`?search=` уже есть) + фильтры домен/категория/бренд/готовность;
- **серверная пагинация** (`page_size` уже поддержан, `core/pagination.py`);
- сортировка: спрос ↔ полнота ↔ имя ↔ дата;
- колонки: Позиция (имя + MPN + бренд) · Готовность · Спрос · Цена/наличие (своё) · Действия;
- bulk: опубликовать · дополнить ИИ · сменить категорию · архивировать;
- `ResponsiveDataTable` (мобильный фолбэк).

Панели «дубли» / «переклассификация» / «покрытие» остаются, но как сворачиваемые баннеры над
таблицей, а не как три карточки под ней (сейчас они уезжают за экран при непустом списке).

### 5.3. Карточка = страница, а не шторка

Слева — прогресс полноты со списком недостающего (каждый пункт — якорь к своей секции). Секции:
1. **Основное** — имя, описание, бренд, MPN, ГОСТ
2. **Классификация** — домен, категория (комбобокс с поиском, отфильтрованный по домену), группы
   оборудования (дерево с поиском), ТН ВЭД (уже хороший компонент)
3. **Характеристики** — таблица ключ/значение с добавлением, правкой, удалением ⟵ закрывает D4
4. **Медиа** — доступно с первого шага (черновик создаётся при первом сохранении автоматически)
5. **Коммерция** — цена, валюта, наличие, склад, сроки, MOQ, срок действия, «активен»
6. **Действия** — опубликовать / снять с публикации / архивировать / объединить с дублем

Кнопки действий — по `useHasCompanyPermission('catalog.manage' | 'catalog.publish')`, скрыты, а
не отключены. `ProductDetail` становится режимом просмотра этой же страницы (для покупателя и
для чужих карточек).

### 5.4. ИИ: «предложение по каждому полю», а не молчаливый патч

Одна панель **«Дополнить с ИИ»** в карточке, отдающая diff по полям:

| Поле | Было | Предложение | ✔ |
|---|---|---|---|
| Описание | — | «Композитная тормозная колодка…» | ☑ |
| Категория | — | Тормозное оборудование → **выбрана** (сопоставлено с id) | ☑ |
| Код ТН ВЭД | — | 8607 19 100 0 — из справочника | ☑ |
| Ед. изм. | — | шт | ☑ |
| Характеристики | 0 | 6 строк (раскрыть) | ☑ |

Применяется только отмеченное. Это закрывает D4, D5, D6 разом и делает enrich честным: продавец
видит, за что заплатил. Эталон — Akeneo AI suggestions / Shopify Magic / Amazon Generate listing.

Бэкенд уже отдаёт `hs_code` и `hs_candidates`; добавить в `enrich_product` `uom_code` (выбор из
справочника, не генерация) и `category_id` (**выбор** из списка кандидатов-категорий, переданных
в промпт — не изобретение id, Rule 1 соблюдён).

### 5.5. Импорт: любой прайс, а не только наш шаблон

Три шага вместо «скачай шаблон — попади в него»:
1. **Файл** — xlsx/csv/pdf/фото. Для pdf/фото переиспользуется уже работающий экстрактор
   (`sourcing/services_ai_extract.py`, тот же, что вытаскивает позиции из заявки).
2. **Сопоставление колонок** — ИИ предлагает маппинг «ваша колонка → поле карточки», человек
   правит выпадающими списками; маппинг сохраняется как профиль поставщика (эталон: Shopify CSV
   mapping, Akeneo import profiles).
3. **Проверка и загрузка** — текущий dry-run остаётся, но отчёт добавляет строку
   «**будет неопубликуемо: N** (нет категории / нет ТН ВЭД)» + кнопку «дополнить ИИ пакетом».

Плюс расширить набор колонок: категория, ТН ВЭД, домен, группы оборудования, ссылка на фото.
Один шаблон вместо двух (`catalog/products/export-template/` и `sourcing/catalog-template/`).

### 5.6. Пакетное дообогащение

Выделил N черновиков → «Дополнить с ИИ» → таблица предложений по всем полям (сейчас так уже
работает подбор ТН ВЭД, `hs_classify` + `hs-apply` — расширяем его на категорию, ед. изм.,
описание и характеристики). Эталон — Avalara bulk classification; механика у нас уже обкатана.

### 5.7. Категории: перестать быть тупиком
Минимум — кнопка «Предложить категорию» из формы (создаёт заявку оператору + позволяет
опубликоваться с временной «Прочее»). Максимум (решение владельца) — разрешить продавцу своё
дерево поверх платформенного, как Google Merchant Center: свой `product_type` + обязательный
маппинг на категорию площадки.
