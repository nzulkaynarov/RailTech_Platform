Повод: наблюдения владельца — «категория и группа заблокированы, хардкод, костыли, тупики;
пройтись по ролям». Метод: код-аудит (2 независимых прохода), живой прогон глазами под тремя
ролями (продавец / покупатель / оператор) на локальном стенде, сверка данных прода.

## 1. Вердикт

Механика волн A–D и T1–T4 (кандидаты, полнота, публикация, ТН ВЭД) работает, но направление
не доведено до целостного продукта: **таксономия платформы пуста и наполнять её некому по
процессу**, у форм есть стирающие данные дефекты, публикация обходится в обход порога полноты,
а слой прав «на бумаге» (`catalog.*`) не совпадает со слоем прав «в бою» (membership).

## 2. Корень «заблокированных» селектов — пустые справочники без владельца процесса

Факт (прод): `Category = 0`, `EquipmentGroup = 0`, `Manufacturer = 0`. Локально: 1 / 0 / 0.

- Категория обязательна для публикации ЛЮБОГО домена (`completeness.py`), группа обязательна
  для сохранения ж/д-карточки (`Product.clean()` + форма). Писать в оба справочника может
  только платформа (`IsPlatformAdmin`), React-страницы `#admin-categories` /
  `#admin-equipment-groups` есть и работают (проверено глазами) — **но никто не наполнил», и
  продавец упирается в «No data» внутри обязательного поля со звёздочкой (скрин d04).
- Бренды хуже: у `Manufacturer` **нет ни одной admin-страницы и ни одного write-эндпоинта** —
  только Unfold (инженерный). При этом Excel-импорт продавца молча СОЗДАЁТ бренды свободным
  текстом (`sourcing/catalog_import.py`) — то есть тенант наполняет глобальный справочник как
  побочный эффект, а через форму не может выбрать ничего.
- Справочник доменов задвоен: миграция сеет `GENERAL`, dev-seed — `GENERAL_GOODS`; оба активны,
  оба видны пользователю в селекте («Общие промышленные товары» и «Общие товары»), а
  `completeness.py` знает только `GENERAL_GOODS`. Все 10 локальных карточек имеют
  `domain_type = NULL`: кандидаты из строк КП рождаются вообще без домена.

Бенчмарк:
- **Amazon browse tree / Odoo категории**: таксономия платформенная, продавец её НЕ создаёт —
  но платформа поставляет её заполненной с первого дня. Пустая таксономия — дефект данных, не
  повод давать продавцу права на неё.
- **Odoo «create on the fly» / Amazon brand**: бренд — нормализуемый ввод продавца
  (автокомплит + создание при отсутствии), не закрытый справочник. Наш импорт уже так делает —
  форма должна уметь то же самое тем же нормализатором (`name__iexact`).
- **Канон этого же репо (ТН ВЭД)**: «пустой справочник не блокирует работу». Группы
  оборудования при пустом справочнике должны деградировать так же (требование выключается),
  а не запирать сохранение карточки.

## 3. Блокеры в коде (подтверждены построчно)

1. **«Открыть» опубликованную карточку — тупик.** `onNavigate('product_detail/<id>')` — такого
   id нет в реестре страниц → молчаливый отскок в #dashboard (подтверждено живьём). Вся
   вкладка «Опубликованные» непроходима насквозь. Чинится передачей параметра как у
   `onProductClick`.
2. **Редактирование из очереди СТИРАЕТ описание.** Форма сидит на строке СПИСКА, а
   `ProductListSerializer` не отдаёт `description` → PATCH шлёт `description: ""`. Молчаливая
   потеря данных при каждом «Дополнить».
3. **…и СТИРАЕТ группы оборудования.** Тот же корень: списочный сериализатор не отдаёт
   `equipment_groups` → у ж/д-карточки с заполненными группами форма требует выбрать их заново
   вслепую, у остальных — молча очищает M2M. (Форма обязана добирать ПОЛНУЮ карточку по id.)
4. **Порог полноты обходится.** `status` — записываемое поле сериализатора, и селект статуса
   (включая «Опубликован») показан продавцу прямо в форме → публикация мимо
   `publish_product()` и мимо полноты. Akeneo-канон «порог считается, а не назначается»
   объявлен в докстринге и опровергнут собственной формой. Чинить с двух сторон: `status` →
   read-only (смена только сервисом, Rule 8), селект статуса убрать у продавца.

## 4. Роли: заявленный слой прав не совпадает с действующим

Матрица «кто что может» (из кода, проверено обоими проходами):

| Способность | Аноним | Покупатель | Продавец (член компании) | Оператор | Superuser |
|---|---|---|---|---|---|
| Видеть PUBLISHED | ✔ | ✔ | ✔ | ✔ всё | ✔ |
| Видеть свои DRAFT | — | ✔ своей компании | ✔ | ✔ все | ✔ |
| Создать/править/удалить карточку | — | — | ✔ (только членство!) | ✔ | ✔ |
| Публиковать | — | — | ✔ (членство + полнота; обход п.3.4) | ✔ | ✔ + emergency |
| Категории/группы (запись) | — | — | — | ✔ любой суб-роли | ✔ |
| Бренды | — | — | побочно через импорт | ✖ нет UI | ✔ Unfold |
| ТН ВЭД инструменты | — | ✔(!) | ✔ | ✔ | ✔ |

Расхождения:
- **`catalog.manage`/`catalog.publish` не проверяются нигде на бэке** — только прячут пункт
  меню. Продавец-«Наблюдатель» не видит «Номенклатуру», но по прямому API создаёт, правит и
  публикует. Два слоя авторизации, кодовый — декоративный. По Odoo-канону (группы прав
  сквозные UI+сервер): либо enforce в сервисах, либо честно убрать из гейта.
- **Карточки, созданные оператором, БЕЗ владельца** (`owner_company = NULL`, на локале таких
  5): продавец никогда не сможет их взять в работу, `can_manage` вечно False. Оператору нужен
  выбор компании-владельца при создании (SAP: материал всегда в орг-области).
- **Любая суб-роль оператора (даже SUPPORT «только просмотр») может удалять товары и
  перекраивать дерево категорий** — каталожные вьюхи не под `OperatorScoped`, кода
  `catalog.*` в OperatorPermission нет (дыра ADR-0004).
- **`hs_lookup`/`hs_classify` (платные LLM-вызовы) без entitlement-гейта** — в отличие от
  enrich на той же странице; доступны в т.ч. покупателю по прямому API.
- Покупатель в UI видит ровно то, что должен (каталог published, без цен/офферов), «Номенклатура»
  и «Справочник ТН ВЭД» скрыты и по прямому хэшу отбрасывают — корректно.
- **Вопрос владельцу (продуктовый):** сейчас «Номенклатура» скрыта до KYC L2. Amazon позволяет
  ГОТОВИТЬ листинги до завершения верификации (продавать — нет). Разрешить наполнение каталога
  до KYC, оставив публикацию/продажу за L2?

## 5. Major (тоже подтверждены)

- **Пагинация**: очередь запрашивает `page_size=200`, но DRF-конфиг не имеет
  `page_size_query_param` → всегда 20 строк, пейджера нет. 21-й кандидат недостижим. То же у
  worklist переклассификации.
- **Смерженный бэкенд без UI**: `merge` (слияние дублей) и `coverage` (метрика покрытия —
  «северная звезда» всей волны) не вызываются ни с одной страницы.
- **Тосты глотают причины**: publish/classify/save показывают «не удалось» без кода
  (`PRODUCT_INCOMPLETE:…`, `AI_DAILY_CAP_REACHED`, 400 валидации); кодов нет и в `apiErrors`.
- **Кнопка «Опубликовать выбранные» появляется и на вкладке «Опубликованные»** (нет фильтра по
  табу, в отличие от кнопки ИИ-подбора).
- **HSDirectoryPage грузит дерево прямо в теле рендера без `.catch`** — при любой ошибке сети
  бесконечный цикл запросов и вечно пустое дерево без ретрая.
- **RU-строки на проводе**: ошибка валидации групп — сырой русский текст без кода и без
  `gettext`; `ActivityLog` пишет «Код ТН ВЭД изменён» словами. Двум подписям полноты нет
  перевода в EN-каталоге — англоязычный продавец видит «missing: Код ТН ВЭД (действующий)»
  (фронт игнорирует передаваемый `item.code`).
- **Мобильная очередь**: тап по чекбоксу/кнопке также открывает форму (нет guard в мобильной
  карточке ResponsiveDataTable), у служебных колонок пустые mobile-подписи.
- **Пустая очередь — без CTA**: объясняет, откуда берутся кандидаты, но не ведёт ни к «создать
  вручную», ни к импорту (Ariba: enablement-очередь всегда предлагает следующий шаг).

## 6. Minor

Бизнес-пороги в коде (0.5 — минимальная уверенность подсказки, 0.3 — recall-порог retrieval,
4 разных limit одного поведения, `MIN_QUERY_LENGTH` задан дважды по-разному); кнопка ИИ-режима
справочника не активна до 5 символов и нигде об этом не говорит; дублированные сериализаторы
Product/ProductList (корень дефектов 3.2/3.3); сортировка таблицы каталога по русским
`*_name` при показе локализованных подписей; `as unknown as`, вечно-включённый `useOffers`
без фильтра в admin-режиме.

## 7. Предлагаемые волны (после утверждения)

- **N1 — данные и корень тупика**: слить `GENERAL`→`GENERAL_GOODS` (данные-миграция);
  стартовая таксономия категорий и групп ж/д (наполнение оператором + миграция-минимум);
  группы при пустом справочнике не блокируют (канон ТН ВЭД); бренд в форме — автокомплит с
  созданием на лету тем же нормализатором, что в импорте; кандидату из строки КП проставлять
  домен по домену заявки.
- **N2 — блокеры формы и публикации**: форма добирает полную карточку по id (лечит стирание
  description/групп); `status` read-only + публикация только сервисом; селект статуса вон из
  формы продавца; «Открыть» ведёт на карточку; пагинация (`page_size_query_param` либо
  fetchAll); честные тосты с кодами.
- **N3 — роли**: enforce `catalog.manage`/`catalog.publish` в сервисах (или осознанно убрать);
  `owner_company` обязателен при создании оператором (+выбор компании в admin-форме);
  `OperatorScoped` на каталог; entitlement-гейт на `hs_lookup`/`hs_classify`.
- **N4 — доводка UX**: UI слияния дублей («возможно, это дубль») и плитка покрытия; CTA в
  пустой очереди; мобильные guard'ы; RU-строки → коды + переводы; пороги → настройки/константы
  одного источника.
