# Станция КП → целевой опыт. Бенчмарк-спека (2026-07-21)

_Исследование по PRODUCT RULES (benchmark-first): 4 параллельных разбора эталонов (Odoo Sales 17/18,
Salesforce CPQ/Revenue Cloud, Bitrix24 + amoCRM/МойСклад, PandaDoc + Qwilr, все утверждения с
URL-источниками) + полный проход текущей станции глазами в браузере за обе роли (продавец: сделка →
билдер → согласование → отправка; клиент: получение → одобрение; публичная ссылка). База: main
`f7d4c00` (#374), локальный стенд. Код НЕ писался. Статус: **ожидает утверждения владельцем**._

---

## TL;DR

**Билдер уже на уровне эталонов — его не трогаем.** После волн #339–#374 грид (секции, реордер,
позиционная наценка, поиск, плотность), экономика-панель с порогом/целью и каскад расходов
соответствуют или превосходят Salesforce QLE: то, что у них продаётся как платный аддон «Pricing
Guidance» (target/norm/floor в гриде), у нас уже стоит в правом рейле.

**Главный разрыв — вокруг билдера, на стыках пути.** Три находки прохода глазами:

1. **Клиентский артефакт — скачиваемый PDF, а не страница.** Публичная ссылка отдаёт
   `Content-Disposition: attachment` — браузер клиента просто скачивает файл. QR внутри PDF ведёт…
   на тот же PDF (замкнутый круг), CTA — «свяжитесь с вашим менеджером». Все четыре эталона сходятся
   в обратном: клиент открывает **веб-страницу** без логина — с кнопкой принятия, отслеживанием
   просмотра и живым статусом (Odoo tokenized page, PandaDoc/Qwilr — вся их категория, Bitrix24 —
   публичная страница документа с триггером «Просмотр»).
2. **Тупик сразу после главного действия клиента.** «Одобрить» → подтверждение «необратимо» →
   выброс на дашборд. Между тем FSM отработал: договор `CT-2026-00002` создан и ждёт подписи
   клиента — но ему об этом не сказали ничего. Единственный намёк — жёлтый счётчик «Договоры на
   подписи: 1» среди виджетов.
3. **Продавец после отправки слеп, а до отправки — в ритуале.** Первая отправка = ~6 кликов через
   3 разные поверхности (статус-дропдаун → «На согласование» → сам себе руководитель → «Согласовать»
   → правая верхняя кнопка → confirm). После отправки — статус «КП отправлено» и тишина: ни
   «просмотрено», ни срока действия (не задан по умолчанию), ни напоминаний.

**Предложение: три связные волны** — A «Страница КП для клиента», B «Отправка и после» (продавец),
C «Полировка документа». Ни одна не добавляет блокировок — только убирает трение (PRODUCT RULES §2).

## 1. Что уже на уровне мировых эталонов (подтверждено исследованием — НЕ трогаем)

| Наша возможность | Эталонное соответствие |
|---|---|
| Грид билдера: инлайн-редактирование, секции/заметки, реордер, поиск в КП, виртуализация, плотность | Salesforce QLE и его наследник TLE (флагман Revenue Cloud); секции = Quote Line Groups / Odoo sections |
| Экономика-панель: себестоимость, валовая прибыль/маржа, **порог 15% · цель 25%** прямо в билдере | Salesforce **Pricing Guidance** (target/norm/floor в гриде) — у них платный аддон CPQ Plus |
| Позиционная наценка c наследованием от КП (NULL=наследовать, 0=по себестоимости, ↺ возврат) | CPQ per-line override; наша визуальная маркировка «переопределено vs наследует» — лучше стоковой CPQ |
| Каскад расходов с промежуточными итогами («почему такая цена») | CPQ price waterfall с именованными ступенями |
| Внутренняя цепочка согласования КП + `below_floor` обоснование | Впереди vanilla Odoo (цепочки нет вообще) и Bitrix24 (только через БП интегратором); строже стокового CPQ |
| Одобрение клиента → автоматическая материализация договора (FSM) | Odoo auto-confirm SO; впереди Bitrix24 (там принятие — ручная перестановка стадии) |
| PDF СНГ-грейд: реквизиты сторон, НДС, **сумма прописью**, менеджер, QR, брендинг | Печатные формы Bitrix24/МойСклад; сильно лучше Qwilr (их PDF-экспорт — признанная слабость) |
| Чат на сделке (продавец ↔ клиент, WebSocket) | PandaDoc comments (частично — у них тред живёт на документе) |

Отдельно: жалоб класса «Bitrix24 перегружен настройками» у нас нет — и это надо беречь.

### Путь клиента

| Шаг | Что увидел | Оценка |
|---|---|---|
| Дашборд | «КП к рассмотрению: 2» — карточка ведёт на список **заявок**, не КП | смещение сущности; счётчик не обновился после одобрения |
| Детали заявки | «КП получено», [Одобрить] [Отклонить], таблица позиций (колонка «Поставщик» вся из «—»), «Скачать КП (PDF)», чат | приемлемо, но КП — не самостоятельный документ, а вкладка заявки |
| «Одобрить» | Confirm «необратимо» → **выброс на дашборд** | тупик: договор уже создан (`PENDING_CLIENT`), клиенту не сказали |

### Публичная ссылка (клиент вне платформы)

- `GET /public/quotes/<token>/` → `Content-Disposition: attachment` → **скачивание файла**, не страница.
- Сам PDF хорош (см. §1), но: «онлайн-версия» и QR ведут на **этот же PDF**; CTA — «для
  подтверждения свяжитесь с вашим менеджером»; **онлайн-принятия не существует**.
- Пустая секция рендерится как «НОВЫЙ РАЗДЕЛ — 0,00» + голая строка «Заметка» (выглядит браком);
  колонка «Срок» вся из «—» (частично чинит открытый PR #375).
- Открытие ссылки **никак не сигналится продавцу** — ни события в таймлайне, ни статуса «Просмотрено».
- Offline-контакт (волна E) получить ссылку может, а **принять КП — нет**: приёмка только для
  залогиненного покупателя. Ценность offline-канала заперта.

## 4. Целевой опыт

### Волна A — «Страница КП» (клиент). Самая ценная

Публичная ссылка (и та же поверхность в кабинете покупателя) открывает **веб-страницу КП**:

```
┌────────────────────────────────────────────────────────┐
│ ООО RailTech          КП № КП-2026-00003 от 30.06.2026 │
│ ИНН · контакты        Действительно до: 14.07.2026     │
├────────────────────────────────────────────────────────┤
│ Позиции (63) — таблица: №, наименование, кол-во,       │
│ цена/ед., сумма; секции с подытогами                   │
│ Итого без НДС · НДС 12% · ИТОГО К ОПЛАТЕ (прописью)    │
├────────────────────────────────────────────────────────┤
│ Ваш менеджер: Aziz Kodirov · aziz.kodirov@railtech.uz  │
│ [✓ Принять предложение]  [Отклонить…]  [⬇ PDF]  [Чат]  │
└────────────────────────────────────────────────────────┘
```

- **Просмотр = событие**: открытие страницы пишет `quote.viewed` в таймлайн сделки, шлёт
  уведомление продавцу, КП получает статус «Просмотрено». (Паттерн: Bitrix24-триггер + Odoo
  «Quotation viewed»; никакого гейта — чистая телеметрия.)
- **Принять**: залогиненный покупатель — как сейчас (одобрение → договор). Незалогиненный
  offline-контакт — step-up подтверждение email-кодом ровно в момент принятия (PandaDoc-паттерн
  «смотреть можно всем у кого ссылка, юридически значимое действие — после верификации»).
- **Отклонить** — с обязательной причиной (API уже принимает reason) → продавцу уведомление+таймлайн.
- **После «Принять» — не дашборд, а «что дальше»**: экран «Предложение принято → договор
  CT-… готов к подписанию → [Перейти к договору]»; offline-контакту — письмо с этим же следующим шагом.
- PDF остаётся равноправным артефактом (скачать с той же страницы; наш WeasyPrint — преимущество,
  Qwilr на этом валится). QR из PDF ведёт на ЭТУ страницу — круг размыкается.

### Волна B — «Отправка и после» (продавец)

```
[Отправить клиенту] →  ┌─ Сводка ────────────────────────┐
                       │ Кому: Local Buyer LLC (client@…) │
                       │ Срок действия: 14 дней [изм.]    │
                       │ Маржа 18% ≥ порога 15% ✓         │
                       │ Согласование: не требуется (авто) │
                       │ [Предпросмотр PDF]  [Отправить]  │
                       └──────────────────────────────────┘
После отправки, вместо немого билдера — панель статуса:
Отправлено 21.07 14:02 → Просмотрено — → Решение —
Ссылка для клиента [копировать] · [Напомнить] · [Отозвать ссылку] · [Создать v2]
```

- **Auto-approve соло/пустой цепочки**: если утверждающих нет ИЛИ единственный утверждающий =
  отправитель, submit сразу даёт «Готово к отправке» с записью в журнал «согласовано автоматически»
  (Salesforce-паттерн). Цепочка НЕ ослабляется там, где она настоящая: ВЭД/руководитель другого
  человека работают как сейчас. Убираем ритуал, не контроль.
- **Превью цепочки** до submit («кто должен согласовать это КП») — Salesforce Approval Preview.
- **Один вход в отправку**: единая кнопка со сводкой; статус-дропдаун остаётся для отзыва/истории.
- **Срок действия по умолчанию** из настроек компании (Odoo Default Validity) — заполняет
  `valid_until`, до сих пор пустой; после истечения — статус «Истекло» и мягкое напоминание
  продавцу (beat-задача `expire_stale_quotes` уже есть).

### Волна C — «Полировка документа»

- Пустые секции/заметки не рендерятся в PDF/странице («НОВЫЙ РАЗДЕЛ — 0,00» исчезает).
- Колонка «Срок» — только при реальных сроках (PR #375 уже делает; влить до/в составе волны).
- Вотермарка «ЧЕРНОВИК» на незамороженном экспорте (#375).
- QR/«онлайн-версия» → на страницу волны A.
- P2 (не сейчас): галерея шаблонов КП в стиле МойСклад (3–5 готовых образов), шаблоны КП с
  предзаполнением условий (Odoo Templates).

## 5. Definition of Done (по PRODUCT RULES §4)

Один сценарий, пройденный глазами и снятый в GIF/скриншоты владельцу:

**заявка → КП (билдер) → [авто-согласование соло] → отправка (сводка) → клиент открыл СТРАНИЦУ
(продавцу пришло «Просмотрено») → клиент принял (для offline — код из письма) → клиент увидел
«договор готов к подписанию» → продавец видит статус «Принято»** — без тупиков, без выброса на
дашборд, на десктопе и телефоне (страница клиента — mobile-first).

## 6. Решения владельца до старта

1. **Объём волны A**: онлайн-принятие сразу и для offline-контактов (email-код)? Рекомендую да —
   это и есть смысл offline-канала волны E; иначе A даёт только чтение.
2. **«Взять в работу»**: спрятать за режим (соло-компания → авто-claim при открытии билдера, кнопка
   исчезает из списков)? Убирает шум, ничего не гейтит. Рекомендую да, в составе волны B.
3. **Порядок**: A → B → C (рекомендую: ценность для клиента раньше удобства продавца) или B → A → C.
4. **PR #375** (вотермарка/срок-колонка/QR) — влить как есть до волн; волна C докроет остальное.
