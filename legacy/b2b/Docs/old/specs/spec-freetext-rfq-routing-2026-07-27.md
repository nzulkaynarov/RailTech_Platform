# Гэп-анализ: авто-подбор продавцов для free-text заявки — 2026-07-27

_Статус: НА УТВЕРЖДЕНИЕ владельцу. Закрывает разрыв №1 карты «входящая заявка» (spec-inbound-rfq):
авто-роутинг работает только для каталожных позиций; free-text заявку покупатель роутит вручную,
угадывая поставщиков._

## Почему это следующий фронт

Весь конвейер W1–W3 (email продавцу → одна кнопка → черновик КП) срабатывает только если заявка
дошла до ПРАВИЛЬНЫХ продавцов. Для позиций из каталога роутинг автоматический
(`route_deal_from_catalog` → владельцы Product). Для free-text (ручной ввод / AI-импорт из файла)
покупатель выбирает компании сам из списка — новичок не знает, кто что продаёт, шлёт не тем или
никому. Конвейер обрывается на первом звене.

## Бенчмарк

| Паттерн | Кто | Как |
|---|---|---|
| **Category-matched routing** | SAP Ariba Discovery | Commodity-коды (UNSPSC) на заявке И в профиле поставщика → авто-match → email-лид поставщику; **match confidence %** (70–100 / 40–70 / <40) |
| **Матч по каталожному следу** | Alibaba RFQ | Заявка матчится к поставщикам по категории/имени товара; ревью перед публикацией; ~3 дня до сделки |
| Pull-рынок заявок (поиск по категории) | Alibaba RFQ | Поставщики сами ищут заявки — **не берём**: противоречит нашей targeted-модели (ADR-0006 Move 2, отказ от whole-pool blast) |

## Наш фундамент (по коду — уже есть)

- `route_deal_from_catalog` (rfq.py) — авто-роутинг по `Product.owner_company` каталожных строк.
- GIN trigram-индексы на `Product.name`/`gost_drawing` (catalog/0006) + smart-match сервис
  (sourcing/services.py) — детерминированный поиск похожих товаров по свободному тексту.
- `DomainKeyword` → `DomainType` (sourcing) — ключевые слова доменов, уже используются в импорте.
- AI-матч `match_lines_to_catalog` (free floor `ai.match`) — опциональное усиление.
- W1 email — уже шлётся всем routed при RFQ_OPEN: новые совпавшие продавцы получат лид автоматически.

## Целевой путь (на утверждение)

Сценарий: *покупатель набил free-text заявку → жмёт «Отправить» → платформа сама предлагает
совпавших поставщиков («нашли N поставщиков по вашим позициям», с галочками, все включены
по умолчанию) → покупатель подтверждает → routed-продавцы получают email (W1) → одна кнопка (W2).*

**Волна R1 — suggest-sellers сервис (детерминированный, без AI).**
`suggest_sellers_for_deal(deal)`: free-text строки заявки → trigram-матч к PUBLISHED Products
(та же инфраструктура, что Smart Match) → `owner_company` совпавших товаров, агрегация по
компаниям со счётом совпавших строк (наш аналог Ariba confidence: «совпало 3 из 5 позиций»).
Endpoint `GET sourcing/requests/{id}/suggested-sellers/`. Никакой записи — чистая подсказка.

**Волна R2 — UI в submit-флоу покупателя.**
На шаге отправки заявки: блок «Кому отправить» = предложенные компании (галочки, включены) +
существующий ручной поиск как дополнение. Пустой матч → текущее поведение (ручной выбор),
без тупика. Совпадения показываются с числом совпавших позиций — покупатель понимает, ПОЧЕМУ
предложен поставщик (прозрачность вместо магии).

**Опция R3 (решение владельца) — AI-усиление.** Для строк без trigram-совпадений — AI-матч
(`ai.match`, free floor, уже 202-паттерн). Дельта качества на «кривых» формулировках; можно
отложить и смотреть на метрику совпадений R1.

Не делаем: pull-рынок заявок (против targeted-модели), новые обязательные шаги (блок —
ПОДСКАЗКА, ручной путь остаётся), новых сущностей в БД (профиль-commodity продавца выводится
из его каталога — стимул наполнять каталог).

Оценка: R1 ~полдня, R2 ~день, R3 ~полдня. DoD: сценарий глазами — free-text заявка без единого
каталожного product_id → предложенные продавцы → email → одна кнопка → КП.
