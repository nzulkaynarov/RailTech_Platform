# Спека: «Документы 2.0» — хаб, произвольные документы по шаблонам, черновики

_Статус: **DRAFT — ожидает утверждения владельцем.** После утверждения — исполнение мультиагентными волнами (Opus), по одной волне за заход, с DoD «пройдено глазами»._

_Бенчмарки: Bitrix24 Document Generator (DOCX-шаблоны с плейсхолдерами из CRM-полей), Odoo (Documents app как отдельный DMS-слой; draft-редактируемость / posted-lock инвойсов; ручное создание из реестра типа), PandaDoc (template-based документы; immutability завершённых). Ссылки в конце._

## 0. Вердикты по пожеланиям владельца (сверено с мировым опытом)

| № | Пожелание | Вердикт | Обоснование |
|---|---|---|---|
| 1 | Централизованно создавать документы | **ЧАСТИЧНО ПОДДЕРЖАНО, форма уточнена** | Транзакционные документы (КП/договор/инвойс/акт) во всех эталонах рождаются ИЗ бизнес-контекста: Odoo — invoice из sales order (ручное создание тоже есть, но из реестра типа, с обязательным выбором контрагента), Bitrix24 — документ генерируется из карточки сделки. «Безконтекстный» конструктор — антипаттерн (документ без сделки/контрагента — сирота). **Решение:** единая кнопка «Создать документ» в хабе = мастер из 2 шагов: тип → сделка/контрагент → существующий контекстный флоу. Это шорткат, не новый флоу. |
| 2 | Вносить редактирование в документы | **ПОДДЕРЖАНО для черновиков, ОПРОВЕРГНУТО для выпущенных/подписанных** | Odoo: draft invoice редактируется, posted — «can no longer be updated» + hash-lock; DocuSign/PandaDoc: completed = неизменяемый архив. Наша модель уже такая для КП (frozen_at) и должна стать такой для инвойса: сегодня инвойс рождается сразу ISSUED (без DRAFT-стадии) — вводим DRAFT → редактирование → действие «Выставить». Редактировать ОТПРАВЛЕННЫЙ/ПОДПИСАННЫЙ документ не будем ни для одного типа — это ломает доверие, ради которого всё строится. Вместо этого — «Новая версия»/«Скорректировать» (у КП уже есть). |
| 3 | Произвольные типы документов (письма, рапорты и т.д.) | **ПОДДЕРЖАНО, паттерн Bitrix24** | Ближайший эталон для нашего рынка: библиотека шаблонов компании с плейсхолдерами (`{{deal.number}}`, `{{company.name}}`, `{{quote.total}}`), генерация из контекста → PDF → реестр, отправка. **Опровергнута** только форма «встроенный редактор документов» (строить Google Docs/PandaDoc-editor — годы разработки; ни Bitrix24, ни Odoo его не имеют — оба используют внешние шаблоны). V1 — HTML-шаблоны (наш WeasyPrint-стек уже HTML→PDF), V2 — загрузка DOCX (требует docxtpl + конвертацию, на VPS тяжело — отдельное решение). |
| 4 | (вытекающее) Файлы/вложения централизованно | **ПОДДЕРЖАНО как DMS-лайт** | Odoo Documents = отдельный файловый слой рядом с транзакционными доками. У нас уже есть универсальный `sourcing.Attachment` (явные FK, kinds SOURCE/SUPPORTING) — добавляем вкладку «Файлы» в хаб (сквозной реестр вложений своей компании), без папок/тегов в v1. |

## 1. Целевой опыт (журни)

### Продавец
1. «Документы» → видит 7 вкладок-реестров: **КП · Договоры · Инвойсы · Акты · Платежи · Исполнение · Прочие** (новая) + «Файлы» (DMS-лайт). Единый паттерн: клик по строке = открыть, короткие статус-действия в строке (реализовано волной #381).
2. Кнопка **«Создать документ»** (одна, в хабе): мастер тип→контекст: «КП» → NewQuoteDialog; «Инвойс» → выбор SIGNED-договора → generate-from-contract; «Акт» → выбор инвойса; «Письмо/произвольный» → выбор шаблона + сделки/контрагента → генерация.
3. **Прочие документы**: реестр сгенерированных по шаблонам (гарантийное письмо, сопроводительное, рапорт, справка). Статусы DRAFT → ISSUED. DRAFT редактируем (поля-значения плейсхолдеров), ISSUED — фиксирован, PDF, отправка (email/копировать ссылку — реюз DocumentActions), привязан к сделке/контрагенту.
4. **Шаблоны** (Settings Hub → «Шаблоны документов», рядом с charge-templates): CRUD HTML-шаблонов компании; каталог плейсхолдеров с подсказкой; предпросмотр на образцовых данных (паттерн document-profile preview уже есть).
5. **Инвойс**: рождается DRAFT (авто-создание из контракта — тоже DRAFT c уведомлением), в DRAFT редактируются: due_date, notes, реквизиты плательщика; суммы — из источника (контракт/КП), не руками. Действие «Выставить» → ISSUED (рендер PDF, письмо клиенту — как у КП send). Отмена: DRAFT — удалить; ISSUED — «Отменить» (новый бэкенд-экшен, статус CANCELLED есть).

### Покупатель
1. Те же реестры, но «полученное»: КП (read-only + принять/отклонить через заявку), договоры (подписать/скачать подписанный), инвойсы (оплатить/скачать), акты (подписать), исполнение (принять/спор), прочие документы (полученные письма — read-only + скачать).
2. Кнопка «Создать документ» у покупателя ограничена его типами: «Платёж» (record-payment) и «Письмо» (по своим шаблонам — покупательская компания тоже может иметь шаблоны: запрос, претензия, доверенность).
3. Файлы: вложения своих сделок сквозным списком.

## 2. Архитектура (Rule 8, ARCH-01/03, IRON RULES)

### Новые модели (одна миграция, аддитивная)
- **`crm.DocumentTemplate`**: company FK, name, kind (LETTER/REPORT/CUSTOM — lookup-таблица `DocumentTemplateKind` через data-migration, Rule 1), body_html (TextField), placeholders_used (JSON, derived), is_active, created_by, timestamps. Company-scoped (никаких кросс-tenant шаблонов). Permission: `settings.edit` управляет, `quote.build`-класс может генерировать.
- **`crm.GeneratedDocument`**: company FK, deal FK (nullable), contact FK (nullable), template FK (PROTECT), number (нумератор через существующий `numbering.py`), status FK (lookup `GeneratedDocumentStatus`: DRAFT/ISSUED/CANCELLED, data-migration), values (JSON — снапшот значений плейсхолдеров на момент генерации; НЕ живые ссылки — документ не должен «плыть» задним числом), pdf_file, issued_at, created_by. PDF-рендер офф-тред (`render_document_pdf` doc_type="generated" в существующем реестре `_render_pdf_for`), инвалидация DRAFT-PDF при правке values — тот же invalidate-on-write, что у КП (#379).
- **Invoice**: без новой модели; data-migration статуса DRAFT уже существует в lookup; изменяется точка создания (services/billing.py: создавать DRAFT; экшен `issue` → ISSUED + рендер; экшен `cancel` → CANCELLED, только не-PAID; авто-инвойс из CLOSED_WON — создаёт DRAFT и шлёт уведомление продавцу «выставьте инвойс», НЕ автоматом ISSUED — владелец теряет контроль иначе; ОТКРЫТЫЙ ВОПРОС №2 ниже).

### Подстановка плейсхолдеров — БЕЗОПАСНОСТЬ
НЕ Django-template-движок по пользовательскому шаблону (SSTI-инъекция). Только плоская замена `{{code}}` по **белому списку** резолверов: `deal.*`, `company.*` (своя), `counterparty.*`, `quote.*`, `contract.*`, `user.*`, `today`. Резолверы — один модуль `crm/services/document_placeholders.py` с реестром; неизвестный плейсхолдер остаётся как есть + предупреждение при сохранении шаблона. HTML шаблона санитайзится (bleach-класс allowlist тегов) перед сохранением; рендер в PDF — через базовый `_document_base.html` (бренд-обвязка компании, как у всех документов).

### Фронтенд
- Хаб: существующие страницы; новая `OtherDocumentsPage` (реестр по канону #381: клик-по-строке → Sheet, DocumentActions, статус-действия), `DocumentCreateWizard` (диалог «Создать документ»), `DocumentTemplatesSettings` (секция Settings Hub, по образцу ChargeTemplatesSettings), вкладка «Файлы» (`CompanyFilesPage`, на Attachment API — понадобится list-эндпоинт с company-скоупом).
- Инвойс-Sheet: режим DRAFT — форма (due_date, notes) + «Выставить»; ISSUED+ — как сейчас + «Отменить».

### Ограничения/энтайтлменты (ОТКРЫТЫЙ ВОПРОС №3)
Предлагается: шаблоны и генерация — в `SUBSCRIPTION_BASELINE_FEATURES` (фича подписки, как quote.send); лимит шаблонов на компанию (напр. 20) — конфиг, не хардкод (Rule 2).

## 3. Волны исполнения (мультиагенты Opus; по одной волне за заход)

_Общие guardrails каждому агенту: PRODUCT RULES + IRON RULES из CLAUDE.md; benchmark-паттерн назван в задаче; тесты нового поведения в СОБСТВЕННЫХ файлах; build+vitest+pytest+i18n-symmetry зелёные до PR; стек-мерж только сверху-вниз; DoD волны = сценарий пройден глазами со скриншотами владельцу._

### Волна A — «Создать документ» + Прочие документы (ядро ценности)
| Агент | Задача |
|---|---|
| A1 backend | Модели DocumentTemplate/GeneratedDocument + lookups (data-migrations) + сервисы (create/generate/issue/cancel, нумерация, снапшот values) + placeholders-модуль с белым списком + PDF-рендер (реестр doc_type) + инвалидация DRAFT + ViewSets (company-scoped, viewer-гейт) + тесты |
| A2 frontend-реестр | OtherDocumentsPage по канону #381 (клик→Sheet, DocumentActions, статусы) + пункт «Прочие» в nav «Документы» + i18n |
| A3 frontend-мастер | DocumentCreateWizard (тип→контекст→генерация; existing-типы маршрутизирует в их флоу) + кнопка в хабе (buyer/seller-скоупы типов) |
| A4 адверсариальное ревью | SSTI/инъекция шаблонов, IDOR company-скоупов, XSS в body_html, «плывущие» значения (снапшот!), объём файлов |
| DoD | Глазами: создать шаблон «Гарантийное письмо» → сгенерировать по сделке → DRAFT → правка значения → «Выпустить» → PDF с брендом → отправить ссылку. Скриншоты. |

### Волна B — Шаблоны в Settings Hub
| B1 | DocumentTemplatesSettings (CRUD + каталог плейсхолдеров + live-предпросмотр на образцовых данных через существующий preview-паттерн) + права `settings.edit` |
| B2 | Санитайзер/валидация шаблона (bleach-allowlist, предупреждение о неизвестных плейсхолдерах) + тесты на инъекции |
| DoD | Глазами: создать/править/деактивировать шаблон, предпросмотр, неизвестный плейсхолдер подсвечен. |

### Волна C — Инвойс: DRAFT-стадия (ERP-канон)
| C1 backend | Создание в DRAFT (ручное и авто из CLOSED_WON — по решению ОВ-2), экшены issue/cancel, гейты (issue — только продавец, cancel — не-PAID), уведомления, тесты; миграция ДАННЫХ не нужна (существующие ISSUED не трогаем) |
| C2 frontend | Invoice-Sheet: DRAFT-форма (due_date/notes) + «Выставить»; «Отменить» для ISSUED; бейдж DRAFT в реестре; авто-инвойс уведомление «выставьте инвойс» |
| DoD | Глазами: контракт → «Создать инвойс» → DRAFT → правка срока → «Выставить» → PDF/статус → «Отменить» другой. |

### Волна D — Файлы (DMS-лайт)
| D1 | Attachment list-эндпоинт company-scoped (+deal-фильтр) + CompanyFilesPage (реестр: имя, сделка, kind, дата, скачать; клик → скачать/открыть) |
| DoD | Глазами: файлы всех сделок компании одним списком, скачивание. |

_Порядок: A → B → C → D. A и B можно одним заходом (B зависит только от модели A1)._

## 4. Решения владельца (утверждено 2026-07-22)

**Спека УТВЕРЖДЕНА владельцем 2026-07-22.** Ответы на 4 вопроса:

1. **Стартовый набор шаблонов-заготовок** (не уточнён явно → берём рекомендацию): гарантийное письмо, сопроводительное письмо, доверенность, претензия, рапорт — как примеры в data-migration (company-agnostic, создаются для компании при первом входе в раздел «Шаблоны» либо как глобальные образцы «скопировать к себе»; см. волну B).
2. **Авто-инвойс при выигрыше сделки → DRAFT + уведомление** «выставьте инвойс» (контроль продавца, ERP-канон). НЕ сразу ISSUED.
3. **Монетизация → в базовую подписку** (`SUBSCRIPTION_BASELINE_FEATURES`, как `quote.send`). Новый FeatureKey `document.generate`.
4. **DOCX-шаблоны → ОТЛОЖЕНО** (V2). Старт только на HTML-шаблонах (WeasyPrint HTML→PDF).
