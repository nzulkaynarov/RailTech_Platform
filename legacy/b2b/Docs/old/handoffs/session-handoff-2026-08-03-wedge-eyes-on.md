# Session handoff — 2026-08-03: сквозной прогон клина глазами, шесть живых 500 и адаптивность

Продолжение `session-handoff-2026-08-03-event-feeds-and-scope.md`. Здесь — что показал полный
проход по клину на локальном стенде, что починено и что осталось.

## 1. Сценарий пройден ЦЕЛИКОМ

Заявка → позиции → отправка → продавец взял в работу → сборка КП с ценами → согласование →
отправка клиенту → публичная страница → подтверждение кодом из письма → договор → подписи двух
сторон → счёт → выставление → оплата → отгрузка → доставка → приёмка → акт → приёмка акта.

Финал карточки сделки: «Цепочка пройдена полностью: договор, оплата, акт и приёмка закрыты.»
Сделка #17, договор `CT-2026-00004`, счёт `INV-2026-00005`, акт `ACT-2026-00002`, квитанция
`RCP-2026-00001`, накладная `DN-2`.

**Но без правок ниже сценарий обрывался трижды** — на подписании договора покупателем, на
приёмке акта и на выпуске акта.

## 2. Шесть живых 500 одного корня (ПОЧИНЕНО)

`select_for_update` вне транзакции → `TransactionManagementError` → 500. Пользователь видел
`ERR_BAD_RESPONSE`.

| Путь | Симптом |
|---|---|
| `sign_contract_by_client` | покупатель НЕ МОГ подписать договор |
| `sign_act` | заказчик НЕ МОГ принять акт |
| `remind_act_acceptance` | напоминание по акту падало |
| `cancel_act` | аннулирование акта падало |
| `generate_act` | продавец НЕ МОГ выпустить акт |
| `generate_contract_from_quote` | прямое создание договора из КП упало бы |

Два разных механизма одного корня:

* **Расхождение близнецов.** У `sign_contract_by_manager` декоратор `@transaction.atomic` был,
  у `sign_contract_by_client` — нет. Две функции одного двустороннего документа разошлись.
* **Транзитивная блокировка.** `generate_act` не содержит `select_for_update` вовсе: он зовёт
  `_next_act_number`, тот — `next_document_number`, и блокировка счётчика живёт ТАМ.
  `next_document_number` этого и требует: «MUST be called inside the caller's atomic block».

### Почему молчали 1154 зелёных теста

`pytest.mark.django_db` оборачивает каждый тест в транзакцию — `select_for_update` внутри теста
работает ВСЕГДА, независимо от того, атомарен сервис или нет. Поведенческий тест этот класс не
ловит в принципе.

Поэтому guard (`crm/tests/test_locked_paths_are_atomic.py`) проверяет **структуру исходников**:
строит граф вызовов и требует, чтобы на пути от публичной функции до блокировки было хотя бы
одно атомарное звено. Блокировка распространяется вверх только через НЕатомарные звенья —
атомарный сервис её поглощает.

**Две ошибки, которые guard совершил при разработке (обе зафиксированы в нём тестами):**

1. Проверка атомарности ПОДСТРОКОЙ считала атомарной `next_document_number` — та упоминает
   `transaction.atomic()` в докстроке. Теперь атомарность читается из AST.
2. Проверка «только прямые блокировщики» не видела цепочку через тонкую обёртку.

## 3. Адаптивность (ПОЧИНЕНО частично)

**Планшетный провал.** `useIsMobile` считает мобильным только `≤767px`, поэтому на 768–1279px
сайдбар оставался развёрнутым на 256px. Замер `scrollWidth − clientWidth` давал ровно 256px на
каждой странице: у реестра сделок за экран уходили «Сумма», «Ответственный», «Дата» и колонка
действий. Эталон (Odoo, Linear, Notion) держит на планшете навигацию свёрнутой в иконки —
режим у нас уже был (`collapsible="icon"`), не хватало стартового состояния.

**`SidebarInset` без `min-w-0`.** Flex-элемент не сжимается ниже ширины своего контента, поэтому
`main` оставался равен ПОЛНОЙ ширине вьюпорта и уезжал вправо на ширину сайдбара (замер: `right`
= 816 при вьюпорте 768). Страница получала горизонтальный скролл вместо того, чтобы его получила
таблица внутри своего `overflow-x-auto` контейнера.

Итог замеров: планшет 222–256px вылета → **0**; мобильный: реестры чисты, таблицы падают в
карточки.

**Осталось:** на 375px правый кластер шапки (валюта + тур + корзина + поиск + чат + поддержка +
уведомления) занимает 459px и даёт вылет 103px на всех страницах. Лечится меню «ещё» —
переделка, а не заплатка, поэтому вынесена из этой волны.

## 5. Найдено и НЕ починено

### 5.1 Стороны выводятся из `activeStatus` — у двойной компании ломается

Компания с типами `CLIENT`+`SUPPLIER` (а таких в базе большинство) получает `activeStatus =
BUYER` (первый тип). Дальше:

* **Карточка заявки** (`request-detail/index.tsx:68`): `isSellerSide = activeStatus === 'SELLER'`.
  Продавец, открывший СВОЮ заявку напрямую, видит ПОКУПАТЕЛЬСКИЙ экран: ни «Взять в работу и
  подготовить КП», ни «Сформировать КП». Единственная видимая кнопка — «Вернуть в очередь»,
  та самая, право на которую считает СЕРВЕР (`viewer_can_release`).
* **Дашборд** шлёт `X-Active-Context: BUYER`, и `/crm/deals/` отдаёт 2 сделки вместо 6.
  Тот же экран после захода на «Сделки» (контекст переключается на SELLER) показывает другое.

Это ровно тот канон, который CLAUDE.md уже фиксирует для пути «после контракта»: «Стороны
считает СЕРВЕР, не `activeStatus` (тот = первый тип компании и ломался у компании, которая и
покупает, и продаёт)». Сервер уже умеет считать сторону (`_viewer_routing` в
`crm/serializers/deal.py`) — не хватает поля `viewer_is_seller` в ответе.

### 5.2 Плитка «Заявки без КП» структурно всегда 0

Считает `PRE_KP_STAGES && !d.active_quote`. Но позиции заявки покупателя ФИЗИЧЕСКИ ЛЕЖАТ в
DRAFT-КП (`_request_draft_quote` в `crm/services/rfq.py`: «The single DRAFT quote holding the
buyer's requested items»). Значит у любой отправленной заявки `active_quote` есть всегда, и
плитка не может показать ничего, кроме заявок без позиций — которые и отправить нельзя.

Комментарий в коде обещает «ЧЕСТНЫЙ счёт (ресерч 2026-07-28)», но опирается на признак, которого
у заявки не бывает.

### 5.3 Русские слова в английском интерфейсе — продолжение волны #523/#524

* **Цепочка сделки** печатает статусы словами: «CT-2026-00004 · Подписан сторонами»,
  «INV-2026-00005 · Оплачен», «Принято клиентом». Сервер (`crm/services/deal_documents.py`)
  отдаёт готовую ПОДПИСЬ, а не код.
* Виджет «Недавние документы» печатает «КП v1» вместо «Quote v1».

### 5.4 Русский словарь: жаргон и обрубленные склонения

* `Deal #{{deal_id}}` в ШЕСТИ русских шаблонах журнала — рядом со строкой «Сделка #17».
* «{{count}} позиц.» / «{{count}} продавц.» — при том что БАЗА хранит правильные «2 позиции» и
  «1 продавцу»: шаблон витрины ХУЖЕ текста, который уже записан сервером.
* Сырые коды в русских строках: `READY_TO_SEND`, `APPROVED`, `CLOSED_WON`, «(RFQ)»,
  «(RFQ routing)».

### 5.5 Мелкое

* **Реестр договоров:** колонка «Действия» пуста у договора, который ждёт подписи именно этого
  пользователя. Действие доступно только кликом по строке.
* **Накладная нумеруется `DN-{id}`** в пяти местах кода, мимо схемы нумерации, по которой идут
  все остальные документы (квитанция — уже по схеме, `RCP-2026-00001`). Починка требует
  хранимого номера и решения о ретроактивности.
* **«Документы сделки»** пишет «По сделке пока нет документов» прямо под блоком «Цепочка
  сделки», где их пять. Два разных смысла слова «документы» на одном экране.
* **Подписант документов = `Company.contact_person`** (правило #287). В демо это «System Admin»,
  и он печатается в акте и квитанции. Контактное лицо и подписант — разные роли; стоит решения
  владельца.

## 6. Проверено и НЕ подтвердилось (чтобы не искали заново)

* «Авто-счёт при выигрыше падает `IntegrityError`» — устаревшая схема в celery-воркере
  (известная грабля: celery не перезагружает код после миграций). После рестарта — работает.
* «Цепочка показывает Черновик после выставления» — гонка в тест-скрипте, не кэш.
* «Поле себестоимости съедает ввод» — артефакт Playwright `fill()`; реальный набор работает.
* «Форма платежа не предзаполнена» — сумма подставляется после выбора счёта; не предвыбран
  только сам счёт.
* Английская публичная страница КП остаётся русской — это ЗАДОКУМЕНТИРОВАННОЕ решение
  (КП вне волны M1), пункт B4 скоупа.
