## 2. Главный вывод сессии: собственную спеку тоже надо проверять бенчмарком

В спеке 29-07 и в моём предыдущем хендоффе стояло: «по эталонам акт выпускают **после оплаты**».
Ресерч это **опроверг**. Оплата не является триггером закрывающего документа ни в одном эталоне;
канон — **поставка → приёмка → счёт → оплата**, и это подтверждают два независимых основания:
IFRS 15 / ASC 606 (выручка по передаче контроля, «not when a contract is signed or a payment is
received») и правило составления первички по факту хозяйственной жизни.

Утверждение пришло из чужой спеки, я перенёс его в хендофф не проверив, и оно чуть не стало
основанием для решения. Приём тот же, что и с чужими утверждениями в F0: **проверять фактами
до того, как строить на них продукт.**

## 3. Решения, зафиксированные бенчмарком (не менять без нового ресерча)

- **Триггер акта — факт поставки, выпуск ручной.** Авто-выпуск при выигрыше удалён; он и не
  срабатывал ни разу (счёт рождается DRAFT, `generate_act` требует ISSUED+). В Odoo триггер —
  валидация отгрузки, в SAP приёмку подтверждает получатель («принцип двух рук»).
- **`OVERDUE` НЕ проставляется намеренно.** Просрочка вычисляется из `due_date` + остатка, как у
  Stripe (там `past_due` вообще не статус счёта), Odoo и QuickBooks. Chargebee — единственный, кто
  хранит, и у него задокументированы ровно те рассинхроны, которых мы избегаем. Хранится только
  `Invoice.payment_reminder_sent_at` — состояние ПРОЦЕССА напоминаний.
- **Акт двусторонний.** В узбекской практике «подтверждён двумя сторонами» (ГК РУз ст. 646
  привязывает возражения заказчика к акту приёмки), в российском ЭДО — два титула. Односторонняя
  подпись это форма СЧЁТА. Выпустивший больше не может принять свой же акт.
- **Писем ровно четыре.** Минимум, на котором сходятся Stripe/Odoo/Xero/QuickBooks/PandaDoc/
  DocuSign/Bill.com. Порог Google/Yahoo — 0,3% жалоб (ориентир 0,1%), репутация считается по
  домену целиком: мусорные письма бьют по доставке критичных. Есть тест, что черновик письма НЕ
  порождает.
- **Клик без E-IMZO — не юридическая подпись.** Формулировка «согласовано в системе», тег
  `[MANUAL_MODE]`. Интеграции с ЭДО (Didox / Soliqservis) в проекте нет — это отдельная задача,
  если понадобится юридическая значимость.

Полный разбор с источниками — в `Docs/dev/specs/spec-post-contract-open-questions-2026-07-30.md`.

## 4. Как мержился стек (повторить при следующем стеке)

Инцидент 2026-07-21 не повторился, потому что порядок был такой:

1. смержить **базовый** PR (#468) squash-ом, **не удаляя ветку** — иначе у стоящего сверху PR
   пропадает база;
2. локально `git rebase --onto origin/main <старая база> <ветка стека>` — после squash история
   схлопнута, и без rebase верхний PR принесёт дубли;
3. **прогнать гейты заново на новой базе** (я прогнал полностью: 1663 backend, 566 frontend,
   миграции, сборка, i18n, линтеры);
4. `gh pr edit <верхний> --base main`, force-push, затем мерж.

`mergeable` у GitHub может залипнуть в `UNKNOWN` — надёжнее проверять локально:
`git merge-base --is-ancestor origin/main HEAD` и число коммитов расхождения.
