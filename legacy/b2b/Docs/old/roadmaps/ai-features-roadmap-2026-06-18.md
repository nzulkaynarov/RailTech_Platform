  `sourcing/tasks.py:process_excel_import` при `use_ai=True`.

  `AI_IMPORT_ENABLED=True` — AI-импорт работает вживую (с 2026-06-18 ~18:34).
- **Настройки:** `backend/core/settings.py` — `ANTHROPIC_API_KEY`, `AI_IMPORT_MODEL`,
  `AI_IMPORT_ENABLED` (авто-derive из ключа), `AI_IMPORT_CHUNK_ROWS`, `AI_IMPORT_MAX_BYTES`.
- **UX-аудит buyer-фронта (36 находок) — ЗАКРЫТ** и задеплоен (PR #79 + #81 в `main`).
  Эти 8 AI-идей — отдельный, ещё **НЕ начатый** блок (владелец: «все сразу, потом прогон, потом багфикс»).

## Технические опоры (переиспользовать, не изобретать)

- **Паттерн вызова:** `services_ai.py` — `_client()`, output_config / Structured Outputs,
  чанкинг, обработка `stop_reason`, `_normalize_items()`, инжект справочников в промпт
  (как `code_guidance` для `unit_code`).
- **IRON RULE 1:** id/коды — ВСЕГДА из БД. Модель ранжирует/извлекает, но НЕ выдумывает
  product_id, currency_code, category_code и т.п. Валидировать результат против БД.
- **Приватность:** любой вызов наружу (Anthropic, серверы вне UZ) → opt-in disclaimer
  (как у AI-импорта). Особенно для цен КП, банковских реквизитов, истории чата.
- **Деньги:** финансовые расчёты — в коде на `Decimal`, НИКОГДА не доверять числу из LLM.
- **Smart-match преселект:** GIN-trigram индексы на `Product.name`/`gost_drawing` (см. conventions).
- **Human-in-loop:** AI-результат — подсказка/черновик под ручное подтверждение, не блокировка
  и не авто-отправка.

## Полный список идей (из мультиагентного UX-аудита, с verify-вердиктом)

### 1. Семантический поиск/мэтчинг позиции заявки к товарам каталога (PIM)  — effort M
- **Где в потоке:** Между импортом/составлением заявки (RequestItemsEditor) и отправкой КП: каждая строка заявки сопоставляется с товарами catalog.Product.
- **Польза:** Закрывает главный разрыв: заявка приходит свободным текстом (name/mpn/note на рус/узб/англ), а в каталоге товар назван иначе. ИИ предлагает 1-3 кандидата Product по строке → покупатель привязывает product_id (как уже делает cart-flow). Ускоряет составление КП продавцом, снижает дубли в PIM, делает заявку «структурной», а не текстовой.
- **Как (Claude API):** Tool use / Structured Outputs. Кандидаты сначала сужаем дешёвым SQL (GIN-trigram по Product.name/gost_drawing/mpn, mpn/gtin точное совпадение), затем Claude (opus-4-8) ранжирует shortlist: вход = строка заявки + N кандидатов из БД, выход по json_schema [{product_id, confidence, reason}]. Кандидаты ВСЕГДА из БД (Rule 1), модель только ранжирует — не выдумывает id. Переиспользует client/_client() и output_config-паттерн из services_ai.py.
- **Риски:** Точность: уверенные ложные мэтчи опаснее пустых — нужен порог confidence + ручное подтверждение (как is_incomplete-гейт). Приватность: уходит только строка + shortlist каталога (не вся заявка). Стоимость: 1 вызов на строку дорого — батчить строки в один запрос, кэшировать по (name+mpn). Без trigram-индексов SQL-преселект деградирует.

### 2. Нормализация и обогащение карточек каталога (PIM data quality) при массовом импорте  — effort M
- **Где в потоке:** Seller-сторона смежно с покупательской: catalog import (sourcing/catalog_import.py) — чистит каталог, по которому покупатель потом ищет/мэтчит.
- **Польза:** Покупательский поиск и авто-мэтчинг работают только если каталог чистый. ИИ разбивает свалку «название+характеристики» на name/mpn/gost_drawing/tech_params, нормализует бренд, предлагает категорию из дерева Category. Прямо усиливает идею №1 и буквальный поиск покупателя.
- **Как (Claude API):** Structured Outputs по схеме Product-полей (name, mpn, gost_drawing, tech_params как JSON, category_code). Список валидных категорий и брендов инжектится в промпт ИЗ БД (как code_guidance для unit_code в services_ai.py), результат валидируется против БД. Dry-run уже есть в catalog import — ИИ-предложения показываем в превью, импортёр подтверждает.
- **Риски:** Это seller-зона, не строго buyer-flow (помечаю явно). Точность ГОСТ/чертежей критична — ошибка в gost_drawing вводит в заблуждение; держать human review в dry-run. Стоимость на 50k строк высокая — гейтить флагом, батчить, только для строк, не прошедших детерминированный парс.

### 3. ИИ-помощник для сравнения полученного КП с заявкой («что не так с предложением»)  — effort M
- **Где в потоке:** Шаг «получил КП» (RequestDetailPage, статус Quote received): покупатель видит QuoteItem'ы с ценами от продавца.
- **Польза:** Покупатель-непрофессионал не всегда замечает: продавец заменил позицию аналогом, изменил количество/единицу, не оценил часть строк, или note-требование («допускается замена», ГОСТ) проигнорировано. ИИ даёт короткое резюме расхождений заявка↔КП простым языком → осознанное accept/reject.
- **Как (Claude API):** Один вызов с structured output: вход = строки исходной заявки + строки КП (обе из БД, snake_case), выход по схеме [{issue_type: substitution|qty_mismatch|unit_mismatch|unpriced|note_ignored, line, explanation}]. Детерминированную часть (непокрытые строки, расхождение qty/unit) считаем кодом БЕЗ ИИ; ИИ только для смысловых расхождений (аналог ли это, выполнено ли note-требование). Результат — подсказка, не блокировка.
- **Риски:** Не должно звучать как юр-совет/гарантия (как в disclaimer AI-импорта — оператор не отвечает). Приватность: цены КП — чувствительные; уходят за пределы УЗ → тот же opt-in disclaimer. Стоимость низкая (1 вызов на КП). Галлюцинация «проблемы» там, где её нет → чётко помечать как ассистивную подсказку.

### 4. Черновик ответа продавцу в чате заявки (reply assist)  — effort S
- **Где в потоке:** Чат покупатель↔продавец (send_deal_message, WS+REST), привязан к request-detail.
- **Польза:** Покупатель часто не знает, как сформулировать уточнение по позиции (запросить аналог, ГОСТ, срок, сертификат). ИИ предлагает 2-3 черновика на основе контекста заявки/КП — снижает трение, ускоряет согласование, делает диалог профессиональнее.
- **Как (Claude API):** Один вызов без сложной схемы (можно plain text или structured [{draft}]). Контекст = текущая строка/КП + последние сообщения чата из БД. Кнопка «предложить ответ» в чат-композере; пользователь правит и отправляет САМ (ничего не уходит автоматически). Переиспользует _client().
- **Риски:** Низкий риск, но опасно автоотправлять — только черновик под ручную отправку. Приватность: история чата уходит наружу → opt-in/disclaimer на саму кнопку. Тон/факты могут не подходить — пользователь редактирует. Стоимость низкая.

### 5. Двуязычная нормализация наименований заявки (рус↔узб↔англ) для поиска и КП  — effort S
- **Где в потоке:** Сразу после извлечения позиций (services_ai.py / RequestItemsEditor), до мэтчинга и отправки.
- **Польза:** Уже есть в УЗ-реальности: заявки на узб-кириллице/латинице, каталог на русском. Канонизация + перевод ключевых терминов на язык каталога резко повышает попадание буквального и семантического поиска (идея №1) и читаемость КП для продавца.
- **Как (Claude API):** Можно сложить в ОДИН вызов с экстракцией: расширить ITEM_SCHEMA полем name_canonical/search_terms. Structured Outputs гарантирует JSON. Оригинал name по правилу 6 промпта остаётся как есть (не теряем исходник), канон — отдельное служебное поле для поиска. Минимальная доработка существующего сервиса.
- **Риски:** Перевод техтерминов/брендов может исказить смысл — хранить и оригинал, и канон, искать по обоим. Стоимость ~ноль (тот же вызов экстракции). Приватность покрыта существующим AI-import disclaimer'ом. Не показывать канон как «правильное» имя — только как поисковый ключ.

### 6. Извлечение структурированных данных из подписанного контракта / счёта (PDF)  — effort M
- **Где в потоке:** Шаги контракт→инвойс (crm contracts/billing): покупатель загружает подписанный контракт или встречный счёт PDF.
- **Польза:** Сверяет суммы/валюту/срок/реквизиты контракта и инвойса с данными КП в БД и подсвечивает расхождения (цена в счёте ≠ итог КП, чужая валюта, просроченный срок). Защита покупателя от ошибок/подмены в финальных документах перед оплатой.
- **Как (Claude API):** Тот же vision-паттерн, что и для PDF-заявок (document base64 block в services_ai.py) + Structured Outputs по схеме {total, currency_code, valid_until, bank_details, line_totals[]}. Сверку с Quote/Contract из БД делаем КОДОМ (decimal-точность как в проекте), ИИ только извлекает из PDF. Валюты валидируем против master_data.Currency.
- **Риски:** Финансовая точность критична — ИИ-цифры ТОЛЬКО как подсказка для ручной сверки, расчёты в коде на Decimal, никогда не доверять числу из LLM для оплаты. Приватность: банковские реквизиты уходят наружу — сильнее всего бьёт по UZ-локализации, нужен явный opt-in именно на этот шаг. Стоимость низкая (1 PDF).

### 7. Проверка комплектности и качества заявки перед отправкой («pre-flight»)  — effort S
- **Где в потоке:** Гейт submit_request (Draft→RFQ_OPEN), рядом с существующей проверкой is_incomplete.
- **Польза:** Помимо формальной проверки (есть name или mpn) ИИ ловит смысловые проблемы: дубль аналогов разными словами, неправдоподобное количество/единица, отсутствие критичной спецификации для технической позиции. Покупатель отправляет продавцу более полную заявку → меньше итераций уточнений.
- **Как (Claude API):** Один вызов на заявку: вход = все строки из БД, выход по схеме [{line, severity, hint}]. Детерминируемое (пустые поля, дубль-ключ — merge_request_lines уже есть) считаем кодом; ИИ — только смысловые подсказки. Неблокирующие предупреждения в UI рядом с кнопкой Submit; жёсткий гейт остаётся кодовым.
- **Риски:** Не должно мешать отправке (ассистивно, не блокирующе) — иначе ложное срабатывание заблокирует валидную заявку. Стоимость низкая (1 вызов на submit). Приватность: вся заявка уходит наружу → существующий AI-disclaimer. Возможны бесполезные/очевидные подсказки — держать порог severity.

### 8. Conversational-ассистент составления заявки из свободного описания  — effort L
- **Где в потоке:** Старт покупательского flow: альтернатива каталогу/импорту — покупатель описывает потребность текстом/в чате, получает черновик строк заявки.
- **Польза:** Для покупателя, который не знает точных артикулов/каталога: «нужны тормозные колодки на вагон такой-то, 4 комплекта, и подшипники буксовые» → ИИ предлагает структурированные строки заявки в editable-грид (тот же human-in-loop). Снижает порог входа, ведёт к каталогу через мэтчинг (идея №1).
- **Как (Claude API):** Multi-turn tool use: модель задаёт уточняющие вопросы и вызывает tool search_catalog (наш реальный поиск по Product, из БД) для подсказок, финал — Structured Outputs в request-line схему → RequestItemsEditor. Переиспользует мэтчинг (идея №1) как tool. Покупатель всё правит и подтверждает.
- **Риски:** Самая дорогая/сложная (multi-turn + tool roundtrips, L). Риск увести от реального каталога — обязательно грунтить tool'ом по БД, не давать выдумывать товары (Rule 1). Приватность: диалог наружу → disclaimer. Стоимость на диалог заметная — лимит ходов, кэш системного промпта. Делать после того, как №1 (мэтчинг) уже работает.
