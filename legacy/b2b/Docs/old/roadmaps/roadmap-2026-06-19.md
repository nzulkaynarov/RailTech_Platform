### F3.8 — детальная заметка (мировая практика)

**Проблема сейчас:** `logistics_cost` + `customs_duty` живут на `QuoteItem` → для поставки из N позиций одной машиной логистику приходится размазывать/дублировать вручную по строкам. Это неверно для консолидированной отгрузки.

**Лучшая практика (ERP/UBL/PEPPOL):**
- **Header-level charges** (на весь документ КП): фрахт/логистика, страхование, упаковка, погрузка, прочие сборы — заносятся **один раз**. Если нужен per-unit landed cost для наценки — **аллокация** header-расхода по позициям по выбранной базе: по стоимости (value), весу (weight) или объёму (volume).
- **Line-level charges**: то, что объективно по позиции — себестоимость, пошлина если она по HS-коду/стоимости позиции, наценка по строке.
- **Incoterms-driven колонки**: базис поставки определяет, до какой точки расходы включены в цену продавца. EXW → цена = только товар (всё остальное несёт покупатель, показываем информативно/скрываем); CIF/CIP → включены фрахт+страховка до порта; DAP → доставлено, пошлины покупателя; DDP → всё включено. Набор видимых колонок расходов = функция от Incoterm.
- **Модель данных**: ввести Quote-header поля (или таблицу `QuoteCharge` в духе UBL `AllowanceCharge`: scope=header|line, type=freight/insurance/customs/other, amount, allocation_method). `landed_cost` позиции = frozen_base + аллоцированная доля header-расходов + line-пошлина.

**Усилие:** L (миграция модели + пересчёт landed/margin + UI-перестройка `QuoteBuilderGrid` + PDF-шаблон). Делать ПОСЛЕ консолидации seller-КП workspace (F3.1), чтобы не перестраивать две поверхности.

### F6.X — Конвейер «AI intake → match → enrich → promote» (owner-aligned 2026-06-23)

Связывает #1 (matching), #2 (PIM-enrich) и #8 в один поток. Цель: заявка с минимальными правками «садится» в каталог, без двойной работы продавца, и БЕЗ замусоривания каталога сырым покупательским текстом. Мировая практика = PIM data-governance (Akeneo/Salsify) + e-procurement catalog-first (Ariba/Coupa) + **провенанс полей**.

1. **Rich extraction.** AI извлекает максимум структурированных полей (даже не показываемых покупателю): `name, qty, unit/unit_code, mpn, gost_drawing, brand, country, category_hint, specifications{k:v}, note`. Покупатель видит чистый минимум; остальное — «под капотом» для каталога.
2. **Catalog-match-first.** Каждая строка матчится к существующему `Product`: точный `mpn+brand` → `gost_drawing` → нечёткое имя. Совпало → переиспользуем выверенную карточку (нет двойной работы).
3. **Enrich-on-miss.** Не нашли → AI/веб-обогащение как КАНДИДАТ с пометкой «AI, не подтверждено».
4. **Seller promote-to-Product (курация-гейт).** Каталог наполняет ПРОДАВЕЦ одним кликом «создать карточку» (предзаполнено из извлечения, `owner_company`=продавец, мин. правки). НЕ авто-ингест из заявки — иначе зоопарк.
5. **Провенанс/confidence на каждом AI-поле** (источник: buyer / AI / catalog / web). Главный антидот «грязным данным».

Зависимость: веб-обогащение требует внешнего search-инструмента + бюджета на запросы — отдельно. Фундамент (чистые канон-поля строки заявки: убрать `gtin`/штрихкод, добавить `gost_drawing`) делается СЕЙЧАС в `fix/rfq-clean-line-fields`.

**UI review-грида (progressive disclosure, owner-aligned 2026-06-23):** master-список + раскрывающаяся строка.
- Свёрнутая строка: `наименование · кол-во · ед.изм · MPN|ГОСТ · бейдж` (✓ найдено в каталоге / ⚠ неполно / 🤖 AI).
- Раскрытая панель: полные идентификаторы + обогащённые поля (бренд, страна, категория, спеки) с **провенансом** на поле (🤖 AI / 📋 каталог / ✍ покупатель) + inline-правка.

**Разделение редактирования (PIM data-governance):**
- **Покупатель → СПРОС** (редактирует): name, qty, unit, mpn, gost_drawing, note. Блок отправки ТОЛЬКО при отсутствии идентификатора (name|mpn|gost).
- **AI + продавец → КАТАЛОГ** (дорабатывают): brand, country, category, specifications, канон-имя, equipment_groups. Покупателя не обязываем; он может поправить, ответственность — продавца (`owner_company`). «Полнота в базе» строится курацией продавца при promote, не покупателем.
