## 🔴 P0-1 — БЛОКЕР КОНВЕРСИИ: продавец не видит свой контракт → не может подписать

**Симптом `[проверено]`.** После того как покупатель одобрил КП и подписал контракт CT-2026-00002 (статус «Ожидает менеджера»), продавец (и `diana` SALES_MANAGER, и `aziz` OWNER) на странице «Документы → Контракты» видит **«Контракты не найдены», KPI 0/0/0**. Кнопка «Перейти к контракту» со страницы сделки ведёт в тот же пустой список, а не к конкретному контракту. Итог: двойная подпись не замыкается, сделка не переходит в `CLOSED_WON`. Тот же контракт покупатель видел и подписал без проблем.

**Root cause `[по коду]` — цепочка из двух дефектов:**

1. **Страница «Контракты» контекст-нейтральна и не переключает контекст.** `frontend/src/App.tsx:337-350` — `contracts` (а также `invoices`/`payments`/`acts`/`fulfillments`) перечислены **в обоих** множествах `BUYER_PAGES` (`:340`) и `SELLER_PAGES` (`:348`). Поэтому `pageContextOf('contracts')` возвращает `null` (`:356-362`) → страница «нейтральна» и **не флипает** `activeStatus` при заходе.

2. **Дефолт контекста = BUYER, а бэк скоупит контракты по стороне контекста.** `frontend/src/store/userStore.ts:140` — `activeStatus: 'BUYER'` по умолчанию (dual-компания стартует как покупатель). Клиент шлёт `X-Active-Context: activeStatus || 'BUYER'` (`frontend/src/api/client.ts:38-39`). Бэк `backend/crm/views/billing.py:101-105`:
   ```python
   visible_deal_ids = seller_visible_deal_ids(user, self.request)   # None вне SELLER-контекста
   if visible_deal_ids is not None:
       return qs.filter(deal_id__in=visible_deal_ids)
   user_company_ids = user.memberships.filter(is_active=True).values_list("company_id", flat=True)
   return qs.filter(deal__company_id__in=user_company_ids)          # только сделки, где МОЯ компания — ПОКУПАТЕЛЬ
   ```
   В BUYER-контексте `seller_visible_deal_ids` возвращает `None` → выборка фильтрует `deal.company_id ∈ мои компании`, т.е. только сделки, где компания — **инициатор-покупатель**. Для OOO RailTech сделка #3 инициирована UTY Tashkent → исключается → **0 контрактов**.

**Почему баг «мерцающий».** Sell-side контракты продавца видны, только если `activeStatus === 'SELLER'` в момент запроса. Это случается лишь если продавец до «Контрактов» побывал на seller-only странице (`crm-deals`), которая флипнула контекст. В обычном сценарии (заход из дашборда/нав-меню) контекст = BUYER → список пуст. То же затрагивает Инвойсы/Акты/Платежи/Исполнение (те же 5 вьюсетов billing.py:223/311/331/378 с идентичным скоупом).

**Фикс `[по коду]` (backend, минимальный).** Документы-по-сделке должны быть видны участнику, чья компания на **любой** стороне сделки, независимо от UI-тумблера. В `ContractViewSet.get_queryset` (и 4 sibling-вьюсетах billing.py) заменить взаимоисключающую ветку на объединение:
```python
from django.db.models import Q
seller_ids = seller_visible_deal_ids(user, self.request) or []
user_company_ids = list(user.memberships.filter(is_active=True).values_list("company_id", flat=True))
return qs.filter(Q(deal__company_id__in=user_company_ids) | Q(deal_id__in=seller_ids)).distinct()
```
Дополнительно (frontend, чтобы не зависеть от тумблера): показывать в строке контракта индикатор стороны («Мы — продавец / покупатель») и не полагаться на `activeStatus` для документ-страниц. Правка формы ответа не меняется → `api-contract` не затрагивается.

**Приоритет.** P0 — это финальный шаг монетизируемой петли (закрытие сделки). Без него продавец не может завершить сделку в дефолтном сценарии.

## 🟠 P1 — заметные проблемы

**P1-1 · «Открытый RFQ» отсутствует как колонка Канбана + claim недостижим для точки входа.** `[проверено]` Свежая routed-заявка (этап RFQ_OPEN «Открытый RFQ») **не показывается ни в одной колонке Канбана** (колонки: Черновик / Ожидание KYC / Подбор поставщиков / Расчёт цен / КП отправлено / Договор подписан / Закрыта). При этом единственная кнопка claim живёт в Канбан-карточке. Итог: новую заявку нельзя взять в работу ни из списка (нет кнопки), ни из Канбана (нет колонки), ни со страницы деталей («Действия: только Открыть КП»). Claim становится доступен лишь когда сделка доходит до этапа, у которого есть Канбан-колонка (напр. «Договор подписан»). *(Сборку КП это не блокирует — assignment опционален, но документированный шаг «взять в работу» недостижим для входа воронки.)*

**P1-2 · Продавец приземляется на пустой buyer-онбординг.** `[проверено]` И `diana`, и `aziz` после входа видят «Добро пожаловать! Начните за 3 шага» с покупательскими карточками, хотя у компании есть входящие заявки и КП. Продавцовская сводка (очередь согласований) не показывается, т.к. контекст по умолчанию BUYER (та же корневая причина, что P0-1). Продавец не видит свою работу на главном экране.

**P1-3 · Прямой deep-link на `#request-detail/3` падает.** `[проверено]` Переход по URL на страницу деталей на холодной загрузке дал «Не удалось загрузить данные»; работает только навигация внутри приложения (известный pitfall hash-роутинга). Ломает шаринг ссылок на сделку.

## 🟡 P2 — эргономика и мелочи

- **P2-1 · Колонка «Маржа» выглядит редактируемой, но read-only.** `[проверено]` Ввод в ячейку «Маржа» не применяется; тултип поясняет «Наценка задаётся на весь КП — измените в „Настройки КП"». Пользователь (как и я) естественно пытается редактировать per-line — несоответствие аффорданса. Плюс в таблице деталей заявки колонка «Наценка» показывает **0.0%**, хотя финальная цена явно с наценкой 18% (14 160 = 12 000×1.18) — вводит в заблуждение.
- **P2-2 · Панель контракта не обновляется после подписи.** `[проверено]` И на стороне продавца («Подпись менеджера поставлена»), и покупателя («Подписать клиент» не исчезает) поле подписи остаётся «—», кнопка активна — риск повторной подписи. Реальное состояние применяется, но требует close+reopen панели (нет рефетча/оптимистичного апдейта).
- **P2-3 · «Сохранить» в «Настройки КП» не срабатывает, пока числовое поле в фокусе.** `[проверено]` Первый клик по «Сохранить» ничего не сделал (без ошибки/тоста); сохранилось только после снятия фокуса с поля маржи. Молчаливый неуспех.
- **P2-4 · Диалог «Настройки КП» выше вьюпорта — футер с кнопкой обрезан.** `[проверено]` При высоте окна ~717px кнопки «Отмена/Сохранить» не видны и модалка не скроллится внутренне; пришлось увеличивать окно.
- **P2-5 · Число `ctrl+a` не выделяет в number-инпуте.** `[проверено]` В поле «Маржа КП» `ctrl+a`+ввод дал «180» вместо «18» (вставка перед текстом). Нужен надёжный select-all/clear для числовых полей.
- **P2-6 · Строка контракта не кликабельна.** `[проверено]` В «Контрактах» открытие только через иконку «Действия» справа; в «Сделках» кликабельна вся строка — несогласованность.
- **P2-7 · Плюрализация.** `[проверено]` В истории «Deal #3: 1 продавцов» (должно «1 продавцу/продавец»).
- **P2-8 · Событие submit RFQ не залогировано в «Историю».** `[проверено]` После отправки заявки лента показала только «Заявка адресована» + «Сделка создана», без записи о переходе DRAFT→RFQ_OPEN.
- **P2-9 · Терминология этапа vs состояние подписи.** `[проверено]` Продавец видит этап «Договор подписан», покупатель для той же сделки — «В работе», а сам контракт — «Ожидает клиента/менеджера» (0 подписей). Три разных ярлыка одного состояния.
- **P2-10 · Согласование по правам, но UI называет конкретное лицо.** `[проверено]` Шаг цепочки помечен «РУКОВОДИТЕЛЬ — Aziz Kodirov», но согласовала его `diana` (SALES_MANAGER). Согласование по permission, а не по имени — имя в UI вводит в заблуждение (требует подтверждения замысла).
- **P2-11 · Канбан требует горизонтальной прокрутки; тумблер «Список/Канбан» и KPI обрезаются при 1329px.** `[проверено]` Приходилось сворачивать сайдбар. Плотность колонок Канбана велика для узких окон.

## Новые находки (собрано при исправлении P0/P1/P2 — НЕ починено попутно)

Всплыло при реализации фиксов (ветка `fix/e2e-audit-2026-07-08`). Записано, не исправлено — кандидаты в следующий заход.

1. **Лента «История» устаревает после большинства мутаций.** React-Query ключ `['timeline','deal',id]` не инвалидируется ни одной мутацией, кроме (после этого PR) submit-RFQ. Прочие мутации сделки — добавление/правка позиций, claim/назначение, смены стадий — оставляют ленту в до-мутационном кэше до полной перезагрузки. Фикс: добавить `invalidateQueries(['timeline','deal',dealId])` в `onSuccess` этих мутаций в `frontend/src/hooks/useCRM.ts`.

2. **Индикатор стороны контракта — по UI-контексту, а не по факту.** Бейдж «Мы — продавец / Мы — покупатель» вычисляется из `activeStatus` (тот самый ненадёжный сигнал из P0-1): продавец в BUYER-контексте видит «Мы — покупатель» на своём же продавцовском контракте, и бейдж одинаков для всех строк одного контекста. Правдивый фикс (api-contract): read-only `viewer_side` (`SerializerMethodField`) в `ContractSerializer` — `'buyer'|'seller'|null` сравнением company-id зрителя с `deal.company` и `DealSellerRouting`; N+1-безопасно переиспользовать set из `seller_visible_deal_ids(user, request, force=True)` (уже считается в `ContractViewSet.get_queryset`) через serializer-context; затем регенерация схемы + `gen:api-types`, бейдж читает `contract.viewer_side` с контекстом-fallback.

3. **Колонка «Наценка» на RequestDetailPage теперь всегда «—».** Per-line `QuoteItem.margin_percent` — структурно мёртвый дефолт (0), реальная наценка на уровне КП. На deal-detail эндпоинте колонка правдиво, но постоянно «—». Рассмотреть удаление колонки в этом представлении либо серверное заполнение per-line наценки, если она станет фичей.

4. **Строки `ResponsiveDataTable` не активируются с клавиатуры.** `ResponsiveDataTable.tsx` (~L76–98) вешает `onClick` без `tabIndex`/`role`/`onKeyDown` → все list-page на нём нарушают конвенцию «rows must be keyboard-accessible». Один фикс в компоненте покрыл бы все страницы (для ContractsPage a11y сделан вручную).

5. **Мёртвые i18n-неймспейсы.** `dealSplit.*` и легаси-блок `pages.deals.stages.*` (коды NEW/QUOTING/NEGOTIATION/IN_DELIVERY) не рефятся живыми компонентами — кандидаты на удаление.

6. **Дашборд dual-компании показывает только SELLER-лендинг.** После фикса контекста дашборда dual buyer+seller-компания приземляется на продавцовский дашборд (минимум); богатый комбинированный лендинг (обе воронки, дедуп KYC-баннера) отложен.

**Анкеры (drift от 670d3f7):** грид — `frontend/src/components/Admin/QuoteBuilderGrid.tsx` (не `CRM/`); список сделок — `frontend/src/pages/DealsPage.tsx`; RFQ_OPEN routed-заявки УЖЕ доходят до продавца (диагностика P1-1 подтвердила: дефекта серверного скоупа нет, причина — только достижимость claim из List-вида).

## Статус e2e и как разблокировать

Прогон доведён до подписи контракта покупателем; финальная подпись продавца заблокирована P0-1. Сделка #3 осталась в `CONTRACT_SIGNED` со статусом контракта «Ожидает менеджера». Обходной путь для завершения вручную: продавцу открыть seller-only страницу `#crm-deals`, затем сразу `#contracts` в той же сессии (пока `activeStatus=SELLER`) — контракт может появиться; но это «мерцающее» поведение и не является нормальным UX. Корректное решение — фикс P0-1.

**Приоритет исправлений:** P0-1 (блокер закрытия сделки) → P1-1 (claim/Канбан для входа воронки) → P1-2 (контекст дашборда) → P2-2/P2-3 (подпись/сохранение без обратной связи) → остальные P2.
