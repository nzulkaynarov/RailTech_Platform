code, TS hacks, flow — 47 findings). This file is the remediation backlog; fix in waves,

## Admin-role sweep — 2026-06-24 (audit now CLOSED: buyer + seller + admin all swept)

Method: same as above. Dockerized-Playwright login as `admin@railtech.uz` (Platform Admin),
all 13 admin pages (dashboard, users, kyc, subscriptions, role-apps, catalog/categories/
equipment-groups/offers, companies, deals, master-data, support) screenshotted + console/HTTP/
raw-key checks; multi-agent static root-cause pass; **every finding re-verified in this repo**
(the static agents wandered into the sibling `RailTech_B2B_Ecosystem` checkout — their file:line
citations were discarded and re-derived here).

**Baseline (good):** 0 console errors, 0 HTTP 4xx/5xx, 0 raw-i18n-key leaks on all 13 pages.
No 403/500 dead-ends (unlike the seller sweep). Companies / Master-data / KYC / Subscriptions /
Support are world-standard (filters, search, export, badges; Support empty-state is exemplary).
The real admin dashboard (`#dashboard`) is a proper platform dashboard (triage queue / pulse /
KYC actions) — **not** buyer content.

Findings:
- **A — MED / i18n (real, systemic).** DB display-names (Russian-only `.name`) rendered raw in the
  EN admin UI. Deals: `pages/AdminDealsPage.tsx:137` `<Badge>{d.stage_name}</Badge>` (also :112 search,
  :177 force-stage "before"). Users: `pages/AdminUsersPage.tsx:116` `{m.role_name ?? m.role_code}`.
  Backend ALREADY exposes the code (`crm/serializers.py:265,292` `stage_code`; `role_data.code`), and
  these pages already use the code for *logic* (stats/filtering) — only *display* leaks the raw name.
  Fix: render `t()` keyed on the code + add ru/en keys (per `lib/codes.ts` plan, item #15). Blast
  radius: every surface showing a DB lookup `*_name` (deal stages, quote statuses, system/workspace
  roles, charge types) in a localized UI.
- **B — MED / seed-data.** Retired SystemRoles leak into the Users filter chips: the chips are correctly
  DB-sourced (`useSystemRoles()`), but the DB holds `GUEST, CLIENT, EMPLOYEE, ACCOUNT_MANAGER,
  SALES_MANAGER` on top of the canonical `{ADMIN, USER}`. Migration `accounts/0010_platform_admin_model.py:58`
  deletes non-`{ADMIN,USER}`, but `core/migrations/0002_seed_enterprise_lookups.py:151` seeds them and a
  dev seed re-introduces them after 0010 → stale rows. Fix: stop seeding retired SystemRoles + clean the
  DB (`SystemRole.objects.exclude(code__in=['ADMIN','USER']).delete()`); UI auto-heals (already DB-driven).
- **C — LOW / robustness.** An unknown hash route (stale/typo'd link) falls through the page switch
  (`App.tsx` default branch) to the buyer `<Dashboard>` even for a platform admin, instead of a
  not-found/redirect. (This produced a *false* "admin sees the buyer dashboard" reading during the sweep —
  the probe used a non-existent `admin-dashboard` hash; the real route is `dashboard`. Corrected.)
- **D — LOW / wording.** Users page title "Company Users / Manage employees…" is company-scoped wording
  for what is, for a Platform Admin, the platform-wide user list.
- **E — INFO / verify.** Admin lists (Users/Companies/Deals) likely share the `DataTable` that
  paginates/sorts/searches client-side over the first server page (same as catalog H4) — not observable
  here (each list had <20 rows). Verify before these lists are trusted at scale.

**Remediation:** fold A into the existing `lib/codes.ts` migration (#15) — it's the same code→label work,
just extended to admin deals/users. B is a seed fix + one-line DB cleanup. C/D are small polish. E to be
confirmed against `components/DataTable`.
