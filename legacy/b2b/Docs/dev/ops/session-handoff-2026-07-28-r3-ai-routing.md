- `sourcing/services.py::suggest_sellers_for_deal_ai` — в модель уходят **только промахи триграма**
  (не жжём деньги на уже решённых строках). Общие куски R1/R3 вынесены в хелперы
  `_request_lines_for_routing`, `_owner_ids_for_products`, `_build_seller_suggestions`.
- `sourcing/tasks_ai.py` — хендлер `suggest_sellers` в `FEATURE_HANDLERS`.
- Фронт: кнопка «Дополнить подбор ИИ» в диалоге «Кому отправить заявку?»
  (`RequestItemsEditor.tsx`), результат мержится с триграмом по бо́льшему счёту совпадений;
  хинт и предвыбор считают по **объединённому** списку. i18n-ключи `requestItems.aiSuggest*`.

### Тарифные лимиты ИИ (решение владельца 28-07)
- План → дневная норма: `AI_DAILY_CAP_BASIC` (Старт, 75), `AI_DAILY_CAP_STANDARD` (Про, 300),
  `AI_DAILY_CAP_PREMIUM` (Безлимит, **0 = выключен**). Коды планов в БД не трогали.
- Компания без операционной подписки — прежний `AI_DAILY_JOB_CAP_FREE`.
- **Пер-компанийный override оператора** через `CompanyEntitlement(ai.daily_cap).limit` — оживили
  дремавшее поле `limit`. Промо/VIP/троттлинг абьюза руками поддержки в React Admin, а не правкой
  кода. Override выигрывает у плана. `limit=0` — это «не задан», а не «безлимит» (безлимит
  выражается планом PREMIUM).
- `FeatureKey.AI_DAILY_CAP` намеренно **НЕ** в `FREE_FLOOR` / `SUBSCRIPTION_BASELINE` — это
  носитель override, а не выдаваемая фича.
- Разрешение потолка: override → тариф плана → free-floor. У юзера в нескольких компаниях берётся
  самый щедрый (безлимит побеждает любой конечный).

## 2. Две дыры, которые нашёл ТОЛЬКО живой прогон (второй коммит `b043da5`)

**Это главный урок сессии: тесты со стабами их не ловили.**

### 2.1 Подсказка врала — предлагала продавцов, которых пикер не показывает
Пикер получателей (`accounts/views/company.py::suppliers`) отдаёт только KYC-верифицированных, а
подсказка (**и R1, который уже на проде!**) фильтра по верификации не имела. Непроверенная компания
попадала в предвыбор `selectedSellerIds` **без видимой строки**: покупатель её не видит, снять не
может, а `routeDeal` её получает.

Починка: обе стороны считают по канону `KYC_VERIFIED_CODES` из `accounts/services/kyc.py`
(`{L2_VERIFIED, L3_CONTRACTED}`) — подсказка ⊆ пикер по построению.

**Побочно вылечен второй тупик:** пикер фильтровал строго по `L2_VERIFIED` и тем самым прятал
`L3_CONTRACTED` — то есть именно законтрактованных поставщиков, которых покупатель зовёт в первую
очередь.

> **РЕШЕНО ВЛАДЕЛЬЦЕМ 2026-07-29: оставляем {L2, L3}.** Канон `KYC_VERIFIED_CODES` действует в обоих
> местах (`accounts/views/company.py::suppliers` и `sourcing/services.py::_owner_ids_for_products`).
> Законтрактованные (L3) поставщики снова видны покупателю в пикере получателей.

### 2.2 R3 был пустышкой ровно в заявленном сценарии
`match_lines_to_catalog` строит шорт-лист товаров **триграмом** по `name` + `name_canonical`.
У латиницы «relsy R65» сходство с кириллической карточкой ≈ 0 → шорт-лист пуст → `continue` →
**модель не вызывается вообще**. А `name_canonical` заполняет только файловый ИИ-импорт
(`extract_request_items`); у строки, набранной руками в гриде, его нет.

Итог: кнопка отрабатывала вхолостую именно на опечатках и латинице — том самом, ради чего делалась.

Эмпирическое подтверждение (живой ИИ, локальный стенд):
```
A. {'name': 'relsy R65 zzz', 'name_canonical': ''}   → shortlist [] → AI match []
B. {'name': 'relsy R65 zzz', 'name_canonical': 'Рельс Р65'}
   → shortlist [(6,'Рельс Р65 ГОСТ Р 51685'), (7,'Накладка двухголовая Р65')]
   → AI match: product 6, confidence 0.95
```

Починка: батчевый `canonicalize_names(names) -> {raw: canonical}` в `sourcing/services_ai.py`
(один вызов, JSON-schema, деградирует в `{}` при выключенном ИИ/ошибке) + шаг
`_canonicalize_missing_names` в `suggest_sellers_for_deal_ai` **перед** матчингом.

**Поправка к первому коммиту:** платных вызовов теперь **два** (канонизация + матчинг), а не один.

## 5. Как поднять окружение на другой машине

```bash
git fetch origin && git checkout feat/ai-routing-r3
cp docker-compose.override.yml.example docker-compose.override.yml   # если свежий клон
make up && make migrate && make seed
docker compose exec backend python manage.py init_superadmin
```

**ИИ по умолчанию выключен.** Ключ `ANTHROPIC_API_KEY` живёт только в `.env` рабочей машины (в git
его нет и быть не должно). Чтобы прогнать R3 вживую на новой машине:

1. вписать свой `ANTHROPIC_API_KEY` в `.env`;
2. `AI_IMPORT_ENABLED=true`;
3. **`docker compose up -d backend celery-worker-ai`** — именно `up -d`, а не `restart`:
   `restart` НЕ перечитывает `env_file`.

Данные для сценария (на локальной dev-БД рабочей машины они уже подготовлены; на новой машине
нужно повторить):
- продавцы «ООО Рельсы10» / «ООО Крепёж10» — тип SUPPLIER, статус **L2_VERIFIED**, с PUBLISHED-товарами
  («Рельс Р65 ГОСТ Р 51685», «Накладка двухголовая Р65», «Скрепление КБ-65 в сборе»);
- покупатель `testbuyer@railtech.uz` (компания Test Buyer Co) — **L2_VERIFIED**, иначе навигация
  урезана до T0 и «Мои заявки» не видно; пароль на рабочей машине сброшен на `Demo1234!`;
- заявка-черновик с free-text позициями латиницей.

> После смены KYC в БД **нужен перелогин** в UI: capabilities из `/me` лежат в persist-сторе,
> обычная перезагрузка страницы их не обновляет.

с **нулём шагов и нулём логов**, включая тривиальную `i18n-symmetry` (просто python-скрипт);

Workflow **Deploy b2b.railtech.uz** при этом **зелёный**. Разница: Deploy на **self-hosted** раннере,
CI на `ubuntu-latest` (**GitHub-hosted**). То есть GitHub-hosted раннеры не выдаются — исчерпана
квота минут / проблема с биллингом. **Чинится только владельцем в настройках биллинга GitHub.**

## 9. graphify — граф знаний репозитория (добавлено 2026-07-29)

**Установка на новой машине:**

```bash
uv tool install graphifyy      # ПАКЕТ называется graphifyy (две «y»), CLI — graphify
graphify install               # регистрирует скилл /graphify для Claude Code
graphify update .              # собрать/обновить граф → graphify-out/
```

**Про платный кэш — почему он переносится между машинами.** Семантический (LLM) проход по
`Docs/` стоит денег; его результат лежит в `graphify-out/cache/semantic/p{fingerprint}/` и
**закоммичен** (PR #438, 199 файлов, 1.3 МБ). Остальное в `graphify-out/` игнорируется — AST-проход
пересобирается бесплатно.

`p{fingerprint}` — это sha256 **текста промпта экстракции** (`references/extraction-spec.md` в
скилле), а НЕ путь и не машина; переводы строк нормализуются, чтобы CRLF-чекаут не выставлял счёт
заново. Имя файла внутри — хеш содержимого исходника. Отсюда переносимость.

**Как проверить, что кэш подхватился (перед тем как платить заново):**

```bash
python -c "
from pathlib import Path
from graphify.cache import prompt_fingerprint
print(prompt_fingerprint(Path.home()/'.claude/skills/graphify/references/extraction-spec.md'))"
# должно совпасть с именем каталога в graphify-out/cache/semantic/ (сейчас d5fd89c46bb5)
```

Проверено 2026-07-29 на второй машине: отпечаток совпал, **150 из 166 файлов корпуса попали в
кэш** (841 узел, 1086 связей переиспользованы) — повторной оплаты не потребовалось. Не в кэше
16 мелочей (шаблоны писем, `CLAUDE.md`, `.pytest_cache/README.md`).

Если отпечаток НЕ совпал — значит версия graphify изменила промпт экстракции; кэш будет промахнут
и корпус переэкстрагируется за деньги. В этом случае не запускать семантический проход, а сначала
поставить ту же версию graphify (сейчас **0.9.29**).
