# Аудит двух админ-панелей — React Admin и Django Unfold (19–20.08)

_Задача от владельца: «аналогичный аудит и рефакторинг админ панелей реакт и анфолд». Прогон
такой же, как по клину: панели открывались глазами в браузере, каждое утверждение подтверждалось
экраном или ответом API, находки проверялись скептиком отдельно — с обязательной классификацией
«регрессия волн 18–19.08 / было всегда / так задумано»._

**Итог: 28 подтверждённых дефектов. Ни один не оказался регрессией недавних волн — всё жило в
коде месяцами.** Ноль находок класса «сломали рефактором» — это отдельный положительный
результат прогона.

## S. Дверь в инженерную админку (единственная находка с необратимым ущербом)

Сотрудник компании-арендатора с флагом `is_staff` и **без единого права на модели** открывал
`/admin/`, видел стартовый экран с ключевыми метриками ПЛАТФОРМЫ (оборот, активные сделки,
компании) и скачивал `/admin/accounts/company/export/` — CSV на 42 компании с ИНН, банковскими
счетами и статусами KYC. Проверено вживую: файл `Company-2026-08-20.csv` получен арендатором.

Три независимые причины:

1. **Дверь**. Django пускает в админку по `is_staff`. Группа `system_engineers` и команда
   `manage.py grant_engineer` заведены ещё в апреле (`accounts/0006`), но ADR-0001 Phase 5
   остался TODO — гейта входа не было, и флаг работал в обход задуманной схемы.
2. **Выгрузка**. `django-import-export` закрывает правами только список объектов; страницы
   `/export/` и `/import/` по умолчанию не закрывает вовсе. Лечится настройками
   `IMPORT_EXPORT_{EXPORT,IMPORT}_PERMISSION_CODE`.
3. **Содержимое выгрузки**. `UserResource` вёз `role` и `is_staff`, `CompanyResource` —
   `verification_status`: загруженный XLSX раздавал права платформы и уровень KYC мимо сервисов,
   инвариантов и аудита.

Ловушка, стоившая времени: подмена сайта админки через `AdminConfig.default_site` НЕ работает,
пока `unfold` стоит в `INSTALLED_APPS` дефолтной конфигурацией — её `ready()` безусловно делает
`admin.site = UnfoldAdminSite()` и затирает наш сайт. Нужен `unfold.apps.BasicAppConfig`.

## O. Пять путей, которые не работали ВООБЩЕ

Экран есть, кнопка нажимается, запрос уходит — и упирается в стену. Тестами это не ловилось:
тесты проверяли сервисы, а мёртвыми были склейки.

| Путь | Что видел оператор | Корень |
|---|---|---|
| Создать пользователя | 400 `username`; выбранная роль молча игнорировалась | `username` обязателен у `AbstractUser`, а `role` лежит в `read_only_fields` `UserSerializer`. Даже пройди запрос — аккаунт родился бы с непригодным паролем и без письма |
| Удалить пользователя | 500 либо тихое разрушение | `CompanyMember.user` и `crm.Message.sender` каскадные (компания без администратора, исчезнувшая переписка), а таблицы истории pghistory держат живой FK с `DO_NOTHING` → `IntegrityError` |
| Отклонить заявку на роль | 415 Unsupported Media Type | классовые `parser_classes` были только multipart (нужны подаче с файлами), а модерация шлёт JSON |
| Подать заявку на роль | 403 у администратора компании, 500 у оператора | поле `company` стало read-only при закрытии M2, а `perform_create` продолжал читать его из `validated_data` — то есть всегда `None` |
| Править справочник | правка пропадала до 10 минут | `cache_page(600)` висел на `list` того же вьюсета, который выполняет запись |
| KYC-реестр | 20 записей из 42; счётчики вкладок считались по этим же 20 | оба запроса ходили без `fetchAll` (соседние реестры давно с ним) |

### Найдено уже при проверке починки KYC-реестра

Когда реестр перестал обрезаться, обнаружилось второе дно: **сумма вкладок не сходилась с
итогом** — «Всего 42», «Верифицированы 27», а «На проверке» и «Не верифицированы» по нулю при
пятнадцати строках в таблице. Причина не во фронте: `Company.verification_status` — nullable, и
часть путей его не заполняла (компания, заведённая оператором из панели — поле read-only в
сериализаторе; оффлайн-клиент из адресной книги продавца). Пятнадцать компаний жили ВНЕ любой
вкладки, показываясь подстановочным бейджем.

«Нет статуса» и «не верифицирован» различимы только для базы; для человека и для фильтра это
одно состояние. Теперь оно одно: `Company.save` ставит `L1_UNVERIFIED` на создании, миграция
`accounts/0046` заполняет исторические строки. Держит тест «сумма вкладок сходится с итогом».

## A. Действия без следа

`log_admin_action` существует и используется в KYC, слиянии компаний, break-glass и массовой
смене статуса подписок. Но мимо него идут:

- деактивация пользователя (`toggle_user_active`);
- смена системной роли (`change_user_role`);
- выдача и снятие операторской роли (`assign_operator_role`);
- выдача, правка и отзыв прав-энтайтлментов (`CompanyEntitlementViewSet` — голый CRUD);
- одиночные «Приостановить»/«Активировать» подписку: следа нет, а **массовый** вариант той же
  операции требует причину и пишет аудит — расхождение внутри одного экрана.

Отдельная поправка к первоначальной формулировке аудита: «4338 событий без автора» на живой базе
не подтвердилось. На дев-стенде из 233 записей `ActivityLog` без автора 38, и все они
**законно** безавторные: клиент открыл КП по публичной ссылке, задача просрочила КП, авто-счёт
после выигрыша сделки. Дефект не в них, а в перечисленных выше действиях оператора.

### Найдено уже при проверке волны A

Деактивация записалась, автор в базе стоял — а в журнале доступа ячейка «Автор» осталась
**пустой**, то есть запись с человеком выглядела точно так же, как системное событие без него.
Причина: `user_name` брался из `get_full_name()`, а он возвращает пустую строку, когда имя и
фамилия не заполнены — у служебных и заведённых оператором аккаунтов это обычное дело. Теперь
показывается email (как Django admin показывает username, Odoo и Stripe откатываются на логин);
безавторные события остаются безавторными — `crm/audit_display.py`.

Приостановка подписки **не** получила обязательной причины, хотя массовый вариант её требует:
это была бы новая блокировка, а владелец просил их не добавлять (PRODUCT RULE 2). Причину
принимаем и записываем, но не требуем — аудит не гейт.

## Чего в аудите НЕ нашлось

- Ни одной регрессии волн 18–19.08 (правила React Compiler, `useUrlState`, билдер КП).
- Ни одной дыры в разграничении арендаторов на стороне API `/api/v1/` — операторская плоскость
  и плоскость компании разведены; проблема была ровно в ВТОРОЙ панели (Unfold), мимо DRF.
