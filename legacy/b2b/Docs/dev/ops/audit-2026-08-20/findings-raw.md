## 1. [blocker] Сервер принимает платёж БОЛЬШЕ остатка по счёту — счёт закрывается неверной суммой, остаток уходит в минус

- **Где:** POST /api/v1/crm/invoices/{id}/record-payment/ (кнопка «Record payment», #invoices → ящик счёта); backend/crm/services/billing.py, функция record_payment
- **Что видит человек:** Обе стороны на карточке сделки #28 видят «Invoices RTYRTX-INV-2026-00001 · Paid» и «Payments Paid UZS 99,999,999,999.00» при сумме счёта UZS 73,472,000.00. В реестре счетов строка: Amount UZS 73,472,000.00 / Paid UZS 99,999,999,999.00, статус Paid. Никакой пометки о переплате нет, вкладка «Paid» пересчиталась с 2 на 3.
- **Чем подтверждено:** В браузере гейт ЕСТЬ: ввод 99999999999 → тост «Amount exceeds balance due (73472000.00)», ни одного запроса не ушло (перехват сети пуст, wedge-50-gate-overpay.png). Тем же токеном покупателя (client@uty.uz) curl POST /crm/invoices/19/record-payment/ {"amount":"99999999999.00"} → HTTP 201, выдана квитанция RTYRTX-RCP-2026-00001. В БД: Invoice 19 status=PAID, amount_paid=99999999999.00, balance_due=-99926527999.00. Скриншоты wedge-51-overpaid-buyer.png / wedge-51-overpaid-seller.png. В коде record_payment проверяет знак суммы (PAYMENT_AMOUNT_MUST_BE_POSITIVE), DRAFT (INVOICE_NOT_ISSUED), CANCELLED и «уже оплачен» (INVOICE_ALREADY_PAID) — сверки с balance_due НЕТ. (Платёж откачен мной после снятия доказательств.)
- **Почему дефект:** Единственная защита денежного реестра живёт в браузере — значит её нет: любой клиент API (или наш же фронт после регрессии) пишет в реестр сумму, которой не было. Счёт получает статус PAID при неверной сумме, остаток становится отрицательным, и на переплату уже выпущена квитанция — печатный артефакт. Эталоны денежного контура (Stripe, Odoo, QuickBooks) не дают записать поступление больше остатка без явного решения «аванс/переплата»; сам сервис в комментарии декларирует «no over-payment», но проверяет только статус.
- **Эталон:** Stripe / Odoo / QuickBooks: сумма поступления ограничена остатком, излишек требует отдельного объекта (аванс, кредит-нота)

## 2. [blocker] Оператор без права platform.settings открывает «Справочники» и «Email-шаблоны» по прямому хэшу и сохраняет правки — сервер право не проверяет

- **Где:** #admin-master-data, #admin-email-templates (аккаунт platform.thin@example.com: SystemRole=ADMIN, OperatorRole только с users.manage)
- **Что видит человек:** В боковом меню у такого оператора пунктов «Master data», «Email templates» и «Access log» НЕТ. Но если вбить адрес с #admin-email-templates, открывается полноценный редактор: он выбирает живой шаблон quote_sent, меняет тему письма, жмёт Save и получает зелёный тост «Template saved». То же со справочниками — создаёт платформенную единицу измерения.
- **Чем подтверждено:** Скриншоты platform-57-thin-admin-email-templates.png, platform-58-thin-mail-editor.png, platform-59-thin-mail-saved.png. Перехват сети: 200 PATCH admin/email-templates/2/ + 200 GET admin/email-templates/. Через API тем же токеном: POST master-data/units/ → HTTP 201 (создана единица __THIN, id=22); PATCH admin/email-templates/2/ → HTTP 200, тема живого шаблона стала «platform QA: тему письма поменял оператор без права platform.settings», updated_by_email=platform.thin@example.com; POST admin/email-templates/2/test-send/ → HTTP 200, реально ушло письмо (email_log_id=764). Для сравнения: единственный экран, где сервер отказывает, — журнал доступа: GET admin/access-log/ → HTTP 403. Код: PlatformAdminShell.tsx:128,131 ставит requires:'platform.settings', а notifications/views.py:103 — permission_classes=[IsAuthenticated, IsPlatformAdmin], master_data/views.py — IsPlatformAdminOrReadOnly; ни один из них про platform.settings не знает. Всё возвращено в исходное (тема шаблона и единица __THIN откачены).
- **Почему дефект:** Разграничение операторских суб-ролей (ADR-0004 G1) на этих двух экранах существует только в меню. Эталон O-HIDE-NOT-DISABLE требует ровно двух вещей сразу: элемента нет И сервер отказывает. Здесь вторая половина отсутствует, и оператор, которому право платформенных настроек НЕ выдавали, может переписать текст письма, уходящего клиентам всех арендаторов, и поменять справочник, на который ссылаются документы всех арендаторов. Усугубляется тем, что ни одно из этих действий не попадает в «Журнал доступа» (см. отдельную находку) — правка платформенного масштаба проходит молча и без следа.
- **Эталон:** O-HIDE-NOT-DISABLE (Odoo), SF-PROFILE-PLUS-SETS (Salesforce Setup)

## 3. [blocker] «Экспорт → XLSX/CSV» не отдаёт файл — открывает пустую вкладку приложения

- **Где:** #admin-kyc и #admin-companies, кнопка «Экспорт» → пункты XLSX / CSV (компонент AdminDataTable, triggerExport)
- **Что видит человек:** Оператор нажимает «Экспорт → XLSX». Открывается новая вкладка, в ней мигает адрес выгрузки и остаётся пустая оболочка SPA («RailTech · Платформа»). Файл не скачивается, ошибки нет, тоста нет. Повтор даёт то же самое.
- **Чем подтверждено:** Playwright перехватил открытие вкладки: адрес http://localhost:5173/api/v1/accounts/companies/export/?fmt=xlsx, итоговый URL вкладки — http://localhost:5173/, тело — «RailTech · Платформа». curl по тому же адресу: status=200 content_type=text/html size=1118 (это index.html: frontend/nginx.conf отдаёт `try_files $uri $uri/ /index.html`, прокси /api там нет). Тот же эндпоинт на API-origin: без токена 401, с Bearer — 200, application/vnd.openxmlformats-officedocument.spreadsheetml.sheet, 8723 байта. Причина: window.open(url) уходит на window.location.origin обычной навигацией, без заголовка Authorization, а JWT живёт в памяти (сессионной авторизации на /api/v1/ нет). На проде Caddy отдаёт /api/* Django — там вкладка покажет JSON 401 вместо файла. Скриншот kyc-59-export-tab.png.
- **Почему дефект:** Именованный орган управления не делает ничего из того, что обещает надписью, и молчит об этом. Обрывается путь «отфильтровал очередь → выгрузил для отчёта/комплаенса». Нарушен O-EXPORT (экспорт как рабочий инструмент списка) и базовое правило «ошибка не выдаётся за успех».
- **Эталон:** Odoo O-EXPORT

## 4. [blocker] Заявку на роль, поданную из продукта, невозможно одобрить — форма арендатора не даёт приложить документы, а сервер их требует

- **Где:** #settings → раздел «Компания» → карточка «Роль компании на платформе» → кнопка «Отправить заявку»; затем #admin-role-apps → меню строки → «Одобрить»

Диалог обещает: «Компания __QA-people-Co получит роль Поставщик... автоматически выдаётся TRIAL на 30 дней». После подтверждения — красный тост «Contract and NDA files are required for SUPPLIER», заявка остаётся в работе. Приложить документы негде: ни в форме арендатора (в ней только селект роли и кнопка отправки), ни на карточке оператора (там только ссылки «Скачать»). Действий «запросить документы»/«ожидание оплаты» в меню строки нет — только «Одобрить» и «Отклонить», хотя такие статусы в модели есть.
- **Чем подтверждено:** POST accounts/role-applications/ → 201, тело: contract_file:null, nda_file:null, partnership_agreement:null (заявка #13). POST accounts/role-applications/13/approve/ → 400 {"detail":"ROLE_APPLICATION_MISSING_CONTRACT_NDA"}. Код: accounts/services/applications.py:31-36 — SUPPLIER требует contract_file+nda_file, MANUFACTURER — partnership_agreement. Форма: frontend/src/components/Settings/CompanyRoleSection.tsx — вызывает createRoleApplication({company, requested_type}) без файлов; DOM формы: «Роль компании на платформе | Текущие роли | Покупатель | Запросить роль | Выберите роль | Отправить заявку» — ни одного input[type=file]. Меню строки в реестре оператора замерено: ['Approve','Reject']. Контрольный замер: заявка #14, созданная через API С приложенным partnership_agreement, одобрилась (200) — то есть путь работает только в обход интерфейса. Скриншоты people-a01-company-role.png, people-a09-app-card.png, people-a13-approve-dialog.png
- **Почему дефект:** Цикл «подал → рассмотрели» разорван: единственная форма подачи в продукте физически не может произвести заявку, которую можно одобрить. Ровно тот класс «показано, но не сработает», который UI-волна U1 вычищала. Эталон (Odoo/Salesforce onboarding-заявки, O-STATUSBAR): если для перехода нужны вложения, форма подачи их запрашивает, а модератор может вернуть заявку в статус «нужны документы» — здесь нет ни того, ни другого.

## 7. [blocker] Мастер компании открыт члену группы без единого модельного права и ставит KYC L2 мимо сервиса, без причины и без аудита

- **Где:** /admin/accounts/company/wizard/, шаг 3 «Роль на платформе» → селект «Статус верификации»
- **Что видит человек:** Инженер, заведённый ровно так, как предписано (manage.py grant_engineer), не может открыть ни один экран админки — но пункт «+ Создать компанию» работает. Он проходит 4 шага, на третьем в выпадающем списке выбирает «KYC подтверждён (L2_VERIFIED)» (подсказка под полем говорит лишь «Начальный статус KYC»), на четвёртом вводит e-mail владельца — и компания с подтверждённым KYC готова.
- **Чем подтверждено:** unfold.staff@qa.local: группа system_engineers, user_permissions=0, Group.permissions.count()=0. Обход всех 45 ссылок админки запросом: 200 отдают ДВЕ — /admin/ и /admin/accounts/company/wizard/, остальные 43 → 403. Прошёл мастер: создана компания id=61 «unfold-QA-Стенд», ИНН 990000111, verification_status=L2_VERIFIED, типы CLIENT+SUPPLIER, владелец id=53 + CompanyMember(OWNER, is_primary=True). Код: CompanyWizardView.dispatch проверяет только site.has_permission(request), has_add_permission(Company) не спрашивается; done() делает Company.objects.create(verification_status=...) напрямую. Скрины unfold-02…06.
- **Почему дефект:** KYC L2 — это ключ ко всей платформе (клиент получает право отправлять заявки, продавец — отправлять и выгружать КП). Здесь он выдаётся строкой в форме: без документов, без обязательной причины, без письма компании и без единой записи в журнале — то есть без всего, ради чего написан accounts/services/kyc.verify_company_kyc. Нарушены Rule 8 (логика мимо сервисов) и ST-SECURITY-HISTORY (изменение уровня доступа обязано быть именуемо и датировано). Плюс дыра в правах: экран, который ПИШЕТ, доступен тому, кто не имеет права даже ЧИТАТЬ список компаний.
- **Эталон:** Rule 8, ST-SECURITY-HISTORY, O-HIDE-NOT-DISABLE

## 8. [major] Новичок до KYC создаёт заявку, которую потом не может открыть — черновик виден в списке, но карточка отбрасывает на дашборд

- **Где:** #my-requests → «New request» → «Create»; далее клик по строке заявки или #request-detail/29. Роль: владелец новой компании до одобрения KYC (T0)
- **Что видит человек:** Человек проходит подсказку онбординга «Create your first request → Create», попадает в «Мои заявки», жмёт «Новая заявка», вводит название, жмёт «Создать». Открыть, наполнить позициями или удалить свой черновик нельзя ничем: единственная страница, где живёт содержимое заявки, ему закрыта. При этом чек-лист «Getting started» ставит галочку «Create your first request» и показывает 2 of 3 steps — то есть сообщает, что шаг выполнен
- **Чем подтверждено:** Сеть: 201 POST crm/deals/ {"id":30,"company":46,"company_name":"EDGE Audit Co",...}. База: docker compose exec -T backend manage.py shell → Deal.objects.filter(company__name__icontains='EDGE Audit') вернул «30 edge — заявка новичка DRAFT» и «29 edge — заявка новичка DRAFT». Хэш после создания: location.hash == '#dashboard'. Хэш после клика по строке: '#dashboard'. Прямой deep-link '#request-detail/29' → '#dashboard'. Скриншоты edge-t0-list-with-drafts.png (строки в реестре), edge-t0-row-click.png (отскок + тост). Корень в коде: frontend/src/config/pageRegistry.ts — строка 112 { id: 'my-requests', buyer: true, kycExempt: true, navigable: true }, а строка 105 { id: 'request-detail', buyer: true, seller: true, adminReachable: true } БЕЗ kycExempt; frontend/src/routes/pageGuard.ts возвращает { action: 'bounce', reason: 'kyc' }
- **Почему дефект:** ADR-0006 Phase E прямо разрешает до L2 «register + browse + DRAFT заявка»: блокируется только ОТПРАВКА (KYC_REQUIRED_TO_SUBMIT). Здесь разрешение выродилось в пустую оболочку — объект создаётся и учитывается, но недоступен на запись и на чтение. Обрывается первый шаг клина (заявка → КП → контракт) ровно для того, ради кого он и написан — для нового клиента. Эталон: в Odoo и Salesforce черновик, который система дала создать, всегда открывается; гейт вешают на переход состояния, а не на просмотр собственной записи. Побочно: пользователь копит неудаляемые пустые черновики (у меня их два за два прохода)

## 125. [cosmetic] Бейдж очереди KYC в сайдбаре отстаёт от экрана до минуты после вынесенного вердикта

## 127. [cosmetic] Вкладки по системной роли — единственные без счётчика, и часть пользователей не попадает ни на одну из них

- **Где:** #admin-users → полоса вкладок («Все 40», «Активен 34», «Неактивен 6», «Администратор платформы», «Пользователь»)

## 129. [cosmetic] Пустое состояние обоих экранов не подсказывает, что делать, и не отличает «ничего нет» от «ничего не нашлось»

## 130. [cosmetic] Экран удаления справочника — самый опасный текст админки — целиком на английском

- **Где:** /admin/crm/dealstage/<id>/delete/ (и любой другой /delete/)
- **Что видит человек:** Русская админка, русское меню, русская кнопка «Да, я уверен» — а сам вопрос и объяснение по-английски: «Deleting the Этап сделки 'Заявка открыта (RFQ_OPEN)' would require deleting the following protected related objects:», «Are you sure?».
- **Чем подтверждено:** Запрос с Accept-Language: ru → строка остаётся английской (проверено обоими заголовками, ru и en-US; при ru модельные имена русские, каркас фразы английский). Проверил происхождение: `translation.override('ru'); gettext("Deleting the %(object_name)s ... protected related objects:")` возвращает исходную английскую строку, msgid отсутствует в django/contrib/admin/locale/ru/LC_MESSAGES/django.po (пробел каталога Django 6.0); «Are you sure?» — там же. Скрины unfold-18/19.
- **Почему дефект:** На единственном экране, где решение необратимо, человек читает по-английски именно ту фразу, ради которой экран существует, — что удаление заблокировано и какими объектами. Происхождение стороннее (каталог Django), но видит это пользователь продукта, а у проекта есть собственный каталог локализации, куда строку можно добрать.
- **Эталон:** Rule 5
