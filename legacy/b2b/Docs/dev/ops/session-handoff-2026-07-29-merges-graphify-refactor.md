## 3. graphify — граф знаний репозитория

Установлен на второй машине. **Пакет на PyPI называется `graphifyy` (две «y»), CLI — `graphify`.**
Версия 0.9.29.

```bash
uv tool install graphifyy
graphify install      # скилл /graphify в ~/.claude/skills/graphify/
graphify update .     # сборка/обновление → graphify-out/
```

Ставит `graphify` и `graphify-mcp` в `~/.local/bin`; попутно создаёт короткий `~/.claude/CLAUDE.md`
(3 строки про триггер `/graphify`).

### Почему платный кэш переносится между машинами

Семантический (LLM) проход по документам стоит денег; результат лежит в
`graphify-out/cache/semantic/p{fingerprint}/` и **закоммичен** (сейчас 226 файлов, 1.5 МБ).
Остальное в `graphify-out/` игнорируется — AST-проход пересобирается бесплатно.

`p{fingerprint}` — это sha256 **текста промпта экстракции**
(`~/.claude/skills/graphify/references/extraction-spec.md`), а НЕ путь и НЕ машина; переводы строк
нормализуются, чтобы CRLF-чекаут не выставлял счёт заново. Имя файла внутри — хеш содержимого
исходника. Отсюда переносимость.

**Проверка ДО того, как платить заново:**

```bash
python -c "
from pathlib import Path
from graphify.cache import prompt_fingerprint
print(prompt_fingerprint(Path.home()/'.claude/skills/graphify/references/extraction-spec.md'))"
# должно совпасть с именем каталога в graphify-out/cache/semantic/ (сейчас d5fd89c46bb5)
```

Проверено 2026-07-29: отпечаток совпал, **150 из 166 файлов первой волны попали в кэш** без
повторной оплаты. Догоняющая экстракция 27 новых файлов (хендофф R3, спеки #422/#427, PDF-шаблоны,
письма) стоила **208 017 токенов** и закоммичена в #440 — иначе на следующей машине пришлось бы
платить снова.

Если отпечаток НЕ совпал — версия graphify изменила промпт: кэш будет промахнут, корпус
переэкстрагируется за деньги. Тогда не запускать семантический проход, а сначала поставить ту же
версию.

Граф на 2026-07-29: **11 361 узел, 21 675 связей, 883 сообщества**, 30 МБ в `graphify-out/`.

Паттерн — **published language / anti-corruption boundary** (DDD), в терминах Django его родная
идиома: **кастомный manager + queryset как публичный API приложения**.

### Новый API (единственный дом — `accounts/models/company.py`)

```python
Company.objects.sellers()                  # компании-продавцы
Company.objects.verified_sellers()         # продавец + пройденный KYC = «кого можно пригласить»
CompanyMember.objects.in_seller_company()  # работает и через user.memberships.…
seller_company_q(prefix)                   # фильтр по связи: owner_company__, company__
verified_seller_company_q(prefix)
```

`KYC_VERIFIED_CODES` переехал из `accounts/services/kyc.py` в `accounts/constants.py` — модель не
может импортировать сервис без цикла. Историчный путь импорта сохранён ре-экспортом.

**Побочно:** `crm/services/quotes/lifecycle.py` больше не пересобирает предикат платформенного
админа руками. Замена на `is_platform_admin` **СТРОЖЕ на одну деталь** — дополнительно требует
отсутствия активных членств. Это инвариант ADR-0003, который миграция `accounts/0010` обеспечивает
на данных: на реальных пользователях результат тот же, а расхождение теперь закрывается отказом,
а не тихим допуском. Если это нежелательно — откат в одну строку.

Миграции НЕ нужны: менеджеры не сериализуются в состояние (`use_in_migrations` по умолчанию False).

### Грабли этого рефактора (переиспользуемые)

- **Тесты мокали ФОРМУ ORM-цепочки.** `user.memberships.filter.return_value.exists.return_value`:

- **Сравнивать «грязное до меня» по линтерам надо С КОНФИГОМ репо.** Во временном каталоге без

### #451 — не распил, а устранение класса ошибки

`App.tsx` держал идентификаторы страниц в **четырёх параллельных списках**: union-тип `Page`,
наборы гейтов, инлайновый `validTypes` в `handleNavigate` и 42-веточный `switch` рендера.
Рассинхрон уже ломал продукт, и это было задокументировано прямо в коде: страницы
`clients`/`suppliers` присутствовали в рендере и в наборах контекста, но отсутствовали в
`validTypes` — клик по пункту меню молча уводил на дашборд (ADR-0005 Phase F).

Теперь `frontend/src/config/pageRegistry.ts` — единственный источник; все наборы выводятся из него.
Реестр объявлен через `as const satisfies readonly PageDefinition[]`: форма строк проверяется,
но литеральные типы `id` сохраняются — именно на них держится сужение дискриминированного `Page`.
**Это поймала `npm run build`, а `tsc --noEmit` пропустил** — подтверждение известного правила:
типы в этом репозитории проверяет только сборка.

Доказательство отсутствия изменения поведения (гейты — граница безопасности, «собралось»
недостаточно): 6 тестов сверяют каждый выведенный набор с прежним литеральным, переписанным с
`App.tsx` на `67d7feb` и намеренно **не** выводимым из реестра. Прежние 21 тест гейтов не тронуты —
изменена одна строка импорта.

**Открытый вопрос владельцу.** `navigateTo` не кладёт id в хэш параметризованных маршрутов:
переход «назад» из билдера КП пушит `#request-detail` без номера сделки. Назад/вперёд работают
(id едет в `history.state`), но жёсткое обновление страницы уводит на список заявок вместо карточки.
Поведение унаследованное; сохранил как есть, чтобы не размывать доказательство эквивалентности.
Сборка хэша теперь централизована в `pageToHash` — починка правит одну функцию.

### Хвост волны — #452–#455

**#452 — два дефекта, найденных в #451.** Тогда я сохранил поведение как есть, чтобы не
размывать доказательство эквивалентности, и вынес вопрос отдельно; здесь починка.

1. `pageToHash` подставлял идентификатор только для `product_detail`; `request-detail` и
   `deal-quote` уходили в историю голыми. Назад/вперёд не страдали (страница едет в
   `history.state`), но URL переставал описывать экран: обновление страницы, закладка или
   отправленная коллеге ссылка уводили с карточки сделки на список заявок. Прямые присвоения
   `window.location.hash` (корзина, очередь согласования, уведомления) номер клали ВСЕГДА —
   расходился ровно путь через `navigateTo`, то есть кнопка «Назад» из билдера КП.
2. Голый `#deal-quote` без номера проваливался в общий `return { type: path }` и монтировал
   билдер КП с `dealId: undefined` — сломанный экран. У соседней ветки `request-detail` голая
   форма обрабатывалась, у этой нет.

#### #460 — подписание акта отдавало 500 (самая ценная находка волны)

```python
Act.objects.select_for_update().select_related("status")   # Act.status = null=True
```

`select_related` по nullable FK даёт LEFT OUTER JOIN, а PostgreSQL запрещает `FOR UPDATE` по
его nullable-стороне:

```
NotSupportedError: FOR UPDATE cannot be applied to the nullable side of an outer join
```

Путь живой и пользовательский: `billingApi.ts` → `POST crm/acts/{id}/sign/` →
`views/billing.py:515` → `sign_act`. **Код был непокрыт ровно потому, что никогда не
выполнялся успешно.**

Починка — `select_for_update(of=("self",))`. Проверил все шесть мест связки
`select_for_update()` + `select_related()` в сервисах: nullable-поле только здесь
(`Invoice.deal`, `Contract.deal`, `Fulfillment.deal`, `DealSellerRouting.deal`,
`QuoteItem.quote` — все NOT NULL).
