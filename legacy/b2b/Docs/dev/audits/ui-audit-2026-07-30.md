# Полный аудит UI (React): узкие места, тупики, сломанное и мёртвое

_Дата: 2026-07-30. Статус: **АУДИТ ЗАКРЫТ — восемь волн реализованы и на проде** (PR #473–#481). Разбор ниже сохранён как есть; что сделано и что осталось — в §8 и §9._
_Охват: 344 модуля (42 страницы, 209 компонентов, 26 хуков, 28 API-модулей) — весь `frontend/src`._
_Метод: граф знаний (graphify, 11 724 узла) + пять детекторов по коду + прогон всех страниц под тремя ролями на живом стенде. Каждая находка — с file:line._

---

## 0. Главный вывод: продукт не «дырявый», у него один системный разрыв

Три вещи, которые обычно ищут в таком аудите, здесь **в порядке**, и это важно зафиксировать:

- **мёртвого кода почти нет** — из 334 модулей недостижимы 12, и все 12 это неиспользованные примитивы shadcn (вендорная поставка), значимых нет;
- **битых ссылок нет** — все 20 целей навигации существуют в реестре страниц;
- **ошибки мутаций не глохнут** — глобальный `MutationCache.onError` (`lib/queryClient.ts:20-25`) тостит любую; `alert()`/`confirm()` нет ни одного; все 20 форм защищены от двойной отправки.

Проблема одна и повторяется в 13 местах:

> **Бэкенд отдаёт объект обеим сторонам сделки (видимость правильная), а МАРШРУТ к нему закреплён за одной ролью статическим списком.**
> Виджеты показывают то, что вернул сервер; гейты пускают по тому, что записано в `pageRegistry`. Эти два источника правды разошлись.

Второй по значимости класс — **интерфейс молчит о сбое**: там, где запрос упал, пользователь видит не ошибку, а ноль или «данных нет».

## 1. Тупики доступа: 13 мест, 5 групп

Матрица снята **фактом** — прогоном всех страниц под каждой ролью на живом стенде.

**Покупателю открыты договоры, счета, платежи и отгрузки — и закрыты только акты.** Это единственное исключение из собственной архитектуры продукта.

## 2. Интерфейс молчит о сбое

Здесь пользователь получает не ошибку, а ложную картину. Отсортировано по вреду.

### 2.1 Цифры, которые врут нулями

**Виджеты дашборда не читают состояние запроса вовсе** — проверено фактом: в `components/Dashboard/DashboardWidgets.tsx` **ноль** упоминаний `isLoading`/`isError` на 11 запросов (строки `:85-88, :137-139, :191-192, :216-217`).

При недоступном API плитки «КП на утверждении», «Договоры на подписи», «Заявки без КП», «Счета к оплате», «Просрочено» покажут **0**. Руководитель решит, что работы нет. То же на панели оператора: `pages/PlatformAdminDashboard.tsx:50` (`PulseCards`) и `:74` (`SummaryPanel`) покажут MRR и очередь KYC равными нулю.

### 2.2 Списки, которые говорят «данных нет» вместо «ошибка»

- `pages/AdminLeadsPage.tsx:28` — `isError` не читается: при 500 таблица напишет «Лидов нет».
- `pages/DealsPage.tsx:204-209` — канбан рендерится **до** проверки ошибки: пустые колонки без объяснения и без «Повторить».
- `pages/AdminEntitlementsPage.tsx:194` — нет `isLoading`: во время загрузки видно «прав нет».

### 2.3 Молча пустые справочники (~35 мест)

Выпадающие списки валют, единиц, категорий, базисов поставки при отказе API становятся пустыми без объяснения — пользователь не может заполнить форму и не понимает почему. Полный список в срезе; примеры: `components/CRM/QuoteSettingsDialog.tsx:56-57`, `components/Cabinet/CompanyDefaultsSettings.tsx:78-86`, `components/Billing/RecordPaymentDialog.tsx:47`.

### 2.4 Тихие сбои действий

- `components/Layout/NotificationCenter.tsx:102,121,175,202,210` — «прочитано» молча не срабатывает.
- `pages/CatalogImportPage.tsx:68` — если статус-эндпоинт недоступен, **прогресс импорта замирает навсегда**, без объяснения.
- `store/currencyStore.ts:61` — курс молча остаётся резервным, а по нему считаются отображаемые суммы.

## 3. Действия, недостижимые по построению

### 3.1 Документ нельзя получить, пока его нет — 7 мест

Класс, найденный на актах и подтверждённый по всему UI. Сервер устроен правильно: запрос на скачивание **сам ставит рендер и отвечает 202** (`backend/crm/views/billing.py:30-41`), а фронтовый `lib/download.ts` умеет опрашивать. Но кнопка скрыта условием «файл уже есть»:

`pages/ActsPage.tsx:164,201` · `pages/ContractsPage.tsx:381` · `pages/InvoicesPage.tsx:345` · `components/CRM/DealDocumentsCard.tsx:75` · `pages/OtherDocumentsPage.tsx:368` (+ `signed_file_url` на `ActsPage:208`, `ContractsPage:388`).

Ни в одном месте нет ни подсказки, ни состояния «готовится». Проверено на живом стенде: у акта PDF отсутствовал, ручной запуск рендера отработал за секунду — механизм исправен, недостижим только вход.

Рядом есть **правильный образец**: `pages/request-detail/QuoteView.tsx:104` — кнопка PDF рендерится безусловно и работает через 202.

### 3.2 Возможности без входа в интерфейс

- **Главное изображение товара назначить нельзя**: кнопка есть (`components/Shared/ImageGalleryUpload.tsx:115`), но проп `onSetMain` не передаёт ни один потребитель.
- **Баннер подписки невозможно закрыть**: `components/Shared/SubscriptionStatusBanner.tsx:118`, проп `onDismiss` не передаётся.
- **Заявку на роль подать нельзя** — хук `useCreateRoleApplication` (`hooks/useAccounts.ts:436`) не вызывается нигде, при том что операторская страница модерации таких заявок существует и работает.
- **Права участника (`can_sell`/`can_buy`) сменить нельзя** — `useUpdateMemberCapabilities` (`hooks/useAccounts.ts:99`) не вызывается.
- **Экспорт КП в xlsx/csv недостижим** — `collabApi.exportQuote` (`api/crm/collab.ts:46`) не вызывается; комментарий в `api/crm/quotes.ts:103` при этом ссылается на метод, который тоже мёртв.
- **«Снять с себя сделку»** — `useReleaseDeal` (`hooks/crm/deals.ts:141`) не вызывается.

### 3.3 Ложная сортировка

`SortableHead` всегда рисует курсор-указатель и стрелки, но у пяти колонок обработчик пустой:
`pages/AdminDealsPage.tsx:131,132` · `pages/ProductManagement.tsx:213,214,215`.

## 5. Мёртвое

- **12 недостижимых модулей**, все — неиспользуемые примитивы shadcn (`ui/combobox.tsx`, `ui/field.tsx`, `ui/item.tsx`, `ui/empty.tsx`, `ui/KPICard.tsx` и др.). Для вендорной поставки это норма; удалять не обязательно, но `ui/EmptyState.tsx` стоит убрать отдельно — он **дублирует имя** рабочего `EmptyState` из `pages/shared/PageShell` и провоцирует ошибочный импорт.
- **11 методов API и 13 хуков без вызовов** (список в §3.2 и в срезе) — часть из них симптом отсутствующих экранов, а не просто мусор.

Сырых ключей пользователю не показывается нигде. Неиспользуемых словарей подписей (`*_LABEL_KEY` в `lib/codes.ts`) — 13, что означает: соответствующие статусы выводятся сырым кодом сервера вместо локализованной подписи.

## 6. Что это значит и в каком порядке чинить

Порядок — по вреду для пользователя, а не по объёму работы.

### Волна U1 — «объект показан, значит доступен» (устраняет 13 тупиков)

Корень в том, что маршрутизация опирается на статический список ролей, а видимость — на данные сервера. Лечится не заплатками в 13 местах, а **одним правилом**: страница документа доступна тому, кому этот документ виден.

Практически: `acts`, `deal-quote` и `crm-deals` перестают быть SELLER-only (список и так сужен видимостью на бэкенде — покупатель увидит только свои). Оператору открываются `request-detail` и `invoices`, куда ведут его собственные страницы. Онбординг и баннеры до KYC ведут туда, куда пускают.

### Волна U2 — интерфейс перестаёт врать

Виджеты дашборда и панели оператора читают `isError`/`isLoading` и показывают «не удалось загрузить» вместо нуля. Списки (`AdminLeadsPage`, канбан `DealsPage`, `AdminEntitlementsPage`) отличают ошибку от пустоты. Справочники в формах сообщают о сбое загрузки.

### Волна U3 — документ всегда достижим

Блок действий документа показывается всегда: есть файл — скачать, нет — «Сформировать» (эндпоинт уже умеет это по 202). Один общий компонент вместо семи разных условий; заодно закрывает предпросмотр, которого просил владелец.

### Волна U4 — безопасность необратимых действий

Подтверждение для 11 действий и `disabled` на время выполнения для 8 кнопок. Механика в проекте уже есть (`ConfirmActionDialog`), нужно применить единообразно.

### Волна U5 — уборка

Удалить дублирующий `ui/EmptyState.tsx`, снять ложную сортировку с пяти колонок, починить единственный i18n-ключ, решить судьбу мёртвых API-методов: либо дать им экран (экспорт КП, заявка на роль, права участника), либо удалить.

## 7. Чего в этом аудите нет

Сознательно **не предлагаю новых функций**: ни одна волна выше не добавляет возможностей, которых нет в бэкенде. Всё перечисленное — доведение до рабочего состояния того, что уже реализовано, но недостижимо, молчит или врёт.

Не проверялись: визуальная вёрстка и адаптивность под мобильные, доступность (a11y), производительность рендера. Это отдельные оси, если понадобятся.

## 8. Что сделано (дописано 2026-07-30, после реализации)

Все пять волн реализованы и смержены в `main`. Каждая закрывала не список мест, а правило.

| PR | Волна | Правило, которое теперь держит тест |
|---|---|---|
| #473 | U1 | «объект показан — значит доступен»: маршрут документа вычисляется по стороне зрителя (`lib/documentRoute`), акты стали двусторонней страницей, `handleNavigate` переведён на общий `evaluatePageGuard` |
| #474 | U2 | упавшее чтение не выглядит как «данных нет»: `QueryCache.onError` симметрично мутациям, у виджетов и списков три честных состояния |
| #475 | U3 | документ можно получить, пока он рисуется: кнопка не ждёт готового файла, сервер сам ставит рендер (202) |
| #476 | U4 | необратимое действие спрашивает, повторный клик не проходит |
| #477 | U5 | несортируемая колонка выглядит несортируемой; мёртвое удалено |

### Найденное по дороге (чего в аудите не было)

- **`capabilities.can_sell` считался не тем предикатом**, что авторизация: плоский флаг участника
  по умолчанию `True` у любого члена, поэтому SPA показывала продавцовские поверхности члену чисто
  покупательской компании. Сведено к серверному `is_seller` (членство И тип компании).
- **Бэкенд отдавал готовый маршрут SPA** (`hash` в фиде документов и поиске), не зная про её гейты —
  именно оттуда шли продавцовские ссылки у покупателя. Поле удалено из контракта.
- **`pdf_available`** после U3 не читается никем и удалён: флаг «файл уже существует» — приглашение
  снова закрыть им кнопку.

### Поправка к аудиту

Пункт §3.2 «**Экспорт КП в xlsx/csv недостижим**» — **неверен**. Экспорт живёт в правой панели
билдера (`EconomicsRail`) и поддерживает все три формата; недостижима была не функция, а вторая,
лишняя реализация (`collabApi.exportQuote`), которую и удалили.

### Что осталось открытым — это продуктовые решения, не дефекты

Три возможности бэкенда по-прежнему без экрана. Ни одна не является поломкой: это выбор владельца,
нужны ли они.

1. **Права участника** (`can_sell` / `can_buy`) сменить в интерфейсе нельзя — эндпоинт и модель
   per-member capabilities (ADR-0002) есть, экрана нет. Ближе всего к «архитектура не доведена»:
   раздача прав описана как обязанность OWNER'а.
2. **«Снять с себя сделку»** — `claim` есть, обратного действия нет: менеджер, взявший заявку по
   ошибке, остаётся с ней.
3. **Заявка на смену роли компании** — операторская страница модерации таких заявок работает, а
   подать заявку неоткуда. Это полноценный экран, то есть новая функция.

## 9. Продолжение 2026-07-31: волны U6–U8

Аудит перечислял §3.2 «возможности без входа в интерфейс» как список мёртвых хуков. Разбор
показал, что список неоднородный: часть из них — **недоведённая архитектура** (модель и эндпоинт
есть, обязанность вменена ролью, а сделать это негде), часть — дубликаты, вытесненные живыми
путями, и лишь часть — действительно недостающие экраны.

| PR | Волна | Что |
|---|---|---|
| #478 | U6 | Возврат сделки в очередь (эталон — очереди Salesforce) и раздача прав участника (эталон — Odoo: права на карточке пользователя). Право на возврат считает СЕРВЕР — новое поле `viewer_can_release` |
| #480 | U7 | Карточка акта показывает то, что сервер уже отдаёт: обе подписи двустороннего акта с именами, «чей сейчас ход», причина возврата |
| #481 | U8 | Четыре мёртвых дубликата удалены вместе с их методами api и типом `ActivityLog`; два оставшихся пробела помечены комментарием прямо в коде |

### Приём, который стоит повторять

В U6 понадобилось новое право на действие. Вместо клиентского вывода добавлено серверное поле
`viewer_can_release`, а тест требует, чтобы **подсказка СОВПАДАЛА с результатом сервиса** для
каждого действующего лица (владелец, админ компании, коллега без прав, конкурент, админ
конкурента, покупатель). Расхождение предикатов означает кнопку там, где действие откажет —
ровно тот класс, который вычищала волна U1. Лекало годится для любой новой `viewer_can_*`.

### Что осталось — ровно два, и это решения, а не дефекты

1. **`useCreateRoleApplication`** — операторская модерация заявок на роль компании работает,
   а подать заявку неоткуда: нужен новый экран.
2. **`useAdminActivity`** — пообъектная история для оператора: эндпоинт есть, поверхности нет.
   Естественный дом — карточки в операторских реестрах.

Оба помечены комментарием над объявлением, чтобы следующий прогон детектора не предложил их
удалить как случайный мусор. Детектор после уборки: мёртвых методов api — ноль.
