# Двуязычный контур RU/EN — глобальный подход (бенчмарк + план волн)

_Дата: 2026-08-02. Повод: владелец — «сначала привести в порядок русский и английский в
бэкенд- и фронт-части, нужен глобальный подход». База: полная инвентаризация i18n-разрывов
(аудит-агент 02-08, 18 областей). Статус: НА УТВЕРЖДЕНИИ._

## 1. Что говорят эталоны

| Эталон | Паттерн | Суть |
|---|---|---|
| **Django canon** | LocaleMiddleware chain | Язык запроса: cookie/предпочтение → Accept-Language → default; gettext-каталоги (.po/.mo); `translation.override(lang)` для фоновых задач |
| **Odoo** | `partner.lang` + recipient rendering | Язык — свойство ПОЛУЧАТЕЛЯ: письма и отчёты рендерятся `with_context(lang=partner.lang)`, а не языком запросившего |
| **Odoo (16+)** | Translatable fields = JSONB | Переводимые поля моделей хранят `{lang: value}` с фолбэком на базовый язык — канон для справочников |
| **Stripe** | `preferred_locales` on Customer | Локаль получателя (массив в порядке предпочтения) локализует счета/квитанции/письма. **Custom fields не переводятся** — пользовательский контент остаётся языком автора |
| **Наш же ARCH-05** | Codes over the wire | `{"detail": CODE}` + `apiErrors.*`, `stage_code` + `lib/codes.ts` — слова живут на краях, по проводам ходят коды. Уже работает для 17 неймспейсов |

**Синтез: три принципа глобального подхода**
1. **Язык — свойство получателя, не запроса** (Odoo/Stripe): письма, уведомления, публичные
   страницы — язык АДРЕСАТА (`user.preferences.language`); API-ответы — язык запроса.
2. **По проводам — коды, слова — на краях** (Stripe API / наш ARCH-05): расширить паттерн на
   уведомления и каталоги, а не тащить переводы в БД.
3. **Пользовательский контент не переводится** (Stripe): названия компаний/товаров, кастомные
   шаблоны, wording-варианты — язык автора. Переводим только ПЛАТФОРМЕННЫЙ текст.

## 3. Волны

* **L0 — фундамент активации** (без него остальное мертво): LocaleMiddleware; axios-интерсептор
  шлёт `Accept-Language: i18n.language`; `resolve_user_language(user)` (preferences → 'ru');
  `locale/en/` каталог + makemessages/compilemessages в Makefile и Docker build; смоук-тест
  «Accept-Language: en → DRF-ошибка валидатора по-английски». Бесплатный выигрыш: 1500
  готовых `_()` оживают (Unfold, DRF built-ins, choices).
* **L1 — коды на краях**: Notification.event_code/params (+сериализатор, NotificationCenter
  локализует, RU-fallback для legacy); label_key в каталогах документов; докодировать
  detail-фразы. Закрывает и `core/services.py:39` (ключи-сироты в титулах тикетов).
* **L2 — письма получателю**: {% trans %} в 18 бандлах + en.po; язык адресата в
  send_templated_email; EmailTemplate-оверрайд: `unique(key)` → `unique(key, language)`.
* **L3 — фронт-полировка**: formatDate/formatMoney-хелперы (замена 58 мест), Intl.DisplayNames
  для стран/валют, списочный переключатель, generalized CI-скрипт.

Каждая волна — отдельный PR с полными гейтами и eyes-on (EN-проход экранов/письма).

## 4. Чего сознательно НЕ делаем
Перевод юр-PDF и «суммы прописью» на EN (отдельное направление по запросу); перевод
пользовательского контента; переписывание RU-истории в БД; django-modeltrans/parler —
пока языков два и решает Intl.DisplayNames, схему справочников не трогаем.

## 5. Почва под узбекский (решение владельца 2026-08-02)

Владелец: «после того как система будет широко использоваться, нужно добавить узбекский с
возможностью кириллицы и латиницы, но пока подготовить почву для русского и английского».

### Что выяснил бенчмарк про ДВА СКРИПТА одного языка

* **Django поддерживает скрипт-варианты нативно**: формат имени локали `ll_Scrp`
  (`sr_Latn`, `uz_Cyrl`, `uz_Latn`) — язык строчными, скрипт с заглавной. Отдельного
  механизма не нужно, это обычные локали.
* **CLDR содержит готовые двусторонние правила транслитерации `uz-Cyrl ↔ uz-Latn`**
  (Unicode transform charts), есть открытые реализации.
* **MediaWiki LanguageConverter** — канон для языков с двумя системами письма: контент
  хранится в ОДНОМ скрипте, второй получается конвертацией на лету.

**Вывод, который меняет оценку работы:** узбекский — это **один перевод плюс
транслитерация**, а не два перевода. Держать в актуальности два узбекских каталога не
придётся: `uz-Latn` переводится, `uz-Cyrl` получается конвертацией (и наоборот, смотря
какой скрипт выберем исходным).

### Что значит «подготовить почву» — требования к L2/L3

Ни одно место в коде не должно знать, что языков ровно два:

1. **Реестр локалей — данные, а не код.** Один список на фронте и `settings.LANGUAGES` на
   бэке; ВСЁ остальное (переключатель, детектор, форматирование) читает его.
2. **Коды BCP 47 со скриптом должны проходить всю цепочку**: `Accept-Language: uz-Latn` →
   Django (`uz_Latn`) → i18next → `Intl.*`/date-fns. Никаких `language === 'ru' ? … : …`.
3. **Переключатель — список**, а не тумблер на два значения.
4. **CI-гейт симметрии — на N локалей**, а не на два захардкоженных файла.
5. **Даты и деньги — через локаль интерфейса**, а не через прибитый `'uz-UZ'`.
6. **Письма — через gettext-каталоги**, чтобы новый язык означал новый `.po`, а не 18 новых
   файлов шаблонов на каждый язык.

Эти требования и есть содержание волн L3 (почва) и L2 (письма) ниже. Сам узбекский НЕ
добавляем — по решению владельца это работа «после широкого использования».
