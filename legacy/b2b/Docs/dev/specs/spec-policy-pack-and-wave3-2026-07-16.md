## 0. Скоуп и процесс

Пять утверждённых направлений: (P1) AI-гейтинг compose/enrich/extract; (P2) register-энумерация; (P3) sync-PDF экспорт → 202; (P4) удаление orphan-эндпоинтов; (P5) волна 3 КП-конструктора + fast-follows. Итого **~9 PR в 3 волны**.

Процесс (отработан волнами 0–2): параллельные Opus-агенты — **один backend-лейн** (main-репо, Docker) + **frontend-лейны в worktree**; грид-задачи сериализуются (один файл); адверсариальное ревью объединённой волны ДО мержа (обязательные гейты: `npm run build`, backend `pytest --create-db`, линт с репо-root конфигом); фиксы MAJOR оркестратором; мерж по подтверждению владельца; проверка деплоя + бандла на VPS. Тесты каждого PR в своём файле; i18n оба языка; контракт-регенерация при изменении API.

## 1. P1 — AI-гейтинг compose/enrich/extract (аудит #13, policy-часть)

**Сейчас:** `enrich` (catalog/views/ai.py:62), `compose` (views_ai_conversational.py:74), `extract` (sourcing/views.py:846) гейтятся только `AI_IMPORT_ENABLED` + throttle + общий спенд-кап #331 (300/день). Ни entitlement, ни KYC. `FeatureKey`: FREE_FLOOR={ai.match, ai.preflight}; SUBSCRIPTION_BASELINE={quote.send, quote.export, ai.draft, roles.custom}.

**Предлагаемая матрица (НА УТВЕРЖДЕНИЕ — это бизнес-решение):**

| Фича | Кто пользуется | Предложение | Обоснование |
|---|---|---|---|
| `enrich` (PIM-обогащение каталога) | Продавец | **Новый `FeatureKey.AI_ENRICH` → SUBSCRIPTION_BASELINE** (как ai.draft) | Продавец — монетизируемая сторона; PIM — премиум-инструмент |
| `extract` (разбор документа заявки) | Покупатель | **Остаётся бесплатным** (новый ключ `AI_EXTRACT` в FREE_FLOOR для явности) | Wedge-воронка ADR-0006: AI-разбор заявки = крючок привлечения покупателя; пейволл убьёт acquisition |
| `compose` (диалоговое составление заявки) | Покупатель | **Остаётся бесплатным** (`AI_COMPOSE` в FREE_FLOOR) | То же |
| **Двухуровневый спенд-кап** | Все | Компания БЕЗ операционной подписки → `AI_DAILY_JOB_CAP_FREE` (дефолт **30**/день); с подпиской → существующий `AI_DAILY_JOB_CAP_PER_COMPANY` (300) | Free-абьюз ограничен в 10× жёстче, подписчики не замечают |

**Реализация (backend, 1 PR):** ключи в `accounts/constants.py`; гейт `has_entitlement(company, AI_ENRICH)` в enrich-вью (403 `AI_FEATURE_NOT_ENTITLED` — код новый, перевод ru+en); `ai_spend_cap.py` — выбор капа по `seller_subscription_operational` компании; тесты (enrich без подписки → 403, с подпиской/промо-грантом → 202; free-кап 30 срабатывает, подписочный 300; DEMO-override через CompanyEntitlement работает). Фронт: перевод кода + обработка в enrich-диалоге (grep вызова enrich в src). Схема: 403 в extend_schema → регенерация.

## 2. P2 — Нейтрализация register-энумерации (аудит #11)

**Сейчас:** `POST auth/register/` на существующий email → 400 `USER_EMAIL_ALREADY_EXISTS` (оракул существования аккаунта); forgot-password уже нейтрален (200 всегда).

**Дизайн (стандарт индустрии):** регистрация ВСЕГДА отвечает **201 + то же нейтральное сообщение** («письмо отправлено, проверьте почту»). Если email занят активным аккаунтом — вместо setup-письма шлём (async, через send_transactional_email из #327) письмо «Вы пытались зарегистрироваться, но аккаунт уже существует — войдите или восстановите пароль» (новый шаблон `emails/register_existing_account.*`). Если занят НЕактивным (pending) — повторно шлём setup-письмо (идемпотентная перерегистрация, УЛУЧШЕНИЕ текущего UX-тупика). Timing-канал закрыт: обе ветки только ставят Celery-задачу.
**UX-изменение (утверждено вами):** честный пользователь с существующим аккаунтом больше не видит «email занят» на форме — узнаёт из письма. Фронт: убрать обработку USER_EMAIL_ALREADY_EXISTS из KYCRegistrationForm (показывать нейтральный success-экран всегда).
**Реализация:** backend `accounts/services/auth.py::create_pending_user` (1 PR, тесты: существующий active → 201 + existing-письмо, ничего не сломано; pending → 201 + повторное setup; новый → как раньше; коды/тайминг не различимы) + фронт-упрощение + i18n. Login lockout / throttle не трогаем.

## 3. P3 — Sync-PDF экспорт КП → 202 (хвост ARCH-03)

**Сейчас:** `GET crm/quotes/{id}/export/?format=pdf` → `handle_quote_export` (exports.py:17) → WeasyPrint **inline** (`services/quotes.py:711`) — блокирует ASGI-воркер; xlsx/csv лёгкие, остаются sync.

**Дизайн:** зеркалим готовый паттерн `download-pdf` (#232, ARCH-03): pdf-ветка `handle_quote_export` → если `pdf_file` актуален — стрим; иначе enqueue `render_document_pdf` + **202 {task_id?/Retry-After}** в том же формате, что download-pdf (изучить и переиспользовать точный контракт + фронт-поллинг download-pdf — grep `download-pdf` в src). «Актуальность» PDF: инвалидация по `updated_at` квоты vs mtime файла ИЛИ существующий признак (изучить, как download-pdf решает свежесть; если никак — рендерим при отсутствии файла, как download-pdf, и фиксируем ограничение).
**UX-изменение (утверждено):** клик «Экспорт PDF» при холодном кэше → короткое «готовится…» с авто-скачиванием (существующий поллинг-механизм), вместо зависшего запроса. xlsx/csv — без изменений.
**Реализация:** backend (1 PR: exports.py ветка + тест 202/200 + schema) + фронт (та же точка, что зовёт export?format=pdf — переиспользовать download-pdf-поллинг; тест).

### 5.3 Optimistic locking QuoteItem (1 PR, full-stack, после 5.2)
Backend: `version` (IntegerField default 0) на QuoteItem + миграция; `OptimisticLockingMixin` (core/optimistic_locking.py — образец QuoteViewSet) на одиночный PATCH и **bulk-update** (пер-строчная проверка version в сервисе, конфликтные строки в rows-ошибках кодом `QUOTE_ITEM_STALE`); schema-регенерация. Frontend: version в payload save; 409/STALE → диалог «строки изменены коллегой» с перечнем + кнопка «Обновить» (рефетч, dirty-строки конфликтные сбрасываются осознанно). Тесты обеих сторон.

### 5.4 Каскад-визуализация charges (1 PR, frontend, параллельно 5.3)

Данные уже в quote.charges (sort_order, amount/rate, resolve_signed-семантика — зеркалить backend `models/charges.py`); строка «ниже floor» подсвечивается (guardrail-вижуал, спека §5 п.18 — только индикация, approval-роутинг НЕ трогаем).
