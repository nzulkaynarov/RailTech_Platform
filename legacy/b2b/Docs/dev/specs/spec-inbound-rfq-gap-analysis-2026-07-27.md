# Гэп-анализ: входящая заявка → черновик КП (front of the wedge) — 2026-07-27

_Статус: НА УТВЕРЖДЕНИЕ владельцу. Запрос: «делай гэп-анализ, одобряю» (27-07)._
_Метод: полная карта текущего пути по коду (6 сегментов, agent-проход) + бенчмарк Odoo CRM/Sales,
Bitrix24, Salesforce (источники внизу). Кода в этом PR нет — только анализ и целевой путь._

## Зачем именно этот фронт

Выход клина (документы: КП/договор/инвойс/акт + онлайн + письма) отполирован волнами D0–D1e и
типографикой. Максимальная же «разница между ручной и автоматизированной работой» — цель платформы —
живёт на ВХОДЕ клина: заявка упала → продавец узнал → КП родился черновиком. Сейчас этот путь
работает, но требует 4–6 ручных шагов на двух экранах, и продавец может вообще не узнать о заявке.

## Бенчмарк: как это решают эталоны

| Паттерн | Odoo | Bitrix24 | Salesforce |
|---|---|---|---|
| **Продавец мгновенно узнаёт** | popup-уведомление при назначении лида (native bus) + automated action «email назначенному» | счётчики на иконках + мгновенное уведомление в чат о горячем лиде + email (мгновенно/ежечасно/ежедневно) | assignment rules → email alert назначенному/очереди; практика: push/SMS в момент падения лида |
| **Speed-to-lead — деньги** | — | — | ответ в 5 минут = 9× вероятность конверсии (Salesforce); 5→30 мин = −21× к квалификации (MIT/InsideSales); медиана B2B — 42 часа (проигрышная) |
| **Один клик до документа** | кнопка **New Quotation** на opportunity: quotation создаётся с предзаполненным клиентом/позициями, стадия НЕ гейтит | лид→сделка конвертация одним действием | конвертация Lead→Opportunity одним действием |
| **Очередь с возрастом** | activities «просрочено» краснеют | счётчик «Запланированные» = просроченные дела | queue + Omni-Channel routing «пока лид горячий» |

Именованные паттерны: **instant-assign-notification** (все трое), **one-click-quotation** (Odoo),
**aging-counters** (Bitrix24). Кастома в целевом пути нет — только эти три.

## Текущий путь (факт по коду)

Полная карта — в приложении внизу. Ключевое:

1. **Подача заявки покупателем — сильная**: 4 способа наполнения (ручной, корзина каталога,
   AI-извлечение из файла, разговорный AI-композер), preflight-проверка, KYC-гейт, авто-роутинг
   по владельцам каталожных позиций (`rfq.py`).
2. **Продавец узнаёт о заявке ТОЛЬКО через колокольчик in-app + WebSocket**
   (`notifications/signals.py:_notify_seller_team`). **Email НЕ отправляется** — оффлайн-продавец
   не узнаёт о заявке, пока сам не зайдёт. Медиана B2B в 42 часа — из таких мест.
3. **Claim не открывает работу**: «Взять в работу» пишет `assigned_to`/`assigned_at`, но стадию
   не двигает. Кнопки «Начать подбор» на карточке заявки в RFQ_OPEN нет (только в DRAFT) —
   перевод стадии делается Kanban-drag'ом на другом экране. Путь неочевиден.
4. **«Сформировать КП» создаёт ПУСТОЙ КП** (`quotes.py:perform_create`) — строки заявки не
   копируются. Копирование делает только отдельная кнопка «AI-черновик» в билдере
   (`draft_quote.py`). Продавец, пошедший «ручным» путём, перенабивает позиции, которые уже есть.
5. **Итого: от «увидел заявку» до предзаполненного черновика — 4–6 ручных действий на 2 экранах**
   (claim → Kanban-drag SOURCING → CALCULATING → «Сформировать КП» → открыть билдер → «AI-черновик»).
6. **SLA-якорь пишется, но не виден**: `assigned_at` сохраняется «для time-to-first-touch», но ни
   возраст непринятой заявки, ни время до первого касания нигде не отображаются. Dashboard
   показывает только счётчик «заявок без КП».

## Целевой путь (на утверждение)

Сценарий глазами: *заявка упала в 09:00 → менеджер продавца получил email+пуш в 09:00 →
открыл по ссылке → нажал ОДНУ кнопку «Взять в работу и подготовить КП» → через ~15 секунд
смотрит готовый AI-черновик КП с позициями, ценами из своих офферов и авто-матчем каталога →
правит → отправляет.* Три волны:

**Волна W1 — «Продавец узнаёт» (instant-assign-notification).**
Email routed-команде продавца о новой заявке (инфраструктура `send_templated_email` готова,
шаблон новый; deep-link в заявку). Это внутреннее письмо продавцу — БЕЗ white-label, бренд
платформы уместен. Тот же email при адресном `assign_deal`. Никаких новых настроек: канал
дублирует существующее in-app уведомление.

**Волна W2 — «Одна кнопка до черновика» (one-click-quotation, Odoo).**
Кнопка «Взять в работу и подготовить КП» на карточке заявки: claim + авто-прогон стадии
(RFQ_OPEN→SOURCING→CALCULATING — FSM не ломаем, сервис проходит цепочку сам, как Move 0
авто-переходы) + создание КП **с копией строк заявки** + для entitled-продавцов (ai.draft) —
сразу AI-черновик (матч+цены), для остальных — предзаполненный КП без AI. Ручной путь
«Сформировать КП» тоже начинает копировать строки (фикс разрыва №4 — пустой КП понижаем
до бага). Существующие кнопки не удаляем — добавляем короткий путь.

**Волна W3 — «Возраст заявки виден» (aging-counters, Bitrix24) — ОПЦИОНАЛЬНА, решение владельца.**
В Dashboard-strip и списке заявок: «ждёт N ч» на непринятых заявках (данные `created_at`/
`assigned_at` уже есть). Это НЕ новый гейт и НЕ SLA-блокировка — только видимость для
руководителя («руководители видели стабильность»). Если не нужна — вычёркиваем без влияния
на W1/W2.

Порядок: W1 → W2 (независимы, но узнавание без короткого пути даёт меньше эффекта). Оценка:
W1 ~полдня, W2 ~1–1.5 дня, W3 ~полдня. DoD каждой волны — сценарий глазами end-to-end
(заявка → email → одна кнопка → черновик) + скриншот/GIF владельцу.

## Приложение: карта пути по коду (6 сегментов)

1. **Подача**: `CreateDealDialog.tsx` → `crm/services/deals.py:52` (DRAFT); строки:
   `rfq.py:buyer_add_request_item(s)` (ручной/корзина, дедуп `_line_dedup_key`),
   `sourcing/views_imports.py:ExcelImportView` + `views_ai.py:DocumentExtractView` (AI-файл),
   `views_ai_conversational.py:ComposeRequestView` (разговорный); preflight
   `PreflightCheckView` (free floor); сабмит `rfq.py:submit_request` — KYC-гейт
   `KYC_REQUIRED_TO_SUBMIT`, полнота строк, ≥1 получатель.
2. **Fan-out**: `DealSellerRouting`; авто `rfq.py:route_deal_from_catalog` (владельцы
   Product), вручную `route_request_to_sellers`; скоринга/подбора поставщиков нет; solo —
   `assignment.py:ensure_creator_seller_routing`.
3. **Claim→КП**: `assignment.py:claim_deal` (assigned_to/at, стадию НЕ двигает);
   `RequestActionBar.tsx` — «Начать подбор» только в DRAFT; `canBuildQuote` требует
   SOURCING/CALCULATING; `GenerateQuoteDialog` → `quotes.py:perform_create` — ПУСТОЙ DRAFT-КП;
   builder `QuoteBuilderGrid.tsx:298` empty-state «AI-черновик»/«вручную».
4. **AI**: `draft_quote.py:generate_draft_quote` — копия строк + exact GOST/MPN + AI fuzzy
   (порог 0.9) + цены из офферов; гейт `ai.draft` (подписка) + `consume_credit`; запуск ТОЛЬКО
   ручной кнопкой на пустом КП. Smart Match (`AICatalogMatchDialog`) и pricing-assist — ручные;
   `ai.match` — free floor.
5. **Уведомления**: `notifications/signals.py:notify_deal_stage_change` → `_notify_seller_team`
   (только routed can_sell) — in-app Notification + WS; **email на этот триггер не подключён**;
   адресное — только `_notify_assignee` при assign_deal (тоже без email).
6. **Dashboard**: `DashboardWidgets.tsx:SellerAttentionStrip` — счётчик `rfqsNeedingKp`
   (RFQ_OPEN/SOURCING/CALCULATING), без возраста/таймеров; `assigned_at` нигде не поверхностится.
