# Gap-анализ: путь «после подписания контракта» (CONTRACT_SIGNED → оплата → акт → приёмка → CLOSED_WON)

_Дата: 2026-07-29. Статус: НА УТВЕРЖДЕНИИ владельцем, код не начат._
_Метод: PRODUCT RULES §1/§3 — benchmark-first, целевой путь целиком, потом одна связная волна. Ресерч: 2 агента (backend + frontend), полные факты с file:line в тексте ниже._

## 1. Почему этот отрезок

Граф знаний показал: страницы `payments`, `acts`, `fulfillments` имеют **ноль контекстных переходов** из контента — достижимы только из сайдбара. Проверка глазами агентов подтвердила: wedge-петля (заявка → КП → отправка → акцепт) доведена до контракта и там **обрывается**. Всё, что после — деньги и закрывающие документы — работает на бэкенде, но пользователя туда никто не ведёт. Это зона максимального негатива: пользователь уже заплатил доверием (подписал контракт), и именно тут платформа замолкает.

## 2. Бенчмарк: как это решают эталоны

| Паттерн | Эталон | Суть |
|---|---|---|
| **Deal card = hub** | Odoo (sales order smart-buttons), Bitrix24 (вкладки карточки сделки), Salesforce (related lists) | Карточка сделки показывает счётчики-кнопки: «Инвойсы (2)», «Платежи (1)», «Доставка» — один клик до любого документа цепочки. Никогда не «идите поищите в реестре». |
| **Next-step CTA после каждого действия** | Odoo (после Confirm → «Create Invoice» баннер), PandaDoc (post-sign «What's next») | Каждое терминальное действие (подписал / выставил / оплатил) заканчивается не тостом, а предложением следующего шага сценария. |
| **Register payment из инвойса** | Odoo Accounting | Оплата фиксируется из карточки инвойса (у нас уже так — `RecordPaymentDialog`), после оплаты инвойс получает ленту «Paid» и предлагает закрывающий документ. |
| **Actionable notifications** | все эталоны | Уведомление «требуется подпись» ведёт на кнопку подписи, «инвойс выставлен» — на инвойс. Не на «карточку сделки вообще». |
| **Кликабельный таймлайн (chatter)** | Odoo chatter, Bitrix24 таймлайн | События «создан контракт», «выставлен инвойс» — ссылки на объекты. |

Кастома не требуется: весь целевой путь собирается из именованных паттернов выше.

Дополнительные дефекты целостности/безопасности (backend-агент, полный список у него):
- 🐞 **Сырой CRUD**: `POST /crm/payments/` создаёт Payment мимо `record_payment` (без пересчёта `amount_paid`/статуса, без buyer-гейта); `DELETE` не откатывает суммы. `IsCompanyMemberOrPlatformAdmin` не имеет `has_permission`.
- 🐞 Биллинговые вьюсеты без `filterset_fields` — `?deal=<id>` не фильтрует (блокер для хаба сделки).
- 🐞 Статус инвойса `OVERDUE` объявлен и читается аналитикой, но ни один таск его не проставляет.
- 🐞 `Fulfillment.contract` никогда не заполняется → seller-видимость уходит в фолбэк.
- Ни одного email на всём post-contract отрезке (только in-app).

## 4. Целевой путь (та же петля, без обрывов)

1. Подписал контракт вторым → экран говорит: «Контракт подписан, сделка выиграна. Инвойс создан черновиком → [Открыть инвойс]» (точечный deep-link `invoices?open=<id>` — механизм уже есть).
2. Карточка сделки (обе поверхности) — **хаб**: блок «Документы сделки» показывает контракт, инвойсы (со статусом оплаты), акты, отгрузку — счётчики-ссылки в стиле Odoo smart-buttons.
3. Каждое уведомление ведёт на объект, а не «на сделку вообще»; появляются недостающие уведомления: платёж записан (продавцу), акт выставлен/подписан (второй стороне).
4. После каждого действия — следующий шаг: выставил → «покупатель уведомлён, ждём оплату»; оплата закрыла инвойс → «сформировать акт»; акт подписан → «отгрузка».
5. Dashboard-полосы внимания видят вторую половину воронки (инвойсы к выставлению/оплате, акты на подписи, поставки).

## 5. Предлагаемые волны (на утверждение)

**Волна F0 — целостность и безопасность backend (маленькая, срочная, вне UX):**
`sign_act` без проверки стороны; сырой CRUD Payment/Invoice/Act (закрыть create/delete, оставить сервисные экшены); нелогируемое падение авто-акта; потеря dispatch авто-инвойса. Это дефекты, не продуктовые решения — предлагаю делать сразу.

**Волна F1 — «Сделка-хаб + следующий шаг» (ядро):**
- `DealDetailSerializer` (или отдельный лёгкий endpoint `deals/{id}/documents/`) отдаёт цепочку contract/invoices/payments/acts/fulfillment (+ `filterset_fields` на биллинг-вьюсетах).
- `DealDocumentsCard` → полный хаб документов сделки (паттерн smart-buttons).
- Точечные deep-links: «Открыть/Создать инвойс» → `invoices?open=<id>`; `?open=` для acts; `BuyerAcceptedPanel` после CLOSED_WON показывает инвойс к оплате.
- Next-step CTA в 6 терминальных точках (подпись, выставление, оплата, акт).
- Фикс ролевых гейтов: `activeStatus` → серверные права (по образцу `viewer_can_sign_*` из ContractsPage); `DealLink` — ролевая развилка.

**Волна F2 — «Уведомления, ведущие на объект»:**
- `NotificationCenter` перестаёт затирать `link` (или бэкенд шлёт структурные target'ы — по образцу existing FK-механики).
- Новые in-app уведомления: платёж записан, акт выставлен, акт подписан, статус отгрузки (получатели — по сторонам, не legacy `deal.manager`).
- Кликабельный таймлайн сделки (события-ссылки), починка кнопки «Смотреть все».

**Волна F3 — «Dashboard: вторая половина воронки»:**
плитки «Инвойсы к выставлению/к оплате», «Акты на подписи», «Поставки в пути/просрочены» — данные уже считаются на страницах, вывести на полосы внимания.

## 7. DoD

Сценарий глазами, одной сессией, без тупиков: акцепт КП → подпись двумя сторонами → продавец из уведомления попадает в DRAFT-инвойс → выставил → покупатель из уведомления оплатил → продавец увидел оплату → акт → подпись акта → отгрузка → приёмка → CLOSED_WON. GIF владельцу. «Тесты зелёные» ≠ done.
