# Аудит дизайна клиентских документов (PDF + email) — 2026-07-26

_Статус: УТВЕРЖДЕНО владельцем 27-07 (с правками: подпись/печать — только текст, без изображений — QR-модель; + 2 гэпа в D1: онлайн-КП=PDF-анатомия и блок-4 таблица). Запрос: «пройдись по всем PDF и email — не устраивает то, что получает клиент»._
_Метод: все 5 типов PDF отрендерены боевыми шаблонами с ПОЛНОСТЬЮ заполненным брендом (лого, банк, подписант, cover), все 5 клиентских писем — с реалистичным контекстом; каждый артефакт отсмотрен глазами. Бенчмарки: анатомия КП/документов из утверждённой spec-kp-blank (ADZ Nagano / Odoo Document Layout / EN 16931), транзакционные письма — Stripe/DocuSign-паттерн (бренд отправителя, а не платформы)._

## Вердикт

Фундамент профессиональный: единый letterhead-шаблон, дизайн-токены, A4/ГОСТ, пагинация, «Стр. X из Y», QR. «Дилетантскую картину» дают не шаблоны как таковые, а **(а) дыры данных** («Поставщик: —», пустые боксы, висячие плейсхолдеры), **(б) несогласованность документов между собой** (3 разных формата итогов НДС), **(в) дубли** (реквизиты ×2 в КП, заголовок ×2 в письме-документе), **(г) плохая пагинация** (пустая 2-я страница КП), **(д) платформенный бренд вместо бренда продавца в письмах**. Это чинится двумя волнами без смены архитектуры.

## Дефекты по артефактам

### КП (quote_pdf) — оценка 7/10
- **P0** Пустая стр. 2: в потоке после «Условий» остаётся хвост → почти пустой лист с одним футером. Футер должен быть `@bottom` / последний блок не должен отрываться.
- **P0** Cover-letter с пустым `{{buyer}}` печатает «…сотрудничеству, .» — резолвер обязан чистить пустые подстановки (запятые/пробелы).
- **P0** Cover-letter: `{{deal}}` получает НОМЕР КП («в ответ на Вашу заявку КП-2026-00099») — семантика неверна, нужен номер/название заявки.
- **P1** Дубль реквизитов: шапка-letterhead (ИНН+банк) и бокс «ПОСТАВЩИК» повторяют одно и то же. Мировая практика: шапка = бренд, parties = стороны кратко (имя, ИНН). Банк — один раз (шапка ИЛИ низ).
- **P1** Пустой серый бокс «ПОКУПАТЕЛЬ» на соло-сделке — скрывать или печатать контакта.
- **P2** «Ваш менеджер» без телефона (только email); заголовок «Коммерческое предложение» дублирует «КП №…» из шапки.

### Договор (contract_pdf) — оценка 5/10
- **P0** §10 «Реквизиты и подписи Сторон» НЕ содержит реквизитов — только линии подписей. Для юрдока обязательна таблица 2 колонки: юр.название, адрес, ИНН, р/с, МФО, банк, подписант каждой стороны.
- **P1** Спецификация: «ЦЕНА, UZS» (нетто) + единственная строка «Итого с НДС» — нет разбивки «Итого без НДС / НДС / Итого с НДС», несогласовано с КП и инвойсом.
- **P1** Линии подписей без ФИО/должности подписантов (данные есть в профиле/контракте).
- **P2** Нет строки «г. Ташкент · дата» (стандарт СНГ для преамбулы договора).

### Инвойс (invoice_pdf) — оценка 3/10 (ручной без договора) ⚠ худший
- **P0** «ПОСТАВЩИК: —» и шапка «RailTech B2B»: supplier резолвится ТОЛЬКО через contract→quote; ручной инвойс (Wave G) без договора теряет продавца. Резолв должен падать на source_quote → deal.seller_routing.
- **P0** «ПЛАТЁЖНЫЕ РЕКВИЗИТЫ / Получатель: —» — счёт без реквизитов получателя недействителен как платёжный документ.
- **P0** «Оплата по счёту № … от , в т.ч. НДС» — дырка вместо даты.
- **P1** Мета в шапке: «от» на пустой строке + «оплата до…» — сломанная вёрстка меты.
- **P2** «Руководитель / Главный бухгалтер» без ФИО (профиль знает подписанта).

### Акт (act_pdf) — оценка 7/10
- **P1** «Итого:» одной строкой без НДС-разбивки — несогласовано с КП/инвойсом (акт должен зеркалить инвойс).
- **P2** Длинный заголовок «Акт № …» сталкивается с названием компании в одну строку шапки (нужен перенос-приоритет).

### Произвольный документ (generated_document_pdf) — оценка 6/10
- **P0** Дубль заголовка: title документа + `<h3>` в теле шаблона печатаются подряд («Гарантийное письмо» ×2). Либо не печатать doc_title при совпадении, либо чистить в сэмплах.
- **P1** Нет блока подписи: signatory из профиля не печатается (письмо/доверенность без подписи выглядят незавершёнными).

### Письма (все 5) — оценка 6/10
- **P0** `quote_sent`: сумма БЕЗ валюты («6 182 400.00»); «по сделке №32» (внутренний ID) вместо «КП-2026-00099»; тема с вложенными «ёлочками» и №сделки.
- **P1** Бренд: шапка всех писем = «RailTech B2B» (платформа). Письмо с КП клиенту должен открывать бренд ПРОДАВЦА (имя + accent), платформа — мелко в футере (Stripe/DocuSign white-label паттерн).
- **P1** `invite_client`: «ваш поставщик приглашает» — приглашающая компания НЕ названа.
- **P1** CTA `quote_sent` «Открыть и скачать КП» преуменьшает: на публичной странице КП можно ПРИНЯТЬ (Волна A). Верный CTA: «Открыть предложение онлайн».
- **P2** «ёлочки» двоятся при seller_name с кавычками («ООО «СолоСеллер»» → шаблон не должен добавлять свои); сырой `/api/v1/public/...` URL в тексте.

## Предложение: 2 волны

**Волна D0 — контент-корректность (P0, ~день):** пустая стр.2 КП; чистка пустых плейсхолдеров cover; `{{deal}}`=заявка; supplier-резолв ручного инвойса + платёжные реквизиты + дата; дубль заголовка документа; валюта+№КП+тема в quote_sent; (уже готово на этой ветке: robust-лого data-URI).

**Волна D1 — «Документный дизайн 2.0» (P1, 1–2 дня):** единый стандарт parties/реквизитов (шапка=бренд, стороны кратко, полные реквизиты одним блоком там, где юридически нужно — договор §10, инвойс «Реквизиты»); единый 3-строчный итог НДС во всех 4 транзакционных PDF; подписные блоки с ФИО/должностью подписанта (текстом) везде; white-label писем (бренд продавца в шапке 5 клиентских писем); invite с именем приглашающего.

> **Подпись/печать — только текст (ФИО + должность), БЕЗ изображений.** Решение владельца 24-07: цифровая печать/факсимиле подписи = подделка. Модель подлинности — **QR на онлайн-оригинал** (уже реализован); при необходимости документ печатают и ставят живую подпись. Поля изображений печати/подписи (`signature_image`/`seal_image`/`sign_mode`) НЕ добавляются — в модели их нет, и добавляться не должны (см. [[project-kp-letterhead-proposal]] K6, spec-kp-blank «печать/подпись НЕ делаем»).

**Волна D1 — дополнено (гэпы, найденные при сверке 27-07):**
- **Онлайн-страница КП = близнец PDF.** Сейчас `quote_public_page.html` (страница, куда ведёт QR-«оригинал») на СТАРОЙ анатомии: нет сопроводительного, структурных «Условий поставки», банка в шапке, колонки «Срок». Расхождение подрывает саму QR-модель (клиент сканирует «оригинал» и видит документ беднее PDF). `public_quote_page_context()` в `crm/services/documents.py` не кладёт `cover_text`/`quote_terms` — переиспользовать те же единые builder'ы (`resolve_cover_letter`/`build_quote_terms`), что и PDF.
- **Блок 4 (таблица КП) по утв. spec-kp-blank / EN 16931.** Заголовки цен — «Цена за ед. **без НДС**» / «Сумма без НДС» (устраняет неоднозначность, согласуется с единым итогом НДС). Колонка «Срок/наличие» с fallback: per-line lead → общий срок КП → «В наличии» (данные `lead_time_days`/`effective_delivery_lead_time_days` уже есть; сейчас колонка условная без fallback).

P2 — по остатку в той же волне D1, без отдельного цикла.
