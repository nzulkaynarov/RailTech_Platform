# Номенклатура: жизненный цикл товара — ресерч, бенчмарк и предложение

Основание: наблюдение владельца 03-08 — «клиент шлёт заявку на позиции, система ищет совпадения,
но этих товаров у продавца нет; продавец формирует КП из воздуха; после закрытия сделки товаров
как не было, так и нет; перед отправкой КП можно заполнить ТН ВЭД, сроки — а куда они пишутся,
непонятно».

Статус: **НА УТВЕРЖДЕНИЕ**. Код не начат (PRODUCT RULE 3 — сначала целевой путь и картина).

---

## 1. Что происходит сейчас (проверено в коде и на данных)

### 1.1 Наблюдение владельца подтверждается количественно

| Замер на локальной базе | Значение |
|---|---|
| Строк КП всего | 98 |
| Из них **без привязки к товару** | **90 (92%)** |
| Товаров в каталоге | 8 |
| Из них со статусом `PUBLISHED` | 3 |
| Из них **без статуса вообще** (`status IS NULL`) | **5** |
| Товаров без `owner_company` | 5 |
| Предложений поставщиков (`SupplierOffer`) | 5 |

**92% товарного оборота проходит мимо каталога.** Жизненного цикла де-факто нет: у большинства
карточек не проставлен даже статус.

### 1.2 Данные для карточки СОБИРАЮТСЯ, но никуда не уходят

`QuoteItem` уже несёт всё, из чего состоит карточка товара:

`imported_raw_name`, `name_canonical` (AI-нормализованное русское имя), `mpn`, `gost_drawing`,
`hs_code`, `unit_code` (UN/ECE Rec 20), `note`, `quantity`, `frozen_base_price`,
`lead_time_days`.

Комментарий в модели описывает поток ОДНОСТОРОННЕ: «ТНВЭД, замороженный **из** `Product.hs_code`».
Обратного потока (строка КП → карточка товара) **нет ни одного**. Единственное место, где
создаётся `Product` — `sourcing/catalog_import.py` (массовый импорт файла).

Итог: продавец на каждой сделке заново вводит ТН ВЭД, срок, единицу — и это знание умирает
вместе с КП. Владелец описал ровно это.

### 1.3 У продавца ЕСТЬ право заводить товар, но НЕТ поверхности

* Бэкенд: `IsProductManagerOrAdmin` разрешает участнику seller-компании создавать товар и
  редактировать СВОИ карточки (`owner_company`).
* Фронт: форма создания/редактирования живёт **только** в плоскости оператора
  (`pages/admin-catalog`, хуки `useCreateProduct` / `useUpdateProduct`).
* Страница продавца `ProductManagement` (пункт меню «Номенклатура») — **витрина только для
  чтения** с кнопкой «в корзину»: она про ПОКУПКУ из каталога, а не про ведение своей
  номенклатуры.

То есть меню обещает продавцу управление номенклатурой, а экран его не даёт.

### 1.4 Публикация — привилегия платформы

`bulk_publish` закрыт `IsPlatformAdmin`. Продавец не может опубликовать даже собственную
карточку; в Unfold есть действие `publish_products` — то есть массовая публикация существует
только для инженеров и операторов.

### 1.5 Матчинг ищет по всему каталогу без границ

`smart_match_product` работает по `Product.objects.all()` — без фильтра по `owner_company` и
**без фильтра по статусу**. Черновик чужой компании — законный кандидат на подстановку в КП.
Это одновременно риск утечки (карточка конкурента как подсказка) и причина мусорных совпадений.

### 1.6 Что уже сделано хорошо (не ломать)

* Разделение **Product (PIM) ↔ SupplierOffer (коммерция)** — правильная модель: справочные
  данные отдельно от цены/наличия/срока. Это линия Akeneo/Pimcore + отдельный price book.
* `Product.hs_code` с формулировкой «один раз внесли — больше не ищем заново» — намерение
  верное, не хватает того, кто его наполняет.
* Дедупликация задумана как **бренд + MPN** (комментарий на `manufacturer_part_number`).
* AI-обогащение (`catalog/ai_enrich.py`) уже есть и правильно спроектировано: **черновик,
  который продавец правит**, не автозапись; категория — подсказка, а не выдуманный id.
* `unit_code` по UN/ECE Rec 20 и мысль про UBL/Peppol — это ровно то, на чём стоят B2B-каталоги.

## 2. Бенчмарк: как это устроено у эталонов

### 2.1 Позиция, которой нет в каталоге — это НОРМА, а не ошибка

| Эталон | Механика |
|---|---|
| **SAP MM** | Есть штатное понятие **one-time material**: закупка позиции без мастер-записи, с текстовым описанием. Но она помечена как one-time и **не притворяется** позицией каталога. |
| **Coupa / SAP Ariba** | Разделение **catalog item** и **non-catalog (free-text) request**. Free-text уходит в очередь **catalog enablement** — там из повторяющихся free-text позиций создают каталожные. |
| **Odoo** | В строке заказа можно ввести новый товар — Odoo предложит **«Создать product.template»** прямо из строки; ввод не остаётся сиротой. |
| **Salesforce CPQ** | Строка обязана ссылаться на `Product2` + `PricebookEntry`; «товара из воздуха» не бывает вовсе — это самый строгий полюс. |

**Вывод для нас:** запрещать КП по несуществующему товару НЕЛЬЗЯ (это торговля запчастями, где
клиент присылает чертёж). Но безымянная строка обязана оставлять след, из которого рождается
карточка. Наш случай ближе всего к **Ariba catalog enablement**: free-text → очередь → каталог.

### 2.2 Жизненный цикл карточки — это workflow, а не поле статуса

| Эталон | Механика |
|---|---|
| **Akeneo PIM** | Ядро — **completeness score** по каналу: карточка «готова» не когда кто-то нажал кнопку, а когда заполнены обязательные атрибуты для канала публикации. Есть рабочие процессы и «enrichment queue». |
| **Pimcore** | Data Objects + **Workflow Management**: draft → in review → approved → published, с правами на переход. |
| **Shopify / BigCommerce** | Просто `draft` / `active`, но публикация — действие ВЛАДЕЛЬЦА товара, не площадки. |
| **Amazon Business / Alibaba** | Продавец сам заводит и публикует; площадка модерирует ПОСТ-фактум и по сигналам, а не блокирует каждую карточку. |

**Вывод:** у нас `ProductStatus` (DRAFT/PUBLISHED/ARCHIVED) уже есть, но (а) он nullable и не
проставляется, (б) публикация отобрана у владельца карточки, (в) нет понятия «полноты».
Нужен **completeness-порог вместо ручного благословения платформы**.

### 2.3 Идентичность и дедупликация

* **GS1**: глобально — GTIN, но для промышленных запчастей он бессмыслен (в коде это уже
  осознано и GTIN убран 2026-06-23 — верное решение).
* **ETIM / UNSPSC / eCl@ss**: отраслевая классификация технических товаров; ETIM — стандарт
  де-факто для промышленных каталогов в Европе.
* Практика промышленных маркетплейсов (Grainger, RS Components, Würth): ключ —
  **бренд + MPN**, плюс кросс-референс «наш номер ↔ номер производителя ↔ ГОСТ/чертёж».

**Вывод:** наш ключ «бренд + MPN, плюс ГОСТ/чертёж» — правильный и уже заложен. Не хватает
**реестра кросс-ссылок** (один и тот же подшипник у разных продавцов зовётся по-разному) и
дедупликации на входе.

### 2.4 Кто владелец карточки: общий каталог или каталог продавца

| Модель | Кто так делает | Плюс | Минус |
|---|---|---|---|
| **Единый мастер-каталог платформы**, продавцы вешают офферы | Amazon (ASIN), Ozon, Wildberries | одна карточка — много цен, сравнение работает | нужна модерация и сильная дедупликация |
| **Каталог каждого продавца свой** | Alibaba, Ariba supplier catalogs | продавец свободен | сравнения нет, дубли неизбежны |
| **Гибрид: свой каталог + мастер-записи платформы** | Grainger, Mercateo | быстрый старт продавца + сопоставимость | сложнее |

**Наша модель уже гибридная** (`owner_company` + `SupplierOffer`), и это верно для рынка
запчастей. Но сейчас гибрид не достроен: 5 карточек из 8 вообще без владельца, а матчинг не
различает «моё / чужое / платформенное».

### 2.5 Роль AI

Эталоны 2024–2026 (Akeneo AI, Salsify, Shopify Magic, Amazon listing assistant) сходятся:

1. **Извлечение** из файла/фото/текста — AI (у нас есть).
2. **Нормализация и классификация** (категория, единица, HS-код) — AI как **подсказка с
   уверенностью**, решение за человеком (у нас есть для описания, нет для HS/категории).
3. **Дедупликация** — AI предлагает «похоже на существующую карточку», человек подтверждает.
4. **Полнота** — детерминированный расчёт, НЕ AI.
5. **Цены и обязательства AI не трогает никогда** (у нас это уже железное правило).

## 3. Предложение: жизненный цикл позиции

### 3.1 Главная идея

**Ни одна строка КП не остаётся сиротой.** Строка без товара порождает (или обогащает)
**кандидата в номенклатуру** — карточку-черновик, принадлежащую продавцу, с происхождением
«из заявки №…». Продавец дополняет её (единично или массово) и публикует. Следующая такая же
заявка подставляется автоматически.

Это ровно то, что описал владелец, и это же — **catalog enablement** из Ariba/Coupa.

### 3.2 Состояния карточки

```
  ЧЕРНОВИК-КАНДИДАТ ──обогащение──> ГОТОВ К ПУБЛИКАЦИИ ──публикация──> ОПУБЛИКОВАН
   (из строки КП,        (полнота             (порог полноты        (участвует в
    заведён системой)     растёт)              достигнут)            матчинге)
         │                                                                │
         └──────────── дубль ──> СЛИТ С СУЩЕСТВУЮЩЕЙ ──┐                  ▼
                                                        └──────────> АРХИВ
```

* `DRAFT` — уже есть в справочнике, начинает наполняться автоматически.
* **Новое: «готов к публикации»** — вычисляется, а не назначается (порог полноты).
* `PUBLISHED` — публикует **владелец карточки**, не платформа (Amazon/Alibaba/Shopify).
* `ARCHIVED` — есть.
* **Новое: слияние дублей** — вместо второй карточки.

### 3.3 Полнота (completeness) — вместо ручного благословения

Порог считается детерминированно, по домену:

| Атрибут | Ж/д техника | Общие товары | Услуги |
|---|---|---|---|
| Наименование | обяз. | обяз. | обяз. |
| Единица измерения (`unit_code`) | обяз. | обяз. | обяз. |
| Категория | обяз. | обяз. | обяз. |
| Бренд + MPN **или** ГОСТ/чертёж | обяз. | желат. | — |
| Группа оборудования | обяз. (уже валидируется) | — | — |
| ТН ВЭД | обяз. | обяз. | — |
| Описание, фото | желат. | желат. | желат. |

Публикация доступна при 100% обязательных. Процент виден на карточке — это Akeneo-паттерн и он
сам по себе объясняет пользователю, что делать дальше.

### 3.4 Откуда берутся кандидаты

1. **Из строки КП без товара** — основной источник (сегодня 92% оборота).
2. Из импорта файла — уже есть.
3. Ручное создание — нужно дать продавцу форму.

### 3.5 Что происходит в момент отправки КП

Сейчас: ТН ВЭД, срок, единица заполняются и умирают вместе с КП.

Станет: значения **сохраняются в карточку-кандидат** (провенанс — из какого КП). Продавец
второй раз ту же позицию не заполняет. Это буквальный ответ на вопрос «куда они пишутся».

### 3.6 Дедупликация

На создании кандидата: точное совпадение бренд+MPN или ГОСТ → **не плодим карточку, а
привязываемся к существующей**. Похожее (trigram + AI) → показываем как «возможно, это дубль»
с кнопкой «привязать». Решение всегда за человеком.

### 3.7 Границы матчинга (закрываем 1.5)

Кандидат в подстановку — только:
* `PUBLISHED` карточка любого продавца **или** платформенная (общий каталог), **либо**
* **своя** карточка (в т.ч. черновик) — продавец обязан видеть свои.

Чужой черновик не должен ни подставляться, ни быть виден.

## 4. UX/UI по ролям

### 4.1 Продавец — «Номенклатура» становится рабочим местом

**Экран «Требуют внимания»** (входная точка, паттерн Ariba enablement + Akeneo enrichment queue):

```
Номенклатура
┌───────────────────────────────────────────────────────────┐
│ [ Кандидаты 12 ] [ Готовы к публикации 3 ] [ Опубликовано 148 ] [ Архив ] │
├───────────────────────────────────────────────────────────┤
│ ☐ Подшипник буксовый 30-232726Е2М                         │
│   из заявки #17 · спрашивали 3 раза · полнота 40%         │
│   не хватает: категория, ТН ВЭД, единица   [Дополнить →]  │
│ ☐ Скрепление рельсовое КБ-65 комплект                     │
│   из заявки #17 · полнота 60%                             │
│   не хватает: ТН ВЭД                        [Дополнить →] │
├───────────────────────────────────────────────────────────┤
│ Выбрано 2:  [Заполнить ИИ]  [Опубликовать]  [Слить дубли] │
└───────────────────────────────────────────────────────────┘
```

Ключевое:
* сортировка по **частоте спроса** — сначала то, что спрашивают чаще (окупается быстрее);
* «не хватает: …» — конкретный список, а не абстрактный процент;
* **массовые действия** — владелец прямо просил «массово или единично»;
* «Заполнить ИИ» на выделенных — пакетное обогащение с обязательным просмотром.

**Карточка товара:** слева атрибуты, справа — полнота, происхождение («создан из заявки #17,
спрашивали 3 раза»), кандидаты на дубли, кнопка публикации (активна при 100%).

**В билдере КП:** у строки без товара — метка «нет в номенклатуре» и действие
**«Завести карточку»** (Odoo «создать товар из строки»). После отправки КП — тихое
уведомление «2 позиции добавлены в кандидаты».

### 4.2 Покупатель

Меняется мало и в лучшую сторону: чем полнее каталог, тем чаще его заявка распознаётся. Явно:
* в заявке у распознанных позиций — пометка «найдено в каталоге» с карточкой;
* у нераспознанных — честное «продавец подберёт», без ложного ощущения ошибки.

Ничего нового у покупателя **не спрашиваем** (PRODUCT RULE 2 — трение не добавляем).

### 4.3 Платформенный оператор (React Admin)

Согласно ADR-0001 бизнес-функции живут в React Admin:
* **очередь модерации** — не блокирующая: карточки публикуются сразу, оператор смотрит по
  сигналам (жалоба, подозрение на дубль, ошибка классификации) — линия Amazon/Alibaba;
* **дубли по всей платформе** — слияние карточек разных продавцов в мастер-запись;
* **справочники** — категории, группы оборудования, бренды;
* **метрика покрытия** — какой % строк КП попадает в каталог (сегодня 8%): одна цифра, которая
  показывает, работает ли направление.

### 4.4 Инженер (Unfold)

Без изменений по ADR-0001: массовые правки данных, импорт/экспорт, аварийные операции.
Действие `publish_products` остаётся как инженерный инструмент, но перестаёт быть ЕДИНСТВЕННЫМ
способом публикации.

## 5. Gap-анализ: что делать

| # | Разрыв | Работа | Вес |
|---|---|---|---|
| N1 | Строка КП без товара не оставляет следа | кандидат из строки + провенанс + счётчик спроса | **ключевой** |
| N2 | У продавца нет формы товара | создание/редактирование в плоскости продавца | **ключевой** |
| N3 | Публикация только у платформы | публикует владелец при 100% полноты | **ключевой** |
| N4 | Нет понятия полноты | расчёт по домену + отображение «не хватает: …» | высокий |
| N5 | ТН ВЭД/срок/единица из КП не сохраняются | обратная запись в карточку при отправке КП | высокий |
| N6 | Матчинг не различает своё/чужое/черновик | границы выборки | высокий (риск утечки) |
| N7 | Нет дедупликации на входе | точный ключ + подсказка похожих | средний |
| N8 | `status` nullable и пуст у 5 из 8 | сделать обязательным, бэкфилл миграцией | средний |
| N9 | Нет метрики покрытия | % строк КП с товаром на дашборде оператора | средний |
| N10 | AI не предлагает категорию/ТН ВЭД кодом | расширить `ai_enrich` до классификации с уверенностью | средний |

### Предлагаемый порядок

**Волна A (каркас, закрывает наблюдение владельца):** N1 + N5 + N2 — кандидат из строки,
обратная запись, форма продавца. После неё вопрос «куда пишется ТН ВЭД» получает ответ.

**Волна B (жизненный цикл):** N4 + N3 + N8 — полнота, публикация владельцем, статус обязателен.

**Волна C (качество каталога):** N6 + N7 + N9 — границы матчинга, дедупликация, метрика.

**Волна D (AI-ускорение):** N10 + пакетное обогащение выделенных.

## 6. Что сознательно НЕ делаем

* **Не блокируем КП по несуществующему товару.** Это рынок запчастей по чертежам; блокировка
  убила бы основной сценарий (PRODUCT RULE 2 — новых гейтов не вводим).
* **Не заставляем покупателя выбирать из каталога.** Свободный ввод остаётся.
* **Не отдаём AI решение о публикации, ценах и дедупликации.** AI предлагает — человек решает.
* **Не строим ETIM/UNSPSC-классификацию сразу.** Сначала покрытие, потом стандарты; иначе
  получим пустой каталог с идеальной таксономией.
* **Не переносим позиции заявки из `Quote` в отдельную модель.** Хранилище работает; менять
  его ради этой задачи — переписывание половины домена.

## 7. Вопросы владельцу

1. **Кто владеет карточкой при дубле?** Предлагаю: у каждого продавца своя карточка, платформа
   сводит их в мастер-запись позже (гибрид Grainger). Альтернатива — сразу общий мастер-каталог
   с модерацией: строже и сопоставимее, но медленнее старт.
2. **Публикация без модерации?** Предлагаю сразу публиковать при 100% полноты, модерация
   пост-фактум по сигналам (Amazon/Alibaba). Альтернатива — предмодерация оператором.
3. **Показывать ли покупателю, чья карточка?** Предлагаю НЕ показывать до КП — иначе
   «скрытая конкуренция» (ADR-0003 §5) протекает через каталог.
