## 0. TL;DR для исполнителя

Пять PDF-шаблонов (`_document_base.html`, `quote_pdf.html`, `contract_pdf.html`, `invoice_pdf.html`, `act_pdf.html`, всего 564 строки) — архитектурно чистые (один базовый шаблон, один брендинг-пайплайн, WeasyPrint-safe), но **как деловые документы они на уровне «черновик стартапа», а не международного B2B-стандарта**. Главные системные дефекты:

1. **Деньги печатаются без разделителей разрядов и без валюты** (`20608000.00` вместо `20 608 000,00 UZS`) — сразу читается как непрофессионально. Затрагивает все 5 шаблонов.
2. **Акцентный цвет бренда применяется только наполовину** — заголовок и линейка красятся, а шапка таблицы, строка ИТОГО и рамки блоков остаются жёстко-синими `#15294d`. Селлер с красным брендом получает «сломанный» документ.
3. **Нет устойчивости к разрывам страниц** — `page-break-inside: avoid` отсутствует везде; блок ИТОГО, подписи и строки таблицы могут разрываться между страницами.
4. **КП не закрывает воронку** — на главном (монетизируемом) артефакте нет контакта менеджера, нет QR/ссылки «Принять онлайн» через `public_access_token`, нет сопроводительного текста. Это тупик конверсии.
5. **Договор — не договор**, а спецификация с подписями: нет ни одной правовой статьи (предмет, расчёты, качество/приёмка, ответственность, форс-мажор, споры, срок действия).
6. **Инвойс не годен к оплате** — нет валюты, нет назначения платежа, нет выделенного блока банковских реквизитов, нет суммы прописью.
7. **Акт без табличной части** — одна фраза «поставлено в полном объёме» вместо перечня принятого.
8. **Только русский, только UZS-центрично** — `lang="ru"` захардкожен, нет двуязычного/EN-режима для ВЭД-контрагентов, статические подписи не через i18n.

Ниже — полный разбор по каждому файлу с привязкой к строкам, затем прескриптивное ТЗ по фазам с критериями приёмки и инвариантами, которые ломать нельзя.

## 2. Методология аудита

Каждый шаблон оценён по 4 осям международного B2B-стандарта:
- **Бизнес-ценность** — документ продаёт, вызывает доверие, двигает сделку и закрывает воронку заявка→КП→контракт (ADR-0006 wedge).
- **Дизайн** — визуальная иерархия, типографика, ритм, брендируемость, качество печати.
- **Информативность** — есть ли всё, что нужно закупщику, юристу, бухгалтеру и банку; нет ли пробелов в реквизитах.
- **Эргономика** — читаемость, сканируемость, поведение при печати и на многостраничных документах.

Шкала важности: **P0** (блокер профессионализма/юридической силы) · **P1** (серьёзный ущерб доверию/конверсии) · **P2** (заметный недочёт) · **P3** (полировка).

## 4. Детальный аудит по шаблонам

### 4.1 `_document_base.html` — общий каркас

**Сильные стороны (сохранить):** единый базовый шаблон и один брендинг-пайплайн (DRY, ADR-0006 P1); WeasyPrint-safe вёрстка на таблицах и pt-единицах; корректный DEMO-watermark на `position:fixed`; счётчик страниц в `@bottom-center`; аккуратные карточки сторон.

**Находки:**

- **F-03 (P0) Полутемизация бренда.** `accent` прокидывается инлайном только в `.brand-name` (128), `.rule` (139), `h1.doc-title` (141). А эти поверхности захардкожены `#15294d` и игнорируют бренд селлера:
  - `table.lines thead th { background:#15294d }` (70) — шапка таблицы;
  - `table.totals tr.grand td { background:#15294d }` (86) — строка ИТОГО;
  - `.term-box { border-left:2.5pt solid #15294d }` (90) — рамки условий;
  - `.doc-id .doc-no { color:#15294d }` (55).
  Итог: селлер с фирменным красным получает красный заголовок и синие таблицы — документ выглядит собранным из двух шаблонов. Для B2B, где документ = лицо поставщика, это подрывает доверие.

- **F-04 (P0) Разрывы страниц.** В CSS нет ни одного `page-break-inside: avoid` / `break-inside: avoid`. На многостраничном КП блок `table.totals` (ИТОГО к оплате) и `table.signatures` могут разорваться между листами; строка `table.lines tbody tr` — тоже. Разорванный итог/подпись в коммерческом документе читается как брак типографии.

- **F-14 (P2) Нет типографической шкалы.** Размеры разбросаны: 16pt, 14pt, 13pt, 10.5pt, 9.5pt, 9.2pt, 9pt, 8.8pt, 8.7pt, 8.5pt, 8pt, 7.8pt, 7.6pt. Нет ритма, тяжело поддерживать, визуально «шумно».

- **F-15 (P2) Не табличные цифры.** Колонки денег выровнены по правому краю (`.num`), но шрифт пропорциональный → цифры не выстраиваются вертикально по разрядам. Финансовые документы международного уровня используют tabular/lining figures (`font-variant-numeric: tabular-nums`).

- **F-16 (P2) Нет running-header.** На страницах-продолжениях есть только счётчик внизу; сверху нет «№ документа / поставщик», поэтому оторванный второй лист теряет идентификацию.

- **F-10 (P1) Локализация.** `<html lang="ru">` (24) захардкожен; все подписи — сырые русские строки. Для ВЭД (ж/д Узбекистана ↔ РФ/КНР/ЕС) нет ни EN-, ни двуязычного вывода, ни i18n через `{% trans %}`.

- **F-21/F-22/F-23 (P3):** скруглённый `<td>` под ИТОГО может дать артефакты в WeasyPrint; нет `orphans/widows`; нет маркера «Оригинал/Копия/Черновик».

### 4.2 `quote_pdf.html` — КП (ядро монетизации)

Это **самый важный** документ платформы: именно он монетизируется (entitlement `quote.send`) и двигает сделку. Планка — максимальная.

**Сильные стороны:** корректная клиентская проекция (нет `landed_cost`/`margin`/логистики/пошлины/FX — инвариант конфиденциальности соблюдён и задокументирован, 2-14, 106-111); мост итогов (subtotal → charges → НДС → total); подсветка «действительно до»; тумблер колонки «Срок».

**Находки:**

- **F-01 (P0)** Все суммы — `floatformat:2` (53,54,67,72,76,81,85): `1500000.00`, `20608000.00 UZS`. Нет группировки разрядов; валюта — сырой код `UZS` только у итогов, а в колонках «Цена/Сумма» валюты нет вообще.
- **F-02 (P0)** Нет «Суммы прописью» под ИТОГО — в СНГ это де-факто обязательный элемент коммерческого документа.
- **F-08 (P1)** `prepared_by` грузится в контекст, но в шаблоне нет блока «Ваш менеджер: ФИО · тел · email». Покупателю **не к кому обратиться**, чтобы принять КП — прямой удар по конверсии.
- **F-09 (P1)** Нет CTA и QR. `public_access_token` существует и уже используется для публичного КП, но на PDF нет ни ссылки «Принять предложение онлайн», ни QR. Wedge-петля (заявка→КП→**контракт**) на бумаге обрывается.
- **F-11 (P1)** Блок условий (93-112) содержит только срок и базис поставки. Нет: условий оплаты (предоплата %/постоплата), гарантии, страны происхождения, упаковки/маркировки, сертификации/соответствия (критично для ж/д-номенклатуры).
- **F-17 (P2)** Колонка `Кол-во` слепляет число и ед.изм. (`10 шт.`, стр. 51); нет отдельной колонки «Ед.изм.» и «Производитель» (доступен `item.product.manufacturer`).
- **P3:** «Доп. расходы / скидки» (71) одной строкой — метка двусмысленна, если по факту это надбавка.

### 4.3 `contract_pdf.html` — Договор поставки (юр. документ)

**Сильные стороны:** реальный селлер как «Поставщик» (не платформа); блок ПЭП с идентификацией подписанта и таймстампами (91-120) — достойно в рамках текущего техдолга по e-sign.

**Находки:**

- **F-05 (P0) Это не договор.** Содержимое: одна фраза «Предмет» (48-51), таблица позиций, ИТОГО, подписи, оговорка о ПЭП. Отсутствуют базовые статьи договора поставки: **предмет** (развёрнуто), **цена и порядок расчётов**, **сроки и условия поставки**, **качество/комплектность и приёмка**, **ответственность сторон** (пени/неустойка), **форс-мажор**, **порядок разрешения споров/применимое право**, **срок действия**, **количество экземпляров**, **приложения/спецификация**. В текущем виде юридическая сила близка к нулю.
- **F-12 (P1)** Не выведены существующие поля: `contract.currency` (сумма ИТОГО печатается **без валюты**, 81), `contract.valid_from/valid_until` (срок действия). Нет банковских реквизитов **покупателя** (только поставщика).
- **F-20 (P2)** Предмет ссылается на «КП v{version}» (50) — внутренний артефакт платформы в юридическом тексте; должно быть «согласно Спецификации (Приложение № 1)».
- **F-19 (P2)** Нет места печати (М.П.) у подписей — норма делового оборота СНГ.

### 4.4 `invoice_pdf.html` — Счёт на оплату

**Находки:**

- **F-06 (P0) Не годен к оплате.** (а) Суммы без валюты (74-76): «К оплате: 12345.00». (б) Нет **назначения платежа** («Оплата по счёту № … от … , в т.ч. НДS …») — банки Уз/СНГ его требуют. (в) Банковские реквизиты спрятаны мелким текстом в карточке стороны (25), а не вынесены в заметный блок «Платёжные реквизиты». Счёт без явных платёжных инструкций не выполняет свою единственную функцию.
- **F-02 (P0)** Нет «Суммы прописью».
- **F-13 (P1)** Не выведены: `invoice.amount_paid`/остаток (для переоформленного/частично оплаченного счёта), ставка НДС в % (только сумма, 75), основание — `invoice.contract` («по договору № …»).
- **F-19 (P2)** Нет места печати/подписи (М.П., «Руководитель», «Гл. бухгалтер»).
- **F-17 (P2)** У `InvoiceItem` нет колонки ед.изм.

### 4.5 `act_pdf.html` — Акт приёма-передачи

**Находки:**

- **F-07 (P1) Нет табличной части.** Вместо перечня принятого — одна фраза «услуги/товары … в полном объёме. Сумма: X» (22-25). Акт юридически должен перечислять принятые позиции (наименование, кол-во, цена, сумма), как договор/инвойс.
- **F-18 (P2)** `{% block parties %}{% endblock %}` пуст (13) — у акта **нет реквизитов сторон вообще**, только имена на линиях подписи. Несогласованно с остальными документами.
- **F-01/F-02 (P0)** Сумма без валюты и без прописи.
- **P2:** нет фразы об отсутствии претензий («Стороны претензий по объёму/качеству/срокам не имеют»), нет даты/места подписания сверху, нет М.П.

## 5. ТЗ на рефакторинг

Соблюдать все IRON RULES (особенно Rule 6 «read before write», Rule 8 «логика в services», i18n, семантические токены на фронте — но здесь бэкенд-шаблоны, поэтому фронт-токены не применимы; про инварианты см. §6).

## 6. Инварианты и ограничения — НЕ нарушать

1. **Конфиденциальность КП (жёсткое правило).** В `quote_pdf.html` НИКОГДА не выводить `landed_cost`, `margin_percent`, `logistics_cost`, `customs_duty`, любые `QuoteCharge`-строки и **снимок курса FX/ЦБ** (`fx_snapshot`) — по нему покупатель восстановит валютную себестоимость (sourcing-leak). См. `quote_pdf.html:2-14, 106-111`. Любые новые поля на КП проверять этим фильтром.
2. **WeasyPrint-контекст.** Рендер off-thread (ARCH-03). Никаких сетевых ресурсов в шаблоне: шрифты, изображения, QR — только инлайн/`data:`-URI (CSP на проде режет внешние хосты; WeasyPrint по сети не ходит). Вёрстка — таблицы + pt, без опоры на flex/grid.
3. **Реальный поставщик, не платформа.** «Поставщик» во всех документах резолвится через `document_brand_context`/`_quote_seller_company`; НЕ хардкодить платформенную идентичность (Rule 1/2). Фолбэк при отсутствии селлера — «—», не фейковые ИНН/реквизиты.
4. **Rule 8.** Любая новая логика (расчёт контраста акцента, генерация QR, резолв позиций акта, выбор валютных слов) — в `crm/services/*` или `templatetags`, не в вьюхах/тасках как дубли. Шаблон остаётся презентационным.
5. **Rule 6.** Перед правкой каждого файла — перечитать его и связанный сервис. Схема моделей меняется быстро.
6. **Миграции + OpenAPI.** Любое новое поле модели (напр. текст сопроводиловки/статей на `CompanyDocumentProfile`/`CompanySettings`) → миграция с `RunPython` для дефолтов при необходимости (seed = миграции, Rule 1) + регенерация OpenAPI (spectacular) и `schema.d.ts`, иначе падает CI-гейт `api-contract`.
7. **INF-05.** `requirements.txt` не редактировать вручную — только через `requirements.in` + `pip-compile --generate-hashes`. Касается добавления `num2words`/`qrcode`.
8. **Совместимость предпросмотра.** `render_document_profile_preview_html` (`documents.py:23`) кормит `quote_pdf.html` образцовыми словарями (не ORM-объектами). Любой новый доступ к полю в шаблоне (`item.product.manufacturer`, `quote.prepared_by...`) обязан деградировать безопасно на этих образцовых данных — обновить образцовый контекст.
9. **Тесты, которые обязаны остаться зелёными:** `crm/tests/test_document_toggles.py`, `test_demo_watermark.py`, `test_quote_document_profile.py`, `test_contract_document_profile.py`, `test_document_base.py`, `test_pdf_p0_correctness.py`, `test_arch03_pdf_202.py`, `test_pdf_render_on_commit.py`, `test_quote_public_send.py`. Добавить новые unit-тесты на `money`/`money_words` и на присутствие новых блоков.
