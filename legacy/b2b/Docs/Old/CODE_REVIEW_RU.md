# Ревью кода: RailTech B2B Ecosystem — Полная кодовая база

**Ревьюер:** Claude
**Дата:** 2026-03-17
**Охват:** Все исходные файлы backend (Django/DRF) и frontend (React/TypeScript)

## Резюме

RailTech B2B Ecosystem — грамотно спроектированная корпоративная платформа с сильным доменным моделированием, правильной изоляцией финансовых расчётов и чистым разделением ответственности. Кодовая база демонстрирует качественную инженерию: серверные финансовые расчёты, мультитенантность через CompanyMember, версионирование КП и 3-уровневый движок умного сопоставления. Однако в ходе ревью выявлено **5 критических проблем**, **8 замечаний высокой серьёзности** и ряд улучшений среднего/низкого приоритета в областях безопасности, производительности, корректности и поддерживаемости.

## Критические проблемы

| # | Файл | Строки | Проблема | Серьёзность |
|---|------|--------|----------|-------------|
| 1 | `crm/consumers.py` | 82–91 | **Сломанный RBAC в WebSocket ChatConsumer** — `check_deal_access` ссылается на `UserRole.SALES_MANAGER` (enum), которого не существует. Модель использует `SystemRole` (справочник из БД), а не Python-enum. При запуске возникнет `AttributeError`, полностью блокируя доступ к чату через WebSocket. | 🔴 Критический |
| 2 | `crm/models.py` | 238–248 | **Двойной пересчёт при сохранении QuoteItem** — `save()` вызывает `calculate_item_prices(commit=False)`, затем `super().save()`, затем `recalculate_totals()`, который пересчитывает ВСЕ позиции заново, включая только что сохранённую. Каждое сохранение одной позиции запускает полный O(n) пересчёт КП. При импорте Excel (100+ позиций) это создаёт O(n²) записей в БД. | 🔴 Критический |
| 3 | `sourcing/views.py` | 15–25 | **Нет проверки авторизации на владение сделкой при импорте Excel** — `ExcelImportView` проверяет только `IsAuthenticated`. Любой аутентифицированный пользователь может импортировать позиции в ЛЮБУЮ сделку, передав произвольный `deal_id`. Необходимо проверять доступ пользователя к сделке. | 🔴 Критический |
| 4 | `sourcing/views.py` | 49–55 | **IDOR на эндпоинте статуса импорта** — `ImportStatusView` позволяет любому аутентифицированному пользователю проверить любую Celery-задачу по ID. Хотя ID задач — UUID, результаты могут содержать конфиденциальные данные сделки (количество позиций, сообщения об ошибках с названиями компаний). | 🔴 Критический |
| 5 | `catalog/views.py` | 69–86 | **bulk_publish без проверки прав на объект** — Действие `@action` наследует `get_permissions()`, который для `list` и `retrieve` возвращает `AllowAny`, а для остальных — требует Admin. Однако `product_ids` передаётся пользователем и не валидируется — злоумышленник может опубликовать черновые товары, к которым не должен иметь доступа, угадав ID. | 🟡 Высокий |

## Замечания высокой серьёзности

| # | Файл | Строки | Рекомендация | Категория |
|---|------|--------|--------------|-----------|
| 1 | `core/settings.py` | 339–342 | **Слишком мягкие лимиты запросов (throttle)** — `anon: 1000/min` и `user: 10000/min` чрезмерно высоки. Публичный эндпоинт `LeadCreateView` может быть использован для спама. Рекомендуется: `anon: 20/min`, `user: 200/min` с переопределением для отдельных эндпоинтов. | Безопасность |
| 2 | `sourcing/tasks.py` | 53 | **Неограниченная обработка Excel-файлов** — `pd.read_excel(BytesIO(file_content))` без ограничения строк. Вредоносный файл на 500 МБ исчерпает память Celery-воркера. Нужно добавить ограничение `nrows` и валидацию размера файла перед передачей в Celery. | Безопасность / Производительность |
| 3 | `sourcing/tasks.py` | 102–103 | **Утечка внутренних ошибок** — `return {'status': 'error', 'message': str(e)}` передаёт клиенту внутренние детали ошибок (имена таблиц, SQL-ошибки, пути к файлам). Необходимо санитизировать сообщения об ошибках. | Безопасность |
| 4 | `crm/views.py` | 112–115 | **ActivityLog без RBAC-фильтрации** — `ActivityLogViewSet` использует `queryset = ActivityLog.objects.all()` без фильтрации по пользователю/компании. Журнал действий виден всем аутентифицированным пользователям. `IsOwnerOrManagerOrAdmin.has_object_permission` не сработает для объектов ActivityLog (нет полей `company`, `deal`, `quote`), поэтому не-сотрудники получают пустой результат. Это хрупко — откат к `return False` неявный, а не намеренный. | Безопасность |
| 5 | `accounts/services.py` | 36–37 | **URL настройки пароля использует VITE_API_URL** — `getattr(settings, 'VITE_API_URL', 'http://localhost:5173')` по умолчанию возвращает localhost. Это фронтенд-переменная, а не Django-настройка. В продакшене письма будут содержать ссылки на `http://localhost:5173`. Нужна отдельная Django-настройка `FRONTEND_URL`. | Корректность |
| 6 | `frontend/src/api/client.ts` | 14–26 | **JWT хранится в localStorage** — Access- и refresh-токены в localStorage уязвимы к XSS. Если любая зависимость или инъектированный скрипт вызовет `localStorage.getItem('railtech-auth')`, оба токена будут скомпрометированы. Рекомендуется httpOnly cookie для refresh-токена. | Безопасность |
| 7 | `catalog/models.py` | 143–151 | **Обновление пути EquipmentGroup через строковый Replace** — `Replace(F('cached_path'), Value(old_path), Value(new_path))` некорректно обновит узлы с совпадающим префиксом пути. Например, переименование "Вагоны" в "Вагоны-2" также заменит префикс в "Вагоны грузовые", даже если это отдельное поддерево. Нужна фильтрация по `startswith` с точной заменой префикса. | Корректность |
| 8 | `crm/consumers.py` | 93–97 | **Нет ограничения длины сообщения в WebSocket** — `save_message` принимает текст любой длины. Клиент может отправлять многомегабайтные сообщения, переполняя базу данных и Redis channel layer. Нужна проверка `max_length` (например, 5000 символов). | Безопасность |

## Замечания средней серьёзности

| # | Файл | Строки | Рекомендация | Категория |

| 1 | `catalog/views.py` | 89–98 | **SupplierOfferViewSet слишком открыт для записи** — Любой аутентифицированный пользователь может создавать/обновлять офферы (`return [permissions.IsAuthenticated()]`). Должна требоваться принадлежность к компании-поставщику или staff-уровень доступа. Сейчас пользователь-CLIENT может создавать фейковые офферы поставщиков. | Безопасность |
| 2 | `sourcing/tasks.py` | 67–91 | **Создание QuoteItem в цикле запускает индивидуальные save** — Каждый `QuoteItem.objects.create()` вызывает `QuoteItem.save()`, который запускает `recalculate_totals()`. Для импорта из 200 строк Excel это означает 200 полных пересчётов. Финальный `quote.recalculate_totals()` на строке 100 избыточен. Используйте `bulk_create` и один финальный пересчёт. | Производительность |
| 3 | `crm/services.py` | 55 | **Позиции КП загружаются без оптимизации** — `items = quote.items.all()` загружает все позиции, затем итерирует в Python. Для КП с большим количеством позиций нужен `select_related('product__domain_type')`, чтобы избежать N+1 запросов при проверке `item.product.domain_type.code`. | Производительность |
| 4 | `accounts/views.py` | 115 | **UserViewSet использует Django-встроенный IsAdminUser** — `permissions.IsAdminUser` проверяет `user.is_staff` (встроенный флаг Django). Остальной код использует `SystemRole.is_staff_level` для RBAC. Пользователь может быть `is_staff=True`, но иметь роль CLIENT — создаётся несогласованный доступ. Используйте кастомный `IsAdminUser` из `core.permissions`. | Безопасность |
| 5 | `core/settings.py` | 192 | **CORS_ALLOW_ALL_ORIGINS в режиме DEBUG** — Хотя ограничено DEBUG-режимом, это позволяет любому источнику делать аутентифицированные запросы в разработке. В сочетании с `CORS_ALLOW_CREDENTIALS = True` это рискованно, если DEBUG случайно попадёт в staging-окружение. | Безопасность |
| 6 | `catalog/models.py` | 229–238 | **Валидация RAILWAY_MACHINERY работает только при обновлении** — `clean()` проверяет `self.pk and not self.equipment_groups.exists()`, то есть при первом создании (`self.pk` равен None до save) валидация пропускается. Группы оборудования (M2M) можно добавить только после создания товара, поэтому эта валидация никогда не поймает отсутствие группы при создании. Рассмотрите post-save сигнал или валидацию на уровне формы. | Корректность |
| 7 | `frontend/src/api/client.ts` | 46 | **Гонка при обновлении токена** — Несколько одновременных 401-ответов запустят независимые попытки refresh. Только первая успеет; остальные могут провалиться, если включён `ROTATE_REFRESH_TOKENS` (старый refresh-токен инвалидируется). Нужна очередь/мьютекс для refresh. | Корректность |
| 8 | `crm/views.py` | 37–39 | **Создание сделки автоматически назначает компанию без валидации** — `perform_create` использует `request.user.primary_company`, но если у пользователя нет основной компании (null), сделка создаётся с `company=None`. Поле `company` в Deal не nullable (`on_delete=models.CASCADE`), поэтому возникнет `IntegrityError`. Нужна проверка на null. | Корректность |

## Что сделано хорошо

- **Финансовый конвейер только на сервере** — `QuoteCalculationService` выполняет все денежные расчёты с `Decimal`, атомарными транзакциями и `select_for_update()`. Это продакшен-уровень.
- **Доменно-ориентированная архитектура** — Трёхдоменная модель (RAILWAY_MACHINERY, GENERAL_GOODS, SERVICES) со строгими правилами иерархии грамотно спроектирована и чётко соблюдается.
- **Мультитенантность через CompanyMember** — Паттерн M2M через промежуточную модель чистый, поддерживает множество компаний на пользователя и правильно фильтрует QuerySet'ы.
- **Движок умного сопоставления** — 3-уровневый подход (точное совпадение → извлечение чертежа → триграммный нечёткий поиск) хорошо спроектирован с правильными весами скоринга.
- **Дисциплина TypeScript на фронтенде** — Не обнаружено типов `any`. Используются правильные интерфейсы, Zod-валидация и Decimal.js для отображения расчётов на клиенте.
- **Паттерн master data** — `AbstractLookup` устраняет захардкоженные enum'ы и делает систему конфигурируемой без изменения кода.
- **Аутентификация WebSocket** — JWT-мидлвар для Channels корректно реализован с правильным отклонением анонимных подключений.
- **Массовые операции** — `bulk_update` в `recalculate_quote`, `Replace` для путей групп оборудования — демонстрируют внимание к производительности БД.

## Вердикт

**Требуются доработки** — 5 критических проблем должны быть устранены до вывода в продакшен:

1. **Исправить RBAC в ChatConsumer** — Заменить `UserRole.SALES_MANAGER` на корректную проверку через `SystemRole`, соответствующую паттерну из `IsOwnerOrManagerOrAdmin`.
2. **Устранить O(n²) при импорте Excel** — Использовать `bulk_create` для QuoteItem при импорте, затем один `recalculate_totals()` в конце.
3. **Добавить авторизацию на уровне сделки в sourcing-эндпоинты** — Проверять доступ пользователя к сделке перед разрешением импорта.
4. **Ограничить статус задачи запрашивающим пользователем** — Сохранять `user_id` вместе с Celery-задачей и валидировать принадлежность при проверке статуса.
5. **Ужесточить права на запись SupplierOffer** — Требовать staff-уровень или принадлежность к компании-поставщику для создания/обновления.

Кодовая база фундаментально надёжна в своей архитектуре и финансовой корректности. Критические проблемы — это в основном пробелы авторизации в более новых эндпоинтах (sourcing, WebSocket), которые, вероятно, были добавлены после создания основного RBAC-фреймворка.
