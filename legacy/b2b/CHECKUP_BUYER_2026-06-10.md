## 🔴 Критично

### 1. Покупатель не может открыть RFQ — 403 «только для платформенных админов»
- Создание заявки работает: `POST /crm/deals/` → **201**, сделка появляется в статусе «Черновик».
- Перевод «Черновик → RFQ_OPEN» через кнопку «Открыть RFQ»: `POST /crm/deals/41/open-rfq/` → **403**, тело: `{"detail":"Access restricted to platform administrators."}`.
- Тот же 403 с тем же сообщением на `GET /accounts/companies/?types__code=SUPPLIER` (список поставщиков для приглашения).
- Проверено через `/me/`: пользователь — обычный `USER`, `OWNER`, `can_buy=true`, `is_platform_admin=false`. То есть это **легитимный покупатель**, которому закрыли его же ключевое действие.
- **Влияние:** сделка навсегда застревает в «Черновик». Нет перехода в RFQ → нет приглашения поставщиков → нет бидов → нет КП → нет контракта. **Весь цикл закупки у покупателя не работает.**

**Точная причина (подтверждено по коду):**
- `backend/crm/views/deals.py:206` — экшен `open-rfq` получил `permission_classes=[IsAuthenticated, IsPlatformAdmin]` (скопировано с соседнего админского `force-change-stage`). `IsPlatformAdmin` отсекает всех не-админов до вызова сервиса.
- При этом сам сервис `crm/services/deals.py::open_rfq` написан **правильно для покупателя**: возвращает `ADMIN_VIEWER_CANNOT_ACT` для админ-вьюера и требует `is_member_of(actor, deal.company_id, capability="buy")`. То есть бизнес-логика ждёт покупателя, а вью-пермишен делает ровно наоборот.
- Соседний `change-stage` (стр. 120) сделан корректно — без override, наследует классовый `[IsAuthenticated, IsCompanyMemberOrPlatformAdmin]`.
- **Почему CI не поймал:** `crm/tests/test_golden_path.py` вызывает `open_rfq(deal.id, buyer_user)` на уровне сервиса, минуя пермишен вью. DRF-интеграционного теста на эндпоинт нет (см. test-debt в CLAUDE.md).

**Фикс (одна строка):** в `backend/crm/views/deals.py:206` убрать `permission_classes=[IsAuthenticated, IsPlatformAdmin]` у `open-rfq` — пусть наследует классовый `IsCompanyMemberOrPlatformAdmin`; реальную авторизацию (`capability="buy"`) уже выполняет сервис. Затем добавить DRF-тест: покупатель (can_buy) открывает RFQ → 200; админ → 403/`ADMIN_VIEWER_CANNOT_ACT`.

**По списку поставщиков** (`GET /accounts/companies/?types__code=SUPPLIER`, тот же `IsPlatformAdmin`): решить продуктово — должен ли покупатель видеть всех поставщиков. Если да — заменить пермишен на членский; если нет — убрать вызов из UI приглашения.

### 2. Тихий провал — пользователь не видит ошибку
- При 403 на «Открыть RFQ» модал просто **остаётся открытым**: ни тоста, ни сообщения, в консоли тоже пусто.
- Реальный покупатель будет жать кнопку без какой-либо реакции и не поймёт, что и почему не работает.
- **Что сделать:** показывать ошибку с бэка (toast) на всех мутациях; не «глотать» 4xx молча.

## 🟠 Блокер по данным / UX

### 3. Пустой каталог → создать заявку через каталог невозможно
- Каталог на проде: **0 товаров, 0 офферов, 0 поставщиков** («Товары не найдены»).
- Кнопка «Новый запрос» в «Мои заявки» ведёт **в каталог** (флоу через корзину) — а он пуст → тупик.
- Даже при исправленных правах покупателю нечего искать и не у кого запрашивать.
- **Что сделать:** засеять каталог/офферы/поставщиков; для пустого каталога показать понятный empty-state с альтернативой (например, заявка с импортом позиций из Excel, минуя каталог).
