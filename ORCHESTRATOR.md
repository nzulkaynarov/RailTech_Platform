# ORCHESTRATOR — управление работами RailTech Platform (`rt_platform`): CRM · Cabinet · ERP

Версия 1.0 · 2026-10-13 · Владелец: Нурбек · Этот документ — единственный источник правды о том,
**что делается сейчас, кем и в каком порядке**. Агент читает его первым в каждой сессии, обновляет
`docs/PROGRESS.md` в конце каждой сессии и никогда не начинает веху, гейт которой не отмечен владельцем.

---

## 1. Цель

Из двух готовых систем (CRM и B2B-платформа) собрать три:

| Система | Для кого | Отвечает на вопрос | Домен |
|---|---|---|---|
| **CRM** | фронт-офис | «кто пришёл и стоит ли с ним работать?» | `crm.railtech.uz` |
| **ERP** | бэк-офис | «что сделать по запросу клиента и в каком он состоянии?» | `erp.railtech.uz` |
| **Cabinet** | клиент | «что с моими запросами и где мои документы?» | `cabinet.railtech.uz` |

Ансамбль универсален для товаров и услуг, без отраслевых сущностей, с ИИ во всех трёх по принципам
CRM. Ценность и пути — `docs/BUSINESS.md`; устройство — `docs/ARCHITECTURE.md`; шов — `docs/CONTRACTS.md`.

## 2. Топология (чтобы все одинаково понимали «две сущности»)

- **Два бэкенда**: `apps/crm` (своя база `crm`) и `apps/erp` (своя база `erp`).
- **Три фронтенда**: CRM SPA, ERP SPA, Cabinet SPA. Cabinet без бэкенда — ходит в ERP `/api/portal/*`.
- **Связь CRM ↔ ERP**: интеграционный API ERP (CRM зовёт), вебхуки ERP → CRM, `erp-mcp` для бота,
  SSO-токены в обе стороны. Всё в `docs/CONTRACTS.md`.
- **Общие сервисы** (`infra/`): Caddy, PostgreSQL 17 (две базы), Redis, LiteLLM, Langfuse, RustFS,
  SMTP-релей. Один клиентский Telegram-бот, принадлежит CRM; Mini App указывает на Cabinet.

## 3. Инварианты (нарушение = PR не принимается)

1. **Одна система — один главный пользователь.** Клиент не входит в CRM и ERP; сотрудник не входит в Cabinet (только режим «глазами клиента» из ERP).
2. **Общих таблиц нет.** `crm` и `erp` — разные базы. Связь по внешним идентификаторам (`crm_client_id`, `erp_company_id`, `erp_deal_id`), идемпотентность по ним.
3. **Контракт раньше кода.** Любое изменение API/событий/MCP/токенов начинается с `packages/contracts`, генерируемые клиенты пересобираются в том же PR, обе стороны обновляются в одной вехе.
4. **Код решает, модель предлагает.** Стадии, права, доступ к данным, цены — детерминированная логика с тестами. Идентификаторы клиента/компании в инструменты агентов приходят только из подписанного контекста.
5. **Клиент видит только опубликованный слой** каталога и только проекцию сделки (без поставщиков, себестоимости, маржи). Проверяется негативными тестами.
6. **Секреты только в окружении.** `gitleaks` в pre-commit. Модели — через LiteLLM по алиасам; прямых SDK-вызовов провайдеров в коде нет.
7. **Одна передача — один владелец.** Лид → клиент: CRM. Результат → клиент: ERP. Вопрос → ответ: бот CRM с данными ERP.
8. **Документация в том же PR**: контракты, ADR, PROGRESS, runbook, OpenAPI.
9. **DoD с UI = сценарий глазами** (скриншот/GIF в PR), с замером, не предположением.
10. **Отклонение от ARCHITECTURE / CONTRACTS — через ADR** (`docs/adr/`, MADR, статус proposed) и решение владельца. Никогда молча.
11. **`legacy/b2b` не редактируется.** Берём из него код копированием; после вехи M2 папка удаляется, остаётся тег `b2b-final`.
12. **Benchmark-first для продуктовых задач** (правило владельца из B2B): перед механикой — как это решают Odoo / ERPNext / SAP B1 / Intercom / PandaDoc, именованный паттерн, потом код.
13. **Продуктовый подход и минимум работы админа** (поручение владельца 2026-10-14). Любое решение оценивается по пути пользователя — лида, клиента, сотрудника фронт- и бэк-офиса, администратора: понятно, коротко, без лишних шагов и терминов. **Одна консоль администратора — CRM** («Подключения», «Модели ИИ», «Почта», «Пользователи», «Состояние системы», «Расходы»): ключи, токены, секреты и адреса внешних сервисов вводятся там один раз и не дублируются в ERP/Cabinet и не требуют правки `.env` и перезапуска; всё, что система может сгенерировать, проверить или подставить сама — делает сама (кнопки «Подключить», «Проверить связь», понятные ошибки с подсказкой, что сделать). `.env` — только для загрузки и аварийного резерва. **Админ видит и контролирует все внешние сервисы ансамбля** (всё, что интегрировано помимо CRM и ERP: Telegram Bot API, вендоры моделей через LiteLLM, Langfuse, почтовый релей, S3-хранилище, docling, источники курсов ЦБ и таможенного тарифа, Sentry, внешнее хранилище бэкапов, TLS-сертификаты доменов, позже платёжные провайдеры и ЭЦП): для каждого — живой статус, последние ошибки, нагрузка и стоимость, включить/выключить, ключи, оповещение при сбое. Новый внешний сервис не принимается в код без строки в реестре внешних сервисов (M3-CRM-12).

## 4. Агенты и зоны ответственности

Работа ведётся сессиями Claude Code. Каждая сессия берёт **одну роль** и **одну задачу** из §6.

| Роль | Зона | Читает первым | Не трогает |
|---|---|---|---|
| **Оркестратор** (ведущая сессия) | назначает задачи, следит за `PROGRESS.md`, собирает вопросы владельцу, готовит гейты | ORCHESTRATOR, PROGRESS, QUESTIONS | код приложений |
| **Агент CRM** | `apps/crm` | `apps/crm/CLAUDE.md`, SPEC CRM, CONTRACTS | `apps/erp`, `apps/cabinet` |
| **Агент ERP** | `apps/erp` | `apps/erp/CLAUDE.md`, ARCHITECTURE §4, MIGRATION-MAP, CONTRACTS | `apps/crm`, `apps/cabinet` |
| **Агент Cabinet** | `apps/cabinet` | `apps/cabinet/CLAUDE.md`, ARCHITECTURE §5, CONTRACTS (portal) | бэкенды; при нехватке портального API — задача агенту ERP через QUESTIONS/PROGRESS, не обход |
| **Агент Infra** | `infra/`, `packages/`, CI, Makefile корня | ARCHITECTURE §10, CONTRACTS | бизнес-код |
| **Агент QA (глазами)** | сквозные сценарии через три системы, скриншоты, axe, дефекты одной волной | BUSINESS §4–5 | не чинит сам — заводит находки |

Правила совместной работы:
- Ветка `m<N>/<система>-<NN>-<slug>` (пример `m1/erp-03-fresh-migrations`). Один PR — одна задача.
- Исправления по аудиту — ветка `fix/<система>-<NN>-<slug>` (пример `fix/erp-02-portal-master-code`; `all` — несколько систем), NN — номер FIX. `main` защищена: в неё попадает только PR с зелёным «CI ok», прямой push и `git merge` в `main` запрещены.
- Перед PR: `make check-<система>`; для задач с контрактом — `make contracts`.
- Параллельность: задачи одной вехи без зависимостей идут в разных сессиях. Зависимости указаны в §6.
- Конфликт двух агентов на одном файле контракта — решает оркестратор, контракт не правят вдвоём.
- Каждая сессия заканчивается строкой в `docs/PROGRESS.md`: задача, статус, что осталось, что нужно владельцу.

## 5. Гейты владельца

Веха закрыта только после отметки владельца в `docs/PROGRESS.md`. Что он проверяет — в столбце
«Гейт» §6. Агент готовит к гейту: чек-лист «Проверить глазами» в описании последнего PR вехи,
скриншоты, `make up` на трёх доменах локально.

## 7. Протокол сессии агента

1. Прочитать: `ORCHESTRATOR.md` → `docs/PROGRESS.md` → `docs/QUESTIONS.md` → `docs/DECISIONS.md` → `CLAUDE.md` своего приложения → разделы `docs/ARCHITECTURE.md`/`docs/CONTRACTS.md`, на которые ссылается задача.
2. Взять задачу по ID, проверить, что её зависимости закрыты в PROGRESS. Если нет — взять другую или спросить оркестратора.
3. Ветка по схеме §4. Для продуктовой задачи — короткий benchmark-разбор в описании PR.
4. Реализация тест-first для доменной логики; контракт — раньше кода; документация — в том же PR.
5. `make check-<система>`, для UI — прогон глазами со скриншотом, для контракта — `make contracts`.
6. PR по шаблону: что, почему, как проверить глазами, что обновлено в docs, открытые вопросы.
7. Строка в `docs/PROGRESS.md`; новые вопросы — в `docs/QUESTIONS.md` (контекст → варианты → рекомендация).
8. Нельзя: начинать следующую веху без гейта; править `legacy/b2b`; добавлять общие таблицы; звать провайдера моделей напрямую; тратить деньги на evals без «да» владельца на конкретный прогон.

## 8. Что делает владелец

Решения (`docs/DECISIONS.md`), ответы на вопросы (`docs/QUESTIONS.md`), гейты вех, инфраструктурные действия
(`docs/OWNER-CHECKLIST.md`), приёмка глазами с агентом QA. Время владельца на веху — решения в начале и
приёмка в конце.

Поручение владельца 2026-10-13: до гейта очередной вехи агенты **не ждут ответа** на открытые вопросы —
решают по рекомендации из `QUESTIONS.md` или по бенчмарку (§3.12), записывают решение в `docs/DECISIONS.md`
с пометкой «по рекомендации»; владелец пересматривает их на гейте.
