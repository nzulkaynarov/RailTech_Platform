## Итог в трёх фразах

1. **Основа здоровая.** Права ролей соблюдены везде (прямой URL → понятный 403, наблюдатель не видит кнопок записи), горизонтальной прокрутки нет, общие компоненты прошлого аудита (`PageHeader`, `PageState`, `labels`, `lib/time`) внедрены.
2. **Но это пока набор CRUD-экранов, а не рабочее место менеджера**: главный сигнал (кто ждёт и сколько) нигде не выделен, в карточке лида 6 равновесных кнопок, а главная кнопка на чужом лиде — перехват.
3. **Тема Ant Design по умолчанию не проходит WCAG AA**: 565 нарушений контраста на 57 из 58 экранов, и всё это — одно место (`App.tsx:93`, `ConfigProvider` без `theme`).

## Что работает хорошо

- Права: навигация = `policy.seed.csv`; чужой раздел → 403 с «На главную»; наблюдатель видит причину под чатом вместо поля ввода.
- Нет кликабельных `div`/`tr`, нет `outline: none`, `<html lang="ru">`, подтверждение опасных действий, ошибки входа — `role="alert"`, модалки держат фокус.
- Фильтры лидов в URL, таймзона Ташкента в `lib/time`, неактивные кнопки с причиной.
- Тексты бота: все ключи на трёх языках, кнопки короче 30 символов.

## План

Порядок — от «одна правка закрывает много» к перестройке экранов. Платных вызовов моделей ни одна волна, кроме отмеченной, не требует.

**Волна A — без решений владельца, быстрые (≈ 1 PR):**
1. Тема `app/theme.ts` с цветами из отчёта 4 (все пары ≥ 4.74:1) → повторный axe-скан как проверка (#1).
2. Добить сырые коды: триггеры в `transitionReason`, diff аудита, продукты, подписи 26 текстов бота + тест-сторож «нет латинских кодов в UI» (#2).
3. Ошибки API: подкоды / `details.field` → конкретный текст и подсветка поля; 404 → `NotFound` (#3).
4. Дашборд: ссылки плиток по правам, «Сделок» → корректный фильтр, цвета баров по смыслу (#19).
5. Мобильное меню в шапку (#15); `LeadActionDialog` → `tashkent()` (#13); статус соединения текстом (#14); ссылка «Сменить пароль» в профиле (#12).
6. a11y-база: h1 = заголовок страницы, `<main>` на логине, `DocumentTitleHandler`, подписи фильтров / `Switch` / `Progress`, `role="log"` для чата, `aria-live` для тостов (#6).
7. Карточка канала: стадия и причины словами из CRM, порог из настроек (#22).

**Волна B — перестройка рабочих экранов (≈ 1–2 PR, после A):**
8. Иерархия действий лида: одно primary по состоянию, редкое в «Ещё», чужой лид — баннер вместо серых кнопок, «Перехватить» не primary (#8).
9. «Входящие»: SLA-таймер и цвет по порогам из настроек, сортировка по ожиданию, счётчик в меню; «Забрать» → сразу в карточку (#7, #10).
10. Мобильные: лиды карточками на `xs`, закреплённое поле ответа, Enter = перенос, цели ≥ 44 px (#16, #17).
11. Настройки: навигация слева с группами, типизированные виджеты (время, дни, пользователи по имени), группы текстов бота с описанием «когда отправляется» и липкое «Сохранить» (#18).
12. Дизайн-система: `LeadLink`, `EmptyState`, `useApiErrorToast`, `PageState` для всех запросов, `PageBody`, CSS-переменные вместо хардкода; разделить `ru.ts` (>400 строк) (#5, #20).

**Волна C — нужны решения владельца** (вынести в `docs/QUESTIONS.md`):
- Q-015: один термин — «Передача» или «Эскалация»; метки стадии `handoff` («Передан») и режима паузы («Бот на паузе») (#4).
- Q-016: «Нет ответа в базе» — честное «позвать менеджера?» вместо «уточню у коллег» (#21). Меняет промпт → golden + один целевой прогон eval (≈ 5–10 вызовов, < $0.1) **только с вашего «да»**.
- Q-017: сервисные запросы — отдельный список/фильтр во «Входящих» со статусом «в работе» (#9) — связано с Q-013 «Сделка как сущность».
- Q-018: «Отложить» открытую эскалацию может любой менеджер (сейчас так, `services/leads.py:165`) или только назначенный дежурный?
