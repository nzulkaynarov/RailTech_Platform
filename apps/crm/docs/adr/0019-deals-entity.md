# 0019. Сделка — отдельная сущность рядом с лидом; воронка лида не дублируется

- Статус: accepted (2026-10-12, владелец: Q-013 «по бенчмарку» Pipedrive / HubSpot / Kommo)
- Дата: 2026-10-12
- Авторы: агент, владелец
- Связано: SPEC §5.2, §5.7, §10.1; ADR-0015, ADR-0016, ADR-0017; DECISIONS Q-013

## Контекст и проблема

Итог работы с лидом фиксировался только стадией лида (`won` / `lost`) и текстовой заметкой. Нельзя было
ответить «сколько заработали за месяц», «почему проигрываем», «какие сделки у клиента в работе», а у
клиента с повторными покупками все итоги смешивались в одном лиде (ADR-0015: «Новая сделка» лишь
возвращает лид в работу). Владелец решил (Q-013): таблица `deals`, у клиента несколько сделок; продукт,
сумма (необязательно), стадия, ожидаемая дата, ответственный, причина отказа из справочника в «Настройках»;
дашборд — выигрыш/проигрыш по причинам и суммам.

## Драйверы решения

- Не ломать принятый жизненный цикл лида (ADR-0015) и действия команды над лидом.
- Данные согласованы: закрытый лид и его сделка не могут разойтись.
- Код решает, справочник задаёт админ (ADR-0016): причины отказа — настройка, а не константы.
- Минимум новой воронки: у бенчмарков (Pipedrive, HubSpot, Kommo) лид/контакт и сделка — разные объекты,
  но маленькой команде не нужна вторая настраиваемая воронка.

## Рассмотренные варианты

1. **Таблица `deals` с тремя стадиями `open` / `won` / `lost`; воронка остаётся у лида** (выбран).
2. Сделка с собственной настраиваемой воронкой (как Pipedrive pipelines) — дублирует стадии лида,
   менеджер ведёт два статуса одного разговора; отложено до запроса владельца.
3. Поля суммы и причины прямо в `leads` — не даёт нескольких сделок клиента (повторные покупки).

## Решение

Вариант 1.

**Схема** (`deals`, миграция `0015_deals`): `id, client_id NULL → clients, lead_id NULL → leads,
title, product_key NULL, amount NUMERIC(14,2) NULL (≥ 0), currency CHAR(3) DEFAULT 'UZS',
stage 'open'|'won'|'lost', expected_close_date DATE NULL, closed_at NULL, lost_reason NULL,
owner_user_id NULL → users, created_at, updated_at`. Внешние ключи `ON DELETE SET NULL`: удаление лида
или пользователя не стирает историю продаж.

**Связь с лидом и клиентом.** Лид — точка входа из Telegram, как прежде. Сделка создаётся вручную
(раздел «Сделки», карточка клиента) или при закрытии лида. Действия лида `close_won` / `close_lost`
в той же транзакции (`LeadService.close` → `services/deals.apply_lead_outcome`):
- «Сделка заключена» — открытая сделка лида становится `won`, иначе создаётся выигранная сделка
  (название — имя лида, продукт — первый из `product_interest`, клиент и ответственный — из лида);
  сумма — необязательное поле тела `Close.amount`;
- «Закрыть отказом» — открытая сделка лида становится `lost` с причиной; причина — значение
  `Close.lost_reason`, если оно есть в справочнике, иначе «Другое» (свободный текст отказа остаётся
  заметкой лида, как раньше). Отказ без открытой сделки сделку не создаёт.
Ошибка записи сделки откатывает и закрытие лида — частично закрытых состояний нет.
Стадии лида `won` / `lost` и переход в `customer` (ADR-0015) не меняются.

**Переходы стадий сделки** (`domain/deals.py`, параметризованные тесты): `open → won/lost`,
`lost → open/won` (переоткрыть), `won` — финал: менять может только админ (409 `deal_won_final`).
`closed_at` ставится при `won`/`lost` и снимается при возврате в `open`.

**Справочник и валюта** — ключ настроек `deals`: `lost_reasons` (список подписей; по умолчанию «Дорого»,
«Выбрали конкурента», «Нет бюджета», «Не актуально», «Не вышли на связь», «Другое») и `currency`
(по умолчанию `UZS`). Причина хранится в сделке **текстом подписи**, а не отдельным кодом: переименование
или удаление причины в настройках не превращает старые сделки в «неизвестный код», отчёт группирует по
сохранённому тексту. Валюта — поле каждой сделки; сводка суммирует по валютам раздельно, без конвертации.

**API и права**: `GET/POST /api/v1/deals`, `GET/PATCH /api/v1/deals/{id}`,
`GET /api/v1/deals/summary?days=`, `GET /api/v1/deals/options` (справочник для форм — менеджер не имеет
`settings:read`). `deals:read` — viewer/manager/admin, `deals:write` — manager/admin; каждая мутация —
запись в `audit_log` (`deal.create`, `deal.update`, `deal.won`, `deal.lost`).

## Последствия

- Плюсы: выручка и причины отказов видны на дашборде; у клиента история сделок; плитка «Сделок»
  получила переход (`/deals?stage=won`) вместо тупика.
- Минусы: два места с итогом (стадия лида и сделка) — согласованность держит одна транзакция и тесты.
  Сделки, закрытые до миграции, не восстанавливаются (бэкфилл не делаем: сумм и причин в данных нет).
- Отложено: собственная воронка сделок, конвертация валют, поле суммы и выбор причины в диалогах
  закрытия лида на фронте (API уже принимает `amount` / `lost_reason`).
