# 0014. Ограничивать расходы на модели в три уровня; нагрузочный smoke — в процессе

- Статус: accepted (2026-10-12, владелец: «принимаю все рекомендации», Q-007)
- Дата: 2026-10-08
- Авторы: агент
- Связано: SPEC §11 (бюджет моделей), §13; PLAN Фаза 7 задача 4, Фаза 8 задачи 7–8; ADR-0004

## Контекст и проблема

PLAN Фазы 8 просит «бюджеты LiteLLM по ключам». В LiteLLM 1.104.2 бюджеты ключей и
глобальный `max_budget` работают только с БД LiteLLM (Prisma); без неё прокси пишет
«budget will NOT be enforced». Отдельная БД, миграции Prisma и выпуск виртуальных
ключей — заметная эксплуатационная нагрузка ради одного ограничителя.

Нагрузочный smoke (PLAN: locust, 50 диалогов) по HTTP не измеряет ход: webhook Telegram
отвечает 200 сразу, ответ уходит асинхронно.

## Решение

Бюджет — три уровня:
1. **Мягкий** — `settings.budget.daily_usd` (сутки по Ташкенту): BudgetGuard переводит диалог
   на `fallback-model`, квалификатор работает; алерт в канал при > 80 %.
2. **Жёсткий** — `router_settings.provider_budget_config` LiteLLM (USD/сутки на провайдера,
   счётчик в памяти прокси, БД не нужна): сверх лимита запросы отклоняются → бот передаёт
   диалог человеку (штатная деградация).
3. **Провайдер** — лимиты расходов в консолях Anthropic/Google на prod-ключах (человек, runbook).

Значения (решение владельца 2026-10-12, Q-008): жёсткий потолок Anthropic **$3/сутки** (диалог,
квалификатор, судья eval), Gemini **$1/сутки** (fallback-model, эмбеддинги); мягкий `daily_usd` **$2** —
алерт с $1.6, с $2 диалог на `fallback-model`, квалификатор продолжает до потолка $3. Учитывать:
платные прогоны (`make eval` ≈ $0.5, `make load-test`) идут через тот же LiteLLM и расходуют те же сутки.

Нагрузочный smoke — CLI `python -m app load-test`: 50 параллельных синтетических клиентов
через тот же `ConversationService`, что и бот (модели, MCP, KB, очередь квалификатора),
гейт p95 ≤ 6 с и очередь вернулась к исходной; синтетические лиды удаляются.

### Последствия

- Хорошо: нет новой БД; три независимых предохранителя; нагрузка меряет реальный путь хода.
- Плохо: счётчик LiteLLM сбрасывается при рестарте прокси (поэтому есть уровень 3).
- Плохо: отклонение от формулировок PLAN («по ключам», «locust») — отражено в PROGRESS.
- Пересмотр: появится несколько потребителей LiteLLM (другие команды) → БД LiteLLM и ключи.

### Как проверяем

Unit/integration BudgetGuard и монитора; гейт Фазы 8: `make load-test` PASS; `daily_usd = 0.01`
на dev → ответы через fallback-model и алерт бюджета.
