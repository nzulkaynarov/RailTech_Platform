# 0018. Подключения настраивает админ в CRM; секреты интеграций — в БД зашифрованными

- Статус: accepted (2026-10-12, владелец: «делай все» по плану `docs/audit/2026-10-12-admin-console-scope.md`)
- Дата: 2026-10-12
- Авторы: агент, владелец
- Связано: SPEC §2, §3, §5, §11, §13; CLAUDE.md §2.3, §11; ADR-0003, ADR-0004, ADR-0013, ADR-0014; DECISIONS Q-008, Q-010

## Контекст и проблема

Токен бота, режим бота, ключи моделей и жёсткие лимиты расходов жили в `.env` и конфиге LiteLLM: любая
смена — доступ к серверу и перезапуск. Канал команды подключался вводом `-100…` вручную, первый админ —
командой `make create-admin`. Статус системы и алерты уходили в канал команды, полный расход не был виден.
Владелец: «максимально отдадим админу всё», CRM при старте должна вести через настройку подключений.

## Драйверы решения

- Запуск и смена подключений без разработчика и без доступа к серверу (BUSINESS C6).
- Безопасность секретов не хуже, чем в `.env`.
- Не изобретать: использовать штатные механизмы (LiteLLM, Telegram Bot API) там, где они есть.

## Рассмотренные варианты

1. Всё в `.env`, CRM только показывает статус.
2. Секреты интеграций в нашей БД зашифрованными, ключ шифрования — в `.env`; инфраструктура остаётся в `.env`.
3. Генерировать `.env`/конфиги из CRM и перезапускать контейнеры.

## Решение

Вариант 2.

**Граница.** В интерфейсе админа: токен бота, канал команды, лимиты по провайдерам, расходы, состояние
системы, бэкап «сейчас», личные уведомления, мастер первого запуска. На сервере (`.env`): пароли Postgres и
S3, `JWT_SECRET`, `AGENT_CONTEXT_KEY`, мастер-ключи LiteLLM и шифрования (`SECRETS_KEY`), домен, TLS, порты.

**Секреты.** Таблица `integration_secrets`: шифротекст (Fernet, ключ `SECRETS_KEY`), последние 4 символа,
кто и когда. Поле только на запись, значение не возвращается в API и не пишется в логи; смена — с
повторным вводом пароля админа и записью в аудит без значения. Порядок чтения: БД, иначе `.env` — старые
стенды работают без изменений. Бэкап содержит только шифротекст; `SECRETS_KEY` в бэкап не входит.

**Telegram.** Токен проверяется `getMe` до сохранения; бот перезапускается в процессе API без перезапуска
контейнера. Канал находится по событию `my_chat_member`, когда бота делают админом канала.

**Модели ИИ.** Сегодня — только просмотр ролей, статус, расход и платная проверка по кнопке. Смена провайдера
и ключа из CRM — следующим шагом через штатную БД LiteLLM (`store_model_in_db`, ключи шифруются
`LITELLM_SALT_KEY`), отдельным ADR после проверки на установленной версии LiteLLM.

**Лимиты.** Дневной лимит по провайдеру — `settings.budget.providers`, проверяет наш код перед вызовом;
`provider_budget_config` LiteLLM остаётся аварийным потолком; консоли провайдеров — третий уровень (ADR-0014).

**Уведомления.** Системные алерты — личным сообщением админам с Telegram ID и подпиской, канал — запасной
путь. Менеджеру — личное сообщение о новом сообщении его лида (Q-010), без кнопок.

### Последствия

- Хорошо: запуск и смена подключений из CRM; полный учёт расхода; канал команды — только про лидов.
- Плохо: появляется ключ `SECRETS_KEY`, его потеря делает сохранённые секреты нечитаемыми — их нужно
  ввести заново (значения в `.env` продолжают работать как запасные).
- Плохо: поверхность атаки CRM растёт — компенсируется ролью admin, повторным паролем и аудитом.
- Меняется: SPEC §5 (новые таблицы), §11 (секреты), CLAUDE.md §2.3 (модели — из конфига LiteLLM или его БД
  после следующего ADR), `.env.example`, runbooks `deploy.md`, `key-rotation.md`.

### Как проверяем

Unit: шифрование туда-обратно, значение не попадает в ответы и логи, повторный пароль обязателен, неверный
токен не сохраняется. Приёмка на стенде: смена токена бота из CRM — бот отвечает без перезапуска; канал
найден автоматически; тестовое сообщение дошло. Пересмотр — если появится внешний менеджер секретов (Vault).
