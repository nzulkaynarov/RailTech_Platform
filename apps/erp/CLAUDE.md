# CLAUDE.md — ERP (бэк-офис), `apps/erp`

Ты работаешь над **ERP** ансамбля Платформы: бэк-офис одной компании — заявка → КП → договор →
снабжение → исполнение → финансы. Один главный пользователь — **специалист бэк-офиса** (расчётчик,
закупщик, логист, финансист; «Администратор» = суперпользователь). Клиент сюда не входит — ему служит
Cabinet через портальный API этой же ERP. Продукт нейтрален к отрасли и бренду: имя и логотип — настройки.

**Статус документа: окончательный (M1-ERP-10, 2026-10-15).** Веха M1-ERP полностью реализована (задачи
M1-ERP-01…10 выполнены). Код очищен от наследия B2B/маркетплейса (§9), выстроена каноническая архитектура
приложений (§4), введены 6 системных ролей бэк-офиса и 10 пространств прав (§6), 2 слоя каталога (§5),
Settings Hub (M1-ERP-09), фиксация курсов валют и учёт отклонения маржи (M1-ERP-08), а контракт API зафиксирован
в `packages/contracts` с полным снимком схемы в `packages/contracts/openapi/erp-internal-full.json`.
Комплект эксплуатационных регламентов доступен в `apps/erp/docs/runbooks/`.

## 2. Инварианты ансамбля применительно к ERP (нарушение = PR не принимается)

1. **Один главный пользователь.** В ERP входят только сотрудники (SSO из CRM или пароль). Клиентских аккаунтов нет; клиент — контакт контрагента в `parties` с сессией портала, а не `User`.
2. **Общих таблиц с CRM нет.** База `erp` своя. Связь — внешние идентификаторы `crm_client_id`, `crm_lead_id`, `crm_contact_id`, `crm_user_id` (CONTRACTS §0); идемпотентность по ним и по `Idempotency-Key`.
3. **Контракт раньше кода.** Любой эндпоинт `portal`/`integration`, событие, инструмент MCP, claim токена — сначала `packages/contracts` (есть с M0-INF-02: `openapi/erp-*.yaml`, `events.schema.json`, `mcp-tools.json`, `sso-token.md`), потом код; клиенты пересобираются в том же PR (`make contracts`).
4. **Код решает, модель предлагает.** Стадии, права, цены, доступ — детерминированно и с тестами. Идентификаторы компании никогда не приходят от модели: только из подписанного `X-Agent-Context`.
5. **Клиент видит только опубликованный слой** каталога и проекцию сделки: без поставщиков, себестоимости, маржи. Каждый портальный эндпоинт — негативный тест «чужая компания → 404», «внутренний слой не отдаётся».
6. **Секреты только в окружении.** `gitleaks` в pre-commit корня. Модели — через LiteLLM по алиасам; импорт SDK провайдера в коде ERP запрещён (M1-ERP-06).
7. **`legacy/b2b` не редактируется.** Код копируется в `apps/erp`; `git log --follow` сохраняет историю.
8. **Документация в том же PR:** OpenAPI в `packages/contracts`, ADR, runbook, `docs/PROGRESS.md`.
9. **DoD с UI = сценарий глазами** (скриншот/GIF в PR, 1440 и 390 px), не «тесты зелёные».
10. **Benchmark-first** для продуктовых задач: как у Odoo / ERPNext / SAP B1 — именованный паттерн в описании PR, потом код.

## 5. Конвенции кода (из B2B; то, что остаётся верным)

**Python**
- Бизнес-логика **только в `<app>/services/`** как обычные функции: переходы FSM, валидации, побочные эффекты, письма, Celery-диспетчи. `views` и `admin.py` — тонкие обёртки: авторизовать → валидировать → вызвать одну функцию сервиса → вернуть. Одна и та же логика в admin-action и DRF-эндпоинте — запрещена; оба зовут сервис.
- **Словари сеются миграциями** (`RunPython` + `get_or_create`, reverse no-op): стадии, статусы, виды документов, роли, образцы шаблонов. После `migrate` на пустой базе каждый код, на который ссылаются сервисы, уже существует. В горячих путях — `Model.objects.get(code=...)`, не `get_or_create`. `loaddata` и management-команды — только для dev/demo.
- **Нет фейковых данных:** каждый эндпоинт читает реальную БД; никаких статических массивов и заглушек в продуктовом коде.
- **Нет хардкода:** URL, ключи, идентификаторы — из окружения; бизнес-константы — из БД или настроек; роли, стадии, статусы сравниваются по `code`, никогда по переведённому `name`.
- Ошибки API — `{"detail": "<CODE>"}` (DRF-native, CONTRACTS §0); фронтенд сравнивает код по значению. Держит тест вида `core/tests/test_error_shape.py` B2B.
- Бизнес-дата — `timezone.localdate()`, никогда `timezone.now().date()` (`TIME_ZONE=Asia/Tashkent`, `USE_TZ=True`).
- Списки — `select_related` / `prefetch_related`, без N+1; дашборды — `aggregate()` с условными `Count`, не `.count()` в цикле; пагинация у всех списков.
- Запрос не блокирует ASGI: PDF, импорт, ИИ — в Celery; публичные и тяжёлые ответы — 202 + `Retry-After`. Celery-задачи — с `time_limit`/`soft_time_limit`, ретраями и backoff (исключение — ИИ-задача, одна попытка: платный вызов).
- Загрузки — через валидаторы `core` (размер, тип, расширение, magic-bytes).
- **Вход в портал (FIX-14).** `MagicLinkToken.token_hash` и `PortalSession.token_hash` — SHA-256 токена (`portal/services/tokens.py`), сырой токен живёт только в cookie или в письме клиенту; в логи — не больше префикса из 6 символов (`core.logging.RedactPortalTokenFilter` прячет `/auth/magic/<token>` в путях запросов, `notifications.emails._redact_secrets` — в `EmailLog`, и `/auth/magic#token=<token>` тоже). Погашение — `select_for_update` + `used_at` + сессия в одной транзакции. Письмо входа — шаблон `portal_magic_link` через `send_templated_email` (→ `EmailLog`); не больше `PORTAL_MAGIC_LINK_MAX_PER_HOUR` (5) запросов в час на адрес, считаются и неизвестные адреса (429 не должен выдавать наличие контакта). Запрос ссылки гасит только прежние ссылки входа (`purpose=login`), приглашение из ERP (`purpose=invite`, 24 ч) остаётся. Рабочая ссылка входа клиента не попадает в ответы API, журнал и в CRM (handoff отдаёт `CABINET_URL` без токена). Ссылка в письмах входа и приглашения — `{CABINET_URL}/auth/magic#token=<токен>` (FIX-21, `build_login_url`): токен во фрагменте, в пути и query его нет; Cabinet меняет его на сессию через `POST /auth/magic {token}`, `GET /auth/magic/{token}` снят в контракте 0.3.0 (FIX-25): маршрута нет, 404 (обмен: 410 `MAGIC_LINK_EXPIRED`, 403 `FORBIDDEN` для архивной компании; лишнее поле тела — 422). Telegram — только по подписанному `telegram_user_id`; контакты архивных компаний (`Company.is_active=False`) не входят ни одним каналом (403 `FORBIDDEN`); адрес, общий у активных контактов разных компаний, письма не получает.
- **Защита портала (FIX-15).** Лимиты — `portal/throttles.py`: `PortalSessionRateThrottle` (ключ — id сессии, не IP; общий анонимный 20/мин по IP на портал не распространяется), `PortalLoginRateThrottle` (`portal_login`, вход без сессии, по IP) и `PortalAcceptRateThrottle` (`portal_accept`, акцепт КП с кодом); ставки — `REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]` (env `PORTAL_*_RATE`), ответ 429 `TOO_MANY_REQUESTS` + `Retry-After` формирует `portal_exception_handler`. CSRF сессии в cookie — `portal/middleware.py`: на `/api/portal/*` `POST`/`PATCH` без `Idempotency-Key` → 400 `IDEMPOTENCY_KEY_REQUIRED`, тело не `application/json` → 415 (исключение — multipart на `/uploads`); `core.idempotency` отделяет ключи по сессии портала и не повторяет ответы с `Set-Cookie`. Cookie сессии — `PORTAL_COOKIE_SAMESITE` (`Lax` по умолчанию, `None` для Mini App ⇒ всегда `Secure`; значение проверяется при старте). CORS: `*.localhost`/Vite — только при `DEBUG=True`, иначе `CABINET_ORIGIN` (через запятую) + `CORS_ALLOWED_ORIGINS`. Живая сессия валидна, пока компания в обороте (`active_company_q`, общий предикат — `portal/services/access.py`) и контакт остался в компании сессии (`portal/authentication.py`). Письмо ссылки входа выпускает и шлёт задача `portal.send_magic_link` (в брокер уходит только id контакта, токен рождается в задаче). Журнал запросов — `core.logging.AccessLogMiddleware` (logger `core.access`), а не access-лог Daphne: Daphne запущен с `-v 0`, иначе путь `/auth/magic/<токен>` печатается в stdout мимо `RedactPortalTokenFilter`.
- **Ответы портала = контракт (FIX-21).** Форма каждого ответа `/api/portal/v1/*` — ровно `components.schemas` из `packages/contracts/openapi/erp-portal.yaml`: сериализаторы (`portal/serializers.py`) раскладывают по полям то, что считают чистые проекции `portal/projections.py` (статусы ERP → статусы контракта, строки КП из клиентской проекции PDF `client_projection_items`, строки поставки, источник запроса, `DealRef` = `D-<id>`); внутренних полей (ставка НДС, `items`, себестоимость, внутренние id) в ответе нет, данных нет — `null`, а не выдумка. Сторож `portal/tests/test_contract_guard.py` читает `erp-portal.yaml` (контейнер тестов монтирует `packages/contracts` в `/packages/contracts`; нет файла — тест падает, не пропускается), на фикстурах во всех статусах проверяет каждый GET портала JSON Schema, множество ключей ⊆ `properties` и тела ошибок; новый GET в контракте без фикстур сторожа или маршрут без контракта роняют его. Коды `detail` — только из `ErrorCode` (`portal/error_codes.py` сверяется с контрактом тестом; обработчик приводит чужие исключения к коду по статусу и отдаёт ровно `{"detail": CODE}`). Лимиты контракта: `summary` ≤ 5000 (полный текст — `portal.PortalRequestSummary`, `Deal.title` — 255), `Reason` ≤ 2000, загрузка ≤ `PORTAL_UPLOAD_MAX_MB` (10). Новое поле ответа — сначала в контракт, потом в сериализатор и в фикстуры мира (`portal/tests/contract_world.py`).
- **Жизненный цикл в портале — только через сервисы ERP (FIX-22).** Вьюхи портала не пишут статусы и не двигают стадии сделки: КП — `verify_code_and_accept` / `perform_quote_rejection` (`ValueError` → 409), код акцепта — `crm.services.public_page.issue_acceptance_code(quote, ip, contact=…, send=…)` через `portal/services/acceptance.py` (Telegram — только при `PORTAL_ACCEPT_CODE_TELEGRAM` и токене бота, иначе письмо через `EmailLog`; ни того ни другого — 422 `CONTACT_CHANNEL_REQUIRED`; Q-FIX22-1), договор — `sign_contract_by_client(…, portal_contact=)`, акт — `sign_act` / `reject_act(…, portal_contact=)`. Субъект портала — `Contact` своей компании с `can_act`: сервисы проверяют это сами, `client_signer` / `acceptor_signer` остаются пустыми, кто действовал — в `ActivityLog` (`contact_id`, `channel=portal`). - **Гейт на каждом эндпоинте мутации** — `core.permissions.RoleGatedViewMixin` (первым в базах вьюхи) +
  `required_permissions = {"<action или HTTP-метод>": "<код>" | ("<код>", …) | ADMIN_ONLY | SELF_SERVICE | BUYER_ONLY}`.
  Проверка — в `check_permissions` до `get_object()`; отказ — 403 `{"detail": "ROLE_NOT_PERMITTED"}`
  (`ADMIN_ONLY` — `PLATFORM_ADMIN_REQUIRED`); мутация без объявления закрыта. Новый эндпоинт мутации без строки в
  `required_permissions` (или в `OPEN_ENDPOINTS` теста с причиной — вход, 2FA, свои уведомления, публичная страница КП)
  роняет `accounts/tests/test_role_matrix.py`: тест перечисляет все мутации из URLConf и проверяет матрицу
  «нет права → 403, есть право / администратор → не 403, участник компании-клиента → 403».
- Сервисы проверяют **те же коды** через `accounts.services.permissions.member_has_permission` (своя компания —
  `staff_permissions`: объединение ролей; администратор — всё). Выводов из должности OWNER (WorkspaceRole) и флага
  `can_sell` для сотрудников нет; должность при приглашении только подставляет стартовые роли.
- **Покупательских аккаунтов в ERP нет (FIX-13, ORCHESTRATOR §3.1).** Удалены `accounts.services.buyer_access`, маркер
  `BUYER_ONLY` и `buyer_actions` вьюх, `BuyerPermission`, поле `CompanyMember.can_buy` (миграция `accounts/0005`, данные не
  переносятся), покупательские эндпоинты internal (акцепт / отклонение КП, подпись договора и приёмка акта клиентом,
  сборка и отправка заявки, ИИ-помощники заявки) и сервисы заявки `buyer_*`. Мутация не от сотрудника своей компании и
  не от администратора — 403 `ROLE_NOT_PERMITTED` на любом гейте. Вход участнику компании-клиента (и пользователю без
  активного членства в своей компании, кроме `is_superuser`) закрыт: 403 `STAFF_ONLY` до выпуска токенов
  (`accounts.services.auth.assert_staff_login`). Клиент — контакт контрагента с сессией портала; его шаги (подпись
  договора, приёмка акта и поставки, акцепт КП) — только в `/api/portal/v1/*`. Сервисы `sign_contract_by_client`,
  `sign_act` / `reject_act` вызывает портал (FIX-22, `portal_contact=`): изнутри ERP без контакта портала они недостижимы.
- `/me`: `capabilities.permissions` — действующие коды (у администратора — весь каталог), `capabilities.is_solo_team` —
  в команде один сотрудник с `deal.manage` (прячет «Взять в работу»). SPA прячет и блокирует UI только по этим кодам
  (`useHasCompanyPermission`, `buildNavigation`, `buildSettingsSections`).
- «Администратор» в CRM = суперпользователь ERP (все права без ролей); инвариант «≥ 1 администратор» держит CRM, у своей компании ERP нет «Администратора компании» и never-orphan. Одному человеку — несколько ролей, очереди складываются.
- Источник истины по людям и доступам — CRM (ADR-0003): пользователь создаётся провижинингом (`POST /api/integration/v1/users/provision`), вход — SSO-токеном на 60 с с одноразовым `jti` (CONTRACTS §6), отзыв доступа в CRM отзывает сессии ERP. Локальный пароль и 2FA (из B2B) остаются как запасной вход. **Отзыв (FIX-11)** — `DELETE /api/integration/v1/users/{crm_user_id}/sessions` (`integration.services.provision.revoke_crm_user_sessions`): refresh-токены в чёрный список, `CustomUser.token_version` растёт (access-токен несёт версию в claim `tv`; `accounts.authentication.TokenVersionJWTAuthentication`, подключена в `core/settings/auth.py`, отвечает 401 на access с другой версией — прежний отзыв не гасил access до 30 минут и перебирал все сессии Django), `is_active=false` (локальный пароль и его сброс доступ не возвращают), аудит `sso.revoke`; повторный провижининг включает пользователя. Новый код выпуска токена — через `accounts.services.tokens.refresh_for(user)`. Провижининг принимает только коды каталога (`Permission`; чужой код → 422), создаёт членство с должностью `MEMBER`. `/me.capabilities.crm_access` — есть `CrmUserMapping`: только такому сотруднику показана кнопка «В CRM». `CookieTokenRefreshView` не продлевает refresh тому, кто больше не сотрудник (403 `STAFF_ONLY`) и чей доступ отозван (401).
- Права проверяются гейтом эндпоинта и **в сервисах** (`member_has_permission`), фронт только прячет кнопки. Никаких «OWNER»/«Sales Manager» в коде — только коды прав и коды ролей.
- **Своя компания** (компания-владелец, единственный продавец — BUSINESS §3.3) — одна точка истины `core.tenant.own_company()` / `own_company_id()` (с M1-ERP-02 волна 3): настройка `OWN_COMPANY_ID` (окружение; на проде обязательна, если компаний-продавцов с участниками больше одной; проброс в compose — Infra, M5-INF-01), иначе — единственная активная компания-продавец с активными участниками (dev, тесты, свежий стенд; в тестах фикстура создаёт одну такую компанию), несколько без настройки — `ImproperlyConfigured`, ни одной — `None` (действует только администратор). Сотрудник бэк-офиса = активный участник своей компании (`accounts.services.permissions.is_seller`, `sees_all_deals`, `primary_seller_company_id`); видит все сделки и документы, действует по правам роли в своей компании. Продавец КП / счёта без КП / получатели уведомлений о заявке — тоже своя компания.
- Режим «глазами клиента» (ORCHESTRATOR §3.1) — сотрудник смотрит проекцию компании из ERP; это не вход в Cabinet.

**`erp-mcp` (FIX-36, S-12).** Официальный SDK `mcp` (та же версия, что у CRM) в отдельном процессе `python -m integration.mcp` (compose-сервис `erp-mcp`, порт 8104 только внутри сети; `/mcp` снаружи — 404, FIX-03). Код — `integration/mcp/`: `server.py` (`MCPServer`, streamable HTTP, stateless + JSON; `list_tools`/`call_tool` отдают инструменты контракта), `contract.py` (читает `packages/contracts/mcp-tools.json` — имена, описания, режимы и `input_schema` в коде не дублируются; файл монтируется в `/packages/contracts`, нет файла — процесс не стартует), `gate.py` (ASGI-вратарь: контекст на каждом запросе → 401, лимит → 429, `jti` на `tools/call`, аргументы → 400), `tools.py` (только обработчики `HANDLERS`), `context.py`. Новый инструмент = строка в `mcp-tools.json` (контракт раньше кода) + обработчик в `HANDLERS`; расхождение роняет старт и тест. Ошибка инструмента отдаётся кодом (`TOOL_NOT_AVAILABLE_IN_MODE`, `TOOL_EXECUTION_ERROR`, `INTERNAL_ERROR`), текст чужого исключения модели не уходит. Обработчики — синхронный ORM через `sync_to_async`; тесты — `integration/tests/mcp_support.py` (приложение SDK в процессе теста + клиент `mcp.Client`).

Правила: эндпоинты — kebab-case, множественное число; `Idempotency-Key` на всех POST интеграции (ключ хранится 7 дней);
деньги — строка с двумя знаками + ISO-4217; даты — ISO-8601 с зоной; версия — префикс `v1`, несовместимое изменение — новый префикс.
Любое изменение здесь начинается с `packages/contracts` и PR с обеих сторон в одной вехе.
