# Событие шины

Правила — ORCHESTRATOR §3 п. 14 и 16 (интеграции только через шину, один владелец у поля), ADR-0014,
`docs/architecture/CONTRACTS.md` §9 (конверт, типы и файлы, подписки, совместимость), `docs/architecture/rt-bus.md`
(публикация §4, подписки и доставка §5, приёмник §6, разработка §10). Прямой HTTP между доменами — только чтение
публичного API.

## Шаги

1. **Контракт** (скилл `contract-change`):
   - схема `data` — `packages/contracts/events/<домен>/<сущность>.<действие>.v<N>.json` (JSON Schema 2020-12, `$id` повторяет
     путь; общие определения — `_defs.v<N>.json`);
   - пример полного конверта — `events/<домен>/examples/<сущность>.<действие>.v<N>.json`;
   - канал и сообщение в `events/asyncapi.yaml`; подписчик — в `packages/contracts/bus/subscriptions.yaml` (CONTRACTS §9.5);
   - строка в таблице типов CONTRACTS §9.2.
   `make contracts` сравнит схему с `main`: в `vN` — только новые необязательные поля, иначе новый файл `v(N+1)`.
2. **Издатель** — запись в outbox в той же транзакции, что и изменение сущности (rt-bus.md §4). Событие снимка несёт
   сущность целиком, без персональных данных сверх контракта.
3. **Подписчик** — inbox с дедупликацией по id события; обработчик идемпотентен по внешним идентификаторам
   (`crm_client_id`, `erp_company_id`, `erp_deal_id`); снимок заменяет проекцию целиком, поздний снимок со старым `updated_at`
   не применяется; лишние поля терпит (rt-bus.md §6). Чужие данные — только проекции.
4. **Тесты**:
   - откат транзакции издателя — события нет;
   - повторная доставка — один эффект;
   - неизвестное поле в `data` — принимается;
   - для конкурентных сценариев — мутационная проверка (ORCHESTRATOR §4.1).
5. Эксплуатационные заметки домена — `docs/runbooks/rt-bus-crm.md`, `rt-bus-erp.md`; новое поведение — строка в
   соответствующем разделе CONTRACTS.
6. Перед PR — скилл `pre-pr`: `contracts`, `rt-bus` (если трогал библиотеку) и задания издателя и подписчиков.
