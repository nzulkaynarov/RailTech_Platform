# Архитектура Платформы: BFF, вход, сущности, события, развёртывание
Статус: действует · Владелец: архитектор · Обновлено: 2026-10-27

Версия 1.1 · 2026-10-23 · Решение уровня ансамбля — ADR-0011 с поправками ADR-0014 и ADR-0015. Термины — SPEC-v3 §2.

> **Поправки стратегии 2026-10-23 (действуют поверх текста ниже).** (1) Письма, резолюции, служебные записки и маршруты
> согласования (включая одобрение КП) — в отдельном сервисе **EDS** (`apps/eds`, ADR-0015), а не в приложении `eds` внутри ERP.
> (2) События между доменами и в интерфейс — шина **`rt_bus`** (ADR-0014): outbox домена → подписка BFF → SSE в браузер;
> Redis Streams `rt:events` не вводятся. (3) BFF ходит только в публичные версионированные API доменов (этап B5), не во
> внутренние API старых фронтов. (4) Сосуществования со старыми фронтами нет: они удаляются на этапе C2; фазы P2–P6 заменены
> этапами C–E стратегии.

## 1. Схема

```
 сотрудник ── https://platform.railtech.uz ──► Caddy
                                                ├─ /            → platform-web  (статика SPA)
                                                └─ /api/*       → platform-bff  (FastAPI, без своей БД)
                                                                    │ сессия сотрудника в Redis
                                                                    │ токены CRM и ERP сотрудника
                                         внутренняя сеть compose    ▼
                                ┌────────────────────────┬─────────────────────────┐
                                │ crm-api:8000 /api/v1   │ erp-backend:8000 /api/v1 │
                                │ лиды, клиенты, бот, KB, │ заявки, расчёт, КП,     │
                                │ люди и роли (IdP),      │ договоры, счета, акты,  │
                                │ интеграции, внешние     │ склад, каталог, EDS*,   │
                                │ сервисы                 │ чаты сотрудников*       │
                                └───────────┬────────────┴────────────┬────────────┘
                                            │ шов: API, вебхуки, erp-mcp, SSO (CONTRACTS.md)
 клиент ── cabinet.railtech.uz ─► Cabinet SPA ─► ERP /api/portal/v1   (без изменений в архитектуре)
 клиент ── Telegram ─► бот CRM                                         (без изменений)
                                                               * — новые приложения ERP, §4
```

Правила, которые делают схему устойчивой:

1. **BFF не владеет данными.** Нет своей базы, нет бизнес-правил, которые решают «можно или нельзя». BFF
   переводит словарь (старые коды → SPEC-v3 §2), собирает экраны из нескольких источников, держит сессию
   сотрудника и раздаёт события. Решает бэкенд.
2. **BFF действует от имени сотрудника.** Каждый вызов в CRM и ERP идёт с токеном того, кто нажал кнопку. Права,
   журнал «кто и когда», лимиты — в бэкендах, как сейчас. Сервисные токены шва BFF не использует.
3. **Контракт раньше кода.** Публичный API BFF — `packages/contracts/openapi/platform-bff.yaml`; новые сущности и
   эндпоинты бэкендов — в их OpenAPI и `erp-integration.yaml` в том же PR, что и код (инвариант 3 ORCHESTRATOR).
4. **Инварианты ансамбля не меняются**: две базы, общих таблиц нет, CRM — источник истины по людям, «код решает,
   модель предлагает», секреты только в окружении, ИИ через LiteLLM.

## 2. Почему BFF, а не прямые вызовы из SPA

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| SPA ходит в CRM и ERP напрямую (`/api/crm/*`, `/api/erp/*` на одном домене) | нет нового сервиса | два набора токенов в браузере; словарь и 7 шагов считаются в браузере; экраны «Моя очередь», «Все заявки», поиск — по 3–6 запросов из браузера; смена бэкенда ломает SPA | нет |
| **BFF (backend-for-frontend)** | одна сессия-cookie, токены не видны браузеру (паттерн «token handler» из IETF «OAuth 2.0 for Browser-Based Apps»); словарь и маппинг в одном месте; агрегация экранов; бэкенды можно оптимизировать (T5), не трогая SPA | ещё один сервис | **да** |
| Логика Платформы внутри CRM-бэкенда | меньше контейнеров | CRM превращается в «бог-сервис»; ломает разделение фронт-офис / бэк-офис; оптимизация бэкендов (T5) упирается в него | нет |

**Язык BFF — Python 3.12 + FastAPI** (как CRM): прод-VPS умеет только x86-64 v1, а Python-образы ансамбля на нём
проверены; Node-рантайма на проде нет. Конвенции — как в `apps/crm/backend`: uv, ruff, mypy strict, pytest,
httpx, pydantic v2, structlog.

## 3. Вход, сессия, доступ к ERP

```
SPA  POST /api/v1/auth/login {email, password}
 └► BFF → CRM POST /api/v1/auth/login            → access (тело) + refresh (cookie rt_refresh)
        → CRM GET  /api/v1/me                     → id, имя, роль CRM, platform_access, platform_role_refs*
        → CRM POST /api/v1/auth/sso/token {aud: erp}   (если есть доступ к ERP)
        → ERP POST /api/v1/auth/sso/exchange/     → access ERP + refresh ERP (cookie)
        → Redis: session:{sid} = {crm_access, crm_refresh, erp_access, erp_refresh, user, roles, exp}
 ◄─ Set-Cookie: rt_pf_session=<sid>; HttpOnly; Secure; SameSite=Lax; Path=/
    Set-Cookie: rt_pf_csrf=<random>; Secure; SameSite=Lax; Path=/          (double submit)
```

- Браузер видит только `rt_pf_session` (256 бит случайности, httpOnly) и CSRF-cookie. Мутирующие запросы несут
  заголовок `X-CSRF-Token` = значению CSRF-cookie.
- Истёк access CRM или ERP → BFF обновляет его refresh-токеном сам; refresh не прошёл → сессия удаляется, SPA
  получает 401 `SESSION_EXPIRED` и показывает вход.
- Выход: BFF вызывает logout в CRM и ERP и удаляет сессию.
- Отключение сотрудника в CRM: CRM уже гасит его ERP-сессии (`DELETE /users/{crm_user_id}/sessions`); refresh CRM
  перестаёт работать → сессия Платформы умирает на ближайшем обновлении (не позже TTL access, 5–15 мин).
- Сотрудник без доступа к ERP (`platform_access = ["crm"]`): ERP-токенов в сессии нет, модули EDS/ERP скрыты.
- Вход только по логину CRM. Форма входа ERP, страница `/sso/exchange` CRM, переключатель CRM ↔ ERP, ADR-0010
  «вход в ERP через страницу CRM» после T4 не нужны (T5 удаляет).
- `platform_role_refs*` — роли Платформы сотрудника с их матрицами (R-1/R-2, §6); старое поле `platform_roles` (коды) удалено в R-1b.
- **EDS (с W13-A2, `docs/architecture/sso-token.md`, «Токен сотрудника для EDS»).** Не при входе, а при первом обращении к EDS:
  CRM `POST /api/v1/auth/sso/token {"aud": "eds"}` → EDS `POST /api/v1/auth/sso/exchange` → токен доступа EDS (15 минут, без
  refresh) в сессии (`eds`); истёк или EDS ответил 401 — новый обмен. CRM не выдаёт токен (нет `permissions.eds`) или EDS не
  знает сотрудника — 403 `FORBIDDEN` `details.reason = eds_not_granted`; сбой — 503 и пауза 15 с до следующей попытки.
  Отказ EDS сессию Платформы не закрывает. Адрес — `PLATFORM_EDS_URL` (по умолчанию `http://eds-api:8000`, только сеть compose).
  **Входящие письма и резолюция (D1-3, BFF 0.16.0).** Тем же токеном доступа EDS BFF вызывает письма (`/letters`, `/letters/{id}`,
  `…/resolution|return|reject`), реестр для адресации по номеру (`GET /registry?kind=letter_in&number=ВХ-104/26`, EDS адресует письма
  UUID) и файлы (`GET /files/{id}` потоком, ответ отдаётся только вложением). Раздел каталога — `eds.inbox`: чтение даёт список и карточку
  (менеджер, бухгалтер), полный — решения (директор); BFF проверяет раздел до обращения в EDS, право `letters.*` и переходы статусов решает EDS.
  Ошибки EDS переводятся в `Error` с `source = eds` и сохранённым `details.reason` / `details.fields` (`due_in_past`, `not_active_employee`,
  `invalid_state`); `eds_not_granted` — как выше. Данные заявки (название, стадия сделки) приходят из ERP по `erp_deal_id` письма: ERP не
  ответил — карточка 200 с `sources.erp = unavailable`. Поле «Маржа не ниже» (`min_margin_pct`) отдаётся только ролям с группой `cost_margin`.

### 3.1. Первый запуск и временный пароль (W13-A4, BFF 0.10.0)

Пока в CRM нет активного администратора, вход ведёт на экран «Первый запуск» (`/setup`, без сессии):

```
SPA  GET  /api/v1/setup/state                    → BFF → CRM GET /setup/state          {needs_admin}
SPA  POST /api/v1/setup/admin {code, name, email, password}
 └► BFF → лимит входа (IP и e-mail; неверный код расходует попытку)
        → CRM POST /setup/admin {code, email, full_name, password}   → первый администратор (роль ADMIN, ERP — провижининг)
        → CRM POST /auth/logout (refresh, который CRM открыла сама)    → семья токенов не висит
        → обычный вход (CRM login → /me → SSO → ERP exchange → Redis)   → cookie rt_pf_session и rt_pf_csrf
```

- Код первого запуска знает только CRM: она выдаёт его, пока администратора нет, и один раз пишет в журнал `crm-api`
  (`setup_code_issued`); BFF его не хранит и не возвращает. Блокировку перебора (10 неверных кодов — 15 минут) держит CRM,
  BFF добавляет лимит входа.
- Дальше — мастер в Admin (`/admin/setup`, раздел `admin` полный): шаг «своя компания» — ERP `setup/status/` и `setup/company/`
  токеном администратора (ERP выдаёт доступ новому администратору с задержкой провижининга: до тех пор BFF отвечает
  503 `BACKEND_UNAVAILABLE` с `source = erp`, а экран предлагает «Проверить снова»); чек-лист из пяти шагов
  (`GET /setup/checklist`) — бот и модели из CRM `/setup/checklist`, ERP — `/integrations/erp`, почта — `/integrations/smtp`,
  первый сотрудник — `/users` (есть активный сотрудник кроме администратора). Чего бэкенд не сказал, то `unknown`.
- Сотрудник без почты: `POST /admin/users` (CRM `POST /users`) и `POST /admin/users/{id}/temporary-password` (CRM
  `POST /users/{id}/reset-password`) отдают **временный пароль один раз** в теле ответа с `Cache-Control: no-store`.
  CRM хранит только хеш, поэтому повторно получить пароль нельзя — выдают новый, а прежний и сессии сотрудника гаснут.
  BFF не пишет пароль в журнал и ошибки, не кладёт в Redis и сессию; SPA держит его в состоянии одного окна и убирает по «Готово».
  Сотрудник входит с временным паролем (`must_change_password`) и обязан сменить его (`POST /auth/change-password`).

### 3.2. Профиль /me, фото, Telegram сам, замещение и «Забыли пароль?» (W15-H6, BFF 0.21.0)

Профиль — страница `/me` (вход — пункт «Профиль» в меню аватара), а не окно. Поля принадлежат CRM (ADR-0015), BFF
переводит и проксирует токеном самого сотрудника; чужого профиля нет ни в одной операции, кроме чтения фото коллеги.

```
SPA  GET   /api/v1/me/profile        → CRM GET /me + GET /me/covering        {имя, телефон, пояс, подпись, фото, Telegram, замещение}
SPA  PATCH /api/v1/me/profile        → CRM PATCH /me {full_name, phone, language, timezone, email_signature}
SPA  PUT   /api/v1/me/avatar         → CRM PUT /me/avatar   (multipart, поле avatar; BFF проверяет размер и тип части, CRM — содержимое)
SPA  GET   /api/v1/staff/{id}/avatar → CRM GET /staff/{id}/avatar  → картинка потоком, nosniff, Cache-Control: private
SPA  POST  /api/v1/me/telegram-link  → CRM POST /me/telegram-link  → {url: t.me/<бот>?start=staff_<код>, expires_at}
SPA  PUT   /api/v1/me/deputy         → CRM PUT /me/deputy {deputy_user_id, date_from, date_to}
```

- **Фото.** Клиент режет круг 256×256 (PNG) сам; в CRM — S3 бакета файлов CRM под `staff-avatars/<id>/`, до 1 МБ, тип проверяется по
  содержимому. Ссылок на S3 в ответах нет: `Me.avatar_url` и `Profile.avatar_url` — адреса BFF `/api/v1/staff/{id}/avatar?v=<версия>`;
  версия меняет кэш браузера при замене. Рейл и меню аватара показывают фото вместо инициалов. Версия лежит в снимке сессии.
- **Привязка Telegram.** Код одноразовый, короткоживущий (10 минут), в БД CRM — хеш; клиентский бот один, поэтому код сотрудника — `/start staff_<код>`,
  клиентские deep-link'и и `/start` без аргумента идут прежним путём. Хранение то же, что при привязке админом (`users.tg_user_id`),
  плюс ник для «Привязан как @…». Числовой id Telegram наружу не отдаётся. Пока окно со ссылкой и QR открыто, SPA опрашивает
  `GET /me/profile` раз в 3 с и закрывает окно, когда бот подтвердил привязку.
- **Замещение.** Одно на сотрудника: заместитель и период (даты включительно, по календарю замещаемого, не в прошлом, ≤ 366 дней).
  Заместитель — активный сотрудник с рабочей ролью CRM. BFF добавляет к «Моей очереди» заместителя строки замещаемого
  (`QueueItem.on_behalf_of`, «за {имя}»): `GET /me/covering` и `GET /inbox?on_behalf_of=<id>` CRM — только пока период идёт и только
  назначенному заместителю (иначе 403 `not_a_deputy`). Права на сами объекты — свои, BFF их не расширяет. Берутся только личные дела
  замещаемого (его «мои» лиды с новым сообщением, передачи, которые взял он); общие списки заместитель видит и так. Счётчики карточек
  и бейдж «Клиенты» считают только свою работу, бейдж «Мои задачи» — всю очередь. **Разрыв:** очередь EDS и ERP (одобрение КП, резолюции)
  замещающему не переносится — ERP отдаёт `my-approval-queue` по токену пользователя, EDS своей очереди не ведёт; нужна операция
  «очередь за коллегу по замещению» в ERP и EDS (`docs/QUESTIONS.md`).
- **«Забыли пароль?».** `POST /auth/forgot-password` без сессии: ответ 202 один для любой учётной записи (перечислять сотрудников нельзя),
  лимит BFF — 5 запросов в час на IP и на адрес (429 `TOO_MANY_REQUESTS`), в CRM — три ссылки в час на учётную запись. CRM шлёт ссылку на
  Платформу (`PLATFORM_PUBLIC_URL`, `<адрес>/reset-password?token=…`) по почте (если коннектор «Почта» настроен), иначе в Telegram (если привязан);
  нет ни того, ни другого — ссылки нет, а экран входа заранее говорит «обратитесь к администратору». `POST /auth/reset-password` — новый
  пароль по одноразовой ссылке (час): токен гасится вместе с остальными, сессии сотрудника закрываются, вход — с новым паролем.
  После успеха CRM закрывает все сессии сотрудника сразу (`password_changed_at`: выпущенные раньше access-токены не принимаются; профиль в BFF перечитывается раз в минуту). Экран `/reset-password` убирает токен из адреса и просит браузер не слать Referer. Загрузка фото читается потоком с отсечкой (413 `PAYLOAD_TOO_LARGE`), в Caddy — `request_body max_size`. Неверная, использованная или просроченная ссылка — 422 `VALIDATION_FAILED` с `details.reason = reset_token_invalid`.

### 3.3. Мост в старые экраны (W15-H1, BFF 0.19.0)

Пока раздел Платформы — заглушка, сотрудник не упирается в «пока нет»: `SectionStubPage` говорит, где эта работа делается
сейчас, и даёт кнопку «Открыть в старой CRM / старом ERP» в новую вкладку (`target=_blank`, `rel=noopener`). Карта «раздел
Платформы → старая система и путь в ней → когда появится» — `apps/platform/web/src/modules/bridge.ts`; запись есть, пока раздел
заглушка (волна 16 удаляет записи по мере появления настоящих экранов). Разделы без аналога в старых фронтах говорят честно:
«Сейчас этой работы в интерфейсе нет; её делает …», а «Когда появится» — словами («в ближайшем обновлении» — разделы волны 16,
«к пилоту» — остальное).

```
SPA  GET  /api/v1/bridge            → {crm_url, erp_url, erp_sso}      публичные адреса старых фронтов
SPA  POST /api/v1/bridge/erp-sso    → BFF → CRM POST /auth/sso/token   {url: "{ERP}/sso/exchange#token=…"}
```

- **Адреса без правки `.env`.** `PLATFORM_CRM_PUBLIC_URL` и `PLATFORM_ERP_PUBLIC_URL` (необязательны, не секреты); пусто —
  адрес выводится из адреса, по которому открыта Платформа: `platform.<домен>[:порт]` → `crm.<домен>[:порт]`, `erp.<домен>[:порт]`
  (стенд — `*.localhost:8088`, прод — `crm.railtech.uz`, `erp.railtech.uz`, как в `.env.prod.example`). Хост берётся из `Host`,
  схема — из `X-Forwarded-Proto` только от доверенного прокси (`PLATFORM_TRUSTED_PROXIES`), хост проверяется строгим шаблоном.
  Не задан и не выводится (Платформа открыта не на `platform.*`) — `null`: кнопки нет, текст остаётся честным.
- **Вход в старый ERP — тот же SSO, что у кнопки «Перейти в ERP» старой CRM** (`docs/architecture/sso-token.md`): CRM выдаёт
  токен на 60 секунд токеном сотрудника, адрес обмена берёт сама CRM (`ERP_FRONTEND_URL`). Клик по кнопке открывает пустую
  вкладку, берёт адрес и ведёт вкладку на него; не вышло (CRM отказала, всплывающие окна закрыты) — вкладка получает обычную
  ссылку `{ERP}/#<раздел>`, а старый ERP сам попросит войти тем же логином. После обмена старый ERP открывает главную
  страницу (его `SsoExchangePage` не сохраняет хэш-маршрут), поэтому под кнопкой написан путь в его меню.
- **Старая CRM — отдельный вход.** Обмена SSO в CRM нет (CRM — источник входа), поэтому под кнопкой стоит «Вход в старую CRM —
  теми же логином и паролем».
- Токен в журнал BFF и в ответы об ошибках не попадает; ответ `no-store`; доступ — любому сотруднику с сессией и разделами
  (права на экраны проверяют старые системы).

### 3.4. Расчёт по заявке (D2-1, BFF 0.24.0)

Экраны «Заявки в расчёте», «Мои расчёты» и «Расчёт по заявке ЗВ-…» (SPEC-v3 §7.4) — тег `calc`, `/erp/calc*`, поверх ERP
`/api/v1/calc/*` (`crm.services.calculation`). BFF не решает: зону строки, визы, «Расчёт готов» и права решает ERP.

- **Разделы.** Чтение — `erp.calc` (список, расчёт, каталог); начать расчёт, «Расчёт готов», ИИ-разбор — `erp.calc` полный;
  правка, удаление и виза строки — `erp.calc.goods` или `erp.calc.services` полный (строку без карточки BFF проверяет по её
  типу до ERP). Решает ERP правами `quote.visa_goods` и `quote.visa_services` (ADR-0012 п. 6; CRM выдаёт их из этих разделов):
  товар правит и визирует снабженец, услугу — гл. инженер (ставка бригады × дни = закупка услуги), отказ — 403
  `details.reason = zone_not_permitted`. Кто визирует — факт визы (`visa.by`): операции «сотрудники по разделу» в CRM нет (B-007).
- **Номер ЗВ.** До ERP-09 (B-010) номер составляет BFF (`feeds/numbers.deal_number`); заявку по номеру BFF находит в лёгком
  справочнике ERP `GET /calc/deals/` (id, создана, стадия — без строк и виз, с новых), `id` из номера не разбирается (B-075).
- **Поля с ограничением** (решение архитектора по Q-D2-1-2 и Q-D2-1-4; режет сам ERP и так же BFF). Закупку и себестоимость
  строки (у услуги — ставку и дни бригады) видит `cost_margin` или держатель зоны этой строки; цены поставщиков —
  `supplier_prices` или держатель зоны товаров; наценку, итоги себестоимости и наценки и порог маржи — только `cost_margin`.
  Бухгалтер (`totals_only`, без `supplier_prices`) — цены клиенту, итоги и НДС. Закупку товара без `cost_margin` и без зоны
  товаров BFF не принимает (422 `cost_forbidden`).
- **Виза** привязана к версии строки (`QuoteItem.version`): правка через любой путь, в том числе старый `crm/quote-items`,
  визу снимает; при возврате КП директором визы неизменённых строк остаются (Q-D2-1-3).
- **«Расчёт готов».** Только на стадии расчёта и когда завизированы все строки (ERP — 409 `DEAL_NOT_IN_CALCULATION`,
  `VISAS_MISSING` с `details.missing`; экран заранее получает `ready.blocker = not_in_calculation`); КП уходит директору
  в EDS тем же событием `quote.ready_for_approval`, что после виз КП, но `required_zones` — зоны строк, `visas` — подписи строк.
- **Резолюция в «Задании»** — проекция события EDS в ERP (`CalcTask`): у снабженца и гл. инженера нет раздела `eds.inbox`, письмо
  EDS им не читается. Чат проекта — ссылкой-подсказкой до волны 18 (B-019).
- **ИИ-разбор** — задание в очереди ИИ ERP (модель через шлюз по алиасу), итог — предложение строк; пишет строки только
  `POST …/lines` после выбора сотрудника. Выключенный ИИ — 409 `ai_disabled`.

## 5. События и реальное время

- **Опрос — запасной путь.** TanStack Query обновляет «Мою очередь», счётчики меню и колокольчик раз в 30 с и при
  возврате на вкладку; открытый чат — раз в 3 с.
- **Поток подсказок (B5, волна 11, ADR-0014).** BFF — подписчик шины `rt_bus` (строка `platform-bff` в
  `packages/contracts/bus/subscriptions.yaml`: события ERP, лидов CRM, сотрудников; приёмник `POST /bus/v1/events` на
  `rt_bus.fastapi.bus_router` + `MemoryReceiver`, без базы; секреты пар `RT_BUS_SECRET_ERP_PLATFORM_BFF`,
  `RT_BUS_SECRET_CRM_PLATFORM_BFF`, с волны 12 `RT_BUS_SECRET_EDS_PLATFORM_BFF` — события EDS подписаны, но до этапа D
  подсказок не дают, приёмник отвечает `skipped`; Caddy `/bus/*` на домене Платформы не отдаёт). Событие превращается в подсказку
  `{"topics": ["notifications"|"counters"|"queue"|"activity"|"messages"], "reason": "<тип события>"}` и уходит в браузер по
  `GET /api/v1/events/stream` (SSE, только вошедшему сотруднику с разделом «Моя очередь»). **В потоке нет данных**:
  браузер перезапрашивает обычные API (с RBAC), поэтому чужое в поток не попадает. Устройство:
  - обработчик приёмника публикует подсказку в канал Redis `platform:hints`; каждый процесс BFF (`--workers 2`) слушает
    канал и раздаёт подсказку своим соединениям; сбой Redis → 503, издатель повторит доставку по расписанию шины;
  - всплеск событий сливается в один кадр (окно 300 мс, `PLATFORM_EVENTS_COALESCE_MS`), в тишине — комментарий
    `: ping` каждые 20 с (`PLATFORM_EVENTS_HEARTBEAT_SECONDS`); при heartbeat BFF проверяет сессию и закрывает поток
    после выхода или по сроку сессии;
  - перед кадром BFF сбрасывает кэш ответов бэкендов сессии (`feed:<sid>:data:*`, 8 с), чтобы перезапрос увидел новое;
  - `Last-Event-ID` нет: слушатель, потерявший Redis, после возврата шлёт подсказку `resync` (все темы), а SPA после
    переподключения потока делает один полный перезапрос;
  - события не несут адресата, поэтому подсказка идёт всем открытым потокам; адресная рассылка — когда в событиях
    появится ответственный (хвост).
  SPA: `EventSource` с переподключением (1, 2, 4, 8, 16, 30 с) в каркасе; пока поток жив, опрос — раз в 5 минут
  (страховка), при обрыве — прежние 30 с.
  Диагностика, если колокольчик, счётчики или очередь «не живут»: (1) вкладка «Сеть» браузера — запрос
  `events/stream` открыт, приходят кадры `: ping`; нет — смотрите Caddy (`flush_interval -1`, `no-transform`) и 401;
  (2) логи `platform-bff`: `POST /bus/v1/events` — 200 (401 — не совпал секрет пары `RT_BUS_SECRET_<ИЗДАТЕЛЬ>_PLATFORM_BFF`
  у издателя и BFF; 503 — Redis); (3) журнал издателя (`rt_bus_delivered`, DLQ) — доставка до BFF; (4) опрос работает
  всегда: при обрыве потока данные догоняются за 30 с.
- **Тема `messages` (D1-1, BFF 0.22.0) — «Клиенты · Ждут ответа» без опроса.** CRM публикует
  `uz.railtech.crm.lead.message_added.v1` на каждое сообщение переписки (входящее и исходящее; сигнал без текста, outbox в той же
  транзакции, что и строка сообщения) и `lead.updated` с `changed_fields = ["handoff"]` на новую передачу от бота. Темы: ERP —
  `notifications`, `counters`, `queue`, `activity`; события лида — `counters`, `queue`, `activity`, `messages`;
  `lead.message_added` — `counters`, `queue`, `messages`, если лид не у бота (`handoff = true`), и только `messages` для диалога
  с ботом (лента «Сегодня» от сообщения не меняется). SPA на `messages`
  перезапрашивает `listCrmMessages` и открытую переписку (`/crm/messages/{lead}`, `/thread`), на `counters` — бейдж «Ждут ответа»
  в меню (`getMenuCounters` → CRM `/inbox`). Путь сообщения клиента до экрана: бот пишет сообщение и строку outbox одной
  транзакцией → после коммита `wakeup` ставит `rt_bus.pump` (без ожидания тика 5 с) → доставка `POST /bus/v1/events` в BFF →
  Redis `platform:hints` → кадр SSE после окна слияния 300 мс → перезапрос ленты. Замер в тестах: запись сообщения и события в
  CRM — одна транзакция (`tests/integration/test_d1_messages.py`); приём события BFF → кадр SSE ≈ 0,4 с с боевым окном 300 мс
  (`tests/test_crm_messages.py`); цель «сообщение клиента в Платформе ≤ 2 с» сквозь стенд проверяет гейт D1-7.
- **Telegram сотруднику** (SPEC-v3 §9): по-прежнему бот CRM. ERP-события, которые должны дойти сотруднику в
  Telegram, идут в CRM существующим вебхуком шва; адресата и настройку «дублировать в Telegram» CRM берёт из
  карточки сотрудника.
- Шов CRM ↔ ERP (`erp-mcp`, SSO) не меняется; события CRM ↔ ERP идут по шине `rt_bus` (ADR-0014).
  CRM SSE `/api/v1/stream` BFF не использует: подписчик шины получает те же изменения лидов.

## 6. Роли и права

> **ADR-0012 (2026-10-22):** роли — данные. Фиксированы только «Администратор» и «Директор»; остальные роли создаёт
> администратор (название и матрица по каталогу разделов), шесть ролей SPEC-v3 становятся предустановками. Права в CRM и ERP
> вычисляются из матрицы роли по каталогу `platform-rbac.yaml`. Текст ниже описывает реализацию фазы P1 до этого ADR.

Шесть ролей SPEC-v3 §4: `MANAGER`, `DIRECTOR`, `SUPPLY`, `ENGINEER`, `ACCOUNTANT`, `ADMIN`; у сотрудника их может
быть несколько.

| Уровень | Что проверяет | Где |
|---|---|---|
| Бэкенд (решающий) | право на операцию и на поле (себестоимость, маржа, цены поставщиков) | CRM casbin, ERP `Permission` (22 кода) — как сейчас |
| BFF | доступ к маршруту и модулю по матрице SPEC-v3 §4.2; удаление полей с ограничением из ответа | `bff/app/rbac.py`, матрица в одном файле, тест на каждую ячейку |
| SPA | видимость модулей, пунктов меню, кнопок; `<Restricted>` для полей | `web/src/app/rbac.ts` из того же файла матрицы (генерируется) |

Выдача ролей — одна карточка сотрудника в Admin · Оргструктура (полный набор `platform_role_ids` в CRM; провижининг ERP
делает CRM). Каталог разделов, шаблонов и системных ролей — один YAML (`packages/contracts/platform-rbac.yaml` v2); генерация
в CRM, BFF и SPA из него.

**С R-2 (BFF 0.3.0, каталог v2):** роли — данные CRM. BFF читает в `/me` CRM роли сотрудника с их матрицами
(`platform_role_refs[].access`, `restricted_fields`; у системных — матрица каталога, Q-R2-1) и считает доступ
объединением матриц, «вид» — по активной роли (id); «Моя очередь» — по секции `queue` каталога; CRM не вызывается
по разделам, которых у ролей нет (источник `not_applicable`). Выдача ролей — полный набор `platform_role_ids` в CRM,
права CRM и ERP вычисляет CRM. Admin · Ролевая матрица — редактор ролей поверх `/admin/roles*` BFF
(→ `/api/v1/platform-roles*` CRM). Генераторы каталога: CRM (`gen_platform_roles.py`), BFF и SPA (`scripts/gen_rbac.py`).

**С R-1b (BFF 0.4.0, CRM API 0.2.0):** директор — `crm.leads` и `chats.external` только чтение (уточнение ADR-0012 п. 2);
чтение ролей — CRM `GET /platform-roles*` по `users:read`, BFF `GET /admin/roles*` по `admin: read` (директор видит матрицу
только для просмотра), изменения — `admin: full`; у роли поле `version`, `PATCH` требует `version`, расхождение — 409
`role_version_conflict` (BFF — 409 `CONFLICT`, `details.reason`); вкладки «Журнал» у роли не было (вернулась в W13-A6, ниже). Права CRM
сотрудника с ролями Платформы — только политики его ролей `pr:<id>`.

**С R-1c (BFF 0.6.0, CRM API 0.3.0, решение R3-D-2):** системная «Администратор» получает в CRM права своей матрицы каталога
(раздел `admin` и др.), а не `admin` CRM (`*:*`): лиды, клиенты, сделки и их выгрузка — 403, администрирование — 200;
бизнес-данные — второй ролью. У сотрудника хотя бы одна роль: пустой `role_ids` — 422 `ROLES_REQUIRED` (CRM — 422
`roles_required`), закрыть доступ — `is_active = false`.

**W13-A6 (BFF 0.12.0): сброс пароля, журнал аудита и профиль.** Чисто добавляющее изменение; новых бизнес-решений в BFF нет.
(1) `POST /admin/users/{id}/reset-password/email` → CRM `/users/{id}/reset-password/email` (`admin: full`): новый временный пароль,
письмо через коннектор «Почта», сессии сотрудника гаснут, статус «Приглашён». Себе сбросить нельзя: BFF отвечает 409 `CONFLICT`
(`details.reason = self_reset`) и в CRM не идёт (CRM этого запрета не знает — см. Q-W13A6-1); почта не подключена — 409
`NOT_CONFIGURED`. Выдача пароля без почты — `POST /admin/users/{id}/temporary-password` (W13-A4): в карточке это второй способ той же кнопки «Сбросить пароль». (2) `GET /admin/audit` →
CRM `/audit` (`audit:read`; BFF — раздел `admin` от чтения: читают администратор и директор, записи не меняет никто): фильтры автор,
действие (код или префикс), объект, период; входы (`auth.login`, `sso.exchange`) скрыты, пока не задан `include_logins`. Коды действий
и объектов остаются кодами CRM — слова к ним даёт SPA (ru/uz/en); значения секретных полей в `before`/`after` BFF заменяет на `***` целиком, любого типа. Имя нормализуется (регистр,
разделители, camelCase). Подстрокой (в том числе в склейках `accesstoken`, `newpassword`, `passwordhash`): password, passwd, secret, token,
credential, authorization, passphrase, passcode, cookie, bearer, signature, hmac, apikey, privatekey, databaseurl; целым словом с отрезанием
хвостовых цифр (`key1`): key, pin, pwd, otp, cvv, jwt, dsn. Исключения явные: имена-коды `service_key`, `product_key`, `settings_key`,
`setting_key`, `section_key`, `agent_context_key` видны всегда; признаки и метаданные (`*_set`, `*_configured`, `*_present`, `*_rotated`,
`*_missing`, `*_changed`, `*_tokens`, `must_change_password`, `has_password`) видны только как флаг, число или `null` (строка — маска);
`*_last4` — только строка до 4 символов. Пустое значение (`null`, `""`) не скрывается. Номера сотрудника, роли и автора журнала в адресе — без ведущих нулей (`^[1-9][0-9]*$`), «это я» сравнивается числом; журнал несуществующей роли — 404. Экран — пункт «Журнал аудита» меню Admin (раздел `admin`, пункт каталога `menu.admin.audit`).
(3) `GET /admin/roles/{id}/journal` — записи аудита CRM `platform_role.create|update|delete` этой роли (CRM пишет их в той же
транзакции, что и изменение, с `before`/`after`); сравнение «что изменилось» делает экран. Смена набора ролей сотрудника
пишется CRM как `user.update` (`platform_role_names`) и видна в общем журнале. Вкладка «Журнал» вернулась в боковое окно роли.
(4) `GET/PATCH /me/notification-settings` и `POST /me/test-notification` — личные уведомления бота (CRM `/me`): доступны каждому
вошедшему, это его собственные настройки; идентификатор Telegram наружу не отдаётся (только «привязан»).

**D1-1 (BFF 0.22.0): Клиенты · Ждут ответа.** `/crm/messages*` — прокси к CRM с токеном сотрудника: очередь (`/inbox` с
запиской передачи CRM-06), карточка лида, лента (`/leads/{id}/messages` с `before_id`, заметки, имена `/team`), вложение потоком
(`Content-Disposition: attachment`, `nosniff`, ключ хранилища наружу не уходит), «Забрать», ответ «От себя» с ключом повтора
`client_message_id`: CRM занимает ключ до отправки (строка `meta.delivery = sending` под advisory-блокировкой на лид и
ключ), поэтому и параллельный повтор не шлёт второе сообщение — пока первый идёт, 409 `CONFLICT` `reply_in_progress`; Telegram
ждём 20 с (меньше таймаута BFF 30 с). Итоги: отказ Telegram — ключ свободен, 502 `INTEGRATION_FAILED` `delivery_failed`;
Telegram не ответил вовремя — 502 `INTEGRATION_FAILED` `delivery_unknown` («Доставка не подтверждена», «Повторить» тем же ключом
не дублирует; правка текста — новый ключ, экран предупреждает, что уйдёт новым сообщением); итог так и не узнали (дольше
2 минут) — 409 `delivery_unconfirmed`, второе сообщение не уходит. В ленте `ThreadMessage.delivery`: `sending` — «Отправляется…»,
`unconfirmed` (CRM пометила или `sending` старше тех же 2 минут) — «Доставка не подтверждена — проверьте у клиента» (B-013).
«Лид отвечен» (`last_human_msg_at`) CRM ставит только при доставке этим запросом — не при отказе и не при возврате уже
доставленного ответа, «Заметка команде», «Подсказать ответ» (ИИ — только CRM/LiteLLM, таймаут пробы), «Вернуть боту»; шаблоны —
`GET /crm/reply-templates`. Раздел `crm.leads`: чтение — `read` (директор видит очередь без действий; CRM `/inbox` с D1-1 —
`leads:read`), действия и шаблоны — `full`. Служебные пометки причины CRM (`dialog: …`) и неизвестные коды экрану не отдаются.

**W13-A3 (BFF 0.8.0): Admin · Компания.** `/admin/company*` проксирует к ERP настройки своей компании (реквизиты и логотип, бланк и бренд,
нумерация, условия КП, статьи расхода, шаблоны документов и писем, справочники, категории и запросы на них, НДС). Раздел
каталога — `company.settings` (чтение — `GET` и предпросмотры, полный — изменения); право на операцию решает ERP (`settings.edit`,
`settings.charge_templates`; запросы на категории и ставка НДС — тоже `settings.edit` или суперпользователь). Id своей компании BFF берёт из
`own_company_id` в `setup/status/` ERP (старая ERP без поля — основное членство), нет компании — 409 `COMPANY_NOT_SET`. Логотипы
BFF отдаёт сам (`/admin/company/logo/image`, `/admin/company/brand/logo/image`): CSP Платформы адреса ERP не пускает.
Загрузка логотипа — `multipart/form-data` целиком, BFF содержимое не разбирает, а проверяет размер (до 2 МБ) и тип части `logo` по её заголовкам (PNG, JPEG, WebP, SVG); содержимое проверяет ERP. Поля маржи условий КП — группа `cost_margin`
(вырезаются и не принимаются без права). Ошибки ERP: 400 → 422 `VALIDATION_FAILED` (`details.reason`, `details.fields`),
«используется»/«уже рассмотрен»/«префикс занят» → 409 `CONFLICT`. Разрывы в ERP — `docs/QUESTIONS.md`, Q-W13A3-1.

## 8. Наблюдаемость и устойчивость

- `X-Request-Id` от Caddy проходит BFF и уходит в CRM и ERP; логи всех трёх связываются по нему.
- **Адрес клиента (волна 11b, T5).** Caddy (`reverse_proxy`) сам ставит `X-Forwarded-For` и не верит такому заголовку от
  клиента. BFF берёт адрес из заголовка только от доверенного прокси: идёт справа налево по цепочке, пока адрес входит в
  `PLATFORM_TRUSTED_PROXIES` (CIDR или адреса через запятую; по умолчанию loopback и частные сети — сеть compose, наружу
  BFF не публикуется); первый адрес вне списка — клиент. Если сокет-партнёр не доверенный (в обход Caddy), заголовок
  игнорируется и берётся адрес сокета; нечитаемые элементы цепочки отбрасываются. Опечатка в списке — ошибка при старте.
  Адрес идёт в лимит входа, в каждую запись журнала BFF (поле `client_ip` рядом с `request_id`; события входа:
  `login_failed`, `login_not_completed`, `login_rate_limited`, `login_succeeded` — e-mail только короткий хеш) и в CRM
  в `X-Forwarded-For` при входе (CRM видит BFF, аудит входа ведёт по заголовку).
- **Лимит входа (O-1).** 10 **неудачных** попыток в минуту отдельно на IP и на e-mail (`PLATFORM_LOGIN_RATE_PER_MINUTE`).
  Попытка записывается в Redis до обращения к CRM (параллельные запросы лимит не обходят) и возвращается, если вход не
  провалился из-за учётных данных: успешный вход (офис за одним NAT), нет ролей Платформы, сбой CRM. Считаются
  `INVALID_CREDENTIALS` и `ACCOUNT_LOCKED`. Успешный вход сбрасывает счётчик e-mail; счётчик IP хранит неудачи других
  пользователей этого адреса. Сверх порога — 429 `TOO_MANY_REQUESTS` с `Retry-After`, в CRM попытка не уходит.
  Тот же лимит (те же счётчики IP и e-mail) действует на `POST /setup/admin` (W13-A4): считаются отказы `SETUP_CODE_INVALID` и
  `SETUP_LOCKED` (перебор кода); `SETUP_CODE_EXPIRED`, `SETUP_DONE`, слабый пароль (`VALIDATION_FAILED`) и сбой CRM попытку возвращают.
  Успешное создание администратора сбрасывает счётчик e-mail. Сверх лимита — 429 `TOO_MANY_REQUESTS`; блокировку кода на 15 минут
  (10 неверных кодов) держит CRM — `SETUP_LOCKED`, 429 с `Retry-After: 900`.
- **Таймаут CRM.** Клиент CRM в BFF ждёт `PLATFORM_CRM_TIMEOUT_SECONDS` (по умолчанию 5 с; было 3 — под нагрузкой вход
  давал 503, runbook r3 O-1; отдельного таймаута для входа нет). Клиент ERP, Redis и проверка health — по-прежнему 3 с.
- **Пробы внешних сервисов (W13-A1).** «Проверить связь» ERP, SMTP и Telegram, сопряжение, ротация ключей, проверка модели и журнал
  расходов LiteLLM идут через CRM дольше обычного вызова: клиент CRM ждёт до 30 с (`PROBE_TIMEOUT_SECONDS`), а 502 CRM («сервис
  за мной не ответил») возвращается как есть и переводится в `INTEGRATION_FAILED` (502) с причиной в `details.reason` — это итог
  проверки, а не сбой CRM (тот остаётся 503 `BACKEND_UNAVAILABLE`). Секреты (токен бота, ключи моделей, пароль SMTP, код
  сопряжения, пароль администратора) BFF только передаёт: они — `SecretStr` в телах запросов, в ответах и журнале их нет, в ответах
  — маски `*_last4`.
- **База знаний и настройки бота (W13-A5, 0.11.0).** `/crm/kb/*`, `/crm/sandbox/*`, `/admin/bot/*` — прокси к CRM с токеном сотрудника; раздел каталога
  проверяет `require_any` / `require_all` (чтение базы знаний — `crm.leads` или `admin`, правка и песочница — `admin: full`, выгрузка — `admin: full` и чтение
  данных). Загрузка файла: BFF читает тело потоком до предела (25 МБ и поля формы), multipart **не разбирает** и передаёт CRM как есть с границей из
  `Content-Type`. Выгрузка CSV: ответ CRM читается кусками (`aiter_raw`) и сразу уходит браузеру, файл в памяти BFF не накапливается, ответ CRM закрывается
  в фоне; ошибка CRM до первого байта — обычный `Error`. Песочница, поиск и пробный прогон ждут CRM как пробы (до 30 с). Ошибки формата документа, размера файла и пути
  невалидных полей настроек доходят в `details` (`reason`, `rule`, `messages`, `max_bytes`, `paths`); значения настроек и схемы форм BFF не знает и не разбирает.
- **EDS · Создать документ и «Мои документы» (D1-5, 0.17.0).** `/eds/documents*`, `/eds/document-files*`, `/eds/deal-options` — прокси к EDS с токеном доступа EDS
  (обмен `aud=eds`); раздел `eds.memo.create` для создания, любой раздел EDS — для чтения, реестр «Все» — чтение `eds.inbox`, `eds.projects` или `eds.payments`.
  Создание с `submit` — два вызова EDS (`POST /documents`, `POST …/submit`): если отправка отклонена, ошибка называет сохранённый черновик
  (`details.document_id`, `saved`). Ошибки EDS переводятся в `Error` с `source = eds` (текст EDS сохраняется; 422 — `details.fields`, `messages`).
  Загрузка файла — как W13-A5 (поток до 25 МБ и поля формы, multipart не разбирается; сверх предела — 413), скачивание — потоком как `attachment`.
- Агрегирующие эндпоинты BFF ходят в источники параллельно с таймаутом 3 с и отдают частичный результат с
  флагом `sources: {crm: ok, erp: unavailable}`; SPA показывает плашку «ERP не отвечает, данные неполные»,
  а не пустой экран.
- `GET /api/v1/health` BFF проверяет Redis, CRM `/health`, ERP `/health`; карточка «Платформа» в Admin ·
  Внешние интеграции (реестр внешних сервисов CRM, ADR-0024 CRM).
- «Требует внимания» (`GET /admin/integrations`, BFF 0.22.0, W15-H3): одна причина — одна строка. Группы по корню, состояние
  словом, «кто исправляет» и действие решает CRM (`external_cause`, поле `groups` ответа реестра); BFF их не оценивает, а
  только добавляет `fix_card` (карточка, где действие выполняется) и убирает дубли других источников: роли моделей
  провайдера, у которого есть общая строка («ключ отклонён»), компоненты «Состояния системы» про тот же сервис
  (бот, бэкап, шлюз, хранилище, `model:*`, сводка «Внешние сервисы»), «бот не запущен», «ещё не подключено» ERP. «Ожидаемо на
  стенде» в список не попадает; сырой текст — отдельным полем `technical`/`group.technical`, интерфейс показывает его
  только свёрнутым.
- Ошибки бэкендов BFF переводит в один формат `{code, message, details, source}` с текстом на языке сотрудника;
  коды ошибок бэкендов сохраняются в `details` для разбора.
