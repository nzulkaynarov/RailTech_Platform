# Архитектура Платформы: BFF, вход, сущности, события, развёртывание
Статус: действует · Владелец: архитектор · Обновлено: 2026-10-23

Версия 1.1 · 2026-10-23 · Решение уровня ансамбля — ADR-0011 с поправками ADR-0014 и ADR-0015. Термины — SPEC-v3 §2.

> **Поправки стратегии 2026-10-23 (действуют поверх текста ниже).** (1) Письма, резолюции, служебные записки и маршруты
> согласования (включая одобрение КП) — в отдельном сервисе **EDS** (`apps/eds`, ADR-0015), а не в приложении `eds` внутри ERP.
> (2) События между доменами и в интерфейс — шина **`rt_bus`** (ADR-0014): outbox домена → подписка BFF → SSE в браузер;
> Redis Streams `rt:events` не вводятся. (3) BFF ходит только в публичные версионированные API доменов (этап B5), не во
> внутренние API старых фронтов. (4) Сосуществования со старыми фронтами нет: они удаляются на этапе C2; фазы P2–P6 заменены
> этапами C–E стратегии.

## 1. Схема

```
 сотрудник ── https://platform.railtech.uz ──► Caddy
                                                ├─ /            → platform-web  (статика SPA)
                                                └─ /api/*       → platform-bff  (FastAPI, без своей БД)
                                                                    │ сессия сотрудника в Redis
                                                                    │ токены CRM и ERP сотрудника
                                         внутренняя сеть compose    ▼
                                ┌────────────────────────┬─────────────────────────┐
                                │ crm-api:8000 /api/v1   │ erp-backend:8000 /api/v1 │
                                │ лиды, клиенты, бот, KB, │ заявки, расчёт, КП,     │
                                │ люди и роли (IdP),      │ договоры, счета, акты,  │
                                │ интеграции, внешние     │ склад, каталог, EDS*,   │
                                │ сервисы                 │ чаты сотрудников*       │
                                └───────────┬────────────┴────────────┬────────────┘
                                            │ шов: API, вебхуки, erp-mcp, SSO (CONTRACTS.md)
 клиент ── cabinet.railtech.uz ─► Cabinet SPA ─► ERP /api/portal/v1   (без изменений в архитектуре)
 клиент ── Telegram ─► бот CRM                                         (без изменений)
                                                               * — новые приложения ERP, §4
```

Правила, которые делают схему устойчивой:

1. **BFF не владеет данными.** Нет своей базы, нет бизнес-правил, которые решают «можно или нельзя». BFF
   переводит словарь (старые коды → SPEC-v3 §2), собирает экраны из нескольких источников, держит сессию
   сотрудника и раздаёт события. Решает бэкенд.
2. **BFF действует от имени сотрудника.** Каждый вызов в CRM и ERP идёт с токеном того, кто нажал кнопку. Права,
   журнал «кто и когда», лимиты — в бэкендах, как сейчас. Сервисные токены шва BFF не использует.
3. **Контракт раньше кода.** Публичный API BFF — `packages/contracts/openapi/platform-bff.yaml`; новые сущности и
   эндпоинты бэкендов — в их OpenAPI и `erp-integration.yaml` в том же PR, что и код (инвариант 3 ORCHESTRATOR).
4. **Инварианты ансамбля не меняются**: две базы, общих таблиц нет, CRM — источник истины по людям, «код решает,
   модель предлагает», секреты только в окружении, ИИ через LiteLLM.

## 2. Почему BFF, а не прямые вызовы из SPA

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| SPA ходит в CRM и ERP напрямую (`/api/crm/*`, `/api/erp/*` на одном домене) | нет нового сервиса | два набора токенов в браузере; словарь и 7 шагов считаются в браузере; экраны «Моя очередь», «Все заявки», поиск — по 3–6 запросов из браузера; смена бэкенда ломает SPA | нет |
| **BFF (backend-for-frontend)** | одна сессия-cookie, токены не видны браузеру (паттерн «token handler» из IETF «OAuth 2.0 for Browser-Based Apps»); словарь и маппинг в одном месте; агрегация экранов; бэкенды можно оптимизировать (T5), не трогая SPA | ещё один сервис | **да** |
| Логика Платформы внутри CRM-бэкенда | меньше контейнеров | CRM превращается в «бог-сервис»; ломает разделение фронт-офис / бэк-офис; оптимизация бэкендов (T5) упирается в него | нет |

**Язык BFF — Python 3.12 + FastAPI** (как CRM): прод-VPS умеет только x86-64 v1, а Python-образы ансамбля на нём
проверены; Node-рантайма на проде нет. Конвенции — как в `apps/crm/backend`: uv, ruff, mypy strict, pytest,
httpx, pydantic v2, structlog.

## 3. Вход, сессия, доступ к ERP

```
SPA  POST /api/v1/auth/login {email, password}
 └► BFF → CRM POST /api/v1/auth/login            → access (тело) + refresh (cookie rt_refresh)
        → CRM GET  /api/v1/me                     → id, имя, роль CRM, platform_access, platform_role_refs*
        → CRM POST /api/v1/auth/sso/token {aud: erp}   (если есть доступ к ERP)
        → ERP POST /api/v1/auth/sso/exchange/     → access ERP + refresh ERP (cookie)
        → Redis: session:{sid} = {crm_access, crm_refresh, erp_access, erp_refresh, user, roles, exp}
 ◄─ Set-Cookie: rt_pf_session=<sid>; HttpOnly; Secure; SameSite=Lax; Path=/
    Set-Cookie: rt_pf_csrf=<random>; Secure; SameSite=Lax; Path=/          (double submit)
```

- Браузер видит только `rt_pf_session` (256 бит случайности, httpOnly) и CSRF-cookie. Мутирующие запросы несут
  заголовок `X-CSRF-Token` = значению CSRF-cookie.
- Истёк access CRM или ERP → BFF обновляет его refresh-токеном сам; refresh не прошёл → сессия удаляется, SPA
  получает 401 `SESSION_EXPIRED` и показывает вход.
- Выход: BFF вызывает logout в CRM и ERP и удаляет сессию.
- Отключение сотрудника в CRM: CRM уже гасит его ERP-сессии (`DELETE /users/{crm_user_id}/sessions`); refresh CRM
  перестаёт работать → сессия Платформы умирает на ближайшем обновлении (не позже TTL access, 5–15 мин).
- Сотрудник без доступа к ERP (`platform_access = ["crm"]`): ERP-токенов в сессии нет, модули EDS/ERP скрыты.
- Вход только по логину CRM. Форма входа ERP, страница `/sso/exchange` CRM, переключатель CRM ↔ ERP, ADR-0010
  «вход в ERP через страницу CRM» после T4 не нужны (T5 удаляет).
- `platform_role_refs*` — роли Платформы сотрудника с их матрицами (R-1/R-2, §6); старое поле `platform_roles` (коды) удалено в R-1b.
- **EDS (с W13-A2, `docs/architecture/sso-token.md`, «Токен сотрудника для EDS»).** Не при входе, а при первом обращении к EDS:
  CRM `POST /api/v1/auth/sso/token {"aud": "eds"}` → EDS `POST /api/v1/auth/sso/exchange` → токен доступа EDS (15 минут, без
  refresh) в сессии (`eds`); истёк или EDS ответил 401 — новый обмен. CRM не выдаёт токен (нет `permissions.eds`) или EDS не
  знает сотрудника — 403 `FORBIDDEN` `details.reason = eds_not_granted`; сбой — 503 и пауза 15 с до следующей попытки.
  Отказ EDS сессию Платформы не закрывает. Адрес — `PLATFORM_EDS_URL` (по умолчанию `http://eds-api:8000`, только сеть compose).

## 4. Кто владеет новыми сущностями (SPEC-v3 §10.4)

Правило выбора: сущность живёт там, где живёт объект, к которому она привязана, и тот, кто отвечает за её стадию.
Заявка, коммерческие документы и деньги — ERP; письма, резолюции, служебки, согласования и реестр документов — EDS;
люди, лиды, переписка с клиентами, интеграции — CRM.

| Сущность | Где | Приложение / модель | Почему |
|---|---|---|---|
| `Letter` (входящее письмо, ВХ-NNN/ГГ) | EDS | сервис `apps/eds` (ADR-0015), связь с заявкой — по id и событиям | шаг 2 пути заявки |
| `Resolution` (текст, исполнители, срок, мин. маржа) | EDS | `apps/eds`; событие `resolution.*` | ERP создаёт задание на расчёт по событию |
| `LineApproval` (виза строки расчёта) | ERP | `sales`, связь с `QuoteItem` | часть расчёта |
| `ContractStatusLog` (Проект → Согласован клиентом → Выставлен у оператора → Подписан, скан) | ERP | `sales`, связь с `Contract` | заменяет «подпись кликом» |
| `PaymentConfirmation` (платёжка из кабинета/бота/вручную, подтверждение бухгалтером) | ERP | `finance`, связь с `Invoice` | деньги — ERP; Cabinet уже ходит в ERP |
| `ServiceMemo` + решения (СЗ-ГГГГ/NNN) | EDS | `apps/eds`, общий движок маршрутов согласования | внутренний документооборот, маршрут «директор → бухгалтер» |
| `ProjectChat`, `TeamChat`, сообщения, вложения | ERP | новое приложение `chats`; Channels уже есть | чат проекта рождается вместе с заявкой; события проекта пишутся в чат системными сообщениями |
| Внешний чат с клиентом (Telegram, почта) | CRM | существующие диалоги бота и ответы менеджера | бот — CRM; Платформа показывает его во вкладке «Внешний» |
| Уведомления сотрудникам | ERP `core.Notification` (расширить) + CRM (новое `staff_notifications` для событий CRM: SLA лида, сбой интеграции) | BFF сливает две ленты | у каждого события один источник |
| Журнал «кто и когда» | ERP (таймлайн сделки и документов), CRM (аудит) | BFF сливает | журнал там, где действие |
| Тикеты от команды (Admin) | CRM | новое `tickets` | Admin — консоль CRM |
| Роли Платформы (данные, ADR-0012) | CRM (IdP) | `platform_roles` (с `version`) + `user_platform_roles` | CRM — источник истины по людям (ADR-0003); системные «Администратор» и «Директор» неизменны, остальные создаёт администратор; провижининг в ERP — вычисленные `permissions`, `role_codes = []` |
| Номера ЗВ/ПР/КП/ИСХ/ДОГ/СЧ/АКТ/СЗ/ЗП | ERP | `DocumentNumberingScheme` + поле `number` у `Deal` | одна нумерация на компанию |
| Номер лида L-NNNN | CRM | форматирование `leads.id` | — |

Отдельной базы у BFF нет; Redis используется только для сессий, кэша на секунды и рассылки событий (§5).

## 5. События и реальное время

- **Опрос — запасной путь.** TanStack Query обновляет «Мою очередь», счётчики меню и колокольчик раз в 30 с и при
  возврате на вкладку; открытый чат — раз в 3 с.
- **Поток подсказок (B5, волна 11, ADR-0014).** BFF — подписчик шины `rt_bus` (строка `platform-bff` в
  `packages/contracts/bus/subscriptions.yaml`: события ERP, лидов CRM, сотрудников; приёмник `POST /bus/v1/events` на
  `rt_bus.fastapi.bus_router` + `MemoryReceiver`, без базы; секреты пар `RT_BUS_SECRET_ERP_PLATFORM_BFF`,
  `RT_BUS_SECRET_CRM_PLATFORM_BFF`, с волны 12 `RT_BUS_SECRET_EDS_PLATFORM_BFF` — события EDS подписаны, но до этапа D
  подсказок не дают, приёмник отвечает `skipped`; Caddy `/bus/*` на домене Платформы не отдаёт). Событие превращается в подсказку
  `{"topics": ["notifications"|"counters"|"queue"|"activity"], "reason": "<тип события>"}` и уходит в браузер по
  `GET /api/v1/events/stream` (SSE, только вошедшему сотруднику с разделом «Моя очередь»). **В потоке нет данных**:
  браузер перезапрашивает обычные API (с RBAC), поэтому чужое в поток не попадает. Устройство:
  - обработчик приёмника публикует подсказку в канал Redis `platform:hints`; каждый процесс BFF (`--workers 2`) слушает
    канал и раздаёт подсказку своим соединениям; сбой Redis → 503, издатель повторит доставку по расписанию шины;
  - всплеск событий сливается в один кадр (окно 300 мс, `PLATFORM_EVENTS_COALESCE_MS`), в тишине — комментарий
    `: ping` каждые 20 с (`PLATFORM_EVENTS_HEARTBEAT_SECONDS`); при heartbeat BFF проверяет сессию и закрывает поток
    после выхода или по сроку сессии;
  - перед кадром BFF сбрасывает кэш ответов бэкендов сессии (`feed:<sid>:data:*`, 8 с), чтобы перезапрос увидел новое;
  - `Last-Event-ID` нет: слушатель, потерявший Redis, после возврата шлёт подсказку `resync` (все темы), а SPA после
    переподключения потока делает один полный перезапрос;
  - события не несут адресата, поэтому подсказка идёт всем открытым потокам; адресная рассылка — когда в событиях
    появится ответственный (хвост).
  SPA: `EventSource` с переподключением (1, 2, 4, 8, 16, 30 с) в каркасе; пока поток жив, опрос — раз в 5 минут
  (страховка), при обрыве — прежние 30 с.
  Диагностика, если колокольчик, счётчики или очередь «не живут»: (1) вкладка «Сеть» браузера — запрос
  `events/stream` открыт, приходят кадры `: ping`; нет — смотрите Caddy (`flush_interval -1`, `no-transform`) и 401;
  (2) логи `platform-bff`: `POST /bus/v1/events` — 200 (401 — не совпал секрет пары `RT_BUS_SECRET_<ИЗДАТЕЛЬ>_PLATFORM_BFF`
  у издателя и BFF; 503 — Redis); (3) журнал издателя (`rt_bus_delivered`, DLQ) — доставка до BFF; (4) опрос работает
  всегда: при обрыве потока данные догоняются за 30 с.
- **Telegram сотруднику** (SPEC-v3 §9): по-прежнему бот CRM. ERP-события, которые должны дойти сотруднику в
  Telegram, идут в CRM существующим вебхуком шва; адресата и настройку «дублировать в Telegram» CRM берёт из
  карточки сотрудника.
- Шов CRM ↔ ERP (`erp-mcp`, SSO) не меняется; события CRM ↔ ERP идут по шине `rt_bus` (ADR-0014).
  CRM SSE `/api/v1/stream` BFF не использует: подписчик шины получает те же изменения лидов.

## 6. Роли и права

> **ADR-0012 (2026-10-22):** роли — данные. Фиксированы только «Администратор» и «Директор»; остальные роли создаёт
> администратор (название и матрица по каталогу разделов), шесть ролей SPEC-v3 становятся предустановками. Права в CRM и ERP
> вычисляются из матрицы роли по каталогу `platform-rbac.yaml`. Текст ниже описывает реализацию фазы P1 до этого ADR.

Шесть ролей SPEC-v3 §4: `MANAGER`, `DIRECTOR`, `SUPPLY`, `ENGINEER`, `ACCOUNTANT`, `ADMIN`; у сотрудника их может
быть несколько.

| Уровень | Что проверяет | Где |
|---|---|---|
| Бэкенд (решающий) | право на операцию и на поле (себестоимость, маржа, цены поставщиков) | CRM casbin, ERP `Permission` (22 кода) — как сейчас |
| BFF | доступ к маршруту и модулю по матрице SPEC-v3 §4.2; удаление полей с ограничением из ответа | `bff/app/rbac.py`, матрица в одном файле, тест на каждую ячейку |
| SPA | видимость модулей, пунктов меню, кнопок; `<Restricted>` для полей | `web/src/app/rbac.ts` из того же файла матрицы (генерируется) |

Выдача ролей — одна карточка сотрудника в Admin · Оргструктура (полный набор `platform_role_ids` в CRM; провижининг ERP
делает CRM). Каталог разделов, шаблонов и системных ролей — один YAML (`packages/contracts/platform-rbac.yaml` v2); генерация
в CRM, BFF и SPA из него.

**С R-2 (BFF 0.3.0, каталог v2):** роли — данные CRM. BFF читает в `/me` CRM роли сотрудника с их матрицами
(`platform_role_refs[].access`, `restricted_fields`; у системных — матрица каталога, Q-R2-1) и считает доступ
объединением матриц, «вид» — по активной роли (id); «Моя очередь» — по секции `queue` каталога; CRM не вызывается
по разделам, которых у ролей нет (источник `not_applicable`). Выдача ролей — полный набор `platform_role_ids` в CRM,
права CRM и ERP вычисляет CRM. Admin · Ролевая матрица — редактор ролей поверх `/admin/roles*` BFF
(→ `/api/v1/platform-roles*` CRM). Генераторы каталога: CRM (`gen_platform_roles.py`), BFF и SPA (`scripts/gen_rbac.py`).

**С R-1b (BFF 0.4.0, CRM API 0.2.0):** директор — `crm.leads` и `chats.external` только чтение (уточнение ADR-0012 п. 2);
чтение ролей — CRM `GET /platform-roles*` по `users:read`, BFF `GET /admin/roles*` по `admin: read` (директор видит матрицу
только для просмотра), изменения — `admin: full`; у роли поле `version`, `PATCH` требует `version`, расхождение — 409
`role_version_conflict` (BFF — 409 `CONFLICT`, `details.reason`); вкладки «Журнал» у роли нет (бэклог C2). Права CRM
сотрудника с ролями Платформы — только политики его ролей `pr:<id>`.

**С R-1c (BFF 0.6.0, CRM API 0.3.0, решение R3-D-2):** системная «Администратор» получает в CRM права своей матрицы каталога
(раздел `admin` и др.), а не `admin` CRM (`*:*`): лиды, клиенты, сделки и их выгрузка — 403, администрирование — 200;
бизнес-данные — второй ролью. У сотрудника хотя бы одна роль: пустой `role_ids` — 422 `ROLES_REQUIRED` (CRM — 422
`roles_required`), закрыть доступ — `is_active = false`.

## 7. Развёртывание

| Что | Значение |
|---|---|
| Домен | `platform.railtech.uz` → VPS 1 (A-запись — владелец); TLS — Caddy, ACME как у остальных доменов |
| Caddy | сайт `{$PLATFORM_DOMAIN}`: `/api/*` → `platform-bff:8000` (`flush_interval -1` для SSE), остальное → `platform-web`; заголовки безопасности и CSP как у CRM (`style-src 'unsafe-inline'` нужен Ant Design); `no_mcp` |
| Сервисы compose | `platform-bff` (uvicorn, 2 процесса, лимит 256 МБ), `platform-web` (статика, лимит 64 МБ); образы `rt-platform-bff`, `rt-platform-web` в GHCR по тегу sha, собирает `deploy.yml` (INF-P0-5, #151). **Caddy не зависит от здоровья Платформы** (`depends_on: service_started`): сбой её образа даёт 502 только на `platform.`, остальные домены живут (INF-P1-0) |
| Переменные | `PLATFORM_DOMAIN` (обязательна: `deploy.sh` без неё останавливается до pull — сначала DNS, потом строка в `/opt/rt/.env.prod`), `PLATFORM_SESSION_TTL_HOURS`, `PLATFORM_CRM_URL=http://crm-api:8000`, `PLATFORM_ERP_URL=http://erp-backend:8000`, `PLATFORM_EDS_URL=http://eds-api:8000` (W13-A2; значение по умолчанию совпадает с compose), `REDIS_URL`; необязательные (не секреты): `PLATFORM_LOGIN_RATE_PER_MINUTE` (10), `PLATFORM_CRM_TIMEOUT_SECONDS` (5), `PLATFORM_TRUSTED_PROXIES` (см. §8); нового секрета нет (сессия — случайный идентификатор, не подписанный токен) |
| Дев-стенд | `platform.localhost` в `Caddyfile.dev`, `make up` поднимает оба сервиса; `make check-platform` |

## 8. Наблюдаемость и устойчивость

- `X-Request-Id` от Caddy проходит BFF и уходит в CRM и ERP; логи всех трёх связываются по нему.
- **Адрес клиента (волна 11b, T5).** Caddy (`reverse_proxy`) сам ставит `X-Forwarded-For` и не верит такому заголовку от
  клиента. BFF берёт адрес из заголовка только от доверенного прокси: идёт справа налево по цепочке, пока адрес входит в
  `PLATFORM_TRUSTED_PROXIES` (CIDR или адреса через запятую; по умолчанию loopback и частные сети — сеть compose, наружу
  BFF не публикуется); первый адрес вне списка — клиент. Если сокет-партнёр не доверенный (в обход Caddy), заголовок
  игнорируется и берётся адрес сокета; нечитаемые элементы цепочки отбрасываются. Опечатка в списке — ошибка при старте.
  Адрес идёт в лимит входа, в каждую запись журнала BFF (поле `client_ip` рядом с `request_id`; события входа:
  `login_failed`, `login_not_completed`, `login_rate_limited`, `login_succeeded` — e-mail только короткий хеш) и в CRM
  в `X-Forwarded-For` при входе (CRM видит BFF, аудит входа ведёт по заголовку).
- **Лимит входа (O-1).** 10 **неудачных** попыток в минуту отдельно на IP и на e-mail (`PLATFORM_LOGIN_RATE_PER_MINUTE`).
  Попытка записывается в Redis до обращения к CRM (параллельные запросы лимит не обходят) и возвращается, если вход не
  провалился из-за учётных данных: успешный вход (офис за одним NAT), нет ролей Платформы, сбой CRM. Считаются
  `INVALID_CREDENTIALS` и `ACCOUNT_LOCKED`. Успешный вход сбрасывает счётчик e-mail; счётчик IP хранит неудачи других
  пользователей этого адреса. Сверх порога — 429 `TOO_MANY_REQUESTS` с `Retry-After`, в CRM попытка не уходит.
- **Таймаут CRM.** Клиент CRM в BFF ждёт `PLATFORM_CRM_TIMEOUT_SECONDS` (по умолчанию 5 с; было 3 — под нагрузкой вход
  давал 503, runbook r3 O-1; отдельного таймаута для входа нет). Клиент ERP, Redis и проверка health — по-прежнему 3 с.
- **Пробы внешних сервисов (W13-A1).** «Проверить связь» ERP, SMTP и Telegram, сопряжение, ротация ключей, проверка модели и журнал
  расходов LiteLLM идут через CRM дольше обычного вызова: клиент CRM ждёт до 30 с (`PROBE_TIMEOUT_SECONDS`), а 502 CRM («сервис
  за мной не ответил») возвращается как есть и переводится в `INTEGRATION_FAILED` (502) с причиной в `details.reason` — это итог
  проверки, а не сбой CRM (тот остаётся 503 `BACKEND_UNAVAILABLE`). Секреты (токен бота, ключи моделей, пароль SMTP, код
  сопряжения, пароль администратора) BFF только передаёт: они — `SecretStr` в телах запросов, в ответах и журнале их нет, в ответах
  — маски `*_last4`.
- Агрегирующие эндпоинты BFF ходят в источники параллельно с таймаутом 3 с и отдают частичный результат с
  флагом `sources: {crm: ok, erp: unavailable}`; SPA показывает плашку «ERP не отвечает, данные неполные»,
  а не пустой экран.
- `GET /api/v1/health` BFF проверяет Redis, CRM `/health`, ERP `/health`; карточка «Платформа» в Admin ·
  Внешние интеграции (реестр внешних сервисов CRM, ADR-0024 CRM).
- Ошибки бэкендов BFF переводит в один формат `{code, message, details, source}` с текстом на языке сотрудника;
  коды ошибок бэкендов сохраняются в `details` для разбора.
