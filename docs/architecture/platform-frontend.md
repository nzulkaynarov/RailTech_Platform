## 1. Стек

Берём версии CRM-фронтенда (`apps/crm/frontend`), чтобы у ансамбля была одна линия Ant Design и одни приёмы.

| Что | Выбор | Примечание |
|---|---|---|
| Язык, сборка | TypeScript ~5.9, Vite 8, pnpm 10 | как CRM |
| UI | React 18.3, **antd ^5.29**, `@ant-design/icons` ^5.6, **`@ant-design/pro-components` ^2** (ProTable, ProForm, ProDescriptions, ProCard) | Pro Components — по SPEC-v3 §5.1; в CRM их нет, добавляются только в Платформу |
| Маршруты | react-router ^7 (data router) | SPEC-v3 говорит «React Router 6»; берём 7, как в CRM и Cabinet, API совместим |
| Данные | TanStack Query ^5; клиент и хуки генерирует **orval** из `packages/contracts/openapi/platform-bff.yaml` | как CRM; моки MSW генерирует тот же orval |
| UI-состояние | Zustand ^5 (панели, язык); сохранение в `localStorage` по пользователю и маршруту, обёрнутое в try/catch | как ERP |
| Формы | ProForm (поверх antd Form) | валидация — по схемам OpenAPI |
| i18n | react-i18next, ru (по умолчанию), uz (латиница), en | словарь SPEC-v3 §2 — отдельное пространство имён `dictionary` |
| Графики | `@ant-design/plots` | только «Сводка по компании», без двойных осей и кругов |
| Тесты | Vitest + Testing Library; Playwright + `@axe-core/playwright` | как CRM |
| Refine | **не используем** | BFF уже отдаёт данные под экраны; лишний слой абстракции не нужен |

## 2. Структура кода

```
web/
  src/
    app/          main.tsx, router.tsx, providers (Query, ConfigProvider, i18n), AppShell, rbac.ts (генерируется),
                  theme.ts (из packages/ui-tokens)
    shared/
      ui/         AppShell части (ModuleRail, ModuleMenu, TopBar, ContextPanel), RequestSteps, StatusTag,
                  Consequence, EmptyState, MoneyText, DocNumber, PersonChip, SourceBanner, Forbidden
      api/        generated/ (orval: хуки, типы, MSW-моки), http.ts (CSRF-заголовок, 401 → вход), errors.ts
      i18n/       ru|uz|en: common.json, dictionary.json, по файлу на модуль
      lib/        форматирование сумм (пробелы разрядов, «сум»), дат (часовой пояс компании), номеров
    entities/     lead, client, request, project, letter, quote, contract, invoice, act, memo, chat, user, role
                  (типы-обёртки, StatusTag-карты, мелкие карточки)
    features/     create-request, resolve-letter, calc-line-approve, calc-complete, approve-quote, return-quote,
                  contract-status, confirm-payment, request-payment-doc, approve-memo, make-memo-from-message,
                  invite-employee, assign-role
    modules/      dashboard, crm, eds, erp, chats, admin — страницы, подменю, конфигурация модуля
  e2e/            сценарии Playwright по фазам (docs/history/platform/05-plan.md)
```

Правила: страница модуля знает только `features` и `entities`; `features` не импортируют друг друга; всё, что
видно больше чем в одном модуле, — в `shared`. Файл ≤ 400 строк (правило CRM).

## 3. Тема и токены

Токены SPEC-v3 §5.2 становятся версией **0.2.0** общего пакета `packages/ui-tokens` (вопрос 7 в
`docs/history/platform/06-questions.md`): так Cabinet и Платформа выглядят одной семьёй. `web/src/app/theme.ts` строится как
`apps/crm/frontend/src/app/theme.ts`: `cssVar: true`, токены из `tokens.generated.ts`, явные `*Bg`/`*Border`.

**Числа вида (цвета, ступени шрифта, радиусы, высоты контролов, компонентные токены AntD) здесь не повторяются:
единственный источник — [стандарт интерфейса](ui-standard.md) §2–§3 и §5, значения живут в `packages/ui-tokens/tokens.json`,
в AntD они попадают через `web/src/app/theme.ts`.** Прежняя таблица токенов SPEC-v3 заменена стандартом 2026-11-15 и убрана отсюда, чтобы агент не читал два набора цветов; в таблицах ниже цвет назван ролью ‹…› из ui-standard §2, а не значением. Здесь остаётся то, чего в
стандарте нет:

- затравка темы — `cssVar: true`, токены из `tokens.generated.ts`, явные `*Bg`/`*Border` у `colorSuccess`/`colorWarning`/
  `colorError` (antd берёт эти токены в текст и под белый текст: в теме antd они равны значению «текст», светлые — явно);
- шрифт — Inter, самостоятельный хостинг woff2 (CSP `font-src 'self'`), не Google Fonts;
- в CSS и коде модулей — только переменные `var(--rt-…)` и токены темы, литералов цвета нет (проверка
  `colorLiterals.test.ts`).

Запрещено (SPEC-v3 §5.1): эмодзи, градиенты, тени на карточках в сетке, цветная полоска слева у карточки,
статус только цветом.

## 4. Каркас `AppShell` — точно по макету v3

панель (поверх основного окна по умолчанию, ширина 480/640 px — стандарт интерфейса §6) выходят за модель `ProLayout`, поэтому `AppShell` собирается из
`antd Layout`, `Layout.Sider` рейла, своей колонки подменю и своего `aside` боковой панели;
внутри основного окна — `PageContainer` из Pro Components. Вид и поведение — как в SPEC-v3 §6.1.

Состояния панелей по умолчанию:
- Списки и таблицы: боковое окно закрыто, открывается кликом по строке или ссылкой с `?panel=open`.
- Карточка объекта (`:id`): на экране ≥ 1200 px открыто, пока не закрыто явно (`?panel=closed`), — **поверх**, как везде
  (решение владельца 2026-10-30, п. 2; UX-1a): рабочая область при открытии карточки не сужается. Раздел может держать окно
  закрытым и на карточке (`defaults.panelOpen: false`: журнал заказа уже на карточке; карточка расчёта — таблица на всю
  ширину, «Задание» по кнопке «Показать панель»).
- Закреплённое рядом — только выбор пользователя булавкой; булавка и ширина, как и подменю, — одни на пользователя во
  всех разделах (оболочка не зависит от раздела; в `chats` — всегда поверх), у разделов своих умолчаний нет. Помещается ли
  окно рядом, каркас считает по ширине экрана: рейл 64 + подменю 200 (если открыто) + окно 480/640 + рабочая область ≥ 736.
  «Ждут ответа»: окно поверх не закрывает поле ответа — страница берёт отступ справа из `--pf-overlay-inset` (ширина окна
  поверх или 0), ширина основного окна та же.
- Подменю: пока пользователь не выбрал — развёрнуто при `≥ 1440px`, свёрнуто при `< 1440px`; дальше — его выбор, одно
  значение на все разделы.
- Сетки карточек в две колонки считаются от ширины карточки (`@container`), а не экрана (`@media`): с окном рядом или
  подменю колонка реквизитов уходит вниз, а не сжимается до букв. Переключатели «таблица ↔ список» по ширине блока —
  `useCompactBlock` с запасом 40 px у порога.

### 4.1. Архитектурные инварианты UI/UX Оболочки (UI Guardrails для ИИ-агентов)

1. **Инвариант 1: Запрет Layout Shift для широких таблиц.**
   Боковое окно `ContextPanel` по умолчанию открывается **поверх** основного окна у правого края, без затемнения. Это
   немодальная область `complementary` (`aside`), а не `Drawer`: у `Drawer` — `aria-modal` и ловушка фокуса (axe
   `aria-allowed-attr`), а из окна Tab должен возвращаться в таблицу. Запрещено при открытии сжимать таблицы списков по
   умолчанию — это сбивает колонки и даёт горизонтальную прокрутку. Закрепление рядом (`docked`) — только по кнопке-булавке, на экране `≥ 1280px` и когда
   рабочей области остаётся `≥ 736 px`; иначе окно поверх, выбор помнится. Это касается и карточки объекта: окно само не
   закрепляется. «Рядом» и «поверх» — одна обёртка, меняется класс: булавка и переход порога не размонтируют вкладки и
   формы окна. Ширины подменю и окна не анимируются (`transition: none`; появление поверх — только `transform`). В модуле
   `chats` закрепления нет (`isStrictlyOverlay`).

2. **Инвариант 2: Чистота URL vs LocalStorage (декуплинг состояния от настроек).**
   - Открытие панели (`panelOpen`) задаёт **только** адрес: `?panel=open` или `?panel=closed`; без параметра — закрыто в
     списках и открыто на карточке объекта на ≥ 1200 px.
   - Сохранённые в `localStorage` записи открытие не меняют.
   - В `localStorage` (ключ `rt-pf-panels-v2`) сохраняются **исключительно визуальные предпочтения**: режим (`panelMode`: `overlay` | `docked`), ширина (`panelWidth`: `default` | `wide`) и свёрнутость подменю (`menuOpen`: `boolean`) — одни на пользователя, запись `<пользователь>|*` (прежние значения по разделам переносятся при чтении: выбор, сделанный чаще, при равенстве — последний); по разделу — только последняя выбранная вкладка (`lastTab`: `string`).
   - При закрытии в списке параметр `panel` удаляется из адреса, на карточке объекта — `panel=closed`.

3. **Инвариант 3: Запрет деструктивных редиректов из колокольчика.**
   Центр уведомлений открывается в правой шторке `NotificationDrawer` (420 px). Запрещено уводить пользователя на другой URL при переключении фильтров (ссылка `Все уведомления` -> `/dashboard/queue?panel=open&tab=notifications` ликвидирована). Все уведомления доступны прямо в шторке через сегменты `Непрочитанные (N)` / `Все` и селектор категорий. Пользователь никогда не теряет текущий экран и несохранённые данные при чтении уведомлений.

4. **Инвариант 4: Строгая иерархия диалогов и окон.**
   - **Inline (по месту)**: базовое редактирование, фильтры, быстрые переключатели.
   - **Slide-over Drawer (шторка)**: контекстные карточки сущностей, детальный просмотр, формы создания и редактирования сущностей (`ContextPanel`, `NotificationDrawer`, `HelpDrawer`).
   - Полная таблица «задача → место» и правило секций — §4.1a (решение владельца 2026-11-12); при расхождении верна §4.1a.
   - **Modal (модальное окно, ширина — ui-standard §6, без прокрутки)**: строго зарезервировано ТОЛЬКО для одношаговых подтверждений и критических действий («Отправить письмо», «Удалить запись», «Подтвердить дату»). Текст окна — по CONVENTIONS §2 п. 8: действие и объект, без блока последствий.

5. **Инвариант 5: Шапка и формы не двигаются сами (UX-1b, аудит 2026-10-30, S5, S6, S13, S15).**
   - Правая группа шапки (поиск, «?», колокольчик, кнопка окна) постоянной ширины: кнопка окна — иконка 32 px без
     подписи; на разделах без окна (`/me`, `/help`, 403, 404) она `visibility: hidden` и держит место. Крошки — гибкая
     область (`flex: 1 1 0`, `min-width: 0`, многоточие). Поиск стоит на одном x во всех разделах и при открытии окна.
   - `ContextualSaveBar` не вставляется в поток при первой правке: место под него в конце формы держится всегда (бар
     невидим, `inert`), с правками бар — полоса на всю ширину формы или её карточки — прилипает к низу прокручиваемой
     области поверх контента; поле в фокусе прокручивается выше бара, а не уходит под него. Второй кнопки «Сохранить …» под
     формой с баром нет.
   - Активный пункт подменю, рейла и вкладки окна выделяется цветом и фоном, без смены `font-weight`.
   - Рабочая область и тело окна — `scrollbar-gutter: stable`: появление прокрутки не меняет ширину.

6. **Инвариант 6: Данные обновляются на месте (UX-1c, аудит 2026-10-30, S8, S9, S10).**
   - *Скелетон — только при первой загрузке.* Клиент запросов (`app/queryClient.ts`, `keepSamePathData`) для каждого
     запроса без своего `placeholderData` подставляет прежние данные, пока грузится ответ **того же адреса** с другими
     параметрами (фильтр, вкладка, страница); у карточки другого объекта адрес другой — там скелетон, чужие данные не
     подставляются. Список показывает прежние строки с признаком загрузки (`DataBlock busy`: полоса 2 px поверх верхнего
     края через 150 мс и `aria-busy`), высота блока не меняется. `QueryState rows={размер страницы}` делает это сам;
     экраны со своим `isPending` оборачивают тело в `DataBlock busy={isPlaceholderData} resetKey={useShownKey(…)}`.
     Пришёл ответ — список строится заново (`resetKey`), а не двигает совпавшие строки; фокус остаётся на «том же»
     элементе. Колонки и подписи, зависящие от условий (колонка «Ответственный» реестра «Все»), берутся из условий
     показанных данных (`useShownValue`), числа на вкладках — последние известные (`useLastDefined`).
   - *Скелетон первой загрузки — высоты итога:* `ListSkeleton` — строки высотой строки таблицы (44 px) по размеру
     страницы, но не больше 10, с отступом 16 px от рамки. Пока внутри скелетон (новая вкладка с другим запросом),
     `DataBlock` держит ровно прежнюю высоту (длинный скелетон обрезается, а не растягивает блок).
   - *Вкладки-фильтры не размонтируют тело:* `TabsBar` — полоса antd `Tabs` без своих панелей и одна панель
     (`tabpanel`) под ней для всех вкладок.
   - *Колонки фиксированы:* таблицы рабочих списков — `table-layout: fixed` (`pf-fixed-table`), ширины из `<colgroup>`
     (`TableCols`, гибкая — `null`, тема/название), ниже суммы ширин (`tableMinWidth`) таблица прокручивается в своей
     области. **Ширина колонки — по её типу (§4.2), не по данным страницы; меняется только действием пользователя**
     (ручная ширина и прочая настройка сотрудником — `DataTable`, ниже). Длинное имя — многоточие с `title` (`pf-ell`), тема и название
     переносятся по словам; номера, даты и суммы — `tabular-nums`; заголовок и тег статуса — одна строка с многоточием
     (§4.2). У `DocNumber` место кнопки копирования есть всегда.
   - *Блоки после ответа — в слоте:* счётчики «Моих задач» до ответа — карточки-скелетоны той же высоты (столько,
     сколько было в прошлый раз в этом браузере, впервые — 4); баннер «Настройка Платформы» и пункт «Первый запуск» —
     рабочая область администратора скрыта (`visibility: hidden`, место держит, экран уже грузится), пока не ответил
     чек-лист (`useSetupKnown`), но не дольше 800 мс (`SETUP_WAIT_MS`: завис — экран показывается, а поздний баннер встаёт
     в конец рабочей области этого адреса, `useLateSetupBanner`; со следующего перехода — сверху, UX-2b), поэтому баннер не
     вставляется над готовым экраном; `SourceBanner` меняет состояние
     (появиться/исчезнуть) только если новое продержалось 3 с, первое состояние — сразу.
   - Цель (замер UX-1c, сборка на моках, API 300 мс, 1440 и 390): при смене фильтра, вкладки и страницы высота блока не
     проваливается в скелетон, границы колонок сдвигаются ≤ 2 px, layout-shift ≤ 0,01.

### 4.1a. Где что: страница, секции, боковое окно, окно поверх (решение владельца 2026-11-12)

Одна задача — одно место. Сотрудник заранее знает, где откроется следующее действие; новых видов окон не заводим.
Выбор — по задаче, а не по удобству разработчика.

| Задача сотрудника | Где | Как выглядит | Примеры |
|---|---|---|---|
| Просмотреть много объектов, выбрать | **Список** на странице | таблица с фильтрами; на телефоне — карточки | Входящие, Лиды, Исходящие |
| Взглянуть на объект, не теряя список | **Боковое окно** поверх (`ContextPanel`) | вкладки «Карточка», «Обсуждение», «Документы» | карточка лида, документа, контрагента |
| Долго работать с объектом | **Страница объекта**; боковое окно — сведения, маршрут, история | действия — в центре, не в окне | заявка с расчётом, КП на подпись, проект |
| Короткая форма (4–15 полей по ui-standard §6), одно действие | **Боковое окно**, если форма о выбранном объекте; иначе — страница | одна колонка, кнопка внизу | новый лид, заявка из лида, поручение |
| Длинная форма (больше 15 полей по ui-standard §6) или разные по смыслу части | **Секции по шагам** (`StepSections`): на странице, если это самостоятельный документ; в боковом окне, если форма о выбранном объекте | нумерованные секции, открыта одна | письмо, внутренний документ, регистрация входящего, реквизиты компании, карточка партнёра, заказ поставщику |
| Первая настройка | **«Быстрая настройка»** — те же секции; рядом «Все параметры» | | почта, реквизиты |
| Короткое действие над открытым объектом: подтвердить, указать причину, дату — до 3 полей | **Окно поверх** (`Dialog`, ширина и поля — ui-standard §6) | действие и объект в заголовке, кнопка повторяет действие | подписать, отклонить с причиной, отметить дубль, передать с запиской |
| Правка одного значения | **По месту** | поле в строке или в карточке | переименовать, статус, ответственный |
| Настройки раздела | **Страница Настроек** с баром сохранения (`ContextualSaveBar`) | без кнопки «Сохранить» под формой | Компания, Справочники |
| Уведомления, помощь | **Шторка справа** (`NotificationDrawer`, `HelpDrawer`) | не уводит с экрана | колокольчик, «?» |
| Создать что угодно | **Окно «Создать»** — единственное меню-окно | группы, подписи, поиск | кнопка «+» |

**Секции по шагам (`StepSections`)** — одно правило на все длинные формы:
- Секции пронумерованы и названы по смыслу («О чём и кому», «Текст и вложения»), открыта одна; «Далее» сворачивает её
  в **строку итога** («ГНИ Мирабадского района · gni@… · в ответ на ВХ-109/26») и открывает следующую.
- Вернуться можно к любой секции щелчком по заголовку; ничего не теряется. Секции не блокируют друг друга («Далее» и
  заголовок не запрещены), кроме той, что зависит от предыдущей (маршрут считается из вида и суммы) — тогда она
  подписана, чего ждёт.
- **Галочка шага — тот же валидатор, что у отправки** (СЦ-6): форма считает невыполненные требования шага одной функцией
  и отдаёт их секции (`requirements`); пока список не пуст, галочки нет. Шаг без обязательных полей получает галочку,
  только когда человек его прошёл. Когда шаг уже покидали, его требования названы на самом шаге («Чтобы шаг был
  готов: …»), у поля — текст ошибки, у заголовка — отметка «нужно исправить»; на только что открытом шаге пустая форма
  требованиями не пестрит.
- Если результат уходит наружу или запускает маршрут, последняя секция — **«Проверка»**: сводка с «Изменить» у каждой
  секции, список **«Осталось»** (шаг — что сделать, пункт ведёт на шаг) и главная кнопка. Пока осталось хоть что-то,
  кнопка недоступна, а причина — список рядом с ней (`aria-describedby`); форма не возвращает человека на пройденный
  шаг. Если форма просто сохраняет настройки — проверки нет, работает бар сохранения.
- Главная кнопка одна — в конце последней секции; «Сохранить черновик» — на шагах, пока есть всё, что нужно черновику
  (у документа — тема и текст), иначе вместо кнопки подсказка, чего не хватает; в настройках его нет.
- Что проверить заранее нельзя (отказ сервера: номер входящего не найден, проект, неактивный согласующий), открывает свою
  секцию, ставит фокус на поле и ставит отметку «нужно исправить»; правка формы снимает её.
- Черновик, который хранится в браузере (заявка, регистрация входящего), предлагается кнопками «Продолжить» и
  «Начать заново» — молча в форму не подставляется.
- На телефоне — те же секции списком; боковое окно — лист на весь экран; окно поверх — нижний лист.
- Короткие формы (до порога ui-standard §6) секций не получают.

**Запрещено:** форма больше порога окна поверх (ui-standard §6); форма создания нового объекта в окне поверх; вторая кнопка
«Сохранить» под формой с баром; свой вид окна или мастер вне `StepSections`.

**Что пока не по правилу** (переделывается вместе с PR своего модуля, отдельной волны нет; EDS · новый документ
переведён на секции 2026-11-13, пункт «Ш»; «Компания · реквизиты» — секции «Компания», «Контакты», «Банковские счета»,
`?section=bank` открывает счета, 2026-11-13; ERP · карточка партнёра — секции «Компания» и «Контакт» в боковом окне
через общий `shared/ui/Sheet`, правка — на месте карточки, 2026-11-13; ERP · строка расчёта и запрос цены — формы в
боковом окне на вкладке «Задача» (`Sheet` с `tab`), 2026-11-14; EDS · регистрация входящего — пять секций, блок дубля
над ними, 2026-11-14; ERP · новый заказ поставщику — страница `/erp/stock/new` с секциями «Партнёр и способ» и «Строки»,
2026-11-14; CRM · «Создать заявку» — секции «Клиент», «Контакт», «Запрос», «Проверка и отправка» в боковом окне,
2026-11-14; Справочники · значение — форма в боковом окне (`useSheetPanel` открывает окно по адресу), 2026-11-14;
Компания · банковский счёт — форма в боковом окне (`FormSheet`), 2026-11-14). Все экраны из списка переведены.

### 4.2. Таблицы рабочих списков: тип колонки → ширина (T0, решение владельца 2026-11-02)

Ширина по умолчанию зависит только от **типа** колонки, а не от данных на странице, поэтому инвариант 6 (колонки стоят на
месте при смене фильтра, вкладки и страницы) сохраняется. Эталоны — SAP Fiori elements (ширина по метаданным типа с
пределами), Salesforce `lightning-datatable` (`fixed` по умолчанию, обрезка с подсказкой), Material Design 2 (числа и их
заголовок — вправо, длинный заголовок — многоточие); разбор — [ресёрч «Таблицы»](../research/2026-11-02-flexibility/1-tables.md)
§3–§4. Ширина в `COLS` экрана — с отступами ячейки.

| Тип | Ширина, px (по умолч. / мин. / макс.) | Растёт | Выравнивание | Перенос |
|---|---|---|---|---|
| номер (`DocNumber`, `ВХ-104/26`) | по формату номера, 108–148 (с кнопкой копирования — 148) / = / 160 | нет | лево, `tabular-nums` | нет; тип документа или версия — второй строкой `pf-hint` |
| дата | 104 / 96 / 120 | нет | лево, `tabular-nums` | нет |
| дата и время | 104: время — второй строкой `pf-hint` (иначе 148) | нет | лево, `tabular-nums` | дата и время — две строки |
| сумма, количество, процент | 120–148 (по заголовку «Сумма с НДС») / 96 / 200 | нет | **право**, `tabular-nums`, заголовок тоже (`pf-col-num`) | нет |
| статус (тег) | по самой длинной частой подписи на ru, uz, en / = / 220 | нет | лево | нет: многоточие и подсказка |
| лицо (автор, исполнитель, ответственный) | 120–136 (не уже заголовка «Ответственный») / 120 / 240 | нет | лево | одна строка, многоточие и `title` (`pf-ell`) |
| имя (клиент, корреспондент, поставщик) | гибкая или 160 / 150 / 360 | да | лево | одна строка с многоточием или до 2 строк по словам; связанный номер (заявка) — второй строкой `pf-hint` |
| текст (тема, описание) | гибкая (`null`), мин. в `tableMinWidth` 170–240 | да | лево | по словам |
| действие (кнопка строки) | по кнопке на самом длинном языке, 104–156 / = / 160 | нет | лево | нет: длинная подпись — многоточие, полное имя — `aria-label` |
| иконка, флаг | 48 / 48 / 48 | нет | центр | — |

Общие правила (`shared/ui/data-block.css`, `.pf-fixed-table`):
- отступ ячейки — 12 px, у краёв таблицы — 16 px; одно правило на все списки;
- заголовок — одна строка, длинный обрезается многоточием; полный текст остаётся в разметке (скринридер) и в `title`
  (ставит `TableCols`, только обрезанному); тег статуса — так же (`StatusTag` ставит `title` только обрезанному; если текст
  тега — разметка, полный текст передаётся пропом `title`);
- в ячейке перенос — по словам (`overflow-wrap: break-word`), слово рвётся, только если само не помещается; глобального
  `overflow-wrap: anywhere` нет;
- кнопка и тег в ячейке не шире колонки: таблица не распирается подписью на узбекском;
- не помещается вся таблица — сначала второстепенное уходит второй строкой в соседнюю ячейку (тип документа под номером,
  заявка под корреспондентом, время под датой — как карточка на телефоне и pop-in Fiori), а не горизонтальная прокрутка;
- **на 1440 px с открытым подменю и закрытым окном (рабочая область 1111 px) рабочие списки помещаются без прокрутки
  вбок** на ru, uz и en: `Σ COLS + мин. гибкой ≤ 1111`; проверка — `e2e/t1-table-widths.spec.ts` (прокрутка, заголовки и
  теги в одну строку, обрезанное — с подсказкой) и `e2e/stable-data.spec.ts` (геометрия колонок ±2 px);
- на телефоне (< 768 px) списки — карточки.

**Настройка сотрудником — `shared/ui/DataTable`** (пункт «Т» плана 2026-11-12, ресёрч 2026-11-02 §4.2; состояние столбцов —
TanStack Table 9, разметка своя: `pf-fixed-table`, `<colgroup>`, `caption`, `ScrollRegion`). Экран передаёт столбцы
(`id`, заголовок, ширина по типу или `null`, `numeric`, ячейка) и строки; сотрудник сам меняет:
- ширину — мышью за правую границу заголовка (слой ручек над таблицей, `aria-hidden`; двойной щелчок — по содержимому видимых
  строк) и с клавиатуры «−»/«+» в «Столбцах» (шаг 16 px, пределы `minWidth`/`maxWidth`);
- видимость (первый столбец скрыть нельзя), порядок, закрепление слева (`position: sticky`, тень у последнего закреплённого);
- «Сбросить» — вид по умолчанию.

Хранение — в браузере на пользователя: `localStorage` `rt-pf-tables-v1`, запись `<пользователь>|<таблица>`; столбцы, которых
нет на экране сейчас (другая вкладка), пропускаются. Ширина меняется только действием сотрудника — инвариант 6 сохраняется.
Переведены: EDS — «Все документы», «Входящие», «Проекты», «Счета», «Служебки на оплату»; ERP — «Заявки», склад
(остатки, заказы поставщикам, приёмка, отгрузки); CRM — «Лиды», «Клиенты»; «Люди»; админка — сотрудники, журнал аудита,
статьи, шина (подписчики, доставки, входящие), обращения, загрузка файла справочника и все таблицы настроек через
`ListTable` (`modules/admin/company/common.tsx`: справочники, шаблоны, счета, начисления, права подписи, правила почты,
журнал курса, запросы категорий). Таблицы строк (расчёт, КП) — следующими PR. Телефон — по-прежнему карточки.
Страницы на клиенте — `pageSize` (длинные справочники, «Люди»): переключатель под таблицей, после фильтра номер страницы
не выходит за последнюю; пусто или загрузка — слова и скелет вместо таблицы (решает экран или `ListTable`).

### 5.2. Просмотр документа — один компонент (ПРОСМ-1, решение владельца 2026-11-26)

Любой PDF и любая картинка в Платформе показываются одним компонентом `shared/ui/DocumentViewer`; своих просмотрщиков в
модулях нет. `shared/ui/PdfViewer` — тонкая обёртка над ним (вид `panel`), поэтому «На весь экран» есть в каждом месте с файлом:
образец бланка и шаблона, шаблоны писем, письмо на бланке, карточка документа, техдокументация и файлы каталога.

- **Построен на готовом `pdfjs-dist`** (`PDFViewer`, `EventBus`, `PDFFindController`, `PDFLinkService` из `web/pdf_viewer.mjs`):
  страницы рисуются по мере прокрутки (предела на число страниц нет), поверх холста — текстовый слой (выделение, копирование,
  поиск), холст в физических пикселях экрана (чёткость на 2×, тест `pdfv1-sharp-preview`). Ни `iframe`, ни `object`, ни `eval`:
  CSP Платформы не меняется (`object-src 'none'`, `isEvalSupported: false`, рабочий поток с того же адреса). Свои — только
  рамка, панель инструментов, миниатюры, адрес слоя и общая обёртка «построить → дождаться → показать».
- **Панель инструментов одна в обоих видах**: «По ширине | 100 %», масштаб, страница «N из M», поиск со счётчиком и «вперёд/назад»,
  «Скачать» (главная кнопка — на весь экран), «На весь экран» / «Свернуть» (Esc). Клавиши: `+` `−` масштаб, `0` по ширине,
  `←` `→` страницы, Ctrl F поиск.
- **На весь экран** — слой по правилам окон (antd `Modal`: фокус внутри, Esc закрывает, фокус возвращается на кнопку, страница
  под слоем не прокручивается), адрес `?view=full&page=N` (`useFullRoute`): «Назад» сворачивает слой, ссылка ведёт на страницу,
  перезагрузка оставляет слой открытым. Если просмотров на странице несколько, слой открывает один — первый занявший адрес.
  На телефоне (< 768) нажатие на лист открывает слой сразу; миниатюр там нет. Браузерный Fullscreen API не используется.
- **Файл, который сервер строит в фоне** (образец, письмо на бланке): `useRenderedPdf` (`shared/ui/DocumentViewer`) скачивает
  готовые байты один раз и держит прежнюю версию на экране, пока строится новая; запрос на построение и опрос — у вызывающего.
- **Охрана**: `pdfjs-dist` импортируется только внутри `src/shared/ui/DocumentViewer/` — правило `no-restricted-imports` в
  `web/eslint.config.js`. Дальше по плану (`ПРОСМ-2…К`): боковое окно «Открыть», адрес `/documents/<номер>`, Кабинет.

## 6. Маршруты и состояние URL

Карта маршрутов — SPEC-v3 §6.3, без изменений. Правила реализации:

- Номер объекта в URL — бизнес-номер (`/eds/projects/ПР-2026-104`); кодирование `encodeURIComponent`; BFF
  принимает номер и сам находит внутренний id.
  Номер со «/» (`ВХ-104/26`, `КП-2026/118`) открывает карточку и без кодирования (`/eds/inbox/ВХ-104/26`): `matchSection` склеивает
  хвост пути, если он — бизнес-номер (D1-3). Письмо можно открыть и по id (UUID), и по номеру.
- Боковое окно на телефоне (< 768 px) у «Резолюции» — собственный лист на весь экран (`?sheet=resolution`) с кнопками решения внизу;
  ссылки с `panel=open` превращаются в лист (D1-3, UX P0-4). Черновик резолюции — `sessionStorage` вкладки на письмо.
- `?panel=open|closed&tab=<вкладка>` управляют боковым окном на всех экранах; фильтр списка Chats «Внутренний / Внешний» —
  `?scope=internal|external` (в SPEC-v3 §6.3 он `?tab=`; переименован, чтобы `tab` везде значил вкладку бокового окна, Q-PLT-12-3); клик по строке таблицы меняет `?<объект>=<номер>`
  и открывает объект в боковом окне без перехода.
- Строка очереди «Доработать» (`rework_document`, D1-6b) ведёт на `/eds/new?draft=<id документа>` — форму «Продолжить» D1-5: у экрана
  «Создать документ» нет боковой карточки, отдельного экрана доработки нет.
- Клиенты · Лиды и Клиенты (D1-2b): карточка — `?lead=L-2041` / `?client=42` (или путь `/crm/leads/L-2041`, `/crm/clients/42` —
  так открывают поиск ⌘K, колокольчик и очередь), форма «Создать заявку» — тот же адрес с `&create=1`; фильтры лидов —
  `?status=`, `?scope=mine|overdue`, `?channel=`, `?q=` (статус лида не `tab`: `tab` — вкладка бокового окна). На телефоне карточка
  и форма — лист на весь экран с кнопками внизу. Ключ формы заявки (`request_key`, UUID) — один на открытие формы: повтор
  после сбоя и двойной клик не создают вторую заявку.
- Хлебные крошки — из маршрута (`handle.crumb`) и названия объекта.
- **Переходы из «Моей очереди», колокольчика, поиска ⌘K и ленты «Сегодня» (D1-6).** Одна функция `modules/objectLinks.ts` (`objectLink`) приводит
  адрес объекта из BFF к полному: бизнес-номер или id в пути, `panel=open` и вкладка решения — письмо `ВХ-…` → «Резолюция» (`tab=resolution`), КП на
  одобрении → «Одобрение» (`approve`), служебка, заявление, отчёт → «Согласование» (`agree`); диалог клиента (передача бота) — `/crm/messages?lead=L-NNNN`;
  свои документы — `/eds/documents?doc=<id>`, создание — `/eds/new`. Строка очереди получает «Открыть» (primary у «сегодня/просрочено»),
  уведомление и результат поиска — ссылку. Объект, к которому у роли нет действия, открывается в режиме чтения («Только
  просмотр», без формы решения); раздел, которого роли не положено, — «Нет доступа». На телефоне `panel=open` превращается в лист на весь экран (`sheet=`).
- Маршрут защищён `RequireAccess resource` по матрице; нет доступа → `Forbidden`.
- Модули загружаются лениво (`lazy`), чтобы первый экран открывался быстро на слабых ноутбуках.

## 7. Данные

- Все запросы — через хуки orval из `platform-bff.yaml`; ручных `fetch` нет.
- Ключи кэша — по ресурсу и номеру; после мутации — `invalidateQueries` очереди, счётчиков меню и объекта.
  Так же после действий над документами EDS (`useRefreshDocuments`: сохранить, отправить): отправленный документ автору больше не
  «Доработать» — строка исчезает сразу, не дожидаясь подсказки потока.
- Обновление «живых» данных (очередь, счётчики меню, колокольчик, лента «Сегодня»): поток подсказок BFF
  (`useEventStream` в каркасе, `GET /events/stream`) — по событию шины запросы перезапрашиваются сразу; опрос
  (`usePollQuery`) — запасной: 30 с и при фокусе окна, пока потока нет или он оборвался, раз в 5 минут при живом потоке;
  открытый чат — 3 с (до потока чата).
- Ошибка 401 `SESSION_EXPIRED` → экран входа с возвратом на тот же URL; 403 → `Forbidden`; 409 (устаревшая
  версия объекта) → «Объект изменился, обновите» с кнопкой.
- Оптимистичные обновления — только для чата и «прочитано»; переходы стадий — по ответу сервера.
