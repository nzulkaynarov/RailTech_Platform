# Фронтенд Платформы (`apps/platform/web`)
Статус: действует · Владелец: архитектор · Обновлено: 2026-10-28

Версия 1.0 · 2026-10-22 · Источник требований — SPEC-v3 §5–§7, §10.1; макеты — канвас v3
(<https://claude.ai/code/artifact/d82c5f3c-cb33-4914-ae86-c3b85757bea6>, страница «v3 — итоговая»).

## 1. Стек

Берём версии CRM-фронтенда (`apps/crm/frontend`), чтобы у ансамбля была одна линия Ant Design и одни приёмы.

| Что | Выбор | Примечание |
|---|---|---|
| Язык, сборка | TypeScript ~5.9, Vite 8, pnpm 10 | как CRM |
| UI | React 18.3, **antd ^5.29**, `@ant-design/icons` ^5.6, **`@ant-design/pro-components` ^2** (ProTable, ProForm, ProDescriptions, ProCard) | Pro Components — по SPEC-v3 §5.1; в CRM их нет, добавляются только в Платформу |
| Маршруты | react-router ^7 (data router) | SPEC-v3 говорит «React Router 6»; берём 7, как в CRM и Cabinet, API совместим |
| Данные | TanStack Query ^5; клиент и хуки генерирует **orval** из `packages/contracts/openapi/platform-bff.yaml` | как CRM; моки MSW генерирует тот же orval |
| UI-состояние | Zustand ^5 (панели, активная роль, язык); сохранение в `localStorage` по пользователю и маршруту, обёрнутое в try/catch | как ERP |
| Формы | ProForm (поверх antd Form) | валидация — по схемам OpenAPI |
| i18n | react-i18next, ru (по умолчанию), uz (латиница), en | словарь SPEC-v3 §2 — отдельное пространство имён `dictionary` |
| Графики | `@ant-design/plots` | только «Сводка по компании», без двойных осей и кругов |
| Тесты | Vitest + Testing Library; Playwright + `@axe-core/playwright` | как CRM |
| Refine | **не используем** | BFF уже отдаёт данные под экраны; лишний слой абстракции не нужен |

## 2. Структура кода

```
web/
  src/
    app/          main.tsx, router.tsx, providers (Query, ConfigProvider, i18n), AppShell, rbac.ts (генерируется),
                  theme.ts (из packages/ui-tokens)
    shared/
      ui/         AppShell части (ModuleRail, ModuleMenu, TopBar, ContextPanel), RequestSteps, StatusTag,
                  Consequence, EmptyState, MoneyText, DocNumber, PersonChip, SourceBanner, Forbidden
      api/        generated/ (orval: хуки, типы, MSW-моки), http.ts (CSRF-заголовок, 401 → вход), errors.ts
      i18n/       ru|uz|en: common.json, dictionary.json, по файлу на модуль
      lib/        форматирование сумм (пробелы разрядов, «сум»), дат (часовой пояс компании), номеров
    entities/     lead, client, request, project, letter, quote, contract, invoice, act, memo, chat, user, role
                  (типы-обёртки, StatusTag-карты, мелкие карточки)
    features/     create-request, resolve-letter, calc-line-approve, calc-complete, approve-quote, return-quote,
                  contract-status, confirm-payment, request-payment-doc, approve-memo, make-memo-from-message,
                  invite-employee, assign-role
    modules/      dashboard, crm, eds, erp, chats, admin — страницы, подменю, конфигурация модуля
  e2e/            сценарии Playwright по фазам (docs/history/platform/05-plan.md)
```

Правила: страница модуля знает только `features` и `entities`; `features` не импортируют друг друга; всё, что
видно больше чем в одном модуле, — в `shared`. Файл ≤ 400 строк (правило CRM).

## 4. Каркас `AppShell` — точно по макету v3

панель (поверх основного окна по умолчанию, ширина 440/600 px) выходят за модель `ProLayout`, поэтому `AppShell` собирается из
`antd Layout`, `Layout.Sider` рейла, своей колонки подменю и своего `aside` боковой панели;
внутри основного окна — `PageContainer` из Pro Components. Вид и поведение — как в SPEC-v3 §6.1.

Состояния панелей по умолчанию:
- Списки и таблицы: боковое окно закрыто, открывается кликом по строке или ссылкой с `?panel=open`.
- Карточка объекта (`:id`): на экране ≥ 1200 px открыто, пока не закрыто явно (`?panel=closed`), — **поверх**, как везде
  (решение владельца 2026-10-30, п. 2; UX-1a): рабочая область при открытии карточки не сужается. Раздел может держать окно
  закрытым и на карточке (`defaults.panelOpen: false`: журнал заказа уже на карточке; карточка расчёта — таблица на всю
  ширину, «Задание» по кнопке «Показать панель»).
- Закреплённое рядом — только выбор пользователя булавкой; булавка и ширина, как и подменю, — одни на пользователя во
  всех разделах (оболочка не зависит от раздела; в `chats` — всегда поверх), у разделов своих умолчаний нет. Помещается ли
  окно рядом, каркас считает по ширине экрана: рейл 56 + подменю 208 (если открыто) + окно 440/600 + рабочая область ≥ 760.
  «Ждут ответа»: окно поверх не закрывает поле ответа — страница берёт отступ справа из `--pf-overlay-inset` (ширина окна
  поверх или 0), ширина основного окна та же.
- Подменю: пока пользователь не выбрал — развёрнуто при `≥ 1440px`, свёрнуто при `< 1440px`; дальше — его выбор, одно
  значение на все разделы.
- Сетки карточек в две колонки считаются от ширины карточки (`@container`), а не экрана (`@media`): с окном рядом или
  подменю колонка реквизитов уходит вниз, а не сжимается до букв. Переключатели «таблица ↔ список» по ширине блока —
  `useCompactBlock` с запасом 40 px у порога.

### 4.1. Архитектурные инварианты UI/UX Оболочки (UI Guardrails для ИИ-агентов)

1. **Инвариант 1: Запрет Layout Shift для широких таблиц.**
   Боковое окно `ContextPanel` по умолчанию открывается **поверх** основного окна у правого края, без затемнения. Это
   немодальная область `complementary` (`aside`), а не `Drawer`: у `Drawer` — `aria-modal` и ловушка фокуса (axe
   `aria-allowed-attr`), а из окна Tab должен возвращаться в таблицу. Запрещено при открытии сжимать таблицы списков по
   умолчанию — это сбивает колонки и даёт горизонтальную прокрутку. Закрепление рядом (`docked`) — только по кнопке-булавке, на экране `≥ 1280px` и когда
   рабочей области остаётся `≥ 760 px`; иначе окно поверх, выбор помнится. Это касается и карточки объекта: окно само не
   закрепляется. «Рядом» и «поверх» — одна обёртка, меняется класс: булавка и переход порога не размонтируют вкладки и
   формы окна. Ширины подменю и окна не анимируются (`transition: none`; появление поверх — только `transform`). В модуле
   `chats` закрепления нет (`isStrictlyOverlay`).

2. **Инвариант 2: Чистота URL vs LocalStorage (декуплинг состояния от настроек).**
   - Открытие панели (`panelOpen`) задаёт **только** адрес: `?panel=open` или `?panel=closed`; без параметра — закрыто в
     списках и открыто на карточке объекта на ≥ 1200 px.
   - Сохранённые в `localStorage` записи открытие не меняют.
   - В `localStorage` (ключ `rt-pf-panels-v2`) сохраняются **исключительно визуальные предпочтения**: режим (`panelMode`: `overlay` | `docked`), ширина (`panelWidth`: `default` | `wide`) и свёрнутость подменю (`menuOpen`: `boolean`) — одни на пользователя, запись `<пользователь>|*` (прежние значения по разделам переносятся при чтении: выбор, сделанный чаще, при равенстве — последний); по разделу — только последняя выбранная вкладка (`lastTab`: `string`).
   - При закрытии в списке параметр `panel` удаляется из адреса, на карточке объекта — `panel=closed`.

3. **Инвариант 3: Запрет деструктивных редиректов из колокольчика.**
   Центр уведомлений открывается в правой шторке `NotificationDrawer` (420 px). Запрещено уводить пользователя на другой URL при переключении фильтров (ссылка `Все уведомления` -> `/dashboard/queue?panel=open&tab=notifications` ликвидирована). Все уведомления доступны прямо в шторке через сегменты `Непрочитанные (N)` / `Все` и селектор категорий. Пользователь никогда не теряет текущий экран и несохранённые данные при чтении уведомлений.

4. **Инвариант 4: Строгая иерархия диалогов и окон.**
   - **Inline (по месту)**: базовое редактирование, фильтры, быстрые переключатели.
   - **Slide-over Drawer (шторка)**: контекстные карточки сущностей, детальный просмотр, формы создания и редактирования сущностей (`ContextPanel`, `NotificationDrawer`, `HelpDrawer`).
   - **Modal (модальное окно 440–520 px)**: строго зарезервировано ТОЛЬКО для одношаговых подтверждений и критических действий («Отправить письмо», «Удалить запись», «Подтвердить дату»). Модальные окна обязаны содержать блок последствий `Что произойдёт` (`Consequence`).

5. **Инвариант 5: Шапка и формы не двигаются сами (UX-1b, аудит 2026-10-30, S5, S6, S13, S15).**
   - Правая группа шапки (поиск, «?», колокольчик, кнопка окна) постоянной ширины: кнопка окна — иконка 32 px без
     подписи; на разделах без окна (`/me`, `/help`, 403, 404) она `visibility: hidden` и держит место. Крошки — гибкая
     область (`flex: 1 1 0`, `min-width: 0`, многоточие). Поиск стоит на одном x во всех разделах и при открытии окна.
   - `ContextualSaveBar` не вставляется в поток при первой правке: место под него в конце формы держится всегда (бар
     невидим, `inert`), с правками бар — полоса на всю ширину формы или её карточки — прилипает к низу прокручиваемой
     области поверх контента; поле в фокусе прокручивается выше бара, а не уходит под него. Второй кнопки «Сохранить …» под
     формой с баром нет.
   - Активный пункт подменю, рейла и вкладки окна выделяется цветом и фоном, без смены `font-weight`.
   - Рабочая область и тело окна — `scrollbar-gutter: stable`: появление прокрутки не меняет ширину.

### 5.1. Формы по схеме CRM, загрузка и выгрузка (W13-A5)

- **`modules/admin/bot`** — «Настройки бота»: форма раздела строится по JSON Schema Pydantic из `GET /admin/bot/settings` (`SchemaField`, виджеты
  времени, дней недели, праздников, часового пояса, сотрудников, причин передачи); подписи — словарь `bot` (три языка, тест-сторож: каждое поле схемы
  и каждый текст бота подписан), неизвестное поле CRM не теряется — подпись берётся из схемы. Тексты бота и шаблоны правятся в боковом окне
  (`?text=`, `?template=`), раздел экрана — `?section=`; несохранённые изменения защищает `UnsavedGuard` (`shared/ui`, тот же, что в баре).
- **`modules/crm/kb`** — «База знаний»: вкладки `?view=docs|gaps|sandbox`, карточка документа и пробела и формы создания — в боковом окне
  (`?doc=`, `?gap=`, `?new=upload|manual`); формат документа, пример и промпт — из `src/generated/kb-docs` (копия `docs/kb`, `pnpm kb:sync`).
- **`shared/ui/FormParts`** — поле с подписью, ошибка словами, состояние запроса (загрузка, нет права, сбой), таблица с прокруткой для клавиатуры.
- **Файлы:** загрузка — `FormData` через сгенерированный клиент (BFF передаёт тело CRM без разбора); выгрузка CSV — `shared/api/download.ts`
  (`fetch` с cookie, ошибка BFF — `ApiError`, файл сохраняется под именем из `Content-Disposition`).
- **Тесты:** `test/botKit.tsx` (вход, рендер по адресу, учёт пропущенных ключей словаря); в `test/setup.ts` форма файла собирается в multipart вручную —
  `FormData` и `File` jsdom не понимает Node fetch.

## 6. Маршруты и состояние URL

Карта маршрутов — SPEC-v3 §6.3, без изменений. Правила реализации:

- Номер объекта в URL — бизнес-номер (`/eds/projects/ПР-2026-104`); кодирование `encodeURIComponent`; BFF
  принимает номер и сам находит внутренний id.
  Номер со «/» (`ВХ-104/26`, `КП-2026/118`) открывает карточку и без кодирования (`/eds/inbox/ВХ-104/26`): `matchSection` склеивает
  хвост пути, если он — бизнес-номер (D1-3). Письмо можно открыть и по id (UUID), и по номеру.
- Боковое окно на телефоне (< 768 px) у «Резолюции» — собственный лист на весь экран (`?sheet=resolution`) с кнопками решения внизу;
  ссылки с `panel=open` превращаются в лист (D1-3, UX P0-4). Черновик резолюции — `sessionStorage` вкладки на письмо.
- `?panel=open|closed&tab=<вкладка>` управляют боковым окном на всех экранах; фильтр списка Chats «Внутренний / Внешний» —
  `?scope=internal|external` (в SPEC-v3 §6.3 он `?tab=`; переименован, чтобы `tab` везде значил вкладку бокового окна, Q-PLT-12-3); клик по строке таблицы меняет `?<объект>=<номер>`
  и открывает объект в боковом окне без перехода.
- Строка очереди «Доработать» (`rework_document`, D1-6b) ведёт на `/eds/new?draft=<id документа>` — форму «Продолжить» D1-5: у экрана
  «Создать документ» нет боковой карточки, отдельного экрана доработки нет. Адрес должен быть исполнимым (`isActionable`), поэтому
  разделы `eds.new` и `eds.documents` — в `NATIVE_SECTIONS`, а не в мосту.
- Клиенты · Лиды и Клиенты (D1-2b): карточка — `?lead=L-2041` / `?client=42` (или путь `/crm/leads/L-2041`, `/crm/clients/42` —
  так открывают поиск ⌘K, колокольчик и очередь), форма «Создать заявку» — тот же адрес с `&create=1`; фильтры лидов —
  `?status=`, `?scope=mine|overdue`, `?channel=`, `?q=` (статус лида не `tab`: `tab` — вкладка бокового окна). На телефоне карточка
  и форма — лист на весь экран с кнопками внизу. Ключ формы заявки (`request_key`, UUID) — один на открытие формы: повтор
  после сбоя и двойной клик не создают вторую заявку.
- Хлебные крошки — из маршрута (`handle.crumb`) и названия объекта.
- **Переходы из «Моей очереди», колокольчика, поиска ⌘K и ленты «Сегодня» (D1-6).** Одна функция `modules/objectLinks.ts` (`objectLink`) приводит
  адрес объекта из BFF к полному: бизнес-номер или id в пути, `panel=open` и вкладка решения — письмо `ВХ-…` → «Резолюция» (`tab=resolution`), КП на
  одобрении → «Одобрение» (`approve`), служебка, заявление, отчёт → «Согласование» (`agree`); диалог клиента (передача бота) — `/crm/messages?lead=L-NNNN`;
  свои документы — `/eds/documents?doc=<id>`, создание — `/eds/new`. Исполнимость адреса — одна функция `isActionable` (`bridge.ts`): у раздела нет записи
  моста ⇒ строка получает «Открыть» (primary у «сегодня/просрочено»), уведомление и результат поиска — ссылку; иначе — «Где сделать» / «Где посмотреть».
  Новый настоящий экран = ключ в `NATIVE_SECTIONS` и удалённая запись `BRIDGE`. Объект, к которому у роли нет действия, открывается в режиме чтения («Только
  просмотр», без формы решения); раздел, которого роли не положено, — «Нет доступа». На телефоне `panel=open` превращается в лист на весь экран (`sheet=`).
- Маршрут защищён `RequireAccess resource` по матрице; нет доступа → `Forbidden`.
- Модули загружаются лениво (`lazy`), чтобы первый экран открывался быстро на слабых ноутбуках.

## 7. Данные

- Все запросы — через хуки orval из `platform-bff.yaml`; ручных `fetch` нет.
- Ключи кэша — по ресурсу и номеру; после мутации — `invalidateQueries` очереди, счётчиков меню и объекта.
  Так же после действий над документами EDS (`useRefreshDocuments`: сохранить, отправить): отправленный документ автору больше не
  «Доработать» — строка исчезает сразу, не дожидаясь подсказки потока.
- Обновление «живых» данных (очередь, счётчики меню, колокольчик, лента «Сегодня»): поток подсказок BFF
  (`useEventStream` в каркасе, `GET /events/stream`) — по событию шины запросы перезапрашиваются сразу; опрос
  (`usePollQuery`) — запасной: 30 с и при фокусе окна, пока потока нет или он оборвался, раз в 5 минут при живом потоке;
  открытый чат — 3 с (до потока чата).
- Ошибка 401 `SESSION_EXPIRED` → экран входа с возвратом на тот же URL; 403 → `Forbidden`; 409 (устаревшая
  версия объекта) → «Объект изменился, обновите» с кнопкой.
- Оптимистичные обновления — только для чата и «прочитано»; переходы стадий — по ответу сервера.

- Реальные `button`, `a`, `input` + `label`; `aria-label` на иконочных кнопках (тексты из макета: «Свернуть

  таб-порядок по зонам слева направо; ⌘K не перехватывает ввод в полях.

  axe без нарушений, скриншоты экранов рядом с артбордами v3 в PR (DoD SPEC-v3 §11.2 — «глазами»).
