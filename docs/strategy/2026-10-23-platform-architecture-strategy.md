## 0. Резюме

**Где мы.** Платформа выросла из двух систем, сшитых «точка-точка»: CRM и ERP зовут друг друга напрямую, события ERP
уходят одним вебхуком в один адрес, Платформа (BFF) читает внутренние API старых фронтов. Это работает, но три вещи делают
архитектуру хрупкой: (1) **данные могут потеряться** — файлы ERP не попадают в бэкап, события ERP при ошибке пропадают молча,
база восстанавливается только на сутки назад; (2) **нет шины** — подключить второго получателя событий (Платформу, 1С, банк)
нельзя без переделки, CRM вообще не публикует событий; (3) **нет правил версий** — номера в контрактах никто не проверяет,
внутренние API могут поменяться и сломать Платформу.

**Что предлагаю.** Эталоны (SAP, Salesforce, Dataverse, 1С, Odoo) сходятся в одной схеме, и её мы берём: **неприкосновенное
ядро** (CRM, EDS, ERP как доменные сервисы со своими базами), **публичные версионированные API и события** у каждого домена,
**шина** с журналом, повтором и подписками, **коннекторы** к внешним системам — снаружи ядра, каждый в своей очереди, так что
сбой 1С или банка не останавливает работу. Шина — наш интерфейс `rt_bus`: в первой версии на PostgreSQL (то, что уже
работает в ERP, обобщённое), во второй — NATS JetStream на третьем сервере, без правок бизнес-кода.

**Как двигаемся.** Восемь этапов от «надёжности сейчас» до «экосистемы мирового уровня», каждый — версия платформы с гейтом.
Ближайшие три (A — надёжность, B — шина v1 и контракты, C — EDS как сервис и роли) — это примерно 5–7 волн агентов, 3–5
недель; затем путь заявки на новой основе (D), пилот и переключение (E) — **Платформа 1.0**. Дальше — третий сервер, шина v2
и первые внешние интеграции (F), продукт для других компаний (G), экосистема (H).

**Что нужно от владельца сейчас** — §5: утвердить 12 решений (стек, шина, домены, версии, надёжность, темы, продукт) и пять
действий вне кода (CPU у хостера, внешнее хранилище бэкапов в РУз, юрист по хранению данных, потом третий сервер).

## 2. Стратегия развития

### 2.1. Принципы, которые не меняются

1. **Ядро неприкосновенно.** Внешние системы подключаются только через опубликованные API и события. Никаких прямых чтений
   чужих баз, никаких правок ядра «под 1С» (SAP Clean Core).
2. **Интеграция не останавливает бизнес.** Ядро не ждёт внешние системы: всё внешнее — асинхронно, через очередь коннектора,
   с повтором, предохранителем и ручным путём. Справочное (курс, проверка ИНН) — из кэша с пометкой «устарело».
3. **Каждый домен — один владелец своих данных.** Своя база, свои таблицы, публичный API и события. Дубли — только как
   проекции, обновляемые событиями.
4. **Контракт раньше кода, версия у каждого контракта.** Ломающее — только новым мажором и с переходным периодом.
5. **Поэтапно и через версии.** Каждый этап — версия платформы с гейтом владельца; откат возможен.
6. **Человек с ЭЦП — часть процесса.** Юридически значимые шаги (ЭСФ, договор, платёжка, ГТД) — задачи подписанту с
   напоминаниями; система не делает вид, что подписала сама.
7. **Продукт с первого дня — без лишней сложности.** «Одна компания — одна установка»; идентификатор компании (`tenant`) в
   событиях и настройках сразу, общая база на много компаний — только когда понадобится.

### 2.2. Этапы и версии

| Версия | Этап | Цель | Что получает бизнес | Гейт |
|---|---|---|---|---|
| **0.9** | **A. Надёжность сейчас** | данные не теряются, сбой одного компонента не роняет остальные | файлы и база восстановимы; события не пропадают молча | восстановление из бэкапа проверено на стенде; ни одного «тихого» пропуска событий за неделю |

| **1.x** | **F. Третий сервер, шина v2, первые внешние интеграции** | интеграции не трогают ядро; вход не зависит от CRM | ЭСФ через оператора, банковские выписки, курсы ЦБ, проверка ИНН, обмен с 1С | сбой коннектора не влияет на SLO ядра; выключение коннектора — одной кнопкой |
| **2.0** | **G. Продукт для других компаний** | развернуть платформу для новой компании за день | установка по сценарию, настройка из Admin, свои роли и шаблоны | вторая компания работает на своей установке |
| **3.0** | **H. Экосистема мирового уровня** | партнёры подключают свои коннекторы и расширения | маркетплейс коннекторов, портал разработчика, SLA | первый сторонний коннектор по публичной документации |

### 2.3. Что делать не будем (и почему)

- **Kafka, Redpanda, Debezium, ESB на Java** — память, JVM и требования к CPU несоразмерны объёмам B2B-компании (бенчмарк §3).
- **Микросервисы ради микросервисов** — три доменных сервиса плюс сервисы платформы; дальше делим только по причине (нагрузка,
  команда, изоляция отказов). Внутри домена — модульный монолит.
- **Kubernetes сейчас** — compose на нескольких VPS до этапа G; оркестратор — решение этапа G по факту.
- **Собственные модули ЭСФ «как у 1С»** — только коннектор к оператору ЭДО (ADR-0011: ЭДО вне ядра).
- **Переписывать ERP** — Django остаётся; новые сервисы — на стандартном стеке (§3.5).

### 3.4. Шина и интеграции

- **Интерфейс `rt_bus`** (библиотека Python для всех сервисов): `publish(event)` в той же транзакции, `@subscribe(type)`;
  конверт CloudEvents (`id`, `source`, `type`, `time`, `subject`, `dataschema` + `tenant`, `correlationid`, `traceparent`);
  тип — `uz.railtech.<домен>.<сущность>.<действие>.v<N>`.
- **v1 (этап B):** outbox и inbox в базе каждого сервиса; ретранслятор — периодическая задача (Procrastinate, в ERP — Celery)
  с `SKIP LOCKED`; доставка подписчикам — подписанные HTTP-вызовы (обобщение текущих вебхуков ERP→CRM, HMAC v2), у каждого
  подписчика свой повтор, журнал, DLQ и «повторить»; Платформа получает события в браузер через SSE от BFF.
- **v2 (этап F, третий сервер):** NATS JetStream одним узлом; ретрансляторы outbox публикуют в JetStream; потребители
  подписываются; PostgreSQL-outbox остаётся источником правды. Бизнес-код не меняется.
- **v3 (этап G):** кластер NATS из трёх узлов.
- **Три шаблона коннектора** (из ландшафта РУз): «API с опросом» (ЭДО, банк, ЦБ, SMS), «входящие вызовы» (Payme, Click,
  Telegram — тонкий приёмник пишет в inbox и отвечает из своей базы), «ручной адаптер» (таможня, ЕЭИСВО, ж/д — форма ввода и
  файл, в журнале шины это событие с источником `manual`). Для каждого потока — ежедневная сверка.
- **Манифест коннектора**: версия, подписки, нужные права, схема настроек, секреты, флаг включения; включение и выключение — в
  Admin · Внешние интеграции, состояние и журнал — там же.
- **Правило**: ни одного синхронного вызова внешней системы в пути пользователя, кроме справочных с таймаутом и кэшем.

волна 9 (роли) идёт сейчас ──────────────────┘
```

A — до любых новых функций (данные). B и C идут параллельно разными дорожками. D начинается, когда есть шина v1 и каркас EDS.

### 5.2. Действия вне кода

1. **Хостер — модель CPU виртуальной машины** `host-model` или `host-passthrough` для обоих VPS. Сейчас VM видит «QEMU Virtual
   CPU version 2.5+» без SSSE3, SSE4.2 и AVX; это настройка виртуализации, а не другое железо. Снимает ограничения для
   наблюдаемости, ИИ-шлюза и брокеров.
2. **Внешнее хранилище для бэкапов в Узбекистане** (S3-совместимое у местного провайдера или второй VPS у другого хостера) —
   нужно для этапа A.
3. **Юрист: хранение персональных данных граждан РУз в стране** (закон с 15.04.2021) — до продукта для других компаний и до
   отправки данных во внешние облака, включая ИИ-провайдеров.
4. **Третий сервер** — к началу этапа F (4 ядра, 8 ГБ, у того же или другого хостера, с правильной моделью CPU).
5. **Договоры и доступы для коннекторов этапа F**: оператор ЭДО (API-доступ), банк (выписки по API или DiBank), заявка в ГНК на
   услугу 708 (проверка контрагента), доступ к 1С бухгалтерии.

## 7. Карт-бланш владельца 2026-10-23 и что он меняет в плане

Решение владельца: «даю карт-бланш сносить все старые базы, уничтожить старые фронты и переделывать системы; на проде нет
работающих аккаунтов и продовых данных». Все 12 решений §5.1 считаются утверждёнными.

| Что было в плане | Что теперь |
|---|---|
| Сосуществование старых фронтов и Платформы, этапы T1–T4 (пилотная команда → только чтение → отключение) | **сосуществования нет.** `apps/crm/frontend` и `apps/erp/frontend` удаляются той же волной, в которой их экраны переезжают в Платформу (этап **C2 «Паритет Admin»** — подключения, бот, модели ИИ, база знаний, первый запуск, реквизиты, шаблоны, нумерация, сотрудники и роли). Cabinet остаётся — это фронт клиента |
| Переименование стадий, ролей и кодов под словарь SPEC-v3 — этап T5 после пилота; до этого маппинг в BFF | **сразу, в бэкендах** (этап C3 «Родной словарь»): FSM ERP — `REQUEST, RESOLUTION, CALCULATION, QUOTE, CONTRACT, PAYMENT, DONE, LOST`; статусы документов SPEC-v3 §2.4; номера SPEC-v3 §2.2 в моделях; BFF без слоя перевода |
| Перенос существующих данных (файлы ERP, коды ролей, история миграций) | **не нужен**: прод поднимается на чистых базах при первом деплое этапа 0; миграции CRM сворачиваются в одну базовую; ERP — свежие миграции под новые модели |
| Дубли CRM и ERP закрываются постепенно (проекции, события) | **удаляются**: зеркало сделок CRM как отдельная воронка, свои пароли и сброс ERP, режим `local` CRM, `KYC_PENDING`, роли «CRM Sync», второй SMTP и бренд в env ERP — в этапах 0–C |
| Expand-contract для данных прода | до версии 1.0 данные прода можно сбрасывать; правило expand-contract обязательно **с версии 1.0** (с первыми реальными пользователями); для контрактов между сервисами — с сегодняшнего дня (они меняются в одном PR с обеих сторон) |

Уточнённый порядок (заменяет §4.1 для этапов A–E):

```

Волна 9 «Роли как данные» (идёт) ──────────────┤
Этап B «Шина v1 и контракты» (волна 11) ───────┼─► C1 EDS-сервис ─► C2 Паритет Admin + удаление старых фронтов ─► C3 Родной словарь
                                               │                                     │
                                               └──────────── C4 Темы ────────────────┘
                                                                                     ▼
                                     D «Процесс шаги 1–9 на шине» (4–5 волн) ─► E «Пилот» (без сосуществования) ─► 1.0
