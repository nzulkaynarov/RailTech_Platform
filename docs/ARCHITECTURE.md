## 2. Схема

```
                         Telegram (один клиентский бот, принадлежит CRM)
                                 │ диалог                 │ Mini App
                                 ▼                        ▼
   crm.railtech.uz        ┌────────────┐        cabinet.railtech.uz
   фронт-офис, админ      │    CRM     │        ┌────────────────┐   веб-вход клиента
   ┌──────────────────────┤ FastAPI    │        │   Cabinet SPA  │◄──────────────
   │  Refine/AntD SPA     │ бот, KB,   │        │ (без бэкенда)  │
   │                      │ агенты, MCP│        └───────┬────────┘
   └──────────────────────┴─────┬──────┘                │ /api/portal/*  (Telegram initData,
                                │ события, передача      │                 magic-link)
                                │ клиента, erp-mcp       ▼
                                │                ┌──────────────────────┐   erp.railtech.uz
                                └───────────────►│         ERP          │   бэк-офис
                                  SSO-токены     │ Django · продажи ·   │◄──────────────
                                                 │ каталог · снабжение ·│   shadcn SPA
                                                 │ финансы · ИИ-задачи  │
                                                 └──────────┬───────────┘
                                                            │
        ┌───────────────── общая инфраструктура (один VPS) ─┴──────────────────────────┐
        │ Caddy (3 домена, TLS) · PostgreSQL 17 (базы crm, erp; pgvector) · Redis     │
        │ LiteLLM (шлюз моделей, алиасы, бюджеты) · Langfuse (трейсы) · RustFS (файлы)  │
        │ очереди: Procrastinate (CRM), Celery (ERP) · бэкапы pg_dump → S3             │
        └───────────────────────────────────────────────────────────────────────────────┘
```

Правила, которые делают схему устойчивой:

- **Каждая система — один главный пользователь:** CRM — фронт-офис, ERP — бэк-офис, Cabinet — клиент.
- **Общих таблиц нет.** Две базы (`crm`, `erp`) на одной инстанции PostgreSQL. Связь — API и события
  с внешними идентификаторами. Cabinet базы не имеет.
- **Один клиентский бот**, он в CRM. ERP в Telegram не пишет: события ERP приходят в CRM, бот говорит.
- **ИИ — общая инфраструктура, а не два зоопарка**: оба бэкенда ходят к моделям через LiteLLM по
  алиасам, трейсятся в Langfuse, бюджеты и ключи — в одной консоли (ADR-0020 CRM). ERP сегодня зовёт
  провайдера напрямую через SDK — переводится на шлюз.

## 3. Монорепозиторий

```
platform/                         ← имя репозитория выберет владелец
  apps/
    crm/                          ← действующая CRM (backend FastAPI + frontend Refine)
    erp/                          ← новая ERP (backend Django + frontend shadcn) — из B2B
    cabinet/                      ← новая Cabinet (frontend shadcn, без бэкенда) — из покупательской части B2B
  legacy/
    b2b/                          ← старая B2B, только чтение, удаляется после вехи M2
  packages/
    contracts/                    ← OpenAPI ERP (внутренний, портальный, интеграционный), схемы событий, схемы MCP-инструментов
    ui-tokens/                    ← общие токены дизайна (цвета, шрифты, радиусы) для AntD и shadcn
  infra/
    compose/                      ← base / dev / prod для всего ансамбля
    caddy/                        ← три домена
    ai/                           ← LiteLLM (модели по алиасам), Langfuse
    db/                           ← инициализация двух баз, бэкапы
  docs/
    strategy/ adr/ runbooks/      ← уровень ансамбля; у приложений свои docs и ADR
  CLAUDE.md                       ← карта: что где лежит, какой CLAUDE.md читать; конвенции — у приложений
  Makefile                        ← `make check` = проверки всех приложений; CI с фильтрами по путям
```

Два фронтенда остаются на разных библиотеках: CRM на Ant Design (владелец доволен), ERP и Cabinet на
shadcn (там живут билдер КП и документы). Чтобы ансамбль выглядел одной семьёй, общие токены
(`packages/ui-tokens`) задают цвета, шрифт, радиусы и плотность обеим; унификация компонентов —
не цель.

## 4. ERP: состав

**Стек:** Django + DRF + Celery + Channels из B2B. **История миграций начинается заново**: 197 старых
миграций не переносятся, приложения получают новые имена и одну начальную миграцию каждое; данные
старого прода переносятся скриптом на вехе M5. Это освобождает от названий «crm» внутри ERP и от
удалённых моделей в истории.

| Приложение ERP | Что внутри | Откуда |
|---|---|---|
| `accounts` | сотрудники (провижининг из CRM), роли бэк-офиса (`CompanyRole` → `Role` с правами `quote.*`, `contract.*`, `supply.*`, `finance.*`), 2FA, сессии, приём SSO-токена CRM | B2B `accounts`, минус KYC, подписки, операторские роли, заявки на роли, регистрация |
| `parties` | контрагенты: клиент / поставщик / субподрядчик, контакты (с `telegram_user_id`, языком), реквизиты, `crm_client_id` | B2B `Company`/`Contact`/`CompanyDocumentProfile`, минус KYC-уровни, слияние по ИНН, `CounterpartyRelationship` |
| `catalog` | товар и услуга в одной карточке; два слоя (внутренний / опубликованный) с политикой видимости `cabinet` / `on_request`; категории; импорт Excel; ИИ-обогащение по полям; полнота; ТН ВЭД как справочник | B2B `catalog` + `master_data.HSCode`, минус `EquipmentGroup`, `DomainType` ЖД, предложения поставщиков переезжают в `supply` |
| `sales` | запрос → сделка (FSM) → КП (билдер, версии, экономика, согласование, курс на дату КП) → договор → публичная страница акцепта | B2B `crm` (deals, quotes, contracts, approvals, numbering, wording, document_blocks) |
| `supply` | **новое**: поставщик, заказ поставщику (из строк заказа клиента, back-to-back, флаг дропшипа), приёмка, счёт поставщика, оплата поставщику, сроки и просрочки; субподряд как заказ со строками-этапами | B2B `SupplierOffer`, `availability.py` (ATP) как основа; остальное новое |
| `inventory` | **новое**: журнал движений (приход, отгрузка, корректировка), остаток = сумма движений, резервы под подтверждённые заказы, «доступно к обещанию» | B2B `Fulfillment` переносится сюда как отгрузка по строкам/траншам |
| `finance` | счета клиентам, платежи, акты (двусторонние), напоминания, отклонение маржи по курсу | B2B `crm/services/billing`, `invoice_lifecycle`, `deal_emails` |
| `documents` | шаблоны компании, PDF off-thread, квитанции, накладные, поиск и «недавние» | B2B `documents/`, `generated_documents`, `crm.tasks.render_document_pdf` |
| `ai` | очередь `ai`, задачи: разбор запроса, сопоставление с каталогом, черновик КП, обогащение карточки, разбор прайса поставщика, диф КП; клиент моделей — LiteLLM по алиасам; трейсы в Langfuse; evals по образцу CRM | B2B `sourcing/*ai*`, `tasks_ai.py`, минус прямой SDK |
| `portal` | **новое**: API кабинета `/api/portal/*` — только данные своей компании, вход по Telegram initData и magic-link, действия клиента (новый запрос, акцепт, подпись, приёмка) | B2B покупательские вьюхи + публичная страница КП |
| `integration` | **новое**: API для CRM (создание клиента из передачи, статусы, документы), исходящие вебхуки с подписью и журналом, `erp-mcp` для бота | — |
| `core` | настройки, аудит, идемпотентность, оптимистичные блокировки, валидаторы загрузок, health | B2B `core` |

**Домены-словари** (Rule 1 B2B сохраняется): стадии, статусы, виды документов сеются миграциями.

## 5. Cabinet: состав

- Отдельный SPA (`apps/cabinet`), домен `cabinet.railtech.uz`, тот же домен — Mini App в BotFather.
- Вход: Telegram `initData` (подпись токеном бота CRM; ERP только проверяет), magic-link по e-mail,
  необязательный пароль. Регистрации «с улицы» нет: первый вход по приглашению из передачи CRM.
- Экраны: запросы (и «Новый запрос»), КП (принять / отклонить), договоры (подписать), счета, акты
  (принять / вернуть), поставки по строкам со статусами, документы, компания и команда, опубликованный
  каталог с ценами и наличием (решение владельца: только здесь).
- Кнопка «Написать менеджеру» → бот с контекстом сделки. Позже — веб-виджет того же агента CRM
  (новый канал в CRM, SPEC §15).
- Что переезжает из B2B: покупательские страницы (`MyRequestsPage`, `QuotesPage`, `ContractsPage`,
  `InvoicesPage`, `ActsPage`, `FulfillmentsPage`, `CompanyFilesPage`, `SettingsPage` в части профиля
  и команды), публичная страница акцепта, адаптивная таблица КП для телефона.

## 7. Администратор

Не четвёртая система, а роль с одним входом и переключателем. Администрирование делится по принципу
«настраивается там, где живут данные»:

| Где | Что настраивает администратор | Уже есть |
|---|---|---|
| CRM → Администрирование | пользователи и роли **всех** платформ, доступы, бот, тексты, правила квалификации и передачи, KB, модели ИИ и бюджеты, ключи, коннекторы (Telegram, ERP, почта), бэкапы, аудит, состояние системы (включая здоровье ERP), **центр внешних сервисов ансамбля** — статус, ошибки, метрики, выключатели и оповещения по всем внешним интеграциям CRM и ERP (ORCHESTRATOR §3.13, M3-CRM-12) | да (ADR-0018, ADR-0020); центр — M3-CRM-12 |
| ERP → Настройки | реквизиты компании, шаблоны документов и нумерация, роли бэк-офиса, политики каталога (видимость цен, порог публикации), политика курса, правила уведомлений клиенту о сдвигах, справочники | частично (Settings Hub B2B) |
| Cabinet | ничего: отражает ERP | — |

Роль «Администратор» в CRM = суперпользователь ERP; инвариант «≥ 1 активный администратор» остаётся
в CRM как в источнике истины по людям. Инженерная админка Django в ERP остаётся инженерам (ADR-0001
B2B), бизнес-настройки — в SPA.

## 8. ИИ во всех трёх

| Система | Агенты и задачи | Инфраструктура |
|---|---|---|
| CRM | диалоговый агент, квалификатор, ИИ-черновик менеджеру, судья качества (есть) | LiteLLM, Langfuse, бюджеты, evals, MCP (есть) |
| ERP | разбор запроса в строки; сопоставление с каталогом; черновик КП; обогащение карточки; **разбор прайса поставщика** (Excel/PDF → предложения); **подсказка поставщика и срока** по истории; **объяснение отклонения маржи**; ассистент бэк-офиса над сделкой («что по этой сделке задерживается?») через `erp-mcp` | очередь `ai`, клиент → LiteLLM по алиасам `intake/match/draft/enrich-model` своим ключом с бюджетом на день, трейсы → Langfuse колбэком ключа в шлюзе, evals по образцу CRM (M1-ERP-06) |
| Cabinet | своего ИИ нет: вопросы клиента — бот CRM (Mini App рядом) и позже веб-виджет того же агента | — |

**Затраты на ИИ** — один дашборд на ансамбль в консоли админа CRM (страница «Расходы»): LiteLLM
тегирует каждый вызов системой, функцией и моделью; бюджеты на день — по системе; это и есть «биллинг»
в терминах владельца (решение 2026-10-13). Теги — в теле запроса `metadata.tags`: `system=crm|erp`,
`feature=<функция>`, `model=<алиас>`; CRM читает журнал LiteLLM `GET /spend/logs/v2` напрямую (без
эндпоинта расходов в ERP), бюджет ERP — `settings.budget.erp_daily_usd` в CRM (M3-CRM-09). Принципы CRM распространяются на ERP: код решает, модель предлагает; идентификаторы компании никогда
не приходят от модели; промпты в файлах с версией по хэшу; платные прогоны только с согласия.

## 9. Единый вход и роли

| Субъект | Где входит | Как | Роли |
|---|---|---|---|
| Сотрудник | CRM (пароль, временный при создании) | CRM выдаёт сессию; переход в ERP — токен-передача на 60 с, ERP обменивает на свою сессию; обратно так же | CRM: admin / manager / viewer; ERP: роли бэк-офиса с правами; `platform_access` в CRM решает, что показывать в переключателе |
| Клиент | Cabinet | Telegram initData или magic-link | контакт компании-клиента; права «смотреть / действовать» на уровне компании |
| Администратор | CRM | как сотрудник | admin в CRM = суперпользователь ERP |

Отзыв доступа в CRM отзывает сессии в ERP. Клиенты в CRM и ERP не входят никогда.

## 10. Домены, инфраструктура, деплой

- Два VPS с внутренней сетью (решение владельца 2026-10-13; раскладка — `docs/runbooks/servers.md`):
  **VPS 1 `app`** (`176.101.56.141`, 4 vCPU, 8 ГБ, NVMe 120 ГБ) — `crm.`, `erp.`, `cabinet.railtech.uz` через
  Caddy (конфиг из репозитория), оба бэкенда с воркерами, LiteLLM, RustFS, Redis; Langfuse и docling — профилями
  по очереди (вместе в 8 ГБ не помещаются). **VPS 2 `db`** (`170.168.6.209`, 2 vCPU, 2 ГБ, NVMe 40 ГБ) —
  PostgreSQL 17 с базами `crm` (pgvector), `erp`, `litellm`, `langfuse`, слушает только внутренний IP; бэкапы
  `pg_dump` ежедневно в RustFS на VPS 1 и еженедельно во внешнее хранилище. Mini App в BotFather указывает на
  `cabinet.railtech.uz`. Бренд компании в доменах — нормально; продукт внутри нейтрален: имя и логотип — настройки.
- Один PostgreSQL 17 (VPS 2) с базами `crm` и `erp`; один Redis (раздельные БД); один RustFS с бакетами CRM и `erp`
  (факт M0-INF-03: CRM хранит файлы в своих трёх бакетах `kb-sources`, `client-documents`, `tg-attachments` —
  переименование в один бакет потребовало бы правок кода CRM и отложено); LiteLLM и Langfuse — общие.
- Деплой: один workflow на ансамбль с фильтрами по путям; образы в GHCR; на VPS 1 — `pull` + `up`, миграции ERP и
  CRM после pg_dump-гейта (как в B2B); CI — GitHub-hosted после разблокировки биллинга (QUESTIONS Q-10).

## 11. Биллинг — три разных вопроса

| Что имеется в виду | Ответ |
|---|---|
| **Счета клиентам и оплаты** | остаются в ERP → `finance`: счёт из договора по политике (предоплата / по факту / по этапам), напоминания, фиксация оплаты; интеграция с платёжным провайдером (Click / Payme) — позже, отдельным решением; акты двусторонние |
| **Подписки и права платформы** (бывшие entitlements B2B: кто за что платит в продукте) | **в этой фазе не нужны**: ансамбль обслуживает одну компанию, продавец один, монетизировать нечего. Если ансамбль станет продуктом для других компаний — рекомендуемая модель «один арендатор — одно развёртывание» (своя инстанция на компанию), и тогда биллинг — вопрос эксплуатации и договора, а не кода. Многоарендность внутри одной базы не возвращаем |
| **Биллинг GitHub Actions** (CI мёртв у B2B) | CI нужен ансамблю. Варианты: оплатить минуты; или self-hosted runner для CI на отдельной машине (на прод-VPS нельзя: память); `make ci-local` остаётся запасным протоколом |

Если под биллингом имелось в виду что-то четвёртое — уточните, допишу.

## 17. Все входы клиента (уточнение 2026-10-13)

Принцип один: **любой новый человек — это лид в CRM, любой известный клиент — приглашение в Cabinet.**
Саморегистрации в ERP нет: привязку человека к компании подтверждает сотрудник (тот же инвариант, что
защищает документы в боте). Так устроен портал Odoo: доступ выдаётся приглашением, а не «зарегистрируйтесь».

| Вход | Что видит человек | Что происходит | Кто владеет |
|---|---|---|---|
| **Telegram** (как сегодня) | бот | лид в CRM, квалификация, передача | фронт-офис |
| **Сайт → `cabinet.railtech.uz`**, аккаунта нет | страница входа с двумя путями: «Войти» (e-mail / Telegram) и «Я новый клиент» | форма «Запрос» (имя, компания, телефон, e-mail, что нужно, согласие на обработку ПДн; вложений нет — файлы после приглашения, Q-12) → **лид в CRM с источником `web`**; рядом кнопка «Написать в Telegram» → бот с меткой `web` | фронт-офис |
| **Звонок** | — | менеджер создаёт лида **вручную** в CRM (источник `phone`), заполняет компанию и контакты, дальше обычный путь; если звонит известный клиент — из его карточки «Новый запрос» → заявка в ERP | фронт-офис / бэк-офис |
| **Известный клиент без запроса** (например, по договорённости на встрече) | письмо или сообщение в Telegram с приглашением | бэк-офис в ERP создаёт компанию и контакт → «Пригласить в кабинет» → magic-link на e-mail и/или в Telegram, если идентичность известна; то же доступно из CRM через «Передать в бэк-офис» без заявки | бэк-офис |
| **Клиент из Cabinet** | «Новый запрос» | заявка в ERP, минуя CRM; CRM получает событие для ленты | бэк-офис |

Следствия:

- **CRM получает второй и третий источники лидов** — веб-форма и ручное создание (телефон, почта,
  рекомендация) — при том же жизненном цикле. Это изменение границы BUSINESS.md §7 («только Telegram
  в первой версии»), фиксируется там же. Лид с телефоном, позже написавший в бот и поделившийся
  номером, **склеивается** с ручным лидом по номеру.
- **Веб-онбординг — это не регистрация, а запрос.** Полноценный веб-онбординг появится, когда CRM
  получит веб-канал агента (виджет чата на сайте и в Cabinet, SPEC §15): тогда посетитель сайта
  разговаривает с тем же ассистентом, что и в Telegram. До этого — форма.
- **Кабинет создаётся тремя способами**: передачей из CRM, вручную в ERP, самим клиентом из Mini App
  после подтверждённой идентичности. Приглашение уходит по e-mail и/или в Telegram; у контакта есть
  «предпочитаемый канал».

## 18. E-mail: пересмотр

Сегодня: в CRM SMTP нет по решению Q-010 (пользователей создаёт админ с временным паролем, клиенту
пишет бот). В B2B — полноценный движок: три канала (транзакционный / маркетинговый / системный) с
отдельными SMTP, 20 шаблонов, журнал `EmailLog`, предпросмотр. Пересматриваю так:

| Вид почты | Где живёт | Что это |
|---|---|---|
| **Транзакционная клиенту** | ERP (`notifications`, из B2B) | приглашение в кабинет, КП отправлено, счёт выставлен, напоминание о просрочке, акт ждёт подтверждения, код акцепта, сдвиг срока поставки. Шаблоны компании, журнал, предпросмотр — уже есть |
| **Транзакционная сотруднику** | CRM (новый коннектор «Почта» в консоли админа, ADR-0018) и ERP | приглашение сотрудника, сброс пароля, 2FA-уведомления; CRM остаётся самодостаточной (не ходит в ERP за письмом) |
| **Дублирование бота** | политика контакта «предпочитаемый канал»: Telegram / e-mail / оба | клиент без Telegram получает всё по почте; с Telegram — в боте, а по почте только документы (КП, счёт, акт) |
| **Рассылки** (маркетинг) | **не строим свой инструмент** | сегменты и экспорт контактов из CRM (согласие на рассылку — отдельный флаг, не согласие на обработку); отправка через внешний сервис рассылок; канал `marketing` в ERP остаётся зарезервированным |
| **Входящая почта** (лид пишет на info@) | позже | канал CRM по образцу веб-формы; не в первой волне |

Инфраструктура: не свой почтовый сервер, а SMTP-релей транзакционного провайдера; на стороне владельца —
домен отправки, SPF, DKIM, DMARC (в B2B это уже было задачей `post-deploy`). Один набор SMTP-настроек
на ансамбль, хранится в консоли админа CRM и выдаётся ERP как секрет окружения.
