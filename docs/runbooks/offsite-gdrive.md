# Runbook: внешняя копия бэкапов — Яндекс Диск компании и Google Drive (OPS-GDRIVE, OPS-YADISK)
Статус: действует · Владелец: архитектор · Обновлено: 2026-10-31

Основание: решение владельца 2026-10-28 — внешняя копия бэкапов прода хранится вне наших серверов (закрывает «копию вне площадки»
ADR-0017 п. 2 для архива базы); юрист владельца одобрил 2026-10-28 хранение на Google Drive. **Решение владельца 2026-10-31
(OPS-YADISK):** основной провайдер — **Яндекс Диск компании** (Яндекс 360 уже используется для почты) через пароль приложения типа
«Файлы», который админ вводит в интерфейсе. Google Drive сервисным аккаунтом работает только с общим диском Google Workspace: на
личном Google копия падала с `storageQuotaExceeded` («Service Accounts do not have storage quota», прод 2026-10-29). Google Drive
остаётся вторым провайдером (выбор — в той же форме). Юристу — подтвердить одной фразой хранение копий на Яндекс Диске
(`docs/OWNER-CHECKLIST.md`). Архив WAL-G и восстановление на момент времени — [`backup-pitr.md`](backup-pitr.md); деплой —
[`deploy.md`](deploy.md). Имя файла runbook'а осталось прежним, чтобы не ломать ссылки.

## Как устроено

```
VPS 2 (db)                         VPS 1 (app)                                         Яндекс Диск (WebDAV) или Google Drive
┌──────────────────────┐ wal-push ┌───────────────────────────────────────────┐        ┌───────────────────────────────────┐
│ postgres + WAL-G     ├─────────►│ rustfs: бакет wal/pg17 (14 суток)         │ rclone │ RailTech-backups/prod/ (Яндекс)   │
│ walg: копия 21:00 UTC│          │ offsite-backup (rclone 1.75.2, 128 МБ):   ├───────►│ или папка общего диска (Google):  │
└──────────────────────┘          │   раз в сутки 23:00 UTC, полоса 2 МиБ/с   │ copy   │   pg17/basebackups_005/           │
                                  │   итог → бакет offsite/status.json        │        │   pg17/wal_005/                   │
                                  │ CRM: читает только status.json ──► строка «Внешняя копия бэкапов»                           │
                                  └───────────────────────────────────────────┘        └───────────────────────────────────┘
```

| Что | Значение |
|---|---|
| Что копируется | Базовые копии WAL-G за `OFFSITE_KEEP_DAYS` (14) суток, копия, покрывающая границу срока, и **весь WAL с её начала** + файлы истории веток. С такой папки восстанавливаются на любой момент окна |
| Куда | **Яндекс Диск** (рекомендуется): WebDAV `https://webdav.yandex.ru`, логин — адрес почты Яндекс 360, пароль приложения типа «Файлы», папка по умолчанию `RailTech-backups/<окружение>` (на проде `RailTech-backups/prod`; нет — создаётся). **Google Drive**: папка общего диска Google Workspace, сервисный аккаунт. Провайдер выбирается в интерфейсе; `OFFSITE_PROVIDER` в `.env.prod` (аварийно) сильнее интерфейса |
| Как | `rclone copy` (не `sync`): исчезновение объектов в RustFS (сбой, ошибка, злоумышленник) не стирает копию. Срок хранения на Диске — свой, по базовым копиям самой папки: всё старше копии, покрывающей границу, удаляется — у Google в корзину общего диска (содержимое удаляется через 30 дней), у Яндекса в Корзину Диска (**она занимает место**: проверьте её очистку, если строка пишет про место). Яндекс WebDAV не сохраняет время файлов: на Диске время — момент выгрузки, поэтому «с ДД.ММ» в строке у Яндекса — дата выгрузки самой ранней копии, а срок хранения считается от неё (удаляется чуть позже, не раньше) |
| Когда | Ежедневно в `OFFSITE_AT_UTC` (23:00 UTC = 04:00 Ташкент, через 2 ч после базовой копии); сразу при старте, если успешной копии не было больше суток; после сбоя — повтор через 30 мин; «не настроено» — проверка раз в 10 мин |
| Сеть | `--bwlimit 2M` (2 МиБ/с ≈ 7 ГБ/ч, `OFFSITE_BWLIMIT`), 2 передачи, не больше 5 запросов в секунду, повторы операции (3 × 30 с) и запросов (10), тайм-ауты 5 мин; одна копия — не дольше 6 ч (остаток — следующей попыткой). Яндекс местами ограничивает скорость WebDAV: средняя скорость выгрузки — в событии журнала `offsite_sync_finished` (`avg_speed`, `avg_bytes_per_s`, `copied_bytes`, `copy_seconds`) и в строке «Внешняя копия бэкапов» («средняя скорость …») |
| Квота | `OFFSITE_MAX_GB` (100 ГБ): выборка больше — не выгружается (строка — «сбой», кто исправляет — владелец); от 80 % — предупреждение. Ориентир: 15 базовых копий (сжатый размер базы, на пилоте < 3 ГБ каждая) + WAL за 14 суток |
| Шифрование | Объекты уже зашифрованы WAL-G (libsodium, `WAL_ENC_KEY`). Ключа нет ни на VPS 1, ни на Drive — только на VPS 2 и офлайн. Открыто лежат лишь метаданные копий (`*_backup_stop_sentinel.json`, `metadata.json`: время, LSN, размеры, имя хоста) |
| Пароль Яндекса | Пароль приложения типа «Файлы» (Яндекс ID → Безопасность → Пароли приложений). **Вводится в интерфейсе** (раздел 1): CRM хранит его зашифрованным (`integration_secrets`, `offsite_yandex_password`, только на запись — в ответах логин и «задан», последних символов нет ни в ответах, ни в базе), смена — в журнале действий без значений. Сервису копирования доставляется через бакет `offsite-config` (объект `yandex-password`); сервис сразу пропускает его через `rclone obscure` — в томе состояния лежит только obscure-форма (chmod 600), в журнал и `status.json` не попадают ни пароль, ни логин |
| Ключ Google | Сервисный аккаунт Google Workspace с ролью «Менеджер контента» только в одной папке общего диска. **Загружается в интерфейсе** (раздел 1): CRM хранит его зашифрованным (`integration_secrets`, только на запись — в ответах адрес аккаунта и последние 4 символа ID ключа), смена — в журнале действий, права — `admin: full`. Сервису копирования ключ и ID папки доставляются через бакет `offsite-config` (ниже). Аварийный путь — файл `/opt/rt/secrets/gdrive-sa.json` на VPS 1 (chmod 600, каталог создаёт `deploy.sh`) и `OFFSITE_GDRIVE_FOLDER_ID`: если заданы, они сильнее настройки из интерфейса. В репозитории ключа нет |
| Доставка настройки сервису | Бакет `offsite-config` RustFS (`settings.json` — провайдер и несекретное, плюс `yandex-password` или `gdrive-sa.json`): у ключа `crm` там только запись (`PutObject` — прочитать и перечислить обратно не может), у `offsite` — только чтение. Сервис раз в минуту сверяет список объектов и после смены сразу копирует; копия ключа в томе состояния — chmod 600. Выбрано вместо «offsite забирает ключ по внутреннему адресу CRM служебным токеном»: не нужен новый вход в CRM и новый секрет, ключ не идёт открытым текстом по HTTP, права проверяет `s3-init` при каждом деплое матрицей доступа. Плата — ключ лежит в RustFS незашифрованным (как и сами файлы бакетов); читать его может только `offsite` и корневой ключ RustFS |
| Права S3 | Свой ключ `S3_OFFSITE_*` (создаёт деплой, `make-env-prod.sh ensure-secrets`): чтение бакетов `wal` и `offsite-config`, запись только в бакет `offsite`. CRM — только список бакета `offsite` и чтение одного объекта `offsite/status.json` (политика по объекту, как `crm-probe` в Redis), больше ничего о копии не знает |
| Код | `infra/offsite/offsite-sync.sh` (сервис `offsite-backup`, `infra/compose/prod.yml`; до OPS-YADISK — `gdrive-sync.sh`), `infra/deploy/offsite-check.sh` (аварийный путь Google: ключ на сервере), настройка в интерфейсе — CRM `services/offsite_connector.py` (проверки — `integrations/yadisk.py`, `integrations/gdrive.py`), Платформа `OffsitePanel.tsx`, `infra/db/restore-from-offsite.sh` (восстановление и учения, оба провайдера) |

**Модель угроз:** при компрометации VPS 1 копию на Диске защищает только корзина (Google — 30 дней, Яндекс — Корзина Диска): у сервиса
есть право записи и удаления в папке (у Яндекса пароль «Файлы» даёт доступ ко всему Диску аккаунта — поэтому для копий лучше
отдельный аккаунт Яндекс 360 без других файлов), он может удалить и испортить объекты; прочитать данные не может (ключа `WAL_ENC_KEY`
на VPS 1 нет).

**Почему без второго слоя шифрования (rclone crypt).** Содержимое и так зашифровано WAL-G ключом, которого нет ни у Google, ни на
сервере приложений. Второй слой дал бы ещё один ключ, без которого копия бесполезна (его тоже хранить офлайн и не потерять), и
непрозрачные имена на Drive — при том что раскрывает он только метаданные копий. Решение исполнителя OPS-GDRIVE; пересмотреть, если
на Drive начнут класть незашифрованное (например, файлы бакетов RustFS — B-OPSG-1).

## 1. Включение — в интерфейсе, без сервера (основной путь)

Платформа → Admin → Подключения → карточка «Хранилище» → блок **«Внешняя копия бэкапов»** → «Настроить» (или «Изменить
подключение»). В форме — выбор: **«Яндекс Диск (рекомендуется)»** или **«Google Drive (общий диск Workspace)»**. На сервер заходить
не нужно; нужен вход в Платформу с правом `admin: full`.

### Яндекс Диск (≈ 3 минуты)

1. Войти в Яндекс ID аккаунта Яндекс 360, на Диске которого будут лежать копии (лучше отдельный ящик вроде `backup@<домен компании>`).
2. Яндекс ID → **Безопасность → Пароли приложений** (<https://id.yandex.ru/security/app-passwords>).
3. Создать пароль приложения типа **«Файлы»** (доступ к Диску по WebDAV), назвать, например, «RailTech бэкапы». Пароль показывается
   один раз — скопировать. Раздела нет или пароль не создаётся — администратор Яндекс 360 запретил пароли приложений или доступ к
   Диску по протоколам: разрешить в админке Яндекс 360 (Безопасность).
4. В форме: адрес почты этого аккаунта, папка (по умолчанию `RailTech-backups/prod`, можно оставить), пароль приложения, свой пароль
   администратора → **«Сохранить и проверить»**.

Проверка сразу после сохранения: вход по WebDAV, папка (нет — создаётся по цепочке), запись и удаление маленького проверочного файла.
Итог словами: «Доступ есть: папка … на Яндекс Диске» или причина:

| Причина | Что сделать |
|---|---|
| Яндекс не принял логин или пароль приложения | проверить адрес почты; пароль создан именно для «Файлов» и не удалён — создать новый (шаг 3) и сохранить |
| Похоже, введён обычный пароль аккаунта | нужен пароль приложения «Файлы» (16 латинских букв) — шаги 2–3 |
| Яндекс закрыл доступ к Диску по WebDAV | администратор Яндекс 360 запретил доступ к Диску по протоколам или у аккаунта нет Диска — разрешить в админке 360 |
| На Яндекс Диске нет места | освободить место, очистить Корзину Диска или расширить тариф |
| По пути — файл, а не папка | указать другой путь |
| Яндекс Диск не ответил | сеть сервера (хостинг); повторить «Проверить» позже |

После сохранения пароль больше не показывается (видно только «Пароль приложения: ••••» — «задан»); логин, папка и пароль сразу
уходят сервису копирования, первая копия начинается в течение пары минут. Сменить пароль или папку — «Изменить подключение» (пустое
поле пароля — остаётся прежний). Каждая смена — в журнале действий.

### Google Drive (только общий диск Google Workspace, ≈ 20 минут)

**Нужен общий диск Google Workspace. Личный Google Drive не подходит:** у сервисного аккаунта нет своего места, копия упадёт с
`storageQuotaExceeded` (так было на проде 2026-10-29). Нужны права администратора Google Workspace (или его помощь в шагах 2 и 3).
В форме выбрать «Google Drive (общий диск Workspace)» — там четыре шага подготовки со ссылками на консоль Google:

1. **Общий диск и папка.** В Google Drive: «Общие диски» → «Создать» (например, «RailTech — бэкапы»; можно существующий) → внутри
   «Создать» → «Папка» (например, `rt-platform-offsite`). В «Моём диске» папка **не годится**: у сервисного аккаунта нет своего места.
2. **Проект и Google Drive API.** <https://console.cloud.google.com/apis/library/drive.googleapis.com> под корпоративной учётной
   записью → выбрать или создать проект (например, `rt-backups`) → «Enable».
3. **Сервисный аккаунт и ключ JSON.** <https://console.cloud.google.com/iam-admin/serviceaccounts> → «Create service account»: имя
   `rt-offsite-backup`, роли проекта **не** нужны → «Done» → открыть аккаунт → «Keys» → «Add key» → «Create new key» → JSON → файл
   скачается. Кнопка недоступна — политика организации `iam.disableServiceAccountKeyCreation`: администратор Workspace разрешает
   создание ключей для этого проекта.
4. **Доступ к папке.** В Drive на папке из шага 1 → «Открыть доступ» → адрес сервисного аккаунта → роль **«Менеджер контента»** →
   снять «Уведомить». Не даёт добавить адрес вне организации — администратор разрешает в настройках общего диска доступ
   пользователям вне организации.

Затем в форме: выбрать скачанный файл ключа (форма покажет адрес аккаунта из файла), вставить ID папки или её адрес целиком, ввести
свой пароль администратора → **«Сохранить и проверить»**. Ключ хранится зашифрованным и больше не показывается (только адрес
аккаунта и `•••• <последние 4 символа ID ключа>`); проверка у Google показывает итог словами: «Доступ есть: папка … на общем диске»
или что исправить (ключ отозван, не включён Drive API, папка не найдена, папка в «Моём диске», нет роли «Менеджер контента»).
Сменить ключ или папку — «Изменить подключение» (файл можно не выбирать — останется прежний ключ).

### Переключение провайдера

Выбор в форме и «Сохранить и проверить»: настройки обоих провайдеров хранятся, копирует сервис только на выбранный. Прежняя копия
на другом Диске не удаляется — убрать её руками, когда новая копия станет «В порядке». Старая настройка Google Drive (до OPS-YADISK)
продолжает работать без миграции: пока провайдер не выбран, настроенный Google Drive остаётся Google Drive.

**Как понять, что всё работает:** в том же блоке «Состояние копии» — «Работает: Копия на Яндекс Диске (или Google Drive) обновлена
N ч назад: X ГБ, базовых копий K (с ДД.ММ), средняя скорость …»; та же строка «Внешняя копия бэкапов» — в списке сервисов. В папке на
Диске — каталог `pg17` с `basebackups_005/` и `wal_005/`.

## 1а. Аварийный путь Google Drive: ключ на сервер (если интерфейс недоступен)

Для Яндекс Диска аварийного пути через файлы на сервере нет: пароль вводится только в интерфейсе. Выбор провайдера можно
принудительно задать на сервере: `OFFSITE_PROVIDER=yandex|gdrive` в `/opt/rt/.env.prod` (сильнее интерфейса; пусто — как в
интерфейсе), затем деплой или `docker compose … up -d --force-recreate offsite-backup`.

Шаги Google 1–4 выше, затем на сервере. Файл и переменная, если заданы, **сильнее** настройки из интерфейса — после возврата к интерфейсу
уберите их (`rm /opt/rt/secrets/gdrive-sa.json`, пустой `OFFSITE_GDRIVE_FOLDER_ID`, затем `offsite-check.sh` или деплой).

1. **ID папки.** Открыть папку в браузере: адрес `https://drive.google.com/drive/folders/<ID>` — нужна только часть `<ID>`
   (без `?usp=…`).
2. **Ключ на сервер** (со своего компьютера; `/opt/rt/secrets` создаёт деплой, до первого деплоя с OPS-GDRIVE — `mkdir -m 700`):

   ```bash
   scp ~/Downloads/<скачанный-файл>.json deploy@<VPS 1>:/opt/rt/secrets/gdrive-sa.json
   ssh deploy@<VPS 1> 'chmod 600 /opt/rt/secrets/gdrive-sa.json'
   rm ~/Downloads/<скачанный-файл>.json      # копия не нужна: ключ всегда можно выпустить новый (раздел 5)
   ```
3. **ID папки в `.env.prod`** (на VPS 1, от `deploy`; переменная может отсутствовать в старом файле — команда добавит):

   ```bash
   f=/opt/rt/.env.prod; id='<ID из шага 1>'
   grep -q '^OFFSITE_GDRIVE_FOLDER_ID=' $f && sed -i "s|^OFFSITE_GDRIVE_FOLDER_ID=.*|OFFSITE_GDRIVE_FOLDER_ID=$id|" $f \
     || echo "OFFSITE_GDRIVE_FOLDER_ID=$id" >> $f
   ```
4. **Включить и проверить:** `/opt/rt/current/infra/deploy/offsite-check.sh` — проверяет ключ (chmod, владелец, что это ключ
   сервисного аккаунта; печатает адрес аккаунта — сверить с шагом 4 раздела 1) и ID папки, пересоздаёт сервис `offsite-backup` и сразу копирует.
   Первая выгрузка — весь архив за 14 суток: при 2 МиБ/с ≈ 7 ГБ в час. Итог печатается JSON-ом (`"result":"ok"`).

Проверка — как в разделе 1; на сервере: `docker compose … logs offsite-backup | grep offsite_sync_finished` (итог и средняя скорость).

## 2. Что видно в «Состоянии системы»

Строка «Внешняя копия бэкапов» (группа «Ансамбль», карточка «Хранилище»), проверка раз в минуту — чтение `status.json` из бакета
`offsite`. Политика оповещений общая (H3): непрерывный сбой 15 минут — одно «Сломано», 5 минут нормы — «Восстановлено».

| Состояние | Когда | Кто исправляет |
|---|---|---|
| В порядке | последняя успешная копия моложе 26 ч | — |
| Внимание | копия заняла ≥ 80 % `OFFSITE_MAX_GB` | владелец: место на Диске или `OFFSITE_MAX_GB` |
| Сбой | последняя попытка с ошибкой **или** успешной копии нет дольше 26 ч (сервис остановлен или завис) | по причине — таблица раздела 3 |
| Не настроено | провайдер не выбран; Яндекс — нет логина, пароля или папки; Google — нет ключа, ключ не того типа, нет ID папки; или сервис ещё ни разу не отметился | владелец: шаги раздела 1. Текст строки называет, чего не хватает. На стенде — серое «ожидаемо» |
| Не проверено | CRM не прочитала `status.json` (нет бакета `offsite` или прав) | хостинг: деплой (`s3-init` применяет политику `crm`) |

## 3. Диагностика

Причина — поле `reason` в `status.json` (`docker compose … exec offsite-backup cat /state/status.json`), подробности — журнал
`docker compose … logs offsite-backup` (JSON-строки `offsite_*` и хвост журнала rclone; ID папки и логин в журнале скрыты, пароля
там нет). Проверка связи и доступа без копирования: `docker compose … exec offsite-backup sh /offsite/offsite-sync.sh --probe` (папка
на Диске и бакет `wal`). Поле `provider` в `status.json` — куда шла копия. Медленная выгрузка — `logs offsite-backup | grep
offsite_sync_finished`: `avg_speed` заметно ниже `OFFSITE_BWLIMIT` — Яндекс ограничивает WebDAV; копия продолжится следующей попыткой
(`timeout`), при постоянной нехватке — поднять `OFFSITE_KEEP_DAYS` нельзя, а выгрузку растянуть: `OFFSITE_RUN_TIMEOUT_S` (хостинг).

| `reason` | Что значит | Что делать |
|---|---|---|
| `no_config`, `bad_provider` | провайдер не выбран (или `OFFSITE_PROVIDER` не `yandex`/`gdrive`) | раздел 1: «Настроить» в блоке «Внешняя копия бэкапов» |
| `no_login`, `no_password`, `no_folder` (Яндекс) | не настроено | раздел 1, Яндекс Диск: логин, пароль приложения, папка |
| `no_key`, `bad_key`, `no_folder` (Google) | не настроено | раздел 1, Google Drive: ключ, папка |
| `access` (Яндекс) | WebDAV ответил 401 или 403: логин или пароль приложения не приняты (удалён, не «Файлы»), доступ к Диску по WebDAV закрыт администратором Яндекс 360 | «Проверить» назовёт причину; новый пароль приложения — «Изменить подключение» |
| `access` (Google) | Drive отказал: ключ отозван или удалён, у аккаунта нет роли в папке, неверный ID папки | «Проверить» в блоке «Внешняя копия бэкапов» назовёт причину; шаг 4 раздела 1 (роль «Менеджер контента»), ID папки — «Изменить подключение», отозванный ключ — раздел 5. Если ID верен, а Drive отвечает «File not found» — указать ещё и ID общего диска: `OFFSITE_GDRIVE_SHARED_DRIVE_ID` (адрес общего диска `…/drive/folders/<ID>` в корне) |
| `not_shared_drive` | Google: папка в «Моём диске» или личный Google без Workspace (`storageQuotaExceeded`, «Service Accounts do not have storage quota») | общий диск Workspace (шаг 1) — или перейти на Яндекс Диск (раздел 1) |
| `quota` | выборка больше `OFFSITE_MAX_GB` или кончилось место на Диске (Яндекс — 507 Insufficient Storage, в том числе из-за Корзины) | освободить место на Диске (очистить Корзину Яндекс Диска) или поднять `OFFSITE_MAX_GB` (переменная сервера — хостинг) |
| `network` | нет связи с Диском (или он ограничил частоту запросов) | хостинг: сеть VPS 1 наружу (`webdav.yandex.ru:443` или Google); повтор сам через 30 мин |
| `timeout` | копия не уложилась в 6 ч (первая выгрузка большого архива) | ничего: следующая попытка продолжит с места остановки. Часто повторяется — поднять `OFFSITE_BWLIMIT` |
| `source` | не прочитан бакет `wal` RustFS | хостинг: `rustfs` жив? политика `offsite` применена (журнал `s3-init` последнего деплоя) |
| `source_empty` | в бакете `wal` нет базовых копий — копировать нечего; **копия на Диске не тронута** | строка «Архив журнала базы (WAL)» и `backup-pitr.md` раздел 5; внешняя копия сейчас — единственная, не трогать |
| `error` | прочее | журнал контейнера |

## 4. Восстановление и учения

**Когда применять:** потеряны оба сервера или хранилище RustFS (бакет `wal`); раз в месяц — учения. Боевая база не трогается.
Нужны: Docker, этот репозиторий (каталог `infra`), образ `rt-db-postgres:local` (на VPS 2 есть; на новой машине —
`docker build -t rt-db-postgres:local -f infra/db/Dockerfile.postgres infra/db`), доступ к Диску (Яндекс — логин и файл с паролем
приложения «Файлы», лучше отдельный пароль для учений; Google — ключ сервисного аккаунта и ID папки) и **`WAL_ENC_KEY`**
(офлайн-копия или `/opt/rt-db/.env.db`). Места на диске — объём последней базовой копии с WAL после неё
(`--check`, `--latest`) или всей копии (`--target-time`) плюс размер базы.

```bash
# Яндекс Диск: пароль приложения — только из файла (chmod 600), в аргументах и журнале его нет
infra/db/restore-from-offsite.sh --check --login backup@<домен> --password-file /root/yadisk-pass \
  [--folder-path RailTech-backups/prod] --env-file /opt/rt-db/.env.db
# Google Drive
infra/db/restore-from-offsite.sh --check --sa-file /root/gdrive-sa.json --folder-id <ID> --env-file /opt/rt-db/.env.db
# восстановление до конца копии или на момент — контейнер rt-pitr-offsite остаётся, дальше backup-pitr.md, раздел 3, «Действие 2»
infra/db/restore-from-offsite.sh --latest --login … --password-file … --env-file …
infra/db/restore-from-offsite.sh --target-time "2026-10-22 14:30:00+00" --login … --password-file … --env-file …
```

Под капотом — `restore-pitr.sh --source file --file-dir <каталог>` (тот же путь, что восстановление из RustFS, раздел 3
`backup-pitr.md`): WAL-G читает скачанную копию как файловое хранилище (`WALG_FILE_PREFIX`), только на чтение.

**Учения раз в месяц** (вместе с ежемесячной проверкой WAL-G, `backup-pitr.md` раздел 4; делает архитектор или хостинг, 15–30 минут):

1. На VPS 2 обновить каталог `infra` до текущего `main` (как для `db-up.sh`).
2. Временно положить доступ. Яндекс: создать отдельный пароль приложения «Файлы» для учений и на VPS 2
   `install -m 600 /dev/null /root/yadisk-pass && cat > /root/yadisk-pass` (вставить пароль, Ctrl+D). Google: со своего компьютера
   `scp <ключ>.json root@<VPS 2>:/root/gdrive-sa.json`, на VPS 2 `chmod 600 /root/gdrive-sa.json`.
3. `infra/db/restore-from-offsite.sh --check …` (команды выше) → «учения пройдены». VPS 2 — 2 ГБ памяти: восстановленный экземпляр
   ограничен 512 МБ, как у `restore-pitr.sh`.
4. `shred -u /root/yadisk-pass` (и удалить пароль приложения в Яндекс ID) или `shred -u /root/gdrive-sa.json`. Итог (дата, базовая
   копия, время) — строкой в описании PR или отчёте раунда.

Не прошло — внешняя копия непригодна: не удалять ничего на Диске, сохранить вывод, эскалация владельцу; основной путь восстановления
(RustFS) при этом не затронут. Автоматизировать учения пока не стали (B-OPSG-2): на VPS 1 нет `WAL_ENC_KEY` (и не должно быть), а
доступ к Диску на VPS 2 расширил бы круг серверов с доступом к копии.

## 5. Смена пароля приложения или ключа сервисного аккаунта

Яндекс: Яндекс ID → Безопасность → Пароли приложений → новый пароль «Файлы» → Платформа → «Внешняя копия бэкапов» → «Изменить
подключение» → новый пароль → «Сохранить и проверить» → «Доступ есть» → удалить старый пароль в Яндекс ID. Удаление пароля без
замены даёт «Яндекс не принял логин или пароль приложения» при проверке и `reason: access` при следующей копии.

Google: Google Cloud → аккаунт → «Keys» → «Add key» (новый JSON) → Платформа → «Внешняя копия бэкапов» → «Изменить подключение» → выбрать
новый файл → «Сохранить и проверить» → «Доступ есть» → удалить старый ключ в «Keys». Отзыв ключа без замены даёт «Google не принял
ключ» при следующей проверке и `reason: access` при следующей копии. Аварийно — файл на сервере (раздел 1а).
## 6. Ограничения

- Копируется только архив базы (WAL-G). Ежедневные дампы `pg_dump` (бакет `backups`, на VPS 1 лежат незашифрованными) и файлы
  бакетов RustFS (`erp-*`, `eds-private`, CRM) на Диск не попадают — B-OPSG-1.
- «Проверить» ходит на Диск из CRM, а не из контейнера `offsite-backup` (B-OPSG2-2): сеть VPS 1 наружу у них общая, но точный
  ответ для сервиса — `offsite-sync.sh --probe`.
- Внешняя копия отстаёт до суток (копия раз в сутки): при потере обоих серверов RPO — до 24 ч + время копирования, а не 5 минут.
- Каталог архива — `WAL_S3_PREFIX` VPS 1 (по умолчанию `pg17`). После ротации ключа шифрования (`backup-pitr.md` раздел 6) поменять его и
  на VPS 1, иначе копия продолжит идти из старого каталога; старый каталог на Диске удалить руками через 14 суток.
- Дельта-копии WAL-G не используются; если их включат (`WALG_DELTA_MAX_STEPS`), срок хранения на Диске выключается сам (копируется
  всё, в журнале `offsite_delta_backups_found_retention_off`) до пересмотра правила.
- Лимиты Google: общий диск — до 400 000 объектов (14 суток WAL ≈ 20 000), выгрузка — до 750 ГБ в сутки на аккаунт. Яндекс: место —
  по тарифу Яндекс 360 (Корзина считается), скорость WebDAV местами ограничена — смотреть `avg_speed` в `offsite_sync_finished`.
