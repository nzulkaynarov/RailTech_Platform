# crm-bot — Telegram-бот отдельным процессом (S0-4)
Статус: действует · Владелец: лид · Обновлено: 2026-10-27

Волна 10, этап 0; основание — ADR-0017 (надёжность), `arch-audit-current.md` §3.1 и §7.5. Бот больше не живёт в процессе `crm-api`.

## Кто что делает

| Процесс | Telegram |
|---|---|
| `crm-bot` (`python -m app bot`, образ `rt-crm-backend`, **одна реплика**) | **Всё входящее:** long polling (`getUpdates`) или приём `POST /telegram/webhook`; проверка заголовка `X-Telegram-Bot-Api-Secret-Token`; `setWebhook` по `CRM_DOMAIN` / `TELEGRAM_WEBHOOK_URL` (FIX-66); диалоговый агент, меню, ответы клиенту; публикация профиля бота при старте; статус и пульс в таблицу `bot_runtime` |
| `crm-api` | Бота не запускает, апдейтов не принимает (`/telegram/webhook` в нём нет — 404). **Исходящие**, которые он делает сам: «Проверить канал» (`sendMessage` в канал команды), публикация профиля бота при сохранении (`setMyName` и т. п.), проверка токена `getMe` перед сохранением. Сохраняет токен в БД и просит `crm-bot` перезапуститься |
| `crm-worker` | Только исходящие из очереди: карточки эскалаций и уведомления команде, сообщения лидам (`CurrentBotSender`, `Container.telegram_bot()` — токен читается из БД при каждом вызове, перезапуск не нужен) |
| «Центр внешних сервисов» (монитор в воркере) | Прямые `getMe` + `getWebhookInfo` к Telegram — правда о токене и вебхуке, от процессов не зависит |

Почему одна реплика: у одного токена может быть один потребитель `getUpdates`; второй получит `409 Conflict`. В режиме webhook вторая реплика
безвредна, но смысла не имеет.

**Выкладка.** Пока идёт деплой, старый `crm-api` (в котором ещё живёт бот) и новый `crm-bot` могут недолго работать вместе. Кратковременный
`409 Conflict` от Telegram (`getUpdates`) в этот момент ожидаем: старый контейнер останавливается, новый подхватывает апдейты, ничего не теряется.
Если `409` держится дольше минуты — где-то остался второй потребитель того же токена (старый стенд, другой сервер).

## Связь через БД (таблица `bot_runtime`, одна строка)

* `crm-bot` пишет: `running`, `source` (`db`/`env`/`none`), `username`, `last_error`, итог публикации профиля, **пульс** `heartbeat_at`
  (при изменении статуса — сразу, иначе раз в `BOT_HEARTBEAT_S` = 10 с). При штатной остановке пульс сбрасывается.
* `crm-api` читает статус для «Подключений», «Состояния системы» и чек-листа настройки. Пульса нет дольше `BOT_STALE_AFTER_S` = 45 с
  (или процесс ни разу не отчитывался) — бот считается **не работающим**, причина — «Процесс бота (crm-bot) не отвечает».
* Смена токена в «Подключениях»: `getMe` → запись токена (зашифрованного) и `restart_requested_at` в одной транзакции → API ждёт до
  `BOT_RESTART_WAIT_S` = 10 с, пока `crm-bot` выполнит запрос, и отвечает. `crm-bot` опрашивает БД раз в `BOT_POLL_INTERVAL_S` = 2 с, при
  запросе (или при смене `integration_secrets.updated_at` токена другим путём) перезапускает бота **внутри процесса**: останавливает
  polling, снимает вебхук старого бота (webhook), стартует с новым токеном. Диспетчер и агент пересобираются не каждый раз.
* Не успел за 10 с (процесс лежит или занят) — токен всё равно сохранён; когда `crm-bot` поднимется, он прочитает действующий токен сам.
* Режим (`TELEGRAM_MODE`) — переменная окружения, в БД её нет и в «Подключениях» её не меняют: поправьте `.env` и `up -d crm-bot crm-api`.
* Недоступный Telegram при старте процесс не роняет: ошибка в `last_error`, повторная попытка каждые `BOT_RETRY_S` = 30 с. Упавший polling
  (отозванный токен, `409`) поднимается тем же путём.

## Диагностика

| Симптом | Что смотреть |
|---|---|
| «Процесс бота (crm-bot) не отвечает» | `docker compose ps crm-bot`, `docker compose logs crm-bot`; healthcheck — `GET :8001/health` (503, если упал внутренний цикл; недоступный Telegram не повод для перезапуска) |
| «Telegram не принимает токен» / `409` | токен в «Подключениях»; второй сервер/стенд с тем же токеном — остановить |
| Вебхук не доходит | `docker compose logs caddy` (маршрут `/telegram/webhook` → `crm-bot:8001`), «Центр внешних сервисов» → Telegram: url, `pending_update_count`, последняя ошибка; `python -m app telegram-webhook info` |
| Токен сменили, бот со старым | `docker compose logs crm-bot | grep bot_restart_requested`; в БД: `SELECT restart_requested_at, restart_applied_at, heartbeat_at FROM bot_runtime;` |

## Проверка на стенде без токена (заглушка Bot API)

`apps/crm/scripts/fake_bot_api.py` — заглушка на стандартной библиотеке. В `.env` стенда: `TELEGRAM_BOT_TOKEN=<число>:<любая строка>` (формат
токена, значение вымышленное), `TELEGRAM_API_BASE_URL=http://fake-bot-api:8081`. Заглушку запустить в сети проекта:

```
docker run -d --name <проект>-fake-bot-api --network <проект>_default --network-alias fake-bot-api -p 127.0.0.1:18999:8081 \
  -v "$PWD/apps/crm/scripts/fake_bot_api.py:/fake.py:ro" --entrypoint python <образ crm-api> /fake.py --port 8081
curl -s -X POST 127.0.0.1:18999/_inject -H 'Content-Type: application/json' -d '{"update_id":1,"message":{...}}'   # апдейт
curl -s 127.0.0.1:18999/_log                                                                                       # вызовы Bot API
```

Сценарии: апдейт доходит до обработчика и `sendMessage` уходит; остановка `crm-api` — бот отвечает; остановка `crm-bot` — API работает, статус «не
отвечает»; смена токена через `PUT /api/v1/integrations/telegram/token` — в журнале заглушки вызовы нового бота (`bot_id`); webhook: `setWebhook`
виден в журнале, `POST` через Caddy с верным заголовком — 200, с неверным или без — 404, прямой `POST` в `crm-api` — 404. После проверки — `down -v`
проекта и удаление контейнера заглушки.

## Deep-link `/start <параметр>` (D1-9)

Параметр после `/start` разбирает `app/bot/handlers.py::on_start` → `StartLinkService` (`services/start_links.py`, чистые функции — `domain/start_link.py`).
Приветствие и согласие отвечают как раньше; сверху — одно дополнительное сообщение, если ссылка что-то сделала. Ошибка разбора приветствие не ломает.

| Параметр | Откуда | Что делает бот |
|---|---|---|
| `web` | кнопка «Написать в Telegram» на сайте и в кабинете («Я новый клиент», страница входа) | новому лиду без истории ставит источник `web` («пришёл с сайта»); существующему ничего не меняет |
| `deal_<id>` | «Написать менеджеру» в кабинете (`id` — заявка ERP, `deals.erp_deal_id`) | привязывает диалог к заявке, **только если** этот Telegram уже привязан и проверен менеджером как клиент (`telegram_identities.client_id` + `verified_at`) **и** заявка принадлежит этому же клиенту. Иначе — обычное приветствие и запись `lead.start_deal_rejected` в аудит: ссылку кабинета без подписи может написать кто угодно, чужую заявку подставить нельзя. При успехе — заметка в ленте лида и ответ «Вижу вашу заявку «…»» |
| `lead_<id>_<срок>_<подпись>` | ссылка на бота в письме-подтверждении запроса с сайта | подписанная ссылка (HMAC на отдельном ключе — HKDF от `JWT_SECRET` с контекстом `start-link`, 14 дней), выдаётся только системой. Склеивает чат с карточкой запроса (`merge_with_lead`). Одноразовая по состоянию: если у запроса уже есть Telegram-аккаунт или чат — клиент (`client_id`), ссылка не срабатывает — «ссылка устарела». Подделка, чужой ключ, истёкший срок — то же |
| `tg_<48 символов>` (NOTIFY-1) | кабинет: Профиль → «Уведомления» → «Подключить» (кнопка или QR; ссылку выпускает ERP `POST /me/telegram-link` из сессии контакта) | привязка Telegram к контакту **без подтверждения менеджера** — `services/contact_telegram.py`, разбор — `domain/contact_link.py`. Подпись — HMAC ключом из секрета пары шины `erp → crm` с меткой `rt-telegram-link/v1` (пробуются все действующие секреты), срок 15 минут, одноразовость — nonce в `telegram_link_nonces`. Успех: `telegram_identities.client_id` + `verified_at` (без `verified_by_user_id`), `client_contacts.telegram_identity_id`, лид — клиенту, аудит `client.contact_telegram_self_link`, `crm.contact.updated` с `telegram_user_id` → ERP заполняет проекцию → Mini App входит; ответ — приветствие на языке контакта. Повтор, подделка, просрочка, несуществующий контакт — одно сообщение «ссылка устарела или уже использована» (не выдаёт, есть ли контакт); Telegram уже у другого клиента или контакта — «уже связан с другим контактом, напишите менеджеру», ничего не меняется и ссылка не гасится |
| всё остальное (`quote_…`, `invite_…`, мусор) | — | игнорируется, только приветствие |

Проверка на стенде: письмо-подтверждение приходит на указанный в форме адрес (на стенде почта — консоль `crm-worker`), в нём ссылка `https://t.me/<бот>?start=lead_…`;
перейти в бот, нажать «Начать» — карточка запроса получает чат, менеджер видит переписку на той же карточке.

### Привязка Telegram контактом (`tg_…`, NOTIFY-1)

Симптом → что смотреть:
- **Клиент пишет «бот сказал: ссылка устарела»** — ссылка живёт 15 минут и срабатывает один раз; пусть нажмёт «Подключить» в
  Профиле ещё раз. Если сразу после выпуска — проверьте сопряжение CRM ↔ ERP («Подключения» → ERP): у сторон разный секрет
  вебхуков, и подпись не сходится (`contact_link_refused reason=invalid_or_expired` в логе `crm-bot`).
- **«Уже связан с другим контактом»** — Telegram этого человека привязан к другому клиенту или контакту; разберитесь в карточке
  клиента (отвязать там и попросить подключить снова).
- **Бот подключил, а в кабинете «не подключён»** — статус в кабинете — проекция ERP по `crm.contact.updated`: журнал шины
  («Подключения» → «События», доставка `crm → erp`), строка `rt_bus_projection contact` в логе ERP (Telegram уже у другого
  контакта ERP — поле не применяется).
- **«Подключить» в кабинете не показывается** — `GET /me/telegram` отдаёт `available=false`: не задан `TELEGRAM_BOT_USERNAME`
  в ERP, нет сопряжения с CRM или контакт ещё не сопоставлен с контактом CRM.

Отключение: кабинет → `DELETE /me/telegram` → событие `erp.contact.telegram_unlink_requested` → CRM в очереди шины снимает
Telegram с контакта и клиента (`client.contact_telegram_self_unlink` в аудите) → `crm.contact.updated` без `telegram_user_id`.
Лид этого Telegram, его клиент и стадия не меняются (в отличие от отвязки менеджером); `telegram_identities.notifications_off_at`
выключает аккаунт из клиентских рассылок (уведомления, отслеживание запроса, приглашение) до повторного подключения. `/delete`
стирает имя и ник Telegram и в проекции контакта ERP (`crm.contact.updated` без них); смена ника или имени — тоже снимок. Повторная привязка другим аккаунтом
освобождает прежний так же; ERP при уже привязанном Telegram ссылку не выдаёт (409 `TELEGRAM_ALREADY_LINKED`). Telegram,
подтверждённый менеджером, сохраняет `verified_by_user_id`. Заглушённый лимитом `/start tg_…` пишется в переписку как `tg_***`.

Проверочное сообщение: кабинет → `POST /me/telegram/test` → событие `erp.contact.telegram_test_requested` (inline) → бот пишет
«Проверка связи…» на привязанный Telegram контакта. Не пришло — в логе CRM `contact_telegram_test_skipped` (контакт без
привязки или заблокировал бота, бот не настроен) или `contact_telegram_test_failed` (ошибка Telegram); повторить можно через
минуту (раньше ERP отвечает 429).
