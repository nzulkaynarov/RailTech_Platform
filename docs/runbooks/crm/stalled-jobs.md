# Зависшие задачи очереди: как видно и как снять вручную
Статус: действует · Владелец: лид · Обновлено: 2026-11-27 (ЗАВИС-1)

## Когда применять
- В «Сервисах» у приёма почты: «Ящик давно не опрашивался», у проверок: «фоновые проверки не идут».
- В «Состоянии системы» у очереди: «N задач выполняются дольше 15 минут».
- Периодическая задача с `lock` (опрос ящика) не стартует, хотя воркер жив.

## Что произошло
Воркер остановили во время задачи (деплой, нехватка памяти) или вызов завис без таймаута — задача осталась в `doing`.
Следующие такие же с общим `lock` (`inbound_mail_poll`, общий lock `render_pdf` у EDS) не начинаются, пока она «выполняется».

## Что делает система сама (CRM и EDS)
- При старте воркера и каждые 3 минуты (`stalled_jobs_recovery`) задачи в `doing` у воркера без сердцебиения (>90 с)
  снимаются по политике `app/tasks/policy.py`: периодические и неидемпотентные — `failed`, идемпотентные — в очередь
  заново. В журнале: `stalled_job_recovered` (task, job_id, action, age_s).
- Любая задача ограничена своим `timeout_s` из той же таблицы: дольше — отменяется и становится `failed`.
- Остановка воркера (деплой): `stop_grace_period: 40s` у `crm-worker` и `eds-worker`, воркер ждёт задачи до 25 с, потом
  отменяет их с записью статуса — в `doing` они не остаются.
- Подсказка на экране различает «воркер не работает» (сердцебиения нет → к хостингу) и «задача зависла» (воркер жив →
  подождать несколько минут и нажать «Проверить»).

Новая задача очереди без строки в `POLICIES` не пройдёт тест `test_every_queue_task_has_an_explicit_policy`: повтор задачи
по умолчанию не делается никогда.

## Диагностика
```bash
docker compose exec crm-worker python -m app worker --help >/dev/null   # образ жив
docker compose exec postgres psql -U <user> -d <crm_db> -c "
  SELECT j.id, j.task_name, j.worker_id, w.last_heartbeat, now() - e.started AS age
  FROM procrastinate_jobs j
  LEFT JOIN procrastinate_workers w ON w.id = j.worker_id
  LEFT JOIN LATERAL (SELECT max(at) AS started FROM procrastinate_events
                     WHERE job_id = j.id AND type = 'started') e ON true
  WHERE j.status = 'doing' ORDER BY e.started"
```
Норма: у каждой строки `last_heartbeat` свежее 30 с и `age` меньше `timeout_s` задачи. Строка с пустым `worker_id` или старым
сердцебиением — зависшая; восстановление снимет её за ≤ 3 минуты.

## Как снять вручную
1. Подождать 3 минуты и перепроверить запрос выше: чаще всего задача уже снята (`stalled_job_recovered` в журнале воркера).
2. Не снялась (воркер жив, задача «висит» дольше `timeout_s`): перезапустить воркер — `docker compose restart crm-worker`;
   при старте восстановление снимет задачи прежнего процесса.
3. Крайний случай, только для периодической задачи (повтор не опасен): пометить её упавшей —
   `UPDATE procrastinate_jobs SET status = 'failed' WHERE id = <id> AND status = 'doing'` — и убедиться, что следующий тик
   (через 2 минуты для опроса ящика) стартовал. Неидемпотентные задачи (`send_email`, уведомления) руками не повторять:
   письмо уходит дважды.
4. Для ERP (Celery): `lock` у задач — ключи кэша с TTL и `pg_advisory_xact_lock` в транзакции, постоянной блокировки нет.
