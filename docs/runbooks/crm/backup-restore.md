# Бэкап и восстановление

## Когда применять
Плановая проверка (раз в месяц), перед рискованной операцией, потеря данных, переезд.

## Как устроено (ADR-0013)
Сервис `backup` ежедневно в 03:00 Asia/Tashkent: `pg_dump` (custom) + копия бакетов
`kb-sources`, `client-documents`, `tg-attachments` → том `railtech_backups`,
каталог `<UTC-штамп>/` с `SHA256SUMS`; хранится 14 дней (`BACKUP_KEEP_DAYS`).
Том смонтирован и в api: экран CRM «Резервные копии» (`/backups`, админ) показывает список,
возраст последней копии (предупреждение > 26 ч) и кнопку «Сделать сейчас» — она кладёт в том
файл-флаг `request_now`, демон `backup` проверяет его раз в 30 с и запускает тот же `backup_once`.
pg_dump есть только в образе `backup`, поэтому api сам бэкап не делает. На dev демон не запущен
(профиль `backup`) — запрос будет ждать; там используйте `make backup`.
Демон раз в 30 с (и во время бэкапа) пишет `heartbeat` (epoch) в том: старше 2 мин — CRM
показывает «Сервис резервного копирования не отвечает» (экран «Резервные копии» и «Состояние»);
запрос, не забранный за 2 мин, помечается зависшим, и кнопку можно нажать снова.

## Как CRM видит бэкап на проде (M5-CRM-01)
На проде бэкап делает контейнер `backup` на VPS 2 (`infra/db/backup.sh`); том `crm_backups` у CRM смонтирован
и там (base.yml), но его никто не пишет. Поэтому прод задаёт `BACKUP_SOURCE=rustfs` явно (`infra/compose/prod.yml`,
`crm-prod-env`; тест — `infra/deploy/tests/crm-backup-source-test.sh`, `make deploy-check`).
Значения `BACKUP_SOURCE`: `auto` (по умолчанию) — том, если смонтирован в api; нет тома — бакет только при
`APP_ENV=prod`, вне прода прежнее «том не подключён»; `volume` / `rustfs` — принудительно. dev и стенд — `auto` (том).
- **Формат бакета** (пишет скрипт, отдельного файла статуса нет): `<UTC-штамп>/<база>.dump` для `crm`, `erp`,
  `litellm`, `langfuse` и `<UTC-штамп>/SHA256SUMS`. Копия базы успешна, если в каталоге есть SHA256SUMS и непустой
  дамп этой базы; список баз берётся из SHA256SUMS свежего каталога, время копии — штамп каталога. Последний успех —
  копия самой отстающей базы (выгрузка rclone не упорядочена, поэтому проверяется каждая база).
- **Где видно:** «Внешние сервисы» → «Хранилище резервных копий» (источник, время последней копии, часы по базам) и
  «Резервные копии» (источник, копии по базам, список каталогов). «Сделать сейчас» там нет — копию запускают на
  VPS 2: `infra/deploy/backup-now.sh`.
- **Инцидент:** нет успешной копии за 26 ч (сутки + запас на выгрузку) или в бакете нет ни одной полной копии —
  статус «Сбой» (после 15 минут подряд — «Сломано»), инцидент и одно оповещение на причину, не чаще раза в сутки
  (`docs/runbooks/crm/integration-health.md`).
- **Ошибки бакета** (в экране — текст и «что сделать»): бакета нет — создать в RustFS (`S3_BUCKETS` у `s3-init`) и
  проверить `BACKUP_RUSTFS_*` на VPS 2; ключ не принят — `S3_ACCESS_KEY`/`S3_SECRET_KEY` у `crm-api`/`crm-worker`; в ансамбле (compose `infra/compose`) это ключ сервиса CRM `S3_CRM_ACCESS_KEY`/`S3_CRM_SECRET_KEY` из `.env.prod` (S0-9): он читает `backups` и пишет только в бакеты CRM, `s3-init` обновляет его при деплое;
  RustFS недоступен — статус «нет данных» (инцидент не меняется), смотреть «Хранилище файлов» и сеть VPS 1.
- **Что CRM не видит:** живость контейнера `backup` на VPS 2 (heartbeat — только у тома): о сбое узнаем по возрасту
  копии, то есть не раньше чем через 26 ч. Логи — `docker logs rt-db-backup-1` на VPS 2.

## Диагностика
- `scripts/backup.sh --prod --list` — список бэкапов; последний — не старше суток.
- `docker compose ... ps backup` — `healthy` (unhealthy = бэкапа нет > 26 ч);
  `make logs s=backup` — события `backup_done` / `backup_failed`.
- Каталоги `*.partial` — незавершённые попытки (удаляются автоматически через 6 ч).

## Действие
**Внеочередной бэкап:** CRM → «Резервные копии» → «Сделать сейчас» (через ~30 с `make logs s=backup`
покажет `backup_requested` → `backup_done`), или с сервера `scripts/backup.sh --prod`.
Запрос «завис» (контейнер backup остановлен): запустите его или удалите флаг —
`docker compose ... exec api rm /backups/request_now`.

**Копия вне VPS (раз в неделю, человек):**
`docker run --rm -v railtech_backups:/b -v "$PWD":/out alpine tar -czf /out/backups.tgz -C /b .`
→ перенести в защищённое хранилище.

**Восстановление** ⚠️ перезаписывает БД и файлы стенда:
1. `scripts/backup.sh --prod --list` → выбрать штамп.
2. `scripts/restore.sh --prod <штамп>` (подтвердить `yes`): остановит api/worker/MCP,
   проверит суммы, `pg_restore --clean`, загрузит объекты, запустит сервисы, smoke.

**Проверка восстановления на dev (гейт Фазы 8, ежемесячно):**
1. На VPS: `scripts/backup.sh --prod`; архив тома (см. выше) скопировать на dev-машину.
2. На dev: `docker run --rm -v railtech_backups:/b -v "$PWD":/in alpine tar -xzf /in/backups.tgz -C /b`.
3. `make restore b=latest` → `scripts/smoke_dev.sh` → в CRM видны лиды и документы с prod.

## Проверка
`/ready` 200; в CRM количество лидов = prod на момент бэкапа; документ клиента скачивается.

## Эскалация
Разработчику: вывод restore.sh, `make logs s=backup`, штамп бэкапа.

## База LiteLLM (ADR-0020)

Модели и ключи, заданные в CRM «Модели ИИ», живут в отдельной БД `litellm`. Копия снимает её в
`litellm.dump`, восстановление загружает, если файл есть. Ключи в ней зашифрованы
`LITELLM_SALT_KEY` — восстанавливайте на сервере с тем же значением в `.env`, иначе ключи придётся
ввести в «Модели ИИ» заново (модели по умолчанию восстановит `litellm-seed`).
