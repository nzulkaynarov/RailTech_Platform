## 2. Стенд и данные

**Состав ансамбля** (минимум для сценариев, `--no-deps` для `crm-worker` и `caddy`): `postgres` (pgvector, PG 17), `redis`, `rustfs` + `s3-init`, `db-init`, `litellm` + `litellm-seed`
(их требует `crm-api`), `crm-migrate`, `crm-api`, `crm-worker` (провижининг ERP, без `docling`), `erp-backend`, `platform-bff`, `platform-web`, `caddy`.
**Не поднимались:** `crm-web`, `erp-web`, `cabinet-web`, `docling`, `crm-mcp-*`, `erp-mcp`, `erp-worker`, `erp-worker-ai`, `erp-beat`, `erp-ai-gateway`, Langfuse. Следствия — в §7.
Память моего проекта — около 1,9 ГБ (`docker stats`), общий стенд параллельно ~5 ГБ из 11,67 ГБ.

**Окружение.** `.env` создан из `.env.example` скриптом `infra/compose/make-env.sh` в worktree (в `.gitignore`, секреты случайные, после прогона удалён); `HTTP_PORT=18089`, `DEV_*_PORT` со сдвигом 1xxxx, `PLATFORM_SSO_ENABLED=true`,
`TELEGRAM_MODE=disabled`, `PLATFORM_COOKIE_SECURE=false` (по умолчанию `dev.yml`, стенд по http).

**Первый запуск.**
1. Администратор — мастер `/setup` CRM: код из лога `crm-api` (`setup_code_issued`) и `POST /api/v1/setup/admin` (интерфейс CRM `crm-web` не поднимался, вызов — тем же API, что у страницы `/setup`).
   Результат (CRM-01b): `platform_roles = [ADMIN]`, `platform_access = [crm, erp]`.
2. Шов CRM ↔ ERP — **через `.env`** (ADR-0009, «живой стенд на токенах из `.env`»): `PUT /api/v1/integrations/erp` с `http://erp-backend:8000`, `SERVICE_TOKEN_CRM_TO_ERP` и `WEBHOOK_SECRET` из `.env`;
   «Проверить связь» — `status: ok`. Сопряжение кодом/bootstrap не делалось, окно bootstrap осталось открытым (для одноразового стенда допустимо).
3. Сотрудники — **через Платформу**: Admin · Оргструктура → «Пригласить сотрудника» (5 человек, `@demo.example`: менеджер, директор, снабженец, «универсал» с двумя ролями, «новичок»).
   Почта в стенде не подключена, поэтому каждое приглашение закончилось ожидаемым «Сотрудник добавлен, но письмо не отправлено» (контракт 0.2.x, Q-PLT-15-1 п. 3).
   Временные пароли — CRM API `POST /api/v1/users/{id}/reset-password` (в Платформе их, правильно, не видно). Первую смену пароля четырёх сотрудников сделал скриптом через `POST /api/v1/auth/change-password` BFF;
   «новичка» оставил для сценария 7 (смена в интерфейсе).
   Роли после приглашений выправлены `PATCH /api/v1/users/{id}` CRM: в моём первом проходе форма приглашения не сбрасывалась между отправками, и роли накапливались (см. D-3).
4. Данные: **ERP** (Django shell своего проекта) — своя компания через сервис мастера первого запуска `create_own_company` (FIX-65), три сделки (ЗВ-2026-001…003) и четыре уведомления директору
   (`notify_user`: «КП на согласовании», «Заявка назначена», «Договор подписан клиентом», служебное). **CRM** (API) — клиент «ООО «Демо Клиент CRM»», лид вручную и лид с веб-формы (`L-0002`, свободный).
   Ролей на сотрудников: `manager` — MANAGER; `director` — DIRECTOR; `supply` — SUPPLY; `multi` — MANAGER + ADMIN (проверка смены активной роли: у ролей разные модули); `newbie` — ACCOUNTANT.

**Повторить:** поднять стенд как выше (`QA_OUT` — каталог **только вне репозитория**: туда скрипт пишет сгенерированный пароль «новичка» и журнал входов), затем
`QA_CREDS=<файл KEY=VALUE вне репозитория> QA_OUT=<каталог> QA_COMPOSE=<обёртка docker compose -p rt-p1-qa …> node docs/runbooks/qa/plt-p1/run.mjs s1 s2 s3 s4 s5 s7 s6 s9 s10 s11`
и `node docs/runbooks/qa/plt-p1/summarize.mjs`. Скрипт лежит вне `apps/platform/web/e2e` (тесты на MSW не затронуты), зависимости берёт из `apps/platform/web/node_modules`; сам держит лимит входа BFF (≤ 8 входов в минуту).

## 5. Наблюдения (не дефекты — решение за архитектором)

- **O-1. Лимит входа считает и успешные входы.** 10 входов с одного адреса за минуту (в BFF адрес берётся из последнего `X-Forwarded-For`) — и одиннадцатый вход **любого** сотрудника с этого адреса — `429 TOO_MANY_REQUESTS`
  («Слишком много попыток входа. Повторите через минуту.»). Офис за одним NAT в 09:00 или QA с одного компьютера упрутся в лимит; по runbook 3.3 это заданное поведение. Рекомендация: считать только неудачные попытки на IP, успешные — по e-mail.
- **O-2. 401 в консоли на странице входа.** Каждое открытие `/login` без сессии делает `GET /api/v1/me` → 401 (виден в консоли браузера). Работе не мешает; можно проверять `/auth/session`.
- **O-3. Задержка плашки «ERP не отвечает»** до ~38 с (кэш снимка 8 с + опрос 30 с) — для «минуты простоя» нормально.
- **O-4. Поиск и заглушки.** Номер без нулей (`ЗВ-2026-1`) и латинская «ZV-» не находятся (в ERP номер вида `ЗВ-2026-001` составляет BFF — Q-PLT-14-1); объект, на который ведёт уведомление/поиск, показывает заглушку P1 «Заявок пока нет», хотя заявка есть — ожидаемо до P2, но владельцу лучше сказать заранее.
- **O-5. Экран Forbidden:** слева остаётся меню «1. Dashboard», крошки называют запрошенный раздел; боковое окно и «Скрыть панель» скрыты. Допустимо, косметика на усмотрение дизайна.
- **O-6. Роли открытой сессии** подтягиваются ≤ 60 с (CRM при этом отказывает сразу). Текст «Изменения применяются сразу» в блоке «Что произойдёт» относится к ERP и CRM; меню открытой сессии обновится в течение минуты, не мгновенно.

## 6. Что владелец проверяет сам на гейте P1

Условия: общий стенд пересобран лидом от `main`, ERP на нём уже имеет свою компанию (иначе вот-вот упрётесь в D-2).
1. **Вход.** `http://platform.localhost:8088` → войти администратором (письмо-приглашение на настоящую почту — только если подключён SMTP) → попадаете в «Моя очередь», рейл: Dashboard, EDS, Chats, Admin.
2. **Роли.** Admin · Оргструктура → «Пригласить сотрудника» → менеджер → выйти → войти им (временный пароль взять в CRM → «Пользователи» → сброс) → сменить пароль → рейл без Admin; вернуться админом, выдать вторую роль, зайти заново — новые модули.
3. **Каркас на своём экране.** Свернуть меню и боковое окно, обновить страницу — состояние сохранилось; сузить окно до телефона — нижняя панель и выезжающее меню; Safari — вход по http (cookie без Secure) и 1280/1440 без горизонтальной полосы.
4. **Forbidden.** Ввести в адресной строке чужой раздел (менеджер → `/admin/org`) — «Нет доступа».
5. **Уведомления и поиск на реальных данных.** Любое настоящее событие ERP (например, КП на согласование директору — моим прогоном не воспроизводилось): колокольчик, переход по уведомлению, «Отметить все прочитанными»; ⌘K по номеру настоящей сделки.
6. **Устойчивость.** `docker compose stop erp-backend` на минуту — плашка «ERP не отвечает», CRM-часть работает; вернуть.
7. **Что смотреть глазами, чего скрипт не оценит:** совпадение с артбордами «0. Каркас», «v3 · 1. Dashboard», «v3 · 6. Admin» (сверку с макетами агент не делал — только скриншоты рядом с этим отчётом), тексты ru/uz/en, ощущение скорости, D-1 на живой ленте.

## 7. Что не удалось проверить и почему

- **Интерфейсы CRM и ERP** (`crm-web`, `erp-web`) не поднимались (память стенда, runbook просил минимум): «CRM-часть жива» проверено через `crm-api /health`, `crm.localhost/health` через Caddy и **данные CRM внутри Платформы** (поиск клиента и лида, очередь менеджера), но не кнопкой «Войти» в самой CRM.
- **Реальные события ERP.** `erp-worker`, `erp-beat`, `erp-mcp`, `docling`, LiteLLM-ключи моделей не работали; уведомления директору созданы прямым вызовом сервиса ERP; очередь директора «КП на одобрение» (`my-approval-queue`) и «Входящие без резолюции» не проверены на данных — нужна цепочка согласования КП (задачи ERP-01…06 и P2). Сводка по компании и все экраны модулей — заглушки P1.
- **Письмо-приглашение и Telegram.** SMTP и бот не подключены: проверено поведение «письмо не отправлено» и временный пароль из CRM, но не доставка письма и не приглашение по Telegram (P3).
- **TLS и прод.** Только http на `*.localhost:18089` (dev-Caddy). `PLATFORM_COOKIE_SECURE=true`, `Caddyfile.prod`, HSTS не проверялись; Safari и Firefox не запускались (только Chromium); телефон — только эмуляция 390×844.
- **Языки uz и en** не проверялись (все сценарии на ru); тексты BFF — только русские (Q-PLT-14-5, известно).
- **Сроки и токены.** Срок жизни сессии (12 ч) и обновление access-токена CRM (15 мин) отдельным сценарием не проверялись; сессия «новичка» и директора жили 5–35 минут без разрывов.
- **Нагрузка и параллельная работа** нескольких сотрудников в одном браузере, SSE/WebSocket-уведомления (P4) — не проверялись.
- **Сверка с макетами v3** (`docs/architecture/platform-frontend.md` §10 п. 1–5) агентом не делалась: доступа к канвасу макетов в прогоне не было; скриншоты 1440 приложены для сравнения владельцем.
- **Данные стенда** (бонус честности): бывшие приглашения `form-*@demo.example` — отключены; `bootstrap`-окно ADR-0009 на стенде не закрывалось. Стенд после прогона удалён (`down -v`, образы `rt-p1-qa-*` удалены, `.env` стёрт).
