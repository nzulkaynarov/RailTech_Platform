# Runbook: вебхуки ERP → CRM не доходят, дублируются, секрет меняется (FIX-33, FIX-35)

Контракт — `docs/CONTRACTS.md` §3: заголовки `X-Event-Id`, `X-Event-Type`, `X-Timestamp`, `X-Signature`; ретраи ERP 1, 5, 30 мин, 2, 6, 24 ч; после них событие `FAILED` ждёт ручного повтора.

## Симптом → где смотреть

| Симптом | Где смотреть | Что значит |
|---|---|---|
| Клиент не получил сообщение бота о КП/счёте, в ленте лида нет записи | ERP: админка Unfold → «Исходящие события интеграции», фильтр по типу и статусу | `PENDING` с большим `attempts` — CRM отвечает ошибкой; `FAILED` — сетка ретраев исчерпана; события нет вовсе — компания не сопоставлена с клиентом CRM (`CrmClientMapping`) |
| Строки `PENDING` стоят, `attempts = 0` | то же | Celery-воркер или Redis лежали: Beat-задача `integration.requeue_stuck_webhook_events` (раз в 5 мин) сама поставит повтор; нет секрета `ERP_WEBHOOK_SECRET` — события ждут, пока он не появится |
| CRM: центр внешних сервисов, строка «События из ERP» красная | CRM → «Внешние сервисы» | `rejected` — событие принято и отклонено (текст ошибки: `company mismatch`, `invalid event envelope` — тело не по схеме известного события, расхождение заголовка `X-Event-Type` с телом, `replayed body` — то же тело уже принято под другим `X-Event-Id`); `failed` — обработка упала `MAX_ATTEMPTS` раз; «зависло» — принято, но не обработано дольше 10 мин (воркер CRM) |

## Повторить доставку (ERP)

1. Админка Unfold → «Исходящие события интеграции» → отметить строки. `SENT` и `PENDING`, который ждёт своего запланированного ретрая (`next_attempt_at` в будущем), действие пропускает.
2. Действие «Повторить доставку в CRM» (видно только суперпользователю) → указать причину → подтвердить. Счётчик попыток обнуляется, запускается полный цикл ретраев; действие записывается в «Журнал доступа».
3. Проверить: статус стал `SENT`, `response_status = 200`. CRM гасит дубли по `X-Event-Id` — повтор уже принятого события безопасен.

## Что делает CRM со сбоями

* Подпись проверяется по сырому телу первой; неверная — 401, тело не разбирается.
* Тело, которое CRM не принимает, — 200 и строка `rejected` (ретраи ERP не помогут).
* Читатель терпимый (FIX-35): лишние поля в конверте и в телах игнорируются; **неизвестный тип события** (новое событие более новой ERP) — 200 и строка `skipped` («пропущено», `unknown event type: …`): не обрабатывается, не повторяется и красным в центре внешних сервисов не горит. Конверт разбирается дискриминированными моделями по `event` (`apps/crm/backend/app/schemas/erp_events.py`).
* Повтор тела (FIX-35): подпись не покрывает `X-Event-Id` и `X-Timestamp`, поэтому CRM хранит `sha256` каждого тела; то же тело под другим `X-Event-Id` — 200, строка `rejected` (`replayed body: already received as event <id>`), обработки нет. Полная защита (подпись заголовков и окно `X-Timestamp`) — Q-FIX35-2.
* Сбой постановки в очередь не теряет событие: строка `received`, сборщик (раз в минуту) ставит её заново.
* Сообщения в Telegram уходят после коммита и не больше одного раза на событие (`erp_incoming_events.notified_at`).
* События применяются по `occurred_at`: более старое после нового зеркало сделки не откатывает.

## Что знать эксплуатации

* `visibility_timeout` Celery-брокера = 25 ч (`core/settings/infra.py`) и действует на ВЕСЬ брокер ERP, а не только на вебхуки: задача, взятая воркером и не подтверждённая (`acks_late` есть у `crm.auto_invoice_on_closed_won`), при падении воркера вернётся в очередь только через 25 ч, а не через час. Для вебхуков это страхует Beat-задача (5 мин); для остальных `acks_late`-задач помните о задержке.
* Расписание Beat в ERP имеет два источника: записи, засеянные миграцией `core/0002` (`core/seeds/beat.py`), и `CELERY_BEAT_SCHEDULE` в настройках (его `DatabaseScheduler` переносит в БД при старте beat). Задача подбора вебхуков живёт во втором; изменить её периодичность из админки нельзя — только настройкой и перезапуском `erp-beat`.
* CRM отвечает 409 (секрет вебхуков не настроен) ДО проверки подписи — это сознательно: ERP ретраит и ничего не теряет, но неподписанный запрос узнаёт, что секрет не задан.
* Подпись по-прежнему покрывает только тело (формат — контракт, Q-FIX35-2); повтор гасится по `X-Event-Id` и по хешу тела.
* Лимит запросов CRM к ERP (`/api/integration/v1/*`) — свой, по сервисному токену: `INTEGRATION_RATE` (по умолчанию 300/minute). Превышение — 429 `TOO_MANY_REQUESTS` с `Retry-After` (в контракт код 429 ещё не внесён — Q-FIX35-1).
* Проверка тела по `events.schema.json` в ERP (`ERP_EVENTS_CONTRACT_MODE`): `strict` (по умолчанию при DEBUG и в тестах) — несоответствие поднимает исключение и событие не создаётся; `log` (прод) — запись ERROR в лог и отправка как есть; `off`. Схема читается из `/packages/contracts/events.schema.json`; в прод-образе её нет — проверка тогда пропускается с одним предупреждением (Q-FIX35-5).

## Ротация секрета вебхуков без простоя (FIX-35)

> Если ERP подключена кнопкой «Подключить ERP» (M3-CRM-10), секрет меняет кнопка «Обновить ключи» вместе с токенами — шаги ниже нужны только для ручной схемы с `.env` (`docs/runbooks/crm-erp-pairing.md`).

ERP подписывает **текущим** секретом; CRM принимает **текущий и предыдущий**. Менять секрет можно, не останавливая обмен и не перезапуская CRM.

1. Сгенерируйте новый секрет (`openssl rand -hex 32`).
2. **CRM** → «Подключения» → «ERP»: в поле «Секрет вебхуков» введите **новый**, в поле «Предыдущий секрет вебхуков» — **прежний**; сохраните (пароль админа). В карточке строка «Предыдущий секрет» покажет «Принимается: ••••xxxx». С этого момента CRM принимает подпись обоими. (Если секрет задан не в «Подключениях», а в `.env` CRM, — запишите там `ERP_WEBHOOK_SECRET=новый,прежний` и перезапустите CRM.)
3. **ERP**: в `.env` стенда/прода — `WEBHOOK_SECRET=новый` (допустимо `WEBHOOK_SECRET=новый,прежний` или `WEBHOOK_SECRET_PREVIOUS=прежний`: подписывает всегда ПЕРВЫЙ), перезапустите `erp-backend`, `erp-worker`, `erp-beat`. События, записанные до перезапуска и ещё не доставленные, подписываются при отправке уже новым секретом.
4. Убедитесь, что новые события принимаются: ERP → «Исходящие события интеграции» — свежие `SENT` с `response_status = 200`; в CRM строка «События из ERP» зелёная.
5. **CRM** → «Подключения» → «ERP»: отметьте «Снять предыдущий секрет» и сохраните. Подпись прежним секретом теперь — 401, ERP-события со старой подписью (если какой-то воркер ERP не перезапущен) будут ретраиться по сетке, пока воркер не подхватит новый секрет.

* Для ERP `WEBHOOK_SECRET_PREVIOUS` справочная: подпись идёт только первым значением списка; предыдущий секрет ERP не использует.
* Предыдущий секрет, заданный в `.env` CRM (второе значение `ERP_WEBHOOK_SECRET`), кнопкой «Снять предыдущий секрет» в интерфейсе не снимается: уберите его из `.env` и перезапустите CRM (кнопка видна, только когда предыдущий секрет сохранён в «Подключениях»).

Откат на шаге 3–4: верните в ERP прежний секрет первым (`WEBHOOK_SECRET=прежний,новый`) — CRM принимает оба, пока предыдущий не снят. Значения секретов не показываются нигде: в карточке — только «задан» и последние 4 символа; в аудите — `erp_webhook_secret_last4`, `erp_webhook_secret_previous_last4`.
