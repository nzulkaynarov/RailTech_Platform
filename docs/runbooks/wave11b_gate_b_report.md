(нужны для «первого запуска глазами»: `/setup` и мастер ERP), две заглушки шины. Не поднимались: `crm-bot`, `crm-mcp-*`, `erp-mcp`, `erp-worker-ai`, `cabinet-web`, `langfuse`, `eds-*`.
Память: пик ≈ 9,3 ГиБ из 11,7 вместе со стендом владельца; порты — `HTTP_PORT=8098`, `DEV_*` на 5498, 6398, 6399, 9098, 9099, 4098, 8096, 8097, заглушки — 127.0.0.1:8095 и 8094.
`.env`: `TELEGRAM_MODE=disabled`, `PLATFORM_SSO_ENABLED=true`; секреты пар шины с EDS у издателей пустые (EDS не развёрнут — доставки к нему ждут без попыток, §5 O-5).

**Подписчики-заглушки** (Python 3.12, `http.server`, файл вне репозитория): `POST /bus/v1/events`; проверка подписи HMAC v2 (`sha256=HMAC(secret, "{id}.{timestamp}.{body}")`, секрет пары `RT_BUS_SECRET_<ИЗДАТЕЛЬ>_STUB`),
окна 300 с по `X-RT-Timestamp` (ISO 8601 UTC); журнал `id, type, source, publisher, время приёма, номер попытки по id, sig_ok, ответ, correlationid, X-Request-ID`; ответ — 200/503/422 по переключателю `POST /_ctl {"mode": …}`; «выключение» —
`docker stop` (имя перестаёт разрешаться). Заглушек две: `stub` (час простоя) и `stub2` (DLQ и `enabled`), чтобы проверки пунктов 2 и 3 не ждали друг друга. Строки в `subscriptions.yaml` (копия файла из репозитория + две строки, смонтирована каталогом `/opt/rt/contracts/bus` в `crm-api`, `crm-worker`, `erp-backend`, `erp-worker`, `erp-beat`):

```yaml
  - name: stub
    endpoint: http://bus-stub:9000/bus/v1/events
    types: [uz.railtech.erp.*.v1, uz.railtech.crm.*.v1, uz.railtech.identity.user.*.v1]
  - name: stub2
    endpoint: http://bus-stub2:9000/bus/v1/events
    types: [uz.railtech.erp.*.v1, uz.railtech.crm.*.v1]
```

Секреты пар — окружением издателей. **Перезапуск (пересоздание) контейнеров ради env** — два раза: при первом `up` (секреты `stub`) и один раз при добавлении `stub2` (секреты `STUB2`); образы CRM и ERP не пересобирались, код приложений не менялся. Файл подписок после этого правился на месте и подхватывался без перезапуска (по mtime): `enabled: false/true` у `stub2` подействовали за ≤ 7 с.
Первая отладка: первые три попытки к `stub` получили 401 от **самой заглушки** (моя ошибка разбора метки времени: считал её эпохой, а не ISO) — исправлено, доставка повторена `bus retry`; к продукту это не относится.

### 3. DLQ и «повторить» — пройден

Шаги: `stub2` → `{"mode": 422}`, новый клиент (CRM — 8 событий, ERP — 2); затем `{"mode": 200}`; повтор.

- 422 → **сразу `dead`, `attempts = 1`**, `last_status_code = 422` у всех 10 ([`p3-stub2-422-log.txt`](../screens/w11b-gate-b/logs/p3-stub2-422-log.txt), [`p3-dlq-retry-operator-path.txt`](../screens/w11b-gate-b/logs/p3-dlq-retry-operator-path.txt)).
- Просмотр: CRM `docker compose … exec crm-api python -m app bus dead --subscriber stub2` (8 строк); ERP `… exec erp-backend python manage.py bus_retry --list --status dead --subscriber stub2` (2 строки).
- Повтор одной: CRM `python -m app bus retry 73`, ERP `manage.py bus_retry --delivery 30` → «поставлено на повтор», `delivered` с попытками с нуля (через 4–6 с — ждёт ближайшего `pump`); «повторить все dead»: CRM `bus retry-dead --subscriber stub2` («7»), ERP `bus_retry --all-dead --subscriber stub2` («1») → все `delivered`, dead 0. Заглушка получила тот же `id` дважды (422, затем 200).
- **Удобство для администратора:** есть и «одну», и «все по подписчику», и просмотр — но только командами внутри контейнера на сервере (CRM и ERP — разные команды); в интерфейсе CRM плитка «Внешние сервисы → События из ERP» следит только за подписчиком `erp` (в «В норме» при 134 ждущих и паузе у `stub` — [снимок](../screens/w11b-gate-b/p3-crm-external-services-1440.png)); в ERP есть действие в Django-админке (по runbook, суперпользователь; глазами не проверялось). Для подписчиков, которых добавляют строкой в файл, администратор Платформы об остановке не узнаёт. → O-2.

## 4. Дефекты

Серьёзность: блокер · важный · малый. «Где искать» — подсказка, не предписание: код приложений и пакетов QA не правит.

**W11B-G-1 · важный · взаимная блокировка при записи итога доставки (`rt_bus_subscriber_state`).** Две задачи `pump` идут параллельно (периодическая и пробуждение по коммиту, T4); обе записывают состояние подписчиков в разном порядке.
- Шаги/факт: в 01:00:13 `crm-worker`: `rt_bus.pump[181]` завершён `Error` (10,4 с), `psycopg.errors.DeadlockDetected` на `INSERT … ON CONFLICT (subscriber) DO UPDATE` по `rt_bus_subscriber_state` (первая запись состояния нового подписчика `stub2`); параллельно шёл `pump[188]` (пробуждение). Доставки, взятые в аренду упавшей задачей, вернулись только по истечении аренды (60 с): `lead.created`/`stage_changed`/`updated` в BFF **доставлены через 74 с** (и 10 с) вместо 0,1 с — на это время колокольчик и счётчики «молчат» ([выдержка](../screens/w11b-gate-b/logs/w11b-g-1-deadlock-excerpt.txt)). Потери нет, самоизлечение.
- Ожидание: параллельные `pump` не блокируют друг друга (или упорядочены); одна ошибка не задерживает чужих подписчиков на аренду.
- Воспроизведение: единичное за ~1,5 ч работы стенда (в ERP — 0; серия из 70 событий — 0); условие — первая запись состояния нового подписчика (L5: «новый подписчик — строка в файле») при совпадении двух `pump`. На продуктиве после T4 пересечения нормальны.
- Где искать: `packages/rt-bus/rt_bus/sql.py` (`INSERT … ON CONFLICT` по `STATE`, ~122–136), `rt_bus/sqlalchemy/bus.py` (запись итогов пачки; порядок подписчиков), Django-адаптер; идеи — единый порядок обновления состояний (по имени подписчика), `pg_advisory_xact_lock` на «записать итоги», ретрай транзакции при `40P01`.

**W11B-G-2 · важный · `enabled: false` теряет события, опубликованные за время остановки.** (Семантика и документация; решение — архитектора: код или текст runbook'ов.)
- Шаги: `stub2` → `enabled: false` в файле подписок; опубликовать события; через 6 мин `enabled: true`.
- Факт: ранее разложенные доставки дождались и ушли (в 01:08:40–45); события, опубликованные при `false`, ни разу не доставлены — раскладка для выключенного подписчика не создаёт строку, `outbox` помечается разложенным (10 событий, [журнал](../screens/w11b-gate-b/logs/p2-enabled-false-lost-events.txt)). Дозаказать их нельзя (нет строк `rt_bus_delivery` для «повторить»).
- Это **соответствует** `rt-bus.md` §5 («`enabled: false` останавливает и новые раскладки …», код — `subscriptions.py`: «новых доставок не получает»; формулировка «они ждут» относится к уже разложенным), но **противоречит** [`rt-bus-crm.md`](rt-bus-crm.md) п. 4 («остановить доставку подписчику на время работ: `enabled: false` (доставки ждут, потом уходят)») — по нему администратор ждёт, что ничего не потеряет. `rt-bus-erp.md` про `enabled` не говорит.
- Вопрос архитектору: **менять код** (для выключенного подписчика строки доставки создаются в `pending` и ждут) **или текст** `rt-bus-crm.md` п. 4 (и уточнить «они» в `rt-bus.md` §5): «выключенный подписчик пропускает новые события; для остановки на время работ используйте простой endpoint/паузу». Сами runbook'и QA не правит.
- Где искать: код — `packages/rt-bus/rt_bus/subscriptions.py:67` (`for_event`: `s.enabled`), `rt_bus/core.py:203,230`; текст — `docs/runbooks/rt-bus-crm.md` ~строка 64, `docs/architecture/rt-bus.md` §5 (строки ~119–120).

**W11B-G-3 · малый · в CRM у администратора постоянно «Нет связи» и серия 403.** `GET /api/v1/stream` отвечает 403 администратору (права лидов у него нет — R3-D-2), клиент повторяет раз в ~3 с; индикатор в шапке всегда «Нет связи» — на каждой странице CRM. Ожидание: индикатор не врёт или поток не требует прав на лиды. Где: `apps/crm/frontend/src/app/Header.tsx` (`useEventStream`), `apps/crm/backend` — `/api/v1/stream`. **W11B-G-4 · малый · ERP: архивный контакт выглядит живым.** Карточка клиента показывает контакт, удалённый в CRM, без пометки «в архиве», с кнопкой «Пригласить в кабинет», в счётчике «Контактов» (2 вместо 1); нажатие даёт 400 `CONTACT_ARCHIVED` и два тоста с **сырым кодом** «CONTACT_ARCHIVED» ([снимок](../screens/w11b-gate-b/p4-erp-archived-contact-invite-1440.png)). **W11B-G-5 · малый · первый экран администратора CRM — «Нет доступа».** После первого входа CRM ведёт на `/leads`, где администратор видит «Нет доступа к этому разделу … Раздел доступен другой роли» ([снимок](../screens/w11b-gate-b/first-run-crm-after-login-1440.png)); для нового клиента это первое впечатление. Ожидание: стартовая страница администратора — «Подключения» или «Пользователи». Где: `apps/crm/frontend` (редирект после входа / стартовый маршрут по правам).

**W11B-G-6 · важный · хвост задержки пробуждения: 4,8 с (нарушает ≤ 2 с в механизме T4).** `lead.created` (outbox 01:10:30.869) дошёл до `platform-bff` в 01:10:35.7, задержка 4832 мс. Периодическая `rt_bus.pump[389]` поставлена в очередь в 01:10:30.597, но **запущена только в 01:10:35.621** (+5,0 с; соседние тики [387] и [388] стартовали через 14 и 6 мс); пробуждение по коммиту, по `rt-bus.md` §4, слилось с ней через `queueing_lock` («ожидающий `pump` ещё не начал раскладку и заберёт новое событие») и ждало её запуска.
- Ожидание: пробуждение ≤ 2 с при любом совпадении с периодическим тиком. Факт: один случай на 56 доставок CRM с первой попыткой (прочие замеры пробуждения — до 0,7 с); при повторе эффект возможен каждый раз, когда событие совпадает с поставленной, но не запущенной периодической задачей.
- Выдержка журнала `crm-worker` и БД — [`w11b-g-6-late-pump-excerpt.txt`](../screens/w11b-gate-b/logs/w11b-g-6-late-pump-excerpt.txt). Строки про `AlreadyEnqueued` в журнале **нет**: по коду (`contrib/procrastinate.py`, `wakeup`) это штатный тихий случай, поэтому слияние выведено из совпадения времён (событие создано через 0,27 с после постановки [389], которая стартовала на 5 с позже), а не из записи в логе. Стенд снят — подтвердить повторным прогоном нечем.
- Где искать: `packages/rt-bus/rt_bus/contrib/procrastinate.py` (строки ~41, 60: `queueing_lock="rt_bus.pump"`, `wakeup`), опрос очереди воркером CRM (почему поставленная задача стартует через ~5 с).

## 5. Наблюдения

- **O-1.** `platform-bff`: журнал приёмника `POST /bus/v1/events` — стандартная строка uvicorn без времени и `request_id`; цепочка «`X-Request-ID` доставки → логи» (`rt-bus.md` §9) на стороне BFF не видна. CRM и заглушка видят тот же идентификатор.
- **O-2.** Оператору для подписчиков вне пары CRM ↔ ERP: только команды в контейнере; плитка «События из ERP» не отражает паузу и `dead` у чужих подписчиков (например, у `stub`). Для «строкой в файле» разумно показывать подписчиков с `dead`/`paused` в «Внешние сервисы» (идея, не дефект). Ещё: «повторить» только для `dead` — для ждущих после долгой паузы массового действия нет (одна доставка — `bus retry <id>`); на стенде не понадобилось: после пробы всё ушло за 1–2 мин.
- **O-3.** Лимит веб-формы `POST /leads/web` — 5 запросов в час с адреса: 429 на пятом, `Retry-After` нет (ответ `rate_limited`). Для офиса за одним NAT (R3 O-1) — ограничение входа лидов.
- **O-4.** `rt_bus.pump` запускается ≤ 5 с после `bus retry` (повтор не будит ретранслятор) — терпимо.
- **O-5.** На стенде без EDS: доставки к `eds` (секрета пары нет) остаются `pending` с 0 попыток («отложить на 5 мин, попытка не засчитывается» — как заявлено), но `oldest_undelivered_age_seconds` растёт и пересечёт порог алерта 1 ч (в `bus status` — 4546 с). Для стенда без EDS — шумящая метрика; на проде EDS будет.
- **O-6.** Почта не подключена → приглашение «Приглашён», пароль недоступен интерфейсу; тупик первого запуска без почты — только CRM API/CLI (как в R3, пункт 4 первого запуска). Решение владельца: «Подключения → Почта» перед приглашениями.
- **O-7.** Форма входа ERP на `erp.localhost` не принимает пароль администратора CRM («Не найдено активной учётной записи») — вход только через «В бэк-офис (ERP)» (SSO). Подсказки на форме нет.
- **O-8.** «Подключения → ERP» после успешного сопряжения по-прежнему показывает абзац «Пока коннектор не настроен, CRM работает автономно…» над зелёным «Настроен».
- **O-9.** Индикатор `/setup` CRM — три шага («Администратор», «Компания», «Готово»); после шага 1 браузер уходит на `/login`, шагов 2–3 нет (компанию заводят позже в ERP).
- **O-10.** Предохранитель срабатывает на пачке из N параллельных попыток: счётчик 6 при пороге 5 (CRM, 01:00:42). Мелочь.
- **O-11.** Журнал CRM: `rt_bus_breaker_open` — 15 раз за час, ERP — 12 (по одной на пробу); `rt_bus_delivery_dead` у `stub2` — 8 + 2 (422 по пункту 3).

## 6. Что не проверено и почему

- **Другие типы событий ERP** (`quote.*`, `invoice.*`, `deal.*`, `act.*`, `delivery.*`, `contract.signed`, `document.created`) — на стенде они не порождались (нужна сквозная сделка с КП и счётом, без Cabinet/Telegram); их формы проверяют юнит-тесты шины и контракты.
- **Колокольчик от настоящей цепочки ERP**: уведомление и событие созданы одним скриптом через сервисы продукта (§3.5). Реальные потоки ERP (КП на согласование, оплата счёта) — позже, этап D.
- **Шаги расписания 1 ч, 6 ч, 24 ч и `dead` после 7-й попытки** — за час простоя недостижимы (предохранитель); покрыты тестами пакета.
- **Откат транзакции не будит ретранслятор, недоступная очередь** (`rt_bus_wakeup_failed`) — тесты T4; на стенде запись не наблюдалась (0).
- **Воспроизводимость W11B-G-1** по требованию — не добивался (одно срабатывание); стресс-серия из 70 событий без повтора.
- **Интерфейс «повторить» в Django-админке ERP** (по runbook, суперпользователь) — глазами не открывался (нет суперпользователя на стенде); проверены команды.
- **EDS** (`eds-*`), Cabinet, Telegram-бот, ИИ — вне гейта; `litellm` поднят только как зависимость `crm-api`.
- **Доступность (axe) и горизонтальная прокрутка** для снимков 390 — не прогонялись (вне T6; R3 — 0 нарушений).
- **Safari/Firefox** — только Chromium.
