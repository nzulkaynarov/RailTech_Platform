# 0032. Группы Telegram с секретарём

- Статус: proposed (владелец 2026-11-24 принял модель «группа с секретарём»; перевод в accepted — по строке
  [DECISIONS](../DECISIONS.md) 2026-11-24 «роль Telegram») · Дата: 2026-11-25
- Основание: исследование «Telegram в RailTech» 2026-11-24, вариант Б и ограждения (раздел 6) · Уточняет
  [ADR-0015](0015-eds-service-and-domain-boundaries.md) (чаты — CRM) и [ADR-0023](0023-cabinet-chat-and-counterparty-notifications.md)
  (каналы беседы), не меняет [ADR-0002](0002-no-shared-tables-api-and-events.md)

## Контекст

Переписка с клиентом по заявкам идёт в общих группах Telegram, которые создают сотрудники со своих аккаунтов. Бот в группах
молчит и ничего не пишет: история живёт только в Telegram, уйдёт сотрудник — уйдёт и она. Владелец принял правило
«Telegram — дверь и звонок, не шкаф» и группы одного стандартного вида: группа с секретарём. Этот ADR — первый шаг: привязка
группы к клиенту и запись её переписки. Запрос из сообщения, темы, сводки и исключение участников — следующие шаги.

## Варианты

A. Отдельное хранилище сообщений групп. B. **Беседа клиента в существующем хранилище переписки с новым каналом `group`**
(выбран). C. Telegram Business или сторонний посредник — отложены решением владельца.

Почему не A: вторая лента, второй доступ, второй поиск; лента клиента в Платформе читает `conversations`/`messages`, права к
ним уже настроены (`chat_access`). Почему не C: личные чаты менеджеров и платный посредник — не этот шаг.

## Решение

1. **Привязка.** Бот, ставший администратором группы или супергруппы, заводит запись `telegram_groups` (`pending`) и один раз
   пишет в группу короткий код. Сотрудник с правом `clients:write` вводит код в Платформе и выбирает клиента (`bound`).
   Код: 6 знаков без похожих, действует 48 часов, одноразовый; в ответах API его нет; новый — командой `/connect` администратора
   группы. Отключить группу (`unbound`) можно из Платформы; бота убрали — `removed`, привязка клиента сохраняется.
2. **Канал команды не клиентская группа — в обе стороны.** Чат, выбранный каналом команды, не получает записи и не привязывается; чат с привязанной или ждущей код группой каналом команды выбрать нельзя (409); каналы
   (`channel`) в клиентские группы не попадают. Поток «кандидат в канал команды» (`telegram_chat_candidates`) не менялся.
3. **Что хранится.** Только в `bound`: текст или подпись, автор (имя, ник и идентификатор Telegram, наш ли это сотрудник по
   `users.tg_user_id`), время, на какое сообщение ответ, файлы как вложения. Беседа — `conversations.channel = 'group'`, одна на
   группу, на якорном лиде `source = 'group'` (по одному на клиента, не лид личного чата — обезличивание личного лида не
   стирает группу). Якорь скрыт: в реестре лидов, входящих, «С клиентами», счётчиках, воронке и таймерах его нет (общий предикат `lead_visibility`); лид кабинета остаётся как был. Правка обновляет текст, прежние тексты — в `meta.previous_texts`, метка «изменено» — `meta.edited_at`.
   **Удаление сообщения боту не приходит** (Bot API его не присылает): в системе сообщение остаётся. До привязки, в
   `pending`/`unbound`/`removed` — ничего, кроме записи группы. Сообщения своего бота и других ботов не пишутся.
4. **Файлы.** Через общий разбор вложений бота; Bot API отдаёт боту файлы до 20 МБ. Больше — вложение-ссылка без файла
   (`stored: false`, `note: «файл больше 20 МБ — откройте в группе»`). Сбой скачивания — та же пометка, сообщение не теряется.
5. **Уведомление.** После привязки секретарь пишет и закрепляет: «Сообщения и файлы этой группы сохраняются в карточке клиента
   RailTech.» (ru; uz — новый латинский алфавит; en). Нет права писать или закреплять — группа в состоянии «нужны права
   администратора» (`access = admin_required`); запись при этом идёт, если бот читает группу.
6. **Режим приватности.** Бот читает все сообщения группы, только если он администратор (или приватность выключена у BotFather);
   иначе Telegram присылает ему лишь команды и ответы ему. Поэтому «нужны права администратора» — и признак того, что запись
   может быть неполной.
7. **Бот молчит.** В группе нет ответа ИИ, нет сценария лида личного чата, нет «не так быстро»: лимит и обработчики диалога
   работают только в личном чате.
8. **Кто видит.** Те же сотрудники, что видят переписку клиента (`GET /leads/{lead_id}/messages`, `chat_access`); список групп и
   привязка — права `clients:read` / `clients:write`. Срок хранения — один с карточкой клиента.
9. **Владелец группы** — служебный аккаунт компании (решение владельца 3); это организационное правило, кодом не проверяется
   (Bot API не сообщает владельца группы боту надёжно). Бот один.
10. **Данные под следующие шаги.** `topic_mode` (`none` | `request`, по умолчанию `request`) и `language` группы хранятся уже
    сейчас; бот ими пока не пользуется.

## Последствия

- Таблица `telegram_groups`, уникальный индекс беседы группы, новый канал `group` у беседы и сообщения (поле `channel` уже
  строка), эндпоинты `/api/v1/telegram-groups`, `edited_message` в разрешённых апдейтах бота. Контракт `crm.yaml` — только
  добавления.
- Ответить в группу из Платформы этот шаг не даёт (ТГ-2); без канала ответа якорь не показывается в «С клиентами». Нет ограничения на число попыток привязки по коду: неверные попытки пишутся в журнал (`telegram_group.bind_failed`), счётчика попыток нет.
- Негативное: без прав администратора бот видит не всё; удалённое в группе остаётся в системе (отражено в уведомлении только
  общим «сохраняются»); код в чужой группе, где бота добавили администратором, получит любой её участник — привязка требует
  права на клиентов, но выпуск кода не ограничен (бот выходит из неподключённых групп — отдельный шаг).
