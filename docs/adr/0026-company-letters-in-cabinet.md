# 0026. Официальные письма компании в кабинете

- Статус: proposed (архитектор, 2026-11-16) — продуктовое решение принято владельцем 2026-11-16
  ([DECISIONS](../DECISIONS.md) 2026-11-16 «письма в кабинете», план, ЛИД-8) · Дата: 2026-11-16
- Уточняет [ADR-0015](0015-eds-service-and-domain-boundaries.md) (EDS — владелец документооборота),
  [ADR-0022](0022-counterparty-cabinet-supplier-relationship.md) (кабинет контрагента, модули по ролям),
  [ADR-0024](0024-signing-authority-and-official-documents.md) (официальный документ и код проверки)

## Контекст

Владелец 2026-11-16: кабинет — место хранения всего официального, что компания-контрагент получила от нас и отправила нам;
почта и бот — только доставка и уведомление. Контрагент видит только свои письма.

Сейчас у контрагента в «Документах» только документы сделки ERP (КП, договор, счёт, акт, спецификация, накладная). Наши
исходящие письма (`letter_out`, ИСХ) живут в EDS и уходят только на почту; его входящие, которые мы регистрируем в EDS (ВХ),
он не видит вовсе и не знает, дошло ли письмо. Кабинет читает только портальный API ERP (ADR-0001, CONTRACTS §4); ERP о
письмах EDS знает лишь резолюцию и отказ (`letter.resolved`, `letter.rejected`) и подписанный документ для проверки по
коду (`document.signed` → `PortalDocumentVerification`). Файлов EDS ERP не читает.

Бенчмарки — [разбор](../research/2026-11-16-cabinet-lead-path.md) §«Письма»: корпоративные банки (раздел «Письма», ответ в
цепочке исходного письма), операторы ЭДО (письмо — документ рядом с договором и счётом), архивы отправленной корреспонденции
(поиск по номеру и дате, статус доставки по каждому письму).

## Решение

1. **Источник — реестр EDS, кабинет — проекция ERP.** ERP держит `PortalLetter`: компания, направление (`in` — письмо
   компании нам, `out` — наше письмо компании), номер (ВХ или ИСХ), дата, тема, сделка ERP, «в ответ на» (номер ВХ),
   статус (`registered` → `answered` для `in`; `sent` для `out`). Чужих полей EDS (резолюция,
   исполнитель, срок, внутренние пометки, черновики) в проекции нет.
2. **Чьё письмо — только по явной связи.** Сделка ERP (`erp_deal_id` → компания сделки); без сделки — точное совпадение ИНН
   получателя (`out`) или отправителя (`in`) с ИНН компании ERP. Совпадения нет — письмо в кабинет не попадает. По
   названию не сопоставляем никогда. Письмо, где адресат — не сама компания (банк, госорган, третье лицо), в кабинет
   этой компании не попадает, даже если речь о ней.
3. **События.**
   - Входящее — существующее `uz.railtech.eds.letter.registered.v2` (`sender.inn`, `links.erp_deal_id`, номер, тема, дата
     получения); ERP добавляет подписку.
   - Исходящее — `uz.railtech.eds.document.registered.v2` получает необязательный блок `letter` для `kind = letter_out`:
     получатель (название, ИНН, почта) и «в ответ на» (`eds_letter_id`, номер ВХ). Хеша PDF в событии нет: номер ИСХ
     выдаётся при отправке, итоговый PDF собирается после. Совместимое
     расширение v2 (новые необязательные поля, CONTRACTS §9.4). ERP добавляет подписку.
   - Повтор события — один эффект (inbox ERP, ключ — id письма EDS); поздний снимок не откатывает новый (`registered_at`).
4. **Файл исходящего — через ERP по сервисному токену.** Кабинет просит `GET /api/portal/v1/letters/{id}/file`; ERP
   проверяет, что письмо принадлежит компании сессии, и читает PDF у EDS: `GET /api/v1/service/letters/{eds_document_id}/pdf`
   с `Authorization: Bearer <SERVICE_TOKEN_ERP_TO_EDS>` (тот же приём, что CRM → ERP, M3-ERP-05: до двух активных токенов
   для ротации). EDS отдаёт только итоговый PDF отправленного `letter_out` (с его хешем в заголовке); ERP отдаёт поток.
   Прямого доступа ERP к хранилищу EDS нет. Файл входящего письма — у компании свой; в кабинете — только квитанция о
   регистрации.
5. **Портал.** Модуль `letters` есть у клиента и у партнёра (обе роли, ADR-0022); `GET /letters` (направление, проект,
   период, поиск по номеру и теме), `GET /letters/{id}`, `GET /letters/{id}/file`. Пункт меню «Письма» — в блоке
   «Документы».
6. **Позже (декабрь):** «Написать письмо» из кабинета — портал → шина → регистрация входящего в EDS без распознавания;
   статус доставки исходящего («доставлено», «открыто») — по событиям журнала писем CRM (`uz.railtech.crm.mail.*`).
   Отдельным решением.

## Последствия

- Контрагент видит переписку с нами в одном месте и квитанцию о каждом своём письме; мы — доказательство, что отправили.
- Новая межсистемная связь «ERP читает EDS по сервисному токену» — только чтение, только PDF отправленных писем; секрет
  `SERVICE_TOKEN_ERP_TO_EDS` — в `.env` обеих систем, в репозитории нет.
- Сопоставление по ИНН зависит от точного ИНН в карточке компании ERP и в письме EDS: письмо без сделки и без ИНН в
  кабинет не попадает — это безопасная сторона ошибки.

## Шаги (план, ЛИД-8)

8a — контракт: блок `letter` в `document.registered.v2`, подписки ERP, OpenAPI портала (`letters`) и сервисный путь EDS;
8b — EDS: блок `letter` при отправке ИСХ, сервисная выдача PDF; 8c — ERP: проекция, приёмник, API портала и прокси файла;
8d — Cabinet: «Письма» в блоке «Документы»; 8e (декабрь) — «Написать письмо» и статус доставки.
