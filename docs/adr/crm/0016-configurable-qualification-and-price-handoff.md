# 0016. Квалификацию и передачу по цене решает код по настраиваемым правилам

- Статус: accepted (2026-10-09, решение владельца в обсуждении PR #8)
- Дата: 2026-10-09
- Авторы: агент, владелец
- Связано: BUSINESS §5, C2; SPEC §1.3, §5.7, §6.2, §7.2, §8.1; ADR-0001, ADR-0015; QUESTIONS Q-014

## Контекст и проблема

Первый настоящий прогон eval-gate показал две проблемы:

1. Стадию «Квалифицирован» выбирала модель (`proposed_stage`). На одном и том же диалоге она ставила то «Вовлечён», то «Квалифицирован» — eval-gate мигал, и правило было скрыто в промпте, а промпт расходился с BUSINESS §5.
2. Передача по цене: бот называет цену только дословно из базы, иначе обещает «расчёт делает менеджер», но триггер `price_or_contract_asked` смотрел на косвенный признак (`kb_best_score < min_score`). Первое исправление («любой вопрос о цене — менеджеру») сломало бы сценарий с загруженным прайсом.

Владелец: правила не должны быть зашиты под один бизнес — другое направление может иметь другие критерии квалификации, цены могут появиться в базе знаний.

## Драйверы решения

- SPEC §1.3: модель предлагает, код решает.
- Админ меняет правила без разработчика (BUSINESS C6).
- Стабильный eval-gate.

## Рассмотренные варианты

1. Правило в коде, критерии — в настройках; цена — по факту «названа ли сумма из базы».
2. Зашить правило BUSINESS §5 в код; цена — всегда менеджеру.
3. Оставить решение модели.

## Решение

Вариант 1.

**Квалификация.** Модель только извлекает факты (потребность, продукт, срок, роль в решении, бюджет, компания). `domain/qualification_rules.py` решает: «Квалифицирован», если известны все обязательные факты и не меньше `min_any_of` дополнительных; срок засчитывается в пределах горизонта, роль — из разрешённого списка. Модель не может квалифицировать лида сама (её `qualified` без фактов → `engaged`); `new`/`engaged` по-прежнему предлагает модель. Критерии — `settings.qualification` («Настройки → Квалификация»):

| Поле | По умолчанию (решение владельца 2026-10-09) |
|---|---|
| `required_facts` | потребность, продукт |
| `any_of_facts` | срок, роль в решении, бюджет |
| `min_any_of` | 1 |
| `timeline_max` | любой известный срок |
| `decision_roles` | ЛПР, влияет, собирает информацию |

BUSINESS §5 обновлён этой формулировкой.

**Цена.** `domain/pricing.py`: цена «названа», если в ответе бота есть сумма с валютой и это число есть во фрагментах базы (в прайсе числа часто без валюты). Признак `price_quoted` пишется в meta ответа; `price_or_contract_asked` срабатывает на интент `pricing`, если цена не названа. Флаг `escalation.price_always_to_manager` (по умолчанию выключен) передаёт менеджеру любой ценовой вопрос.

### Последствия

- Хорошо: стадия воспроизводима и объяснима; другой бизнес меняет критерии в настройках; загрузка прайса снимает лишние передачи.
- Плохо: качество зависит от точности извлечения фактов (срок vs длительность услуги — уточнено в промпте); критерии пока общие, не по продуктам.
- Меняется: `domain/qualification_rules.py`, `domain/pricing.py`, `domain/qualifier_decision.py`, `domain/triggers.py`, `schemas/settings.py`, промпт квалификатора, golden квалификатора, форма настроек (выбор нескольких значений), SPEC §5.7, §7.2, §8.1, BUSINESS §5.

### Как проверяем

Таблицы unit-тестов (`test_qualification_rules`, `test_pricing`, `test_triggers`, `test_qualifier_decision`); eval-gate квалификатора (точность стадий ≥ 0.85) и golden-кейс «цена из прайса — без передачи».

Пересмотреть, если появятся продукты с разными критериями — тогда критерии на уровне продукта (`products`).
