# 0021. Единый слой данных фронта — хуки TanStack Query из orval; Refine — оболочка

- Статус: accepted (2026-10-12, владелец: «по твоим рекомендациям, приступай» по `docs/audits/crm/2026-10-12-refine-antd-capabilities.md`)
- Дата: 2026-10-12
- Авторы: агент, владелец
- Связано: SPEC §2, §10; ADR-0002 (уточняется); docs/systems/crm/CONVENTIONS.md §4 (типы API только сгенерированные)

## Контекст и проблема

ADR-0002 обещал, что Refine даст `dataProvider` и CRUD-страницы. На деле `app/providers/data.ts` — заглушка для двух ресурсов, ни одна страница через неё не ходит. Все данные идут через ≈ 580 строк ручных хуков TanStack Query (`src/api/*Queries.ts`) поверх fetch-функций orval. SSE (`hooks/useEventStream.ts`) обновляет экраны, сбрасывая ключи кэша TanStack. Два слоя данных в одном приложении недопустимы, а текущий — наполовину ручной.

## Драйверы решения

- Типы API только из OpenAPI (docs/systems/crm/CONVENTIONS.md §4), без ручных дублей и приведений `as never`.
- «Готовое вместо кастомного» (SPEC §1.7): не писать обвязку запросов руками.
- Обновления в реальном времени по SSE не должны сломаться.
- Миграция без большого разового переписывания.

## Рассмотренные варианты

1. **A.** orval генерирует хуки TanStack Query (`client: "react-query"`); ручные хуки заменяются сгенерированными; Refine остаётся оболочкой.
2. **B.** Полный `dataProvider` Refine на ≈ 15 ресурсов; страницы переходят на `useTable`, `useList`, `useModalForm`, liveProvider.
3. Оставить как есть.

## Решение

Вариант A.

- Хуки запросов и мутаций генерирует orval из `docs/api/openapi.json` (`client: "react-query"`, общий `mutator` `src/api/http.ts`). Файлы `src/api/*Queries.ts` остаются тонкими: инвалидация после мутаций, `placeholderData: keepPreviousData` для списков с пагинацией, составные хуки.
- SSE сбрасывает кэш по сгенерированным ключам (`get…QueryKey`), явный список на каждое событие, с тестом.
- Refine — оболочка: `authProvider`, `accessControlProvider` (`useCan`), `ThemedLayout`, `notificationProvider`, `UnsavedChangesNotifier` / `useWarnAboutChange`, `DocumentTitleHandler`. `dataProvider`-заглушка удаляется, если Refine 5 позволяет; иначе остаётся минимальной без использования.
- Миграция — по одному файлу `*Queries.ts`, каждый шаг с зелёными unit и e2e.

### Последствия

- Хорошо: хуки и типы всегда совпадают с API; ручной обвязки меньше; один слой данных.
- Плохо: хуки Refine для данных (`useTable` с синхронизацией с адресом, отменяемые мутации, liveProvider) недоступны — их задачи решаем antd `Table` и TanStack Query, фильтры в адресе — своим хуком.
- Меняется: SPEC §2 (строка Frontend), §10 (абзац про Refine), ADR-0002 (уточнение), `frontend/orval.config.ts`, `src/api/*`, `hooks/useEventStream.ts`.

### Как проверяем

Unit-тест SSE: каждое событие сбрасывает нужные ключи. e2e сценарии C2–C4 и админка зелёные после каждого шага. Ручных хуков-дублей сгенерированных нет (ревью). Пересмотр — если появятся десятки однотипных CRUD-экранов, где `useTable`/`useForm` Refine дают больше, чем стоит миграция.

## Плюсы и минусы вариантов

### A. orval + TanStack Query

- Плюс: полная типизация, дёшево, SSE как сейчас, миграция по шагам.
- Минус: хуки данных Refine не используются.

### B. dataProvider Refine

- Плюс: `useTable`, `useModalForm`, liveProvider, отменяемые мутации из коробки.
- Минус: записи Refine не типизированы по нашим схемам; кэш и SSE переделываются; крупная разовая миграция всех экранов.

### Оставить как есть

- Плюс: ноль работы.
- Минус: ≈ 580 строк ручной обвязки и расхождение с ADR-0002.
