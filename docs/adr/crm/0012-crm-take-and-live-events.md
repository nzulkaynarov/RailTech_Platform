# 0012. «Забрать» из любой активной стадии; live-события через PostgreSQL NOTIFY

- Статус: accepted (2026-10-08, решение агента по поручению владельца «принимай решения по своим рекомендациям»)
- Дата: 2026-10-08
- Авторы: агент
- Связано: SPEC §6.2, §10.1, §2 (без Redis), BUSINESS.md C2–C3, PLAN Фаза 4

## Контекст и проблема

1. SPEC §6.2 разрешает `→ in_progress` только из `handoff`. Но в CRM менеджер видит таблицу лидов и может захотеть взять лида, по которому эскалации не было (клиент знаком, пришёл по рекомендации). Без ребра `engaged → in_progress` действие «Забрать» в CRM для такого лида невозможно, а обход через фиктивный `trigger` исказил бы журнал.
2. «Входящие» и карточка лида обновляются live (SSE). События рождаются в двух процессах — `api` (ход диалога) и `worker` (квалификатор, таймеры). Нужен межпроцессный канал; SPEC §2 исключает Redis для приложения.

## Драйверы решения

- Журнал переходов должен честно отражать источник (`user`).
- Минимум инфраструктуры; события только после коммита.

## Рассмотренные варианты

1. Ребро `new|engaged|qualified|unresponsive → in_progress` от `user`; события — `pg_notify` в транзакции + одно соединение `LISTEN` в процессе API.
2. «Забрать» только из `handoff`; события — опрос БД фронтом раз в N секунд.
3. Redis Pub/Sub.

## Решение

Вариант 1. `LeadService.take` переводит лида в `in_progress` из любой активной стадии; открытая эскалация (если есть) получает статус `taken`. События `message.created`, `lead.updated`, `escalation.updated` публикуются `pg_notify('crm_events', …)` в той же транзакции, что и изменение; `EventBroker` в API раздаёт их подписчикам `GET /api/v1/stream` (SSE). Полезная нагрузка — типы и id; фронт перечитывает данные по REST.

### Последствия

- Хорошо: честный журнал; нет Redis; событие не уходит при откате транзакции.
- Плохо: NOTIFY ограничен 8000 байт (нагрузка минимальна); при обрыве LISTEN события за паузу теряются — фронт перечитывает данные при переподключении SSE.
- Меняется: SPEC §6.2 (ребро), `domain/stage_machine.py`, тесты таблицы переходов.

### Как проверяем

Unit-таблица переходов; integration: событие приходит подписчику после коммита и не приходит при откате; e2e сценарий handoff.
