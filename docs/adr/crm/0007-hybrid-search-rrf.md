# ADR CRM-0007. Гибридный поиск по базе знаний: вектор + BM25 → RRF, порог по косинусу

- Статус: accepted (2026-10-08, решение агента по поручению владельца)
- Дата: 2026-10-08
- Связано: SPEC §5.5, §7.1 (`retrieve`, `decide`, `fallback`), §12; PLAN Фаза 1; ADR-0004

## Контекст и проблема

SPEC §7.1: «вектор (cosine) + BM25 (`ts_rank_cd`) → RRF → top-6 → порог `kb.min_score`». Нужно уточнить: какой поиск по тексту для трёх языков в PostgreSQL 16, к какой величине применять порог, как фильтровать по `product_key` без потери полноты HNSW.

## Факты (проверено по исходникам pgvector 0.8.7 и PostgreSQL 16)

- HNSW `vector` — до 2000 измерений; фильтры применяются после индексного сканирования, при `ef_search=40` и селективном фильтре результатов будет мало; с 0.8.0 есть `hnsw.iterative_scan`.
- В PostgreSQL 16 есть конфигурации `russian`, `english`, `simple`; узбекской нет. `russian` для латиницы применяет английский стеммер.
- `to_tsvector(regconfig, text)` immutable — допустим в GENERATED-колонке.
- RRF: `score = Σ 1/(k + rank)`, k = 60 (Cormack et al., SIGIR 2009).

## Решение

1. **Текстовый индекс.** `kb_chunks.tsv` — GENERATED STORED: `to_tsvector('simple', text) || to_tsvector(<конфиг языка документа>, text)`, где конфиг: ru → `russian`, en → `english`, uz → `simple`. Текст = `heading_path || ' ' || content`. GIN-индекс.
2. **Запрос BM25.** Язык запроса — `app/domain/language.py`; конфиг тот же; запрос строится как OR лексем (`plainto_tsquery(...)::text`, `&` → `|`), ранжирование `ts_rank_cd(tsv, q, 1|4)` (нормализация на длину документа и плотность совпадений). Пустой tsquery (одни стоп-слова) → BM25-список пуст.
3. **Вектор.** `embedding vector(1536)`, HNSW `vector_cosine_ops` (m=16, ef_construction=64); в транзакции поиска `SET LOCAL hnsw.ef_search = 100` и `SET LOCAL hnsw.iterative_scan = relaxed_order` (фильтры `is_active`, `product_key`).
4. **Слияние.** По 20 кандидатов из каждого списка → RRF (k=60) в чистой функции `app/domain/rrf.py` → top-6 (`kb.top_k`).
5. **Порог.** `kb.min_score` применяется к **максимальной косинусной близости** (1 − cosine distance) среди возвращённых чанков, а не к RRF-оценке: RRF не откалибрована и зависит только от рангов. `best_score` пишется в `messages.meta.kb_hits` и в `kb_gaps.best_score`. Значение по умолчанию 0.55 — стартовое, калибруется на демо-KB (`scripts/kb_search_eval.py` печатает распределение близости для релевантных/нерелевантных вопросов) и меняется админом в настройках (Фаза 5).

### Последствия

- Хорошо: кросс-язычные вопросы (uz → документ на ru) находит вектор, точные термины/артикулы — BM25; порог интерпретируем.
- Плохо: для узбекского нет стемминга (только `simple`); апострофы o‘/gʻ нормализуются в `'` перед индексацией и запросом (`app/domain/text.py`).

### Как проверяем

Unit — RRF и сбор запроса; integration — поиск на демо-KB (детерминированные векторы-фикстуры), PLAN Фаза 1: правильный чанк в top-3 ≥ 13/15.
