# ADR CRM-0005. JWT + Casbin на старте, Keycloak позже

- Статус: accepted (2026-10-08, решение владельца продукта в обсуждении Фазы 0)
- Дата: 2026-10-08
- Связано: SPEC §2, §5.1, §10.3, §11, §15; docs/systems/crm/BUSINESS.md §4; PLAN Фаза 4

## Контекст и проблема

Нужны аутентификация пользователей CRM и ролевая модель admin / manager / viewer с инвариантом «≥ 1 активный admin». Пользователей мало, SMTP нет, пользователей создаёт админ с временным паролем.

## Драйверы решения

- Минимум инфраструктуры на старте (VPS 4 vCPU / 8 GB).
- Готовые решения вместо своего RBAC (SPEC §1.7).
- Возможность перейти на SSO без переписывания фронта.

## Рассмотренные варианты

1. Keycloak (OIDC) сразу.
2. Собственный JWT (argon2id, access 15 мин в памяти + refresh 30 дней в httpOnly cookie с ротацией) + Casbin (pycasbin) с политиками в БД.
3. Собственная таблица прав без Casbin.

## Решение

Вариант 2. Модель Casbin — RBAC с доменами «на будущее» (`infra/casbin/model.conf`), seed-политики — `policy.seed.csv`; проверка — зависимость `require(action, resource)` на каждом эндпоинте, объектные проверки — в сервисах. Фронт получает матрицу прав из `GET /api/v1/me/permissions` и только скрывает UI. Переход на Keycloak — замена `authProvider` и `security/auth.py`.

### Последствия

- Хорошо: нет отдельного сервиса аутентификации; RBAC декларативен и тестируем матрицей роль × действие.
- Плохо: ответственность за безопасность auth (lockout, ротация refresh, хранение хэшей) — на нас; нужны тщательные тесты.

### Как проверяем

Фаза 4: integration-тесты RBAC на каждый эндпоинт; негативные тесты lockout и отзыва refresh. Пересмотр — при требовании SSO/2FA или росте числа пользователей.

## Плюсы и минусы вариантов

### Keycloak сразу

- Плюс: SSO, 2FA, стандарты из коробки.
- Минус: тяжёлый сервис и эксплуатация ради 5–15 пользователей; без SMTP теряет часть ценности.

### Своя таблица прав

- Плюс: просто.
- Минус: изобретение RBAC — противоречит SPEC §1.7.
