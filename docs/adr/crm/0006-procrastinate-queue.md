# ADR CRM-0006. Procrastinate как очередь и планировщик на PostgreSQL

- Статус: accepted (2026-10-08, решение владельца продукта в обсуждении Фазы 0)
- Дата: 2026-10-08
- Связано: SPEC §2, §3.3, §5.8, §7.2, §8.2; PLAN Фаза 0 (задача 5), Фаза 3

## Контекст и проблема

Нужны фоновые задачи (квалификатор по событию с дедупликацией, ингест KB) и таймеры (SLA эскалаций, снуз, unresponsive, ежедневные сводки). SPEC явно исключает Redis/RabbitMQ.

## Драйверы решения

- Одна БД для всего (SPEC §2): бэкапы, транзакционность, меньше сервисов.
- Дедупликация задач по лиду (`queueing_lock`) и отложенный старт (батчинг 5 с).
- Периодические задачи без отдельного cron.

## Рассмотренные варианты

1. Procrastinate (PostgreSQL, LISTEN/NOTIFY, `queueing_lock`, periodic tasks).
2. Celery / Dramatiq / arq + Redis или RabbitMQ.
3. Собственная очередь на таблице + `SELECT … FOR UPDATE SKIP LOCKED`.

## Решение

Вариант 1, версия 3.10.0, коннектор `PsycopgConnector` (psycopg 3, см. ADR-0010). Воркер — отдельный процесс `python -m app worker` (сервис `worker`), healthcheck — `procrastinate healthchecks`.

**Управление схемой.** Документация Procrastinate не предлагает рецепта для Alembic и оставляет учёт миграций приложению. Поэтому:

- первая ревизия Alembic применяет зафиксированный снимок `schema.sql` версии 3.10.0 (`backend/alembic/sql/procrastinate_3.10.0_schema.sql`) и полностью откатывает его в `downgrade`;
- обновление Procrastinate — отдельная ревизия Alembic, применяющая SQL-файлы из `procrastinate/sql/migrations` между версиями (с учётом `pre`/`post`), и новый снимок не создаётся;
- версия зафиксирована: Dependabot её игнорирует, unit-тест сверяет установленную версию со снимком и падает с инструкцией при расхождении.

`procrastinate schema --apply` не используется: он не идемпотентен и не знает о ревизиях Alembic.

### Последствия

- Хорошо: нет Redis; задачи и домен в одной транзакционной БД; миграции очереди — в общей истории Alembic с проверкой upgrade/downgrade в CI.
- Плохо: нагрузка очереди на ту же БД (приемлемо для масштаба проекта; метрика «очередь > 100 задач» — алерт, SPEC §13); обновление Procrastinate — ручная операция.

### Как проверяем

Integration-тест: upgrade → downgrade → upgrade, `check_connection` видит схему. Фаза 3: тест «дубликаты задач не создаются». Пересмотр — если очередь мешает OLTP-нагрузке.

## Плюсы и минусы вариантов

### Celery/Dramatiq + брокер

- Плюс: зрелые экосистемы.
- Минус: дополнительный сервис (запрещён SPEC §2); дедупликация и отложенные задачи — дополнительными библиотеками.

### Своя очередь

- Плюс: полный контроль.
- Минус: изобретение очереди — противоречит SPEC §1.7.
