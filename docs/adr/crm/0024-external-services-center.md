# ADR CRM-0024. Центр внешних сервисов: реестр, фоновые проверки без платных вызовов, журнал инцидентов, оповещения и выключатели

- Статус: accepted (2026-10-14, по рекомендации — поручение владельца, ORCHESTRATOR §8; пересматривается на гейте M3)
- Дата: 2026-10-14
- Авторы: агент CRM
- Связано: ORCHESTRATOR §3.13, §6 M3-CRM-12 (M3-CRM-11, M3-ERP-06); DECISIONS 2026-10-14 «Требование владельца: админ видит и контролирует все внешние сервисы»; SPEC §5.8, §10.1, §13, §13.1; ADR-0006, ADR-0013, ADR-0014, ADR-0017, ADR-0018, ADR-0020, ADR-0023

## Контекст и проблема

Владелец (2026-10-14): «админ должен видеть и контролировать работу всех внешних сервисов — Telegram-бот,
ИИ-вендоры, почтовые сервисы и т. д., всё, что интегрировано помимо двух основных систем». Сейчас
здоровье внешних сервисов разбросано: «Состояние системы» показывает готовность S3/LiteLLM, бота и бэкап,
«Модели ИИ» — платную пробу по кнопке и раз в час, «Подключения» — «Проверить связь» по кнопке, «Расходы» —
журнал LiteLLM. Нет единого списка, истории проверок, инцидентов, оповещений о восстановлении и способа
остановить сервис, который ведёт себя плохо. Новый внешний сервис может попасть в код незамеченным.

## Драйверы решения

- Одна консоль админа — CRM; минимум работы админа: система проверяет сама, ошибка — с подсказкой «что сделать» и ссылкой туда, где это исправляется (§3.13).
- Платных вызовов моделей нет: проверка вендора — без генерации (ORCHESTRATOR §7 п. 8, docs/systems/crm/CONVENTIONS.md §6.5).
- Сбой (неверный ключ, недоступный хост) виден за ≤ 1 мин, оповещение приходит, но без спама.
- Выключатель реально останавливает вызовы сервиса во всём ансамбле (CRM и ERP ходят в один LiteLLM).
- Штатные механизмы (LiteLLM admin API, Procrastinate, `MailService`, аудит), без новых зависимостей.
- Место для сервисов ERP (M3-ERP-06) без опроса ERP сейчас.

## Проверка на установленной версии (LiteLLM v1.105.0, 2026-10-14)

Одноразовые контейнеры `rt-spike-es-*` (`postgres:17-alpine` + `ghcr.io/berriai/litellm:v1.105.0`,
`STORE_MODEL_IN_DB=True`, конфиг как `infra/ai/litellm.config.yaml`), модели — `/model/new` с
`mock_response` (провайдер не вызывается, ключи фиктивные); контейнеры удалены. Исходник —
`litellm/proxy/health_endpoints/_health_endpoints.py`, `spend_tracking/spend_management_endpoints.py`,
`management_endpoints/model_management_endpoints.py`, `proxy_server.py`, `router.py`.

1. `GET /health` **вызывает каждую модель** (без `background_health_checks`) — платно, не используется.
   `GET /health/liveliness` и `/health/readiness` (`{"status":"healthy","db":"connected"}`) — без вызова моделей.
2. `GET /provider/budgets` (мастер-ключ) — бюджет и расход провайдера по `provider_budget_config`:
   `{"providers":{"anthropic":{"budget_limit":3.0,"time_period":"1d","spend":0.0,"budget_reset_at":…}}}`.
3. `GET /spend/logs/v2` — строка на вызов: `custom_llm_provider` (вендор, обслуживший вызов), `status`
   `success|failure`, `startTime`/`endTime` (задержка), `model_group`, `metadata.error_information`
   (`error_class`, `error_code`, `error_message`) — источник доступности, доли ошибок, p95 и расхода по вендору.
4. `POST /model/block` / `/model/unblock` `{"model_id"}` — блокирует deployment из БД: запрос к алиасу,
   у которого заблокированы все deployment, получает **403 «Model is blocked» без перехода на
   `router_settings.fallbacks`**. Для «снять с маршрута» блокировка одна не годится.
5. `POST /config/update` `{"router_settings":{"model_group_alias":{"dialog-model":"fallback-model"}}}`
   (эндпоинт админ-UI прокси, мастер-ключ) — применяется **сразу, без перезапуска**: `dialog-model`
   обслуживает deployment `fallback-model` (его ключ — тот, что уже лежит в БД LiteLLM; копировать ключи
   не нужно), в журнале `custom_llm_provider` = вендор запасной модели. Пустой `model_group_alias` —
   возврат. Значение хранится в БД прокси (`LiteLLM_Config`) и переживает перезапуск. Приоритет
   разрешения в роутере: `model_group_alias` выше имени группы. `fallbacks`/`provider_budget_config` из
   конфига при этом не меняются. Текущее значение — `GET /router/settings` → `current_values.model_group_alias`.

## Рассмотренные варианты

1. **Расширить «Состояние системы»** новыми строками, проверять при открытии страницы.
2. **Отдельный реестр в домене + фоновая задача Procrastinate + таблицы проверок/инцидентов/выключателей**;
   вендоры — по журналу LiteLLM и его бюджетам; выключатель вендора — `model_group_alias` прокси.
3. **Внешний мониторинг** (Uptime Kuma, Prometheus + Alertmanager) рядом с ансамблем.

## Решение

Выбран вариант 2.

**Реестр** (`domain/external_registry.py`, чистые функции): ключ, название и назначение по-русски, система
(`crm`/`erp`), источник данных (`crm` — проверяет CRM, `erp` — передаст ERP), способ проверки, частота
(`cheap` — раз в минуту, `heavy` — раз в 15 мин), место настройки (путь в CRM) и вид выключателя.
Сервисы CRM: Telegram Bot API, шлюз LiteLLM, **каждый вендор моделей отдельно** (из алиасов LiteLLM
`/model/info`, при недоступности — из `litellm.models.yaml`), Langfuse, почтовый релей, S3 (RustFS),
docling, хранилище резервных копий, TLS-сертификаты `crm.`/`erp.`/`cabinet.`. Сервисы ERP (M3-ERP-06) —
курсы ЦБ, тариф и ТН ВЭД, почта ERP, модели в ERP, S3 ERP, Sentry — строки с источником `erp`: состояние
берётся из `externals[]` в ответе ERP на integration `GET /health` (кэш коннектора 30 с, ничего сверх
существующей пробы); ERP не отвечает — «нет данных» без инцидентов (сбой самой ERP виден в «Состоянии
системы»), ERP без поля — «нет данных: обновите ERP».
Правило: новый внешний сервис принимается в код только со строкой в реестре (§3.13).

**Проверки** (без платных вызовов):

| Сервис | Как | Частота |
|---|---|---|
| Telegram | `getMe` (токен принят) + `getWebhookInfo` (`pending_update_count`, `last_error_message`, `last_error_date`) прямым HTTP к Bot API | 1 мин |
| Шлюз LiteLLM | `/health/liveliness` + `/health/readiness` (БД прокси) | 1 мин |
| Вендор | журнал `/spend/logs/v2` за 15 мин (доля ошибок, последняя ошибка) и `/provider/budgets`; за 24 ч — вызовы, ошибки, p95, USD, вызовы запасной модели | 1 мин / 15 мин |
| Langfuse | `GET /api/public/health` и `GET /api/public/projects` с ключами (ключи приняты); ключей нет — «не подключён» | 1 мин |
| Почта | `email_log` за 24 ч (отправлено/ошибки/в очереди); «проверка связи» — EHLO/STARTTLS/AUTH без отправки (ADR-0023) | 1 мин / 15 мин |
| S3 | `GET /health`; занятое место и число объектов по бакетам (`list_objects_v2`) | 1 мин / 15 мин |
| docling | `GET /health` | 1 мин |
| Резервные копии | heartbeat демона и возраст последней копии (`services/backups`, ADR-0013) | 1 мин |
| TLS | TLS-рукопожатие с проверкой цепочки, дней до `notAfter`; http/localhost — «не применимо» | 15 мин |

Статусы: `ok`, `warn`, `fail`, `unknown` (нет данных), `off` (не подключён / не применимо). У каждого
не-`ok` результата — «что сделать» и путь, где это исправляется. Пороги вендора: за 15 мин ≥ 3 вызовов и
≥ 50 % ошибок — `fail`, ≥ 20 % — `warn`; расход ≥ 100 % `provider_budget_config` — `fail`, ≥ 80 % — `warn`.
TLS: ≤ 7 дней — `fail`, ≤ 21 — `warn` (Caddy продлевает за 30 дней). Задачи: `external_checks_cheap`
(`* * * * *`) и `external_checks_heavy` (`*/15 * * * *`), каждая проба со своим таймаутом.

**Хранение** (одна миграция `0022_external_services`): `external_service_checks` (сервис, время, частота,
статус, задержка, итог, ошибка, подсказка, метрики JSONB; хранится 8 дней, чистит тяжёлая задача),
`external_service_incidents` (начало, конец, последняя ошибка, когда оповестили о сбое и восстановлении),
`external_service_switches` (выключен ли, кем, когда, причина, состояние применения JSONB). Агрегаты 24 ч /
7 дней (доля успешных проверок, сбои, p95 задержки) — SQL по проверкам; список для страницы — кэш 15 с.

**Инциденты.** Переход в `fail` открывает инцидент, `ok`/`warn` — закрывает (длительность = конец − начало);
`unknown`/`off` инцидент не меняют. **Оповещения**: одно о сбое на инцидент и одно о восстановлении (только
если о сбое сообщали); новый инцидент того же сервиса раньше `service_alerts.repeat_minutes` (60) после
прошлого оповещения — без оповещения (антиспам). Каналы — настройка `service_alerts`: личные сообщения
админам с подпиской на системные уведомления, канал команды (`fallback` — если в личку никому не
доставлено, как у монитора по ADR-0018; `always`; `never`), письмо активным админам и дополнительным адресам
через `MailService` (шаблон `service_alert`). Сбой Telegram оповещается почтой, сбой почты — в Telegram.

**Выключатели** (пароль админа, аудит `external_service.disable|enable`, баннер «выключено вручную»):

- **Вендор модели** — «снять с маршрута»: алиасы-чаты вендора (кроме `fallback-model`) получают
  `model_group_alias → fallback-model` через `/config/update` (п. 5); алиас эмбеддингов вендора блокируется
  `/model/block` (п. 4, перехода нет — честный отказ). Вендор запасной модели выключить нельзя
  (409 `service_not_switchable`, подсказка — сменить провайдера запасной модели в «Модели ИИ»). Значение
  `model_group_alias` целиком принадлежит CRM: каждая минутная проверка сверяет его с выключателями и
  восстанавливает, если оно разошлось (сброс БД прокси, смена модели в «Модели ИИ»).
- **Langfuse** — трейсы не пишутся (`integrations/langfuse.client()` → no-op), во всех процессах ≤ 30 с.
- **Почта** — пауза очереди: письма ставятся в журнал `queued`, воркер их не отправляет; «Включить» ставит
  ожидающие письма в очередь заново.
- **Telegram** — пауза исходящих: клиент на любое сообщение получает текст `texts.maintenance` («Технические
  работы…», ru/uz/en, не чаще раза в 10 мин на чат), диалог с ИИ не запускается; исходящие воркера (посты в
  канал, личные уведомления) пропускаются, «Ответить» из CRM — 409 `telegram_paused`.
- **Сервисы ERP** (кроме Sentry) — операция `PUT /externals/{code}/switch` в ERP: ERP хранит состояние и
  перестаёт вызывать сервис (курсы и ТН ВЭД — прогон пропускается, почта — письма не уходят, в журнале
  ERP `FAILED` «выключено из CRM», модели — нейтральный отказ, S3 — обращения отклоняются). CRM пишет
  строку и аудит только после ответа ERP 200; пароль админа — как у остальных выключателей.
- LiteLLM, S3, docling, бэкапы, TLS — без выключателя (остановка ломает CRM или не управляется из CRM).

**API** (admin, ресурс RBAC `external_services`): `GET /api/v1/admin/external-services`,
`GET …/{key}` (история проверок за 24 ч, сутки за 7 дней, инциденты за 30 дней), `POST …/{key}/check`,
`POST …/{key}/disable`, `POST …/{key}/enable`; ошибки ADR-0017. «Состояние системы» показывает одну
строку-сводку «Внешние сервисы» со ссылкой на центр.

### Последствия

- Хорошо: один экран для всех интеграций; сбой виден за ≤ 1 мин с подсказкой и ссылкой; инциденты и
  оповещения о восстановлении; выключатель вендора действует на CRM и ERP сразу, без перезапуска и без
  копирования ключей; ни одного платного вызова модели.
- Плохо: состояние вендора — по реальным вызовам: без трафика за 15 мин статус «нет вызовов» (не ошибка), а
  сбой ключа без трафика проявится с первым вызовом (бот при этом честно передаёт диалог человеку; проба по
  кнопке в «Модели ИИ» остаётся). Пока вендор выключен, вызовы в журнале LiteLLM идут с `model_group`
  исходного алиаса и вендором запасной модели — на «Расходах» они не считаются деградацией (`model_group` ≠
  `fallback-model`).
- Плохо: `/config/update` — эндпоинт админ-UI LiteLLM (`include_in_schema=False`); при обновлении LiteLLM
  проверка повторяется (тест на записанный ответ и чек-лист PR).
- Плохо: проверок ~20 строк в минуту (~200 тыс. строк за 8 дней) — чистка раз в 15 мин.
- Что меняется: миграция `0022_external_services`; `domain/external_registry.py`, `domain/external_status.py`,
  `integrations/external_probes.py`, `integrations/litellm_admin.py` (бюджеты, `model_group_alias`,
  блокировка), `services/external_services/*`, `tasks/external_services.py`, `api/v1/external_services.py`;
  `integrations/langfuse.py`, `bot/maintenance.py`, `services/mail.py`, `container.telegram_bot()`; настройка
  `service_alerts`, текст `texts.maintenance`; RBAC `external_services`; страница «Внешние сервисы»;
  том бэкапов подключён к воркеру только на чтение (`backups:/backups:ro`).

### Как проверяем

Unit: реестр (полнота, вендоры из алиасов, места ERP), правила статусов (таблицы кейсов), агрегаты,
переходы инцидентов, антиспам, правила выключателей (какие алиасы перенаправляются, вендор запасной модели);
respx — Telegram (успех, 401, таймаут, недоступен), LiteLLM (журнал, бюджеты, `model_group_alias`,
блокировка), S3/docling/Langfuse; SMTP — подставной транспорт. Integration: миграция up/down/up, API и матрица
ролей, «Проверить сейчас», выключатель с паролем и аудитом, оповещение. Vitest — страница. Пересмотр — если
LiteLLM уберёт `model_group_alias` из `/config/update` или появится штатный «disable provider».

## Плюсы и минусы вариантов

### Вариант 1 — строки на «Состоянии системы»

- Плюс: минимум кода.
- Минус: проверки только при открытой странице — сбой ночью никто не увидит; нет истории, инцидентов,
  оповещений о восстановлении, выключателей.

### Вариант 2 — реестр + фоновые проверки + инциденты + выключатели

- Плюс: всё в одной консоли, без внешних систем; оповещения с антиспамом; управление вендором на уровне шлюза.
- Минус: свои таблицы и задачи; вендор — по журналу реальных вызовов, а не синтетической пробой.

### Вариант 3 — внешний мониторинг

- Плюс: зрелые инструменты, графики.
- Минус: вторая консоль и второй вход для админа (против §3.13), нет связи с подсказками и коннекторами CRM,
  нет выключателей; ещё один сервис в ансамбле.

## Дополнение 2026-10-27 (W15-H3): политика оповещений

Решение архитектора (DECISIONS 2026-10-27). Оповещение по инциденту сервиса («Сбой» сразу, «Восстановлено» при первом `ok`,
антиспам `service_alerts.repeat_minutes`) заменено политикой по **причине**; поводом стали ложные письма на проде: каждая
5–6-я проверка api.telegram.org и api.anthropic.com отвечала дольше 3 с, проверка падала и на следующем проходе
восстанавливалась — около 25 писем за 3 часа.

- Проверка к внешнему сервису: таймаут ≥ 10 с (12 с) и один повтор внутри проверки до признания `fail`.
- «Сломано» — только непрерывный `fail` не короче 15 минут от начала полосы; короче — «Нестабильно» (жёлтое, без писем и Telegram).
  Короткие провалы не открывают инцидент и не создают записи причины.
- «Восстановлено» — только после непрерывного `ok` не короче 5 минут и только если о сбое сообщали.
- Не больше одного «Сломано» на причину за 24 часа: повторные провалы — «Нестабильно» в «Здоровье интеграций» и счёт «провалов за
  сутки» в следующем «Сломано», а не серия сообщений. Дедупликация — `external_cause_alerts` (переживает рестарт).
- «Ожидаемо на стенде» (`APP_ENV=dev`) и «Выключено намеренно» не оповещают. `service_alerts.repeat_minutes` устарел.
- Состояние (`broken`, `unstable`, `degraded`, `not_configured`, `disabled`, `expected`, `not_checked`), «кто исправляет» и действие
  вычисляет код CRM (`domain/external_cause.py`); интерфейс только показывает.

### Уточнение (W15-H3b)

- «Сломано» считается по проверкам: непрерывные 15 минут — между первой и последней проверкой полосы `fail`; затухание повторов
  1, 2, 5, 7 минут ставит проверку ровно на 15-ю минуту, четыре провала за 8 минут «Сломано» не дают.
- Подавление «раз в сутки» не отменяет сообщения: когда сутки с прошлого «Сломано» прошли, а сбой всё ещё непрерывный,
  приходит одно «Сломано» со сводкой «Нестабилен: N провалов с прошлого сообщения»; по окончании — одно «Восстановлено».
- «Восстановлено» — по `ok` проверки (дребезг не мешает), короткий провал между двумя `ok` отсчёт пяти минут не сбрасывает; пока
  «Восстановлено» ждёт, сервис проверяется раз в минуту (в том числе только тяжёлого уровня).
- Прежние алерты монитора `litellm_down` и `ai_failures` сняты: единственный отправитель «Сбоя» по шлюзу моделей и ответам ИИ —
  центр внешних сервисов. Остальные алерты монитора (очередь, бюджет, проба моделей, упавшие задачи) не менялись.
