# 0001. Два агента, решения принимает код

- Статус: accepted (2026-10-08, решение владельца продукта в обсуждении Фазы 0)
- Дата: 2026-10-08
- Связано: SPEC §1.2–1.5, §6, §7, §8; docs/systems/crm/BUSINESS.md §6 (C1–C2), §10, §11

## Контекст и проблема

Бот отвечает лидам и должен вовремя передавать их менеджеру. Ошибки дороги: выдуманная цена, «зря передал» > 15 %, «не передал» > 5 % (docs/systems/crm/BUSINESS.md §10), утечка документов между клиентами — недопустима. Нужно решить, сколько LLM-агентов в системе и кто принимает решения о стадии, оценке, эскалации и доступе к данным.

## Драйверы решения

- Объяснимость каждой передачи («почему к вам») и воспроизводимость решений.
- Тестируемость: пороги и правила — в параметризованных тестах, а не в промптах.
- Стоимость: дорогая модель — только там, где нужен живой диалог.
- Безопасность: модель не может расширить доступ к данным.

## Рассмотренные варианты

1. Один агент: диалог + квалификация + решения в одном промпте.
2. Два агента (диалоговый синхронный + асинхронный квалификатор со structured output), решения — детерминированный код.
3. Мультиагентная система (роутер, продавец, сервис, юрист…) с A2A.

## Решение

Вариант 2. Диалоговый агент (сильная модель, LangGraph) отвечает только по найденным фрагментам KB. Квалификатор (дешёвая модель) по событию возвращает `QualifierOutput` — сигналы. Стадия (state machine), score, триггеры эскалации и доступ к данным вычисляет код в `app/domain/` (чистые функции, `mypy --strict`, unit ≥ 90 %).

### Последствия

- Хорошо: каждое решение — запись `qualifier_runs`/`stage_transitions` с причиной; правила меняются через PR с тестами и eval; модель заменяема конфигом LiteLLM.
- Плохо: больше кода домена, чем при «одном умном промпте»; изменения порогов требуют разработчика (осознанно — `SPEC §6.3`).
- Код: `domain/stage_machine.py`, `scoring.py`, `triggers.py`, `escalation.py`; агенты ходят в данные только через MCP.

### Как проверяем

Параметризованные тесты переходов и триггеров (Фаза 3); evals escalation precision ≥ 0.85, recall ≥ 0.95, stage accuracy ≥ 0.85 (`SPEC §12`). Пересмотр — если метрики пилота не достигаются из-за жёсткости правил.

## Плюсы и минусы вариантов

### Один агент

- Плюс: меньше кода, быстрее старт.
- Минус: решения необъяснимы и нестабильны между версиями модели; дорогая модель на каждом шаге; сложно тестировать.

### Мультиагентная система

- Плюс: учебная ценность (docs/systems/crm/BUSINESS.md §3.4).
- Минус: оверинжиниринг для 2 ролей; дороже и медленнее; вынесен в Фазу 10 как эксперимент.
