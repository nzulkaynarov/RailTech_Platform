# 0017. Отдавать в ошибках API стабильный подкод `details.reason` и поле `details.field`

## Контекст и проблема

Тело ошибки — `{code, message, details}`, но `code` — класс ошибки (`conflict`, `validation_failed`). Фронт по нему показывает общее «Действие недоступно…» / «Проверьте поля формы», хотя причины разные: email занят, лида уже забрали, неверный текущий пароль, файл больше лимита. `message` — английский текст для логов, показывать его нельзя. Ошибки валидации FastAPI (`{"detail": [...]}`) и `HTTPException` (404 без `code`) шли в другом формате — фронт показывал «HTTP 404».

## Драйверы решения

- Пользователь видит, что случилось и как исправить; поле формы подсвечивается.
- Тексты для людей — на фронте (i18n), бэк отдаёт машинные коды.
- Не ломать существующих клиентов: `code` и HTTP-статусы прежние.

## Рассмотренные варианты

1. Подкод `details.reason` (enum `Reason`) поверх прежнего `code` + единый формат для всех ошибок.
2. Новые классы исключений с собственным `code` на каждый случай (`email_taken` вместо `conflict`).

## Решение

Вариант 1. `DomainError(message, reason=Reason.X, field=..., ...)` кладёт `reason` в `details`. Значения `Reason` — контракт с фронтом (тест `test_reason_values_are_a_stable_contract`). Один модуль `app/api/errors.py` переводит в `{code, message, details}` также `RequestValidationError` (`validation_failed`, `details.field` — первое поле с ошибкой, `details.errors` — все) и `HTTPException` (404 → `not_found`, 401/403/405 — по смыслу, прочие — `http_error`). В OpenAPI 422 описан схемой `ErrorOut` (вместо `HTTPValidationError`), так фронт получает тип `Reason`.

### Последствия

- Хорошо: фронт выбирает текст по `details.reason ?? code`; старый фронт продолжает работать по `code`.
- Плохо: два уровня кодов — нужно помнить, что `reason` уточняет `code`, а не заменяет.
- Что меняется: `app/domain/errors.py` (`Reason`), `app/api/errors.py`, `app/schemas/errors.py`, сервисы (подкоды на местах), `docs/api/openapi.json`, клиент orval.

### Как проверяем

Unit `tests/unit/test_api_errors.py` (формат, поле, 404, стабильность значений); integration — подкоды на реальных сценариях (`test_crm_actions`, `test_auth_rbac`, `test_customer`).

## Плюсы и минусы вариантов

### Вариант 1

- Плюс: обратная совместимость, один handler, расширяется без новых классов.
- Минус: подкод можно забыть передать — тогда фронт покажет общий текст по `code` (безопасный откат).

### Вариант 2

- Плюс: один уровень кодов.
- Минус: ломает фронт и HTTP-маппинг по классам, взрывает иерархию исключений.
