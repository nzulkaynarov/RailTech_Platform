# 0012. Роли Платформы — данные, а не код: две системные роли и роли, которые создаёт администратор

- Статус: accepted (требование владельца 2026-10-22; устройство — по рекомендации архитектора) · Дата: 2026-10-22
- Меняет: SPEC-v3 §4.1–§4.3 (шесть фиксированных ролей), ADR-0011 п. 3, решение владельца 2026-10-22 п. 8 («матрица только
  для просмотра до P4»), `packages/contracts/platform-rbac.yaml` (секция `roles`)

## Контекст

SPEC-v3 задаёт шесть ролей кодом (`MANAGER`, `DIRECTOR`, `SUPPLY`, `ENGINEER`, `ACCOUNTANT`, `ADMIN`), волны 7–8 реализовали их
так: перечисление в контракте, `users.platform_roles` в CRM, карта в ERP. Владелец 2026-10-22: Платформой пользуются и большие
компании, и маленькие, где несколько участков ведёт один человек; роли не должны быть захардкожены. Фиксированы только
**администратор** и **директор**; остальные роли администратор создаёт сам — название и рабочая матрица; должность — текст в
карточке сотрудника.

## Бенчмарк

| Продукт | Как устроено | Что берём |
|---|---|---|
| ERPNext | Role + Role Permission Manager: роль — запись, права — строки «DocType × уровень × действие»; системные роли (Administrator, System Manager) неизменны | роль — данные; каталог объектов и действий — код |
| Odoo | группы доступа по приложениям, «Пользователь: свои документы / все документы / администратор»; пользовательские группы поверх | уровни доступа по разделу; несколько групп у человека — объединение |
| Bitrix24 | «Права доступа» CRM: роли с матрицей «сущность × действие × охват» (свои / отдела / все), назначение сотрудникам и отделам | редактор-матрица, назначение ролей сотрудникам |
| HubSpot Enterprise | permission sets: шаблоны прав, которые администратор копирует и правит | предустановки как шаблоны, а не как жёсткие роли |
| Zoho CRM | profiles (что можно) отдельно от roles (иерархия видимости) | права — профиль; должность и иерархия — не роль |

Именованный паттерн: **«каталог возможностей в коде + роли как данные»** (capability catalog + role-based access with custom roles).

## Решение

1. **Каталог возможностей — в коде и контракте.** `packages/contracts/platform-rbac.yaml` перестаёт перечислять роли и становится
   каталогом: разделы и действия (`resources`, как сейчас), пункты меню (`menu`), поля с ограничением (`restricted_fields`),
   виды работы для «Моей очереди» (`queue`), и для каждого раздела и поля — **отображение в права бэкендов**: права CRM (casbin)
   и права ERP (`Permission`, 22 кода) для уровней `read` и `full`. Каталог меняется только PR с тестом; каждый элемент каталога
   тестируется один раз, и любая собранная из него роль корректна по построению.
2. **Две системные роли — неизменные.**
   - **Администратор** (`ADMIN`): сотрудники, роли, интеграции, тикеты; бизнес-данные по умолчанию не видит.
   - **Директор** (`DIRECTOR`): все бизнес-разделы с полным доступом, утверждения (резолюция, одобрение КП, служебные записки);
     Admin — чтение.
   Их матрица задаётся в каталоге, в интерфейсе не редактируется и не удаляется. Инварианты: в компании всегда есть хотя бы один
   активный администратор и хотя бы один активный директор.
   *Примечание R-1b (решение архитектора 2026-10-23, Q-R2-2).* «Все бизнес-разделы с полным доступом» уточнено: у директора
   `crm.leads` и `chats.external` — **чтение**. Директор видит воронку и внешнюю переписку, но не берёт лиды и не отвечает
   клиентам (нет «Взять в работу», в «Моей очереди» нет видов «ответить лиду» и «взять лид»); директору, который сам ведёт лиды,
   администратор выдаёт вторую роль (права объединяются). Директор видит Ролевую матрицу только для чтения (раздел `admin` —
   `read`: `GET /admin/roles*`), менять роли по-прежнему может только администратор.
3. **Остальные роли — данные.** Администратор в Admin · Ролевая матрица создаёт роль: название, описание, уровень по каждому
   разделу (полный / чтение / скрыто), поля с ограничением (видит себестоимость и маржу, цены поставщиков, только итоги).
   Хранение — CRM (источник истины по людям, ADR-0003): таблица ролей Платформы и связь сотрудник ↔ роли (несколько ролей у
   одного человека, права — объединение, как раньше). Журнал изменений — кто, что, когда, «до/после».
4. **Предустановки вместо жёстких ролей.** «Менеджер», «Снабженец», «Гл. инженер», «Бухгалтер» из SPEC-v3 §4.2 поставляются как
   шаблоны: при первом запуске создаются обычными редактируемыми ролями (переименовать, изменить, удалить). Маленькая компания
   может создать одну роль «Менеджер и бухгалтер» или выдать человеку две роли.
5. **Права в бэкендах вычисляются, а не перечисляются.** При сохранении роли или выдаче ролей CRM пересчитывает для каждого её
   сотрудника: базовую роль и политики casbin CRM, права ERP — объединение отображений по разделам с уровнем не ниже нужного;
   провижининг уходит в ERP списком `permissions` (роль «CRM Sync» ERP держит вычисленный набор; `role_codes` для сотрудников
   Платформы не используются). Пересчёт — фоновой задачей с итогом в карточке сотрудника (`erp_sync`).
6. **Процесс опирается на возможности, а не на названия ролей.** SPEC-v3 называет роли в процессе («снабженец и гл. инженер
   по резолюции», «бухгалтер подтверждает оплату»). В реализации: исполнители резолюции — сотрудники с доступом `full` к
   разделу расчёта; виза строки — по типу позиции: товар — возможность «расчёт товаров и склад», услуга — «расчёт услуг»
   (два новых элемента каталога вместо ролей SUPPLY/ENGINEER); подтверждение оплаты — `full` к «Счета и оплаты»; утверждения —
   директор или роль с возможностью утверждения (элемент каталога «утверждение КП и служебных записок», у директора всегда).
   «Моя очередь» собирается из возможностей сотрудника.
7. **Защита от ошибок администратора.** Перед сохранением роли — блок «Что произойдёт»: сколько сотрудников и какие разделы
   получат или потеряют; роль, выданную сотрудникам, нельзя удалить без переназначения; нельзя лишить компанию последнего
   администратора или директора.

## Варианты

1. **Оставить шесть ролей кодом** (SPEC-v3 как есть) — не подходит маленьким и большим компаниям одновременно. Отклонено
   требованием владельца.
2. **Полностью настраиваемые роли, включая администратора и директора** — риск запереть компанию (никто не может управлять
   сотрудниками или утверждать КП). Отклонено: две системные роли неизменны.
3. **Свободные права «по эндпоинтам»** вместо каталога разделов — непонятно администратору, легко открыть деньги и чужие данные.
   Отклонено: администратор работает с теми же разделами, что видит в меню.

## Последствия

- Контракт BFF 0.3.0: роль сотрудника — `{id, name, system}` вместо перечисления; `/admin/roles` — список, создание, изменение,
  удаление, предпросмотр последствий; `Me.roles` — ссылки на роли. `platform-rbac.yaml` v2: каталог с отображением в права
  бэкендов, системные роли, шаблоны.
- CRM: модель ролей Платформы, миграция данных (существующие коды → роли: `ADMIN`, `DIRECTOR` — системные, остальные четыре —
  роли из шаблонов), casbin по вычисленным правам (бывшая «задача P6» из решения Q-CRM-01-1 (д) становится частью этой работы),
  пересчёт и провижининг фоновой задачей.
- ERP: без изменений модели — получает вычисленный список прав; `role_codes` остаются для ручных сотрудников ERP до T4.
- Платформа: Admin · Ролевая матрица — редактор (решение «только просмотр до P4» отменено); очередь, меню, поля — по
  возможностям; названия ролей в интерфейсе — из данных.
- План: первым эпиком волны 9 (до экранов P2, которые опираются на роли в процессе); гейт P1 доводится на шести ролях как
  на предустановках. SPEC-v3 §4 читать с поправкой этого ADR; при следующей редакции SPEC владельцем — внести.
