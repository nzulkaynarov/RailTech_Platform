# 0027. Позиция каталога — одна сущность во всех документах

- Статус: accepted (владелец 2026-11-17, макет «Позиция каталога: одна сущность» —
  [DECISIONS](../DECISIONS.md) 2026-11-17, [план](../history/runbooks/plan-2026-11-12.md) §4.1 СУЩ-1) · Дата: 2026-11-17
- Уточняет [ADR-0012](0012-configurable-platform-roles.md) п. 6 (зона строки по типу позиции); основание —
  [аудит сущностей](../audits/2026-11-16-entities.md)

## Контекст

Владелец 2026-11-16: «раньше в erp была фича: если в запросе товары или услуги, которые отсутствуют в каталоге, они
автоматом заводились в каталог со статусом черновик… в КП можно всё что угодно записать?» и «собрать все сущности, чтобы
не городить мусор везде».

Сейчас строка расчёта и КП (`QuoteItem`) может жить без карточки (`product = NULL`): тогда она — текст
(`imported_raw_name`), тип «товар или услуга» хранится только в строке расчёта (`CalcLine.kind`). Черновик карточки
(`catalog/candidates.py`) рождается только при отправке КП и строку не связывает: следующая заявка начинается с того же
текста, услуга становится черновиком без типа, из счёта и заказа поставщику карточку не открыть. Счёт (`InvoiceItem`) хранит
описание текстом, строка заказа поставщику может быть без карточки, количество везде целое.

Срез прода 2026-11-17: 6 строк КП без карточки, 0 карточек, 0 счетов и заказов поставщику.

## Решение

1. **Строка любого документа ссылается на карточку.** Позиция не из каталога получает карточку-черновик (`Product` в
   статусе `DRAFT`) в момент, когда строка входит в расчёт: добавление строки, черновик из заявки, копия прошлого расчёта,
   «Расчёт готов» и отправка КП. Одна функция `catalog.candidates.link_quote_lines(quote)` идемпотентна и вызывается во
   всех этих точках; строка без карточки после неё — только раздел или примечание. Исключение (СЦ-10, 2026-11-20):
   строка расчёта, похожая на карточку каталога (`CalcLine.catalog_hint`), ждёт решения человека — «Выбрать» или «Новая
   позиция» — и до него не подтверждается; отправка КП и счёт связывают её в любом случае.
2. **Тип карточки — из строки.** Черновик получает `domain_type` по типу строки расчёта (`GENERAL_GOODS` или `SERVICES`),
   поэтому артикул и зона визы сразу правильные.
3. **Дубль ловится до создания** — внутри карточек нашей компании: артикул изготовителя, ГОСТ или чертёж, то же название
   без учёта регистра, «ё», пробелов, знаков препинания и латинских букв-двойников (`catalog.naming.name_key`, СЦ-10,
   2026-11-20). Архивная карточка строку не принимает; из одинаковых — опубликованная, затем старейшая. Похожие названия
   («Болт М22» и «Болт М24») не склеиваются. Совпало — строка связывается с найденной карточкой, у неё растёт счётчик спроса.
4. **Слова клиента не меняются.** `imported_raw_name` строки остаётся как было — это то, как позицию назвал клиент; название
   карточки — то, как её знает каталог.
5. **Переименование строки в расчёте.** Если строка связана с черновиком, который она же и создала (спрос 1, та же сделка),
   переименовывается черновик; иначе строка заново проходит поиск или создание карточки.
6. **Владелец карточки — наша компания** (`core.tenant.own_company_id`): компания — оператор сделок, каталог её.
7. **Разовая позиция** (деталь по чертежу) остаётся черновиком навсегда: в документах она есть, в витрине кабинета — нет.
8. **Перенос прода** — миграцией данных: строки КП без карточки проходят тот же `link_quote_lines`. Резервная копия базы
   перед выкладкой; откат миграции снимает связь у созданных ею черновиков.

Дальше, отдельными PR этого же решения: очередь «Новые из заявок» в каталоге Платформы (спрос, слить дубль, дополнить,
опубликовать); строка позиции (`ItemCell`) в расчёте, КП, заказе поставщику и кабинете; строка счёта и акта со ссылкой на
карточку; единица из справочника и дробное количество.

## Количество и единица (дополнение 2026-11-17)

9. **Количество дробное** — `Decimal(14, 3)`: 12,5 т, 0,75 м³; ввод — от 0,001. В API Платформы — число (`12.5`, целое —
   `12`), не строка; портальный контракт, где количество уже было строкой, — строкой без хвостовых нулей («150», «12.5»).
   Порядок — снизу вверх по цепочке, чтобы не было временных ограничений: **шаг 1** — склад, снабжение, поставки и запросы
   цены (остатки, движения, резервы, отгрузки, партии, заказ поставщику, приёмка); **шаг 2** — строки расчёта, КП, счёта,
   акта и договора. Серийный учёт дробное количество не принимает (число серийных номеров должно совпасть).
10. **Единица — из справочника** (`UnitOfMeasure`, коды UN/ECE Rec 20): строка хранит код (`unit_code`) и подпись на языке
   документа; свободный текст единицы остаётся только у строк, заведённых до перехода. Карточка каталога задаёт единицу по
   умолчанию для новых строк. Входит в шаг 2.
11. Контракты: `platform-bff.yaml` и `erp-portal.yaml` — минором выше `main`; выгрузка ERP `erp-internal.yaml` (версия ≥ 1.0,
   единственный потребитель — BFF, переведён в том же PR) — записью в `openapi-breaking-exceptions.yaml` со сроком.

## Последствия

- В расчёте больше нет состояния «Нет в каталоге»; бейдж «черновик» показывает, что карточку надо дополнить.
- Каталог наполняется из реальных заявок; отчёты по позициям становятся возможны без сопоставления текста.
- Черновиков станет больше — очередь «Новые из заявок» обязательна сразу после этого PR.
- Слияние дублей перевешивает строки всех документов на основную карточку; это необратимо для пользователя — с отменой
  в течение дня (решение очереди).
