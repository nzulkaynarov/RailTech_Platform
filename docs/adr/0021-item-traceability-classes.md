## Контекст

BUSINESS §12 записал «партии и серийные номера не делаем — интеграция с учётной системой». Склад ERP обезличен: остаток —
товар × склад × ячейка, отгрузка ссылается на резерв, а не на приёмку; ни поля, ни модели для партии или серийного номера нет
(as-is §0). Владелец 2026-11-02: любой товар или услуга должны иметь прослеживаемость — через год ответить, **откуда** единица
(изготовитель, поставщик, заказ, приёмка, сертификат) и **куда** она ушла (клиент, проект). Платформа универсальная: продаёт что
угодно, от техники с гарантией на каждую единицу до мелочи, поэтому глубина учёта не может быть одной для всех и не может быть
зашита в коде.

## Варианты

1. **Оставить §12: прослеживаемость — во внешней учётной системе.** Плюсы: нет кода. Минусы: учётной системы с партиями у
   компании нет; ответа «откуда эта единица» нет нигде; сертификат не связать с поставкой; гейт P7 (сквозной проход одного
   товара) не проходит.
2. **Полный складской учёт по партиям и серийным** (остаток по партиям, FEFO, карантин, себестоимость по партии). Плюсы: как у
   SAP и 1С:ERP в полном объёме. Минусы: переписывает склад, движения и резервы; недели работы; противоречит «просто для людей».
3. **Прослеживаемость как разрез, класс — данные категории** (выбрано). Класс учёта задаётся на **категории** номенклатуры и
   наследуется товаром: **S** — серийный (каждая единица), **L** — партия (номер изготовителя и срок годности), **N** — только
   количество (по умолчанию). Номер вводится на приёмке и обязателен на выбытии; склад по количеству не меняется, единицы
   прослеживаемости — отдельные записи со ссылками на строку приёмки и строки отгрузки. Эталоны сходятся именно здесь:
   Odoo «Track Inventory» (By Quantity / By Lots / By Unique Serial Number, номер обязателен при «Validate»), Business Central
   «Item Tracking Code» (Specific Tracking — номер на каждом выбытии), 1С:ERP «политика учёта серий» вида номенклатуры,
   SAP S/4HANA batch management и serial number profile; смена уровня у всех — только при нулевом остатке (to-be §3.1).

## Решение

1. **Класс — данные категории.** `catalog.Category`: «учёт единиц» `tracking` — `serial` (S) / `lot` (L) / `none` (N, по
   умолчанию) и «нужен документ соответствия» `requires_conformity_doc` (да/нет). Правит администратор (раздел «Компания ·
   Категории» Платформы, право `settings.edit` или `catalog.manage`). Товар наследует класс своей категории; товар без категории —
   N. Переопределение на карточке товара и подъём класса для строки договора — MVP-T1. Ничего отраслевого в коде: какие категории
   серийные, решает администратор.
2. **Единица прослеживаемости** (`inventory.TraceUnit`): вид (S/L), товар, номер изготовителя, срок годности (L), количество
   (S — 1, L — принятое), строка приёмки (откуда), статус «на складе» / «отгружен». Серийный номер уникален в пределах товара.
   Связь с отгрузкой — `inventory.TraceAllocation` (единица, строка отгрузки, количество): партия может уйти несколькими
   отгрузками.
3. **Приёмка** (`supply.GoodsReceiptLine`): для S — серийные номера списком (их число = принятому количеству), для L — номер
   партии и срок годности; если категория требует документ соответствия — № сертификата или декларации и срок действия (поля на
   строке приёмки; запись сертификата со своим жизненным циклом — MVP-T1). Для N на экране и в API ничего нового.
4. **Отгрузка клиенту** (`inventory.ShipmentLine`): для S — выбор серийных из принятых и свободных этого товара, их число =
   количеству строки; для L — партии и количество из каждой. Без номера для S/L отгрузка не проводится.
5. **Поиск по серийному номеру или партии** (Платформа, «Склад · Прослеживаемость»): назад — приёмка, заказ поставщику,
   поставщик, изготовитель, документ соответствия; вперёд — отгрузка, клиент, проект. Это запрос по связям, а не отдельное
   хранилище событий.
6. **Строка заказа поставщику ссылается на цену поставщика** (`supply.SupplierOrderLine.supplier_offer`), из которой создана:
   Incoterms и срок цены видны в заказе.
7. **Смена класса** при ненулевом остатке товаров категории по эталонам запрещена; запрет и переопределение на товаре — в MVP-T1.
   До него класс меняет администратор осознанно: единицы для уже принятого задним числом не создаются.

## Последствия

- BUSINESS §12: строка «партии, серийные номера» снимается — учёт партий и серийных есть как разрез прослеживаемости; полноценный
  складской учёт по партиям (остаток, FEFO, себестоимость, карантин) по-прежнему не делаем.
- Миграции — по одной на приложение: `catalog` (поля категории), `supply` (поля строки приёмки, ссылка строки ЗП на цену),
  `inventory` (`TraceUnit`, `TraceAllocation`); все обратимые. Склад по количеству, резервы и движения не меняются; для N всё как
  было.
- Контракты: BFF (`platform-bff.yaml`) — поля категории, строки приёмки и отгрузки, поиск; выгрузка `erp-internal.yaml`.
  Событий шины не добавляется (прослеживаемость — данные ERP; наружу — когда понадобится CRM, по GS1 CTE).
- Негативное: товар, принятый до включения класса, единиц не имеет — отгрузить его как S/L нельзя, пока администратор не вернёт
  класс N или не примет остаток заново (корректировкой). Это честное ограничение минимума, оно видно в ошибке отгрузки.
- После пилота — MVP-T1: журнал событий единицы (GS1 CTE), сертификат как запись, гарантия, карточка единицы, дробные количества,
  «Заполнить из документа» (ИИ: серийные и партии из упаковочного листа).
