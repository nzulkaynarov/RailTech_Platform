# 0009. Сопряжение CRM ↔ ERP — одноразовый код, ключи создаёт CRM, ERP хранит их в БД

- Статус: proposed (решение «по рекомендации», M3-ERP-05 + M3-CRM-10; статус проставляет владелец) · Дата: 2026-10-21 · ORCHESTRATOR §3.13

## Контекст
Шов CRM ↔ ERP держится на трёх секретах: токен CRM→ERP, токен ERP→CRM, секрет подписи вебхуков. До этой задачи их
выпускали руками (`openssl rand`), клали в `.env` ERP и вводили в «Подключения → ERP» в CRM; смена — правка `.env` и
перезапуск четырёх контейнеров. Принцип владельца (§3.13): админ вводит ключи один раз в CRM, всё, что система может
сделать сама, — делает сама, `.env` — только для загрузки и аварийного резерва.

## Бенчмарк
| Продукт | Как сопрягают | Что берём |
|---|---|---|
| **Tailscale** (auth key) | Админ выпускает в консоли одноразовый/срочный ключ регистрации; узел обменивает его на постоянные учётные данные, ключ после этого бесполезен | выпуск короткоживущего одноразового кода на одной стороне, обмен на постоянные ключи на другой |
| **GitHub App** (manifest flow) | Временный `code` (1 час, один раз) обменивается на учётные данные приложения: вебхук-секрет, ключ | код действует один раз и недолго; секрет вебхуков выдаётся в том же обмене |
| **Home Assistant / Matter / HomeKit** | Короткий код настройки на устройстве, вводится в контроллере; дальше стороны обмениваются ключами сами | код читаем и вводится руками (12 знаков без путаемых символов) |
| **Zapier / Stripe** (ключи API) | Ключ выпускается в одном кабинете и копируется в другой; ротация — «rolling key» (старый ключ живёт ограниченное время) | ротация без простоя: два действующих ключа на переходный срок |
Именованный паттерн: **«одноразовый ключ регистрации → обмен на постоянные учётные данные» (enrollment token / bootstrap
token) плюс «rolling key» для ротации**.

## Решение
1. **Код.** ERP выпускает код: суперпользователь в «Настройки → Интеграция с CRM» или `manage.py pairing_code` (первый
   запуск, когда войти некому). 12 знаков алфавита без `0/O/1/I/L` (59 бит), срок 15 минут (`PAIRING_CODE_TTL_SECONDS`),
   один раз; в БД только SHA-256 кода; новый выпуск гасит прежний неиспользованный. Код нигде не логируется и не пишется
   в аудит.
2. **Обмен.** Админ в CRM «Подключения → ERP → Подключить ERP» вводит адрес и код (и свой пароль — как при любом
   сохранении ключей). **CRM сама генерирует** три секрета (`token_urlsafe(48)`) и вызывает `POST /pairing/accept` с
   кодом вместо токена. Только после успеха сохраняет их у себя (`integration_secrets`, Fernet) и сразу делает «Проверить
   связь». Отказ ERP ничего не меняет у CRM.
3. **Хранение в ERP.** Таблица `ServiceCredential`: Fernet-шифртекст, ключ выводится из `SECRET_KEY` (как секрет 2FA,
   нового внешнего сервиса нет), `last4` для экрана. Аутентификация integration и подпись вебхуков берут секреты из БД,
   `.env` — запасной путь, пока в БД пусто; `SECRET_KEY` сменили и значения нечитаемы — ERP возвращается к `.env` и пишет
   ошибку в лог. Экран ERP — только чтение статуса («сопряжено / по .env / нет») и выпуск кода.
4. **Ротация «Обновить ключи».** CRM генерирует новую тройку и вызывает `POST /pairing/rotate` под действующим токеном.
   ERP хранит два токена CRM→ERP: новый и прежний (`expires_at`, 1 час, `PAIRING_ROTATION_GRACE_SECONDS`), затем прежний
   не принимается (401). Секрет вебхуков ERP переключает сразу; CRM заранее принимает оба (текущий и предыдущий, FIX-35) и
   сама снимает предыдущий по окончании перехода, а при приёме события срок проверяется сразу (не лениво).
   Новая тройка хранится как «ожидающая» до явного успеха. **Однозначный отказ** (ConnectError, 4xx) первой же
   попытки — CRM возвращает прежние секреты. **Неоднозначный исход** (ReadTimeout, 5xx, обрыв, непонятный ответ) —
   ничего не откатывается (ERP могла уже перейти на новые значения, откат сломал бы вебхуки), повтор «Обновить ключи»
   шлёт ТУ ЖЕ тройку: ERP идемпотентна по ней (контракт). Повторное сопряжение по коду снимает ожидающую тройку.
5. **Защита.** Приём кода — 10 попыток в час с адреса (`PAIRING_RATE`), 59 бит энтропии и срок делают перебор
   бессмысленным; отказы различаются (`PAIRING_CODE_INVALID/EXPIRED/USED`) ради понятной подсказки админу; сравнение
   токенов — `compare_digest`.

## Варианты
1. ERP генерирует ключи и отдаёт их CRM в ответе (как GitHub App). Отклонено: ключи, которые CRM обязана сохранить,
   возникали бы на чужой стороне и «потерянный ответ» терял бы их безвозвратно; CRM — единая консоль (§3.13) и владеет
   жизненным циклом ключей.
2. Общий секрет на двоих вводится руками с обеих сторон (как было). Отклонено §3.13.
3. mTLS / OAuth client credentials. Отклонено: два сервиса одной компании в одной сети, лишняя инфраструктура.

## Последствия
- Контракт 0.x → аддитивно: `POST /pairing/accept`, `POST /pairing/rotate`, схема `pairingCode`; существующие операции не
  менялись (CONTRACTS §2).
- `.env` остаётся рабочим: стенд без сопряжения ведёт себя как раньше. Первый запуск — `manage.py pairing_code` или экран.
- ERP→CRM токен пока только хранится (CRM выдаёт, ERP хранит); приёмник на стороне CRM — M3-CRM-11.
- Если ERP принял ключи, а CRM не смогла их сохранить (отказ БД), нужен новый код; при ротации прежний токен жив ещё час —
  можно повторить.
