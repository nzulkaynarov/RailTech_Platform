## 2. Что на самом деле ценно в каждом проекте

### 2.1. CRM — «входная дверь и голос компании»

Ценность, которую не даёт ничто другое в стеке:

1. **Telegram как канал с ИИ первой линии.** Ответ за секунды по базе знаний, на языке клиента
   (ru/uz/en), с передачей менеджеру и объяснимой причиной. Это единственное место, где лид вообще
   появляется без усилия человека. У B2B публичный приём лидов, по триажу 26-08 (находка 83),
   **недостижим** — маршрут перекрыт.
2. **Квалификация кодом, а не моделью** (стадии, score, триггеры, ADR-0001/0016) — прозрачная воронка.
3. **Рабочее место менеджера** — входящие с SLA, очередь J/K, карточка «резюме · переписка · почему».
   По бенчмарку 11-10 это уже лучше конкурента.
4. **Сервисный режим после сделки** (C5): клиент пишет в тот же чат «пришлите договор» — и получает.
5. **Инженерная платформа**: MCP-серверы с HMAC-контекстом, evals, LiteLLM-шлюз, бюджеты моделей,
   настройки без деплоя. BUSINESS.md §3.4 прямо говорит: это переиспользуемые компоненты.

Чего у CRM **нет и не должно быть** (BUSINESS.md §7): расчёт КП, договорный процесс, счета, акты, каталог
с ценами, склад. Сущность `deals` в CRM — три стадии и сумма, это учёт результата, а не процесс.

### 2.2. B2B — «машина сделки»

Ценность, которую CRM не повторит без годовой работы:

1. **Клин «заявка → КП → договор»** (ADR-0006): билдер КП с юнит-экономикой, каскадными наценками,
   историей правок, цепочкой согласования, версиями. `components/QuoteBuilder` — 5 800 строк, самая
   большая и самая ценная часть фронта.
2. **Документы по шаблонам компании**: договор, счёт, акт, квитанция, накладная; PDF off-thread;
   нумерация; формулировки выбором (E1–E4, D2). Это 11 500 строк `crm/services` и они работают.
3. **Публичная страница КП без логина**: клиент открывает ссылку, принимает с кодом из письма,
   договор материализуется сам. Это «портал клиента» в минимальном и правильном виде.
4. **ИИ-разбор заявки → автопривязка каталога → черновик КП** (ARCH-01, очередь `ai`). Монетизируемое
   ускорение, по ADR-0006 — «ров».
5. **Каталог / PIM с ТН ВЭД**, импорт Excel, Smart Match.
6. **Путь после контракта**: счёт → оплата → отгрузка → двусторонний акт (F1–G3).

Где B2B **тяжёл не по делу** (и откуда 55 находок аудита — почти все из операторской плоскости):

| Слой | Строк (прибл.) | Нужен ли при одном продавце — RailTech |
|---|---|---|
| Multi-tenant маркетплейс: `DealSellerRouting`, скрытая конкуренция, claim | ~2 000 | Нет, пока продавец один |
| KYC L1→L2→L3, заявки на роли, KYC-офицер | ~3 000 | Нет: клиентов знает менеджер |
| Подписки, entitlements, DEMO-водяной знак, лимиты кредитов | ~2 500 | Нет: платить некому, кроме самой RailTech |
| Операторские роли (SUPPORT/KYC_OFFICER/…), break-glass, 16 страниц `Admin*` | ~8 000 фронт + 4 000 бэк | Нет: оператор — это владелец |
| Книга контрагентов + слияние по ИНН + Leads | ~2 500 | Дублирует `clients`/`leads` CRM |
| Email-регистрация, setup-password, 2FA, сессии, lockout | ~3 000 | Частично: нужна только для сотрудников |

Итого порядка 25–30 тысяч строк (из 122) обслуживают гипотезу «платформа для многих продавцов с
подпиской», которую пилот не подтвердил: 5 компаний, из них продавец — RailTech. Именно этот слой
даёт ощущение «сложно и много недоработок»: 40 из 55 открытых находок — операторская админка,
подписки, права, KYC.

## 3. Где они пересекаются (и мешают друг другу)

| Понятие | В CRM | В B2B | Кто должен владеть |
|---|---|---|---|
| Лид | `leads` из Telegram, стадии, score, передача | `Lead` (форма сайта, публичный путь сломан) + `convert_lead_to_deal` | **CRM** |
| Клиент | `clients` + контакты + Telegram-идентичности | `Company` + `CounterpartyRelationship` + слияние по ИНН | **CRM** для контакта и истории; B2B — только реквизиты для документов |
| Переписка | `messages` (лид · бот · менеджер) | `Message` по сделке, ChatDrawer, email | **CRM** |
| Сделка | `deals`: open/won/lost, сумма | `Deal` FSM 9 стадий + КП + договор + счета | **B2B** для процесса; CRM хранит ссылку и итог |
| Документы клиента | загрузка файлов, выдача ботом | генерация по шаблонам | **B2B** генерирует, **CRM** выдаёт |
| Продукты | `products(key, name)` — справочник для KB | PIM с ценами, ТН ВЭД | **B2B** |
| Пользователи/роли | admin/manager/viewer, Casbin | SystemRole + OperatorRole + CompanyRole + WorkspaceRole | у каждого свои, но для сотрудников RailTech — один вход (см. §5, шаг 4) |

Две независимые «карточки клиента», две «ленты», два «лида» — вот источник путаницы. Пока они не
соединены, менеджер будет вести одного человека в двух системах.

## 4. Предлагаемая стратегия: два продукта — одна цепочка

Формула, которую вы сами назвали, верна, только её стоит уточнить:

> **CRM — привлечение и общение. B2B — расчёт, документы и исполнение.**
> Лид живёт в CRM, сделка живёт в B2B, а клиент видит и то и другое через один Telegram-чат.

Путь клиента целиком:

```
Telegram → бот CRM (KB, квалификация) → «Забрать» → менеджер в CRM
   → кнопка «Создать заявку в B2B» (клиент, контакт, потребность из резюме)
   → B2B: ИИ-разбор → каталог → КП → публичная ссылка на КП
   → ссылку клиенту шлёт БОТ CRM (а не только email) → акцепт с кодом → договор
   → счёт / оплата / отгрузка / акт в B2B
   → события B2B приходят в CRM: лента лида, стадия сделки, документы
   → клиент в Telegram: «где наш счёт?» → бот отдаёт PDF из B2B
```

Что это даёт бизнесу:

- Менеджер работает в одном окне (CRM) и переходит в B2B только ради расчёта — это и есть «шустрая»
  система плюс «машина сделки» без дублей.
- Клиенту не нужен логин в B2B вообще: Telegram + публичная ссылка на КП закрывают 90 % его сценариев.
  Регистрация, KYC и пароли клиента перестают быть нужны.
- B2B сбрасывает маркетплейс-балласт и становится тем, чем уже фактически является: **CPQ + документы +
  исполнение для RailTech**, с возможностью включить второго продавца позже.

### 4.1. Почему не «слить всё в CRM» и не «выкинуть CRM»

- Переписать билдер КП, документы по шаблонам и путь после контракта в стеке CRM (FastAPI + Refine) —
  это 30–40 тысяч строк и месяцы. Ценность нулевая: клиент разницы не увидит.
- Выкинуть CRM и дописать Telegram-бота в B2B — потерять агентную архитектуру (MCP, evals, бюджеты),
  которая по BUSINESS.md §3.4 и есть стратегический актив компании, и тащить Telegram в Django-монолит,
  где ИИ уже и так ограничен очередью Celery.
- Разные стеки — это не проблема, если граница ясна и контракт узкий (§5, шаг 1). Граница по
  «общение vs документы» — естественная: у Intercom/Front и у Odoo/PandaDoc она проходит там же.

## 5. План по шагам (от дешёвого к дорогому)

| # | Шаг | Где | Что делать | Результат | Оценка |
|---|---|---|---|---|---|
| 0 | **Зафиксировать решение** | оба | ADR в каждом репо: «CRM владеет лидом, клиентом и перепиской; B2B владеет сделкой, КП и документами». В B2B — ADR-0007, уточняющий ADR-0006: multi-seller и подписки — **заморожены**, не удалены | Одна картина в голове у всех | 1 день |
| 1 | **Контракт интеграции** | оба | `erp-mcp` в CRM (уже предусмотрен SPEC §15) с 5 инструментами: `create_deal_from_lead`, `get_deal_status`, `list_client_documents`, `get_document_file`, `get_quote_public_link`. В B2B — сервисный токен + вебхук `deal.changed`/`document.created`. Идентификаторы клиента — только из подписанного контекста (SPEC §1.5) | Код решает, модель предлагает — тот же принцип на границе | 1 нед |
| 2 | **Лид → заявка одной кнопкой** | CRM + B2B | В карточке лида CRM «Создать заявку» → B2B создаёт `Company`/`Contact`/`Deal` (DRAFT) с резюме потребности; `deals.external_ref` в CRM. B2B `Lead` + `LeadCreateView` — **удалить** (сломан, дублирует CRM) | Менеджер не перенабирает клиента | 1 нед |

| 4 | **Сервисный режим на документах B2B** | CRM | Инструмент `list_client_documents` ходит в B2B `GET crm/deals/{id}/documents/` (уже существует); `documents` в CRM остаются для файлов, которых в B2B нет (письма, сканы) | C5 работает на реальных договорах и счетах | 3 дня |
| 5 | **Заморозить маркетплейс-слой B2B** | B2B | Feature-flag `PLATFORM_MODE=single_seller`: скрыть 16 `Admin*`-страниц, подписки, entitlements, KYC-воронку клиента (KYC-пол для продавца оставить как «профиль заполнен»); оператор = суперпользователь. | 6 | **Один вход для сотрудников** | оба | Сотрудник RailTech входит в CRM; в B2B — по короткоживущему токену из CRM (CRM `security/auth.py` выдаёт, B2B принимает как `CustomUser` с `can_sell`). Keycloak позже (ADR-0005 CRM) | Один пароль, одна роль | 1 нед |
| 7 | **Дашборд владельца в CRM** | CRM | К `deals/summary` CRM добавить агрегаты из B2B: КП отправлено / принято, время до первого КП (TTFK, уже считается в B2B), дебиторка по счетам | Руководитель видит воронку от Telegram до оплаты в одном месте | 1 нед |

## 6. От чего отказаться (и от чего — нет)

**Заморозить в B2B** (флагом, не удалением — данные и миграции остаются):
- Multi-seller routing и скрытая конкуренция. Включить, когда появится второй продавец с реальными заявками.
- Подписки, entitlements, DEMO-водяной знак, кредиты ИИ. Монетизировать нечего, пока продавец один.
- Операторские под-роли, break-glass, заявки на роли, 16 страниц `Admin*`.
- KYC-воронка клиента: регистрация клиента, setup-password, уровни L1–L3. Клиент приходит через Telegram.
- Книга контрагентов и слияние по ИНН — после шага 2 источник клиента один (CRM).

**Удалить в B2B**: `Lead` + `LeadCreateView` + `AdminLeadsPage` (сломано, заменяется CRM); `Message` по
сделке и ChatDrawer — после шага 3 переписка живёт в CRM.

**Не трогать в B2B**: билдер КП, документы и шаблоны, публичная страница КП, путь после контракта,
каталог/ТН ВЭД, ИИ-очередь, 2FA и сессии для сотрудников.

**Не расширять в CRM** (BUSINESS.md §7 остаётся в силе): не делать свой КП, счета, каталог с ценами.
`deals` в CRM — только зеркало итога из B2B.

**Куда направить освободившиеся силы** — расширения CRM, ценные для клиента и уже запланированные
(PLAN Фаза 10, Q-019): ИИ-черновик ответа менеджеру, календарь для звонка, статусы поставок клиенту
в боте (из B2B `Fulfillment`), сайт-виджет и WhatsApp через тот же агент.

## 7. Риски предложения

| Риск | Мера |
|---|---|
| Два репозитория, два стека, два деплоя — рост операционной нагрузки | Узкий контракт (5 инструментов + 2 вебхука), контрактные тесты с обеих сторон, один runbook «цепочка CRM→B2B» |
| Утечка документов между клиентами через интеграцию | Идентификатор клиента в B2B-вызове — только из `telegram_identities` с `verified_at` (SPEC §1.5); B2B проверяет принадлежность документа компании сервисного запроса; негативные тесты |
| Заморозка маркетплейса воспринимается как «выбросили полгода работы» | Ничего не удаляется, флаг обратим; ADR фиксирует условие включения («второй продавец с ≥ N заявок в месяц») |
| CI B2B мёртв — интеграция без автоматических гейтов | Контрактные тесты должны входить в `make ci-local`; CRM-CI жив и может гонять контракт против B2B-стаба |
| Расхождение «клиента» в двух базах до шага 2 | Шаг 2 делать первым продуктовым; до него — правило «клиента заводит CRM» |

# Часть 2. Ответы на вопросы владельца и скоуп по сторонам (2026-10-12, вечер)

Вопросы: будет ли кабинет у клиента и как он туда попадёт; что делать с чатом в B2B; можно ли один
репозиторий и одну БД; какой скоуп на стороне CRM, на стороне B2B и на «свадьбу».

## 9. Кабинет клиента

### 9.1. Что есть сейчас

В B2B у клиента полный арендаторский кабинет: регистрация по e-mail, пароль, KYC L1→L2, команда
компании, заявки, КП, подписание договора как покупатель, запись оплаты, приёмка поставки и акта.
Это нужно, потому что отрезок «после контракта» двусторонний: без входа клиента нельзя подписать
договор, принять поставку и акт. Значит, **кабинет нужен**, вопрос только в том, какой и как в него
входят.

### 9.2. Бенчмарк

| Эталон | Как клиент попадает | Что видит |
|---|---|---|
| Odoo Customer Portal | ссылка-приглашение от продавца, без регистрации; пароль необязателен | свои КП, заказы, счета, поставки; подписывает КП онлайн |
| PandaDoc / Qwilr / DocuSign | magic-link на документ, аккаунт не нужен | один документ, действие по коду |
| Stripe hosted invoice | ссылка на счёт | счёт и оплата |
| Telegram-first сервисы в UZ (банки, госуслуги) | Telegram Login / Mini App | кабинет внутри Telegram |

Именованный паттерн: **Customer Portal по приглашению** (Odoo) + **magic-link на документ** (PandaDoc).
Ни один эталон не требует от клиента регистрации с паролем и KYC, чтобы посмотреть своё КП.

### 9.3. Предложение: три уровня входа, ни одного пароля

| Уровень | Что клиент видит | Как попадает | Что уже есть |
|---|---|---|---|
| **L0. Документ** | одно КП, кнопки «Принять / Отклонить», код из письма или бота | ссылка в Telegram от бота (и e-mail, как сейчас) | публичная страница КП в B2B — готова |
| **L1. Портал** | все свои сделки, КП, договоры, счета, акты, статусы поставок; действия покупателя | кнопка «Кабинет» в боте: CRM выдаёт подписанный короткоживущий токен на подтверждённую Telegram-идентичность, B2B принимает его и открывает портал | покупательский контекст B2B — есть; входа по токену нет |
| **L2. Рабочее пространство** | команда клиента, роли, несколько сотрудников | приглашение от менеджера RailTech (как Odoo «grant portal access»), пароль по желанию | есть целиком; остаётся для крупных клиентов |

Как это выглядит для клиента: бот пишет «Ваше коммерческое предложение готово» с двумя кнопками,
«Открыть КП» (L0) и «Кабинет» (L1). В меню бота постоянная команда «Кабинет». Клиент без Telegram
получает magic-link на e-mail из B2B (запасной путь, уже половина готова: код акцепта).

Идентичность клиента — Telegram-аккаунт, подтверждённый менеджером в CRM (`telegram_identities.verified_at`,
SPEC §1.5). Это тот же инвариант, что защищает документы в боте: кабинет открывается только тому, чью
привязку к компании подтвердил человек. Регистрация, пароли и KYC-воронка для клиентов **исчезают**;
«реквизиты компании заполнены» остаётся как условие печати документов.

Telegram Mini App (весь портал внутри Telegram) — вторая фаза: B2B-фронт уже адаптивный, но нужна
проверка `initData` на бэке и отдельный вход. Сначала токен-ссылка: дешевле и работает в любом браузере.

Юридическая подпись: клик в портале, как и сейчас, «согласовано в системе» с тегом `[MANUAL_MODE]`;
E-IMZO остаётся отложенным блокером владельца. Ничего не меняется.

## 10. Чат с менеджером в B2B

### 10.1. Что есть

В B2B три канала общения: `Message` по сделке (ChatDrawer покупатель ↔ продавец), `SupportButton`
(обращения в поддержку платформы), e-mail-уведомления (20 шаблонов). В CRM один: Telegram-диалог лида
с ботом и менеджером, с резюме, SLA и очередью.

### 10.2. Варианты

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. Два чата, синхронизация | сообщения B2B зеркалятся в ленту CRM и обратно | ничего не выключать | два входящих у менеджера; двусторонняя синхронизация — самый дорогой и хрупкий класс интеграций |
| **B. Один канал — Telegram через CRM** | в портале кнопка «Написать менеджеру» ведёт в бота с контекстом сделки (`/start deal_123`); чат B2B за флаг | одно входящее, одна история, SLA и ИИ-черновик работают на всём | клиент без Telegram пишет на e-mail (как сегодня) |
| C. Веб-виджет CRM в портале | тот же агент CRM, канал «сайт» (SPEC §15) | один канал и внутри портала | новый канал в CRM, это отдельная фаза |

**Рекомендую B сейчас, C следующим шагом** после того, как CRM получит второй канал. Паттерн Intercom:
один тред с клиентом, много точек входа. Обращения в поддержку из B2B (`SupportButton`) идут тем же
путём и становятся `service_requests` в CRM (ADR-0015).

Что остаётся в B2B из «общения»: e-mail как транспорт документов и уведомлений (счёт выставлен,
оплата получена, напоминание, акт ждёт), уведомления сотрудникам RailTech в самом B2B. Письма клиенту
продолжают уходить, но дублируются сообщением бота.

## 11. Один репозиторий и одна база

### 11.1. Факты, которые определяют ответ

- Стеки разные: FastAPI + SQLAlchemy 2 + Alembic + Procrastinate + aiogram + LangGraph против Django 6 +
  DRF + Celery + Channels. Фронты разные: Refine/Ant Design против shadcn/Tailwind/Zustand.
- Обе базы — PostgreSQL. CRM требует `pgvector`; B2B живёт на PostgreSQL 17 на отдельном DB-VPS, где
  `pgvector` ставится из PGDG пакетом.
- Тесты обеих систем делают `TRUNCATE`/пересоздание базы. На общей схеме они бы ломали друг друга.
- B2B CI мёртв по биллингу; CRM CI зелёный. Общий репозиторий означает общий CI.

### 11.2. Три смысла слова «объединить»

| Вариант | Что это | Стоимость | Что даёт | Вердикт |
|---|---|---|---|---|
| **O1. Два репо, два сервиса, контракт** | как в Части 1 | низкая | ничего не ломает | рабочий минимум |
| **O2. Монорепо, два сервиса, одна Postgres-инстанция, две базы** | `apps/crm`, `apps/b2b`, `contracts/`, `infra/`; история переносится `git subtree`; один compose, один деплой, один CLAUDE.md-карта, общий CI с фильтрами по путям | 3–5 дней на переезд | контракт меняется атомарно с обеих сторон в одном PR; агент видит обе системы в одной сессии; одна инфраструктура; CI B2B может ожить на условиях CRM-репо (проверить биллинг) | **рекомендую** |
| **O3. Один монолит на Django** | CRM переписывается как Django-приложения внутри B2B (`telegram`, `agents`, `kb`, `leads`), одна схема, один auth, один Celery; Refine-фронт CRM остаётся (Refine не привязан к бэкенду) | 3–4 недели переписывания ~13 тыс. строк слоёв моделей/сервисов/API; `domain/`, `agents/`, `mcp/`, `bot/` переносятся почти как есть | нет интеграционного слоя вообще; одна база по-настоящему | **отложить**; критерий пересмотра ниже |
| O4. Один монолит на FastAPI | переписать B2B | месяцы | — | нет |

Почему **не общие таблицы** даже в O2: две ORM с двумя системами миграций над одной схемой — классический
антипаттерн «shared database». `clients` в CRM и `Company` в B2B имеют разную форму, миграции будут
гоняться, тесты обеих систем чистят базу. Выгода общих таблиц (нет синхронизации) достигается
вебхуками с идемпотентными внешними идентификаторами (`crm_lead_id`, `b2b_deal_id`) при несравнимо
меньшем риске. Одна инстанция Postgres с двумя базами даёт экономию инфраструктуры без этого риска.

Критерий пересмотра в сторону O3: если после пилота контракт разрастётся сверх ~10 вызовов и ~10
событий, или синхронизация клиента/сделки станет источником инцидентов, или команда захочет одну
панель для всего. Тогда переписывать CRM в Django дешевле, чем наоборот, и Refine-интерфейс при этом
сохраняется. До этого O3 — преждевременная трата.

### 11.3. Раскладка монорепо (O2)

```
railtech/
  apps/crm/        ← crm-rt-ai целиком (backend, frontend, docs, скиллы)
  apps/b2b/        ← RailTech_SaaS_B2B целиком (backend, frontend, Docs, скиллы)
  contracts/       ← OpenAPI интеграционного API B2B, схема событий вебхуков, схемы MCP-инструментов
  infra/           ← compose для обоих стеков, одна Postgres (базы crm + railtech), Caddy, LiteLLM
  docs/            ← стратегия, ADR уровня «вся система», runbook «цепочка CRM→B2B»
  CLAUDE.md        ← карта: где что лежит и какой CLAUDE.md читать; конвенции остаются у приложений
```

Конвенции (ruff против black, Alembic против Django-миграций, Vitest там и там) остаются внутри
приложений: унифицировать их — отдельная работа без бизнес-ценности.

## 13. Решения, которые нужны от владельца

1. **Кабинет**: три уровня без пароля (§9.3, рекомендую) или оставить регистрацию с паролем и KYC
   для клиентов как сейчас.
2. **Чат**: один канал через CRM, чат B2B за флаг (вариант B, рекомендую), или два чата с синхронизацией.
3. **Репозиторий**: монорепо с двумя сервисами и одной Postgres-инстанцией (O2, рекомендую); общие
   таблицы — нет; слияние в один Django-монолит — по критерию из §11.2.
4. **Порядок**: волны 0→1→2 до показа, затем решение по 3–4.
