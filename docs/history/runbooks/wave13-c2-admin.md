## 2. Правила волны

- BFF только проксирует с токеном сотрудника и проверяет раздел каталога (`admin.*`, `company.settings`, `crm.kb` …); прав сверх
  каталога не добавляет. Новые разделы и действия — в `platform-rbac.yaml` (контракт раньше кода, тест отображения).
- Экраны — компоненты и токены Платформы (SPEC §5), тексты — словари i18n (ru/uz/en), блок «Что произойдёт» перед опасными действиями
  (ротация ключа, отключение подключения, повтор всех dead).
- Ничего из перечисленного не требует правки `.env` на сервере (SPEC §7.6), кроме паролей инфраструктуры, доменов и ключей шифрования.
- Старые фронты не трогаем: ни правок, ни удаления (кроме ссылок на них в письмах и уведомлениях бэкендов — это волна удаления).

## 3. «Готово, когда»

- **A0:** конкурентный тест «медленный подписчик (2,5 с) не задерживает быстрого» на настоящем PostgreSQL; замер на стенде p95 ≤ 2 с,
  max ≤ 3 с у быстрых подписчиков; `make -C packages/rt-bus check`, затронутые check-<app>.
- **A1–A6:** контракт BFF и (для A2) сервисов — `make contracts`; unit и e2e Платформы на каждый экран и действие; права — тест «без
  раздела — 403 в BFF и раздел скрыт в меню»; axe 0; снимки 1440 и 390; `make check-platform` и затронутые check-<app>.
- **A7:** отчёт `docs/audits/c2a_admin_gate_report.md`: каждый пункт §4.1–§4.3 — шаг в Платформе, результат, снимок; итог «паритет Admin
  достигнут / не достигнут»; список того, что ещё требует старых фронтов (должен быть пустым для административных функций).

### 4.3. Только CLI или Django admin

Шина и DLQ (CRM, ERP, EDS — `bus status|retry…`, Django admin ERP «Delivery/Inbox/Outbox/SubscriberState»); мастер компании ERP в Django
admin; справочники ExchangeRate, HSCode, Manufacturer, статусы, SystemSetting — Django admin; CLI CRM `create_admin`, `republish_identity`,
`webhook`, `test_alert`; CLI ERP `pairing_code`, `sync_tnved`, `ai_status`. В A2 — шина и DLQ; в A3 — справочники с API; остальное CLI —
эксплуатация, не административная работа владельца.
