## 2. Что есть в коде

**CRM (`apps/crm`)** — рабочая система из `crm-rt-ai`: ADR-0022 («Передан в бэк-офис» = `customer`), коннекторы «ERP» и
«Почта», источники лидов `web`/`phone`/`email`/`referral`, «Расходы» на ИИ, центр внешних сервисов (ADR-0024); передача в ERP,
приёмник событий ERP и SSO — были влиты без ревью, исправлены в волнах 1 и 3. Голова Alembic на 2026-10-20 — `0029_erp_seam_hardening` (актуальная — `alembic heads`).

**ERP (`apps/erp`)** — выделена из B2B (M1-ERP-01…10): канонические приложения, 6 ролей бэк-офиса, ИИ через LiteLLM, два слоя
каталога, курс на дату КП, Settings Hub; портальный API (`portal`, M2-ERP-01…03), интеграционный API, вебхуки и `erp-mcp`
(M3-ERP-01…03). Дефекты портала, интеграции и MCP, найденные аудитом (реестр: префиксы P, I, S), закрыты волнами 1–3;
хвосты — строки FIX-2xb и FIX-30…38 в PROGRESS.

**Cabinet (`apps/cabinet`)** — SPA без бэкенда (React 18, Vite 7, Tailwind 4, shadcn/ui), веб и Telegram Mini App, i18n
ru/uz/en. С волны 2 работает с настоящим портальным API ERP (контракт 0.3.0 после FIX-25, PR #84; сторож контракта в тестах ERP): код
акцепта по запросу, приёмка строк поставки, скан акта, вход `POST /auth/magic` из фрагмента ссылки.

**Инфраструктура** — `make up` поднимает ансамбль на `crm.`, `erp.`, `cabinet.localhost`; `legacy/b2b` удалена (M2-INF-01),
история — тег `b2b-final`. CI — один workflow, обязательная проверка «CI ok»; на PR — по путям, на push в `main` — всё.

## 4. Правила владельца (действуют для всех сессий)

- **Локальная проверка — основная, CI — финальная** (2026-10-19, `CLAUDE.md` корня «Среда разработки, тесты и CI»):
  итерации — затронутыми тестами, перед коммитом — `make check-<приложение>`, перед push — `make ci-local`; после
  открытия PR — остановиться и доложить, CI не опрашивать и не ждать; упал — скажет владелец или увидит лид (одна проверка
  состояния PR перед раундом, без логов), чинить локально. `PROGRESS.md` правит только лид — docs-PR после раунда (2026-10-20).
- **Резерв архитектора**: модели Fable нет — роль берёт Claude Opus, затем Gemini Argon, тем же промптом и по тем же
  правилам (ORCHESTRATOR §4.1); решения помечаются «(резерв …)», смена правил проекта резерву не разрешена.
- **Слияние — автоматическое** (владелец включил Allow auto-merge и удаление веток 2026-10-19): после ревью лид
  ставит `gh pr merge --auto --merge <n>`, GitHub вливает PR при зелёном «CI ok» и удаляет ветку; никто не опрашивает CI
  и не ждёт. Красный CI виден в PR — исполнитель чинит локально.
- Код попадает в `main` **только через PR** с зелёным «CI ok» (ruleset `main`, 2026-10-18); прямой push и `git merge` в `main` запрещены, «готово» в PROGRESS — только со ссылкой на влитый PR.
- Открытые вопросы решать **по рекомендации или бенчмарку** и продуктовому подходу (путь лида, клиента, сотрудника,
  администратора), записывать в `docs/DECISIONS.md` с пометкой «по рекомендации»; не останавливаться (ORCHESTRATOR §8).
- **Одна консоль администратора — CRM**: ключи и интеграции вводятся там один раз, без `.env` и перезапуска;
  администратор видит и контролирует все внешние сервисы (ORCHESTRATOR §3.13).
- Платные вызовы моделей (evals) — только с согласия владельца на конкретный прогон.
