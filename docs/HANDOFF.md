Что всплыло и чем закрыто (для памяти, повторять не надо):
- литерал PEM или тестового ключа в любой ветке краснит gitleaks у **всех** PR (CI сканирует все ветки) — собирать такие строки
  из частей (#323, #324), исключение в `.gitleaks.toml` не добавлять;

  `B-HANDOFF-1`);
- одноимённые компоненты OpenAPI ERP из параллельных PR (`Money`) — переименовывать при merge (`ProjectMoney`, #303);
- параллельные миграции CRM (Alembic) и ERP (Django `parties`) из соседних веток сводить в одну голову перед автослиянием (#408 `44c4ccb1a36d`, #401 `0014_part3_partner_price_visibility`); после новых обязательных полей в OpenAPI BFF перегенерировать MSW-моки Orval (`make gen-api` в `apps/platform`, #401);

### Шаг 1. Завершение регламента официальной подписи коммерческих документов (`SIGN-4`, ADR-0024)
Для исходящих писем в ЭДО подписание по реестру полномочий (`SIGN-1`…`SIGN-3`) и публичная страница проверки подлинности `/v/<код>` (`SIGN-VERIFY`) уже работают. Остался заключительный срез регламента для коммерческих документов ERP:
- **`SIGN-4` (ERP ↔ EDS — единый шаг «Подписать» для КП, договоров, счетов и актов):**
  - В контрактах шины (`packages/contracts/events/`) и AsyncAPI: запрос на подпись коммерческого документа из ERP в EDS (вид документа `quote` / `contract` / `invoice` / `act`, сумма в тийинах для проверки лимита в `SigningAuthority`, проект PDF/данные) и ответное решение `eds.signing.decided` («Подписано» со снимком должности, ФИО, основания, `verification_code` и времени подписи либо «Отклонено» с причиной).
  - В EDS: проверка полномочий подписанта по `SigningAuthority` (вид документа + лимит суммы + срок доверенности) и создание записи подписанного документа с выпуском `verification_code`, который сразу попадает в проекцию `/v/<код>` в ERP.
  - В ERP и Платформе: перевод выпуска КП, договора, счёта и акта на шаг «Подписать» (снятие водяного знака «ПРОЕКТ», печать должности, ФИО, основания полномочий и QR-кода `/v/<код>` на итоговом PDF); удаление старого обходного `force_approve` без записи в реестре полномочий.

### Шаг 2. Волны пути контрагента в кабинете (`J0`–`J4`, по карте пути 2026-11-04)
- **Волна `J0` «Не терять человека» (быстрые исправления входа и навигации):**
  - Разбор `start_param` в Telegram Mini App (`apps/cabinet`) для всех типов объектов: КП (`quote_<id>`), счёт (`invoice_<id>`), акт (`act_<id>`), поставка (`delivery_<id>`), чат (`chat_<thread>`), карточка товара партнёра (`product_<id>`), заявка партнёра (`partner_app`), чтобы кнопка в Telegram открывала сразу нужный документ, а не корень кабинета.
  - Письмо приглашения в кабинет: имя и контакты персонального менеджера (или снабженца для партнёра) и понятный первый шаг.
  - Честные пустые состояния во всех разделах Cabinet: человеческое объяснение и кнопка действия («Создать запрос», «Открыть каталог», «Загрузить прайс», «Написать менеджеру») вместо пустых таблиц.
- **Волна `J1` «Первые шаги и „Ждут от меня“»:**
  - Активационный блок «Первые шаги» на главной кабинета по активным ролям (`client`, `partner`), где каждый пункт закрывается реальным действием (подключить Telegram, проверить реквизиты компании, открыть первый документ / загрузить прайс).
  - Единая страница и блок «Ждут от меня» со счётчиком в левом меню кабинета: КП на решение, договоры на подпись, счета к оплате (с выделением просроченных), акты на приёмку, поставки в статусе «Доставлено», проект партнёрского договора на подпись, карточки товаров с замечаниями снабжения, непрочитанные ответы менеджера.
- **Волна `J2` «Команда и доверие»:**
  - Роль «администратор компании» у контрагента в кабинете: приглашение коллег своей компании, смена ролей (руководитель, бухгалтер, снабженец/менеджер, наблюдатель), мгновенное отключение уволенного сотрудника с гашением всех его активных сессий и токенов.
  - В «Профиле» кабинета: список активных сессий и кнопка «Выйти на всех устройствах».
  - Безопасная смена банковских реквизитов компании в кабинете: подтверждение одноразовым кодом и уведомление всем контактам компании и менеджеру.

## 5. Рабочее место (новый компьютер)

- Правила среды и CI — `CLAUDE.md` корня; worktree — только `.claude/worktrees/<задача>`; зависимости в новом worktree —
  `make -C apps/<app> install`, контракты — `cd packages/contracts && pnpm install --frozen-lockfile`.
- Доступ к прод-серверам: ssh-хосты `vps` (VPS1, приложения) и `db` (VPS2, база) — ключи и `~/.ssh/config` перенести с прежнего
  компьютера владельца (в репозитории их нет). Офлайн-копии секретов прода — `~/RailTech-secrets/` на прежнем компьютере
  (перенести защищённо, не через репозиторий).
- Docker Desktop: ≈ 12 ГБ памяти; стенд `make env && make up` на `HTTP_PORT=8088`; рядом — не больше двух наборов тестов ERP
  (`ERP_TEST_NS=<задача>`) и одного стенда волны. Тестовые тома периодически чистить по префиксам (`rt-itest-*`, `rt-erp-test-*`)
  — общие очистки Docker запрещены.
- `gh` авторизован на аккаунт владельца; автодеплой одобряется `gh api -X POST repos/nzulkaynarov/RailTech_Platform/actions/runs/<id>/pending_deployments -F "environment_ids[]=<env>" -f state=approved`.
