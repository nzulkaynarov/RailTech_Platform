## Q-10 · Биллинг GitHub Actions (только владелец) — **решено 2026-10-14: владелец обновил подписку GitHub; минуты расходуются экономно, см. DECISIONS**

**Контекст.** Первый прогон workflow на `main` (run 38381096602) упал без единого шага: «The job was not started because recent account payments have failed or your spending limit needs to be increased». Это настройка аккаунта GitHub, агент её изменить не может. Пока так — CI на GitHub не работает, гейт мержа — `make ci-local`.

**Варианты.**
1. Settings → Billing & plans: исправить способ оплаты / поднять spending limit для Actions (минуты GitHub-hosted; для приватного репозитория на Free — 2000 мин/мес бесплатно после разблокировки).
2. Self-hosted раннер на Linux-машине вне прода (задать переменную репозитория `CI_RUNNER=self-hosted`). На macOS сервис-контейнеры (`services:`) не поддерживаются, поэтому Mac владельца не подходит без переделки workflow.

**Рекомендация.** Вариант 1 — быстрее и без обслуживания; после первого зелёного прогона включить защиту `main` с обязательной проверкой `ci-ok`.

## Q-18 · Контракт портала: что добавить в `erp-portal.yaml` после FIX-14 (агент ERP → оркестратору, FIX-20) — **решено 2026-10-18 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** FIX-14 меняет поведение входа, а `erp-portal.yaml` в волне 1 не правит никто (runbook волны 1 §4). Расхождения, которые нужно закрыть в FIX-20: (1) `POST /auth/magic-link` теперь может ответить 429 `{"detail": "TOO_MANY_REQUESTS"}` (лимит `PORTAL_MAGIC_LINK_MAX_PER_HOUR`, по умолчанию 5 запросов в час на адрес; считаются и неизвестные адреса, чтобы 429 не раскрывал наличие контакта); (2) `POST /auth/telegram` и `GET|POST /auth/magic/{token}` для контакта архивной компании отвечают 403 `{"detail": "FORBIDDEN"}`; (3) ответ `ContactInviteResponse` внутреннего API (`POST /api/v1/accounts/contacts/{id}/invite/`) больше не содержит `invite_url` и `telegram_url` (сгенерированный `erp-internal-full.json` уже обновлён); `invite.cabinet_url` в ответе передачи клиента CRM (`erp-integration.yaml`) теперь — адрес кабинета без токена, схема не менялась.

**Варианты.** 1) описать 429 и 403 в FIX-20 вместе с остальным контрактом портала; 2) править `erp-portal.yaml` в PR FIX-14 (нарушает «контракт не правят вдвоём»).

**Рекомендация.** Вариант 1. Сопутствующее: в Cabinet текст для 429 `TOO_MANY_REQUESTS` на экране входа («Слишком много запросов, попробуйте через час») — задача агента Cabinet после FIX-20.

## Q-11 · Адрес ERP: где хранить и нужен ли пароль на каждое сохранение (M3-CRM-02) — **решено 2026-10-13 по рекомендации: вариант 1; см. DECISIONS**

**Контекст.** Коннектор «ERP» в «Подключениях» (PR `m3/crm-02-erp-connector`). Секреты (сервисный токен, секрет вебхуков) — в `integration_secrets` зашифрованными, как токен бота (ADR-0018). Адрес ERP — не секрет; ADR-0022 упоминал только `ERP_BASE_URL` из `.env`. В PR адрес хранится в `settings.integrations.erp_base_url` (правится из CRM, скрыт с экрана «Настройки»), `.env` — запасной источник; любое сохранение (даже только адреса) требует пароль админа, потому что оно переключает режим передачи клиентов (`local` ↔ `erp`).

**Варианты.**
1. Как в PR: адрес в `settings` с приоритетом над `.env`; пароль на каждое сохранение.
2. Адрес только в `.env` (как в ADR-0022 дословно), в CRM — лишь просмотр и секреты. Минус: смена адреса — доступ к серверу и перезапуск, против ADR-0018 («отдать админу всё»).
3. Как 1, но пароль только при вводе секретов. Минус: смена адреса без пароля меняет режим жизненного цикла.

**Рекомендация.** Вариант 1. Если владелец выберет 2 или 3 — правка в одном сервисе `services/erp_connector.py`, контракт API не меняется.

## Q-12 · Веб-форма «Запрос»: вложение и согласие на обработку данных (M3-CRM-05) — **решено 2026-10-14 по рекомендации: согласие — поле `consent: true` в API формы (реализовано в M2-CAB-03: 422 `consent_required`, `consent_given_at` лида), вложения — через Cabinet после приглашения; см. DECISIONS**

**Контекст.** ARCHITECTURE §17 перечисляет поля формы: имя, компания, телефон, e-mail, «что нужно», **вложение**. В `POST /api/v1/leads/web` (PR `m3/crm-05-lead-sources`) вложения нет: публичный приём файлов без аутентификации — отдельная поверхность атаки (размер, типы, хранение в S3 до привязки к лиду), а контракт загрузки для Cabinet не описан. Также в форме нет чекбокса согласия на обработку персональных данных: у Telegram-лида согласие берёт бот (`consent_given_at`), у веб-лида поле остаётся пустым (писать ему из CRM и так нельзя — Telegram-идентичности нет); при склейке с Telegram-лидом берётся согласие из бота.

**Варианты.**
1. Вложение — не в первой версии (как сейчас): клиент присылает файл в Telegram или менеджеру после звонка. Согласие — чекбокс на стороне Cabinet с текстом `texts.consent` CRM, в API поле `consent: true` обязательно, `consent_given_at`/`consent_version` пишутся при создании.
2. Вложение в первой версии: `POST /api/v1/leads/web` принимает `multipart` до 10 МБ, типы как у документов клиента, файл — в бакет вложений и в заметку лида; антиспам тот же. Плюс чекбокс согласия как в 1.
3. Вложение через Cabinet после приглашения (клиент загружает уже в кабинете), форма остаётся текстовой.

**Рекомендация.** Вариант 1 сейчас (чекбокс согласия — правка контракта на одну строку, сделает агент CRM после «да»), вариант 3 для файлов: в кабинете файл сразу привязан к компании и заявке ERP.

## Q-13 · Лимит запросов веб-формы по IP хранится в памяти процесса api (M3-CRM-05) — **решено 2026-10-14 по рекомендации: окно по IP в памяти процесса api до появления реплик; при репликах — таблица в Postgres; см. DECISIONS**

**Контекст.** Окно «не больше N запросов в час с одного IP» (`settings.web_form.rate_limit_per_hour`) живёт в памяти процесса api — как `RateLimitMiddleware` бота. На dev и prod сейчас один процесс api за Caddy, IP берётся из `X-Forwarded-For` (uvicorn `proxy_headers`), этого достаточно. При двух и более репликах api окно считается на каждую отдельно (лимит фактически умножается), после перезапуска — обнуляется.

**Варианты.**
1. Оставить в памяти до появления реплик (текущее состояние); зафиксировать в runbook `deploy.md`.
2. Перенести окно в Postgres (таблица `web_form_hits(ip, at)` с индексом и чисткой в cron) — +1 миграция и запрос на каждую отправку формы.
3. Ограничение на Caddy (`rate_limit` плагин) по пути `/api/v1/leads/web` — без кода, но лимит не из «Настроек».

**Рекомендация.** Вариант 1; при масштабировании api — вариант 2 (одна миграция, домен не меняется: `SlidingWindowLimiter` заменяется репозиторием).

## Q-14 · Портал: загрузки файлов нет — вложения «Нового запроса» (M2-CAB-02 → агенту ERP, M2-ERP-01) — **решено 2026-10-14 по рекомендации, контракт не менялся**

**Контекст.** `ClientRequestCreate.attachments` — массив `AttachmentRef {upload_id, name}`, но эндпоинта, который выдаёт `upload_id`, в `erp-portal.yaml` нет (в описании схемы: «заливка — multipart на `/documents`, появится с M2-ERP-01»). DECISIONS Q-12 (M3-CRM-05) решило, что файлы клиент присылает через Cabinet после приглашения.

**Варианты.** 1) `POST /uploads` (multipart, ≤ 10 МБ, типы как у документов) → `{upload_id, name}`, файл привязывается к заявке при `POST /requests`. 2) Загрузка в `POST /documents` с `kind=other`, `upload_id` = id документа. 3) Без вложений до пилота.

**Рекомендация.** Вариант 1 в M2-ERP-01 (контракт — агент ERP). **Обход в Cabinet до этого:** форма «Новый запрос» без вложений, подсказка «спецификации передайте менеджеру — загрузка файлов появится позже»; мок `attachments` не принимает.

## Q-15 · Каталог: фильтр `category_id` есть, а id категории нигде не отдаётся (M2-CAB-02 → агенту ERP) — **решено 2026-10-14 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** `GET /catalog` принимает `category_id`, но `CatalogItem.category` — только строка-название, справочника категорий нет. Фильтровать по id клиенту нечем.

**Варианты.** 1) `CatalogItem.category` → `{id, name} | null` и `GET /catalog/categories` → `[{id, name, count}]` (только опубликованные). 2) Только `category_id` рядом с `category`. 3) Фильтр по названию (`category=<name>`).

**Рекомендация.** Вариант 1 (как в Odoo eCommerce: публичные категории — отдельный справочник). **Обход в Cabinet до этого:** категории — названия из первой сотни опубликованных позиций (`page_size=100`), выбранная категория фильтруется на клиенте по выборке до 100 позиций (`src/lib/catalog.ts`); при каталоге больше 100 позиций фильтр неполон — снять обход сразу после правки контракта.

## Q-16 · Портал: у запроса нет строк и карточки, у сделки — номера для клиента (M2-CAB-02 → агенту ERP) — **решено 2026-10-14 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** `POST /requests` принимает строки, но `ClientRequest` их не возвращает и `GET /requests/{id}` нет — клиент не видит, что именно он просил. ## Q-17 · Коды `detail` портала, на которые опирается Cabinet (M2-CAB-02 → агенту ERP, M2-ERP-01) — **решено 2026-10-14 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** Контракт описывает статусы ответов, но не перечень кодов `{"detail": CODE}`. Cabinet показывает текст по коду, а неизвестный — по HTTP-статусу (CLAUDE.md Cabinet §9).

**Рекомендация.** ERP закрепляет в `erp-portal.yaml` (enum в описании ответов) коды, которые уже использует мок и словари Cabinet: 401 `UNAUTHORIZED`, `INVALID_INIT_DATA`; 403 `FORBIDDEN`; 404 `NOT_FOUND`; 410 `MAGIC_LINK_EXPIRED`; 409 `QUOTE_FINALIZED`, `QUOTE_EXPIRED`, `QUOTE_CODE_INVALID` (неверный код акцепта — 409 по контракту), `CONTRACT_FINALIZED`, `ACT_FINALIZED`; 422 `VALIDATION_ERROR`, `REASON_REQUIRED`, `INN_INVALID`, `TEAM_MEMBER_EXISTS`. Другой код ERP — Cabinet подстроит `apiErrors.*` одной правкой словарей.

## Q-19 · Коннектор «Почта» (M3-CRM-08): чем отправлять и где держать письмо с временным паролем до отправки — **решено 2026-10-14** (вариант 2, по рекомендации; ADR-0023 CRM, см. `DECISIONS.md`); бывш. «Q-12» — номер совпал с вопросом о веб-форме, переименован в FIX-52

**Контекст.** Письмо сотруднику содержит временный пароль. Отправка идёт задачей Procrastinate (не в пути запроса), значит тело письма должно где-то пережить постановку в очередь. В `procrastinate_jobs` аргументы лежат открытым текстом.

**Варианты.**
1. `aiosmtplib` + отправка в пути запроса (тело нигде не хранится, но релей держит запрос и нужна новая зависимость).
2. `smtplib` стандартной библиотеки в потоке + очередь; тело — в `email_log.body_ciphertext` шифртекстом Fernet (`SECRETS_KEY`), стирается после отправки или третьей попытки; без `SECRETS_KEY` письма с паролем не отправляются (409 `secrets_key_missing`).
3. Тело аргументом задачи (открытый текст в таблице задач — неприемлемо).

**Рекомендация.** Вариант 2. Сопутствующие решения по рекомендации: пароль админа на каждое сохранение коннектора (как у ERP, Q-11); язык письма — `ru`, пока у пользователя нет поля языка (Q-012); приглашение/сброс по почте сначала проверяют коннектор и только потом меняют пароль.

## Q-FIX12 · `erp-integration.yaml`: `DeliveryLine.quantity`/`unit` могут быть `null` (FIX-12) — **решено 2026-10-18 по рекомендации**

**Контекст.** В ERP у исполнения сделки (`sales.Fulfillment`, один к одному со сделкой) нет количества и единицы; проекция клиента подставляла `1` и «шт». FIX-12 требует «не выдумывать количества: нет данных — `null`», а `DeliveryLine.quantity` в контракте — строка без `null`. Файл `erp-integration.yaml` по плану волны 1 правит FIX-10 (409 `EMAIL_CONFLICT`).

**Варианты.** 1) Сделать `quantity` и `unit` в `DeliveryLine` nullable (узкая правка двух полей, сгенерированные клиенты пересобраны). 2) Не отдавать ключи, когда данных нет. 3) Оставить `1`/«шт».

**Рекомендация.** Вариант 1 — единственный, где ответ однозначен для бота и не выдумывает данных. Конфликт с FIX-10 возможен только в `erp-integration.yaml` и `packages/contracts/generated/*` (разные участки) — тот, кто сливается вторым, делает `git merge origin/main` и `make contracts`.

## Q-FIX11 · Права менеджера CRM в ERP и «своя компания» на стенде (FIX-11) — **продолжено по рекомендации, решение владельца нужно до включения `PLATFORM_SSO_ENABLED` для менеджеров**

**Контекст.** (1) Карта «роль CRM → права ERP» раньше клала в токен коды, которых нет в ERP, и всем менеджерам — `quote.view_cost_margin` (себестоимость и маржа). Теперь коды — только из каталога ERP (`ErpPermission`, 22 кода). Бизнес-решение, что именно может менеджер продаж в ERP, принимает владелец. (2) Роли бэк-офиса применяются к членству в «своей компании» (`core.tenant.own_company()`): если `OWN_COMPANY_ID` не задан и в ERP нет компании-продавца с активными участниками (чистый стенд), провиженный менеджер членства не получает и в ERP ничего не видит; суперпользователь (роль `admin` в CRM) работает без членства.

**Варианты.** (1) а) `manager` → `deal.manage`, `quote.build`, `quote.edit_pricing`, `quote.send`; `viewer` → ничего; `admin` → суперпользователь ERP; б) как а), плюс `contract.manage` и `quote.review` (роль «Расчёт» целиком, кроме `quote.view_cost_margin`); в) только `deal.manage` — остальное админ ERP добавляет ролью вручную. (2) а) на стенде и проде завести «свою компанию» в ERP (реквизиты в «Настройках») и задать `OWN_COMPANY_ID`; б) создавать компанию провижинингом (нарушает «CRM знает только людей»).

**Рекомендация.** (1) а) — минимум для работы менеджера по запросам и КП без себестоимости; расширять права ролью в «Настройках → Команда» ERP. Реализовано так; смена — правка `app/domain/erp_permissions.py` и таблицы в `sso-token.md`. (2) а) — проброс `OWN_COMPANY_ID` в compose/`.env` — задача инфраструктуры (M5-INF-01, `infra/compose/base.yml` в FIX-11 не правится: файл FIX-15).

## Q-FIX21-1 · `document_id`, `pdf_document_id`, `scan_document_id` портала: у PDF договора, счёта, акта, КП и скана акта нет записи в `GET /documents` (FIX-21) — **решено в FIX-23 (2026-10-19) по рекомендации, кроме `scan_document_id` — см. Q-FIX23-3**

**Контекст.** Контракт 0.2.0 отдаёт `Contract.document_id`, `Invoice.document_id`, `Act.document_id`/`scan_document_id`, `Quote.pdf_document_id` — id документа из `GET /documents`. В ERP такого документа нет: `documents.GeneratedDocument` не связан с договором, счётом, актом и КП (их PDF лежат в `pdf_file` самих моделей, скан акта — `Act.signed_file`). Прежний код подставлял в `document_id` id самого договора — ссылка вела на чужой документ или в 404.

**Варианты.** 1) Выпускать `GeneratedDocument` при каждой подписи/выставлении и хранить связь в самих моделях (миграции в `sales`/`finance`). 2) Отдавать в `GET /documents` проекцию «виртуальных» документов (вид + id источника) и считать `document_id` из неё, не заводя новых таблиц. 3) Оставить `null` и убрать поля из контракта.

**Рекомендация.** Вариант 2 в FIX-23 (он отдаёт PDF КП, договора, счёта и акта «существующим рендером»). До этого сериализаторы честно отдают `null`; сторож FIX-21 уже проверяет, что любой ненулевой `*_document_id` присутствует в `GET /documents`.

**Решение (FIX-23).** Вариант 2: `GET /documents` — проекция выпущенных КП, договоров, счетов, актов и накладных плюс выпущенные `GeneratedDocument` клиентских видов (договор, счёт, акт); идентификатор — `pk * 8 + слот вида` (`portal/services/documents.py`), без новых таблиц. `document_id` / `pdf_document_id` указывают на этот id, пока документ выпущен, иначе `null`; файл — `GET /documents/{id}/file` (PDF существующим рендером, не готов — 202 и рендер в очереди). `scan_document_id` акта — тот же id (скан заводит приёмка FIX-22), см. Q-FIX22-3 / Q-FIX23-3.

## Q-FIX36-1 · HTTP 401/400/429 у erp-mcp и поведение клиента SDK (FIX-36, для M3-CRM-07) — **решено архитектором 2026-10-20 (резерв Opus): вариант 1, M3-CRM-07**

**Контекст.** Контракт (`mcp-tools.json`, CONTRACTS §5) требует HTTP-коды: ошибка контекста — 401 `INVALID_AGENT_CONTEXT`, невалидные аргументы — 400 `INVALID_ARGUMENTS`, лимит — 429. **Рекомендация.** Вариант 1: контракт сохраняется, различение — в клиенте CRM (одна функция разбора исключения с кодом статуса), тест на каждый из трёх кодов — в M3-CRM-07. Вариант 2 — только если разбор исключений в клиенте SDK окажется хрупким.

## Q-FIX31-1 · Ключ идемпотентности передачи: от `crm_client_id` и содержимого, а не только от `crm_client_id` (FIX-31)

**Контекст.** Задача просила ключ, детерминированный от `crm_client_id` (и «версии передачи», если повторная передача по смыслу новая). ERP отвечает 409 `IDEMPOTENCY_CONFLICT` на тот же ключ с другим телом. Между попытками тело может измениться (менеджер добавил контакт, поправил ИНН) — ключ только от `crm_client_id` запер бы клиента в 409 на 7 дней (срок хранения ключа).

**Решение исполнителя.** `uuid5(crm_client_id, SHA-256 тела)`: повтор с тем же телом (таймаут, ретрай задачи) шлёт тот же ключ и получает сохранённый ответ; изменённое тело — другой ключ, а дублей нет, потому что ERP ищет компанию по `crm_client_id` (200 с теми же id). «Версии передачи» не вводил: по смыслу повторная передача всегда та же передача (ERP идемпотентен по клиенту).

**Нужно решение.** Нет, если подходит. Если нужен ключ строго от `crm_client_id` — ERP должна перестать отвечать `IDEMPOTENCY_CONFLICT` для `/clients/handoff` (правка контракта).

## Q-FIX33-1 · Постоянные отказы CRM на вебхук: 200 и запись `rejected`, а не 4xx (FIX-33)

**Контекст.** CONTRACTS §3: «CRM отвечает 200 быстро»; ERP ретраит любой не-2xx до 24 ч. Раньше CRM отвечала 422 на сломанное тело, неизвестный тип события и расхождение заголовка `X-Event-Type` с телом — ERP зря повторяла бы сутки. Конверт у CRM строгий (`extra="forbid"`), поэтому и новое необязательное поле ERP тоже давало бы 422.

**Решение исполнителя.** 401 — только неверная или отсутствующая подпись (проверяется по сырому телу ДО любого разбора и ДО проверки остальных заголовков). При верной подписи: неверный `X-Event-Id`/нет `X-Event-Type` — 422 (ошибка клиента ERP, ретрай бессмыслен, но вызов не наш); тело, которое CRM не принимает (не JSON, неизвестный тип, поля вне схемы, расхождение с заголовком), — строка `erp_incoming_events` со статусом `rejected` и текстом причины, ответ 200. Строка видна в центре внешних сервисов («События из ERP»).

**Нужно решение.** Закрепить в CONTRACTS §3: «постоянный отказ — 200 + журнал CRM». Побочный вопрос: смягчить `extra="forbid"` в конверте до терпимого читателя — это FIX-35 (дискриминированные модели).

## Q-FIX33-2 · Сверка `erp_company_id`: клиент без сопоставления принимает его из события (FIX-33)

**Решение исполнителя (вариант «применить», не «ждать»).** Если у клиента `erp_company_id` пуст, событие применяется и записывает сопоставление: `crm_client_id` в подписанном конверте ERP берёт из сопоставления, которое создала наша же передача. Ожидание привело бы к событию, зависшему навсегда при сбое передачи. ## Q-FIX33-3 · Порядок по `occurred_at` и Q-FIX30-1 (стадия документами без `deal.stage_changed`) (FIX-33)

**Контекст.** `deals.external_stage_at` хранит `occurred_at` последнего применённого события со сделкой. Событие старше него не меняет `external_stage`, название, сумму и валюту зеркала, но попадает в ленту. Итог сделки `deal.won`/`deal.lost` применяется ВСЕГДА (`deals.stage`, `lost_reason`, `closed_at` = `occurred_at` итога) — иначе опоздавший итог терялся бы навсегда; итоги упорядочены между собой по `closed_at` (более старый `won` не переоткрывает более новый `lost`). Устаревшее событие, чьё сообщение клиенту описывает текущее состояние (`delivery.eta_changed`, `delivery.status_changed`, `deal.stage_changed`), в бот не уходит, остальные (КП, счёт, акт) доходят. Равное время применяется (порядок прихода).

**Как уживается с Q-FIX30-1.** Стадия сделки меняется документами (КП, счёт, оплата, акт) без `deal.stage_changed`, но каждое событие со сделкой несёт `deal.stage`, посчитанное `stages.py` на момент события. Поэтому «стадия сделки в CRM» — это стадия из самого свежего по `occurred_at` события любого типа; `eta_changed` после `paid` её не откатывает. Пока события нет, CRM изменения стадии не видит — если нужен `deal.stage_changed` при смене стадии документами, это отдельная задача ERP. `deal.won` по Q-FIX30-1 уходит при подписании договора и несёт `deal.stage = contract`, а CRM пишет `external_stage = won` и `stage = won`, даже если счёт (`invoice.*`) пришёл раньше; следующее по времени событие (например, `invoice.issued`) вернёт `external_stage` в стадию исполнения — по замыслу Q-FIX30-1 «won» и «исполнено» разные шкалы, локальный итог `deals.stage` не откатывается.

## Q-FIX33-4 · Telegram: не больше одного раза на событие (at-most-once) (FIX-33)

## Q-FIX35-1 · `429 TOO_MANY_REQUESTS` в ответах integration (FIX-35, Q-FIX30-4) — для архитектора

**Предлагаемая правка (дословно).** В `packages/contracts/openapi/erp-integration.yaml`:

2. В каждую из 12 операций добавить `'429': {$ref: '#/components/responses/TooManyRequests'}`; в `Error.detail.examples` добавить `TOO_MANY_REQUESTS`.

## Q-FIX35-2 · Подпись вебхука не покрывает `X-Event-Id` и `X-Timestamp`; окно `X-Timestamp` (FIX-35, P2 ревью FIX-33) — для архитектора

**Контекст.** `X-Signature = sha256(HMAC(secret, body))`: заголовки `X-Event-Id` и `X-Timestamp` не подписаны, поэтому перехваченное тело можно переслать под новым `X-Event-Id` и обойти идемпотентность. Формат подписи — контракт, в FIX-35 он **не менялся**. Дешёвая защита, реализованная сейчас: CRM хранит `sha256` сырого тела каждого принятого события (`erp_incoming_events.body_sha256`); тело, чей хеш уже принят под другим `X-Event-Id`, — 200 и строка `rejected` с текстом `replayed body: already received as event <id>`, без обработки. Ограничения: хеш защищает от повтора ровно того же тела, но не от подмены заголовков; журнал не очищается (индекс по хешу растёт вместе с таблицей); два законных события ERP с побайтно одинаковым телом (одно `occurred_at` до микросекунды) второе будут отклонены (на практике не встречается).

**Предлагаемая правка контракта (дословно).** В `docs/CONTRACTS.md` §3 и в `description` корня `events.schema.json`: «`X-Signature: sha256=<HMAC(WEBHOOK_SECRET, f"{X-Event-Id}.{X-Timestamp}.{body}")>`, где `X-Timestamp` — UTC в формате ISO 8601 с `Z` или смещением. CRM отклоняет запрос (200 и запись `rejected`, не 401: ретраи не помогут), если `|now − X-Timestamp| > 300 с`; ERP при ретрае подписывает заново с актуальным `X-Timestamp`, а `occurred_at` в теле остаётся временем события. Переход: CRM принимает обе схемы подписи (старую — только тело), пока ERP не выкатит новую; затем старая схема отключается настройкой `ERP_WEBHOOK_SIGN_LEGACY=false`.»

**Рекомендация.** Принять отдельной задачей после волны 3 (ERP и CRM меняются парой, как ротация секрета: сначала CRM принимает обе схемы). Хеш тела оставить как второй рубеж.

## Q-FIX35-3 · Дефект `Contact` в `erp-integration.yaml`: `allOf` с закрытой `ContactIn` (FIX-35) — для архитектора

**Рекомендация.** Принять первый вариант (`unevaluatedProperties: false` на `Contact`); после правки `allof_safe` в сторожe удаляется.

## Q-FIX55-1 · Что значит `QuoteLine.promised_date` в портале и откуда её брать (FIX-55, m2 D-3) — для архитектора
