## Q-10 · Биллинг GitHub Actions (только владелец) — **решено 2026-10-14: владелец обновил подписку GitHub; минуты расходуются экономно, см. DECISIONS**

**Контекст.** Первый прогон workflow на `main` (run 38381096602) упал без единого шага: «The job was not started because recent account payments have failed or your spending limit needs to be increased». Это настройка аккаунта GitHub, агент её изменить не может. Пока так — CI на GitHub не работает, гейт мержа — `make ci-local`.

**Варианты.**
1. Settings → Billing & plans: исправить способ оплаты / поднять spending limit для Actions (минуты GitHub-hosted; для приватного репозитория на Free — 2000 мин/мес бесплатно после разблокировки).
2. Self-hosted раннер на Linux-машине вне прода (задать переменную репозитория `CI_RUNNER=self-hosted`). На macOS сервис-контейнеры (`services:`) не поддерживаются, поэтому Mac владельца не подходит без переделки workflow.

**Рекомендация.** Вариант 1 — быстрее и без обслуживания; после первого зелёного прогона включить защиту `main` с обязательной проверкой `ci-ok`.

## Q-18 · Контракт портала: что добавить в `erp-portal.yaml` после FIX-14 (агент ERP → оркестратору, FIX-20) — **решено 2026-10-18 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** FIX-14 меняет поведение входа, а `erp-portal.yaml` в волне 1 не правит никто (runbook волны 1 §4). Расхождения, которые нужно закрыть в FIX-20: (1) `POST /auth/magic-link` теперь может ответить 429 `{"detail": "TOO_MANY_REQUESTS"}` (лимит `PORTAL_MAGIC_LINK_MAX_PER_HOUR`, по умолчанию 5 запросов в час на адрес; считаются и неизвестные адреса, чтобы 429 не раскрывал наличие контакта); (2) `POST /auth/telegram` и `GET|POST /auth/magic/{token}` для контакта архивной компании отвечают 403 `{"detail": "FORBIDDEN"}`; (3) ответ `ContactInviteResponse` внутреннего API (`POST /api/v1/accounts/contacts/{id}/invite/`) больше не содержит `invite_url` и `telegram_url` (сгенерированный `erp-internal-full.json` уже обновлён); `invite.cabinet_url` в ответе передачи клиента CRM (`erp-integration.yaml`) теперь — адрес кабинета без токена, схема не менялась.

**Варианты.** 1) описать 429 и 403 в FIX-20 вместе с остальным контрактом портала; 2) править `erp-portal.yaml` в PR FIX-14 (нарушает «контракт не правят вдвоём»).

**Рекомендация.** Вариант 1. Сопутствующее: в Cabinet текст для 429 `TOO_MANY_REQUESTS` на экране входа («Слишком много запросов, попробуйте через час») — задача агента Cabinet после FIX-20.

## Q-11 · Адрес ERP: где хранить и нужен ли пароль на каждое сохранение (M3-CRM-02) — **решено 2026-10-13 по рекомендации: вариант 1; см. DECISIONS**

**Контекст.** Коннектор «ERP» в «Подключениях» (PR `m3/crm-02-erp-connector`). Секреты (сервисный токен, секрет вебхуков) — в `integration_secrets` зашифрованными, как токен бота (ADR-0018). Адрес ERP — не секрет; ADR-0022 упоминал только `ERP_BASE_URL` из `.env`. В PR адрес хранится в `settings.integrations.erp_base_url` (правится из CRM, скрыт с экрана «Настройки»), `.env` — запасной источник; любое сохранение (даже только адреса) требует пароль админа, потому что оно переключает режим передачи клиентов (`local` ↔ `erp`).

**Варианты.**
1. Как в PR: адрес в `settings` с приоритетом над `.env`; пароль на каждое сохранение.
2. Адрес только в `.env` (как в ADR-0022 дословно), в CRM — лишь просмотр и секреты. Минус: смена адреса — доступ к серверу и перезапуск, против ADR-0018 («отдать админу всё»).
3. Как 1, но пароль только при вводе секретов. Минус: смена адреса без пароля меняет режим жизненного цикла.

**Рекомендация.** Вариант 1. Если владелец выберет 2 или 3 — правка в одном сервисе `services/erp_connector.py`, контракт API не меняется.

## Q-12 · Веб-форма «Запрос»: вложение и согласие на обработку данных (M3-CRM-05) — **решено 2026-10-14 по рекомендации: согласие — поле `consent: true` в API формы (реализовано в M2-CAB-03: 422 `consent_required`, `consent_given_at` лида), вложения — через Cabinet после приглашения; см. DECISIONS**

**Контекст.** ARCHITECTURE §17 перечисляет поля формы: имя, компания, телефон, e-mail, «что нужно», **вложение**. В `POST /api/v1/leads/web` (PR `m3/crm-05-lead-sources`) вложения нет: публичный приём файлов без аутентификации — отдельная поверхность атаки (размер, типы, хранение в S3 до привязки к лиду), а контракт загрузки для Cabinet не описан. Также в форме нет чекбокса согласия на обработку персональных данных: у Telegram-лида согласие берёт бот (`consent_given_at`), у веб-лида поле остаётся пустым (писать ему из CRM и так нельзя — Telegram-идентичности нет); при склейке с Telegram-лидом берётся согласие из бота.

**Варианты.**
1. Вложение — не в первой версии (как сейчас): клиент присылает файл в Telegram или менеджеру после звонка. Согласие — чекбокс на стороне Cabinet с текстом `texts.consent` CRM, в API поле `consent: true` обязательно, `consent_given_at`/`consent_version` пишутся при создании.
2. Вложение в первой версии: `POST /api/v1/leads/web` принимает `multipart` до 10 МБ, типы как у документов клиента, файл — в бакет вложений и в заметку лида; антиспам тот же. Плюс чекбокс согласия как в 1.
3. Вложение через Cabinet после приглашения (клиент загружает уже в кабинете), форма остаётся текстовой.

**Рекомендация.** Вариант 1 сейчас (чекбокс согласия — правка контракта на одну строку, сделает агент CRM после «да»), вариант 3 для файлов: в кабинете файл сразу привязан к компании и заявке ERP.

## Q-13 · Лимит запросов веб-формы по IP хранится в памяти процесса api (M3-CRM-05) — **решено 2026-10-14 по рекомендации: окно по IP в памяти процесса api до появления реплик; при репликах — таблица в Postgres; см. DECISIONS**

**Контекст.** Окно «не больше N запросов в час с одного IP» (`settings.web_form.rate_limit_per_hour`) живёт в памяти процесса api — как `RateLimitMiddleware` бота. На dev и prod сейчас один процесс api за Caddy, IP берётся из `X-Forwarded-For` (uvicorn `proxy_headers`), этого достаточно. При двух и более репликах api окно считается на каждую отдельно (лимит фактически умножается), после перезапуска — обнуляется.

**Варианты.**
1. Оставить в памяти до появления реплик (текущее состояние); зафиксировать в runbook `deploy.md`.
2. Перенести окно в Postgres (таблица `web_form_hits(ip, at)` с индексом и чисткой в cron) — +1 миграция и запрос на каждую отправку формы.
3. Ограничение на Caddy (`rate_limit` плагин) по пути `/api/v1/leads/web` — без кода, но лимит не из «Настроек».

**Рекомендация.** Вариант 1; при масштабировании api — вариант 2 (одна миграция, домен не меняется: `SlidingWindowLimiter` заменяется репозиторием).

## Q-14 · Портал: загрузки файлов нет — вложения «Нового запроса» (M2-CAB-02 → агенту ERP, M2-ERP-01) — **решено 2026-10-14 по рекомендации, контракт не менялся**

**Контекст.** `ClientRequestCreate.attachments` — массив `AttachmentRef {upload_id, name}`, но эндпоинта, который выдаёт `upload_id`, в `erp-portal.yaml` нет (в описании схемы: «заливка — multipart на `/documents`, появится с M2-ERP-01»). DECISIONS Q-12 (M3-CRM-05) решило, что файлы клиент присылает через Cabinet после приглашения.

**Варианты.** 1) `POST /uploads` (multipart, ≤ 10 МБ, типы как у документов) → `{upload_id, name}`, файл привязывается к заявке при `POST /requests`. 2) Загрузка в `POST /documents` с `kind=other`, `upload_id` = id документа. 3) Без вложений до пилота.

**Рекомендация.** Вариант 1 в M2-ERP-01 (контракт — агент ERP). **Обход в Cabinet до этого:** форма «Новый запрос» без вложений, подсказка «спецификации передайте менеджеру — загрузка файлов появится позже»; мок `attachments` не принимает.

## Q-15 · Каталог: фильтр `category_id` есть, а id категории нигде не отдаётся (M2-CAB-02 → агенту ERP) — **решено 2026-10-14 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** `GET /catalog` принимает `category_id`, но `CatalogItem.category` — только строка-название, справочника категорий нет. Фильтровать по id клиенту нечем.

**Варианты.** 1) `CatalogItem.category` → `{id, name} | null` и `GET /catalog/categories` → `[{id, name, count}]` (только опубликованные). 2) Только `category_id` рядом с `category`. 3) Фильтр по названию (`category=<name>`).

**Рекомендация.** Вариант 1 (как в Odoo eCommerce: публичные категории — отдельный справочник). **Обход в Cabinet до этого:** категории — названия из первой сотни опубликованных позиций (`page_size=100`), выбранная категория фильтруется на клиенте по выборке до 100 позиций (`src/lib/catalog.ts`); при каталоге больше 100 позиций фильтр неполон — снять обход сразу после правки контракта.

## Q-16 · Портал: у запроса нет строк и карточки, у сделки — номера для клиента (M2-CAB-02 → агенту ERP) — **решено 2026-10-14 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** `POST /requests` принимает строки, но `ClientRequest` их не возвращает и `GET /requests/{id}` нет — клиент не видит, что именно он просил. Сделка у клиента — только `deal_id` (внутренний идентификатор): экран «Сделка №42» (deep-link бота `deal_<id>`) собирается из списков, своего номера/названия у сделки нет.

**Варианты.** 1) `GET /requests/{id}` с `lines: RequestLineIn[]` и `attachments`; в `ClientRequest`, `QuoteListItem`, `Contract`, `Invoice`, `Act`, `DeliveryLine`, `Document` — `deal: {id, number, title}` вместо голого `deal_id`. 2) Только `lines` в `ClientRequest` списка. 3) Оставить как есть.

**Рекомендация.** Вариант 1. **Обход в Cabinet до этого:** карточка запроса — из списка `GET /requests` (суть, статус, «что дальше», КП по сделке), строк не показывает; сделка подписана «Сделка №<deal_id>».

## Q-17 · Коды `detail` портала, на которые опирается Cabinet (M2-CAB-02 → агенту ERP, M2-ERP-01) — **решено 2026-10-14 по рекомендации, контракт обновлён в FIX-20 (2026-10-19)**

**Контекст.** Контракт описывает статусы ответов, но не перечень кодов `{"detail": CODE}`. Cabinet показывает текст по коду, а неизвестный — по HTTP-статусу (docs/systems/cabinet/CONVENTIONS.md §9).

**Рекомендация.** ERP закрепляет в `erp-portal.yaml` (enum в описании ответов) коды, которые уже использует мок и словари Cabinet: 401 `UNAUTHORIZED`, `INVALID_INIT_DATA`; 403 `FORBIDDEN`; 404 `NOT_FOUND`; 410 `MAGIC_LINK_EXPIRED`; 409 `QUOTE_FINALIZED`, `QUOTE_EXPIRED`, `QUOTE_CODE_INVALID` (неверный код акцепта — 409 по контракту), `CONTRACT_FINALIZED`, `ACT_FINALIZED`; 422 `VALIDATION_ERROR`, `REASON_REQUIRED`, `INN_INVALID`, `TEAM_MEMBER_EXISTS`. Другой код ERP — Cabinet подстроит `apiErrors.*` одной правкой словарей.

## Q-19 · Коннектор «Почта» (M3-CRM-08): чем отправлять и где держать письмо с временным паролем до отправки — **решено 2026-10-14** (вариант 2, по рекомендации; ADR-0023 CRM, см. `DECISIONS.md`); бывш. «Q-12» — номер совпал с вопросом о веб-форме, переименован в FIX-52

**Контекст.** Письмо сотруднику содержит временный пароль. Отправка идёт задачей Procrastinate (не в пути запроса), значит тело письма должно где-то пережить постановку в очередь. В `procrastinate_jobs` аргументы лежат открытым текстом.

**Варианты.**
1. `aiosmtplib` + отправка в пути запроса (тело нигде не хранится, но релей держит запрос и нужна новая зависимость).
2. `smtplib` стандартной библиотеки в потоке + очередь; тело — в `email_log.body_ciphertext` шифртекстом Fernet (`SECRETS_KEY`), стирается после отправки или третьей попытки; без `SECRETS_KEY` письма с паролем не отправляются (409 `secrets_key_missing`).
3. Тело аргументом задачи (открытый текст в таблице задач — неприемлемо).

**Рекомендация.** Вариант 2. Сопутствующие решения по рекомендации: пароль админа на каждое сохранение коннектора (как у ERP, Q-11); язык письма — `ru`, пока у пользователя нет поля языка (Q-012); приглашение/сброс по почте сначала проверяют коннектор и только потом меняют пароль.

## Q-FIX12 · `erp-integration.yaml`: `DeliveryLine.quantity`/`unit` могут быть `null` (FIX-12) — **решено 2026-10-18 по рекомендации**

**Контекст.** В ERP у исполнения сделки (`sales.Fulfillment`, один к одному со сделкой) нет количества и единицы; проекция клиента подставляла `1` и «шт». FIX-12 требует «не выдумывать количества: нет данных — `null`», а `DeliveryLine.quantity` в контракте — строка без `null`. Файл `erp-integration.yaml` по плану волны 1 правит FIX-10 (409 `EMAIL_CONFLICT`).

**Варианты.** 1) Сделать `quantity` и `unit` в `DeliveryLine` nullable (узкая правка двух полей, сгенерированные клиенты пересобраны). 2) Не отдавать ключи, когда данных нет. 3) Оставить `1`/«шт».

**Рекомендация.** Вариант 1 — единственный, где ответ однозначен для бота и не выдумывает данных. Конфликт с FIX-10 возможен только в `erp-integration.yaml` и `packages/contracts/generated/*` (разные участки) — тот, кто сливается вторым, делает `git merge origin/main` и `make contracts`.

## Q-FIX11 · Права менеджера CRM в ERP и «своя компания» на стенде (FIX-11) — **продолжено по рекомендации, решение владельца нужно до включения `PLATFORM_SSO_ENABLED` для менеджеров**

**Контекст.** (1) Карта «роль CRM → права ERP» раньше клала в токен коды, которых нет в ERP, и всем менеджерам — `quote.view_cost_margin` (себестоимость и маржа). Теперь коды — только из каталога ERP (`ErpPermission`, 22 кода). Бизнес-решение, что именно может менеджер продаж в ERP, принимает владелец. (2) Роли бэк-офиса применяются к членству в «своей компании» (`core.tenant.own_company()`): если `OWN_COMPANY_ID` не задан и в ERP нет компании-продавца с активными участниками (чистый стенд), провиженный менеджер членства не получает и в ERP ничего не видит; суперпользователь (роль `admin` в CRM) работает без членства.

**Варианты.** (1) а) `manager` → `deal.manage`, `quote.build`, `quote.edit_pricing`, `quote.send`; `viewer` → ничего; `admin` → суперпользователь ERP; б) как а), плюс `contract.manage` и `quote.review` (роль «Расчёт» целиком, кроме `quote.view_cost_margin`); в) только `deal.manage` — остальное админ ERP добавляет ролью вручную. (2) а) на стенде и проде завести «свою компанию» в ERP (реквизиты в «Настройках») и задать `OWN_COMPANY_ID`; б) создавать компанию провижинингом (нарушает «CRM знает только людей»).

**Рекомендация.** (1) а) — минимум для работы менеджера по запросам и КП без себестоимости; расширять права ролью в «Настройках → Команда» ERP. Реализовано так; смена — правка `app/domain/erp_permissions.py` и таблицы в `docs/architecture/sso-token.md`. (2) а) — проброс `OWN_COMPANY_ID` в compose/`.env` — задача инфраструктуры (M5-INF-01, `infra/compose/base.yml` в FIX-11 не правится: файл FIX-15).

## Q-FIX21-1 · `document_id`, `pdf_document_id`, `scan_document_id` портала: у PDF договора, счёта, акта, КП и скана акта нет записи в `GET /documents` (FIX-21) — **решено в FIX-23 (2026-10-19) по рекомендации, кроме `scan_document_id` — см. Q-FIX23-3**

**Контекст.** Контракт 0.2.0 отдаёт `Contract.document_id`, `Invoice.document_id`, `Act.document_id`/`scan_document_id`, `Quote.pdf_document_id` — id документа из `GET /documents`. В ERP такого документа нет: `documents.GeneratedDocument` не связан с договором, счётом, актом и КП (их PDF лежат в `pdf_file` самих моделей, скан акта — `Act.signed_file`). Прежний код подставлял в `document_id` id самого договора — ссылка вела на чужой документ или в 404.

**Варианты.** 1) Выпускать `GeneratedDocument` при каждой подписи/выставлении и хранить связь в самих моделях (миграции в `sales`/`finance`). 2) Отдавать в `GET /documents` проекцию «виртуальных» документов (вид + id источника) и считать `document_id` из неё, не заводя новых таблиц. 3) Оставить `null` и убрать поля из контракта.

**Рекомендация.** Вариант 2 в FIX-23 (он отдаёт PDF КП, договора, счёта и акта «существующим рендером»). До этого сериализаторы честно отдают `null`; сторож FIX-21 уже проверяет, что любой ненулевой `*_document_id` присутствует в `GET /documents`.

**Решение (FIX-23).** Вариант 2: `GET /documents` — проекция выпущенных КП, договоров, счетов, актов и накладных плюс выпущенные `GeneratedDocument` клиентских видов (договор, счёт, акт); идентификатор — `pk * 8 + слот вида` (`portal/services/documents.py`), без новых таблиц. `document_id` / `pdf_document_id` указывают на этот id, пока документ выпущен, иначе `null`; файл — `GET /documents/{id}/file` (PDF существующим рендером, не готов — 202 и рендер в очереди). `scan_document_id` акта — тот же id (скан заводит приёмка FIX-22), см. ## Q-FIX31-1 · Ключ идемпотентности передачи: от `crm_client_id` и содержимого, а не только от `crm_client_id` (FIX-31)

## Q-FIX33-1 · Постоянные отказы CRM на вебхук: 200 и запись `rejected`, а не 4xx (FIX-33) — **решено архитектором 2026-10-21 (резерв Opus): 200 и `rejected` в CONTRACTS §3**

**Контекст.** CONTRACTS §3: «CRM отвечает 200 быстро»; ERP ретраит любой не-2xx до 24 ч. Раньше CRM отвечала 422 на сломанное тело, неизвестный тип события и расхождение заголовка `X-Event-Type` с телом — ERP зря повторяла бы сутки. Конверт у CRM строгий (`extra="forbid"`), поэтому и новое необязательное поле ERP тоже давало бы 422.

**Решение исполнителя.** 401 — только неверная или отсутствующая подпись (проверяется по сырому телу ДО любого разбора и ДО проверки остальных заголовков). При верной подписи: неверный `X-Event-Id`/нет `X-Event-Type` — 422 (ошибка клиента ERP, ретрай бессмыслен, но вызов не наш); тело, которое CRM не принимает (не JSON, неизвестный тип, поля вне схемы, расхождение с заголовком), — строка `erp_incoming_events` со статусом `rejected` и текстом причины, ответ 200. Строка видна в центре внешних сервисов («События из ERP»).

**Нужно решение.** Закрепить в CONTRACTS §3: «постоянный отказ — 200 + журнал CRM». Побочный вопрос: смягчить `extra="forbid"` в конверте до терпимого читателя — это FIX-35 (дискриминированные модели).

## Q-FIX33-2 · Сверка `erp_company_id`: клиент без сопоставления принимает его из события (FIX-33)

**Контекст.** Задача передачи (FIX-31) пишет `clients.erp_company_id` только после ответа ERP, а `request.created`/`invite.sent` приходят уже во время передачи.

**Решение исполнителя (вариант «применить», не «ждать»).** Если у клиента `erp_company_id` пуст, событие применяется и записывает сопоставление: `crm_client_id` в подписанном конверте ERP берёт из сопоставления, которое создала наша же передача. Ожидание привело бы к событию, зависшему навсегда при сбое передачи. Если сопоставление есть и не равно конверту — событие `rejected` («company mismatch»), зеркало, лента и бот не затронуты; в центре внешних сервисов — сбой с текстом. ## Q-FIX33-3 · Порядок по `occurred_at` и Q-FIX30-1 (стадия документами без `deal.stage_changed`) (FIX-33)

**Контекст.** `deals.external_stage_at` хранит `occurred_at` последнего применённого события со сделкой. Событие старше него не меняет `external_stage`, название, сумму и валюту зеркала, но попадает в ленту. Итог сделки `deal.won`/`deal.lost` применяется ВСЕГДА (`deals.stage`, `lost_reason`, `closed_at` = `occurred_at` итога) — иначе опоздавший итог терялся бы навсегда; итоги упорядочены между собой по `closed_at` (более старый `won` не переоткрывает более новый `lost`). Устаревшее событие, чьё сообщение клиенту описывает текущее состояние (`delivery.eta_changed`, `delivery.status_changed`, `deal.stage_changed`), в бот не уходит, остальные (КП, счёт, акт) доходят. Равное время применяется (порядок прихода).

**Как уживается с Q-FIX30-1.** Стадия сделки меняется документами (КП, счёт, оплата, акт) без `deal.stage_changed`, но каждое событие со сделкой несёт `deal.stage`, посчитанное `stages.py` на момент события. Поэтому «стадия сделки в CRM» — это стадия из самого свежего по `occurred_at` события любого типа; `eta_changed` после `paid` её не откатывает. Пока события нет, CRM изменения стадии не видит — если нужен `deal.stage_changed` при смене стадии документами, это отдельная задача ERP. `deal.won` по Q-FIX30-1 уходит при подписании договора и несёт `deal.stage = contract`, а CRM пишет `external_stage = won` и `stage = won`, даже если счёт (`invoice.*`) пришёл раньше; следующее по времени событие (например, `invoice.issued`) вернёт `external_stage` в стадию исполнения — по замыслу Q-FIX30-1 «won» и «исполнено» разные шкалы, локальный итог `deals.stage` не откатывается.

## Q-FIX33-4 · Telegram: не больше одного раза на событие (at-most-once) (FIX-33)

**Контекст.** Сообщения считаются в транзакции обработки и пишутся в `erp_incoming_events.outbox`; после коммита строка захватывается (`notified_at`), затем идёт отправка. Повтор события, повтор задачи и сборщик второго сообщения не шлют.

**Цена.** Если процесс упал после захвата и до отправки, сообщение теряется (не дублируется). Лента лида и зеркало уже записаны. Сообщения, чей захват не состоялся (падение между коммитом и захватом, нет бота, включён dry-run), строка не захватывает — сборщик досылает их через минуту, но не старше 24 часов. ## Q-FIX35-2 · Подпись вебхука не покрывает `X-Event-Id` и `X-Timestamp`; окно `X-Timestamp` (FIX-35, P2 ревью FIX-33) — для архитектора — **решено архитектором 2026-10-21 (резерв Opus): принять, FIX-61 — реализовано в PR FIX-61**

**Контекст.** `X-Signature = sha256(HMAC(secret, body))`: заголовки `X-Event-Id` и `X-Timestamp` не подписаны, поэтому перехваченное тело можно переслать под новым `X-Event-Id` и обойти идемпотентность. Формат подписи — контракт, в FIX-35 он **не менялся**. Дешёвая защита, реализованная сейчас: CRM хранит `sha256` сырого тела каждого принятого события (`erp_incoming_events.body_sha256`); тело, чей хеш уже принят под другим `X-Event-Id`, — 200 и строка `rejected` с текстом `replayed body: already received as event <id>`, без обработки. Ограничения: хеш защищает от повтора ровно того же тела, но не от подмены заголовков; журнал не очищается (индекс по хешу растёт вместе с таблицей); два законных события ERP с побайтно одинаковым телом (одно `occurred_at` до микросекунды) второе будут отклонены (на практике не встречается).

**Предлагаемая правка контракта (дословно).** В `docs/architecture/CONTRACTS.md` §3 и в `description` корня `events.schema.json`: «`X-Signature: sha256=<HMAC(WEBHOOK_SECRET, f"{X-Event-Id}.{X-Timestamp}.{body}")>`, где `X-Timestamp` — UTC в формате ISO 8601 с `Z` или смещением. CRM отклоняет запрос (200 и запись `rejected`, не 401: ретраи не помогут), если `|now − X-Timestamp| > 300 с`; ERP при ретрае подписывает заново с актуальным `X-Timestamp`, а `occurred_at` в теле остаётся временем события. Переход: CRM принимает обе схемы подписи (старую — только тело), пока ERP не выкатит новую; затем старая схема отключается настройкой `ERP_WEBHOOK_SIGN_LEGACY=false`.»

**Рекомендация.** Принять отдельной задачей после волны 3 (ERP и CRM меняются парой, как ротация секрета: сначала CRM принимает обе схемы). Хеш тела оставить как второй рубеж.

## Q-PLT-10-1 · Вход, сессия и RBAC BFF (PLT-10, PLT-11): что контракт не определил, а коду пришлось выбрать — **решено архитектором 2026-10-22 по рекомендации (по пунктам ниже; DECISIONS, контракт BFF 0.2.3)**

**Контекст.** Контракт BFF 0.2.2 и `platform-rbac.yaml` не правились (запрет задачи). При реализации входа нашлись места, где выбор сделан по умолчанию; решения нужны до PLT-14 (агрегирующие ответы) и QA-P1.

**Что выбрано, пока нет решения.**
1. **ERP не ответил при входе — вход всё равно проходит.** Контракт перечисляет «CRM (вход невозможен) или ERP не ответили» как 503. Выбрано мягче: сбой SSO или обмена в ERP (сеть, 5xx, `USER_NOT_PROVISIONED`) не блокирует работу с CRM; в сессии `erp_state = unavailable`, `Me.access.erp` остаётся по `platform_access`, переподключение к ERP — при первом вызове ERP (не чаще раза в 15 с). Иначе недоступность ERP закрывала бы Платформу целиком, вопреки `docs/architecture/platform-bff.md` §8 («частичный результат»).
2. **`sources` в `Session` и `Me` нет** — только в агрегирующих ответах. Состояние `sources.erp = not_applicable` (нет доступа к ERP) хранится в сессии (`SessionData.sources()`) и подставляется агрегирующими эндпоинтами PLT-14; на входе об этом говорит `Me.access.erp = false`.
3. **`USER_DISABLED` при входе недостижим**: CRM на отключённого и на неизвестного сотрудника отвечает одинаково (`auth_failed`, защита от перебора адресов), поэтому вход отдаёт `INVALID_CREDENTIALS`. Отключение, замеченное при обновлении токена, — `SESSION_EXPIRED` (как в контракте).
4. **Блокировка учётной записи CRM (423 `account_locked`)** переводится в 429 `TOO_MANY_REQUESTS` (`Retry-After` — 60 с, точное время блокировки лежит в `details` CRM и не пробрасывается): кода для блокировки в `Error.code` нет.
5. **Язык интерфейса живёт только в сессии** (`PATCH /me {language}`): у пользователя CRM поля «язык» нет, своей БД у BFF нет, поэтому после повторного входа язык возвращается к `ru`. SPA может хранить выбор в `localStorage` и слать при старте.
6. **Тексты ошибок — только русские.** Контракт требует «текст на языке сотрудника»; каталог ru/uz/en для кодов `Error` не заведён (узбекский текст не из чего взять). Код `Error.code` стабилен — SPA переводит по нему.
7. **Профиль CRM перечитывается** не реже раза в минуту при `GET /me` и `GET /auth/session` (роли, доступ к ERP, отключение): выданные в «Оргструктуре» роли действуют без повторного входа. Нет ролей Платформы → 403 `NO_PLATFORM_ROLE` и закрытие сессии; CRM недоступен → снимок сессии. Если сотрудник потерял активную роль, `active_role` сбрасывается в `null`.
8. **Новые переменные окружения BFF** (не секреты): `PLATFORM_COOKIE_SECURE` (по умолчанию `true`; `false` — только для запуска по http без Caddy), `PLATFORM_ERP_REFRESH_COOKIE` (имя cookie с refresh-токеном ERP, по умолчанию `refresh_token` = `REFRESH_COOKIE_NAME` ERP), `PLATFORM_LOGIN_RATE_PER_MINUTE` (10). В compose и `.env.example` не добавлены (зона INF).
9. **Вырезание полей с ограничением** (`strip_restricted`) считается по объединению ролей, как и права операций; активная роль скрывает поля только в SPA через `Me.restricted_fields`. Группы `cost_margin`, `supplier_prices`, `totals_only` в контракте — смысловые; какие ключи ответа к ним относятся, задаёт экран (параметр `rules`).

**Рекомендация.** 1 — оставить как выбрано (и дописать в описание `POST /auth/login`: ERP-сбой не блокирует вход). 2 — оставить. 3 — убрать `USER_DISABLED` из `login` в следующей минорной версии или оставить как зарезервированный. 4 — добавить в `Error.code` отдельный `ACCOUNT_LOCKED` (423) в следующей минорной версии, пока — 429. 5 — решить вместе с PLT-15 (поле `language` у пользователя CRM) или оставить. 6 — отдельная задача на каталог сообщений при первых экранах uz. ## Q-CRM-01b-1 · Администратор без ролей Платформы (CRM-01b): что выбрано и что осталось — для архитектора

**Контекст.** Миграция 0032 оставила `platform_roles = []` у администраторов, созданных до CRM-01; после выхода BFF они получили бы 403 `NO_PLATFORM_ROLE` и не смогли бы выдать роли. Миграции 0033 (данные) и 0034 (`users.language`) в задаче CRM-01b. Выбрано по умолчанию:

1. **Вычисляемые поля для админа не «эквивалентны» без доступа к ERP:** у `/setup`-администратора до CRM-01 `platform_access = ["crm"]` (ERP не выдавался). Правило CRM-01 для `[ADMIN]` — `["crm","erp"]` и роль ERP `admin`. Миграция приводит строку к состоянию, которое вычислил бы CRM-01: `platform_roles = ["ADMIN"]` и `platform_access = ["crm","erp"]` (роль CRM `admin` не меняется). Иначе `/me` отдавал бы `[ADMIN]` при `["crm"]`, BFF не обменивал бы токен ERP, а первое же изменение пользователя молча выдало бы доступ.
2. **Провижининг ERP нужен, и он ставится миграцией:** тем, у кого `"erp"` не было, миграция кладёт в очередь Procrastinate задачу `erp_provision_user` (SQL-функция схемы очереди, ровно как `enqueue_erp_sync`; блокировка `erp_user:<id>`). Если ERP ещё не сопряжена, задача повторится по расписанию и будет видна в «Внешних сервисах» — как при любой выдаче доступа. У кого доступ к ERP уже был, провижининг не нужен: роль `admin` ERP та же. Аудит: `user.update` от системы с «до/после».
3. **`erp_role_codes` миграция не трогает:** для `admin` ERP игнорирует `role_codes` (суперпользователь); следующее изменение пользователя пересчитает их в `[]`.
4. **`create-admin` (CLI) — исправлено в этом же PR** (решение лида: тот же тупик первого входа, штатный путь по README и шаг e2e в CI). `bootstrap_admin` теперь работает как `/setup`: новый админ получает `["ADMIN"]`, `platform_access = ["crm","erp"]`; у восстанавливаемого существующего пользователя роли Платформы сохраняются, `ADMIN` добавляется (`[MANAGER]` -> `[MANAGER, ADMIN]`); после коммита ставится провижининг ERP (в CLI-процессе очередь открывается на время команды; сбой постановки оседает в `erp_sync_error`, команда не падает); повтор идемпотентен. Побочный эффект: роли CRM восстанавливаемого пользователя заменяются на вычисленную `admin` (как при любой непустой `platform_roles`), прежняя «сумма ролей CRM + admin» больше не сохраняется.
5. **`users.language`** — `ru|uz|en`, по умолчанию `ru`, CHECK в БД; `GET /me`, `/users*` отдают, `PATCH /me` (сам себе) и `PATCH /users/{id}` (админ) принимают; изменение пишется в аудит `user.update`. Контракт (`packages/contracts`) не менялся: поле — только в OpenAPI CRM; BFF 0.2.x его в `Me`/`/admin/users` пока не пробрасывает (задача PLT-10+).

**Контекст.** Экран и BFF (`/admin/users*`) сделаны по контракту 0.2.4 без его правки и без обходов в BFF: BFF переводит ответы CRM и ничего не решает («последний админ» — 409 `last_admin` CRM -> `LAST_ADMIN`). Шесть мест, где CRM или контракт не дают сделать то, что обещает SPEC-v3 §7.6. Решения нужны до гейта P1 (QA-P1) — первые два видны на живом стенде сразу.

1. **DIRECTOR не читает список сотрудников на живом CRM — сделано в CRM-01c (#169, `users:read` по `platform_roles ∋ DIRECTOR`).** Матрица и контракт дают `admin` директору «чтение», BFF пускает (`require("admin", "read")`), но CRM `GET /api/v1/users` требует `users:read`, а базовая роль CRM у DIRECTOR — `viewer` (`apps/crm/infra/casbin/policy.seed.csv`: у `viewer` нет `users`). Итог: 403 с `source = crm`, экран показывает «Недостаточно прав». Варианты: (а) `p, viewer, crm, users, read` в seed casbin — один раз и просто; ценой того, что любой токен `viewer` (DIRECTOR, SUPPLY, ENGINEER) может читать `GET /users` напрямую по API (в `UserOut` секретов нет, раздел скрывает BFF); (б) право `users:read` по `platform_roles ∋ DIRECTOR` (`Principal` сейчас несёт только роли CRM — нужна правка модели); (в) убрать чтение у DIRECTOR в SPEC-v3 §4.2. **Рекомендация.** (б): право `users:read` по `platform_roles ∋ DIRECTOR` (в (а) SUPPLY и ENGINEER с токеном `viewer` читали бы всех сотрудников напрямую по API); в CRM-задаче P1, тест «DIRECTOR читает /users, SUPPLY — нет» рядом с CRM-01.
2. **Итог провижининга ERP не виден.** Контракт требует `Employee.erp_sync` (`ok|pending|error|not_applicable`) и `erp_sync_error`, но `UserOut` CRM их не отдаёт (`users.erp_sync_error` читает только центр внешних сервисов). BFF отдаёт `not_applicable` без доступа к ERP и `ok` с доступом; `pending` и `error` в списке недостижимы, хотя web готов их показать («ERP: выдаётся», «ERP: ошибка»). **Рекомендация.** `UserOut.erp_sync_error: str | None` (и признак «в очереди») в CRM; BFF — `error` при тексте, `pending` при признаке.
3. **Приглашение: сотрудник создан, письмо не ушло — повторить нельзя.** `POST /admin/users/invite` создаёт пользователя CRM и вызывает `/users/{id}/invite`; без коннектора «Почта» CRM отвечает 409 `smtp_not_configured`, пользователь уже есть, временный пароль BFF наружу не отдаёт (и не должен). BFF отвечает 409 `CONFLICT` с `details.employee_id` и `details.invite = not_sent`; web говорит об этом словами. Повторной отправки в контракте нет. Если CRM не ответила на приглашение, BFF отвечает 503 `BACKEND_UNAVAILABLE` с теми же `details` (текст про CRM, не про почту). **Рекомендация.** Операция `POST /admin/users/{id}/invite` (повтор приглашения; CRM её уже имеет) в контракте BFF 0.3.0 и кнопка «Отправить приглашение снова» у статуса «Приглашён»; повтор — без смены пароля, если письмо уже ушло (иначе действующий временный пароль пропадёт), и со сменой — если не уходило.
4. **Отключение сотрудника с лидами в работе.** CRM требует `transfer_to_user_id` (ADR-0015) и без него отвечает 409 `user_has_active_leads`; то же при снятии роли менеджера (`stops_work`), в том числе сценарий «менеджер → SUPPLY» (меняет роль CRM `manager` на `viewer`). В `EmployeeUpdate` контракта этого поля нет: BFF отдаёт 409 `CONFLICT` (`details.backend_code = user_has_active_leads`), web объясняет «Передайте лидов коллеге в CRM», но интерфейс CRM отключается в T4 — тупик. **Рекомендация.** `EmployeeUpdate.transfer_to_user_id` (BFF 0.3.0) и выбор коллеги в подтверждении отключения.
5. **«Что произойдёт»: роли ERP — решено архитектором 2026-10-22 (PLT-15b, в PR #166).** Генератор `scripts/gen_rbac.py` теперь выдаёт `ERP_ROLE_CODES` и `ERP_EXTRA_PERMISSIONS` в `rbac.generated.ts` и `rbac_generated.py`; блок под «Сохранить роли» и форма приглашения говорят «В ERP сотрудник получит роли: …» (объединение `erp_role_codes` выбранных ролей; ADMIN — «станет администратором (суперпользователь)»); русские, узбекские и английские названия ролей ERP — в i18n web, не в контракте. Тесты «сгенерированное = контракт» обновлены.
6. **Приглашение по Telegram (SPEC-v3 §7.6) не сделано:** в контракте BFF нет операции и канала (только по почте), в CRM нет приглашения сотрудника через бота. **Рекомендация.** Отдельная задача P3 вместе с CRM-04 (уведомления сотрудникам в Telegram): контракт, затем код.

**Выбрано по умолчанию (не разрыв).** Статус «Приглашён» = пользователь активен и `must_change_password` (временный пароль ещё не заменён): CRM не различает «выслано письмом» и «выдан вручную». Поиск и фильтр по статусу BFF делает сам (CRM `GET /users` фильтров не имеет), список сортируется по имени. «Сохранить роли» с пустым набором в web недоступно (подсказка: «отключите сотрудника»); BFF пустой список пропускает — CRM снимет роли (Q-CRM-01-1, п. 3).

**Q-PLT-14-1. Номера сделок и поиск по ним (ERP-09).** В ERP у `Deal` нет номера ЗВ/ПР и нет операции поиска сделок (`GET /crm/deals/` без `search_fields` и фильтров). Что сделано: пока поля `number` нет, BFF составляет номер для показа из года создания и `id` (`ЗВ-2026-104`, префикс `ПР` — с шага «Договор»), а при появлении поля `number` берёт его. Замечание к карте: `docs/architecture/integration-map.md` §1.1 помечает `GET /crm/deals/?search=` как ✓, но у `DealViewSet` нет `search_fields` и фильтров — параметр `search` игнорируется (карту правит архитектор). Варианты: 1) принять до ERP-09 (P2); 2) вынести ERP-09 раньше и добавить `search` по `number`/`title`/компании. **Рекомендация:** 1; при росте базы — 2.

**Q-PLT-14-2. Уведомления ERP: нет счётчика непрочитанных и фильтра (ERP).** `GET /notifications/` отдаёт страницы без `unread_count` и без `?is_read=`. ## Q-FIX-P1-2-1 · Привязка сотрудников из CRM к только что созданной своей компании ERP: что хранится и что выбрано по умолчанию (FIX-P1-2, QA-P1-D-2) — для архитектора

**Что было.** До создания своей компании `provision_crm_user` сохранял только пользователя (`is_superuser`, `is_active`) и `CrmUserMapping`; `role`, `permissions` и `role_codes` из запроса нигде не оставались, поэтому при создании компании (мастер первого запуска, FIX-65) восстановить роли было не из чего.

**Что сделано (ERP-сторона, контракт не менялся).** В `CrmUserMapping` добавлено поле `provision_snapshot` (JSON: `role`, `permissions`, `role_codes` последнего провижининга; миграция `integration/0006`). `create_own_company` в той же транзакции вызывает `attach_provisioned_users`: каждому активному пользователю с сопоставлением CRM — тот же `bind_member_to_company`, что в провижининге, по снимку (роль «CRM Sync», `role_codes`, суперпользователь без ролей бэк-офиса). Отключённые в CRM и отозванные (`is_active=False`) не привязываются. Идемпотентно; в журнал — одна запись без структурного кода (его словарь живёт во фронтенде ERP, а он заморожен), состав — в `after_data`.

**Гонка «провижининг параллельно с созданием компании».** `provision_crm_user` при отсутствии компании берёт ту же advisory-блокировку, что и `create_own_company` (`acquire_setup_lock`), до любых записей: провижининг дожидается коммита и видит компанию. Взаимной блокировки нет — обе стороны берут её первой. Блокировка Postgres; на других СУБД (только тесты) не действует.

**Что выбрано по умолчанию.** Сопоставление, созданное ДО этого поля (снимка нет, например стенд, где провижининг прошёл раньше, чем вышла эта правка): роль — по `is_superuser` (суперпользователь → `admin`, остальные → `backoffice`), права `permissions` и системные роли пусты — то есть минимальные: сотрудник становится участником и видит сделки (сотрудник компании-владельца видит все), но ничего не меняет, пока CRM не пришлёт провижининг заново (правка ролей в CRM или будущая «синхронизация всех»). На чистой установке снимок есть у всех, этот путь нужен только для ранее созданных сопоставлений.

**Почему не «CRM повторно провижинит всех после смены состояния ERP».** CRM не знает, когда в ERP создали компанию (события о создании компании нет, `sources.erp = ok` и до, и после), значит ей пришлось бы переотправлять всех по таймеру или по каждому опросу; это переносит знание о состоянии ERP в другую систему, оставляет окно между созданием компании и повторной отправкой (сотрудник уже есть в ERP, но без привязки) и требует правок CRM и, возможно, контракта. Привязка в транзакции создания компании даёт ноль окон: сотрудник привязан в тот же момент, когда компания появилась.

**Вопрос.** Нужна ли отдельная операция «синхронизировать всех» в CRM для стендов, где снимка нет (пункт «Что выбрано по умолчанию»)? **Рекомендация:** нет — единичные стенды переживут одну правку ролей в CRM, на проде провижининг идёт после создания компании.

**Правки после гейта P1 (FIX-P1-1).** Лента «Сегодня» (Q-PLT-14-3, QA-P1-D-1): BFF отсеивает служебные записи журнала ERP (`sso.*`, `auth.*`, `login*`, `logout*`, `token.*`, `session.*`) и показывает `event_code` по таблице (`bff/app/feeds/events.py`, словарь SPEC-v3), готовую русскую строку ERP — если кода в таблице нет, иначе «Действие в ERP»; сырой код не показывается. Таблицу нужно пополнять вместе с новыми `event_code` ERP; uz/en — вместе с Q-PLT-14-5. Поиск (Q-PLT-14-1, O-4): латинский префикс `ZV`/`PR`/`KP` заменяется кириллическим, остальной запрос уходит как набран — и в сделки, и в документы ERP (номера документов строит схема нумерации ERP, например `КП-2026-00001`; BFF её не перестраивает). Только для номеров заявок и проектов, которые составляет BFF (`ЗВ-2026-001`), запись без нулей (`ЗВ-2026-1`) ищется ещё и как `ЗВ-2026-001`; `id` из номера по-прежнему не разбирается. Хвост ленты (ERP-16): BFF берёт 50 новейших записей журнала (`LOG_PAGE`) и только потом отсеивает служебные — при частых входах значимые события дня могут не попасть в окно; лечится сквозной лентой ERP-16 без служебных записей (или фильтром `event_code` на стороне ERP).

(4) Сбой перезагрузки политик после правки роли — не 500: ответ 200, флаг `Rbac.stale`, повтор при ближайшей проверке права. Данных прода нет — миграция 0035 пересчитывает права простым образом.

1. *(Заменено решением Q-R1c-1 п. 5 (2026-10-26): суперпользователь ERP — только системная «Администратор».)* **ERP-суперпользователь для администратора сохранён.** Роль CRM `admin` (вычисленная: системная `ADMIN` или любая роль с `admin: full`) по-прежнему провижинится как `role: admin` (все права ERP, `permissions` ERP игнорирует), как в Q-CRM-01-1 п. 1. 3. **Базовая роль CRM (совместимость полей `roles`, «ведёт лидов»)** (`crm_base_role` в каталоге v2): у ролей с кодом — как в v1 (MANAGER/ACCOUNTANT → `manager`, DIRECTOR/SUPPLY/ENGINEER → `viewer`, ADMIN → `admin`; иначе директор с `crm.leads: full` стал бы `manager` и попал в очередь лидов), у ролей без кода — `admin`, если `admin: full`, `manager`, если `crm.leads: full`, иначе `viewer`. ## Q-T5-1 · Лимит входа считает только неудачные попытки: расхождение с текстом контракта BFF (волна 11b, T5) — **решено архитектором 2026-10-26**

**Контекст.** Хвост O-1 волны 8: офис за одним NAT, много сотрудников входят с одного IP, а лимит считал и успешные входы (10 в минуту на IP). Контракт `platform-bff.yaml` (0.3.x) в «Лимитах» говорит «вход — 10 в минуту на IP и e-mail»; контракт в этой задаче не правился.

**Что сделано в BFF (поведение, не схема).** Лимит — 10 **неудачных** попыток в минуту, отдельно на IP и на e-mail. Считаются отказы `INVALID_CREDENTIALS` и `ACCOUNT_LOCKED`; успешный вход, `NO_PLATFORM_ROLE` и сбои CRM (503) счётчик не расходуют; успешный вход сбрасывает счётчик e-mail. Код 429 `TOO_MANY_REQUESTS` с `Retry-After` и схема ответа не изменились.

6. **Логотипы и медиа ERP — решено в PR: через BFF, CSP не расширялся.** ERP строит абсолютные адреса от своего `Host`, то есть для
   BFF это внутренний `erp-backend:8000`, и в `img-src` Платформы такой адрес не прописать (домен ERP тоже не помог бы). Выбран путь
   с наименьшим доступом: BFF отдаёт файл сам (`GET /admin/company/logo/image`, `/admin/company/brand/logo/image`, раздел
   `company.settings` на чтение; берёт только публичные пути логотипов `/media/companies/<id>/logo|doc-profile/logo/<файл>`,
   с заголовками ERP `nosniff` и `Content-Security-Policy: sandbox`), а `logo_url` в ответах — адрес BFF того же origin. Образцы
   документов (бланк, шаблон) BFF встраивает логотипы данными (`data:`), потому что рамка образца наследует CSP. Файлы
   `infra/caddy/Caddyfile.prod` и `Caddyfile.dev` не менялись: `img-src 'self' data: blob:` остаётся.
7. **Категории: кэш и поля — принято.** `GET catalog/categories/` кэшируется ERP на 10 минут и правкой не сбрасывается (как раньше
   справочники, см. `_CachedLookupListMixin`); экран кладёт ответ изменения прямо в кэш запроса и не перечитывает список при
   возврате в окно. Иконка категории и `domain_type` в BFF не выведены. Рекомендация (ERP): версионный ключ кэша, как у справочников.
8. **Нумерация — два вызова — хвост.** Префикс — `doc_number_prefix` настроек компании, схема — `crm/numbering-scheme`: BFF сохраняет
   префикс, затем схему, транзакции между ними нет (занятый префикс — 409 до схемы; неверная маска — 422 после префикса).
   Рекомендация (ERP): принимать `prefix` в `PATCH crm/numbering-scheme/`.
9. **Тестовая отправка шаблона письма не включена — хвост.** `POST settings/email-templates/{id}/test-send/` ходит в SMTP дольше
   таймаута клиента ERP (3 с) и вернула бы 503 на успешной отправке. Образец письма (`preview`) есть. Нужен отдельный таймаут.
10. **Загрузка логотипа (ревью).** BFF проверяет размер (до 2 МБ) и тип части `logo` (PNG, JPEG, WebP, SVG); содержимое и GIF
    решает ERP. Тело читается целиком до проверки длины, если нет `Content-Length` (chunked): лимит срабатывает после чтения в
    память — хвост (читать поток с обрывом на лимите либо оставить лимит Caddy).

**Решение исполнителя сверх контракта.** «Заявка» в словаре SPEC-v3 §2 — потребность клиента; в интерфейсе заявка на новую категорию
называется «запрос на категорию» (в контракте — `CategoryRequest`).

## Q-D15-1 · «Создать документ» и «Мои документы»: решения сверх задачи и хвосты (D1-5 → лид и архитектор) — **открыто**

**Контекст.** BFF 0.17.0 (`/eds/documents*`, `/eds/document-files*`, `/eds/deal-options`), EDS 0.4.0 (`PATCH /documents/{id}`), экраны `/eds/documents` и `/eds/new`.

Вложение снять нельзя (только добавить) — хвост.
2. **«Кому» — только директор.** Выбрать конкретного адресата нельзя: справочника сотрудников с правом `memos.approve`, доступного всем ролям, нет (CRM `/users` — только администратору). EDS уже принимает `addressee_crm_user_id`; нужна операция каталога адресатов (CRM или EDS) и поле в BFF. Поле на форме показано как «Директор» с подсказкой.
3. **Письмо (`letter_out`).** Регистрирует роль с `letters.register` (в каталоге — `eds.inbox: full`: директор); остальным пункт «Письмо» в списке типов неактивен с причиной. Отправка по каналам, бланк и PDF — волна D-DOC (ADR-0020).
4. **Связь с проектом — через сделки ERP, без операции ERP.** `GET /eds/deal-options` ищет в новейших сделках ERP (как сквозной поиск, Q-PLT-14-1; операция поиска ERP-09 так и не появилась); только `crm.clients` или `eds.projects` на чтение. Хвост: полноценный поиск по всем сделкам — вместе с ERP-09.

6. **Дата «нужно до».** Нативное поле даты браузера: формат зависит от языка браузера. Проверка «не в прошлом» — по часовому поясу компании (Asia/Tashkent) в BFF и на форме.
7. **Мобильное окно.** На телефоне (< 768) карточка документа — собственный лист на весь экран (`Drawer` снизу) с кнопками внизу, а не окно каркаса (Drawer 360 px): окно каркаса — зона волны 15 (H5). Если каркас получит такой лист для всех экранов, `DocumentSheet` сводится к `PanelPortal`.
8. **Идемпотентность создания** (по ревью): `Idempotency-Key` идёт от формы через BFF в EDS `POST /documents` — ключ на экземпляр формы и тело запроса (форму изменили — ключ новый); создание с отправкой после сбоя `submit` продолжается по сохранённому черновику. Хвост: ключа нет у `PUT` и вложений (повтор безопасен: `PATCH` идемпотентен по смыслу, повторная загрузка создаёт второй файл).
9. **Хвосты по ревью.**
   - Журнал EDS `document.updated` пишется без списка изменённых полей (кто и когда — есть, что именно — нет).
   - Адресата исходящего письма в `PUT` снять нельзя: BFF передаёт `recipient` только непустым (пустой `null` EDS ради типа `letter_out` принял бы, но экран требует адресата).
   - Для письма проверяются два права: раздел `eds.memo.create` в BFF и `letters.register` в EDS; роль с первым, но без второго получает 403 EDS при создании (в форме пункт «Письмо» неактивен по `eds.inbox: full`).
   - Загрузка файла до 25 МБ целиком читается в память BFF (как W13-A5), потоковая передача в EDS без буфера — хвост.

## Q-D1-3-1 · Входящие письма и резолюция директора: решения исполнителя и разрывы бэкендов (D1-3 → лид и архитектор, волна 16) — **открыто**

**Контекст.** `/eds/inbox`, `/eds/inbox/:номер` и боковое окно «Резолюция» (BFF 0.16.0). EDS и ERP не менялись.

1. **Кто может быть исполнителем зоны — разрыв (CRM/EDS).** EDS при `POST /letters/{id}/resolution` проверяет только, что сотрудник
   есть в проекции и активен (`not_active_employee`), зону против его прав не сверяет; ERP создаёт задание любому названному. Списка
   «сотрудники зоны» ни у EDS, ни у CRM для ролей без `admin` нет. Сейчас BFF берёт `GET /users` и `GET /platform-roles` CRM токеном
   директора (ему открыто чтение `admin`) и сводит матрицы ролей: зона «товары» — раздел `erp.calc.goods` (полный), «услуги» —
   `erp.calc.services`, «условия оплаты» — `eds.payments` — по разделам каталога, не по кодам ролей (CONVENTIONS §2 п. 6). Обхода
   в BFF нет: если чтение справочника закрыто, ответ `directory = forbidden`, форма объясняет и не даёт «Утвердить» (возврат и отказ
   работают). Директор и роль-универсал по матрице попадают во все три зоны сразу (у системной «Директор» `erp.calc.goods`, `erp.calc.services`
   и `eds.payments` — full), поэтому автор резолюции исключается из кандидатов по id сотрудника, не по коду роли. **Варианты:** (1) оставить; (2) операция CRM `GET /api/v1/team?section=<раздел>&level=full` (активные сотрудники с
   разделом каталога; без email и ролей) и BFF перестаёт читать `/users` и `/platform-roles`; (3) проверка зоны в EDS (при резолюции
   исполнитель обязан иметь раздел зоны) через проекцию прав. **Рекомендация:** (2) в CRM — он источник истины по людям и матрицам
   (ADR-0003, ADR-0012); затем (3) в EDS как защита от неверного исполнителя.
2. **«Маржа не ниже, %» — группа `cost_margin`.** Порог маржи — внутренняя экономика: BFF не отдаёт `min_margin_pct` ролям без
   `cost_margin` (менеджер, бухгалтер), форма скрывает поле у роли без этой группы, а запись порога такой ролью — 422 `margin_forbidden`.
   Роль с `eds.inbox: full` без `cost_margin` резолюцию наложит без порога. **Рекомендация:** подтвердить (правило 6 CONVENTIONS Платформы).
3. **В карточке нет частей SPEC-v3 §7.3, для которых нет данных:** «PDF письма», «Переслать», подписанты, позиции, «ожидание
   клиента». EDS отдаёт реквизиты, суть, вложения, связи и журнал; остальное — следующий этап D (документы на бланке, ADR-0020).
4. **Шаг заявки — по стадии сделки ERP** (`deal_step`, хвост PLT-2x в `feeds/numbers.py`), без документов (КП, договор, акт):
   для резолюции наложена — не ниже «Расчёт», дальше — как ответит сделка. Вывод по документам (integration-map §2) остаётся хвостом.
5. **«Отклонить»: клиенту ничего не уходит.** SPEC-v3 §3.3 обещает вежливый ответ клиенту по шаблону; EDS публикует `letter.rejected`,
   ERP переводит заявку в «Отказ», отправки клиенту нет. В «Что произойдёт» этого не обещано. Нужен потребитель `letter.rejected` в CRM (бот).
6. **Адресация по номеру — два вызова EDS** (реестр, затем письмо). **Рекомендация (EDS):** фильтр `number` у `GET /letters` или
   `GET /letters/by-number` — один вызов; низкий приоритет.
7. **Боковое окно «Резолюция» на телефоне — собственный лист** (`?sheet=resolution`), а не окно каркаса: `ContextPanelDrawer` — 360 px
   между шапкой и нижней панелью, «на весь экран» из него не получить без правки `AppShell`/`ContextPanel` (зона волны 15, H5).
   **Рекомендация:** когда каркас получит режим «лист» для боковых окон < 768 px, перейти на него и убрать `ResolutionSlot`.
8. **Хвосты ревью.** `GET /eds/letter-files/{id}` не сверяет файл с письмом: IDOR нет, видимость файла проверяет EDS (404 иначе).
   Fallback `matchSection` для номеров со «/» без кодирования — общий для всех карточек с `detail: …/:id` (`isDocNumber`), а не только письма.
   Черновик резолюции живёт в `sessionStorage` вкладки (переживает перезагрузку, не остаётся на общем компьютере) и стирается при 409 и
   когда письмо уже не ждёт резолюции.

## Q-D20-1 · OpenAPI ERP стала правдой: расхождения BFF ↔ ERP, которые обнаружила сверка (D2-0 → лид и архитектор) — **решено D2-0 (PR #282)**

**Контекст.** D2-0 (B-011): выгрузка `/api/v1` ERP описывает код (без предупреждений drf-spectacular, общий `ErrorDetail`, живые ответы 40+ операций, которые зовёт BFF, сверены с ней тестами `core/tests/test_openapi_*_conformance.py`). 1. **`PATCH accounts/companies/{id}/settings/` принимает `payment_terms_days`** (срок оплаты счёта, дни; целое 0..32767, `null` — сбросить; неверное — 400 `BAD_NUMBER`). Раньше ERP отвечал 200 и молча оставлял старое значение. Тест: `test_payment_terms_days_is_accepted_validated_and_described`.

4. **Предпросмотр шаблона письма с произвольным `key` — не 500.** Если для ключа нет файла и нет активной строки на языке запроса, показывается просматриваемая строка БД; если нет и её (сервис `preview_template` без строки) — 404 `EMAIL_TEMPLATE_NOT_FOUND`. Тесты: `test_email_template_preview_*`.

9. **Замещение: очередь EDS и ERP (W15-H6).** Заместитель получает в «Моей очереди» только дела CRM замещаемого (его «мои» лиды и взятые им
   передачи, `GET /inbox?on_behalf_of`). Одобрение КП (ERP `my-approval-queue` — по токену пользователя), резолюции и служебные записки

   (1) оставить — директор на время отпуска передаёт решения вручную; (2) операция «очередь за коллегу по замещению» в ERP и EDS по данным
   замещения CRM (событие `identity.user.updated` с полями замещения или запрос в CRM при чтении); **Рекомендация:** (2) в ERP и EDS в зоне
   волны 16, когда появятся рабочие экраны директора; до тех пор в профиле честно сказано, что переносится.
10. **Адрес Платформы в письмах сброса пароля (W15-H6).** Ссылка «Забыли пароль?» строится из `PLATFORM_PUBLIC_URL` (PR #272). Если адрес не
    задан, CRM ссылку не выпускает и в журнале пишет `password_reset_skipped: platform_url_missing` — сотрудник идёт к администратору.
    **Рекомендация:** проверка «Состояние системы» уже показывает отсутствие адреса для писем; отдельного оповещения не добавляем.
11. **Колокольчик Платформы без ленты CRM (W15-H6).** Предупреждение «Telegram привязан как @ник. Если это не вы — отвяжите» идёт письмом
    и ответом бота: лента уведомлений Платформы — только ERP (`feeds/notifications.py`, «CRM-лента — с CRM-04»), записать туда событие CRM
    нечем. **Варианты:** (1) оставить письмо и бота; (2) CRM-лента уведомлений сотрудника (таблица и `GET /notifications` CRM) и её слияние в
    BFF. **Рекомендация:** (2) вместе с CRM-04, когда появятся другие уведомления CRM.
12. **Смена пароля самим сотрудником не закрывает его другие сессии (W15-H6).** Сброс (ссылкой, админом, приглашением) закрывает все сессии

## Q-W15-H7 · Помощь, первый вход и обращения к администратору: решения исполнителя и хвосты (W15-H7 → лид и архитектор) — **решено архитектором 2026-10-28 (см. DECISIONS); хвосты — B-079, B-080**

**Контекст.** Задача W15-H7 (UX-оценка P1-2, P1-4): «?» и раздел `/help`, приветствие и тур первого входа, «Написать администратору» и «Настройки · Обращения сотрудников». Принятые решения и то, что осталось вне PR:

1. **Статьи помощи правит тот, у кого доступ к репозиторию — не администратор в интерфейсе.** Статьи — файлы `docs/kb/help/*.md` (отдельный каталог; **не** база знаний бота, которая отвечает клиентам: у неё другие читатели, роль `kb:*` и перепроверка бота). `pnpm kb:sync` копирует их в `apps/platform/web/src/generated/help-articles`, и они едут в сборке SPA; `articles.test.ts` проверяет, что копия равна источнику. Администратор в Платформе их редактировать **не может**. **Варианты:** (1) оставить правку через PR (текст — это документация, ревью бесплатно, откат — git); (2) отдельный раздел «Статьи помощи» в CRM (таблица, редактор, `GET /help-articles` через BFF) — отдельная задача с правами и версиями. **Рекомендация:** (1) до пилота; (2) — если администратор захочет править сам. **Решение архитектора:** (1) — статьи помощи часть продукта и правятся через PR; внутренние инструкции компании — отдельная задача B-079 «Статьи компании» (админ правит в Настройках, показываются в той же помощи рядом с продуктовыми).
2. **Статьи только на русском.** Интерфейс помощи (кнопки, вкладки, словарь, «С чего начать», «Путь заявки», горячие клавиши) переведён на ru/uz/en; тексты статей — только ru, на uz и en в окне сказано «Статьи пока написаны по-русски». **Рекомендация:** перевод статей — после того, как узбекскоязычные сотрудники подтвердят, что они нужны. **Решение:** к пилоту, B-080.
3. **«С чего начать» определяется разделами каталога, а не кодами ролей.** Вид работы — по правам `full` на разделы (`admin`, `eds.inbox`/`eds.memo.approve`, `crm.leads`/`crm.clients`, `erp.calc.goods`, `erp.calc.services`, `eds.payments`); у пользовательской роли «Кассир» с `eds.payments: full` будет «Бухгалтер». Нет ни одного — «любая роль» (3 шага). Тексты шагов — в словаре `help.json`, не в коде.
4. **«Пропустить» скрывает приветствие на сеанс, «Больше не показывать» и «Готово» — навсегда.** Флаг — `users.onboarding_done_at` в CRM, `Me.onboarding_done`; существовавшим сотрудникам миграция ставит «показано», чтобы им карточка не выскочила. «Пропустить» не пишет в CRM (`sessionStorage`): новый вход снова покажет приветствие, пока сотрудник не выберет «Больше не показывать». **Решение архитектора:** принято.
5. **Лимит и права.** Не больше 5 обращений в час на сотрудника (CRM, 429 `ticket_rate_limited`); автор видит только свои, чужой номер — 404. Администратор отвечает и меняет статус (`tickets:write`), директор читает (`tickets:read`) — через раздел `admin` каталога, **отдельного пункта меню нет** (`admin.tickets` уже был в SPEC-v3 §6.2 и стал рабочим экраном). Директору строки «Ответить на обращение» в «Мои задачи» не показываются.
6. **Общий механизм «событие CRM → колокольчик» (закрывает п. 11 хвостов W15-H6, вариант 2).** `staff_notifications` в CRM + `GET /me/notifications` и слияние с лентой ERP в BFF (id `crm:<id>`). Им пользуются обращения и предупреждение «Telegram привязан как @ник. Если это не вы…» (W15-H6): `StaffLinkNotice` кладёт строку в колокольчик, письмо и ответ бота остаются.
7. **Горячие клавиши — только `Ctrl K`/`⌘ K`, `?`, `Esc`, Tab.** Остальных нет, в справке не обещаны. Клавиша `?` на русской раскладке — `Shift+7`, срабатывает как `?`.
8. **Тур не привязан к бокам экрана на узких экранах.** До 768 px рейл — нижняя панель, подменю — Drawer: карточка шага встаёт внизу экрана без подсветки несуществующего объекта.
9. **Тур и приветствие не открываются, пока профиль не загружен и пока у сотрудника временный пароль** (до смены пароля Платформа ведёт на `/change-password`, каркаса нет).
