# «Markdown как единый источник» для документов: оценка предложения и заключение
Статус: заключение принято владельцем 2026-11-12 ([DECISIONS](../DECISIONS.md)) · 2026-11-12

Поручение владельца 2026-11-12: оценить предложение «Docs-as-Code» (файл владельца `docs_as_code.md`): любой документ
хранится в Markdown, оформление — отдельно, PDF строит один генератор, файлы лежат деревом по схеме PARA, как в Obsidian;
входящие документы кратко описаны в Markdown, записаны в базу со ссылкой на файл. Сверено с кодом `origin/main` и с
[ADR-0020](../adr/0020-documents-letterhead-body-rendering.md), [ADR-0024](../adr/0024-signing-authority-and-official-documents.md),
[`rt-docs`](../architecture/rt-docs.md). Пометки: **[Ф]** — факт из кода или документа, **[П]** — вывод.

## Заключение

1. **Идея верная, и её ядро уже построено.** Один генератор на все документы — пакет `rt-docs`: данные отдельно, текст
   отдельно, оформление отдельно, PDF строит WeasyPrint по CSS для печати. Это та же схема, что в предложении. [Ф]
2. **Источником официального документа Markdown делать не стоит.** Остаёмся на структурном теле (JSON), принятом в ADR-0020.
   Причины — в §2. [П]
3. **Markdown берём там, где он силён:** способ набора в редакторе, язык общения с моделью, текст входящих для поиска и
   помощника, выгрузка и вставка. [П]
4. **Ощущение «пишу и сразу вижу документ» сейчас не достигнуто**, и это настоящий разрыв. Редактор тела — самодельный
   набор полей «абзац, список, таблица», а не живой документ. Исследование 2026-10-27 выбрало готовый редактор Tiptap,
   но для пилота был сделан упрощённый. Его и надо поставить. [Ф]/[П]
5. **Дерево папок PARA — как представление, а не как хранение.** Документ живёт в базе своего домена и имеет один дом;
   «папки» получаются из связей: проект, контрагент, вид, архив. [П]
6. **Typst сейчас не берём.** Замена движка означает переписать три макета бланка и подгонку страниц. Вернёмся, если
   замер покажет, что предпросмотр медленный. [П]

## 1. Что из предложения уже есть

| Предложение | У нас [Ф] |
|---|---|
| Реквизиты, текст и оформление разделены; шапку бланка автор не верстает | ADR-0020: документ = бланк + тело; «кому», номер, дата, подписант — поля формы |
| WeasyPrint, CSS для печати, бланк на первой странице, «Стр. X из Y» | `rt-docs`: три макета («письмо», «внутренний», «коммерческий»), нумерация только при двух и более страницах |
| Подпись не уходит одна на страницу, шапка таблицы повторяется, строка не рвётся | есть; дополнительно «Подогнать»: почти пустая последняя страница убирается плотностью и полями |
| Номер выдаёт сервер, а не автор | есть; по ADR-0024 бланк и номер появляются только после подписи уполномоченного |
| «ЧЕРНОВИК» поверх неподписанного | ADR-0024: до подписи документ помечен «ПРОЕКТ» |
| QR-код проверки подлинности | есть: код в колонтитуле и QR на последней странице |
| Сумма прописью | есть на русском, узбекском (латиница) и английском |
| Неизменяемая копия после подписи | снимок тела, данных и бланка |
| Ответ контрагента привязывается к исходящему | в почте хранятся `In-Reply-To` и `References` |
| Фоновая генерация и отправка по почте | рендер в воркере с тайм-аутом; почта — один сервис CRM |
| Предпросмотр совпадает с итогом | предпросмотр — тот же PDF с сервера |

Чего нет: коммерческие документы ERP (КП, договор, счёт, акт) ещё не переведены на `rt-docs` — это PR DOC-1…3 из
[плана документов](2026-11-11-documents-templates/README.md) §10. Пока они не сделаны, генератор «один» только для EDS.

## 2. Почему не Markdown как источник

| Требование к деловому документу | Markdown | Структурное тело (сейчас) |
|---|---|---|
| Поле-подстановка с типом: дата, деньги, контрагент | нет; нужен свой диалект | узел `variable` с кодом из каталога |
| Обязательный блок, который нельзя удалить (реквизиты, предмет договора) | проверить нельзя | `block {locked, required}`, проверка схемой |
| Таблица позиций: ширины колонок, объединение ячеек, числа вправо, итоги | в стандарте нет, только вставкой HTML | узлы таблицы с этими свойствами |
| Подпись двух сторон, место печати, разрыв страницы | нет | узлы `signature`, `pageBreak` |
| Безопасность | шаблонные выражения `{{ … }}` в тексте автора — это исполняемый код в документе | рендерится только известное, сырого HTML и выражений нет |
| Документы хранятся годами | диалект меняется — старые тексты читаются иначе | схема только расширяется, совместимость проверяет `make contracts` |
| Деньги | цены и НДС в шапке документа — второй источник правды | позиции и суммы даёт домен (ERP) блоком данных; «код решает» |

Ещё одно: предложение само советует редактор Tiptap. Его родной формат — то самое дерево узлов, которое у нас и
хранится. Хранить Markdown значило бы каждый раз переводить туда и обратно с потерями.

## 3. Что берём из предложения

| № | Что | Зачем | Готовая библиотека |
|---|---|---|---|
| 1 | **Редактор Tiptap вместо самодельного**, тело то же | «Пишу и вижу документ»: заголовки, списки, таблицы, жирный; набор в стиле Markdown (`# `, `- `, `**…**`) сразу превращается в оформление; вставка из Word | Tiptap core, MIT |
| 2 | **Мост Markdown ↔ тело** в `rt-docs` | Помощник пишет черновик в Markdown — он становится телом; тело отдаётся модели и поиску текстом; «Вставить Markdown», «Скачать .md» | markdown-it-py |
| 3 | **Текст входящего документа в Markdown** рядом с файлом: извлечённый текст и краткое содержание | Поиск по содержанию входящих, контекст для помощника, просмотр без открытия файла. Файл остаётся оригиналом | Docling (уже в плане FORM) |
| 4 | **Связи вместо папок**: «Документы проекта», «Документы контрагента», «Связанные» | То, ради чего в Obsidian держат структуру: найти всё по делу в одном месте | — |
| 5 | **Перевод документов ERP на `rt-docs`** (DOC-1…3) | После него генератор действительно один на всё | уже в плане |

Соответствие PARA нашему меню: Projects — «Проекты» и документы в них; Areas — журналы «Входящие», «Исходящие»,
«Внутренние»; Resources — «Шаблоны», база знаний, статьи компании; Archives — «Архив». Отдельного дерева файлов не нужно.
