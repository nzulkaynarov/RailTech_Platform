# Внешние системы Узбекистана для B2B-платформы: как они интегрируются и как ломаются

Дата ресёрча: 2026-10-22. Источники на русском, узбекском и английском: веб-поиск, чтение официальных страниц (cbu.uz, gov.uz, my.gov.uz, railway.uz, банки, docs.click.uz, developer.help.paycom.uz, developer.uzumbank.uz, core.telegram.org), GitHub-клиенты.
Дополняет `research-uz-edo.md` (ЭДО/ЭСФ/ЭТТН, операторы Didox/Faktura/E-DOCS, E-IMZO, правовая база). Темы оттуда здесь не повторяются, только ссылки.

Обозначения:
- **[Ф]** — факт, подтверждённый источником (ссылки в конце раздела).
- **[П]** — предположение или вывод автора; источником не подтверждено, проверить у поставщика.
- **[?]** — источники противоречат друг другу или устарели.

Контекст: B2B-компания (промышленные товары под заказ, импорт, услуги; связь с ж/д тематикой) строит CRM + документооборот + ERP. Внешние системы подключаются только через интеграционную шину, и сбой внешней системы не должен останавливать бизнес.

## 0. Главное за 60 секунд

1. **Публичных, документированных, самообслуживаемых API в Узбекистане мало.** Открыты и пригодны для автоматизации: курсы ЦБ (cbu.uz JSON/XML, без ключа), Payme/Click/Uzum (приём платежей), Telegram, SMS-шлюзы (Eskiz, Play Mobile), операторы ЭДО Faktura и E-DOCS. Остальное подключается через договор (банки, Asl Belgisi, ГНК) или работает только как веб-кабинет с ЭЦП (таможня, ЕЭИСВО, ж/д). [Ф]
2. **E-IMZO — общий знаменатель.** ЭДО, банк-клиенты, таможня, ЕЭИСВО, Asl Belgisi и my.soliq входят по ЭЦП руководителя или уполномоченного. Серверной подписи «от имени компании» нет, поэтому любое юридически значимое действие во внешней системе требует человека с ключом. Шина должна уметь ставить задачу «подпиши» и ждать. [Ф]+[П]
3. **Банки.** Единого Open Banking API в Узбекистане пока нет: финтех-стратегия ЦБ на 2026–2030 ставит запуск Open Banking на 2028–2029 годы. Сейчас работают три пути: файловый обмен 1CClientBankExchange через банк-клиент; **DiBank** (сервис Didox, около 25 банков, работает из 1С и Didox); собственный OpenAPI отдельных банков по договору (Ipoteka Bank: OpenAPI и SWIFT MT940; Kapitalbank: «Kapital API» через партнёра Venkon Group). [Ф]
4. **Поступления денег** практичнее всего получать опросом выписки по расписанию. Вебхуков о входящих платежах от банков в открытых источниках не найдено. Межбанк в сумах проходит в реальном времени (МПС ЦБ), а для B2B есть система мгновенных платежей ЦБ, работающая 24/7. [Ф]+[П]
5. **1С у контрагентов и у бухгалтерии — почти наверняка.** Локализацию для Узбекистана делает 1S-TOSHKENT: «Бухгалтерия для Узбекистана» 3.0, УТ 11.0 (релиз 11.0.0.23 от 15.05.2026). Технически доступны OData (платформа 8.3.5+, нужна публикация на веб-сервере), HTTP-сервисы (дописываются в конфигурацию) и EnterpriseData. Местные интеграторы рекомендуют начинать с контрагентов и статусов оплат, затем номенклатура и остатки, затем документы. [Ф]
6. **SAP** встречается у крупных компаний (Узавтосаноат, Навоиазот, UZTEX — S/4HANA). Для B1 стандарт — Service Layer (OData v4 `/b1s/v2`, сессия 30 минут, без вебхуков). Для малого бизнеса это скорее «интеграция с клиентом», чем свой стек. [Ф]
7. **Таможня и ВЭД** — веб-кабинеты с ЭЦП (ed1.customs.uz, singlewindow.uz, E-Contract/ЕЭИСВО) без публичного API. ГТД обычно подаёт брокер. Интеграция — ручной ввод статусов, импорт файлов от брокера и бесплатные справочные сервисы (tarif.customs.uz, my.gov.uz «груз по номеру вагона»). [Ф]+[П]
8. **Проверка контрагента по ИНН.** У ГНК есть официальная интерактивная услуга «Интеграция с центральной базой данных налоговых органов» (my3.soliq.uz, услуга № 708, бесплатно). По заявлению ГНК, она отдаёт реквизиты, режим налогообложения, номер и статус свидетельства НДС, руководителя и адреса. Технические условия публично не описаны. Запасные варианты — API операторов ЭДО (Faktura `CheckCompanyExist`) и неофициальные скрейперы orginfo.uz (у сайта API нет). [Ф]+[П]
9. **Логистика и ж/д.** У «Ўзбекистон темир йўллари» нет публичного API для грузоотправителей. ЭТТН при ж/д перевозке автоматически заполняется из e-nakl.railway.uz по номеру вагона, но только внутри ИС ГНК и операторов ЭДО. Для статусов вагонов остаются ИВЦ УТЙ (услуга), коммерческие GPS-трекеры и ручной ввод. [Ф]
10. **Рекомендация для шины [П].** Для каждой внешней системы — адаптер с исходящим outbox, повтором с экспоненциальной задержкой и идемпотентным ключом. Входящие события брать опросом по расписанию; вебхуки (Payme, Click, Uzum, Telegram) принимать только как ускорение, а сверку делать опросом. Для систем без API (таможня, ж/д, ЕЭИСВО) — «ручной статус» в ERP с вложением файла. Первая волна по ценности: банк (выписки), ЭДО (из прежнего файла), курсы ЦБ, проверка ИНН, Telegram/SMS. Вторая волна: 1С бухгалтерии, Payme/Click. Третья: таможня, ж/д, Asl Belgisi.

## 1. 1С в Узбекистане

### 1.1 Продукты и кто их делает
- Типовые локализованные конфигурации: «1С:Бухгалтерия 8 для Узбекистана» (ред. 3.0, руководство на its.1c.eu/uz), «1С:Управление торговлей 8 для Узбекистана» (ред. 11.0, вышла в 2018 году на платформе 8.3, текущий релиз 11.0.0.23 от 15.05.2026), «Розница» и «Управление компанией для Узбекистана» (ред. 3.0), ЗУП, «1С:ERP». **«Редакции 3» у УТ для Узбекистана нет**, актуальная линейка — 11.0. [Ф]
- Локализацию и линию консультаций по УТ ведёт **1S-TOSHKENT** по заказу фирмы «1С». [Ф]
- Цены лицензий (партнёр perfect-solutions.uz, 2026): Бухгалтерия от 3,6 млн сум, УТ от 6,0 млн, ЗУП от 4,3 млн, 1С:ERP от 197 млн сум. [Ф]
- Есть облачная 1С (42clouds.uz публикует «УТ для Узбекистана»). [Ф]
- Партнёры в Ташкенте (официальный список 1С): «ISO Реальная автоматизация / Business Automatization», «1С:Первый Бит», FINSOFT, «1С:Франчайзинг.Старт». Также активны Leading, investadvance.uz, 1cba.uz, 1solution.uz, softteampro.uz, perfect-solutions.uz. [Ф]

### 1.2 Способы интеграции (техника)
| Способ | Что даёт | Синхронность | Особенности |
|---|---|---|---|
| **Стандартный интерфейс OData** | REST-доступ к справочникам, документам, регистрам; JSON при `$format=json` | Синхронно, опрос | Платформа ≥ 8.3.5; нужна публикация базы на IIS/Apache и включение состава OData в самой конфигурации; Basic-аутентификация пользователем 1С. | **HTTP-сервисы** | Узкий версионируемый контракт под конкретную операцию | Синхронно | Пишутся в расширении конфигурации, дороже в разработке, зато устойчивы к обновлениям. [Ф] |
| **EnterpriseData (Универсальный формат)** | XML по XDTO-схеме; 94+ типа бизнес-сущностей; используется в типовой синхронизации «УТ ↔ Бухгалтерия для Узбекистана» | Пакетно, асинхронно (планы обмена, по расписанию) | Для событий в реальном времени не подходит. [Ф] |
| **Файлы** (XML/CSV, 1CClientBankExchange) | Ручной или полуавтоматический обмен | Пакетно | Самый надёжный «минимум», когда 1С у внешнего бухгалтера. [Ф]+[П] |

### 1.3 Что первично и в каком порядке стыкуют
- Узбекский интегратор рекомендует такой порядок [Ф]:
  1. **Контрагенты.** Создаются в CRM, уходят в 1С, реквизиты и банковские данные уточняются бухгалтером и возвращаются; ключ сопоставления — ИНН.
  2. **Счета и статусы оплат.** Счёт создаётся в учётной системе, номер и статус возвращаются в CRM.
  3. **Сводка взаиморасчётов** (долг, просрочка) уходит в CRM.
  4. **Номенклатура и остатки** идут из 1С в CRM; обратный поток редок, потому что списание идёт только через учёт.
- Принцип: «CRM управляет отношениями, 1С отвечает за документы». Документы не создаются в обход учётной системы. [Ф]
- Для нашей платформы [П]: если ERP становится учётной системой для операционки (заявки, КП, договоры, склад), то 1С остаётся системой **бухгалтерского и налогового учёта**. Тогда мастер-данные по направлениям такие: контрагенты и номенклатура — ERP → 1С; оплаты из банка — банк → ERP (или 1С → ERP, если выписку грузит бухгалтер); реализации, акты и ЭСФ — ERP → оператор ЭДО и параллельно → 1С проводкой. Справочник ИКПУ и единиц — общий источник tasnif.soliq.uz. Решить, кто «владелец» выписки, нужно до разработки.
- Типовые сбои [Ф]: дубли контрагентов при разных написаниях; обмен ломается после обновления конфигурации; нетиповые доработки 1С увеличивают объём работ; локальная 1С за NAT недоступна из облака, нужен исходящий канал или VPN.

## 2. SAP в Узбекистане

- **Кто использует.** S/4HANA: UZTEX Group (первое внедрение в текстильной отрасли СНГ), предприятия «Узавтосаноат», АО «Навоиазот»; Узбекнефтегаз планирует SAP (PM, FI, MDG). Офис SAP в Ташкенте открыт в 2022 году. [Ф]
- **Кто внедряет.** ALTITUDE / Accelerated Business Consulting (ABC; B1, S/4HANA, Odoo), LeverX, T4DATA (S/4HANA), подрядчики из списка tovar.uz (B1 «от 3 месяцев»). Размер ABC в справочниках противоречив. [Ф]+[?]
- **Локализация.** Готовой узбекской локализации B1 (ЭСФ, отчётность) в источниках не найдено. По LeverX, локализация в Узбекистане — это хранение статусов ЭСФ и риск-уровня (с 2026 года), мастер-данные (ИНН, статус НДС, ИКПУ, маркировка) и интеграция с госплатформами через промежуточный слой (Integration Suite или PI/PO) с централизованной подписью. Типовые сбои там же: смена формата XML, истечение сертификатов, новые обязательные реквизиты, недоступность API. [Ф]
- **Как интегрироваться с B1** [Ф]:
  - **Service Layer** — REST/OData; v4 `/b1s/v2/` основной с FP 2405, v1 `/b1s/v1/` устарел. Вход `POST /Login` (CompanyDB, UserName, Password) возвращает cookie `B1SESSION`. Сессия живёт 30 минут без активности (настраивается в `b1s.conf`); при истечении — ошибка −5002. Страница по умолчанию — 20 записей, есть `$batch` с атомарными changeset. OAuth/OIDC — с 10.0 FP 2305 через внешний IdP.
  - **DI API** (.NET, на той же машине) и **B1if** (Java-middleware, событийные сценарии).
  - Нативных вебхуков у Service Layer нет. События — через B1if или опрос по `UpdateDate`.
- **S/4HANA** [Ф, общеизвестная практика SAP]: OData (Gateway), IDoc (ALE), RFC/BAPI, SOAP. Подключение почти всегда через SAP Integration Suite или PI/PO у клиента.
- Вывод [П]: для нашей платформы SAP — это сценарий «крупный клиент хочет обмен заказами и счетами». Делать стоит не адаптер к SAP, а свой стабильный API или обмен файлами (CSV/XML по нашей схеме). Мапинг на своей стороне делает интегратор клиента.

## 3. Банки, платёжная система, агрегаторы

### 3.1 Регулирование и инфраструктура
- **Open Banking.** Отдельного нормативного акта ЦБ об обязательных открытых API банков в 2023–2026 годах не найдено. В сентябре 2026 года ЦБ утвердил Национальную стратегию развития финтеха на 2026–2030 годы: 2026–2027 — базовая инфраструктура, **2028–2029 — запуск Open Banking**, регуляторная «песочница». Один англоязычный обзор утверждает, что ЦБ «внедряет Open Banking с 2024 года и создал технические стандарты API». Первоисточником это не подтверждено. [Ф]+[?]
- **Межбанк.** МПС ЦБ работает в реальном времени на валовой основе (секунды) в регламенте операционного дня (с 9:00 до 17:00 — передача и приём; полный регламент — на cbu.uz). **Система мгновенных платежей ЦБ** (с февраля 2020 года) проводит B2B-платежи и платежи в бюджет 24/7, включая выходные. Лимит определяется ликвидностью банка на корсчёте. [Ф]
- **Положение о безналичных расчётах** и платёжное поручение — см. `research-uz-edo.md` §4.

- **Форматы.** Стандарт де-факто — текстовый **1CClientBankExchange** (выгрузка платёжек в файл, загрузка в банк-клиент, подпись там; обратно — файл выписки; кодировка должна совпадать с клиент-банком). Встречаются 1С:ДиректБанк и **MT940** (Ipoteka/SWIFT). Банковских «вебхуков о поступлении» в открытых источниках нет. [Ф]
- **Аутентификация и подпись.** Платёжное поручение подписывается ЭЦП клиента (E-IMZO или ключ банка). Для OpenAPI — договор, комплект документов, согласование параметров. Вероятно, mTLS, IP-белые списки или VPN [П].
- **Типовые сбои [П]:** выписка за день становится окончательной только после закрытия операционного дня, поэтому внутридневные данные могут меняться; дубли при повторной загрузке; несопоставленные контрагенты из-за разных реквизитов (это отмечает и партнёр 1С [Ф]); истечение ЭЦП подписанта (2 года).
- **Вывод [П].** Первый шаг — **не API, а файл**: импорт 1CClientBankExchange или MT940 в ERP с идемпотентностью по (счёт, дата, номер документа, сумма). Второй — OpenAPI банка, где компания обслуживается (Ipoteka/Kapital), или DiBank через Didox Tech. Исходящие платёжки создаются в ERP как черновик и подписываются в банк-клиенте человеком.

## 4. Таможня, ВЭД, курсы валют

### 4.1 ГТК и электронное декларирование
- ГТД подаётся **только в электронной форме** через ЕАИС ГТК. Форматы электронных деклараций ГТК публикует на своём сайте (положение об электронном декларировании). На практике ГТД почти всегда подаёт **таможенный брокер** (классификация по ТН ВЭД, таможенная стоимость, расчёт платежей). По Таможенному кодексу проверка — 1 рабочий день; на практике в среднем около 3 дней. [Ф]
- **Личный кабинет участника ВЭД** (ed1.customs.uz): подача ГТД, онлайн-статус оформления ГТД, E-ombor (электронный учёт товаров на складе), E-tranzit (предварительное информирование по автотранспорту), E-arxiv; экспорт — cargo.customs.uz. Страница кабинета давно не обновлялась; при загрузке вылезла ошибка TLS-сертификата. **Публичного API нет.** [Ф]+[?]
- **my.gov.uz:** около 10 услуг ГТК, в том числе предварительное информирование (услуга 102) и **«информация о ввозимых грузах ж/д транспортом по номеру вагона или контейнера»** (услуга 81: бесплатно, ответ автоматически примерно за 1 минуту). [Ф]
- **Единое окно (singlewindow.uz):** более 50 разрешительных документов от 12 ведомств, отслеживание статуса заявки. Создано по соглашению с Кореей (с 2014 года). Вход по ЭЦП, API для внешних систем не опубликован. [Ф]
- **ЕЭИСВО / E-Contract** (ПКМ № 283 от 14.05.2020): **регистрация всех импортных и экспортных контрактов** с ЭЦП. С 19.05.2025 работает в полном формате, прежние каналы (АИС «Контракт», EXIM) закрыты. Логический контроль: сумма контракта равна сумме спецификаций. Присваивается идентификационный номер (по одному источнику — 27 цифр [?]). Регистрация самостоятельная или через банк — источники расходятся [?]. API нет. [Ф]
- **tarif.customs.uz** («Интегрированный тариф»): ставки пошлин и налогов, нетарифные меры, справочники ТН ВЭД, единиц, стран, постов, калькулятор платежей. **Официального API нет**, только веб. [Ф]
- **Вывод [П].** Для импортных заказов ERP хранит номер контракта ЕЭИСВО, номер и статус ГТД, сумму платежей, документы брокера (PDF/XML). Ввод ручной или импорт файла от брокера, плюс напоминания по срокам. Для ставок — локальный справочник ТН ВЭД с ручным обновлением. Автоматизировать имеет смысл только опрос «груз по номеру вагона», и то если появится машинный интерфейс; сейчас это веб-услуга.

### 4.2 Курсы ЦБ (cbu.uz) — единственный по-настоящему открытый госAPI
- `GET https://cbu.uz/ru/arkhiv-kursov-valyut/json/` (без параметров) отдаёт курсы на текущую дату. На странице для веб-мастеров сказано «прошлой недели», но живой запрос 22.10.2026 вернул записи с `Date: 22.10.2026` [?]. Варианты: `.../json/all/YYYY-MM-DD/`, `.../json/USD/YYYY-MM-DD/`; аналогично `/xml/`; есть CSV на портале открытых данных. [Ф]
- Поля JSON: `id, Code ("840"), Ccy ("USD"), CcyNm_RU/UZ/UZC/EN, Nominal, Rate ("11965.51", строка), Diff, Date ("DD.MM.YYYY")`. Ключ не нужен; лимиты и SLA не указаны; CORS для браузера не гарантирован — запрашивать с сервера. [Ф]

## 5. Налоговая: проверка контрагента, ИКПУ, маркировка

### 5.1 Проверка контрагента
- **Официальный канал ГНК.** На gov.uz описана интерактивная услуга «Интеграция с центральной базой данных налоговых органов» (my3.soliq.uz, **ID 708**). Данные выдаются «заинтересованным юридическим и физическим лицам, в том числе в их информационные системы и мобильные приложения», онлайн-данные — **бесплатно**. Состав: полное и краткое наименование, ОПФ, ОКЭД, СОАТО, код ОКПО, тип налогоплательщика, категория, форма собственности, регистрационные данные, **налоговый режим**, дата прекращения деятельности, **номер и статус свидетельства НДС**, руководитель, телефон, e-mail, уставный капитал, учредители, юридический, фактический и филиальные адреса, банкротство и исключение из реестра, обязательный аудит, административные взыскания. Техника подключения (протокол, ключи, договор) публично не описана; горячая линия 1198. [Ф]
- **Веб-проверки без API** [Ф]: реестр плательщиков НДС на my.soliq.uz (может быть недоступен из-за рубежа); «чёрный список» злоупотребивших НДС (более 5500 компаний); налоговая задолженность по ИНН на soliq.uz; ЕГРПО на registr.stat.uz; fo.birdarcha.uz и new.birdarcha.uz (модуль «Мой бизнес», 2024); исполнительные производства на mib.uz; реестр недобросовестных исполнителей на xarid.uzex.uz.
- **«Рисковые» ЭСФ и налогоплательщики**: риск-уровень с 01.01.2026 — см. прежний файл §1.2. Получать его можно только через ИС ГНК или оператора ЭДО [П].
- **Через оператора ЭДО**: Faktura `GET Api/CheckCompanyExist/{inn}` (прежний файл §2.3). Для Didox метод поиска компании по ИНН в открытых источниках не найден [Ф-отсутствие].
- **Вывод [П].** Адаптер «реестр контрагентов» с цепочкой источников: (1) услуга ГНК 708, если подключат; (2) оператор ЭДО; (3) ручной ввод с отметкой «не проверено». Результат кэшировать с датой и TTL, например 7 дней для статуса НДС. Создание сделки не блокировать, а только предупреждать.

### 5.2 ИКПУ (tasnif.soliq.uz)
- Каталог ИКПУ (17 цифр) нужен в каждой позиции ЭСФ и чека. Поиск по коду, слову или ТН ВЭД; полный каталог можно скачать в Excel. [Ф]
- Есть **недокументированный публичный JSON** `https://tasnif.soliq.uz/api/cls-api`, им пользуются open-source клиенты (mxik-js, ikpu-mxik). Авторы предупреждают, что он «не документирован, может меняться и может не отвечать серверам вне Узбекистана». [Ф]
- **Паттерн [П]:** локальный справочник ИКПУ (импорт Excel или ночной опрос), привязка ИКПУ к номенклатуре человеком, отчёт «позиции без ИКПУ».

### 5.3 ЭСФ, ЭТТН — кратко
Только через ИС ГНК или аккредитованного оператора с подписью E-IMZO. API Faktura и E-DOCS публичны, Didox — за логином. Вебхуков нет, статусы получаем опросом. Подробно — `research-uz-edo.md` §1–2, §5–6. [Ф]

### 5.4 Маркировка Asl Belgisi
- Оператор — ООО «CRPT TURON». ГИС прослеживаемости, коды Data Matrix. С **1 декабря 2025 года** переход на платформу **xTrace 2.0**: изменены публичные API (статус кода, тип упаковки, GTIN, карточка товара, эмитент, даты, партия). Документация API (xTrace 2.0 OpenAPI, API Национального каталога) лежит в справочном центре help.crpt-turon.uz, раздел «Working with API and Technical Documentation»; при загрузке страницы получили 403. [Ф]
- Регистрация в кабинете — по ЭЦП юрлица или ИП. В 2.0 можно добавлять пользователей с ЭЦП физлица. [Ф]
- С 01.07.2026 ЭСФ с маркированными товарами автоматически сверяются с Asl Belgisi; на подтверждение ЭСФ покупателем с маркированным товаром — 1 день (прежний файл). «1С:Бухгалтерия для Узбекистана» 3.0 умеет проверять данные с Asl Belgisi. [Ф]
- Аутентификация API: по аналогии с российским True API («Честный знак»: challenge → подпись PKCS#7 → токен на ~10 ч) вероятна схема E-IMZO → токен [П].
- **Вывод [П].** Актуально, только если компания продаёт или импортирует товары из перечня маркируемых. Для промышленных товаров под заказ — проверить перечень и пока не строить.

## 8. Мессенджеры и SMS

### 8.1 Telegram Bot API
- **Лимиты** (официальный Bots FAQ) [Ф]: около 1 сообщения в секунду в один чат; 20 сообщений в минуту в группу; массовая рассылка около 30 сообщений в секунду. При превышении — HTTP 429 с `retry_after`, который растёт у повторных нарушителей. Платные рассылки до 1000 сообщений в секунду (0,1 Star за сообщение сверх 30/с; нужно ≥100 000 Stars и ≥100 000 MAU). Точные лимиты Telegram не документирует, они разные у ботов и меняются.
- **Доставка входящих** [Ф]: `getUpdates` хранит неполученные обновления **не дольше 24 часов**. Вебхук повторяется при не-2xx ответе и «сдаётся после разумного числа попыток» (число не указано). Порты 443/80/88/8443; `max_connections` 1–100 (по умолчанию 40); заголовок `X-Telegram-Bot-Api-Secret-Token` для проверки источника.
- **Надёжность в Узбекистане** [Ф]: в 2021 году Telegram кратковременно ограничивали из-за требования хранить ПДн в стране, ограничение сняли в течение дней. В 2024–2026 годах ограничений не найдено. Риск регуляторный, не технический.
- **Паттерн [П]:** исходящие сообщения — через очередь с ограничителем (на чат и глобально) и уважением `retry_after`. Входящие — вебхук, который сразу пишет update в БД (inbox) и отвечает 200; обработка асинхронная. Простой бота больше 24 часов ведёт к потере обновлений, поэтому нужен мониторинг `getWebhookInfo` (pending_update_count, last_error).

## 10. Что это значит для интеграционной шины (вывод автора) [П]

1. **Три класса внешних систем — три шаблона адаптера**:
   - *API с опросом* (ЭДО, банки, cbu.uz, Eskiz, телематика): outbox → воркер с повтором (экспонента + джиттер, лимит попыток, DLQ) → периодический опрос статусов → событие во внутреннюю шину.
   - *Входящие синхронные вызовы* (Payme, Click SHOP, Telegram webhook): тонкий приёмник, который пишет в inbox и отвечает сразу, идемпотентно по внешнему ID; бизнес-логика асинхронно.
   - *Без API* (таможня, ЕЭИСВО, ж/д, банк-клиент вручную): «ручной адаптер» — форма ввода статуса и номера плюс загрузка файла; в журнале шины это обычное событие с источником `manual`. Так процессы описываются одинаково, а автоматизацию можно добавить потом без смены модели.
2. **Человек с ЭЦП — часть интеграции.** Каждый юридически значимый шаг (ЭСФ, договор, платёжка, ГТД, ЕЭИСВО) — это задача подписанту с SLA и эскалацией. Сбой тут чаще организационный (ключ истёк, руководитель в отъезде), чем технический. Нужен учёт сроков сертификатов ЭЦП (≤ 2 лет).
3. **Ничего внешнего — в синхронном пути пользователя**, кроме справочных запросов с тайм-аутом и кэшем. Проверка ИНН и курс берутся из кэша, а при сбое показывается предупреждение.
4. **Сверка важнее вебхуков.** Ни банки, ни операторы ЭДО не дают надёжных уведомлений, поэтому для каждого потока нужна ежедневная сверка (выписка ↔ счета, ЭСФ у оператора ↔ реализации, Payme `GetStatement` ↔ платежи).
5. **Изоляция регуляторных форматов.** Форматы ЭСФ, ИКПУ и маркировки меняются несколько раз в год. Их маппинг держать только в адаптере провайдера и покрывать контрактными тестами на фикстурах.
6. **Размещение.** Требование хранить ПДн граждан Узбекистана в стране влияет на выбор хостинга и на отправку ПДн во внешние облака (LLM, SaaS). Проверить с юристом до продуктива.

## 11. Что уточнить до проектирования адаптеров (чек-лист)

1. **Бухгалтерия компании:** какая 1С (Бухгалтерия 3.0 для РУз? УТ 11?), где стоит (локально, облако), кто партнёр 1С; кто «владелец» банковской выписки — 1С или ERP.
2. **Банк(и) компании:** есть ли OpenAPI (Ipoteka), Kapital API (Venkon), подключение DiBank; формат выписки (1CClientBankExchange / MT940), тестовый контур, способ подписи.
3. **ГНК:** порядок подключения к услуге 708 (договор, протокол, ключи, тест), выдают ли её коммерческим ИС.
4. **ВЭД:** доля импорта, кто брокер, что брокер может отдавать в машинном виде (XML ГТД, статусы); кто регистрирует контракты в ЕЭИСВО.
5. **Ж/д:** работает ли компания со своими вагонами или через экспедитора; доступ к услугам ИВЦ УТЙ (форматы, цена); нужна ли телематика.
6. **Маркировка:** входят ли товары компании в перечень Asl Belgisi.
7. **Клиенты:** кто из крупных клиентов на SAP или 1С и ждёт обмена заказами и счетами (EDI-подобный сценарий).
8. **SMS:** зарегистрировать имя отправителя и шаблоны у Eskiz заранее (модерация).
