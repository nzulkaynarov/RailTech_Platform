# Ресёрч 3. «Отметить за контрагента»: действие внешней стороны, записанное сотрудником

Дата 2026-11-02 · только чтение, по `main` @ 442b7a87e · пути от корня репозитория.

## 0. Суть

- Принять КП сейчас может **только клиент**: в Cabinet или по публичной ссылке, в обоих случаях с кодом. У менеджера действия «Клиент
  принял КП» нет нигде: ни в Платформе, ни в API (его сознательно убрали в M1-ERP-02, DECISIONS 2026-10-14, строка 77). Есть только
  `force-approve` суперпользователя, но он ломает цепочку: не двигает стадию, не открывает проект, не формирует договор.
- Клиент «принял устно» → в системе тупик: проекта нет, кнопка «Сформировать проект договора» не появляется, а КП через `valid_until`
  уйдёт в «Срок истёк». Путь P7 «КП → договор» на пилоте с клиентом, который не открыл кабинет, **не проходит**.
- Для договора и акта стандарт фактически уже есть: `contract_flow.TRANSITIONS` («Согласовано клиентом», «Отклонён клиентом» с
  причиной, «Скан» с обязательным файлом) и `act_flow` (скан, возврат с причиной). Не хватает канала, лица со стороны клиента и
  значка «внесено сотрудником».
- Рекомендация: один механизм «Отметить за контрагента» — общий набор полей (атрибуция), одна форма в Платформе, одно необязательное
  поле в событиях шины. До пилота — **только КП (принял / отклонил)**. «Скан договора» уже есть.

## 1. Как сейчас принимается КП (файл:строка)

| Что | Где |
|---|---|
| Ядро акцепта (общее для Cabinet и публичной страницы): проверка «только SENT» → APPROVED → `promote_to_project` → событие `quote.accepted` → стадия `CONTRACT_SIGNED` → договор → журнал | `apps/erp/backend/crm/services/quotes/lifecycle_accept.py:31-109` (проверка статуса — :46) |
| Отказ (так же, причина обязательна) | там же `:112-176` |
| Cabinet: `POST /portal/quotes/{id}/accept` по коду из `request-code` | `apps/erp/backend/portal/views.py:407`, `portal/urls.py:67` |
| Публичная ссылка: код на почту контакта | `apps/erp/backend/portal/public_views.py:276-307`, `core/urls.py:422` |
| Сотрудник: действия «за клиента» нет («Client approve / reject live in the portal (FIX-13)») | `apps/erp/backend/crm/views/quotes/approval.py:1-9` |
| `approve_quote(…, approved_by_user)` существует, но **из вьюх не вызывается** | `crm/services/quotes/lifecycle.py:301` |
| `force-approve`: только `is_superuser`, причина обязательна, `[FORCE_ADMIN]`. Только меняет статус и публикует событие, **без** `transition_deal_stage`, `promote_to_project` и договора. В интерфейсе нет | `lifecycle.py:454-519`, `approval.py:61-77` |
| Истечение: SENT после `valid_until` → EXPIRED | `crm/tasks.py:151` |

**Что блокирует путь к договору без акцепта**
- Проект в Платформе — это сделка на стадии `CONTRACT_SIGNED`/`CLOSED_WON`: `crm/services/projects.py:40-46`. `_accepted_quote` берёт только
  APPROVED (`projects.py:73-74`), а `can_create_contract = quote and contract is None and may_manage` (`projects.py:461`). BFF без этого
  флага отвечает 403 «по принятому КП»: `apps/platform/bff/app/eds_projects.py:197-205`.
- Для КП в статусе SENT в Платформе нет экрана с результатом у клиента: «Исходящие» ведут в старый ERP (`apps/platform/web/src/modules/bridge.ts:88-92`),
  мост снимает P6. Карточка КП `eds/drafts/QuoteView.tsx` показывает маршрут директора, действий после отправки на ней нет.

**Как это обходят сейчас (дыры API, не UI)**
1. `POST /crm/deals/{id}/change-stage` QUOTE_SENT → CONTRACT_SIGNED с правом `deal.manage` (`crm/services/deals.py:54`, `:123-143`).
   Проект появляется, но КП остаётся SENT: договор в Платформе не сформировать, события `quote.accepted` нет, КП истекает.
2. `POST /crm/contracts/generate-from-quote/` пускает **и SENT** (`crm/services/contracts.py:78`). Договор появляется без следа
   «кто и когда принял». После скана стадия QUOTE_SENT → CLOSED_WON запрещена конечным автоматом (`deals.py:54`): `contract.auto_close_failed`,
   автосчёта нет.
3. `force-approve` суперпользователем — см. выше, получается тупик без проекта.
→ Все три обхода оставляют систему в рассогласованном состоянии. Отдельный вопрос: после ввода механизма закрыть SENT в `contracts.py:78`.

Вывод: из шести шагов, где «за него» нужен, дыра одна жизненная (КП) и одна средняя (приёмка поставки). У остальных путь есть, но
атрибуция разнобойная: где-то `note`, где-то `reason`, нигде нет канала, лица у контрагента и значка в журнале.

**Общий стандарт, выведенный из эталонов**
1. Ручная отметка — **штатный второй путь** рядом с онлайн-действием контрагента, а не «админский форс» (Zoho, Odoo, Salesforce, 1С).
2. Право — у роли, которая ведёт документ, а не у администратора (HubSpot: доступ к Sales tools; Odoo: продавец; SAP: закупщик).
3. Источник помечен и отличим от онлайн-действия (Stripe `paid_out_of_band`, DocuSign «In Person Signing» с хостом).
4. Реквизиты: способ или канал, дата, ссылка или номер документа контрагента (Chargebee — способ и номер, SAP — № AB).
   Вложение — где есть документ: скан подписанного (HubSpot written signature, наш `attach_scan`).
5. После отметки запускается та же цепочка, что и при онлайн-действии (Zoho: из принятого КП — заказ или счёт; Salesforce Flow; Stripe
   `invoice.paid`). Отдельного «полуподтверждённого» состояния нет.
6. Повторное подтверждение контрагентом не требуется ни в одном эталоне. Контрагента уведомляют обычным документом: подтверждением
   заказа или квитанцией (Odoo order confirmation, Stripe receipt).

## 4. Рекомендация: один механизм «Отметить за контрагента»

**4.1. Атрибуция (одна схема на все шаги)**

| Поле | Обязательно | Значения |
|---|---|---|
| `channel` | да | `phone` · `email` · `messenger` · `in_person` · `paper` · `edo_operator` |
| `counterparty_person` | да | контакт компании (`erp_contact_id`) или ФИО и должность текстом |
| `occurred_at` | да | дата и время со слов, не позже «сейчас» |
| `comment` | да для КП и приёмки; при отказе — причина (уже есть) | текст |
| `evidence` | по шагу (таблица 4.3) | файл: PDF или изображение, `core.validators.validate_scan_upload`; при `channel=edo_operator` вместо файла допустим номер документа у оператора |
| `recorded_by`, `recorded_at` | система | сотрудник и время записи |

**4.2. Как это ложится в инварианты**
- **Данные — у владельца шага** (ERP для КП, договора, акта, поставки и закупки). Общей таблицы между доменами нет. Внутри ERP —
  одна сущность-вложение `OnBehalfRecord` (entity_type, entity_id, action, поля 4.1, файл; только дополнение, `pghistory`).
  Журнал — существующий `ActivityLog` и `log_admin_action` с `event_params.on_behalf={channel, person}` и `reason=comment`. Прецедент
  формы данных — `Quote.fx_manual_meta {reason, set_by, set_at}` (`sales/models/quotes.py`).
- **Одно ядро на действие**: отметка вызывает **тот же** `perform_quote_acceptance` / `perform_quote_rejection` с новым аргументом
  `on_behalf=…` (правило 8 «нет дублированного конечного автомата» уже записано в докстринге `lifecycle_accept.py:1-14`). Значит, будут
  проект, договор, событие и уведомление продавцу. `force-approve` остаётся аварийным инструментом администратора.
- **Контракт раньше кода, в одном PR**: (а) OpenAPI ERP — компонент `OnBehalfAttestation` и действие
  `POST /crm/quotes/{id}/record-client-decision/` `{decision: accept|reject, reason?, …4.1}`; (б) события — необязательное поле
  `recorded_by_staff {name, channel}` в `_defs.v1.json#/Actor` или `QuoteOutcome`. Изменение аддитивное, но там
  `additionalProperties:false`, поэтому потребители (CRM `erp_event_handlers.py`, BFF `feeds/events.py`) правятся в том же PR (скилл
  contract-change). `actor.type` остаётся `staff`: честно, кто нажал. «За кого» — в новом поле.
- **Инвариант 1** (сотрудник не входит в Cabinet) соблюдён: это запись факта в Платформе, а не вход под клиентом.
- **UI Платформы**: один компонент `RecordOnBehalfModal` (форма 4.1, правила обязательности приходят с сервера по шагу) и один значок
  `OnBehalfTag` («Внесено сотрудником: Иванов, со слов Петрова (телефон)») в журнале, истории документа и подсказке статуса.
  Действия — в карточке КП (`eds/drafts/QuoteView.tsx` после отправки, затем в будущих родных «Исходящих»), во вкладке «Договор»
  (`ContractPanel.tsx`) — те же поля в `client_agreed`, в «Акте» и в будущей «Поставке».
- **Cabinet** показывает статус как обычно, с пометкой «отмечено менеджером по телефону 02.11». Уведомление контрагенту уходит по его
  каналу через CRM (почта или бот, как сейчас `quote.accepted` → бот): «Мы зафиксировали ваше согласие с КП № … (телефон, 02.11). Если это
  ошибка — ответьте на это сообщение». Кнопку «Оспорить» в кабинете отложить (L, после пилота).

**4.3. Доказательство по шагам**

| Шаг | Вложение | Почему |
|---|---|---|
| КП принято / отклонено | желательно (скрин переписки, письмо); обязательны канал, лицо, комментарий | КП — оферта. Акцепт — ответ о принятии (ст. 370 ГК РУз), в том числе действием (оплата и т. п.). Обязательства всё равно оформит письменный договор, поэтому устного согласия с атрибуцией достаточно (Zoho/Salesforce/1С файла не требуют) |
| Договор: редакция согласована | желательно | дальше всё равно подпись и скан |
| Договор подписан | **обязателен скан** (уже есть) или № документа у оператора ЭДО | письменная форма сделки юрлиц; ЭЦП равна собственноручной подписи (ЗРУ-793) |
| Акт подписан | **обязателен скан** (уже есть) | первичный документ |
| Приёмка поставки | **обязателен скан** накладной с подписью получателя (proof of delivery) | спор о поставке решается этим документом |
| Ответ / подтверждение поставщика | желательно файл КП поставщика; № подтверждения — поле | как SAP AB |
| ЭСФ, подпись ЭЦП | **«за него» запрещено** | ЭЦП ставит только владелец ключа (ЗРУ-793; E-IMZO — всегда действие человека, `docs/research/2026-11-01-counterparty-cabinet/README.md:368-369`) |

**4.4. Права**: те же права ролей, что у соседних действий шага, без нового «админского» права. КП — `deal.manage` (менеджер
сделки; директор — по своей роли). Договор — `contract.manage`, акт и поставка — `fulfillment.act`, закупка — `can_manage_supply`.
Контроль постфактум — уведомление директору «КП принято со слов клиента» (лента и колокольчик) и фильтр «Отмечено сотрудником» в
реестрах. Отдельное утверждение директором не вводить: в эталонах его нет.

**4.5. Юридические оговорки (Узбекистан, подтвердить юристу)**
- Сделки юрлиц — в письменной форме; договор можно заключить обменом документами, в том числе электронными. Устное «да» по КП договором
  не является: это коммерческий факт, который запускает подготовку договора. Это совпадает с текущей формулировкой «коммерческий акцепт,
  не ЭЦП» (`lifecycle_accept.py:11-13`).
- Договор у оператора ЭДО, ЭСФ, акты с ЭЦП: система только фиксирует результат (статус, № у оператора, скан). Подпись кликом за сторону
  запрещена (уже так: D2-5, `contracts.py:386-409`).
- Иностранный контрагент без E-IMZO: скан или бумага (`COUNTERPARTY-CABINET.md:91`).

**4.6. Отвергнутые варианты**
1. Дать менеджеру `force-approve` — ломает цепочку (`lifecycle.py:454-519`: ни стадии, ни проекта, ни договора) и смешивает аварийное
   действие администратора с рабочим.
2. Разрешить «договор из SENT» или ручной перевод стадии — это и есть нынешние обходы: без следа «кто принял», КП истекает,
   CLOSED_WON падает.
3. Вход сотрудника в Cabinet «под клиентом» — нарушает инвариант 1, журнал врёт (действие выглядит клиентским).
4. Обязательная «досогласовка» в кабинете — лишний шаг для клиента, которого нет в эталонах; противоречит наблюдению владельца.
5. Обязательное вложение всегда — трение без юридического смысла для КП (HubSpot, Zoho, Odoo его не требуют).
6. Общий сервис или таблица «аттестаций» для всех доменов — нарушает «общих таблиц нет». Общими будут схема в контрактах и
   компонент UI, данные остаются у владельца.
7. Новое право «действовать за клиента» отдельно от права шага — дублирует матрицу ролей SPEC-v3 §4.2.
