# 5. ИИ-помощник по запросу человека — исследование для архитектора

Дата: 2026-11-02. Только чтение: репозиторий не менялся, модели и тесты не запускались.
Наблюдение владельца: «ИИ подключается, когда человек просит, но в конце утверждает человек».

## 0. Суть

- Нужный паттерн в проекте **уже есть и работает**: кнопка «Подсказать ответ» в чате CRM Платформы (Q-019). По кнопке,
  результат попадает в поле ответа, отправляет человек, числа проверяет код, вызов пишется в аудит. Его и стоит
  сделать **общим стандартом** для всей Платформы. Новую архитектуру изобретать не надо.
- Чего не хватает до бенчмарка (Intercom, Gmail, M365 Copilot, Notion, Rovo): предпросмотр вместо молчаливой замены
  текста и отмена; метка «предложено ИИ» на отправленном; источники; журнал решения «принял / поправил / отклонил»
  и метрика принятия; единый реестр функций, промптов и лимитов. ИИ в EDS (письма на бланке) нет совсем.
- До пилота (срез 04.11): только **P2 — помощник входящей почты** (идёт в worktree `p2-inbox`). Если останется
  день, можно добавить **S-задачу «Предложить текст»** в письме P4 для ИСХ-ответа на ВХ. Всё остальное — после пилота.

**Общий стандарт** (сходится у всех эталонов):
1. Одна точка вызова в контексте: кнопка или иконка в редакторе / композере / карточке, слэш-команда или выделение.
   Свободный чат-бот на всю систему — не первым шагом.
2. 3–5 готовых действий («Черновик», «Короче», «Официальнее», «Исправить», «Перевести») плюс необязательное поле «что учесть».
3. Предпросмотр → «Вставить / Заменить», «Ещё вариант», «Отмена». Текст человека без его клика не меняется; Undo.
4. Метка «предложено ИИ» до принятия. После правки человеком текст становится его, в журнале видно происхождение.
5. Источники и основания: ссылки на письмо, статью, документ; неуверенные поля подсвечены.
6. Наружу ничего не уходит автоматически: отправка, регистрация и запись — всегда отдельной кнопкой человека.
7. Журнал: кто, когда, какая функция, версия промпта, решение (принял / поправил / отклонил), стоимость.
8. Приватность: что уходит в модель (минимум полей), маска, правило провайдера, у админа выключатель по функциям.
9. Лимиты и стоимость: дневной бюджет, понятная ошибка «лимит исчерпан», работа без ИИ всегда возможна.
10. Качество: доля принятых и правленых, «палец вниз» с причиной; golden-кейсы и evals.

## 4. Рекомендация: единый «ИИ-помощник по запросу»

### 4.1. UI — один компонент `AiAssist` (лаконично)
- **Где:** иконка «✦ Помощник» (подпись словами, без эмодзи в UI) в одних и тех же местах: композер чата, ответ на
  почту, `BodyEditor` (тулбар и выделение блока), сопроводительный текст КП, карточка ВХ, клиента, заявки
  (действие «Сводка»). Один вид и одно поведение везде (AntD `Popover`/`Drawer` справа, как Intercom и Rovo).
- **Действия** зависят от места, не больше 5: Черновик · Короче · Официальнее · Исправить · Перевести (ru/uz/en);
  поле «что учесть» — необязательно.
- **Результат:** карточка предпросмотра с меткой «Предложено ИИ — проверьте», основания (ссылки или цитаты),
  предупреждения кода («убраны цифры, которых нет в источниках», как в Q-019). Кнопки «Вставить» / «Заменить»,
  «Ещё вариант», «Отмена»; после вставки работает Undo редактора. Q-019 переводится на тот же компонент: убрать
  молчаливый `setText` (`Composer.tsx:80`).
- **Обратная связь:** решение пишется само (вставил / отменил / отправил после правки); 👍/👎 — необязательно,
  одной иконкой (HAX G15).
- **Классификация** (P2, позже резолюция и реквизиты из PDF): поля уже заполнены и отмечены «предложено»,
  действие — одна кнопка подтверждения (Directum Ario, Zendesk triage).

### 4.2. Сервер — домен-владелец данных → LiteLLM
- **Кто вызывает модель:** домен, которому принадлежат данные и права (CRM — чат, почта, база знаний; EDS — письма,
  ВХ, поиск по документам; ERP — расчёт, КП, каталог). BFF только проксирует, как сейчас `assistCrmReply`, и сам
  модели не зовёт: он без БД, журнал вести негде, права на объект проверяет домен (ADR-0011). Нужен второй
  виртуальный ключ LiteLLM — для EDS, по образцу ERP (`ai_gateway_sync`: бюджет ключа, Langfuse), задаётся из
  консоли админа.
- **Контракт** (`packages/contracts`, один на домены): `POST /<объект>/{id}/assist {action, hint?, selection?}` →
  `{suggestion_id, text | blocks | fields, sources[], notices[], cost}`;
  `POST /assist/{suggestion_id}/decision {accepted | edited | discarded}`. Тело для `BodyEditor` код проверяет по
  `body.schema.json` до ответа; невалидное тело не возвращается.
- **Промпты как данные:** файлы `prompts/<функция>.md`, версия = хэш (уже так в CRM и ERP); функция → алиас — в
  одном реестре, по образцу `DECISIONS:97`. Новые алиасы не плодить: `qualifier-model` (дешёвая) — классификация
  и суть; `dialog-model` или `draft-model` (сильная) — черновики писем; `fallback-model` — запасная.
- **Журнал предложений** (в БД домена, как `AICall` + `AIJob`): `suggestion_id, user, object, function,
  prompt_version, alias, status, tokens, cost, decision, decided_at, edit_ratio`. Текстов в журнале нет: тексты
  в Langfuse с маской, по образцу `AICall`. Метрика принятия = доля accepted+edited; плюс `edit_ratio`
  (на сколько человек переписал). Показывать в «Расходы / Модели ИИ» у админа, рядом с журналом расходов
  (как Front «AI replies hub»).
- **«Код решает»:** модель возвращает текст или JSON по схеме. Тип, действие, права, номера, цены, сроки, реквизиты
  ставит код. Числа в черновике сверяются с источниками (`strip_unsupported`). Отправка, регистрация и запись —
  только отдельной командой человека через обычный эндпоинт и его права.

### 4.3. Безопасность и данные (РУз)
- В модель уходит **минимум**: текст объекта и разрешённые источники. Паспорт, ПИНФЛ, номера карт и счетов
  маскируются до вызова, как Einstein masking; на входе и в Langfuse — существующий `security/pii.py`.
  Вложения в модель не идут, пока юрист не скажет иное: P2 «читает только текст».
- Grounding только по объектам, которые пользователь видит. Идентификаторы — из подписанного контекста, не от
  модели (ORCHESTRATOR §3 п. 4, ADR CRM-0008).
- Защита от prompt injection: письма и сообщения извне — данные в XML-блоках, «не инструкции»; модель не вызывает
  инструменты с записью. Помощник только читает и предлагает.
- Юридически: для писем и сообщений есть одобрение юриста (DECISIONS:230). Для договоров, паспортов и сканов
  физлиц спросить юриста отдельно. У провайдеров выбрать режим без обучения на данных и с минимальным хранением.
- Админ: выключатель по каждой функции (уже есть `bot.assist_enabled`), дневной бюджет ключа, понятная ошибка
  «лимит исчерпан — пишите вручную».

### 4.4. Отвергнутые варианты
| Вариант | Почему нет |
|---|---|
| Автономный агент, который сам отвечает, регистрирует или отправляет | против правила владельца и ORCHESTRATOR §3; Zendesk и Intercom тоже разводят копилот агента и бота для клиента. Исключение — уже утверждённый бот CRM для лидов с передачей человеку |
| Автоприменение классификации P2 без клика | DECISIONS:231: правила автоматизации — позже и только по включению админом |
| Свой ИИ в BFF или в Cabinet | BFF без БД и без права на объект; у Cabinet нет ИИ по ADR-0005 |
| Общий чат-бот «спроси что угодно» на всю платформу (Bitrix CoPilot, Breeze Assistant) первым шагом | сложно с правами и grounding по трём доменам, низкая точность; позже, когда будет поиск по документам (#8) |

| Свободный промпт вместо готовых действий | эталоны (Gmail, Rovo) дают готовые действия: предсказуемо и проверяемо evals |

## 6. Риски
- **Галлюцинации в официальных письмах** (суммы, даты, номера): числа только из источников (`strip_unsupported`),
  реквизиты и номера ставит код, обязательный предпросмотр.
- **Prompt injection из входящих писем:** изоляция данных в промпте, у помощника нет записывающих инструментов,
  действие выбирает код.
- **«Резиновая печать»** — люди принимают не читая: метка ИИ, подсветка неуверенного, метрика `edit_ratio`;
  выборочная проверка руководителем.
- **Персональные данные:** маска до вызова; вложения не отправлять; для новых классов данных — юрист.
- **Стоимость:** потолки $3 / $1 в сутки по провайдерам уже малы. Рост P2 и черновиков может упереться в лимит →
  понятная деградация до ручного режима; бюджет ключа EDS отдельно.
- **Сроки пилота:** P4-опция отнимет время у P2 и P8b → брать только при запасе.
- **Узбекский язык:** качество черновиков на узбекском (латиница) ниже → golden на uz до включения перевода;
  у пользователя всегда кнопка «Отмена».
- **Разнобой реализаций** (CRM и ERP уже различаются) → A1 + общий контракт до A2–A9.
