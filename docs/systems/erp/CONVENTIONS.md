# Конвенции кода ERP (бэк-офис), `apps/erp`
Статус: действует · Владелец: лид · Обновлено: 2026-10-23

Ты работаешь над **ERP** ансамбля Платформы: бэк-офис одной компании — заявка → КП → договор →
снабжение → исполнение → финансы. Один главный пользователь — **специалист бэк-офиса** (расчётчик,
закупщик, логист, финансист; «Администратор» = суперпользователь). Клиент сюда не входит — ему служит
Cabinet через портальный API этой же ERP. Продукт нейтрален к отрасли и бренду: имя и логотип — настройки.

Это правила кода ERP; код ссылается на них как `CONVENTIONS.md §N`. Разделы о составе (§4), ролях (§6) и «чего здесь нет»
(§9) описывают код на 2026-10-23. По стратегии 2026-10-23: фронтенд `apps/erp/frontend` заморожен и удаляется на этапе C2,
стадии и коды переходят на словарь SPEC-v3 на этапе C3, события — через `rt_bus` (ADR-0014), согласования — в EDS (ADR-0015).
Запуск и команды — [`README.md`](README.md); runbook'и — [`docs/runbooks/erp/`](../../runbooks/erp/README.md).

## 2. Инварианты ансамбля применительно к ERP (нарушение = PR не принимается)

1. **Один главный пользователь.** В ERP входят только сотрудники (SSO из CRM или пароль). Клиентских аккаунтов нет; клиент — контакт контрагента в `parties` с сессией портала, а не `User`.
2. **Общих таблиц с CRM нет.** База `erp` своя. Связь — внешние идентификаторы `crm_client_id`, `crm_lead_id`, `crm_contact_id`, `crm_user_id` (CONTRACTS §0); идемпотентность по ним и по `Idempotency-Key`.
3. **Контракт раньше кода.** Любой эндпоинт `portal`/`integration`, событие, инструмент MCP, claim токена — сначала `packages/contracts` (есть с M0-INF-02: `openapi/erp-*.yaml`, `events/` + `bus/subscriptions.yaml`, `mcp-tools.json`, `docs/architecture/sso-token.md`), потом код; клиенты пересобираются в том же PR (`make contracts`).
4. **Код решает, модель предлагает.** Стадии, права, цены, доступ — детерминированно и с тестами. Идентификаторы компании никогда не приходят от модели: только из подписанного `X-Agent-Context`.
5. **Клиент видит только опубликованный слой** каталога и проекцию сделки: без поставщиков, себестоимости, маржи. Каждый портальный эндпоинт — негативный тест «чужая компания → 404», «внутренний слой не отдаётся».
6. **Секреты только в окружении.** `gitleaks` в pre-commit корня. Модели — через LiteLLM по алиасам; импорт SDK провайдера в коде ERP запрещён (M1-ERP-06).
7. **B2B — только история.** Код B2B скопирован в `apps/erp` (M1-ERP-01) и дальше живёт здесь; папки `legacy/b2b` нет (удалена в M2-INF-01), исходное состояние — тег `b2b-final`; `git log --follow` сохраняет историю файлов.
8. **Документация в том же PR:** OpenAPI в `packages/contracts`, ADR, runbook; статус и хвосты — в описании PR (`docs/PROGRESS.md` ведёт лид, ORCHESTRATOR §4.1).
9. **DoD с UI = сценарий глазами** (скриншот/GIF в PR, 1440 и 390 px), не «тесты зелёные».
10. **Benchmark-first** для продуктовых задач: как у Odoo / ERPNext / SAP B1 — именованный паттерн в описании PR, потом код.

```
backend/   Python 3.12 · Django 6 · DRF · Daphne (ASGI) · Channels · Celery (+ Beat) · PostgreSQL 17, база `erp` ·
           Redis: `redis-broker` (Celery БД 1, Channels БД 2) и `redis-cache` (кэш БД 0), S0-2 · RustFS (S3), бакет `erp` · WeasyPrint (PDF off-thread) ·
           pandas + openpyxl (Excel) · LiteLLM (алиасы intake-model, match-model, draft-model, enrich-model) · Langfuse
frontend/  React 18 · TypeScript · Vite · Tailwind CSS 4 · shadcn/ui · React Query · Zustand · i18next (ru/en, uz позже) ·
           openapi-typescript (типы из packages/contracts) · Vitest + Testing Library
```

Версии зафиксированы в `backend/pyproject.toml` и `frontend/package.json` (на момент копирования M1-ERP-01 — как в B2B, тег `b2b-final`); обновления — отдельными PR с `make check-erp`.
Общие сервисы (Postgres, Redis, LiteLLM, Langfuse, RustFS, Caddy) — из `infra/compose` (есть; сервисы `erp-*` добавлены в M1-ERP-01),
ERP сам их не описывает. Токены дизайна — из `packages/ui-tokens` (есть: `dist/shadcn.css`); подключение в `frontend/src/index.css` — при перестройке UI (M1-ERP-04).
Хранилище файлов — RustFS через S3-бэкенд Django (S0-1): бакеты `erp-private` (по умолчанию), `erp-public`, `erp-temp` (объекты старше суток удаляются правилом, S0-9); тома `erp_media` нет. У ERP свой ключ S3 (`S3_ERP_*` → `MINIO_ACCESS_KEY/SECRET_KEY`), доступный только бакетам `erp-*` (S0-9). Адрес RustFS наружу не отдаётся: `.url` любого хранилища — путь под `/media/`, приватные файлы — только потоком через аутентифицированное представление (`core/file_streaming.py`), публичные — `/media/*` (белый список в `core/urls.py`; логотип профиля документов `companies/<id>/doc-profile/logo` публичный, **документы товаров** `products/<id>/docs/*` — приватные, в `erp-private`, скачиваются через `catalog/products/{id}/download-document/{doc_id}/`). Файлы S3 отдаются порциями (`ObjectStream`, `core/file_streaming.py`): целиком в память не грузятся — новую выдачу файла делай через `stream_file_field` / `storage_file_response`, не через `FileResponse(field.open())`. Голого `default_storage` в коде нет (тест `test_no_bare_default_storage_in_application_code`): staging ИИ-импорта — `get_temp_storage()` (backend и воркер Celery файловой системы не делят), а `STORAGES["default"]` при заданном `MINIO_ENDPOINT` — тоже `erp-private` (`core/default_storage.py`). Вне `DJANGO_DEBUG` без `MINIO_ENDPOINT` и ключей ERP не стартует; в DEBUG и тестах — файловая система (`MEDIA_ROOT`).

## 5. Конвенции кода (из B2B; то, что остаётся верным)

**Python**
- Бизнес-логика **только в `<app>/services/`** как обычные функции: переходы FSM, валидации, побочные эффекты, письма, Celery-диспетчи. `views` и `admin.py` — тонкие обёртки: авторизовать → валидировать → вызвать одну функцию сервиса → вернуть. Одна и та же логика в admin-action и DRF-эндпоинте — запрещена; оба зовут сервис.
- **События — только через шину `rt_bus` из сервисного слоя, в транзакции изменения** (ORCHESTRATOR §3 п. 14, ADR-0014): `events.publish_*` внутри `transaction.atomic()` сервиса; ни сигналов Django, ни вебхуков, ни `except Exception` вокруг публикации; откат — события нет, ошибка публикации — откат изменения (подробно — ниже, «События ERP → CRM»).
- **Словари сеются миграциями** (`RunPython` + `get_or_create`, reverse no-op): стадии, статусы, виды документов, роли, образцы шаблонов. После `migrate` на пустой базе каждый код, на который ссылаются сервисы, уже существует. В горячих путях — `Model.objects.get(code=...)`, не `get_or_create`. `loaddata` и management-команды — только для dev/demo.
- **Параллельные миграции (владелец 2026-10-28, ORCHESTRATOR §4.1).** Номер в имени файла Django (`0011_…`) не бронируется и не перенумеровывается ради очереди: два PR с миграциями одного приложения от одного листа дают конфликт листьев, его громко ловит `makemigrations --check` (задание CI `erp-schema` на PR и на push в `main`, локально `apps/erp/scripts/test_backend_local.sh --migration-check`). Тогда в своей ветке после merge `origin/main` — `python manage.py makemigrations --merge <app>` или перевести `dependencies` своей миграции на новый лист (переименовать файл в следующий номер — по желанию). Уже применённые на проде миграции не переименовываются.
- **Нет фейковых данных:** каждый эндпоинт читает реальную БД; никаких статических массивов и заглушек в продуктовом коде.
- **Нет хардкода:** URL, ключи, идентификаторы — из окружения; бизнес-константы — из БД или настроек; роли, стадии, статусы сравниваются по `code`, никогда по переведённому `name`.
- Ошибки API — `{"detail": "<CODE>"}` (DRF-native, CONTRACTS §0); фронтенд сравнивает код по значению. Держит тест вида `core/tests/test_error_shape.py` B2B.
- Бизнес-дата — `timezone.localdate()`, никогда `timezone.now().date()` (`TIME_ZONE=Asia/Tashkent`, `USE_TZ=True`).
  `DateTimeField` на печать (документы, письма) — только через местное время (`crm.services.document_blocks.format_document_date` / `timezone.localtime`): `strftime` на UTC-значении даёт вчерашнюю дату после 19:00 UTC; `DateField` часового пояса не имеет и печатается как есть (FIX-54).
- Списки — `select_related` / `prefetch_related`, без N+1; дашборды — `aggregate()` с условными `Count`, не `.count()` в цикле; пагинация у всех списков.
- Запрос не блокирует ASGI: PDF, импорт, ИИ — в Celery; публичные и тяжёлые ответы — 202 + `Retry-After`. Celery-задачи — с `time_limit`/`soft_time_limit`, ретраями и backoff (исключение — ИИ-задача, одна попытка: платный вызов).
- Загрузки — через валидаторы `core` (размер, тип, расширение, magic-bytes).
- **Вход в портал (FIX-14).** `MagicLinkToken.token_hash` и `PortalSession.token_hash` — SHA-256 токена (`portal/services/tokens.py`), сырой токен живёт только в cookie или в письме клиенту; в логи — не больше префикса из 6 символов (`core.logging.RedactPortalTokenFilter` прячет `/auth/magic/<token>` в путях запросов, `notifications.emails._redact_secrets` — в `EmailLog`, и `/auth/magic#token=<token>` тоже). Погашение — `select_for_update` + `used_at` + сессия в одной транзакции. Письмо входа — шаблон `portal_magic_link` через `send_templated_email` (→ `EmailLog`); не больше `PORTAL_MAGIC_LINK_MAX_PER_HOUR` (5) запросов в час на адрес, считаются и неизвестные адреса (429 не должен выдавать наличие контакта). Запрос ссылки гасит только прежние ссылки входа (`purpose=login`), приглашение из ERP (`purpose=invite`, 24 ч) остаётся. Рабочая ссылка входа клиента не попадает в ответы API, журнал и в CRM (handoff отдаёт `CABINET_URL` без токена). Ссылка в письмах входа и приглашения — `{CABINET_URL}/auth/magic#token=<токен>` (FIX-21, `build_login_url`): токен во фрагменте, в пути и query его нет; Cabinet меняет его на сессию через `POST /auth/magic {token}`, `GET /auth/magic/{token}` снят в контракте 0.3.0 (FIX-25): маршрута нет, 404 (обмен: 410 `MAGIC_LINK_EXPIRED`, 403 `FORBIDDEN` для архивной компании; лишнее поле тела — 422). Telegram — только по подписанному `telegram_user_id`; контакты архивных компаний (`Company.is_active=False`) не входят ни одним каналом (403 `FORBIDDEN`); адрес, общий у активных контактов разных компаний, письма не получает.
- **Почта — один отправитель (W18A-P1, CONTRACTS §9.9).** ERP SMTP не знает: любое письмо — `notifications.emails.send_templated_email` (рендер своим шаблоном → строка `EmailLog` `QUEUED` с ключом `erp:email_log:<id>` → Django `EmailBackend` `notifications.bus_backend.BusEmailBackend`) — публикует `uz.railtech.erp.mail.requested.v1` в той же транзакции; `send_mail` идёт тем же путём. Тело — шифртекстом ключа пары `erp → crm` (`notifications/mail_bus.py`), вложение — в `erp-temp` и подписанной ссылкой на 24 ч. Итог (`crm.mail.sent|failed`) обновляет `EmailLog` и для КП — журнал и `send_report`. Настроек `EMAIL_HOST*`, `EMAIL_CHANNELS`, `EMAIL_<канал>_*` нет; паузу почты держит выключатель «Почта» CRM. Новое письмо — шаблон и вызов `send_templated_email(..., ref=(вид, id))`, не своё SMTP-соединение.

**Тесты**
- Backend: pytest + pytest-django, маркеры `unit` / `integration` / `slow`; CI гоняет `--create-db` **с миграциями** (словари сеются ими — база без них другая). Порог покрытия из B2B — 70 % (`--cov-fail-under`). Любой баг сначала воспроизводится тестом.
- Как идёт прогон (W14-S1; `apps/erp/scripts/test_backend_local.sh`, он же CI): pytest-xdist, по умолчанию `-n auto --maxprocesses=6` (`ERP_TEST_MAXPROCS`); воркер `gwN` — своя база Postgres `test_erp_gwN` и свои базы Redis `3·N + 0..2` (`cache.clear()` — это `FLUSHDB`, соседа он не трогает), свой `MEDIA_ROOT` в `/tmp` контейнера (`backend/core/settings_pytest.py`; `core.settings` — прод, его тесты не меняют). Хешер паролей в тестах — MD5 (PBKDF2 стоил секунды на каждом `create_user`); тест, которому нужен конкретный алгоритм, ставит его через `override_settings(PASSWORD_HASHERS=…)`. Базы воркеров клонируются из шаблона `rt_tpl_<хеш>`: миграции (`*/migrations/*`, `rt_bus`, `core/seeds`) гоняются один раз на их набор и заново сами при смене хеша или пересоздании контейнера Postgres. `--reuse-db` между прогонами не используется намеренно: транзакционные тесты (`django_db(transaction=True)`) сбрасывают таблицы, и переиспользованная база теряла бы словари, посеянные миграциями; клон шаблона дешевле и всегда чист. Последовательно (одна база `test_erp`, один процесс): `args="-n0"` или `args="-p no:xdist"`; один тест (`::`) или `-k` скрипт сам гоняет последовательно. Пересобрать образ и шаблон принудительно: `ERP_TEST_REBUILD=1`. Параметры `parametrize` не должны зависеть от случайных значений (`uuid4()` в списке без `pytest.param(..., id=...)`): воркеры xdist собирают тесты независимо, расхождение имён ломает прогон.
- Обязательные классы тестов: матрица прав ролей на каждом эндпоинте мутации (M1-ERP-05); параметризованные таблицы переходов FSM и расчётов; негативные тесты portal (чужая компания 404, подделанный `initData` 401, просроченный magic-link 410), integration (без токена 401, повторный handoff без дубля), MCP (без контекста 401, чужой клиент — пусто); тест на отсутствие N+1 в карточке сделки.
- Frontend: Vitest + Testing Library + jsdom, рендер через провайдеры с настоящим `ru.json`.
- Контрактные тесты по OpenAPI из `packages/contracts`; расхождение схемы и сгенерированного — красный CI.
- **Каждая операция `/api/v1` — с явной схемой запроса и ответа, выгрузка без предупреждений drf-spectacular (D2-0, B-011).** Вьюха, которая читает `request.data` сама или собирает ответ словарём, объявляет `extend_schema(request=…, responses=…)` (сериализатор только для описания допустим: поведение он не меняет); отказы `{"detail": КОД}` описываются ответом 4xx с кодами в `description` — тело `ErrorDetail`/`BadRequest` подставляет `core/openapi.py`, особую форму (`missing_blocks`) задаёт сама операция. `manage.py openapi_v1_check` (шаг `make -C apps/erp openapi` и `openapi-check`) и тест `core/tests/test_openapi_v1_clean.py` падают на любом предупреждении по `/api/v1/`; живые ответы операций, которые зовёт BFF Платформы, сверяет с выгрузкой `core/tests/test_openapi_*_conformance.py` (схема из кода, `core/tests/openapi_internal.py`). Новая операция ERP для BFF — тест сверки в том же PR.

### Каталог в два слоя (M1-ERP-07 — сделано)

- **Внутренний слой** — `Product` + `SupplierOffer` (поставщики, закупочные цены, артикулы поставщиков, остатки

  `CatalogItem` контракта портала **белым списком** (`CATALOG_ITEM_KEYS`), `project_many()` — пачкой,

  (`useHasCompanyPermission`, `buildNavigation`, `buildSettingsSections`).
- «Администратор» в CRM = суперпользователь ERP (все права без ролей); инвариант «≥ 1 администратор» держит CRM, у своей компании ERP нет «Администратора компании» и never-orphan. Одному человеку — несколько ролей, очереди складываются.
- Источник истины по людям и доступам — CRM (ADR-0003): пользователь создаётся провижинингом (`POST /api/integration/v1/users/provision`), вход — SSO-токеном на 60 с с одноразовым `jti` (CONTRACTS §6), отзыв доступа в CRM отзывает сессии ERP. Новый код выпуска токена — через `accounts.services.tokens.refresh_for(user)`. Провижининг принимает только коды каталога (`Permission`; чужой код → 422), создаёт членство с должностью `MEMBER`. **Системные роли из CRM (FIX-63, `role_codes`)**: необязательное поле тела — коды `BackofficeRoleCode` (чужой код → 422); `integration.services.provision._sync_system_roles` добавляет системные роли компании и помечает их в `CompanyMember.crm_granted_roles` («выдана из CRM»), следующий провижининг и отзыв доступа снимают только помеченные; поля нет — системные роли не трогаются (старый CRM); роль, назначенная в «Команде» вручную, не помечается и CRM её не снимает; для `admin` помеченные роли снимаются. `/me.capabilities.crm_access` — есть `CrmUserMapping`: только такому сотруднику показана кнопка «В CRM». `CookieTokenRefreshView` не продлевает refresh тому, кто больше не сотрудник (403 `STAFF_ONLY`) и чей доступ отозван (401).
- Права проверяются гейтом эндпоинта и **в сервисах** (`member_has_permission`), фронт только прячет кнопки. Никаких «OWNER»/«Sales Manager» в коде — только коды прав и коды ролей.
- **Своя компания** (компания-владелец, единственный продавец — BUSINESS §3.3) — одна точка истины `core.tenant.own_company()` / `own_company_id()` (с M1-ERP-02 волна 3): настройка `OWN_COMPANY_ID` (окружение; необязательна, нужна, только если компаний-продавцов с участниками больше одной; проброс в compose — Infra, M5-INF-01), иначе — единственная активная компания-продавец с активными участниками (dev, тесты, свежий стенд; в тестах фикстура создаёт одну такую компанию), несколько без настройки — `ImproperlyConfigured`, ни одной — `None` (действует только администратор; он создаёт её мастером первого запуска — `GET /api/v1/setup/status/`, `POST /api/v1/setup/company/`, `OwnCompanySetupScreen`, FIX-65). Сид ролей миграции `accounts/0003` при `OWN_COMPANY_ID` на компанию, которой в базе нет (чистая база при сбросе прода), её пропускает с записью в лог (не `IntegrityError`); роли такой компании появятся после мастера первого запуска (`ensure_default_company_roles`, T2 волны 11b). Сотрудник бэк-офиса = активный участник своей компании (`accounts.services.permissions.is_seller`, `sees_all_deals`, `primary_seller_company_id`); видит все сделки и документы, действует по правам роли в своей компании. Продавец КП / счёта без КП / получатели уведомлений о заявке — тоже своя компания.

**`erp-mcp` (FIX-36, S-12).** Официальный SDK `mcp` (та же версия, что у CRM) в отдельном процессе `python -m integration.mcp` (compose-сервис `erp-mcp`, порт 8104 только внутри сети; `/mcp` снаружи — 404, FIX-03). Новый инструмент = строка в `mcp-tools.json` (контракт раньше кода) + обработчик в `HANDLERS`; расхождение роняет старт и тест. Ошибка инструмента отдаётся кодом (`TOOL_NOT_AVAILABLE_IN_MODE`, `TOOL_EXECUTION_ERROR`, `INTERNAL_ERROR`), текст чужого исключения модели не уходит. Обработчики — синхронный ORM через `sync_to_async`; тесты — `integration/tests/mcp_support.py` (приложение SDK в процессе теста + клиент `mcp.Client`).

Правила: эндпоинты — kebab-case, множественное число; `Idempotency-Key` на всех POST интеграции (ключ хранится 7 дней);
деньги — строка с двумя знаками + ISO-4217; даты — ISO-8601 с зоной; версия — префикс `v1`, несовместимое изменение — новый префикс.
Любое изменение здесь начинается с `packages/contracts` и PR с обеих сторон в одной вехе.

**Договор и акт проекта (D2-5, SPEC-v3 §2.4).** Договор подписывают вне платформы (оператор ЭДО или бумага): подписи кликом нет. Переходы договора — одна таблица `TRANSITIONS` в `crm/services/contract_flow.py` (`send_to_client`, `client_agreed`, `reject` с причиной, `revise`, `mark_issued`, `attach_scan` → «Подписан (скан)»); недопустимый переход — `409` с кодом `contract_transition_not_allowed`, а не молчаливый отказ. Акт — `crm/services/act_flow.py` (`attach_act_scan`, `record_act_return`; выпуск и повторный выпуск — `billing.py`). Право проверяется в сервисе (`contract.manage`, `contract.sign`, `fulfillment.act`; `RoleGatedViewMixin` — fail-closed), скан — `core/validators.validate_scan_upload` (PDF, jpg, png, webp по сигнатуре и расширению, до 20 МБ). Каждый переход — в транзакции: блокировка строки, журнал `ActivityLog` с `event_code`, событие шины `contract.status_changed` / `act.accepted` / `act.returned` (схемы и совместимость — `packages/contracts/events/erp`). Проект как чтение — `crm/services/projects.py` (`GET /crm/projects/`): шаг, документы, «действия сейчас» с учётом прав, «Выполнено», когда акт подписан и счета оплачены (одна запись `project.done`). Подпись продавца кликом (`sign-manager/`) закрыта: `409 CONTRACT_SIGN_VIA_SCAN`; согласие клиента в портале (`sign_contract_by_client`) даёт только «Согласован клиентом» (`PENDING_MANAGER`), а не «Подписан» — «Подписан» ставит один путь, скан после «Выставлен у оператора»; `revise` сбрасывает все подписи; `upload-signed/` на «Подписан» и «Отменён» — `409 CONTRACT_SCAN_LOCKED`, тип проверяется как у скана, загрузка пишется в журнал. Запись `project.done` пишет `projects.log_project_done_once` (под блокировкой сделки) из трёх мест: скан акта, приёмка акта заказчиком в портале и оплата счёта. Свои PDF (счёт, акт, договор) никогда не называются «счёт-фактурой».
