# Оферта и политика Кабинета — акцепт при входе (ДВ-5)
Статус: действует · Владелец: лид ERP · Обновлено: 2026-11-23 (ДВ-5) · Основание: план 2026-11-12 §4.3 (ДВ-5), решение владельца 2026-11-23 (тексты — по сайту компании и закону, на трёх языках)

Юридические ворота перед приглашением клиентов и партнёров: контакт кабинета принимает действующие условия использования (оферта, вид `terms`) и политику обработки персональных данных (вид `privacy`) при первом входе и при каждой новой редакции. Без этого кабинет не открывается.

## Модель (`portal/models_legal.py`, миграция `portal 0018`)

- `LegalEdition` — редакция одного документа: вид, название (`2026-11-23`), текст `{title, lead, sections[{title, body}]}` с тремя языками в каждом поле, `published_at`/`published_by`, `retired_at`. Опубликованная редакция не правится: новый текст — новая редакция. Действующая — опубликованная и не снятая; такая у каждого вида **одна**, черновик — тоже один (частичные уникальные ограничения).
- `LegalAcceptance` — «контакт принял эту редакцию»: контакт, организация, редакция, время, язык показанного текста, способ входа, IP и устройство. Один акцепт на пару контакт и редакция.
- Миграция кладёт первые редакции из `portal/legal_seed/cabinet-legal-2026-11-23.json` **черновиками**: пока ничего не опубликовано, кабинет открыт как раньше.
- Текст — простой текст: абзацы через перевод строки, пункты списка с «— ». Подстановки `{{company.name|inn|address|support_email|phone}}` заполняются при показе из своей компании ERP и `SystemSetting.support_email` (`portal/services/legal.py:company_values`); чего нет — «—».

## Правило входа

1. `PortalAuthentication` одним подзапросом считает `request.portal_legal_pending` — у контакта есть действующая редакция без его акцепта.
2. `IsPortalAuthenticated` (его проходит любая вьюха с сессией) при `portal_legal_pending` отвечает 403 `LEGAL_ACCEPTANCE_REQUIRED`, кроме вьюх с `legal_exempt = True`: профиль `GET /me`, `GET /legal`, `POST /legal/accept`. Выход (`/auth/logout`) работает всегда. Новый эндпоинт кабинета закрыт по умолчанию; тест `test_all_cabinet_entry_points_are_gated_by_construction` не даёт добавить вьюху с сессией мимо этого места.
3. Вход из Telegram и по ссылке из письма — та же сессия и тот же гейт; `Me.legal_pending` говорит Cabinet показать экран принятия вместо раздела (адрес остаётся прежним).
4. `POST /legal/accept {edition_ids, language}` принимает только ровно действующие редакции; список разошёлся (вышла новая) — 409 `LEGAL_EDITION_CHANGED`. Повтор безопасен. Запись в журнал: `portal.legal.accepted` (организация и контакт — в ленту контрагента).
5. `GET /legal/policy` — публичный текст политики для ссылки на экране входа (`null`, пока не опубликована).

## Публикация и «Настройки»

Страница «Настройки · Компания · Оферта и политика» (`company.settings`, правят директор и администратор): `GET/POST /api/v1/settings/legal-editions/`, `GET/PATCH/DELETE …/{id}/`, `POST …/{id}/publish/`, журнал `GET /api/v1/settings/legal-acceptances/` — всё под правом ERP `settings.edit`. Публикация снимает прежнюю действующую редакцию вида и пишет `admin.portal_legal.published` в «Историю». Все контакты примут новую редакцию при следующем входе; открытые сессии получают 403 `LEGAL_ACCEPTANCE_REQUIRED` на ближайшем запросе, Cabinet перечитывает профиль и показывает экран принятия.

## Что не входит

Принятие сотрудниками, баннер cookie и страницы сайта; публичные страницы КП и документов по ссылке (контакт там не идентифицирован); копия принятой редакции письмом и кнопка отзыва согласия — хвосты в [`QUESTIONS.md`](../../QUESTIONS.md) (Q-DV5-1). Ответственность за вычитку текстов — владелец с юристом: тексты загружены черновиками и без публикации ничего не меняют.
