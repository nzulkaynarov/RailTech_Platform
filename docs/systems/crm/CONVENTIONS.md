# Конвенции кода RailTech CRM, `apps/crm`
Статус: действует · Владелец: лид · Обновлено: 2026-10-23

Ты работаешь над **RailTech CRM** — доменом фронт-офиса ансамбля: лиды, клиенты и контакты, каналы и переписка, база
знаний, клиентский Telegram-бот (диалоговый агент + асинхронный квалификатор, сервисный режим через `erp-mcp`), консоль
администратора; до этапа F — вход, роли и общие настройки (идентичность v1). Интерфейс сотрудников — Платформа; фронтенд
`apps/crm/frontend` заморожен и удаляется на этапе C2 (стратегия 2026-10-23 §7). Это правила кода CRM; код ссылается на них
как `CONVENTIONS.md §N`, нумерация разделов сохранена.

Среда: локальная среда полная — Docker, стенд и одноразовые контейнеры для integration есть (правило владельца —
раздел «Среда разработки, тесты и CI» `CLAUDE.md` корня); CI — финальная проверка, не инструмент разработки.

## 2. Правила работы (не нарушаются)

1. **Этапы и гейты.** Работай по задаче из runbook'а текущей волны (`docs/ORCHESTRATOR.md` §6). Не начинай следующий этап, пока владелец не отметил гейт текущего в `docs/PROGRESS.md`. Фазы 0–10 CRM закрыты (история — `docs/history/crm/PLAN.md`).
2. **Отклонения от SPEC — только через предложение.** Если считаешь, что SPEC ошибочен или устарел: остановись, опиши проблему, предложи 1–2 варианта с последствиями, дождись решения, затем обнови SPEC и напиши/обнови ADR. Никогда не реализуй «свою версию» молча.
3. **Никаких галлюцинаций API.** Перед использованием библиотеки проверь её актуальную документацию (WebFetch/WebSearch) или установленную версию (`uv run python -c "import x; print(x.__version__)"`, `pnpm ls`). Не выдумывай методы, параметры, названия моделей. Идентификаторы моделей — только из LiteLLM: значения по умолчанию в `infra/litellm.models.yaml`, текущие — в его БД (меняет админ в CRM, ADR-0020); код знает только алиасы.
4. **Код принимает решения, модель предлагает** (`SPEC §1.3`). Стадия, score, эскалация, доступ к данным — детерминированная логика с тестами. Если ловишь себя на том, что просишь LLM решить это, — остановись.
5. **Идентификаторы клиента никогда не приходят от модели** (`SPEC §1.5`, `§7.1`). Любой инструмент агента получает контекст из подписанного заголовка.
6. **Секреты.** Ничего похожего на ключ/токен/пароль в код, тесты, фикстуры, доки, коммиты. Только `.env.example` с плейсхолдерами. Перед коммитом — `gitleaks` (в pre-commit).
7. **Тесты — часть задачи, не отдельный шаг.** Доменная логика пишется тест-first (параметризованные таблицы кейсов). Любой баг сначала воспроизводится тестом.
8. **Документация обновляется в том же PR**, что и код, и только в `docs/` (ORCHESTRATOR §3 п. 17): `docs/systems/crm/` (запуск, SPEC), runbooks, ADR, OpenAPI (экспорт); статус — в описании PR (`docs/PROGRESS.md` ведёт лид).
9. **Один PR — одна задача.** Ветка — как в задаче (ORCHESTRATOR §4). Conventional Commits на русском с ID задачи. Шаблон PR заполняется полностью.
10. **Маленькие шаги, частые проверки.** После каждого значимого изменения — `make check` (ruff, mypy, eslint, tsc, unit). Не накапливай непроверенный код.
11. **Не изобретай.** Готовые решения из `SPEC §2` (Refine, Casbin, Procrastinate, docling, FastMCP, LiteLLM, Langfuse) используются как задумано их авторами. Кастомный код — только домен и экраны. Если тянет написать свою очередь/RBAC/парсер — это сигнал перечитать SPEC.
12. **Говори, когда не уверен.** Лучше задать один вопрос до реализации, чем переделывать задачу. Вопросы фиксируй в `docs/QUESTIONS.md` (только открытые), чтобы человек мог ответить пакетом; ответы переноси в `docs/DECISIONS.md`.

## 3. Стек и команды (кратко; полностью — `SPEC §2`, `§4`)

```
backend/   Python 3.12 · uv · FastAPI · SQLAlchemy 2 async · Alembic · aiogram 3 · LangGraph · FastMCP · Procrastinate · pycasbin · structlog
frontend/  React 18 · TypeScript · Vite · Refine · Ant Design · orval (клиент из OpenAPI) · Vitest · Playwright
infra/     Docker Compose (base/dev/prod) · Caddy · LiteLLM · Langfuse · RustFS (S3) · PostgreSQL 17 + pgvector
```

| Команда (из `apps/crm`) | Что делает |
|---|---|
| `make install` | зависимости бэкенда и фронтенда (в новом worktree — первым шагом) |
| `make check` (= `make check-crm` из корня) | ruff + mypy + eslint + tsc + unit-тесты |
| `make test` | unit |
| `scripts/test_int_local.sh` (`ITEST_NS=<имя>`) | integration на одноразовых Postgres/RustFS |
| `make test-e2e` | e2e |
| `make eval` / `make promptfoo` | evals (платно — только с «да» владельца, §6.5) |
| `make openapi` | экспорт OpenAPI + генерация клиента |
| `make migration m="..."` | файл миграции Alembic |
| `make up` из корня | стенд ансамбля (для проверки глазами) |

Один тест: `cd apps/crm/backend && uv run pytest tests/<файл>.py -x -q`; фронтенд — `cd apps/crm/frontend && pnpm test -- <шаблон>`. Unit-тесты не требуют Postgres (домен изолирован от БД; репозитории тестируются в integration).

**Шаблоны писем и образы (W13C-F3, C2A-G-3).** `backend/templates/email/` нужен каждому сервису CRM, который пишет письма. Прод-образ (`target: prod`, и `backup` поверх него) копирует каталог (`COPY templates ./templates`); dev-образ (`target: dev`) не содержит ни кода, ни шаблонов, поэтому `infra/compose/dev.yml` монтирует `apps/crm/backend/templates:/app/templates:ro` в `crm-migrate`, `crm-api`, `crm-worker` и MCP-сервисы (общий якорь `crm-src`) — как `prompts/`. Новый сервис CRM на target `dev`, который рендерит письма, получает тот же том. Нет файла шаблона → `MailService.send` отвечает 500 с кодом `mail_template_missing` без путей (`TemplateMissingError` в лог). Страховка в unit-тестах (`tests/unit/test_mail_templates.py`): все шаблоны, на которые ссылается код, есть и рендерятся; `Dockerfile` копирует `templates`, `.dockerignore` их не исключает; `dev.yml` монтирует том. Ручная проверка собранного образа (скрипты CI не трогают): `docker build --target prod --build-context rtbus=packages/rt-bus --build-context contracts=packages/contracts -t rt-crm-check apps/crm/backend && docker run --rm rt-crm-check python -c "from app.services import mail_templates as m; print(m.render('invite', 'ru', full_name='x', email='x', temporary_password='x', crm_url='x', company='x').subject)"`.

## 4. Соглашения кода

**Python**
- Слои: `api` → `services` → `repositories`/`integrations`; `domain` — чистые функции без I/O; `agents` ходят в данные только через MCP.
- Типы везде; `mypy --strict` для `domain/`, `security/`, `schemas/`. Pydantic v2 для всех DTO и настроек.
- Исключения домена — свои классы в `domain/errors.py`; API маппит их в HTTP через один handler.
- Логи — `structlog`, только kwargs, без f-строк; `lead_id`, `request_id` в контексте. Никаких `print`.
- Все мутации через REST и callback-кнопку — через `security/audit.py`.
- Миграции: одна миграция на PR, обратимая (`downgrade` реализован), имена `YYYYMMDD_HHMM_slug`.
- Промпты — только в `backend/prompts/*.md`, подстановка через явный шаблон; пользовательский текст и фрагменты KB — в отдельных XML-блоках.

**TypeScript**
- Строгий `tsconfig`. Типы API — только сгенерированные (`src/api/`), ручные дубли запрещены.
- Права на фронте — только скрытие/блокировка UI по `GET /me/permissions`; истина на бэке.
- Компоненты без бизнес-логики; логика — в хуках/сервисах.

**События (шина `rt_bus`)**
- Событие CRM наружу — только `app/bus/events.py` из сервисного слоя в той же транзакции, что и изменение; не из API-роутера, не из репозитория, не после коммита.
- Нужен новый тип — сначала схема и пример в `packages/contracts/events/` (контракт раньше кода), затем вызов из сервиса.
- Тест на каждую публикацию: откат — события нет, ошибка публикации — изменение откатывается (`tests/integration/test_bus_publish.py`).
- В `lead.stage_changed.reason` — только код из справочника `app/bus/reasons.py`; свободный текст сотрудника и модели в события не попадает.

**Общее**
- Файлы ≤ 400 строк — иначе дели. Функции ≤ 50 строк.
- Нет закомментированного кода, нет `TODO` без ссылки на issue.
- Тексты для пользователей бота/CRM — через `settings.texts` или i18n, не хардкод.

## 5. ADR

Формат MADR, файл `docs/adr/NNNN-slug.md` из `0000-template.md`. Статусы: proposed → accepted / rejected / superseded by NNNN.

Когда писать: выбор библиотеки/сервиса; схема данных, влияющая на несколько модулей; протокол/контракт (MCP-контекст, SSE); политика безопасности; любое отклонение от SPEC. Начальный список — `SPEC §16`. Решение в ADR сначала `proposed`; человек меняет на `accepted` (или ты — после его явного «принято» в обсуждении, с указанием даты).

## 6. Тесты и проверка

Локальная среда полная (правило владельца — `CLAUDE.md` корня). Поэтому:

1. **Разделяй тесты маркерами:** `unit` (по умолчанию, без внешних сервисов), `integration` (Postgres/RustFS — одноразовые контейнеры `scripts/test_int_local.sh`, в CI — services), `e2e`, `live` (реальные модели; CI не запускает), `eval`.
2. **Мокай границы, не середину:** LiteLLM — через записанные ответы (`tests/fixtures/llm/*.json`, фикстура `llm_replay`); Telegram — через фейковый `Bot` aiogram; S3 (RustFS) — через `moto`-подобный стаб или integration.
3. **Для каждой задачи, которую может проверить только человек**, добавляй шаг в чек-лист приёмки в PR (раздел «Проверить на dev») с точными действиями и ожидаемым результатом.
4. **CI — финальная проверка, не инструмент.** Всё, что проверяет CI, проверяется локально (`make ci-local` по затронутым заданиям); после открытия PR — остановиться и доложить, CI не опрашивать (`CLAUDE.md` корня).
5. **Платные вызовы моделей — только с явного согласия владельца.** `make eval`, `make eval-quick`, `make promptfoo`, `make load-test`, метка `run-evals` на PR тратят деньги владельца: перед запуском назови число вызовов и стоимость и дождись «да» на конкретный прогон. Предпочитай `make eval-quick` или один кейс (`EVAL_CASES=<id>`). Юнит/integration/e2e — бесплатны (подставные модели). Integration-тесты делают `TRUNCATE` — только на одноразовых контейнерах, не на БД dev-стенда.
6. **Скрипты для человека** (`scripts/*.sh|py`) должны быть идемпотентными, с `--help`, понятными сообщениями об ошибках и шагом «что делать дальше».

## 11. Контекст, который нужно помнить

- Рабочие часы и часовой пояс: Asia/Tashkent, 09:00–18:00, пн–пт — везде, где есть время (SLA, off-hours, отчёты, cron).
- Языки: ru / uz / en. Все тексты для клиента (бот, сообщения) — в трёх вариантах. Интерфейс CRM пока только на русском, но все его тексты — только через словари `frontend/src/i18n/`, чтобы uz/en можно было добавить без переписывания экранов (решение Q-012).
- Один клиентский Telegram-бот + один приватный канал команды с одной кнопкой «Забрать». Бот может писать менеджеру лично только уведомления без кнопок со ссылкой в CRM (решение Q-010). Других действий в Telegram нет.
- Модели только внешние, через LiteLLM по алиасам `dialog-model`, `qualifier-model`, `judge-model`, `embed-model`, `fallback-model`.
- Стенды: dev — локальный компьютер человека (polling, без TLS); prod — VPS (webhook, Caddy TLS). Переезд — только после всех гейтов, по runbook.
- Роли: admin / manager / viewer; инвариант «≥ 1 активный admin»; переключатель Админ/Менеджер — только навигация.
- Пользователей создаёт админ с временным паролем; письма сотрудникам (приглашение, сброс пароля) — только через коннектор «Почта» в «Подключениях» (M3-CRM-08, ADR-0023), без него — ручной временный пароль. Рассылок клиентам нет.
- События ERP → CRM и обратно (B4, шина `rt_bus`, ADR-0014, CONTRACTS §3, §9): единственный путь — библиотека `packages/rt-bus` (экстры `sqlalchemy`, `fastapi`) и модели `rt_contracts` (генерация из JSON Schema, ручной копии нет). **Правило кода: события публикуются только через `rt_bus` из сервисного слоя** (`app/bus/events.py`: `client_*`, `contact_*`, `lead_*`, `user_*`) в транзакции изменения — вне транзакции и при ошибке схемы исключение, изменение откатывается; прямых вебхуков, `httpx`-вызовов «сообщить об изменении» и `try/except` вокруг публикации нет. Снимок (`app/bus/snapshots.py`) нормализует телефон (E.164), почту и длины до публикации — грязные старые данные не роняют изменение. Приёмник — `POST /bus/v1/events` (`rt_bus.fastapi.bus_router`, наружу не публикуется); обработчики — `app/bus/handlers.py` (события ERP в очереди — все `uz.railtech.erp.*.v1`, кроме типов для EDS `NOT_FOR_CRM` в `app/bus/erp_event.py`: `quote.ready_for_approval` с маржой CRM не получает и не обрабатывает, волна 12; в транзакции inbox: `ErpEventsService.apply` → `app/services/erp_event_handlers.py`; код акцепта — inline, мимо БД). Читатель терпимый: лишние поля игнорируются, неизвестный тип/версия — `skipped`. Сообщения Telegram по событию кладутся в `erp_event_notices` и уходят после коммита (`app/bus/notices.py`), не задваиваясь. Секреты пары `erp ↔ crm` — `RT_BUS_SECRET_*` или выводятся из секрета вебхуков сопряжения (`app/bus/secrets.py`, L12). Тесты: примеры контракта `packages/contracts/events/*/examples` через `tests/bus_events.py`, стенд `tests/integration/bus_harness.py`; все 21 событие ERP гоняются на настоящей БД (`tests/integration/test_erp_seam_events.py`), публикация — `test_bus_publish.py`, приёмник — `test_bus_receiver.py`. Эксплуатация — `docs/runbooks/rt-bus-crm.md`, CLI `python -m app bus …`. Индекс документов — upsert по `(client_id, erp_document_id)`. Права EDS в `identity.user.*` зависят от каталога `platform-rbac.yaml`: воркер при старте сверяет отпечаток этой части (`eds_catalog_fingerprint`) с `identity_catalog_state` и при изменении сам вызывает `republish_identity` под advisory-блокировкой (`app/services/identity_catalog.py`, W13C-F4; ручная `republish-identity` — резерв); тесты — `tests/integration/test_identity_catalog.py`.
- Сервисный режим бота (M3-CRM-07): клиенту (customer) с `clients.erp_company_id` модель получает инструменты `erp-mcp` (`app/agents/dialog/erp_tools.py`: сделки, статус, поставка, документы, каталог с ценой); вызывает их код через `ErpMcpClient` (`app/agents/erp_mcp.py`) с контекстом, выпущенным заново на каждую попытку (`security/erp_agent_context.py`, ключ `ERP_MCP_CONTEXT_KEY`, общий с ERP). Идентификаторы клиента и компании — только из БД, аргументы модели фильтруются по схеме; лиду `erp-mcp` не открывается (цены лиду не называем). SDK `mcp` не отдаёт код HTTP-ответа — статус 401/429/400 берётся из `event_hooks` (политика: 401 — один повтор с новым `jti`, 429 — `Retry-After` ≤ 5 с ≤ 2 раз, 400 и сеть — без повтора, Q-FIX36-1). Отказ ERP → модель не получает данных, код заводит `create_service_request`; числа ответа сверяются с данными хода (`unsupported_numbers`), иначе `texts.fallback`. Выключатель — `ERP_MCP_ENABLED`; golden-кейсы — `evals/golden/service.yaml` (платный прогон — только с «да» владельца).
- Параллельные прогоны integration (`scripts/test_int_local.sh`): `ITEST_NS=<имя>` даёт свои контейнеры `rt-itest-<имя>-*` и свободные порты; без переменной — прежние `rt-itest-*` и порты 55432/59000.
