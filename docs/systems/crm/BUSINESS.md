# RailTech CRM — бизнес-требования

Версия 1.0 · 2026-10-08 · Владелец документа: Nurbek

Документ отвечает на вопросы «зачем», «для кого» и «что считается успехом». Он не описывает, *как* система устроена (это `docs/systems/crm/SPEC.md`) и *в каком порядке* строится (это `docs/history/crm/PLAN.md`). Если техническое решение противоречит этому документу — прав этот документ.

---

## 1. Проблема

Входящие обращения потенциальных клиентов приходят в Telegram в любое время. Сегодня:

- первый ответ зависит от того, свободен ли менеджер; вне рабочего времени лид ждёт до утра и часто уходит;
- менеджер тратит время на одинаковые вопросы (что за продукт, какие услуги, сроки, как работаем), вместо того чтобы вести тех, кто готов к сделке;
- квалификация лида происходит «в голове» менеджера — нет единого представления, кто на какой стадии, почему не продвинулся, кого забыли;
- после сделки клиент продолжает писать в тот же Telegram, но его вопросы («пришлите договор», «где наше КП», «статус поставки») обслуживаются вручную, с поиском по почте и папкам;
- история общения с клиентом живёт в личных чатах менеджеров и теряется вместе с ними.

## 2. Решение в одном абзаце

**RailTech CRM** — внутренняя система, в которой ИИ-ассистент в Telegram берёт на себя первую линию: отвечает по базе знаний компании, выясняет потребность и предлагает следующий шаг, а в нужный момент передаёт человека менеджеру с готовым резюме и причиной передачи. Команда работает в едином веб-интерфейсе: видит все лиды и клиентов, переписку, стадии, документы, управляет базой знаний и настройками. После сделки тот же бот становится постоянным каналом связи клиента с компанией — выдаёт документы, отвечает на сервисные вопросы, зовёт менеджера.

Это не чат-бот и не ещё одна CRM. Это CRM, у которой в центре — диалог с клиентом, а ИИ — штатный сотрудник первой линии.

## 3. Ценность

### 3.1. Для бизнеса

| Ценность | Как измеряем |
|---|---|
| Ни один лид не остаётся без ответа | Доля лидов с первым ответом ≤ 1 мин — целевое 100 % (сейчас зависит от человека) |
| Менеджер работает только с тёплыми лидами | Доля диалогов, закрытых ботом без участия человека (информационные) — целевое ≥ 50 % |
| Горячий лид попадает к человеку вовремя | Время от триггера эскалации до «Забрать» в рабочие часы — медиана ≤ 15 мин |
| Квалификация прозрачна | У каждого лида есть стадия, оценка и причина последнего перехода, видимые всей команде |
| Клиент обслуживается после сделки без нагрузки на менеджера | Доля сервисных запросов (документы, статусы), закрытых ботом — целевое ≥ 70 % |
| История не теряется | 100 % переписки хранится в системе, не в личных чатах |

### 3.2. Для менеджера

- Утром видит очередь лидов, по каждому — кто, что хочет, на какой стадии, почему к нему.
- Не отвечает на одно и то же.
- Получает уведомление в Telegram-канал команды с кнопкой «Забрать», дальше работает в CRM с полным контекстом.
- Не выдумывает, что ответить по продукту: база знаний общая, ответы согласованы.

### 3.3. Для клиента

- Ответ сразу, на его языке (русский / узбекский / английский), по делу, без давления.
- Если нужен человек — он появится, и ему не придётся повторять всё заново.
- После сделки — один чат, в котором можно получить любой свой документ или задать вопрос.

### 3.4. Для компании как разработчика

Проект — первый шаг RailTech в мультиагентные системы с enterprise-подходом: явная архитектура, стандарты (MCP), наблюдаемость, evals, ADR. Полученные компоненты (MCP-серверы, фреймворк оценки, ролевая модель) переиспользуются в следующих проектах.

## 4. Пользователи и роли

| Роль | Кто | Что делает | Где |
|---|---|---|---|
| **Лид / Клиент** | Внешний человек, пишет в Telegram | Задаёт вопросы, получает ответы и документы, соглашается на следующий шаг | Клиентский Telegram-бот |
| **Менеджер** | Сотрудник продаж / сопровождения | Забирает лидов, ведёт переписку, фиксирует результат, прикладывает документы клиенту | CRM (веб) + Telegram-канал уведомлений |
| **Администратор** | Руководитель / ответственный за систему | Всё, что менеджер, плюс: база знаний, настройки, пользователи и роли, просмотр аналитики | CRM (режим «Админ») |
| **Наблюдатель** | Руководство, финансы | Смотрит дашборд и карточки, ничего не меняет | CRM (только чтение) |

Правила ролей:
- Роли выдаёт администратор. Администраторов может быть несколько; права делегируются между ними. В системе всегда остаётся минимум один администратор.
- Администратор в интерфейсе может переключиться в режим «Менеджер», чтобы работать как менеджер, не отвлекаясь на административные разделы.

## 5. Жизненный цикл клиента

```
Новый → Вовлечён → Квалифицирован → Передан → В работе → Сделка → Клиент
                                                              ↘ Отказ
             любая стадия → Не отвечает (по таймеру) → возвращается при новом сообщении
```

| Стадия | Смысл для бизнеса |
|---|---|
| **Новый** | Написал впервые, дал согласие на обработку данных |
| **Вовлечён** | Задаёт содержательные вопросы, отвечает на уточнения |
| **Квалифицирован** | Понятны потребность и продукт, а также хотя бы одно из: срок, роль в решении, бюджет. Критерии настраивает администратор («Настройки → Квалификация»), это — значение по умолчанию |
| **Передан** | Система решила, что нужен человек; менеджер ещё не взял |
| **В работе** | Менеджер забрал, ведёт сам |
| **Сделка / Отказ** | Результат зафиксирован менеджером |
| **Клиент** | После сделки: бот переключается в сервисный режим (документы, статусы, поддержка) |
| **Не отвечает** | Нет сообщений от лида 7 дней |

## 6. Ключевые сценарии

### С1. Холодный лид → ответ по базе знаний
Лид пишет впервые. Бот предлагает выбрать язык (Oʻzbekcha / Русский / English, Q-022), приветствует и просит согласие на обработку данных на выбранном языке; отвечает на вопрос строго по базе знаний компании. Если вопрос требует уточнения потребности — задаёт один уточняющий вопрос. **Успех:** ответ за ≤ 6 с, без выдуманных фактов, на языке лида.

### С2. Квалификация и передача менеджеру
По ходу диалога система оценивает стадию и готовность. Когда лид спрашивает цену, которой нет в базе, просит звонок, раздражён или просто «созрел», система передаёт его менеджеру: в канал команды приходит карточка с резюме, причиной передачи и рекомендацией; менеджер нажимает «Забрать» и продолжает в CRM. Если лид сам просит менеджера, а номера телефона у него нет, бот сначала просит «Поделиться номером» (менеджер сможет связаться; защита от спама) и передаёт сразу после номера; «Не сейчас» — бот продолжает отвечать сам (решение владельца 2026-10-12, отключается в «Настройки → Передачи»). Передачи по сигналам системы номера не ждут — в карточке «Номер: не указан». Лид получает сообщение, что вопрос передан менеджеру, и ожидаемый срок ответа (SLA в рабочее время или ближайшее рабочее время). **Успех:** менеджер понимает ситуацию из карточки без чтения всей переписки; причина передачи всегда объяснима.

### С3. Менеджер ведёт диалог из CRM
В карточке лида менеджер видит всю переписку, резюме, оценку, заметки. Пишет ответ — он уходит лиду от имени бота. Может вернуть диалог боту (с заметкой), отложить, зафиксировать результат. **Успех:** менеджер не выходит из CRM и не ищет лида в личных чатах.

### С4. Вопрос, на который нет ответа
Бот честно говорит, что точного ответа в его материалах нет, и предлагает передать вопрос менеджеру (кнопка; «Не нужно» — продолжаем с ботом); «уточню и вернусь» бот не обещает (Q-016). Вопрос регистрируется как пробел в базе знаний. Администратор в CRM видит список таких вопросов и закрывает их, добавляя материалы. **Успех:** база знаний растёт из реальных вопросов; повторный вопрос получает ответ.

### С5. Клиент после сделки ищет документ
Клиент (привязанный к компании-клиенту в CRM) пишет: «пришлите договор, который мы заключали в июле». Бот находит документ среди документов *этого* клиента и присылает. Чужие документы недоступны в принципе. Если документа нет или запрос про изменение условий — зовёт менеджера. **Успех:** рутинные запросы закрываются без человека; утечка между клиентами невозможна технически.

### С6. Администрирование без разработчика
Администратор загружает документы в базу знаний, меняет тексты приветствия, рабочие часы, правила передачи, добавляет пользователя и даёт ему роль. Ничего из этого не требует правки кода или деплоя. **Успех:** команда самостоятельна в эксплуатации.

## 7. Что система НЕ делает (границы)

- **Не продаёт и не уговаривает.** Не использует давление, срочность, повторные предложения связаться. Сделку закрывает человек. Это принципиальная позиция бренда.
- **Не выдумывает факты о продукте.** Нет ответа в базе — говорит честно.
- **Не даёт юридических и финансовых консультаций**, не обсуждает конкурентов по существу.
- **Не заменяет ERP и документооборот.** Хранит документы клиентов и даёт их клиенту, но не ведёт договорной процесс, бухгалтерию, склад. Задел на интеграции — да; собственная реализация — нет (см. раздел 9).
- **Три входа клиента, один жизненный цикл** (ARCHITECTURE §17, M3-CRM-05): Telegram-бот (диалог, квалификация, передача), форма «Запрос» на странице входа Cabinet (лид с источником `web`, без диалога — его ведёт менеджер) и ручное создание менеджером после звонка, письма или по рекомендации (`phone` / `email` / `referral`). Лид с номером телефона, который позже написал в бот и поделился тем же номером, склеивается с существующей карточкой. Переписка по почте и телефония внутри CRM по-прежнему не ведутся; веб-онбординг — это запрос, не регистрация (полноценный веб-канал агента — SPEC §15).

## 8. Ограничения и требования

- **Языки:** русский, узбекский, английский. База знаний может быть на русском; бот отвечает на языке клиента.
- **Рабочие часы:** Asia/Tashkent, 09:00–18:00, пн–пт. Вне рабочих часов бот отвечает по базе знаний как обычно, а при передаче менеджеру предупреждает клиента о времени ответа.
- **Персональные данные:** согласие — первое взаимодействие; клиент может запросить удаление переписки; персональные данные не попадают в технические логи. Переписка обрабатывается внешними ИИ-провайдерами — это должно быть отражено в тексте согласия.
- **Инфраструктура:** без локальных ИИ-моделей (нет мощностей); все модели — внешние API. Остальное — бесплатные open-source решения на собственном сервере.
- **Два контура:** `dev` — локальный компьютер для разработки и тестов; `prod` — виртуальный сервер. Переезд на prod только после приёмки на dev.
- **Подход:** enterprise-уровень несмотря на масштаб — документация, архитектурные решения (ADR), автотесты, оценка качества ИИ (evals), наблюдаемость, ролевая модель, аудит действий.

## 9. Стратегическое направление (не в первой версии)

Единый интерфейс команды проектируется так, чтобы вырасти в сторону CRM-полноты и интеграций, а не быть переписанным:

- **Ближайшие расширения:** календарь (бот сам предлагает слот для звонка), статусы заказов/поставок клиенту, шаблоны ответов менеджера, экспорт в учётную систему.
- **Интеграции, а не собственная реализация:** ERP, документооборот, бухгалтерия, телефония — подключаются через стандартные интерфейсы (MCP-серверы / API), сохраняя CRM как «единое окно».
- **Другие каналы:** сайт-виджет, WhatsApp, почта — через тот же диалоговый агент.
- **Telegram Mini App** для менеджеров, если понадобится мобильная работа без ноутбука.

## 10. Критерии успеха пилота (4 недели на prod)

| Критерий | Порог |
|---|---|
| Доля лидов с первым ответом ≤ 1 мин | 100 % |
| Доля ответов бота, подтверждённых базой знаний (по выборочной проверке) | ≥ 95 % |
| Выдуманные цифры/условия | 0 |
| Передачи менеджеру: доля «зря передал» (по оценке менеджеров) | ≤ 15 % |
| Передачи менеджеру: доля «надо было передать, а не передал» | ≤ 5 % |
| Медианное время до «Забрать» в рабочие часы | ≤ 15 мин |
| Пробелы базы знаний, закрытые за пилот | ≥ 80 % зарегистрированных |
| Инциденты с доступом к чужим данным | 0 |
| Команда ведёт эксплуатацию без разработчика (KB, настройки, роли) | Да |

## 11. Риски и как с ними работаем

| Риск | Мера |
|---|---|
| Бот выдумает цену или условие и клиент это запомнит | Ответы только из базы знаний; автоматическая проверка на числа, которых нет в источниках; evals перед каждым изменением |
| Бот «продаёт» и раздражает | Явный запрет в поведении; eval на тон; менеджеры размечают реальные диалоги еженедельно |
| Менеджеры не доверяют передачам и игнорируют канал | Каждая передача объяснима («почему к вам»); SLA-напоминания; разбор 100 % передач на пилоте |
| Утечка документов между клиентами | Идентификатор клиента подставляется кодом из проверенной привязки, а не ИИ; привязку подтверждает менеджер |
| Стоимость внешних моделей | Дешёвая модель на квалификации; дневной бюджет и учёт по каждому вызову; деградация на запасную модель |
| Качество узбекского языка | Отдельный набор тестов на узбекском; выбор провайдера по результатам |
| Зависимость от одного ИИ-провайдера | Единый шлюз, провайдер меняется настройкой |

## 12. Глоссарий

- **Лид** — человек, написавший в бот, до момента сделки.
- **Клиент** — компания или человек после сделки; к нему привязаны Telegram-аккаунты и документы.
- **Передача (эскалация)** — момент, когда система решает, что нужен человек, и уведомляет команду.
- **База знаний (KB)** — согласованные материалы о продуктах и услугах, по которым отвечает бот.
- **Пробел KB** — вопрос, на который бот не нашёл ответа.
- **Стадия** — положение лида в жизненном цикле (раздел 5).
- **Оценка (score)** — число 0–100, насколько лид близок к сделке; считается по правилам, не «на глаз».
- **Канал команды** — внутренний Telegram-канал с уведомлениями о лидах.
