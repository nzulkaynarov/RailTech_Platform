## 2. Стенд

Проект `rt-w15-h9`, `.env` — как `make env` в worktree (секреты сгенерированы на месте, в репозиторий не попали), порты:
`HTTP_PORT=8099`, Postgres 15439, Redis 16391/16392, S3 19091/19092 и др. Поднято только нужное Платформе (память Docker 12 ГБ,
рядом работали другие стенды и сборки): `postgres`, `redis-broker`, `redis-cache`, `rustfs`, `litellm`, `crm-api`, `crm-worker`,
`erp-backend`, `erp-worker`, `eds-api`, `eds-worker`, `platform-bff`, `platform-web`, `caddy`; **без** `docling`, `crm-bot`,
`crm-mcp-*`, `erp-mcp`, `erp-beat`, `erp-worker-ai`, `crm-web`, `erp-web`, `cabinet-web` (ссылки «Открыть в старой CRM/ERP»
проверены по адресу, сами старые фронты не открывались). `PLATFORM_SSO_ENABLED=true`, `TELEGRAM_MODE=disabled`, токена бота и
ключей моделей нет. Пик памяти стенда — 3,9 ГиБ.

**Машина была перегружена** (load average 13–40: соседние стенды и сборки других агентов), ответы бэкендов — секунды, вход
под нагрузкой — до 10 с. Чтобы пройти сценарии, а не мерить таймауты, на стенде (вне репозитория) подняты пределы ожидания BFF:
`PLATFORM_CRM_TIMEOUT_SECONDS=20` и `TIMEOUT_SECONDS` клиента бэкендов 3 → 15 с (подмена `bff/app/clients/base.py` томом).
До этого вход и экраны EDS отвечали 503 «сервис документов не отвечает» — честно, но непроходимо. **Postgres стенда шесть раз
уходил в автоматическое восстановление** (`server process … exited with exit code 2`, рядом — ошибки `procrastinate_defer_periodic_job_v2`),
после чего на минуты были «Нет доступа к CRM», 502 и пустые очереди; сценарии повторялись после восстановления.

Данные: администратор — через `/setup` с кодом из журнала `crm-api`; своя компания и сопряжение ERP — в мастере; сотрудники семи
ролей — «+ Пригласить сотрудника» → «Временным паролем» (смена пароля при первом входе); три демо-лида — `python -m app seed-demo`
CRM (вымышленные); служебная записка с суммой — менеджером в «Документы · Создать документ». Писем, КП, проектов, счетов и заданий
на расчёт на чистом стенде нет: их цепочка начинается с заявки, которая создаётся пока в старой CRM (§7).

```
docker compose -p rt-w15-h9 -f infra/compose/base.yml -f infra/compose/dev.yml --env-file .env up -d --build \
  postgres redis-broker redis-cache rustfs s3-init db-init litellm litellm-seed crm-migrate crm-api erp-backend \
  eds-migrate eds-api eds-worker platform-bff platform-web
docker compose -p rt-w15-h9 … up -d --no-deps --build crm-worker erp-worker caddy
QA_BASE=http://platform.localhost:8099 QA_OUT=<каталог вне репозитория> QA_COMPOSE=<обёртка docker compose -p rt-w15-h9> \
  node docs/audits/qa/w15-h9-gate/run.mjs s1 s1w s1c s2 sD s3 s4 sW s5 s6 sS
docker compose -p rt-w15-h9 … down -v
```

Пароли сотрудников генерируются на лету и лежат только в `QA_OUT/state.json`; на снимках провала поля паролей закрыты маской.
