Каждая из них либо открывает доступ к чужим данным, либо ломает основной путь клиента или сотрудника. В скобках — номера исходных находок аудиторов, по которым видны файлы и строки.

### Известные всем секреты по умолчанию на шве CRM ↔ ERP

SEC-1 · S-1, I-1, G-2 · проверено лидом

Что
Сервисный токен CRM→ERP, секрет вебхуков, ключ контекста агента MCP и общий SSO-секрет имеют значения по умолчанию прямо в коде (`"test-crm-to-erp-token"`, `"dev-platform-sso-secret"` и т.п.), а `infra/compose/base.yml` эти переменные не передаёт. Имя в `.env.example` (`WEBHOOK_SECRET`) не совпадает с тем, что читает код (`ERP_WEBHOOK_SECRET`).

Чем грозит
На любом стенде из этого compose можно подписать SSO-токен с ролью администратора и войти в ERP суперпользователем, вызвать `POST /users/provision` с `role: admin`, подписать контекст агента на любую компанию и читать её сделки и документы.

Нарушено
ORCHESTRATOR §3.6 «секреты только в окружении»

### SSO: захват чужого аккаунта и самопровижининг

SEC-2 · S-2, S-3, S-5, S-7, I-17 · проверено лидом

Что
ERP при выдаче токена в CRM подставляет `sub = user.pk` ERP, если нет сопоставления: сотрудник ERP с pk=N откроет сессию пользователя CRM с id=N. CRM при неизвестном `sub` ищет по email. ERP на обмене сам создаёт пользователя, привязывает существующий аккаунт по email, переписывает `is_superuser` и роли и обходит 2FA. `platform_access`, провижининга и отзыва сессий из CRM нет — ядро M3-CRM-06 не сделано; кнопку перехода видят все. Срок жизни токена не ограничен 60 с.

Нарушено
`docs/architecture/sso-token.md` п.5, ADR-0003, DoD M3-CRM-06

### Портал ломает жизненный цикл документов

FLOW-2 · P-3, P-5, P-6, P-7 · P-7 проверено лидом

Что
Клиент видит и может принять КП, ещё не прошедшее внутреннее согласование. Подпись договора из портала ставит «Подписан сторонами» без подписи компании, в обход FSM, из любого статуса, включая черновик и отменённый. Возврат акта записывает в статус NULL, приёмка акта возможна из черновика и сразу закрывает сделку как выигранную. Карточка КП с позицией из каталога отвечает 500 (`items__product__unit_of_measure`), и акцепт возвращает 500 уже после коммита.

### Интеграционный API падает на реальных сделках, передача теряет события и плодит дубли

FLOW-3 · I-2, I-3, I-4, I-5 · I-2, I-3 проверены лидом

## Что нужно решить вам

По каждому пункту — моя рекомендация. Без ответа на 1–3 начинать волну 0 нельзя; остальное можно решить к началу соответствующей волны.

1**Включить защиту ветки main**

Настройки репозитория → Branches: PR обязателен, обязательная проверка `ci-ok`, запрет force-push. Это может сделать только владелец. Рекомендую сегодня.

2**Заморозить новые задачи M3 до конца волны 3**

Рекомендую: да. Каждая новая задача M3 сейчас строится на сломанном шве (интеграционный API падает, SSO небезопасен).

3**Отозвать «закрытие» вех M1 и M2**

Рекомендую: вернуть в «готово к гейту» и пройти гейты заново после волн 1–2 (FIX-50, FIX-51). Критерий гейта M1 «`legacy/b2b` ещё на месте» проверяем по тегу `b2b-final`, папку не возвращаем.

4**SSO: может ли обмен токена создавать пользователя ERP**

Рекомендую: нет, как в `docs/architecture/sso-token.md`. Пользователь появляется в ERP только при выдаче доступа в CRM, обмен лишь находит его.

5**MCP: официальный SDK или самописный JSON-RPC**

Рекомендую официальный `mcp` SDK, на котором уже работает CRM: меньше своего кода на границе с моделью. Альтернатива — ADR с вашей отметкой.

6**Договорной курс на уже согласованном КП**

Рекомендую: разрешать только в черновике; на согласованном КП — вернуть в черновик с повторным согласованием. Сейчас цена меняется без повторного согласования.

7**Приёмка поставки по строкам — сейчас или в M4**

Рекомендую: контракт и API сделать в волне 2 (это гейт M2), статусы строк из склада — в M4. Если откладываем — кнопки из Cabinet убрать сразу.

8**Откуда брать курс показа «USD ↔ UZS» в интерфейсе ERP**

Рекомендую: только из курсов ЦБ (`finance.services.fx`), поле ручного курса в системных настройках удалить.

## Что сделано хорошо и сохраняем

- Портальная сессия отделена от сессий сотрудников; cookie HttpOnly, на пути `/api/portal`; запросы к объектам фильтруются по компании сессии, явного IDOR не найдено.
- Каталог в портале и MCP идёт через опубликованный слой `catalog.published`; себестоимость и маржа в строках КП клиенту не отдаются.
- Криптография проверки `initData`, HMAC подписи вебхуков по сырому телу, сравнение токенов в постоянном времени, ротация двух токенов, идемпотентность интеграционного API в БД на 7 дней с хешем тела.
- M1-ERP-08: снимок курса с датой и источником, фиксация при отправке на согласование, отправленное КП не пересчитывается, договорной курс с правом, причиной и журналом; тесты действительно параметризованы.
- Вебхуки ERP: журнал событий в БД, отправка после коммита, сетка повторов по контракту. CRM: дедупликация по `X-Event-Id`, быстрый ответ, обработка в очереди; линейная цепочка миграций Alembic.
- Cabinet: мок не попадает в прод-сборку, типы портала сгенерированы, i18n на трёх языках симметрична, к API сотрудников Cabinet не обращается. Тег `b2b-final` на месте.
