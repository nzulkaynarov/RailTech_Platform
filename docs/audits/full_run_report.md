# Полный прогон бизнес-процесса на стенде ансамбля (шаг 4 дорожной карты)

Статус: принят · Владелец: лид · Обновлено: 2026-11-11

Стенд: compose-проект `rt-full-run`, порт 8120 (Платформа `platform.localhost:8120`, кабинет `cabinet.localhost:8120`), чистая установка, без ключей ИИ, без Telegram, без SMTP. Версия: `419fcd8d Merge pull request #473 from nzulkaynarov/w20/erp-legacy-sso` (ветка `w20/full-run`). Проверял QA-агент: Playwright-скрипты на хосте (chromium, 1440 и 390 px), `@axe-core/playwright` (WCAG 2.1 A/AA). Данные вымышленные (`*@demo.example`). Снимки — `docs/screens/full-run/`.

## 1. Итог

Процесс продажи пройден от лида до закрытого проекта (лид → заявка → резолюция → расчёт → КП → одобрение → кабинет клиента → договор → счёт → оплата → закупка у партнёра → приёмка → отгрузка → акт → «Выполнено»), документооборот (входящее → резолюция → поручение → исполнение; служебка → согласование → оплата) тоже. Но только с обходами: «На подпись» отвечает ошибкой, хотя запрос создаётся; списки «Мои» в «Документах» не открываются; лид из интерфейса создать нельзя; вход клиента и принятие КП требуют кода из письма, и код пришлось выпустить из консоли ERP (стенд без SMTP).
Находок 43: **блокеров 2**, **важных 14**, **малых 27**. axe: 0 нарушений на всех экранах, кроме четырёх мест (FR-40…FR-43); на 390 px горизонтальной прокрутки нет нигде. Платформа честно говорит об ошибке ИИ («Разбор не удался: модель не ответила»); неправда — там, где письма «уходят» без почтового сервера (FR-12).

## 3. Находки

### Главная

**FR-1 · блокер · «На подпись» договора, акта и счёта отвечает ошибкой, хотя запрос создан.**
Шаги: менеджер → Проекты → ПР-2026-001 → Договор → «На подпись». Ожидалось: запрос подписи у директора. Получилось: тост «Не удалось отправить на подпись», ответ BFF `503 BACKEND_UNAVAILABLE`, `details.reason = "HTTP 201"`. ERP при этом вернул 201 и создал запрос (в логе ERP `signing_outbound` на каждый клик, дубли). Задача директору появилась, только когда администратор выдал полномочие подписи. Причина: BFF принимает только 200. Код: `apps/platform/bff/app/eds_projects.py:184` (`_json(..., ok=(200,))`), вызов `:289` (`request_signing`). Снимок: [75](../screens/full-run/75-contract-to-sign-503-1440.png).

**FR-4 · малое · аватар менеджера с двумя ролями подписан «Все роли»** вместо названий ролей. Снимок: [72](../screens/full-run/72-project-manager-1440.png).

**FR-6 · важное · данные не доходят до снабженца.** Черновик заказа партнёру ЗП-2026-001 создан при принятии КП, подтверждение партнёром в кабинете пришло, но в «Задачи» снабженца нет ни одной строки (пустое «Заданий на расчёт нет», пока нет расчёта). Так же без задачи осталась заявка на партнёрство. Снимки: [90](../screens/full-run/90-queue-supply-1440.png), [98](../screens/full-run/98-queue-supply-1440.png).

**FR-30 · важное · устаревшая задача у директора.** После моих двух нажатий «На подпись» на подписанном акте у директора осталось «Ждут вашей подписи: Акт АКТ-2026/001», хотя акт уже принят клиентом; заголовок при этом «0 решений». Исправлено 2026-11-14 (план 0.7): EDS закрывает шаг «Подписать», когда ERP сообщает о подписанном, принятом или отменённом документе; «На подпись» у таких документов нет; сумма — с разрядами.

### Документы

**FR-2 · блокер · списки «Мои» не открываются: «Не удалось загрузить документы — Сервер не ответил».**
Шаги: любой, кроме директора (для администратора, менеджера): Документы → Внутренние (или Исходящие, Архив), вкладка «Мои». Ожидалось: список своих документов (в нём автор смотрит статус служебки, П5). Получилось: `422` от EDS: `Input should be 'draft', 'on_approval', 'returned', 'rejected', 'approved', 'to_accountant', 'paid' or 'sent'`. Запрос уходит с `status=awaiting_resolution&status=open` вместе с видами документов. Код: `apps/platform/web/src/modules/eds/documents/DocumentsPage.tsx` (`OPEN_STATUSES`, ~строка 90, статусы реестра подмешиваются в «открытые» для документов). Снимки: [132](../screens/full-run/132-memo-sent-1440.png), [79](../screens/full-run/79-approvals-1440.png).

**FR-5 · важное · «Исходящие» у директора пусты** («В реестре пока пусто»), хотя одобренное КП, счёт и акт существуют; КП в статусе «Одобрено» (ждёт решения клиента) лежит в «Архиве» вместе с входящим письмом «Резолюция наложена» и оплаченной служебкой; договор и акт в реестр не попадают; в колонке «Сумма» везде «—»; действие КП — «В разделе «КП на одобрение»», такого раздела в меню нет. ## 4. Не проверено

- Telegram (бот, привязка, уведомления), ответы бота, помощник и другие функции ИИ (на стенде нет ключей; проверено только, что «Разобрать текст заявки» честно отвечает «модель не ответила»).
- Реальная доставка писем (нет SMTP): вход клиента и партнёра в кабинет и код принятия КП проверены кодом, выпущенным из консоли ERP; приглашение письмом, письмо КП, отправка заказа — только статус экрана.
- Запрос цен партнёру из расчёта (RFQ) и ответ партнёра; загрузка прайса; «Подключение партнёра»: проверка реквизитов, договор, открытие кабинета (проверена только подача заявки и очередь).
- Ветки процесса: возврат на доработку, отказ клиента, истечение КП, частичная оплата, возврат акта, дубль письма, «Вернуть»/«Отклонить» в резолюции и согласовании.
- П6 (закупка вне сделки), П8 (расходы) — пункты «Создать» неактивны («скоро»), оплата партнёру из заказа не проверялась.
- «Календарь»: месячный вид и сроки на следующих неделях; «Чаты»: обсуждения на объектах (панель «Обсуждение») и «Созвон»; «Почта» и «База знаний» с данными; «Шаблоны» документов, «Нумерация», «Налоги», «Журнал» и «Выгрузки» только на открытие экрана и axe.
- Роли «Менеджер» без универсала и «Администратор» проходили только меню и права на экранах; ролей «Юрист» и «Расчётчик» в каталоге нет.
- Языки UZ и EN.
- Стенд-ограничение: ключи ИИ, Telegram и почта; всё, что от них зависит, не засчитано в находки, кроме FR-12 (ложное «отправлено»).
