## 0. Как читать этот документ

Документ адресован ИИ-агентам и разработчикам, которые (1) сопоставят целевое описание с действующими системами RailTech (CRM, ERP, Cabinet, Telegram-бот), (2) реализуют фронтенд единого интерфейса на React + Ant Design Pro, (3) затем подключат его к существующим API.

Порядок чтения: §1 (зачем) → §2 (словарь — обязателен, все имена из него) → §3 (процессы) → §4 (роли) → §5–§6 (дизайн и каркас) → §7 (функции по модулям) → §8–§9 (каналы клиента и уведомления) → §10 (данные и интеграция) → §11 (план и приёмка).

Правила приоритета при конфликте: словарь §2 выше кода действующих систем; процесс §3 выше любого существующего экрана; дизайн §5–§6 выше привычек Ant Design Pro «по умолчанию». Всё, что помечено «ВНЕ ПЛАТФОРМЫ», не реализуется и не интегрируется.

Явные границы v3:

- Нет интеграции с операторами ЭДО/ЭСФ (Didox, Faktura и др.), нет E-IMZO, нет ЭТТН внутри системы.
- Нет интеграции с банками и платёжными сервисами (Click, Payme, банк-клиент).
- Договор, акт и ЭСФ выставляются и подписываются у оператора ВНЕ ПЛАТФОРМЫ. Платформа хранит проект документа, факт выставления, факт подписания и скан, которые бухгалтер вносит вручную. Платформа ведёт журнал «кто и когда».
- Оплаты подтверждаются бухгалтером вручную по платёжному поручению клиента.

## 1. Бизнес-ценность

### 1.1. Проблема (из аудита 21.10.2026)

Три системы (CRM, ERP, Cabinet) построены по правильной архитектуре, но человек, пришедший в них, не видит «дороги»: лид не понимает, где кабинет; менеджер не видит, что происходит с заявкой после передачи; сотрудник ERP не знает, что делать дальше; директор согласует в трёх разных местах; админ бегает между системами, чтобы включить одну интеграцию. Семь корневых причин: нет единого словаря и стадий; передача лид → клиент сделана «для почты», а клиенты в Telegram; роли — коды прав, а не рабочие дни; кабинет недостроен; конфигурация размазана; документы без юридической силы там, где рынок её требует; универсальность товаров и услуг только в каталоге.

### 1.2. Что даёт единая платформа

1. **Один вход для всех сотрудников.** Шесть модулей (Dashboard, CRM, EDS, ERP, Chats, Admin) в одном окне с общим каркасом, поиском и центром уведомлений. Сотрудник больше не переключается между приложениями.
2. **Один путь заявки.** Заявка получает номер при создании из лида и проходит семь шагов до «Выполнено» (§2.3). Шаг всегда виден в шапке карточки; у каждого шага один владелец и одна кнопка.
3. **Очередь вместо поиска работы.** Каждая роль утром видит «Мою очередь»: что требует решения именно от неё. Одна строка — одно действие.
4. **Контекст всегда рядом.** Боковое окно с карточкой объекта, чатом проекта и документами открывается на любом экране без перехода; при работе с таблицами скрывается.
5. **Внутренний документооборот в EDS.** Входящие письма, резолюции, КП, договоры, счета, акты, служебные записки, заявления и отчёты — с маршрутом согласования и журналом. Юридически значимые действия (подпись у оператора, оплата через банк) остаются вне платформы, но их результат фиксируется в ней.
6. **Чаты как оперативный слой.** Чат проекта создаётся вместе с заявкой; командные и личные чаты свободны; из любого сообщения можно оформить служебную записку.
7. **Клиент в своих каналах.** Telegram-бот, почта и кабинет получают одни и те же документы и статусы на языке клиента; внутренние стадии клиенту не показываются.

### 1.3. Что считаем успехом (метрики пилота)

Время первого ответа лиду; время от заявки до первого КП; доля КП, одобренных директором с первого раза; доля заявок, прошедших путь без ручного вмешательства за пределами платформы; время подтверждения оплаты после получения платёжки; доля служебных записок, согласованных в течение дня; число переключений сотрудника между приложениями (целевое — ноль в рабочем дне).

## 2. Словарь

Все имена ниже обязательны в интерфейсе, в коде фронтенда и в контрактах интеграции. Старые коды действующих систем указаны для сопоставления.

### 2.1. Объекты

| Объект | Определение | Где живёт | Сопоставление с действующими системами |
|---|---|---|---|
| **Лид** | Человек или компания, написавшие впервые; ещё не клиент | CRM | `leads` (CRM) |
| **Клиент** | Компания с контактами; появляется при создании заявки из лида | CRM (контакты, переписка) + ERP (контрагент) | `clients` (CRM), `parties.Company` (ERP) |
| **Контакт** | Сотрудник клиента с каналами (Telegram, почта, телефон) и признаком «может принимать решения» | CRM + Cabinet | `Contact.can_act` |
| **Заявка** | Потребность клиента: текст, строки, вложения, письмо; создаётся менеджером из лида | EDS/ERP (единая сущность, номер ЗВ-ГГГГ-NNN) | `Deal` в `DRAFT/RFQ_OPEN` + `PortalRequestLine` |
| **Проект** | Та же заявка после принятия КП клиентом; номер ПР-ГГГГ-NNN наследует NNN заявки | EDS «Все проекты» + ERP | `Deal` от `CONTRACT_SIGNED` и далее |
| **Входящее письмо** | Официальный документ клиента на имя директора; регистрируется с номером ВХ-NNN/ГГ | EDS | новое (сейчас вложение лида) |
| **Резолюция** | Решение директора по входящему: текст, исполнители, срок, ограничение маржи | EDS | новое |
| **Расчёт** | Строки заявки с данными склада, поставщика, визами специалистов | ERP | `Quote` (черновик) + строки |
| **КП** | Коммерческое предложение с версиями; номер КП-ГГГГ/NNN | EDS (Черновик → Исходящие) + ERP (конструктор) | `Quote` |
| **Договор** | Проект договора из принятого КП; статусы по §2.4; скан подписанного прикрепляется вручную | EDS «Все проекты» | `Contract` (убрать `MANUAL_MODE`-подпись кликом, заменить статусами) |
| **Счёт** | Счёт на оплату (предоплата / остаток / по этапу); PDF с реквизитами и QR | EDS «Счета и оплаты» | `Invoice` |
| **Платёжка** | Платёжное поручение клиента (файл), приложенное клиентом в кабинете/боте или бухгалтером | EDS | новое (`PaymentConfirmation`) |
| **Оплата** | Факт поступления, подтверждённый бухгалтером; закрывает счёт целиком или частично | EDS + ERP | `Payment` |
| **Исполнение** | Резерв склада, заказ поставщику, отгрузка, этап услуги | ERP | `Fulfillment`, `DeliveryLine` |
| **Акт** | Акт выполненных работ / поставки; скан подписанного прикрепляется вручную | EDS | `Act` |
| **Служебная записка** | Внутренний документ сотрудника на имя директора: тема, текст, сумма/срок, вложения; маршрут «директор» | EDS | новое (`ServiceMemo`) |
| **Чат проекта** | Внутренний чат, созданный автоматически вместе с заявкой; живёт, пока проект открыт | Chats | новое (`ProjectChat`), частично — канал команды в боте |
| **Обращение** | Вопрос клиента после создания заявки, привязанный к проекту | CRM/Chats | `ServiceRequest` |

Из словаря уходят: «сделка» как отдельный от заявки объект в интерфейсе (внутренний `Deal` остаётся в ERP), «счёт-фактура» для собственных PDF, `KYC_PENDING`, «зеркало сделок» в CRM как самостоятельная воронка, «должности» `WorkspaceRoleCode` как вторая модель ролей, «CRM Sync»-роли.

### 2.3. Путь заявки — 7 шагов (стадии)

Это единственная шкала стадий для сотрудников. Отображается в шапке карточки заявки/проекта на всех экранах (компонент `Steps`, 7 шагов, текущий подсвечен).

| # | Стадия | Владелец | Вход | Выход («следующий шаг») | Код для интеграции | Старые коды ERP |
|---|---|---|---|---|---|---|
| 1 | **Заявка** | Менеджер | «Создать заявку» из лида | письмо зарегистрировано → 2 | `REQUEST` | `DRAFT`, `RFQ_OPEN` |
| 2 | **Резолюция** | Директор | заявка + входящее в EDS·Входящие | «Утвердить резолюцию» → 3; «Вернуть менеджеру»; «Отклонить» → Отказ | `RESOLUTION` | новое |
| 3 | **Расчёт** | Снабженец, гл. инженер (по резолюции) | задание в ERP·Расчёт | все визы собраны → «Расчёт готов» → 4 | `CALCULATION` | `SOURCING`, `CALCULATING` |
| 4 | **КП** | Директор | черновик КП в EDS·Черновик | «Одобрить КП» → отправка клиенту; клиент принял → 5; «Вернуть на доработку» → 3; клиент отклонил/истёк → 3 или Отказ | `QUOTE` (подстатусы `DRAFT`, `SENT`, `ACCEPTED`) | `QUOTE_SENT` |
| 5 | **Договор** | Бухгалтер (подпись — директор вне платформы) | КП принято, проект открыт | редакция согласована клиентом → выставлен у оператора → подписан (скан) → 6 | `CONTRACT` | `CONTRACT_SIGNED` (переименовать) |
| 6 | **Оплата** | Бухгалтер | договор подписан, счёт выставлен | оплата подтверждена по политике (предоплата) → 7 (исполнение идёт параллельно в ERP) | `PAYMENT` | новое |
| 7 | **Выполнено** | Система | акт подписан (скан) + все счета оплачены | «Новая заявка» для клиента | `DONE` | `CLOSED_WON` (переопределить момент закрытия) |
| — | **Отказ** | Кто закрыл; причина обязательна | из 2–5 | восстановление в 3 | `LOST` | `CLOSED_LOST` |

Исполнение (резерв, закупка, отгрузка, этапы услуг) идёт в ERP между шагами 6 и 7 и отображается карточками на экране проекта; отдельной стадии в шкале не имеет, чтобы не удлинять путь.

### 2.4. Статусы документов

| Документ | Статусы (по порядку) | Кто меняет |
|---|---|---|
| Входящее письмо | Зарегистрировано → Ждёт резолюции → Резолюция наложена / Возвращено / Отклонено | система, директор |
| КП | Черновик (отправка заблокирована) → На доработке → Одобрено (ИСХ-номер) → Отправлено → Принято клиентом / Отклонено клиентом / Срок истёк | система, директор, клиент |
| Договор | Проект → Согласован клиентом → Выставлен у оператора → Подписан (скан) / Отклонён | клиент (кабинет), бухгалтер |
| Счёт | Выставлен → Платёжка получена → Оплачен / Частично оплачен → Просрочен (по сроку, задачей) | система, клиент, бухгалтер |
| Акт | Проект → Выпущен → Подписан (скан) / Возвращён с причиной | бухгалтер, клиент |
| Служебная записка | На согласовании → Согласована / Отклонена / Возвращена на доработку → (если с оплатой) Передана бухгалтеру → Оплачена | автор, директор, бухгалтер |

### 2.5. Статусы для клиента

Одно слово в бейдже, одинаковое в боте, кабинете и письме, на языке клиента (ru/uz/en). Внутренние стадии не показываются.

| Стадия сотрудников | Клиент видит |
|---|---|
| Заявка, Резолюция, Расчёт | «Принято в работу, считаем» |
| КП отправлено | «Ждёт вашего решения» (+ срок действия) |
| Договор: проект | «Согласуйте редакцию договора» |

## 3. Процессы

### 3.1. Основной путь: от лида до оплаченного проекта

| Шаг | Кто | Модуль · экран | Действие пользователя | Система делает сама | Клиент видит / получает |
|---|---|---|---|---|---|
| 1 | Лид | Telegram-бот · веб-форма · почта · звонок | Пишет, присылает письмо на имя директора | Создаёт лида (L-NNNN), источник, язык; бот отвечает из базы знаний за секунды; для веб-формы и ручного лида бот пишет в Telegram, если контакт его дал, иначе — письмо-подтверждение | Ответ ≤ 1 мин на своём языке |
| 2 | Менеджер | CRM · Все лиды / Все сообщения | Общается из базы знаний; при запросе КП нажимает **«Создать заявку»** (боковое окно): компания (ИНН), контакт с каналом, суть, письмо, срочность | Лид → Клиент; заявка ЗВ-ГГГГ-NNN; письмо регистрируется ВХ-NNN/ГГ в EDS·Входящие; создаётся чат проекта; менеджер назначен ответственным за переписку; бот переходит в сервисный режим по этому клиенту | Бот: «Заявка ЗВ-… принята, считаем» + кнопка «Открыть кабинет» |
| 3 | Директор | EDS · Входящие · карточка письма | Читает суть письма; в боковом окне — текст резолюции, галочки исполнителей (снабженец / гл. инженер / бухгалтер), срок расчёта, «маржа не ниже»; **«Утвердить резолюцию → задание в ERP»** | Письмо уходит из Входящих (статус «Резолюция наложена»); задание в ERP·Расчёт исполнителям; уведомление + сообщение в чат проекта; стадия → Расчёт | — |
| 4 | Снабженец, гл. инженер | ERP · Расчёт · ЗВ-NNN | Подменю свёрнуто, таблица строк на всю ширину. Снабженец: сверка со складом (остаток/резерв), цена и срок поставщика, «Подтвердить». Гл. инженер: услуги, ТЗ, бригада, «Подтвердить». Кнопка «Запросить цену у поставщика» | Считает наценку/маржу по строкам и итогу; резерв на складе для позиций «в наличии»; кнопка **«Расчёт готов → черновик КП директору»** активна только при всех визах | «Принято в работу, считаем» |
| 5 | Директор | EDS · Черновик · КП-NNN | Видит КП с себестоимостью и маржой (только директор), чек-лист виз и ограничений, выбор каналов отправки; **«Одобрить КП → Исходящие»** или «Вернуть на доработку с комментарием» | КП получает ИСХ-номер и PDF без внутренних полей; уходит клиенту по выбранным каналам; появляется в Исходящих; стадия → КП·Отправлено; напоминание клиенту по сроку действия | Бот: «КП готово» + «Открыть»; кабинет: документ, «Принять» / «Отклонить с причиной» / «Комментарий»; почта: PDF |
| 6 | Клиент | Кабинет / Mini App / бот | Принимает КП (код в тот канал, где клиент), согласует редакцию договора | КП → Принято; открывается проект ПР-ГГГГ-NNN в EDS·Все проекты; ERP: резерв склада и черновик заказа поставщику на дефицит; проект договора из КП — клиенту на согласование редакции | «Согласуйте редакцию договора» → «Договор на подписании» |
| 7 | Бухгалтер | EDS · Все проекты · ПР-NNN | ВНЕ ПЛАТФОРМЫ выставляет договор у оператора; в платформе ставит статус «Выставлен у оператора» (сообщение в чат проекта и клиенту уходит автоматически); после подписи обеих сторон прикрепляет скан → «Подписан» | Журнал: кто, когда, файл; стадия → Оплата; счёт на предоплату по политике договора создаётся автоматически и ждёт выставления | Бот/почта: «Договор выставлен в … , ждём подписи»; затем «Договор подписан, выставлен счёт» + «Открыть счёт» |
| 8 | Бухгалтер, клиент | EDS · Счета и оплаты | Клиент оплачивает ВНЕ ПЛАТФОРМЫ, в кабинете/боте нажимает «Я оплатил» и прикладывает платёжку. Бухгалтер: сверяет с выпиской, **«Подтвердить оплату»** (сумма, дата) / «Частичная оплата» / «Запросить платёжку» | Счёт → Оплачен; стадия → Оплата·выполнено; ERP разрешает отгрузку; напоминания по сроку оплаты и «Просрочен» — задачей по расписанию | «Проверяем оплату» → «Оплата получена, отгружаем» |
| 9 | Снабженец, гл. инженер, бухгалтер | ERP · Склад, Расчёт; EDS · Все проекты | Отгрузка по строкам, этапы услуг; бухгалтер выпускает акт, после подписи прикрепляет скан; счёт на остаток — по факту отгрузки | Ожидаемые даты по строкам клиенту; акт подписан + счета оплачены → стадия → Выполнено; руководителю — цифры | «Выполняется» → «Ждёт вашей приёмки» → «Выполнено»; «Новый запрос» одной кнопкой |

### 3.2. Второй маршрут: внутренние документы

Служебная записка, заявление, отчёт, внутреннее письмо.

1. Сотрудник создаёт документ в EDS («Создать документ» → тип) или из сообщения в чате («Сделать служебку из сообщения» — текст и вложения подтягиваются, ссылка на сообщение сохраняется).
2. Форма: тема, кому (директор по умолчанию), текст, сумма и «нужно до» (необязательные), вложения, связь с проектом (необязательно).
3. Директор видит документ в «Моей очереди» и в EDS·На согласовании; в боковом окне маршрут и три кнопки: **«Согласовать»**, «Вернуть на доработку», «Отклонить» (комментарий обязателен при отклонении).
4. Результат уходит автору уведомлением и карточкой в тот чат, откуда документ создан; документ остаётся в EDS·Все документы с визой и датой.
5. Если в документе есть сумма — после согласования он попадает бухгалтеру в EDS·Счета и оплаты как «к оплате» с приложенным счётом поставщика.

Бухгалтер этим же маршрутом отправляет директору на согласование свои документы (реестры оплат, сверки, отчёты).

### 3.3. Исключения и ветки

- **Вернуть на доработку** (директор на шаге 5 → шаг 3): комментарий обязателен; исполнители получают задание повторно; версия КП увеличивается.
- **Отклонить заявку** (директор на шаге 2): причина обязательна; клиенту уходит вежливый ответ по шаблону; стадия Отказ, восстановление в Расчёт.
- **Клиент отклонил КП**: причина из кабинета или бота; заявка возвращается в Расчёт с заметкой; новая версия КП.
- **Срок КП истёк**: напоминание клиенту за 2 дня; по истечении — статус «Срок истёк», менеджер решает: продлить (новая версия) или Отказ.
- **Договор отклонён клиентом**: комментарий; бухгалтер правит проект; повторное согласование редакции.
- **Частичная оплата**: счёт «Частично оплачен», остаток виден; отгрузка — по политике (директор может разрешить вручную, запись в журнал).
- **Акт возвращён**: причина; задача исполнителю; повторный выпуск.
- **Назад по стадиям**: только с правом (директор) и причиной; каждый откат — запись в журнал.

### 4.3. Сопоставление с действующими системами

- CRM: `admin` → `ADMIN`; `manager` → `MANAGER`; `viewer` → отдельной роли нет (читающий доступ выдаётся как «Ч» внутри ролей выше).
- ERP: `CALCULATION` → упраздняется (расчёт делают `SUPPLY` и `ENGINEER`); `CATALOG_SUPPLY` → `SUPPLY`; `FULFILLMENT` → входит в `SUPPLY` (товары) и `ENGINEER` (услуги); `FINANCE` → `ACCOUNTANT`; `HEAD` → `DIRECTOR`; `VIEWER` → «Ч».
- `WorkspaceRoleCode` (9 «должностей») → текстовое поле «Должность» в карточке сотрудника.
- Роли обеих систем выдаются в одной карточке сотрудника (Admin · Оргструктура); провижининг переносит их в CRM и ERP.

## 5. Дизайн-система

### 5.1. Основа

Ant Design 5 + Ant Design Pro (ProLayout, ProTable, ProForm, ProCard, ProDescriptions). Полностью светлая тема. ### 5.3. Правила композиции

- Один экран — один объект и одно главное действие (кнопка primary). Второстепенные действия — default/text кнопки.
- Отступ основного окна 24 px; между карточками 16 px; внутри карточки 16–24 px.
- Таблицы: заголовок на `#fafafa`, строки 44–48 px, выбранная строка `#e6f4ff`, горизонтальная прокрутка внутри карточки (`overflow-x: auto`), никогда — прокрутка всей страницы.
- Числа — `font-variant-numeric: tabular-nums`, суммы с пробелами разрядов, валюта «сум».
- Каждая главная кнопка с переходом состояния сопровождается блоком «Что произойдёт» (3–4 строки) в боковом окне.
- Пустые состояния: статус + что здесь будет + одно действие («Заявок пока нет. Они приходят из CRM и кабинета — или создайте вручную»).
- Доступность: реальные `button`/`a`/`input` + `label`; `aria-label` на иконочных кнопках; фокус видим; таб-порядок по зонам слева направо.

## 7. Функциональные возможности по модулям

Каждый подраздел: назначение → экраны → элементы и действия → боковое окно → пустое состояние. Макеты: канвас, страница «v3 — итоговая», артборды с префиксом «v3 ·».

### 7.1. Dashboard

**Назначение.** Точка входа каждой роли: что сделать сейчас.

**Экран «Моя очередь»** (макет «v3 · 1. Dashboard»).
- Заголовок «Моя очередь», подзаголовок: роль · дата · число решений.
- Ряд счётчиков-карточек (3–4), каждая — ссылка в раздел: для директора «Входящие без резолюции», «КП на одобрение», «Служебные записки», «Проекты в работе». Набор карточек задаётся ролью (§4.1).
- Карточка «Что сделать сейчас»: список строк; строка = бейдж срока (красный «срок сегодня», золотой «завтра», фиолетовый «служебка»), заголовок действия, подпись (клиент · объект · от кого · когда), кнопка «Открыть» (primary — у самого срочного).
- Сортировка: просроченные → сегодня → по сроку. Роли с несколькими ролями видят объединённый список.
- Боковое окно: вкладки «Сегодня» (лента событий компании за день, 4–8 записей: аватар, кто, что, модуль · время) и «Уведомления».
- Пустое состояние: «Решений от вас пока не требуется. Новые письма приходят из CRM, черновики КП — из ERP, служебки — от сотрудников».

**Экран «Сводка по компании»** (директор): воронка «сообщение → оплата» за период (одна серия, горизонтальные полосы с подписями), застрявшие проекты (дни на стадии > нормы), дебиторская задолженность (просроченные счета), причины отказов. Без двойных осей, без круговых диаграмм.

### 7.2. CRM

**Назначение.** Лиды, клиенты, переписка, база знаний бота; точка создания заявки.

**Экран «Все лиды»** (макет «v3 · 2. CRM»).
- Вкладки: Все · Новые · В диалоге · Просят КП · Стали клиентами (с счётчиками).
- Фильтры: поиск (имя, компания, телефон), канал (Telegram / Почта / Веб-форма / Звонок), менеджер.
- Таблица (ProTable): Лид (имя, должность) · Компания · Канал (тег cyan Telegram / gray Почта…) · Последнее сообщение (текст, время, автор) · Статус (Новый / В диалоге / Просит КП / Без ответа / Клиент) · Менеджер · Действие.
- Действие в строке зависит от статуса: «Забрать» (новый/без ответа), «Ответить» (в диалоге), **«Создать заявку»** (просит КП, primary), «Проекты · N» (клиент).
- Клик по строке — лид в боковом окне (карточка: контакты, каналы, согласие, факты квалификации от бота, последние сообщения).
- Боковое окно «Создать заявку» (открывается по кнопке): пояснение «Лид станет клиентом, письмо уйдёт директору в EDS·Входящие, создастся чат проекта»; поля: Клиент (компания, ИНН — автопоиск в «Все клиенты»/ERP), Контакт (с каналом), Суть запроса (textarea), Письмо на имя директора (файл; подтягивается из чата), Срочность (обычная / срочная); кнопка **«Создать заявку → в EDS директору»**; подпись, что получит клиент.
- Валидации: компания и контакт с хотя бы одним каналом обязательны; e-mail не обязателен; согласие на обработку — обязательно (получено в боте или проставляется вручную с отметкой).
- Пустое состояние: «Лидов пока нет. Они приходят из Telegram-бота, веб-формы и почты — или зарегистрируйте обращение вручную».

**Экран «Все сообщения».** Входящие с SLA: передачи от бота с запиской (запрос, факты, причина, рекомендуемый шаг), таймер SLA, «Забрать». Бот молчит, пока менеджер в диалоге.

**Экран «Все клиенты» / карточка клиента 360°.** Компания, контакты (1:N) с каналами, заявки и проекты со стадией и «что видит клиент» (только чтение, данные из EDS/ERP), документы, обращения, переписка. Кнопка «Новая заявка для клиента».

**Экран «Все заявки».** Таблица всех ЗВ/ПР со стадией (7 шагов), ответственным по стадии, сроком следующего шага, статусом клиента. Фильтр «мои».

**Каналы связи.** Список каналов (Telegram-бот, почта, веб-форма, телефон) с состоянием и настройками текстов приветствий; подключение самих сервисов — в Admin.

**База знаний.** Статьи и быстрые ответы бота по категориям; кнопка «В чат» из переписки отправляет материал клиенту; правила бота «WHEN → DO» (например, цены — только из опубликованного каталога, иначе «уточню у менеджера»).

### 7.3. EDS (внутренний документооборот)

**Назначение.** Все документы компании с маршрутами и журналом: входящие письма и резолюции, КП, договоры, счета и оплаты, акты, служебные записки, заявления, отчёты.

**Экран «Входящие» → карточка письма** (макет «v3 · 3. EDS — Входящие»).
- Шкала 7 шагов (текущий — Резолюция).
- Карточка письма: номер и тема, тег статуса, реквизиты (клиент, исх. номер и дата, на чьё имя), кнопки «PDF письма», «Переслать»; суть документа (текст), подписанты, вложения; справа в карточке — связи: заявка, клиент (ИНН, история), менеджер, дата регистрации, позиции, ожидание клиента.
- Боковое окно «Резолюция»: textarea текста; галочки исполнителей с подписью зоны ответственности (снабженец — склад и цены поставщиков; гл. инженер — услуги, ТЗ, бригада; бухгалтер — условия оплаты, по умолчанию выключен); срок расчёта (дата); «Маржа не ниже, %»; кнопка **«Утвердить резолюцию → задание в ERP»**; «Вернуть менеджеру», «Отклонить» (комментарий обязателен); блок «Что произойдёт».
- Список «Входящие»: таблица ВХ-номер · тема · клиент · заявка · получено · статус · «Открыть».

**Экран «Черновик» → карточка КП** (макет «v3 · 3. EDS — Черновик КП»).
- Шкала (текущий — КП). Карточка КП: номер, тег «Черновик · отправка заблокирована», реквизиты (клиент, заявка, письмо, кто считал, дата), «Предпросмотр PDF», «История версий».
- Таблица строк: № · наименование · кол-во · цена · сумма · срок; итоги без НДС / НДС 12 % / с НДС.
- Внутренний блок (только директор): себестоимость, маржа % и сумма, условия оплаты, срок действия КП и до какой даты действует цена поставщика. Подпись: «Клиент получит PDF без этих полей».
- Боковое окно «Одобрение»: чек-лист (виза снабженца, виза гл. инженера, маржа ≥ порога резолюции, срок клиента выдержан) — каждая строка с датой и автором; «Отправить клиенту через»: Telegram-бот (контакт), Кабинет, Почта (недоступна, если e-mail не указан); кнопки **«Одобрить КП → Исходящие»**, «Вернуть на доработку с комментарием»; блок «Что произойдёт».
- Кнопка одобрения неактивна, пока чек-лист не зелёный. *Уточнение 2026-10-26 (решение архитектора по гейту C1, C1-G-1, `docs/DECISIONS.md`): строка «срок клиента выдержан» — предупреждение, а не блок: КП, готовое позже срока резолюции, директор одобряет, осознанно приняв опоздание (отметка «одобрено с опозданием» в журнале); блокируют визы и маржа; срок резолюции в прошлом не принимается.*

**Экран «Исходящие».** Реестр КП и писем с ИСХ-номером, каналами отправки, статусом у клиента (Отправлено / Принято / Отклонено / Срок истёк), «Напомнить клиенту».

**Экран «Все проекты» → карточка проекта** (макет «v3 · 3. EDS — Проект»).
- Шкала (текущий шаг — Договор / Оплата / Выполнено). Заголовок: ПР-номер, название, тег стадии для клиента; подзаголовок: клиент, сумма с НДС, менеджер, дата открытия, из какого КП. Кнопки «Чат проекта», «Написать клиенту».
- Карточка «Документы проекта»: строки КП · Договор · Счёт (предоплата) · Счёт (остаток) · Акт; у каждой — номер, тип, тег статуса, подпись-история (кто, когда, что), действие («Открыть», «Скан PDF», «Подтвердить оплату», «Прикрепить скан», «—» если документ ещё не создан; тогда подпись объясняет, когда появится).
- Ряд карточек исполнения из ERP (только чтение): Склад (резерв), Закупка (заказ поставщику, ожидаемая дата), Услуги (бригада, даты, ответственный).
- Боковое окно: вкладки «Оплата» / «Договор» (по контексту), «Чат проекта», «Журнал».
  - Вкладка «Договор»: статус; кнопки по стадии: «Отправить клиенту на согласование редакции», «Отметить: выставлен у оператора» (пишет в чат проекта и клиенту), «Прикрепить подписанный скан → Подписан»; история (редакция согласована клиентом · выставлен · подписан — с датами и авторами).
  - Вкладка «Оплата»: счёт, сумма, срок; приложенная платёжка (файл, откуда, когда); поля «Сумма по выписке», «Дата поступления»; **«Подтвердить оплату»**; «Запросить платёжку» (шаблонное сообщение клиенту в бот/почту), «Частичная оплата»; блок «Что произойдёт»; история договора.
- Список проектов: таблица ПР-номер · клиент · стадия · статус клиента · сумма · следующий шаг · ответственный; фильтры «мои», «с проблемами» (просрочки, возвраты).

**Экран «Счета и оплаты»** (бухгалтер). Таблица счетов: номер · проект · клиент · сумма · выставлен · срок · статус (Выставлен / Платёжка получена / Оплачен / Частично / Просрочен) · действие. Вкладки: К выставлению · Ждут оплаты · Платёжки на подтверждение · Просрочены · Служебки к оплате. Карточка счёта = вкладка «Оплата» из карточки проекта.

**Экран «На согласовании» → служебная записка** (макет «v3 · 3. EDS — Служебная записка»).
- Карточка: номер, тема, тег «На согласовании», реквизиты (тип, от кого, кому, дата, «создана из чата #…»); текст; таблица позиций с итогом (если есть сумма); вложения; справа реквизиты (тип, сумма, нужно до, кому и что после, источник со ссылкой на сообщение, предыдущая похожая служебка).
- Ниже — цитата исходного сообщения из чата (если документ создан из сообщения).
- Боковое окно «Согласование»: маршрут (автор → директор → бухгалтер, если сумма); комментарий (обязателен при отклонении); **«Согласовать»**, «Вернуть на доработку», «Отклонить»; «Что произойдёт».
- Форма создания (из «Создать документ» или из чата): тип, тема, кому, текст, сумма, нужно до, вложения, связь с проектом.

**Экран «Все документы».** Единый реестр с вкладками по типу (Письма · КП · Договоры · Счета · Акты · Служебные · Заявления · Отчёты), фильтры статус / период / ответственный / клиент, выбор строк, экспорт реестра. Клик — документ в боковом окне.

Правила EDS: каждый документ имеет журнал (кто, что, когда, файл); отправка КП без визы директора невозможна технически; собственные PDF никогда не называются «счёт-фактура»; сканы хранятся в S3 с версионированием.

### 7.4. ERP

**Назначение.** Расчёт по заявке, склад и резервы, закупки, справочники, документация.

**Экран «Расчёт» → расчёт по заявке** (макет «v3 · 4. ERP — Расчёт»). Подменю по умолчанию свёрнуто.
- Шкала (текущий — Расчёт). Заголовок: «Расчёт по заявке ЗВ-…», подзаголовок: клиент, письмо, срок расчёта, ограничение маржи. Кнопки «Запросить цену у поставщика», «Сохранить».
- Таблица строк на всю ширину: Позиция (название, артикул, тип: товар / товар под заказ / услуга) · Кол-во · Склад (тег «На складе · N» или «Нет · 0», ячейка, резерв) · Поставщик · срок (название, дней, подпись о квоте и сроке действия цены) · Закупка, сум (редактируемое поле) · Клиенту, сум (редактируемое) · Наценка % · Виза (тег «Склад ✓», кнопка «Подтвердить», тег «Гл. инженер · ждёт»).
- Для услуг поля закупки заполняет гл. инженер (ставка бригады, дни); снабженец их видит, но не редактирует.
- Итоговая строка: закупка, клиенту, наценка; подпись «без НДС».
- Низ карточки: подсказка о недостающих визах; кнопка **«Расчёт готов → черновик КП директору»** (неактивна, пока есть строки без визы).
- Боковое окно «Задание»: резолюция директора (цитата, дата); визы по заявке (склад / снабжение / гл. инженер — кто, статус); последние сообщения чата проекта с полем ввода; подсказка «Сделать служебку» для закупок вне КП.
- Редактирование строк: добавить строку, ИИ-разбор текста заявки в строки (предложение, подтверждает человек), сопоставление с каталогом.
- Пустое состояние: «Заданий на расчёт нет. Они приходят после резолюции директора».

**Экран «Все запросы».** Таблица заявок в ERP: ЗВ-номер · клиент · стадия · срок расчёта · визы (3 индикатора) · ответственный · «Открыть расчёт».

**Экран «Склад».** Остатки и резервы по номенклатуре (ячейка, свободный остаток, резерв под проект), заказы поставщикам (ЗП-номер, поставщик, позиции, ожидаемая дата, статус: черновик / отправлен / подтверждён / получен), приёмка от поставщика (строки), отгрузки по проектам (строки, накладная внутренняя, трек).

**Экран «Справочники».** Номенклатура (тип позиции: товар со склада / под заказ / услуга фикс / услуга по этапам / услуга по времени; единица; НДС), поставщики (квоты, сроки действия цен), бригады и исполнители услуг, клиенты-контрагенты (реквизиты).

**Экран «Документация».** ТЗ, чертежи, сертификаты, регламенты ПНР — файлы с привязкой к номенклатуре и проектам; просмотр PDF; «Отправить клиенту в чат».

### 7.5. Chats

**Назначение.** Оперативное общение: чаты проектов (автоматические), командные и личные чаты, переписка с клиентами через Telegram-бот и почту.

**Экран переписки** (макет «v3 · 5. Chats»). Основное окно делится на список чатов (280 px) и переписку.
- Список: поиск; группы «Проекты» (ПР-номер · клиент, последнее сообщение, непрочитанные), «Команда» (#каналы и личные), «Клиенты · Telegram-бот» (контакты). Подменю «Внутренний / Внешний» фильтрует группы.
- Переписка: заголовок (название, тип, участники, «Закреплённые», «Участники»); сообщения с аватаром, автором, временем; у сообщения действия «Ответить», **«Сделать служебку из сообщения»**; карточка документа внутри чата (когда служебка создана — показывает номер и статус, обновляется при согласовании).
- Внешний чат (клиент): переключатель «От себя / Как бот / Заметка команде»; подпись, куда уйдёт сообщение (Telegram · копия в кабинет · почта); быстрые ответы из базы знаний; системные строки «бот передал диалог менеджеру», «бот в сервисном режиме: отвечает по данным проекта».
- Композер: вложение, текст, «Отправить».
- Боковое окно: «О чате» (документы из этого чата со статусами, участники, краткое правило), «Документы» (для чата проекта — цепочка документов проекта), «Файлы».
- Правила: чат проекта создаётся при создании заявки, архивируется при «Выполнено»/«Отказ»; события проекта (резолюция, визы, одобрение КП, выставление договора, оплата) пишутся в чат проекта системными сообщениями; уведомления по сообщениям — по настройке сотрудника.

**Экран «Контакты».** Сотрудники (с ролями и присутствием) и контакты клиентов (с каналами); «Написать», «Создать чат».

### 7.6. Admin

**Назначение.** Роли и права, сотрудники, внешние интеграции, тикеты от команды. Админ не ведёт бизнес-процессы.

**Экран «Ролевая матрица»** (макет «v3 · 6. Admin»). Таблица: строки — модуль · раздел/действие (группами по модулям), столбцы — 6 ролей, ячейки — полный / чтение / скрыто (иконки с легендой). Клик по столбцу — роль в боковом окне: описание, «Что видит утром в Моей очереди», сотрудники с ролью, «Назначить роль сотруднику». Изменения применяются сразу, журнал — кто и когда.

**Экран «Оргструктура».** Список сотрудников: имя, должность (текст), роли (несколько), доступ к CRM/ERP (провижининг), Telegram для уведомлений, статус (активен / приглашён / отключён). Карточка сотрудника — единое место выдачи ролей обеих систем. «Пригласить сотрудника» (по почте или Telegram).

**Экран «Внешние интеграции».** Карточки сервисов: Telegram-бот (токен, канал команды, кнопка Mini App — устанавливается через Bot API), Почта (один SMTP на ансамбль; SPF/DKIM — проверка и подсказка), Хранилище файлов, Бэкапы, Модели ИИ (ключи, бюджет). У каждой: статус (пять уровней), последняя активность, «Проверить», «Переподключить», журнал. Раздел «Требует внимания». Первый запуск — чек-лист из 5 шагов баннером. Ничего из этого не настраивается через `.env`, кроме паролей инфраструктуры, доменов и ключей шифрования.

**Экран «Тикеты от команды».** Обращения сотрудников к админу (ошибка, доступ, предложение): список, статус, ответ в чат.

**Экран «Статьи компании» (W18A-P5, B-079).** Внутренние инструкции «как у нас принято» — кто согласует договор, где лежат шаблоны, график: администратор пишет их сам, в Платформе, не через репозиторий. Список (заголовок, язык ru/uz/en, «Черновик» или «Опубликовано», кто и когда изменил), «Новая статья» и редактор — заголовок, язык, текст в простом Markdown и предпросмотр тем же безопасным показом, что у Помощи (HTML и ссылки остаются текстом). Новая статья — черновик; «Опубликовать», «Снять с публикации» и «Удалить» (с подтверждением) — отдельные действия, каждое пишется в «Журнал». Пишет администратор (`admin` полный), директор читает вместе с черновиками (`admin` чтение), остальным раздела нет. Опубликованные статьи все сотрудники видят в «Помощи» (окно «?» и страница) отдельным разделом «Как у нас принято» рядом с продуктовыми статьями; общий поиск находит и те и другие; черновик не видит никто, кроме тех, кто правит раздел.

**Без переброса между экранами (волна 15 H4, UX-оценка 2026-10-27 §5 P1-6).** Мастер первого запуска: форма каждого шага
(ERP, Telegram-бот, почта, модели ИИ, первый сотрудник) открывается в боковом окне мастера, после сохранения — сразу следующий
шаг; пункт «Первый запуск» в меню — пока шаги не завершены, потом — ссылка «Настройка Платформы» в «Подключениях»; баннер
скрывается «до завтра», вернуть — в мастере. Telegram-бот настраивается в одном месте — Настройки · Telegram-бот, вкладки
«Подключение» (токен, канал команды, профиль), «Тексты», «Поведение и передача», «База знаний» (как бот пользуется базой и вход
в документы базы; в Клиентах база знаний — менеджеру на чтение), «Шаблоны ответов», «Выгрузки»; в «Подключениях» у бота —
состояние и «Настроить бота». Журнал один: фильтр «Действия людей» (аудит CRM) / «Обмен между системами» (шина; только при
полном доступе к Настройкам); журнал роли — ссылка на тот же журнал с фильтром по роли. Боковое окно закрыто по умолчанию там,
где выбирать нечего (обзор подключений, журнал без выбранной записи, мастер, бот, компания, разделы-заглушки).

## 10. Данные и интеграция с действующими системами

### 10.1. Архитектура фронтенда

- Один SPA «RailTech Platform»: React 18, TypeScript, Ant Design 5, `@ant-design/pro-components`, React Router 6, TanStack Query для данных, Zustand для UI-состояния (панели, роль, тема), i18n через `react-i18next` (ru/uz/en), формы — ProForm.
- Каркас: собственная обёртка `AppShell` над `ProLayout` — два `Layout.Sider` (рейл 64 px и подменю 208 px, `collapsedWidth=0`), правый `Layout.Sider` 360 px (`collapsedWidth=0`) или `Drawer mask={false}` на узких экранах; `PageContainer` для основного окна. Состояние панелей — в Zustand + query-параметры, сохраняется в `localStorage` per user/route.
- RBAC на фронте: `useAccess(role, resource)`; маршруты и пункты меню фильтруются по §4.2; поля с ограничением скрываются компонентом `<Restricted to={['DIRECTOR','SUPPLY']}>`.
- Шкала стадий — общий компонент `<RequestSteps stage=… />` (7 шагов, §2.3), используется на всех карточках ЗВ/ПР.
- Боковое окно — общий компонент `<ContextPanel tabs=[…] />` с вкладками Карточка · Чат проекта · Документы; экраны-действия подменяют первую вкладку.
- Таблицы — ProTable с серверной пагинацией/фильтрами, выбранная строка открывает объект в `ContextPanel`.
- Блок «Что произойдёт» — компонент `<Consequence>` с текстом из словаря действий.
- Пустые состояния — компонент `<EmptyState title action />` с текстами §7.

Предлагаемая структура каталогов:

```
src/
  app/            маршруты, провайдеры, AppShell, RBAC
  shared/         ui (ContextPanel, RequestSteps, StatusTag, Consequence, EmptyState), api-клиент, i18n, tokens.ts
  entities/       lead, client, request, project, document (letter, quote, contract, invoice, act, memo), chat, user, role
  features/       create-request, resolve-letter, calc-line-approve, approve-quote, confirm-payment, approve-memo, make-memo-from-message, toggle-panels
  modules/        dashboard, crm, eds, erp, chats, admin  (страницы и подменю)
```

### 10.2. Слой интеграции (BFF)

Фронтенд обращается к одному BFF (`/api/v1`), который агрегирует CRM, ERP, Cabinet и бот. Это позволяет не переписывать бэкенды сразу: BFF маппит старые сущности в словарь §2 и публикует события.

Ключевые эндпоинты (эскиз):

```
GET  /queue?role=DIRECTOR                      → строки «Моя очереди» (объединение источников)
GET  /leads  /leads/:id   POST /leads/:id/request   (создать заявку: lead→client, request, letter, chat)
GET  /requests/:no        (ЗВ/ПР: стадия, следующий шаг, документы, исполнение, чат)
POST /requests/:no/resolution        {text, assignees[], due, minMargin}
GET  /requests/:no/calc   PUT /requests/:no/calc/lines/:id   POST …/lines/:id/approve
POST /requests/:no/calc/complete     → черновик КП
GET  /quotes/:no  POST /quotes/:no/approve {channels[]}  POST /quotes/:no/return {comment}
POST /contracts/:no/status  {status: AGREED_BY_CLIENT|ISSUED_AT_OPERATOR|SIGNED, scanFileId?}
GET  /invoices  POST /invoices/:no/confirm-payment {amount, date}  POST /invoices/:no/request-payment-doc
POST /memos  GET /memos/:no  POST /memos/:no/decision {decision: APPROVE|RETURN|REJECT, comment}
GET  /chats  GET /chats/:id/messages  POST /chats/:id/messages {as: SELF|BOT|NOTE}
POST /chats/:id/messages/:msgId/memo   (служебка из сообщения)
GET  /notifications  POST /notifications/read-all
GET  /admin/roles  PUT /admin/roles/:code  GET/PUT /admin/users/:id
GET  /search?q=…                              (сквозной поиск по модулям)
GET  /events (SSE)                            (обновления очередей, чатов, статусов)
```

События (публикует BFF/бэкенды, потребляют очереди, чаты, уведомления, бот): `request.created`, `letter.resolved`, `calc.line.approved`, `calc.completed`, `quote.approved`, `quote.sent`, `quote.accepted`, `quote.rejected`, `contract.agreed_by_client`, `contract.issued`, `contract.signed`, `invoice.issued`, `payment.doc.received`, `payment.confirmed`, `invoice.overdue`, `act.issued`, `act.signed`, `memo.submitted`, `memo.decided`, `request.done`, `request.lost`.

### 10.4. Сущности, которых нет в действующих системах (создать)

### 11.2. Общие критерии приёмки экранов

1. Экран соответствует макету v3 по структуре зон, меню и названиям кнопок (§6.2, §7).
2. Все строки из словаря §2; ни одного старого кода стадий в интерфейсе.
3. У каждой главной кнопки есть блок «Что произойдёт» и действие реально приводит к описанному.
4. Боковое окно открывается кликом по строке без перехода; обе панели сворачиваются.
5. Пустое состояние написано словами и содержит действие.
6. Контраст текста ≥ 4.5:1 (подписи 12 px — `#767676` или темнее); все интерактивные элементы доступны с клавиатуры; у иконочных кнопок есть `aria-label`.
7. Роль, которой раздел не положен, не видит его в рейле и получает 403-экран по прямому URL с предложением написать админу (тикет).
8. Любое изменение статуса документа — запись в журнале с автором и временем.

### 11.3. Что делает владелец параллельно

ЭЦП руководителя и доступ к оператору — вне платформы, для ручной работы бухгалтера; SMTP с SPF/DKIM; BotFather (кнопка Mini App ставится системой после F0); внешнее хранилище бэкапов; утверждение ролевой матрицы §4.2 и текстов клиенту §8.
